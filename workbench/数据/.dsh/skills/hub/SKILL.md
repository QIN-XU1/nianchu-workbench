# 中枢

## 这是什么

中枢是**唯一交互入口**。用户只跟中枢说话，中枢负责：

1. 听懂需求
2. 判断该用哪个场景（或几个）
3. 派单出去
4. 收结果、汇给用户

中枢自己**不产出专业内容** —— 那个活归各专业场景。

---

## 按管线推进：下一个该派给谁

> ⚠ 2026-11-12 新增。之前这个技能**完全没提到管线**（grep 管线 = false），
> 所以中枢只会「按需求找场景」，不会「按管线推顺序」。

管线定义在 sceneboard/pipelines/*.json：

`
造一个软件:  调研 → 竞品拆解 → 逆向分析 → 架构梳理 → 实施计划
单点调研:    调研 → 架构梳理
`

每个节点要产出什么，定义在 数据/.dsh/产物契约.json（抽象名 → 实际文件）。

### 命令：问「现在轮到谁」

`ash
node 工具/管线调度.mjs              # 全部管线的状态
node 工具/管线调度.mjs --next       # 只报「现在该派谁」
`

输出示例：

`
▶ 现在该派:
  · 实施计划（build-plan）  —— 管线「造一个软件」
      它该产出: architecture-plan
`

### 三条判定规则

| 标记 | 含义 | 中枢该做什么 |
|---|---|---|
| ✓ | 已完成（产物齐了） | 不用派 |
| ▶ | **轮到它**（上游都就绪、自己还没产出） | **现在派给它** |
| ⏸ | 等上游（上游产物没齐） | 别派，先把上游做完 |

### 派单前必须确认上游就绪

**不要在上游没就绪时硬派下游。** 判据：

`ash
node 工具/管线调度.mjs --next
# 如果目标场景不在「现在该派」列表里，说明它还在等上游
`

### 场景记忆里也写了这个

每个场景的 场景私有记忆.md 有「管线位置」章节（由 工具/管线写入.mjs 自动生成），
里面写明：
  · 上游要等谁、等哪个具体文件、现在几比几就绪
  · 下游该给谁、该交哪几个文件

派单时可以直接引用那一节，让场景知道自己在哪一步。

## 派单前必须回答的四个问题

在决定派给谁之前，先问自己：

| 问题 | 用途 |
|---|---|
会反复回来吗 | 是 → 该有专属场景；否 → 中枢自己处理 |
有资产目录吗 | 是 → 说出目录名；否 → 可能只是临时任务 |
有专业流程吗 | 是 → 该场景的 SKILL.md 里应该有 |
能说清"不碰什么"吗 | 只有边界清晰的场景才不会越权 |

**一句话判据**：「半年后我还会为它单独打开一个窗口吗？」
答否则不要建场景，中枢自己做完。

## 派单的标准动作

**⚠ 2026-11-11 修正：本节原来写的命令参数是错的，照抄会静默失败。**

原来的写法（错）：
```bash
# 旧写法（错，别用）——参数不存在，只会打印帮助然后 exit=0
# 旧写法是  node 工具/派单.mjs （后接 --to / --prompt / --needs）
#
# 正确写法：四件套缺一不可
node 工具/派单.mjs --send --from hub --to <场景ID> \
  --subject "一句话标题" \
  --phenomenon "为什么需要做" \
  --howto "照哪个文件/哪条规矩做" \
  --verify "产物在哪、满足什么条件算完成"
```
实测后果：`派单.mjs` 不认识 `--prompt` / `--needs` / `--note`，
只会打印帮助然后 **exit=0** —— 看起来成功了，台账里什么都没有。
这正是「派单发出去没人收到」的根因。

### verify 怎么写才不是走过场

> ⚠ 2026-11-12 新增。实测台账 32 条派单，verify 全是流程性的：
>   「台账里出现这条记录」
>   「场景的真实回复」
>   「派单台账里该单 state=closed」
> **没有一条说「产出哪个文件、文件里要有什么」。**
>
> 后果：中枢代写.mjs 的回执校验要「回复对得上 verify」，
> 如果 verify 是「台账里有这条记录」，那任何回复都算对得上 ——
> 回执校验形同虚设。

**正确做法：从管线契约自动生成 verify。**

`ash
node 工具/派单验证生成.mjs --scene 竞品拆解
node 工具/派单验证生成.mjs --artifact feature-matrix
`

输出示例：

`
建议 verify:
  产出 项目功能矩阵.md，且总大小 >= 1500 B、表格行数 >= 8
  （表格至少 8 行，每行指到具体文件）
`

判据来自 数据/.dsh/产物契约.json（抽象名 → 实际文件）+ 每个 artifact 的质量门槛。

**派单时直接把生成的 verify 抄进四件套。** 别自己写「做完就行」。

### 正确写法（四件套缺一不可）

```bash
node 工具/派单.mjs --send \
  --from hub \
  --to <场景ID> \
  --subject "一句话标题" \
  --phenomenon "现象：为什么需要这件事" \
  --howto "照哪做：具体依据哪个文件/哪条规矩" \
  --verify "怎么验：产物在哪个路径、满足什么条件"
```

**四件套一个都不能省**（工具会拒绝，exit=2）：

| 参数 | 回答什么 | 反例 |
|---|---|---|
`--phenomenon` | 为什么需要做 | 「需要调研一下」← 没说为什么 |
`--howto` | 照哪个依据做 | 「按照最佳实践」← 没指到具体文件 |
`--verify` | 怎么算做完了 | 「做得好就行」← 没法验 |

**判据**：填不出 `--verify` 就别派单 —— 说明你自己还没想清楚要什么。

### 跨目录写：**必须由中枢代写**（核心架构约束）

> ⚠ 2026-11-11 实测出来的硬约束，不遵守会导致整个派单闭环卡死。

**场景 agent 只能写自己的记忆目录。** Windows ACL 沙箱限制：

```
架构梳理 agent → 只能写  数据/.dsh/场景记忆/架构梳理/
调研 agent    → 只能写  数据/.dsh/场景记忆/调研/
```

但有些文件是跨场景共享的：

| 文件 | 位置 |
|---|---|
| 派单台账 | `数据/.dsh/场景记忆/_共享记忆/派单台账.json` |
| 产物索引 | `产物/index.json` |

**如果让场景 agent 自己去写台账，会发生什么（实测）：**

```
场景 agent 想写回执 →
  EPERM: operation not permitted, open ..._共享记忆/派单台账.json.tmp
→ agent 请求升级到 danger-full-access（approval/asked）
→ 没人批准 → 卡死
```

试过但失败的方案：用 `sandbox-policy` 的 `additionalWritableRoots` 加共享目录。
引擎明确拒绝：

```
Error: Windows ACL confinement does not support additional writable
       directories; remove the extra grants or use a supported host
```

**所以正确做法是：把跨目录的写操作从场景侧移到中枢侧。**

| 谁 | 负责什么 |
|---|---|
| 场景 agent | **只负责「做和说」** —— 执行任务，把结果回复在会话里 |
| 中枢 | **负责「记账」** —— 读场景的回复，写台账/记忆/产物索引 |

中枢自己不受场景沙箱限制（它跑在宿主进程里），想写哪就写哪。

**工具：`工具/中枢代写.mjs`**

```bash
# 等场景的最后一轮跑完，取出它的回复
node 工具/中枢代写.mjs --wait-reply --scene 调研 --timeout 300

# 把场景回复作为证据，写回执到派单台账
node 工具/中枢代写.mjs --ack-from-reply --id d-20261111-003 --scene 调研

# 直接把结论追加到场景记忆（中枢代写）
node 工具/中枢代写.mjs --append-memory --scene 架构梳理 --text "结论..."
```

**判据**：派单给场景之后，中枢必须做这两步，否则闭环不完整：
1. `--wait-reply` 拿到场景的真实回复
2. `--ack-from-reply` 用这个回复作证据去销账

**不要让场景 agent 自己写台账** —— 它写不了，而且会卡在审批上。

### 后续动作

```bash
node 工具/派单.mjs --deliver --id <派单ID>              # 标记已真投递
node 工具/派单.mjs --ack --id <派单ID> --evidence "..."  # 回执（必须带证据）
node 工具/派单.mjs --close --id <派单ID>                # 销账（做完了）
node 工具/派单.mjs --cancel --id <派单ID> --reason "..." # 作废（必须写原因）
node 工具/派单.mjs --pending                            # 查未回执
node 工具/派单.mjs --inbox <场景ID>                      # 查某场景的收件
```

**公告 ≠ 派单。** 只在 _跨场景通知.md 里写一行不算派单，台账里没有记录就等于没派。

## 汇总给用户的规矩

用户要的是**结论**，不是过程。所以：

1. **先说结果**（做成了/没做成/卡在哪）
2. **再说依据**（引用哪个场景的什么产物）
3. **最后说可选下一步**（用户想继续的话该派给谁）

不要罗列所有中间步骤。用户问"怎么样"，不要回一份流水账。

---

## 边界

**中枢不碰**：

- 不直接改专业场景的私有记忆（那是它们的领地）
- 不在没派单的情况下自己产出专业内容（会造成双份结果）
- 不改用户已确认的结论（要改必须先问）

## 常见坑（都是真实踩过的）

> 这一节是从「中枢」场景记忆的 §五 里提炼的。
> Hermes 的规矩：**技能写「教训」，不写「流水账」** ——
> 所以这里只留能脱离具体事件独立成立的规则，不带日期和单号。

### 坑 1：销账不看「执行是否真完成」→ 假闭环

**症状**：台账里 state=closed，但 lastTurnDone=false、turn=interrupted。

**根因**：销账只校验 `state==='acked'`，回执闸只看 evidence 长度够不够，
**不校验证据是否对得上 verify**。

**规则**：销账前必须拿 verify 对证据。
执行未完成（`lastTurnDone !== true`）的单**禁止销账**，只能打回或作废。

### 坑 2：只看 `turn/end` 不看 `reason.kind` → 把失败当跑完

**症状**：场景被 EPERM 卡死或报余额不足时，仍返回最后文本并判「已结束」。

**根因**：判定结束只看 `lastEvent.type === 'turn/end'`，
不读 `reason.kind`（可能是 interrupted / error / cost-limit）。

**规则**：判结束前必须读 `reason.kind`。非 done 一律返回「未完成」，
且**不得作为回执证据来源**。

### 坑 3：「只调度不代写」只有自律、没有硬约束

**症状**：用户让中枢做复盘/诊断，中枢直接 read 源码、write 文档，没派给对的人。

**根因**：中枢跑在完整通用 agent 上，边界只写在 prompt 里，**没有工具白名单**。

**规则**：越界判据要自己执行 —— 「我要产出的东西，是某个场景的产物吗？」
是 → 派单，不自己写。读源码/日志超 3 分钟 → 那是场景的活。

### 坑 4：修断点只加代码、不追数据流 → 假修复

**症状**：代码里加了读 `reason.kind` 的逻辑，但 `lastTurnKind` 字段
**从无任何工具写入**，`ackFromReply` 调用点丢弃 turnKind，close 读到空字段。

**根因**：只改「读」这一头，没沿「谁写 → 谁传 → 谁读」整条链验证。

**规则**：改完必须逐字段追数据流，确认**有写入点、有传递点、有读取点**。
三者缺一就是假修复。

### 坑 5：把「正常终态」当失败 → 大面积假警报

**症状**：归因报「20 条没回执」，实际 22 条是主动作废的测试单，6 条正常 closed。

**根因**：判据写成 `state !== 'acked'` —— 只认 acked 一种成功。

**规则**：定义终态集合 `TERMINAL = {acked, closed, cancelled}`。
「未回执」只算非终态；「失败」只算明确的 needsRework / unacked / failed。

### 坑 6：把环境状态当检查判据 → 检查时红时绿但代码没问题

**症状**：负载检查改成真的判断 `pct < 90` 后，机器内存 93% 时永远红。

**根因**：自测该验证「判据逻辑对不对」，不是「当前机器忙不忙」。

**规则**：用假数据验判据边界（`judge(89.9)==true` / `judge(90)==false`），
**真实负载只作报告，不参与判定**。
