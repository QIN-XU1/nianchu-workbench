## 二、标准流程（五步）

### 第 1 步：清点输入

**必做：** 明确"我手上有什么"。

```
node 工具/派单.mjs --inbox arch-review
```

列出：
- 收到的派单（含上游产物路径）
- 共享层的项目清单
- 私有记忆里的历史结论

**判据：** 如果输入少于 2 路，先别下结论 —— 单路输入不叫"汇总"。

### 第 2 步：建立评估维度

**不要凭感觉选方案。** 先定 4~6 个维度。

常用维度：
```
① 可维护性     改一处要动几个地方
② 可验证性     怎么证明它对
③ 复杂度       新加入的人多久能懂
④ 依赖风险     依赖了什么外部东西
⑤ 迁移成本     从现状迁过去要多久
⑥ 性能         在什么量级下会崩
```

**判据：** 维度必须是**可判定的**（能打 1~5 分并说出理由），
不能是"好不好"这种形容词。

### 第 3 步：逐维度打分

**格式（必须表格化）：**

| 维度 | 方案 A | 方案 B | 方案 C |
|---|---|---|---|
可维护性 | 4 | 2 | 5 |
可验证性 | 3 | 5 | 3 |
... | | | |
**加权总分** | | | |

**每条打分必须附一句理由**，不能只有数字。

### 第 4 步：列出风险清单

**每个决策都要写代价。**

格式：
```markdown
| 风险 | 触发条件 | 影响 | 缓解措施 |
|---|---|---|---|
| 单点依赖 | 某服务挂掉 | 全站不可用 | 加降级开关 |
```

**判据：** 风险条目必须能回答"什么情况下会发生"。
说不出的风险 = 没想清楚。

### 第 5 步：定稿并交接

**产出：** `workbench/产物/架构方案.md`

**必须包含：**
```
① 结论（一句话）
② 选择的理由（相对其他方案）
③ 风险清单
④ 下一步（交给谁、要什么输入）
```

**交接：** 写回 §〇 交接，并派单给下游场景。

## 三、验收标准

**怎么算这次活做完了：**

```
✅ 有 ≥2 路输入
✅ 有 ≥4 个可判定的评估维度
✅ 每个打分都有理由
✅ 风险清单每条都能说出触发条件
✅ 有明确的"下一步交给谁"
```

**不达标的表现：**
```
❌ 只有结论没有理由
❌ 用"更好/更优"这种形容词
❌ 风险清单写"可能存在风险"
❌ 没有交接对象
```

## 四、常见坑（真实踩过）

### 坑 1：只汇总不判断

**表现：** 把上游结论原样搬过来，不做取舍。
**后果：** 下游拿到的是"一堆观点"，不是"一个方案"。
**避免：** 必须明确写出"我选了什么，放弃了什么，为什么"。

### 坑 2：维度不可判定

**表现：** "用户体验更好""性能更优"。
**后果：** 无法验证，等于没评估。
**避免：** 每个维度必须能打分，且每分有理由。

### 坑 3：风险清单空泛

**表现：** "可能存在兼容性风险"。
**后果：** 无法防范。
**避免：** 写清"什么操作会触发"。

### 坑 4：状态机末端没考虑（2026-11-09 新增）

**表现：** 判断只覆盖中间状态，忘了末端。
**真实案例：** 健康度统计只认 `acked`，但销账后 state 变成 `closed`，
已完成的活被算成"没回执"。
**教训：** 任何状态机判断，都要问"最后那个状态算什么"。
**更稳的做法：** 用事实字段（如 `ackedAt` 是否存在）而不是状态字符串。
