## 二、标准流程（四步）

### 第 1 步：找到"最小可证明"

**问题：** 如果只能先做一个东西，做哪个能证明整条路走得通？

**判据：** 这个"最小可证明"必须：
```
① 能在 1~3 天内做完
② 做完就能演示（不是"内部完成了"）
③ 它失败会导致整个方案重估（信息量最大）
```

**反例：** "先搭脚手架" 通常不是最小可证明 —— 因为它不能证明核心思路。

### 第 2 步：拆阶段

**原则：每个阶段必须能独立交付。**

格式：

| 阶段 | 目标 | 交付物 | 验收标准 | 依赖 |
|---|---|---|---|---|
P0 | 跑通最小闭环 | 一个能跑的 demo | 端到端能跑一次 | 无 |
P1 | 加错误处理 | 异常有明确提示 | 3 种错误都被捕获 | P0 |
P2 | 补测试 | 覆盖核心路径 | 关键路径有测试 | P1 |

**判据：**
```
❌ "完成 60%" —— 不可验收
✅ "能跑一次完整流程并截图" —— 可验收
```

### 第 3 步：列风险与预案

**每个阶段都要问：**

```
如果这个阶段卡住超过 2 倍预估时间，怎么办？
  → 降级方案是什么
  → 谁可以帮忙
  → 什么时候该重新评估
```

### 第 4 步：写交接

**产出：** `workbench/产物/实施计划.md`

**必须包含：**
```
① 阶段表（含验收标准）
② 关键路径（哪几件事决定总工期）
③ 风险与预案
④ 第一个可开工的任务
```

---

## 三、验收标准

```
✅ 每个阶段都有"能看见"的验收标准
✅ 有明确的关键路径
✅ 有"第一个可开工的任务"
✅ 依赖关系清晰（能画出 DAG）
```

**不达标：**
```
❌ 阶段没有验收标准
❌ 全是"进行中"没有完成定义
❌ 第一个任务依赖外部条件但没说谁提供
```

---

## 四、常见坑

### 坑 1：阶段切得太细

**表现：** 20 个 P0~P19 阶段。
**后果：** 管理成本 > 执行成本。
**判据：** 如果某个阶段小于 2 小时，合并进相邻阶段。

### 坑 2：验收标准不可观测

**表现：** "完成登录功能优化"。
**后果：** 无法判断做没做完。
**避免：** 写"点击 X 后 3 秒内出现 Y"。

### 坑 3：假并行

**表现：** 声称 A 和 B 能并行，但都要改同一个文件。
**后果：** 实际串行，工期估算错了。
**避免：** 并行任务必须不碰同一个文件。

### 坑 4：没有"最小可证明"

**表现：** 直接从 P0 全量搭建。
**后果：** 几个月后才发现思路不对。
**避免：** 强制先做一个 1~3 天能演示的东西。
