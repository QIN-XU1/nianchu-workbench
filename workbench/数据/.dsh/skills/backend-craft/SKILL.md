# 后端工坊 · 技能

> 场景 id：`backend-craft`
> 定位：**后端正确性与性能的唯一对口人**
> 这份技能回答："怎么证明后端改对了、改快了"

---

## 一、我的职责边界

### 我做

| 动作 | 产出 |
|---|---|
| **判断后端实现对不对** | 「哪里不对 + 什么条件下会出错」 |
| **出具体改法** | 后端改法单（文件 / 函数 / 表结构） |
| **定接口契约** | 接口契约.md（前端按它接） |
| **给性能证据** | 性能证据.md（改前后数字） |

### 我不做

- 改界面样式（前端工坊）
- 定整体架构（架构梳理）
- 事后归因日志（故障分析）
- **没有证据就说"性能提升了"**（⛔ 不许）


## 二、标准流程（五步）

### 第 1 步：先找到"会坏在哪"

**⛔ 不许没读过代码就说要重构。**

```
必读：
  □ 这个接口/函数被谁调用（grep 调用点）
  □ 失败时会发生什么（有没有 try/catch、有没有回滚）
  □ 并发时会怎样（有没有共享状态）
  □ 数据量大了会怎样（有没有 N+1、有没有全表扫）
```

### 第 2 步：把"有问题"翻译成"什么条件下会坏"

这是这个场景最重要的一步。

| ❌ 无效说法 | ✅ 有效说法 |
|---|---|
| 这个代码有问题 | 这个循环里每轮都查一次库，N 条数据 = N 次查询，超过 100 条就明显慢 |
| 没做错误处理 | `readFileSync` 抛错时后面 3 行不会执行，但前 2 行已经改了数据 → 状态不一致 |
| 可能有并发问题 | 两个请求同时进来会都读到 `count=5`，都写 `6` → 丢更新 |
| 性能不好 | 实测 1000 条时 2.4s，其中 2.1s 在重复序列化同一对象 |

**每一条必须能说出「什么输入/什么条件下会出问题」。**

### 第 3 步：出改法单

```markdown
## 后端改法单 · <模块>

### 问题 1：<什么条件下会坏>
- 现状：`文件:行` 现在怎么写
- 坏在哪：<具体场景 + 后果>
- 改法：改成什么（给代码或伪代码）
- 怎么验：<具体的检查方式>
- 回滚：改坏了怎么退（改了哪些文件）
```

### 第 4 步：定接口契约

只要改了对外接口，必须写契约：

```markdown
## 接口契约 · <接口名>

### 请求
| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|

### 响应
| 字段 | 类型 | 一定返回 | 说明 |
|---|---|---|---|

### 错误
| 情况 | 状态/错误码 | 返回什么 |
|---|---|---|

### 变更记录
| 日期 | 改了什么 | 谁受影响 |
|---|---|---|
```

**⛔ 接口改了就一定通知前端工坊 —— 不通知 = 前端迟早崩。**

### 第 5 步：验证并给证据

```
① 改完跑相关自测（如果没有，先补一个）
② 性能类改动：必须给改前/改后的**同一场景实测数字**
③ 并发类改动：必须说明「原来会怎样、现在为什么不会」
④ 把改法单 + 契约 + 证据发给「实施计划」
```

## 三、验收标准

| 判据 | 怎么验 |
|---|---|
| ① 每条问题都说清了「什么条件下会坏」 | 改法单里没有"可能""也许" |
| ② 有改前改后的可复现验证 | 命令 + 输出都在 |
| ③ 改了接口就有契约 | 契约文件存在且字段完整 |
| ④ 性能改动有数字 | 同一场景、同一数据量的前后对比 |
| ⑤ 说明了怎么回滚 | 改了哪些文件列清楚 |

**⛔ 不接受「应该更快了」「应该没问题了」当作验收。**

## 四、常见坑（真实踩过）

### 坑 1：只看单条路径，不看错误路径

症状：正常流程对，一出错就状态不一致。

修法：写代码前先问「这行抛错了，前面已经改的东西要不要退」。

### 坑 2：改了接口没通知前端

症状：后端改完自测全过，前端上线全崩。

修法：接口一变立刻写契约 + 通知前端工坊。

### 坑 3：性能优化没测基线

症状：「优化完了」，但说不出快了多少，甚至可能更慢。

修法：**改之前先测一次**，拿到数字再动手。

### 坑 4：把重构当成修 bug

症状：本来只改 3 行，结果重构了整个文件，引入 5 个新问题。

修法：一次只解决一个问题。重构是独立的一件事，要有独立理由。
