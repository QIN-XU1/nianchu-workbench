## 二、标准流程（四步）

### 第 1 步：先问"要它做什么"

**不要一上来就搜。**

```
这个调研结论会被谁用？
  → 用于做决策 → 要结论 + 置信度
  → 用于写文档 → 要出处 + 原文
  → 用于评估可行性 → 要边界条件（什么情况下不成立）
```

**判据：** 如果说不清"给谁用"，先别搜 —— 会搜出一堆用不上的东西。

### 第 2 步：分层查证

**三个层次，按可信度排序：**

| 层 | 来源 | 可信度 | 用于 |
|---|---|---|---|
**L1 一手** | 官方文档 / 源码 / 规范原文 | 高 | 下结论 |
**L2 二手** | 技术博客 / 教程 / 社区讨论 | 中 | 找线索 |
**L3 传闻** | 未署名截图 / 转述 | 低 | 只作参考 |

**判据：** 关键结论必须来自 L1。L2/L3 只能用来"知道有这么回事"。

### 第 3 步：交叉验证

**同一件事至少两个独立来源。**

```
来源 A 说：X
来源 B 说：Y
  → 一致：可信度提高
  → 冲突：标为"存疑"，两个都记
  → 只有一个来源：标为"单一来源，未验证"
```

**真实教训：**
本项目的"数字模型"我一度误判为"sessionId 指向不存在的会话"，
是因为只从一种目录命名格式判断。
换了扫描方式后才发现 10 个全部真实存在。

**教训：** 单一证据源支撑的结论，必须标注置信度。

### 第 4 步：整理成交付格式

**产出：** `workbench/产物/调研结论.md`

**必须包含：**
```markdown
## 结论

- 结论 1（置信度：高 / 依据：官方文档 §X）
- 结论 2（置信度：中 / 依据：两个博客一致，但无官方确认）

## 出处

| # | 来源 | 链接/路径 | 类型 |
|---|---|---|---|

## 存疑项

- 事项 A：来源冲突（A 说 X，B 说 Y）
```

## 三、验收标准

**达标（`check.mjs` 逐条自动验）：**

- 每张情报卡有 `对象:` 字段，且对象是**项目外部**（R2）
- 每张情报卡至少有 1 个 `https?://` 出处（R3）
- 标「置信度高」的卡必须有 ≥2 个独立来源（R4）
- 每条「猜想」五要素齐全：已知事实 / 推理链(≥2个→) / 置信度 / 可证伪条件 / 反方证据（R5）
- 每张卡有 `TTL: T1|T2|T3` 和 `复检: YYYY-MM-DD`（R6）
- 情报卡 ≤ 12 张，猜想 ≤ 5 条（R7，防注水）
- 「事实」栏不出现「本项目 / 我们的 / workbench 的」（R8）
- 有「情报卡索引」分节，且全文至少一张 Markdown 表格（R9）

**不达标：**

- 对象写成本项目路径或「我们的 xxx」（R2 直接拒）
- 结论没有 URL 出处（「据说…」）
- 猜想只给结论 + 「有待验证」
- 13 张卡 / 6 条猜想（注水）
- 把 L3 传闻写成确定结论
- 只给结论不给边界条件

**跑一遍：**
```
node 数据/.dsh/skills/research/check.mjs --check 产物/调研结论.md
```

## 四、常见坑

### 坑 1：搜了不整理

**表现：** 收藏 50 个链接，一个都没读透。
**后果：** 等于没调研。
**避免：** 每读一个就记一条结论，读完了结论也就有了。

### 坑 2：单一来源当真

**表现：** 看到一个博客就下结论。
**后果：** 那个博客可能是错的（包括官方文档也可能过时）。
**避免：** 关键结论必须两个独立来源。

### 坑 3：只报好消息

**表现：** 只写"可行"，不写"什么情况下不可行"。
**后果：** 下游踩坑。
**避免：** 强制写"边界条件"一节。

### 坑 4：不区分事实与观点

**表现：** "这个框架性能更好"（谁的结论？在什么场景？）
**后果：** 把别人的场景当自己的。
**避免：** 标注"这是 X 在 Y 场景下的结论"。

### 坑 5：单一证据源就下结论（2026-11-09 新增）

**真实案例：** 我用一种目录命名格式扫描引擎会话库，
没找到场景配置里的 sessionId，就判定"这些会话不存在"。
实际上是引擎同时用了两种命名格式（`session-xxx` 和裸 `uuid`）。
修正扫描后确认：10 个全部真实存在。

**教训：** 当结论是"某个东西不存在"时，先怀疑自己的查找方式。
