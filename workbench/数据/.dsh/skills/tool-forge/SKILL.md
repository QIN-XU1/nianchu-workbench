# 工具工坊 · 技能

> 场景 id：`tool-forge`
> 定位：**工具层的自我进化载体**
> 这份技能回答："怎么让工具自己长出来，而不是等人拍脑袋加"

---

## 一、我的职责边界

### 我做

| 动作 | 产出 |
|---|---|
| **从缺口反推需要什么工具** | 工具立项单（缺什么 + 为什么必须有） |
| **写工具** | `工具/<名>.mjs`，必须带 `--selftest` |
| **注册进体检** | 机制体检 GUARDS 里加一项 |
| **淘汰失效工具** | 工具清理单（重复/失效/该合并） |
| **记账** | 造工具账本.md |

### 我不做

- 凭"感觉应该有"就造（⛔ 必须有缺口证据）
- 造完不注册进体检（⛔ 那样它就是个孤儿）
- 造完不写 selftest（⛔ 那样它坏了没人知道）
- 改别人的场景（各自场景自己改）


## 二、核心原则：工具不是越多越好

**这个项目已经 146 个工具了。** 再造之前必须先回答：

```
① 现有工具里有没有能改的？（改一个 > 造一个新的）
② 这个缺口是"真的没人干"还是"有人干但没被发现"？
③ 造出来谁维护？（无人维护的工具 = 负债）
```

**判据：造新工具的理由必须是「有具体的、反复出现的活没人干」，不能是「标题上缺一块」。**

---

## 三、标准流程（六步）

### 第 1 步：先证明缺口是真的

⛔ **不许凭感觉立项。** 必须拿到至少一条证据：

| 证据类型 | 具体例子 |
|---|---|
| 反复手工做同一件事 | 「这周我手动查了 3 次 X，每次都是同一条命令」 |
| 事故复盘指向缺失 | 「上次故障如果有 Y 检查，10 分钟就能发现」 |
| 体检项之间有断层 | 「A 检查前半段，B 检查后半段，中间没人管」 |
| 现有工具的已知盲区 | 「某工具注释里写了『暂不支持 Z』」 |

**写进立项单：缺口是什么、证据是哪条、不补会怎样。**

### 第 2 步：查现有工具能不能改

```bash
# 先搜有没有相近的（机制清单 没有 --search，用 grep 搜）
grep -l "关键词" 工具/*.mjs
node 工具/机制清单.mjs | grep "关键词"
```

**如果能通过改现有工具解决，就不造新工具。** 在这一步结束，记一行「不造，改 XXX」。

### 第 3 步：写工具（必须满足四条）

```
① 有 --selftest，且含**反例**（喂坏输入必须判失败）
② 有只读模式（--check / --list / --scan 之一），能进机制体检
③ 判据是「差异集合」不是 0/1（能说出哪里不一致）
④ fail-open 或 fail-closed 要明确写出来（失败时怎么处理）
```

**⛔ 四条缺一条不许提交。** 缺了就是「看起来有实际是空」。

### 第 4 步：自测必须能证伪

这是最关键的一步。

```
自测里必须有至少一条：
  「喂这个坏输入 → 必须判失败」

如果所有断言都写成"应该通过"，
那这个自测就是装饰 —— 它永远不会红。
```

**验证方法：故意把判据改坏，跑一次自测，必须变红。**
（可以直接用 `node 工具/破坏性验证.mjs`）

### 第 5 步：注册进机制体检

```js
// 工具/机制体检.mjs 的 GUARDS 数组
{
  name: 'xxx体检',
  file: 'xxx体检.mjs',
  desc: '一句话说清它守什么',
  invs: 2,
  args: ['--check'],        // ← 必须是只读模式，不能是 --selftest
}
```

**⛔ 不许只注册 `--selftest`** —— 自测通过 ≠ 真实状态合格。
（机制体检的自测会检查这一点，未标 `selfOnly` 会红）

### 第 6 步：记账

写进 `造工具账本.md`：

```markdown
## <工具名> · <日期>

- 缺口：<什么活没人干>
- 证据：<哪条证据让它立项>
- 没改现有工具的理由：<查了哪些、为什么改不了>
- 判据：<守什么、怎么判>
- 反例：<喂什么必须失败>
- 注册：机制体检第 N 项
- 效果：<跑了几次、抓到过什么>
```

**「效果」这一栏最重要 —— 造完没抓到过任何东西的工具，一个季度后该考虑删掉。**

## 四、验收标准

| 判据 | 怎么验 |
|---|---|
| ① 有缺口证据 | 立项单里写了具体证据，不是"应该有" |
| ② 查过现有工具 | 写了查了哪些、为什么不能改 |
| ③ 有 selftest 且含反例 | 坏输入必须判失败 |
| ④ 有只读模式 | 能进机制体检跑真实检查 |
| ⑤ 已注册进机制体检 | GUARDS 里有它，且不是只跑 selftest |
| ⑥ 已记账 | 造工具账本.md 有它，含"效果"栏 |

**⛔ 六条缺一条，这个工具就是半成品。**

## 五、常见坑（真实踩过）

### 坑 1：造完不注册，变成孤儿

症状：工具写好了，但机制体检里没有它，永远不会被跑。

修法：第 5 步是强制的。造完立刻注册。

### 坑 2：自测全写成"应该通过"

症状：自测永远是绿的，但实际上工具可能根本不起作用。

修法：必须有一条「喂坏输入必须失败」的反例。

### 坑 3：判据只给 0/1，不说哪里不一致

症状：报"有问题"，但不说哪个场景、哪一行。

修法：判据输出**差异集合**（像 `文档体检` 那样列出漏登记的具体文件）。

### 坑 4：造了新工具但和旧的重复

症状：项目里两个工具干同一件事，结论还可能打架。

修法：第 2 步必须先查。重复的工具是「两份结论 = 早晚打架」的源头。

### 坑 5：只跑 selftest 就注册

症状：机制体检里显示通过，但实际从没检查过真实数据。

修法：注册时用只读模式参数（`--check` / `--list` / `--scan`）。
