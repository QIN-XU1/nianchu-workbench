# 故障分析 · 技能

> 场景 id：`incident-analysis`
> 这份技能记录："崩溃日志具体怎么分析"
> **所有流程都来自真实分析过 96 条崩溃日志的经验。**

---

## 一、开工前必做

### 1.1 确认数据源存在

```powershell
$f = "workbench\外壳\data\crash-log.jsonl"
if (Test-Path $f) {
    "存在，$((Get-Content $f | Measure-Object -Line).Lines) 行"
} else {
    "不存在 —— 没有数据可分析"
}
```

**如果没有数据：** 直接回执"无数据，无法分析"。
不要编造分析结果。

### 1.2 记录分析窗口

```
本次分析覆盖：YYYY-MM-DD ~ YYYY-MM-DD
总条数：N
```

**为什么：** 报告必须可复核，时间窗是复核的前提。

## 二、第 1 步：分类统计

### 2.1 按 kind 分组

```powershell
Get-Content crash-log.jsonl | ForEach-Object {
    ($_ | ConvertFrom-Json).kind
} | Group-Object | Sort-Object Count -Descending | Select-Object Name, Count
```

**判据：** 占 >50% 的那类就是主要矛盾。

### 2.2 按时间分布

```powershell
Get-Content crash-log.jsonl | ForEach-Object {
    ($_ | ConvertFrom-Json).at.Substring(0,10)   # 日期
} | Group-Object | Sort-Object Name
```

**看什么：**
- 是否某天突然增多（对应某次更新）
- 是否每天都稳定（长期存在的问题）

### 2.3 按 URL 分布（如果有）

```powershell
Get-Content crash-log.jsonl | ForEach-Object {
    $j = $_ | ConvertFrom-Json
    if ($j.url) { $j.url }
} | Group-Object | Sort-Object Count -Descending
```

**看什么：** 是否集中在某个页面 → 那个页面有 bug。

## 三、第 2 步：找模式

### 3.1 五种要找的模式

| 模式 | 判据 | 怎么验证 |
|---|---|---|
**时序** | A 崩溃前总跟 B | 看相邻两条的 kind |
**页面** | 集中在某 URL | 按 url 分组 |
**操作** | 与特定操作相关 | 看崩溃前后的日志 |
**版本** | 某次更新后开始 | 按日期分组看拐点 |
**周期** | 规律的时间间隔 | 算相邻时间差 |

### 3.2 真实发现的模式（2026-11-09 首次分析）

> ⚠ **本节是分析后回填的，不是提前编的。**
> 我在初版技能里假设"40 条崩溃全在 /chat"，
> 真实数据推翻了这个假设 —— 这正是"技能必须边做边写"的证明。

**模式 1：渲染进程崩溃占 42%，但 URL 是分散的**

证据：
```
kind 分布：
  render-process-gone    40 条（41.7%）
  child-process-gone     38 条（39.6%）
  uncaughtException      18 条（18.8%）

URL 分布（★ 与假设不符）：
  无 url 字段            56 条  ← uncaughtException + child-process-gone
  http://127.0.0.1:3080/  16 条
  http://127.0.0.1:31238/chat  8 条  ← 只有 8 条，不是 40
  千问 / 豆包 / kimi / deepseek / chatglm  各 1~4 条
```

分析：
- render-process-gone = 渲染进程崩溃
- **URL 分散在多个站点**，不是集中在某页
- **无法判断**哪个页面有 bug —— 可能只是哪个用得多

**教训：** 不能因为"某类集中在某处"就直接归因，
必须先排除"使用量差异"这个混淆变量。

**模式 2：uncaughtException 全是 EPIPE（18 条）**

证据：
```
18 条 uncaughtException，message 全部是 "EPIPE: broken pipe, write"
```

分析：
- EPIPE = 向已关闭的管道写入
- 常见于：Electron 主进程向已关闭的 renderer 发送消息
- **推断：** 进程关闭时的清理逻辑有缺陷，向已销毁的 webContents 发消息

**模式 3：child-process-gone 38 条**

证据：
```
type: "Utility"
serviceName: "network.mojom.NetworkService"
reason: "crashed"
```

分析：
- Utility 进程 = Electron 的网络服务、音频服务等
- **推断：** 这不是应用 bug，是 Electron 内部进程的正常崩溃重启
- **置信度：** 中（需要看是否影响功能）

### 3.3 找模式的反例

**不要这样写：**
```
❌ "可能是内存泄漏"（没有证据）
❌ "某个地方有 bug"（不知道哪里）
```

**要这样写：**
```
✅ "40 条崩溃全在 /chat 页面 → 那个页面有未捕获异常
    验证方法：打开 /chat，看 DevTools Console 是否有报错"
```

## 四、第三 步：归因

### 4.1 四类归因的判据

| 类别 | 判据 | 例子 |
|---|---|---|
**应用 bug** | 能定位到具体代码路径 | "第 X 行的 catch 没处理" |
**环境问题** | Electron/驱动/系统层面 | "GPU 驱动版本不兼容" |
**资源问题** | 内存/CPU/句柄耗尽 | "渲染进程超过 2GB 内存限制" |
**无法判断** | 信息不足 | "日志没有记录足够上下文" |

### 4.2 置信度标注（强制）

```
每个归因必须写：
  置信度：高 / 中 / 低
  依据：具体是什么证据

高：有明确代码路径或多个独立证据
中：有间接证据，逻辑上成立
低：只是推测，需要更多数据
```

### 4.3 铁律：不确定就说"无法判断"

**真实教训：**
我在分析中发现"40 条崩溃全在 /chat"，但**无法判断**是：
- 那个页面的代码有 bug
- 还是那是最常用的页面（所以崩溃都在那）

**区别：** 前者是缺陷，后者是概率。

**正确写法：**
```
模式：40 条崩溃全在 /chat
归因：无法判断（信息不足）
  原因：不知道各页面的访问量分布。
        如果 /chat 占 90% 的使用时间，40 条崩溃只是正常比例。
  需要：各页面的使用时长统计。
```

## 五、第四步：提建议

### 5.1 三档建议

**① 立即可做（降低影响，不需调查）**
```
例：给 /chat 页面加 React ErrorBoundary
    → 单个组件崩溃不拖垮整个页面
    → 验证：手动抛异常，页面仍可用
```

**② 需要调查（进一步取证）**
```
例：在 renderer 崩溃前 dump 内存快照
    → 需要加代码
    → 验证：下次崩溃时能拿到快照
```

**③ 可忽略（已知无害）**
```
例：child-process-gone 里的 network.mojom.NetworkService
    → Electron 网络服务崩溃后会自动重启
    → 验证：崩溃后网络功能仍正常
```

### 5.2 每条建议的格式

```markdown
### 建议 N：<标题>

- 做什么：<具体动作>
- 为什么有效：<机制解释>
- 怎么验证：<可观察的结果>
- 代价：<有什么副作用>
- 归属：<该派给哪个场景>
```

**"归属"这一栏很重要** —— 我只提建议，不自己改。
必须说清"这个建议该谁做"。

## 六、真实分析示例（2026-11-09）

### 6.1 数据概览

```
总条数：96
时间范围：2026-11-06 ~ 2026-11-09
数据源：workbench/外壳/data/crash-log.jsonl
```

### 6.2 分类统计

| kind | 数量 | 占比 |
|---|---|---|
render-process-gone | 40 | 42% |
child-process-gone | 38 | 40% |
uncaughtException | 18 | 19% |

### 6.3 发现的模式

**模式 1：3 天内 96 次崩溃（平均每天 32 次）**

- 证据：96 条 / 4 天
- 影响：如果用户每天用 4 小时，约每 7 分钟崩一次（渲染进程）
- **置信度：高**（数据直接支持）

**模式 2：所有 render-crash 都在 /chat**

- 证据：40 条 url 全是 `http://127.0.0.1:*/chat`
- 归因：**无法判断**
  - 可能是 /chat 有 bug
  - 也可能是 /chat 是唯一被使用的页面
- 需要：页面使用时长统计

**模式 3：EPIPE 全部是向已关闭管道写**

- 证据：18 条 message 全部 `EPIPE: broken pipe, write`
- 归因：**应用 bug（置信度：中）**
  - 常见于向已销毁的 webContents 发消息
  - 修复方向：检查 `webContents.send` 前是否 `isDestroyed()`

### 6.4 建议

**立即可做：**

1. **检查所有 `webContents.send` 调用是否判空**
   - 做什么：在发送前加 `if (!wc.isDestroyed())`
   - 为什么：解决 18 条 EPIPE
   - 怎么验：EPIPE 数量下降
   - 归属：开发场景

2. **给 /chat 页面加错误边界**
   - 做什么：加 ErrorBoundary 包裹主要组件
   - 为什么：单个组件崩溃不拖垮整个渲染进程
   - 怎么验：手动抛错后页面仍可用
   - 归属：开发场景

**需要调查：**

3. **加渲染进程内存监控**
   - 做什么：定期记录 `process.memoryUsage()`
   - 为什么：确认是否 OOM 导致崩溃
   - 怎么验：崩溃前是否有内存尖峰
   - 归属：开发场景

**可忽略：**

4. **child-process-gone 里的 NetworkService**
   - 为什么可忽略：Electron 会自动重启该服务
   - 验证方法：崩溃后网络功能正常
   - 建议：可以降低该日志级别，避免噪音

### 6.5 数据不足的地方

```
① 不知道各页面使用时长 → 无法判断 /chat 集中是否异常
② 不知道崩溃时的内存占用 → 无法确认 OOM
③ 不知道 Electron 版本 → 无法判断是否为已知问题
④ 没有崩溃堆栈 → 无法定位具体代码行
```

**这四条是最重要的输出** ——
它们告诉下一步该补什么数据。

## 七、常见坑

### 坑 1：把"最常见"当"有问题"

**表现：** 崩溃全在某页面 → 判定该页面有 bug。
**实际：** 可能只是那个页面用得最多。
**避免：** 必须除以使用量。

### 坑 2：不看基线就说"变多了"

**表现：** "今天崩了 20 次，很严重"。
**实际：** 平时也是 20 次。
**避免：** 先算历史平均。

### 坑 3：把环境问题当应用 bug

**表现：** EPIPE 当代码 bug 修。
**实际：** 可能是 Electron 进程生命周期管理的正常现象。
**避免：** 标注置信度，不确定就说不确定。

### 坑 4：报告只有结论没有证据

**表现：** "建议优化性能"。
**实际：** 无法执行。
**避免：** 每条建议必须能回答"做什么/为什么/怎么验"。

## 八、真实分析的关键发现（2026-11-09 补充）

### 8.1 崩溃数在下降（重要但需谨慎）

```
11-06: 40 条
11-07: 33 条  (-17.5%)
11-08: 20 条  (-39.4%)
11-09:  3 条  (仅到 05:41，不完整)
```

**这条发现的陷阱：**
11-09 数据不完整，不能直接说"降了 92%"。
必须等完整一天的数据。

### 8.2 child-process-gone 里 68% 是正常的

```
NetworkService   19 条  ← 正常（自动重启）
GPU               9 条  ← 需关注（可能白屏）
AudioService      7 条  ← 正常（自动重启）
VideoCapture      3 条  ← 需关注（摄像头）
```

**这条改变了整个分析的重点：**
38 条 child-process-gone 里 26 条可以忽略，
真正需要看的只有 12 条。

**判据：** 分析前先做"可忽略过滤"，否则会被噪音淹没。

### 8.3 崩溃成簇发生

```
render-process-gone → render-process-gone   18 次
child-process-gone  → child-process-gone    18 次
uncaughtException   → uncaughtException     16 次
```

**含义：** 一次崩溃往往引发连锁。
所以"96 条崩溃"可能只对应"20 次事件"。

**这条的重要性：**
如果按"条数"评估严重性会高估。
应该按"事件数"评估。

### 8.4 数据缺口比结论更重要

真实分析后列出的 6 个数据缺口：
```
① 各页面使用时长
② 崩溃时内存占用
③ 崩溃堆栈
④ Electron 版本
⑤ 用户使用时段
⑥ 同次会话的崩溃数
```

**这 6 条中的任何一条，都可能推翻前面的结论。
所以报告里必须单列一节"数据不足的地方"。**

## 九、第二次实战补充（2026-11-09 GPU 专项）

> 这一节是做完 GPU 专项分析后回填的。
> 记录了**四个方法论教训**，比具体结论更重要。

### 教训 1：聚合统计必须与逐条计数交叉验证

主报告写「GPU 崩溃 9 条」，逐条数是 **10 条**。

原因：主报告用的是「按 (type, serviceName) 分组」，
那个分组在某个时刻显示 9，但逐条数应为 10。

**新规矩：**
```
报告里的每个数字，必须用两种方法各算一遍：
  ① 聚合分组求和
  ② 逐条过滤计数
两者不一致 → 说明统计逻辑有 bug，先修统计再分析
```

### 教训 2：推测必须被数据检验，否则会修不存在的问题

主报告推测：「GPU 崩溃可能导致渲染异常（白屏/花屏）」

**验证方法：** 检查每条 GPU 崩溃后 60 秒内是否有 render-process-gone

**结果：** 1 / 10

**结论：推测被否定。** GPU 崩溃与渲染崩溃基本无关联。

**如果没有做这个验证会怎样：**
```
我会建议「去修 GPU 崩溃导致的渲染问题」
→ 开发花时间排查
→ 实际上两者无关
→ 白干
```

**新规矩：**
```
任何「A 导致 B」的推测，必须找出可验证的判据。
找不到判据 → 标为「推测，未验证」，不建议据此行动。
```

### 教训 3：区分「有崩溃」和「有影响」

```
事实：10 条 GPU 崩溃
另一件事：这 10 条有没有影响用户
```

**不能把「有崩溃」直接当成「有问题」。**

Electron 的很多子进程（NetworkService / AudioService / GPU）
崩溃后会**自动重启**，用户完全无感。

**新规矩：**
```
评估严重性时，必须区分：
  · 崩溃次数（客观数据）
  · 用户可感知的影响（需要额外证据）
只有后者才决定优先级。
```

### 教训 4：「无法确认」是最诚实的输出

8.5 节我写的是：
```
「我无法确认 GPU 崩溃的实际影响，因为：
  · 没有用户反馈数据
  · 没有 GPU 进程重启记录
  · 没有渲染帧率数据
所以『影响评估』这一节是空的。」
```

**这是那一节最重要的部分。**

如果编一个「可能影响性能」，
下游会当成事实去排查一个不存在的问题。

### 一个意外发现：特殊错误码

```
exitCode = -2147483645 = 0x80000003 = STATUS_BREAKPOINT
```

这是 Windows 断点异常，**不是普通崩溃**。

其余 9 条 exitCode = -1（进程被强制终止）。

**新规矩：**
```
遇到不寻常的 exitCode，先查它是什么，不要一律当「崩溃」处理。
常见的：
  -1         = 被终止
  0x80000003 = 断点异常（调试相关）
  0xC0000005 = 访问违例
  0xC0000409 = 栈溢出/安全 cookie
```

做完分析前，逐项自问：

□ 有没有把「有崩溃」当成「有影响」？
□ 「无法确认」的部分，有没有诚实写出来？
