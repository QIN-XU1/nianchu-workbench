# 检查有效性复盘

> 场景：自我复盘（self-review）· 日期：2026-11-12
> 素材：机制体检 51 项、整体体检 15 项、事故档案 25 条、体检结果.json

## 1. 检查项总数

| 工具 | 检查项数 | 说明 |
|---|---|---|
| 机制体检 | 51 项 | 一次跑完 51 个哨兵（记忆/身份/派单/越界/健康/进化/内容/…） |
| 整体体检 | 15 项 | 端到端：workspace 注册 / 面板可输入 / 真实发消息 / 调度链路 |
| **合计** | **66 项** | |

## 2. 历史：这些检查实际抓到过多少真问题

**先分清「谁抓到的」，这比「抓到了多少」更关键。**

本项目历史上有 25 条事故档案记录 + 若干未入档问题。把它们按「发现者」归类：

| 发现者 | 抓到的真问题 | 代表 |
|---|---|---|
| **整体体检（端到端）** | 工作区没注册（9 面板停在「选择工作区」页）· hub SKILL 派单命令参数错（--prompt/--needs 不存在）· 8 场景主面板是「待接入」占位 | 真正架构级问题 |
| **机制审计（五步法元检查）** | 内容哨兵是「装饰」永远 PASS · 5 个核心哨兵全没自测 | AC-001 / AC-002 |
| **机制体检 51 项（正常运行报警）** | 几乎为零 | 详见下 |

**核心事实：25 条事故里，真问题几乎全是「机制审计」和「整体体检端到端」抓出来的，而那 51 项机制体检在正常运行中，几乎没有主动报警抓到过一个功能 bug。**

## 3. 有效性比率

**判据：真问题数 / 检查项数。**

- 朴素算法：25 条事故 ÷ 66 项 ≈ 0.38（每 2.6 项检查才摊到 1 个问题）。
- 但更该算的是：**「检查项自己报警抓到的」÷ 66 ≈ 0**。51 项机制体检几乎没有主动 FAIL 过一次、抓到一个真 bug。

比值极低 → **按判据，检查设计有问题。而且比「低」更糟。**

## 4. 设计问题在哪（三层）

**① 检查项不是「真问题逼出来的」，是「移植来的」。**
翻 51 项机制体检的 desc，约 2/3 写的是「视频 BVxxx」「参考项目 01/02/…」，是从参考项目的清单里**搬**过来的。它们防的是**别人踩过的坑**，不一定是**本项目会踩的坑**。真正被本项目真实事故逼出来的，屈指可数：健康度计算、健康哨兵、经验真实性、章节唯一性、三方一致、文档命令体检、机制审计/机制清单。

**② 移植来的检查没配反例，成了「只会 PASS 的装饰」。**
AC-001/AC-002 证明：连最核心的 5 个哨兵都从没被证明「会失败」——它们每轮体检都 PASS，但「真实数据通过」只能证明「现在没违规」，不能证明「有违规时它会报」。「41/41 通过」这个数字，其实 17 项从未被证明会失败，给的是**虚假的确定感**。

**③ 真正能抓问题的，恰恰是「元检查」和「端到端」，不是被统计的那 51 项。**
机制审计（查「检查本身有没有反例」）和整体体检（真发一条消息），这两个「少而狠」的检查，抓到了本项目全部架构级问题。而「多而全」的 51 项，是数字好看、抓不到东西的摆设。

## 5. 结论

检查工具**「在防问题」这件事，效果很弱**——但原因不是「检查太少」，而是**「检查的合法性来源错了」**：

- 大多数检查项是**移植**的，不是**本项目真实事故长出来**的；
- 移植来的又**没配反例**，成了只会 PASS 的装饰；
- 于是「检查项数」和「真问题数」脱节，比值判据一算就露馅。

**一句话：检查不是越多越好。一个「带反例、真的会失败、抓到过真问题」的检查，顶十个「只会 PASS 的装饰」。本项目 66 项里，前者只有个位数。**
