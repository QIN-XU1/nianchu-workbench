# 中枢代写方案复盘

> 场景：自我复盘（self-review）· 日期：2026-11-12
> 对象：「因为 Windows ACL 沙箱不让场景写跨目录，所以改成中枢代写」这个方案对不对
> 依据：`工具/中枢代写.mjs`（399 行）、`工具/闭环验证.mjs`、`工具/派单.mjs`、
> 　　　`数据/.dsh/场景记忆/中枢/中枢设计评估.md`、`调研/场景私有记忆.md`、`事故-DSH沙箱工具失效.md`

## 0. 结论先说

**方案「方向对，实现错」。**

- **对的一半**：跨目录写确实不能由场景做 —— 沙箱把它堵死了，这条事实成立（见 §1 的引擎原文）。
- **错的一半**：由此推出「所以中枢要读场景的聊天回复来记账」，并把这个工具一路扩到 `--append-memory`（中枢直接写别的场景的记忆）。这一步越过了中枢自己的边界，而且**前提本身可以推翻**（§3 方案 C）。

## 1. 这个方案成立的前提，是真的

`中枢代写.mjs` 头部写得很清楚，且是实测过的：

```
用 sandbox-policy 的 additionalWritableRoots 加共享目录
→ 引擎明确拒绝：
  「Windows ACL confinement does not support additional writable
    directories; remove the extra grants or use a supported host」
```

外加现场证据：场景 agent 想写回执 → `EPERM` → 请求升级 `danger-full-access` → 没人批准 → **卡死，闭环永远走不完**。

**所以「场景写不了共享目录」是真的，不是拍脑袋。** 方案的出发点是诚实的。

## 2. 代价：中枢额外要干多少事

### 2.1 一个闭环 = 中枢要做 5~6 步，且全是串行阻塞

`闭环验证.mjs` 把一个完整闭环拆成 6 步，其中**中枢侧要执行 5 条命令**：

| 步 | 命令 | 中枢的负担 |
|---|---|---|
| ① | `派单.mjs --send`（四件套 4 个参数） | 中枢要会写 phenomenon/howto/verify |
| ② | `投递通道.mjs --to` | 中枢要自己去投 |
| ③ | `中枢代写 --wait-reply --timeout 180~300` | **阻塞等待**，2.5 秒轮询、要连续 2 轮 idle 才退出 |
| ④ | `中枢代写 --ack-from-reply` | 中枢要判断这段文本算不算证据 |
| ⑤ | `派单.mjs --close` | 中枢自己销账 |

**关键代价不是「多做几步」，是「中枢被钉在等待上」。** `--wait-reply` 是同步阻塞的：一次派单，中枢就有一整个轮次不能干别的。9 个场景并行派活时，这条路径的吞吐上限是「一次一个」，且最坏每次 300 秒。

### 2.2 中枢被迫自己实现一套「信任判定」

场景的产出不是交给中枢的文件，而是**一段聊天文本**。所以 `中枢代写.mjs` 里不得不长出 60 行启发式（第 266–315 行）：

- 兜底话术黑名单：`不知道 / 没做 / 无法完成 / 失败 / 报错 / 没有权限 …`
- 从 `verify` 里正则抽 `*.md|json|mjs` 文件名，要求回复里出现

**这是「代理指标」的典型形态** —— 中枢看不到产物，只能靠字面匹配猜「它到底干了没有」。而它自己注释就承认了这种猜法的失败案例：

> 实测佐证：台账里 `d-20261111-006` 的 receipt 是「我是调研场景：左边搜网页，右边 AI 帮你收拢…」
> —— 这是自我介绍，跟派单要求的 verify 毫无关系，却过了闸。

**更难看的是 `闭环验证.mjs` ② 步现在仍然这样写：**

```js
const msg = '【不需要回执·知悉】请用一句话回答：你是什么场景，负责什么。'
```

**「验证中枢代写方案跑得通」的那条端到端验证，证据就是一句自我介绍。** 如果 `verify` 文本里恰好不含文件名（本次就不含），正则抽不到 key，`verifyOk` 保持 true —— 自我介绍依然过闸。**这条工具测的是「消息能通」，不是「活干完了」。**

### 2.3 它越界了：中枢开始写别人的记忆

`--append-memory` 干的正是「场景自己的记忆自己写」的反面。**不是假设，有实锤：**

```
数据/.dsh/场景记忆/调研/场景私有记忆.md:129
<!-- hub-write: 2026-11-11 15:39 -->
- [2026-11-11 15:39] 实测：沙箱不支持 additionalWritableRoots，跨目录写必须由中枢代写
```

这与项目自己的偏好/铁律直接冲突：

- 六类偏好第 5 条：「中枢只调度不代写；场景自己的记忆自己写」（`工具/偏好记忆.mjs:364`）
- `工具/自动回执.mjs:248` 引用的原话：「场景自治：别人只能提醒，不能代写」

**同一个词「代写」，在项目里同时是「必需方案」和「禁止行为」。** 这不是命名混乱，是边界被方案本身吃掉了：为了「记账」不得不读回复，为了「读回复」不得不信文本，为了「信文本」不得不代写。

### 2.4 代价还有「bug 税」，而且这些 bug 全由方案本身制造

`中枢代写.mjs` 里标了 ≥3 处断点修复，三类全是**假闭环**：

| 断点 | 症状 | 为什么是这个方案才有的问题 |
|---|---|---|
| 断点 3 | 同场景多会话，`find()` 取第一个 → 投到旧会话、读到旧回复 | 中枢要去「猜」场景的会话 |
| 断点 6 | 只看 `turn/end` 不读 `reason.kind` → 被 EPERM 卡死、余额不足、报错中断的 turn 也算「跑完了」→ 半截文本当证据 | 中枢要从事件流反推「它到底跑完没」 |
| 断点 7 | 前 200 字非空就当证据 → 自我介绍也能销账 | 中枢没有产物，只有文本 |

**这三条都不是实现粗糙，是「把写操作挪到中枢、于是中枢必须重建信任」这个设计的必然产物。** 台账 `d-20261110-008/009/010` 三条 `state=closed` 但 `lastTurnDone=false`、`turn=interrupted` —— 就是假闭环的实证。

### 2.5 最贵的一笔：方案事实上半弃用

`中枢设计评估.md` 给出：

> 「派单 … 名存实弱。手工 CLI，agent 实际用引擎 `task` 工具派活，不落台账」
> 「台账 24 条里 13 条测试、4 条真业务；台账只有 4 条真业务闭环」

**即：花了 399 行工具 + 6 步流程 + 3 次断点修复，换来 4 条真业务闭环，而中枢真实派活根本不走这条路。** 按代价/收益算，这笔账是负的。

## 3. 有没有更好的方案

先按「判据：说方案对就要说清别的为什么不行」逐条摆。

| 方案 | 做法 | 能否采纳 | 理由 |
|---|---|---|---|
| **A. additionalWritableRoots** | 给共享目录加可写白名单 | ✗ **已被引擎堵死** | 引擎原文拒绝：「Windows ACL confinement does not support additional writable directories」。不是没试，是试过并回滚。 |
| **B. 换沙箱后端**（`dsh-sandbox-local`，不用 ACL） | 场景直接能写跨目录，中枢代写整个不要了 | △ **能跑通但不可取** | 代价是**隔离消失**：9 个场景可以互写记忆、可以碰私人数据。项目铁律「隔离本身是规矩的一部分」，为省事拆掉隔离是用设计目标换开发便利。 |
| **C. 分片记账（建议）** | 把共享文件「放到场景写得了的地方」：每个场景把自己那份写进**自己目录**，如 `调研/回执/d-xxx.json`；中枢只**读**这些分片，聚合出索引/台账 | ✓ **最该试，且没试过** | 见下 |
| **D. 保留代写但砍掉越界部分** | 删掉 `--append-memory`，只留记账；改名「中枢记账」 | △ 补丁 | 只能治 2.3，治不了 2.2 的「信文本」和 2.4 的断点税 |

### 为什么 C 更好（这是本复盘的核心判断）

**原方案隐含一个没被检验的前提：「共享文件必须放在一个共享目录里，所以场景写不了，只能中枢代写。」**

这个前提是可以推翻的。ACL 约束是「场景只能写自己目录」；那就**把「谁写」迁就「谁能写」**：

```
原：  scenes ──EPERM──>  _共享记忆/派单台账.json   ← 中枢代为写入
改：  scenes ──OK──>     调研/回执/d-xxx.json        ← 场景自己写
                         _共享记忆/台账索引.json     ← 中枢只读聚合（唯一写者=中枢）
```

C 在三件事上严格优于原方案：

1. **证据从「聊天文本」变成「结构化产物」。**
   `回执.json` 里带 `dispatchId / 产物路径 / 文件 SHA / 自检结果`，中枢不需要黑名单猜话术，也不需要正则匹配 verify 关键词。2.2 的整类假闭环**不在于实现，而在于失去存在理由**。
2. **恢复「单写者」原则。**
   AGENTS §4 写着「同一文件不许两个写入者」。原方案里中枢代写正是**第二个写者**；C 里每份分片只有场景一个写者，聚合索引只有中枢一个写者 —— 反而更合规。
3. **不越界。** 中枢回到「只调度、只读、只聚合」，2.3 的偏好冲突自动消失，不需要靠 prompt 自律。

C 的真实成本（要说清，不能只说好处）：
- 台账要从单文件变多分片，需要一个聚合器（约等于把 `派单.mjs` 的一部分拆成读侧）；
- 场景仍可能写一份「假回执」—— 但它此时是**以自己名义作出的虚假声明**，可审计、可追责；而原方案里中枢是**转述者**，连归因都模糊；
- 需要一次性迁移已有台账（24 条）。

## 4. 判定

**方案对错要分开答：**

- **「跨目录写不能由场景做」—— 对。** 有引擎拒绝原文，有 EPERM 实测，有回滚记录，这条不冤。
- **「所以中枢要读场景的聊天回复来记账」—— 不对。** 这是从约束跳到了实现，中间跳过了「换个地方放文件」这一步。
- **「所以中枢可以写场景的记忆」—— 明确错。** 与项目自己的偏好第 5 条正面冲突，且已发生 1 次（`调研/场景私有记忆.md:129`）。

**为什么别的方案不行（判据要求的正面回答）：**
- A 不行 —— 引擎在 Windows ACL 模式下**根本不支持**，不是配置问题，是模式限制，试过并回滚。
- B 不行 —— 它能解决写权限，但**代价是拆掉场景隔离**，而这个项目的设计前提就是「场景是地盘，不许越界」「私人数据永不进共享层」。用隔离换便利，不划算。
- 所以剩下的不是「代写 vs 不改」，而是「代写 vs 分片记账」。**原方案从来没把 C 摆上桌** —— 它把「共享文件必须在共享目录」当成了不可议的公理，于是只能得出「中枢代写」。这是这次复盘最该记住的地方：**约束是真的，但结论不是唯一解。**

## 5. 建议动作（不急，供排期）

1. **立刻**：删掉 `中枢代写.mjs --append-memory`，或改成「只写给中枢自己的日志」。这条越界已发生一次，且有偏好明文禁止。
2. **短期**：把 `中枢代写` 改名「中枢记账」，并在 skill 里写清它只碰台账/索引，不碰场景记忆与专业内容。
3. **中期**：做 C 的最小可行版 —— 先只让「调研」一个场景写自己的 `回执.json`，中枢读它销账，跑通再接其余 8 个。
4. **判据**：C 成功的标志不是「体检全绿」，而是**台账里的 `receipt` 从一段散文变成一个带 hash 的产物引用**。
5. **别忘了**：`闭环验证.mjs` ②步现在用「你是什么场景」当探针，测出来的是连通性，不是闭环。改成「让场景产出一个真文件」再验。
