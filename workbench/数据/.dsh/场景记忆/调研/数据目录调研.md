# 数据目录调研 —— 目录结构、命名、职责重叠

> 场景：调研｜方法：逐个列出 `workbench/数据/` 与 `数据/.dsh/` 的目录与关键文件，读路由表/画像/归档索引等权威文件，对比命名与职责。只看目录事实。

## 一、全貌（目录及用途）

### 1. 数据/ 顶层（3 个）

| 目录 | 用途 |
|---|---|
| `.dsh/` | **主数据根**（真身，一切场景记忆/配置/档案都在这） |
| `.dsh-temp/` | 临时/锁目录：`dsh-XXXXXX` 随机临时、`dsh-acl-locks`、`dsh-acl-skill-*` |
| `.dsh-tui/` | TUI 子应用的**独立数据根**，自带 profiles/storages/temp（与主 .dsh 平行） |

### 2. 数据/.dsh/ 根级散文件（10 个）

| 文件 | 用途 |
|---|---|

| `场景层级.yaml` | 主/子场景层级（root/main/sub） |

| `机制清单.md` / `机制盲区.json` | 机制注册表 |

| 组 | 目录 | 用途 |

## 二、命名不一致 & 职责重叠

### 命名不一致

**① 场景命名两套系统并存（最核心问题）**

同一个 9 个场景，两套命名各管各的目录：

| 英文 id（权威路由表用） | 中文名 | 用在哪 |
|---|---|---|
| hub / research / arch-review / build-plan / competitor-analyze / incident-analysis / pc-cleanup / reverse-eng / self-review | 中枢 / 调研 / 架构梳理 / 实施计划 / 竞品拆解 / 故障分析 / 本地电脑 / 逆向分析 / 自我复盘 | — |

- **英文 id** 用在：`skills/`、`场景注入/`、`sessions/`、`_共享记忆/areas/`
- **中文名** 用在：`场景记忆/`、`项目记忆/`、`影子记忆/`、`封存集/`、`画像/副画像/`

映射关系不直观（hub=中枢、pc-cleanup=本地电脑、incident-analysis=故障分析、self-review=自我复盘），只有 `场景路由.yaml` 一份权威表能对上；目录结构自己「各说各话」，靠人脑查表翻译。

**② `AGENTS.local.md` 两处重复且内容不一致**

- `场景记忆/调研/AGENTS.local.md`（1157 字节）
- `场景注入/research/AGENTS.local.md`（1059 字节）

两处同名同角色、内容却不同，谁权威不清。

**③ 「画像」一词三种含义混用**

| 文件 | 实际含义 |
|---|---|
| `画像/主画像.md` | 用户主画像（只中枢/自我复盘能写） |
| `场景记忆/<场景>/场景画像.md` | 场景**界面**画像（UI 长啥样，自动生成） |
| `画像/副画像/<场景>.md` | 场景对**用户**的观察补充 |

三个都叫「画像」，但一个是「用户的画像」、一个是「界面的画像」、一个是「场景看用户的画像」。

**④ 快照/归档类命名重叠，五个容易混**

`归档层`、`封存集`、`影子记忆`、`回滚快照`、`_共享记忆/基线历史` —— 都是「历史副本」，但用途不同（档案/评估/验证/回滚/基线），名字彼此擦边。

### 职责重叠

**① 一个场景有 5+ 份「关于它自己」的文件**

`场景私有记忆.md`（职责/坑/交接）+ `项目信息.md`（现状/接口）+ `身份卡.md`（我是谁）+ `场景画像.md`（界面）+ `副画像/<场景>.md`（看用户）。边界靠约定，易漂移。

**② 场景记忆目录被当通用工作区**

`场景记忆/调研/` 里，真记忆文件（场景私有记忆/身份卡/画像）和**调研产出报告**（工具真实性调研.md、文档代码一致度.md、文档修复验证.md、机制体系索引.md）混放，模糊了「记忆」与「产出」的界线。

**③ 项目记忆「剥离」不彻底**

`记忆精简.mjs` 把项目信息剥离到顶层 `项目记忆/<场景>/`，但 `场景记忆/调研/` 里仍残留**空的 `项目记忆/` 和 `归档/` 子目录**；且 `归档层/project/` 几乎同时在归档同一批文件 —— 同一份项目信息出现在三处。

**④ 空/残留目录**

`MCP/`、`缓存/`、`场景记忆/<场景>/项目记忆/`、`场景记忆/<场景>/归档/` 均为空。

## 三、应该怎么组织（建议）

1. **场景目录名只留一套，另一套靠路由表查。** 建议全项目统一用英文 id 做目录名（skills/场景注入/sessions 已经是），`场景记忆/`、`项目记忆/`、`影子记忆/`、`封存集/`、`画像/副画像/` 也改成英文 id；中文名只作为 `场景路由.yaml` 里的显示字段。不要靠目录结构「各说各话」。

2. **`AGENTS.local.md` 单一来源。** 定 `场景注入/` 为编译产物（build 时从某处生成），`场景记忆/<场景>/` 里的删掉或改成指针，消除双份漂移。

3. **记忆类收敛为「每场景三件」，画像出列。** 每场景只留：`场景私有记忆.md`（职责/坑/交接）、`项目信息.md`（现状/接口）、`身份卡.md`（我是谁）。`场景画像.md` 是 UI 生成物，挪到 `画像/` 统一管，别和记忆混。

4. **产出与记忆分离。** 调研报告/机制索引这类**产物**从 `场景记忆/<场景>/` 挪到独立的 `产出/` 或 `<场景>/成果/`，记忆目录只放记忆。

5. **快照/归档收敛成三层并写清边界。** 回滚快照（操作级）、归档层（单向档案+哈希）、影子记忆/基线（验证级）；`封存集` 单列并注明「Agent 不可见」，名字别和「归档」混。

6. **清掉空/残留目录。** MCP、缓存、`场景记忆/<场景>/项目记忆`、`场景记忆/<场景>/归档`，该删删、该归位归位。

---

## 结论

数据结构**没有失控，但命名和职责已经出现明显的双轨与重叠**：核心是「英文 id vs 中文名」两套命名并行，以及「记忆/画像/档案/快照」多个概念各自建目录、边界靠约定。当前靠 `场景路由.yaml` 一份权威表兜底还能查对，但目录本身不自我说明，新人或新场景极易写错位置。建议优先做第 1、2 条（统一命名 + AGENTS 单一来源），收益最大、改动最小。
