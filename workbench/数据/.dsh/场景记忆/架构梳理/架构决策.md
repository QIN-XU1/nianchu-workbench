# 架构决策：最该先修哪一个

> 生成：2026-11-12 · 场景：架构梳理（arch-review）
> 依据：`机制盲区.json`（49 条）、`事故档案/`（25 起）、前两轮 `当前架构评估.md` / `验证体系评估.md`
> 判据：说不出「为什么不是另外两个」= 没做决断。

## 一、三个候选（从盲区 + 事故里挑出后果最重的）

| 候选 | 病根（盲区原文） | 一句话 |
|---|---|---|
| **A. 派单投递真实性** | #4「台账写 delivered 但实际没唤醒也能过」· #12「状态机流转合法，但不查真实投递，依赖可能被虚填的 delivered 字段」· #16「自动回执『已修复』但实际没修也能过」 | 闭环是「写出来的」，不是「投出去的」 |
| **B. 备份/回滚真恢复** | #8「只比对 hash，不查能不能真恢复，没做过恢复演练」· #31「恢复后的系统是否真能跑，没端到端演练」 | 救命绳从来没试过牢不牢 |
| **C. 硬规矩/成本闸不执行** | #27「配置了 90% 但派单时不看这个闸」· #26「不含真实 token 计费」 | 事故换来的三条铁律，配了却没人执行 |

## 二、逐项评估

| 候选 | 影响面 | 修复成本 | 不修的后果 |
|---|---|---|---|
| A 派单投递真实性 | **最大**——中枢派单是系统骨干（L4），所有场景、健康度、评估、事故证据全挂在它下游 | 中（要把「读台账」升级成「真握手探测」） | **静默假闭环**：台账全绿，实际没人收到活；下游一切指标都是假数 |
| B 备份真恢复 | 中——L0 平台，低频但高损 | 高（要端到端恢复演练，动快照+重启+全链路） | 灾难时才暴露：数据丢了发现备份是坏的，全盘皆输 |
| C 硬规矩不执行 | 中——只防负载/欠费，是「安全阀」不是主干 | 低（把闸接进派单流程即可） | 负载爆了还继续派活、余额错了不停手，事故重演 |

## 三、决策：先修 A（派单投递真实性）

**理由**——三个维度全指向 A：

1. **它正在持续流血，不是「可能大出血」。** B 是「低频高损」：不修，要等真出事才爆。A 是「高频持续」：每派一单，delivered 字段就多一次被虚填的机会，天天在漏。
2. **它是「静默失败」，是事故档案里最要命的那种。** AC-001/AC-002 反复强调：三起事故的共同点是「都不报错」。C 多少有即时反馈（负载真高了会卡、余额错了会报），身份坏了开场就撞上。唯独 A 是台账看起来全绿、谁都不知道没投出去。
3. **它是「下层坏，上层全假」里最粗的那根承重柱。** 健康哨兵的首过率、记忆评估的 recall、事故档案的证据，全都从派单台账算出来。delivered 可虚填 → 下游全部指标失真。修它 = 一次修好一大片。

## 四、为什么不是另外两个（取舍）

- **为什么不是 B（备份真恢复）：** 影响是「灾难级」，但触发频率是「几乎不触发」。在资源有限时，「天天在漏的静默失败」必须先于「可能永远用不上的救命绳」。而且 B 的成本最高（端到端恢复演练要动快照、重启、全链路），同样的力气修 A 能立刻止血。B 该修，但排第二。
- **为什么不是 C（硬规矩不执行）：** C 和 A 其实是同一类病——「检查配了但不接进真实流程」。但 C 的半径窄（只挡负载/欠费），A 是主干动脉。且 C 有部分即时反馈兜底，A 没有。修完 A 之后，C 的修法（把闸接进派单流程）会顺路一起完成，因为它俩堵在同一个口子上。

## 五、代价（修了会牺牲什么）

1. **「快」会变「慢」。** 现在派单是「写台账即算交付」，修完要每单加一道真实投递探测（探对方会话是否真被唤醒/响应），多一次往返延迟。
2. **会暴露一批「假闭环」。** 真实探测一上，之前报告的绿色数字会变红——「信心」会短期受损（这正是 AC-001 里「没救回来的是信心」的那份代价）。
3. **动了 L4 底层，有误判风险。** 跨会话握手可能把「对方只是还没响应」误判成「没投递」，需要设计超时与重试，否则会制造新的假警报。

## 六、怎么验证修好了

1. **反例**：造一条「台账 state=delivered 但对方会话从未被唤醒」的样本 → 修复后**必须 FAIL**（把盲区 #4/#12 从「已知盲区」升级成「会失败的反例」）。
2. **正例**：造一条「真实投递成功、对方产生响应」的样本 → **必须 PASS**。
3. **收口**：跑 `机制体检.mjs`，派单哨兵、派单闭环、自动回执三项的「投递真实性」反例全部转绿，且 24h 内无新的「静默未投递」被漏。
