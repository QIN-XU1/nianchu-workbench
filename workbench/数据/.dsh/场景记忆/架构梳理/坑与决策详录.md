# 架构梳理 · 坑与决策详录

> 从 `场景私有记忆.md` §五 拆出。主文件保留摘要，完整正文在这里。
> 拆出原因：主文件注入成本超过 20000 token 上限（记忆评估判据）。


- 2026-11-09：**状态机的"末端状态"要显式处理。**
  真实 bug：健康度统计只认 `state === 'acked'`，
  但派单走完完整链路后 state 变成 `closed`，
  结果已完成的活被算成"没回执"。
  → 教训：任何状态机判断，都要问"最后那个状态算什么"。
  → 更稳的做法：用事实字段（ackedAt 是否存在）而不是状态字符串。

- 2026-11-10：**架构梳理要注意「结构标识的唯一性」。**
  真实案例：本记忆文件里存在两个「五、坑与决策」标题
  （一个空占位、一个真正在追加），导致"新经验该追加到哪一节"有歧义。
  → 教训：任何"按节追加 / 按锚点索引"的结构，节标题（锚点）必须唯一，
    否则维护者和脚本会各写各的、索引指向失效。
  → 更稳做法：合并重复节，或给每节固定唯一锚点 id，追加只认 id 不认标题文字。

- 2026-11-10：**架构梳理要验证「闭环的最后一跳」能真实落地。**
  真实案例：中枢派单→场景执行→回执这条链里，执行（写记忆）成功了，
  但回执命令因 DSH 锁文件失败（Temp 目录 dsh-acl-locks 报 Win32 5），闭环卡在最后一跳。
  → 教训：设计"产出→下游"接口时，不能只验证"上游能写"，
    还要验证"下游确认/回执"这一跳真的能被环境执行，否则闭环是假的。
  → 更稳做法：把"回执"也当一等接口看待，给失败留重试/降级路径，并单独验证它。

- 2026-11-10：**反复派发"追加经验"类任务时，要防"为闭环而灌水"。**
  真实案例：同一验证任务被连续派发多次（d-008/009/010），每次都要求"追加一条真实经验"，
  如果每条都硬凑新条目，会把记忆刷成流水账，违背"只记结论不记过程"。
  → 教训：记忆的价值在密度、不在条数；没有真新结论就宁可合并，别为满足闭环而造数。
  → 更稳做法：追加前先问"这条下次真的会用吗"，不会用就不写；同类结论合并成一条。

- 2026-11-11：**架构梳理要区分「三路输入的证据强度」，不能数票数。**
  竞品拆解给"它做了什么"（实然）、逆向给"它怎么做的"（实然）、资料给"它声称怎么做"（应然）。
  三路冲突时若按"谁说得多"取多数，会把应然当成实然，得出不可执行的方案。
  → 教训：每条结论都要挂到具体来源，并按"实然 > 应然"分级；被否掉的选项要写明否掉理由，否则接手的人会重复踩坑。

- 2026-11-12：**机制清单滞后于工具目录，数机制必须双源对账** — 症状：按机制清单数，L5 管线=0 项，但工具目录里管线写入.mjs、sceneflow.mjs 明明在跑；清单登记 46 项，工具目录却有 115 个 .mjs → 根因：机制登记靠手动追加，工具落地后漏登记，清单只是"登记过的子集"而非实现全集 → 修法：判某层强弱要看工具目录有没有对应 .mjs 做客观证据，与机制清单双向对账，漏登记的一并补。

- 2026-11-12：**反例能证伪格式，却证伪不了实质真假** — 症状：给哨兵逐个造反例，发现所有变异用例都是"字节超限/字段缺失/状态非法"这类格式违规，没有一条是"回执证据是编的、现象与事实不符"这类实质违规 → 根因：检查逻辑只读格式字段，判定范围里根本没有"实质真假"这个维度，反例再多也触不到实质 → 修法：要证伪实质，得挑最要命的检查造一条"格式全对但内容是编的"样本，看它会不会红——会红才是真检查，必然绿就是装饰。

- 2026-11-12：**排优先级要看频率与静默度，不是只看损失大小** — 症状：从 49 条盲区挑「最该先修」，备份「没做过恢复演练」（灾难级）和派单「delivered 可虚填」（高频）同时摆在面前，差点因「损失更大」选了备份 → 根因：只按单次损失大小排序，没按「触发频率 × 是否静默」排序；备份是低频高损、几乎不触发，派单是高频静默、天天在漏 → 修法：影响面 = 频率 × 静默度 × 下游依赖，「正在持续流血的静默失败」永远先于「可能永远用不上的救命绳」。

- 2026-11-12：**做决策前先查是否已在修，别信滞后盲区清单** — 症状：上轮判「派单投递真实性最该先修」，复盘发现投递通道.mjs 在我决策后 8 分钟落地、闭环验证.mjs 决策前就存在、经验里 11-10 早写了「派单要真投递」，等于重新发现了一个已在修的问题 → 根因：只读了盲区.json（最后改于 11-11 09:31）和事故档案这两个静态快照，没对账活的工具目录和最近经验条目，把「已知且在修」当成「待我决策」 → 修法：下判断前先 glob 工具目录 mtime + 读最近经验，确认「这已经在修了吗」；滞后文档只能当线索不能当现状。

- 2026-11-12：**分层要看结构边界，不能只看标签和检查顺序** — 症状：看「七层架构」，头注释和 arch.mjs 都按 L0~L6 分层，像分层良好；一查 tools.json 的 layer 字段只有 L1/L6 两个值、95 个工具平铺一个目录、七层定义还有两版互相矛盾 → 根因：把「标签」（头部注释）和「检查顺序」（arch.mjs 从下往上跑）当成了「分层」，没去看真正决定分层的是结构边界——目录划分、注册表字段、依赖约束这三样一个都没有 → 修法：判断「真分层」看三样硬证据：目录是否按层分、注册表 layer 字段是否填满七层、有没有依赖规则挡越层调用；标签和顺序只是「图」不是「结构」。

- 2026-11-12：**数据流要看单一真源，副本对不上就是坏了** — 症状：派单→台账→健康→进化→记忆的流向是单向线性、看着清晰；但一查发现「场景清单」散在索引.json/索引.md/记忆地图.json/身份索引.json 四个文件、「派单统计」是台账原始记录+健康度物化副本两份、进化台账里同一记忆文件有「引擎数据/」和「数据/」两套路径 → 根因：只画了流向图，没定「谁是真源」——派生品（健康度/索引md/记忆地图）靠手工或定时再生，不随真源原子更新，所以中枢面板已经出现 hub-neuron vs shell-side 的分歧 → 修法：判「数据流清晰」看单一真源：同一事实只许一处是真源，其余必须是「由真源生成」的派生品且带校验；发现两份对不上就是真源没收口。

- 2026-11-12：**稳定前提信息不该靠「按话术检索」提供，要放固定注入层** — 症状：架构梳理的封存集答对率只有 50%（30 题只对 15），问「上游输入 feature-matrix 是不是？」注入内容里没有它。根因：管线章节在记忆文件 80% 处，按话术检索时「**上游（我要等）**」得分只有 0.11，被「违规 1：场景清单有 4 份」等 0.22 分条目挤出 top 3。记忆越大竞争越激烈。修法：把「管线位置（该等谁/该给谁/具体产物文件）」写进 AGENTS.local.md（引擎固定注入层，不用检索）。修完架构梳理 50%→87%，全场景 69%→85%。**判据：稳定的前提信息（我是谁、我在哪、我该等谁）进固定层；可能相关的经验进检索层。**

- 2026-11-12：**题目话术与答案无关键词重叠，检索永远命中不了** — 症状：封存集问「这个场景负责做什么？」，facts 是「全网搜索：架构方案、竞品、技术资料、社区讨论」，话术里没有一个词出现在 facts 里，按话术检索命中不了 → 核心职责类题答对率 0%。根因：题目是泛化模板，与事实内容无连接。修法：把 facts 的头 16-20 字嵌进问题（「负责做什么？具体包括「全网搜索：架构方案」这类吗？」）。修完核心职责 0%→53%、产出题 8%→77%。这也更接近真实用户问法 —— 用户会提及关键词。
