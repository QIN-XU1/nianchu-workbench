# 错误处理评估：失败时到底会不会承认失败？

> 生成：2026-11-13 · 场景：架构梳理（arch-review）
> 范围：`工具/` 下各工具的 exit code、catch 处理、fail-open / fail-closed 选择
> 口径：只认实测到的代码事实，不采信注释里的自称

## 一、失败策略统计

`工具/` 目录实测：**457 行**含 `process.exit(`，**315 行**含 `catch`。归成三类策略：

| 策略 | 表现 | 典型工具 |
|---|---|---|
| **A. fail-closed + 退出码** | 判据不过就非 0 退出 | 验证闸、健康哨兵、健康度计算、派单、六件套、全场景验证、scene-validate |
| **B. fail-open 静默吞** | `catch { /* ignore */ }` / `catch { return null }` | 几乎所有读取辅助数据的入口（readTextSafe、getEnginePort、getEngineToken、mem-map、sceneflow） |
| **C. 错误当值返回** | 不抛、不退出，返回 `{ok:false,error}` / `resolve({status:0})` | 投递通道的 `httpRequest` / `call` / `prompt` |

三类本身都没错。**错误在两类交界处**：C 类把错误转成了值，但调用方没接住；B 类把错误转成了 null，但下游把 null 当成了「正常缺省」。

## 二、exit code 语义不统一（自动化的第一道裂缝）

约定看起来是 `0=通过 / 1=检查不过 / 2=用法或环境错`，但实际是交叉使用：

**同一语义，两种码：**

| 场景 | 工具:行 | 码 |
|---|---|---|
| 环境错：找不到派单台账 | `健康度计算.mjs:304` | **1** |
| 环境错：找不到场景 | `mem-map.mjs:147` | **1** |
| 环境错：连不上引擎 | `派单.mjs:349-351` | **2** |
| 环境错：参数缺失 | `验证闸.mjs:412` | 2 |
| 检查不过（有 failCount） | `scene-audit.mjs:191` | **2** |
| 检查不过（allOk=false） | `arch.mjs:281` | **2** |
| 检查不过（!r.pass） | `验证闸.mjs:436` | **1** |
| 检查不过（!okCount===总） | `六件套.mjs:384` | **1** |

结果：**`exit 1` 既可能是「代码/数据有问题」，也可能是「引擎没启动」；`exit 2` 既可能是「检查不过」，也可能是「用法错」。**

危害是具体的：`机制体检.mjs:980` 聚合时只判 `ok: r.status === 0`，**1 和 2 的差别在体检层被彻底抹平**。上层脚本想区分「该重启引擎」和「该修代码」拿不到信息，只能人工点开看输出。

## 三、该 fail-closed 却 fail-open 的地方（核心反例）

### 反例 1（最严重）：投递探针自己失败时，直接认成功

`投递通道.mjs:252`：

```js
} catch { /* 探不到就当成功（保守） */ }
return r;        // r 是 {ok:true}
```

这是**同一起事故的复发**。这个函数存在的全部理由，是修掉「余额不足（402）仍然记为 delivered」——`投递通道.mjs:184-198` 的注释自己写着「台账 d-20261110-001~007 全是余额不足仍 delivered」。

修法是「投递后探一下 turn/end 有没有错误」。但探针本身可能失败：

- `page` 读不到 → `if (!pg || !pg.ok) continue;`（第 231 行）→ 循环空转到 60 秒超时 → `lastReason = null`
- 整个探针抛异常 → 被 `catch {}` 吞掉

两种情况下都落到 `return r`（`ok:true`），于是 `派单.mjs:361` 就把 `d.state = 'delivered'` 写进台账。**「我读不到证据」被当成了「没有坏消息」**，这正是 fail-open 的定义。而注释称它「保守」——恰恰相反，它是替一个未验证的结论背书。

### 反例 2：验证闸的「去重闸」在读不到记忆时认证「全新」

`验证闸.mjs:327-346` 的 `loadExistingItems`：

```js
if (!fs.existsSync(dir)) return [];        // 目录不存在 → 空
const md = readTextSafe(...); if (!md) continue;   // 读不到 → 跳过
```

`验证闸.mjs:171-197` 的 `gate3NotKnown`：`existingItems` 为空 → `best = null` → 返回

```js
{ pass: true, reason: '新内容（最高重合 0%）' }
```

即：**闸 3「是不是已知的」在基线读不到时，输出的结论是「全新」。** 闸 3 的作用是拦截重复，而它最不该在数据缺失时给出的就是「没重复」。`--scene` 传错一个字（目录名不对）也会静默走这条路径——闸看着全过，其实一道也没起作用。

### 反例 3：端口读不到就猜 3083

`投递通道.mjs:68-73`：

```js
function getEnginePort(logPath = LOG) {
  const s = readTextSafe(logPath);
  if (!s) return DEFAULT_PORT;              // 日志读不到 → 猜 3083
  const m = [...s.matchAll(/dsh web: http:\/\/127\.0\.0\.1:(\d+)/g)];
  return m.length ? Number(...) : DEFAULT_PORT;   // 匹配不到 → 猜 3083
}
```

端口是外部事实。读不到时**猜一个默认值并继续**，等于把「我不知道引擎在哪」伪装成「引擎在 3083」。引擎若在别的端口，表现是超时或连错对象，错误会被归因到网络/网关，排查方向直接跑偏。对比同一文件的 `getEngineToken`：读不到返回 `null`，而 `connect()` 第 136 行 `if (!this.token) return {ok:false, error:'拿不到 token'}` —— **这是对的 fail-closed**，端口那个应该照此办理。

### 反例 4：回执只验「字够长」，不验「事真假」

`派单.mjs:422-465`：`--ack` 要求带 `--evidence` 且长度 ≥ `MIN_EVIDENCE_LEN`，`d.receipt = String(evidence)` 直接落台账。状态机层面（第 439-459 行注释）已经补了「必须先 delivered 才能 ack」，这是好修。但**证据本身没有任何校验**：传一句「已完成，产物在 xxx.md」这种恰好够长的字符串，照样 ack 通过并关闭。台账里 `receipt` 于是成了「AI 自己写的自我鉴定」。

注意这不是我脑补：`产物/架构评估.md` 那种「3169 字节 / 99 行」式的回执，正是因为**长度和存在性被当成了正确性**，才让上一轮的七层评估停在「概念分层」上没被拦下。

### 反例 5：一批「打印了但退出 0」的历史坑（已被点名，说明是系统性的）

`机制体检.mjs:280-287` 自己记着：

- 「派单验证生成：输出『达标: 7 / 8』**却不设 exitCode** → 机制体检看到 exit 0 → 判 PASS → 装饰」
- 「技能可见性体检：磁盘层抓到问题也打印了警告，但 `process.exit` 只看引擎层 → exit 0 → 装饰」
- 「文件索引写入：默认模式会自动修复缺失文件，然后报成功 → 删掉索引文件它自己补回来 → 装饰」

这三条是**同一个模式的三个实例**：`console.error` 说坏了，`process.exit` 说没事。人读到红字，机器读到 0。

## 四、还有一处「系统性 fail-open」：重试掩盖

`机制体检.mjs:991`：`const MAX_TRY = g.retry === false ? 1 : 2;` —— 每个哨兵默认重试一次，只要第二次过就算 PASS。

设计意图是吸收环境干扰（第 976-989 行有实测依据：界面回归单独跑 3/3，串跑 100% FAIL）。判断是对的，但代价是：**任何 50% 概率复现的真缺陷，在体检层的期望检出率从 1 掉到 0.5**。且「第二次过了」这件事不落盘，事后无法分辨「一次过」和「第一次失败第二次过」。真正坏掉的东西会因为偶发的第一次失败被记录成 PASS。

## 五、结论

**错误处理架构是「一半真一半装饰」，且装饰集中在最不该装饰的地方。**

- **做对的部分**（依据）：核心判据工具确实是 fail-closed 并给退出码——`验证闸:436`、`健康哨兵:173-177`、`健康度计算:304`、`派单:330-357`、`六件套`、`全场景验证`。判据不过就非 0 退出，这条主干是立住的。C 类「错误当值返回」（`投递通道:154-164`）本身是比抛异常更好的设计，调用方大多也确实接了。

- **没做对的部分**（反例，见上）：
  1. `投递通道:252` 探针失败 → 直接认投递成功，**是「余额不足仍 delivered」那起事故的复发路径**，注释还自称保守。
  2. `验证闸` 闸 3 在记忆读不到时认证「全新」，去重闸在基线缺失时静默失效。
  3. `getEnginePort` 读不到端口猜 3083，把「未知环境」当「已知环境」；同文件的 `getEngineToken` 却是正确写法，说明**同一个文件里两种标准并存**。
  4. `--ack` 只验证据长度不验内容，「回执」退化为自我鉴定。
  5. 多个工具「打印警告但 exit 0」，机制体检层只判 0/非 0，一律判 PASS。

- **元问题**：判据工具（闸、哨兵、体检）大量地用 `catch { /* ignore */ }`（315 处）读自己的输入。**检查器读不到事实时的默认行为，决定了它是真检查还是装饰**——现在的默认行为是「当作一切正常」。

**一句话判断：主干是 fail-closed 的，但主干依赖的输入全是 fail-open 读进来的。上游静默 → 下游必然自证合格。** 这和上一轮「数据流没真源」、上上轮「七层没结构」是同一个病根：**机制之间的信任没有校验，全靠自觉。**

## 六、修法（按性价比排序）

1. **把「读不到」和「没有」区分开**（治本，覆盖反例 1/2/3）
   - `readTextSafe` 家族改成返回 `{ok, value}` 而不是 `null`；用 `null` 同时表示「文件不存在」和「读失败」是这批 bug 的总根源。
   - `loadExistingItems` 读不到目录时 **返回 `{ok:false}`**，让闸 3 输出「无法判定（基线缺失）」并拒绝写入，而不是「全新」。
   - `getEnginePort` 读不到就报错退出，不要猜。
2. **投递判定的默认值反过来**（治反例 1，一行）
   - 探针没拿到 `lastReason` 时返回 `{ok:false, error:'无法确认本轮是否完成'}`，让派单落到 `failed` 而不是 `delivered`。**未确认成功 ≠ 成功。**
3. **统一 exit code 语义并让体检层区分**（治第二节）
   - 定死：`0=通过 / 1=检查不过 / 2=环境或用错误`。`健康度计算:304`、`mem-map:147` 改 2；`scene-audit:191`、`arch:281` 改 1。
   - `机制体检` 聚合时把 exit 2 单独列「环境未就绪」，不算 PASS 也不算 FAIL，避免重启问题被当代码问题。
4. **回执加存在性校验**（治反例 4）
   - `--evidence` 里若出现 `产物/xxx.md` 这类路径，就 `Test-Path` 一下；声称了文件却不存在 → 拒绝 ack。一句话检查，挡掉「意象回执」。
5. **重试要留痕**（治第四节）
   - 第几次通过写进体检快照：`attempt:1` 和 `attempt:2` 分开统计。第一次就失败的哨兵要能被单独列出，别让偶发淹掉真缺陷。
