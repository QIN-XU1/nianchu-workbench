# 数据流评估：从产生到消费，单一真源立住了吗？

> 生成：2026-11-12 · 场景：架构梳理（arch-review）
> 范围：派单台账 / 场景记忆 / 封存集 / 进化台账 / 健康度

## 一、完整流向（产生 → 消费）

```
                      ┌─────────────────────────────────────────────┐
                      │              中枢（hub，只调度）              │
                      └──────────────┬──────────────────────────────┘
                                     │ 派单.mjs 建单（write）
                                     ▼
                      ┌──────────────────────────────┐
                      │  派单台账.json（L4 协作）      │
                      │  dispatches[]：id/from/to/   │
                      │  subject/state/回执/销账      │
                      └──────────────┬───────────────┘
              ┌──────────────────────┼───────────────────────────┐
              │ 场景回执（acked/closed）│                        │
              ▼                        ▼                          ▼
   ┌──────────────────┐      ┌──────────────────────┐   ┌──────────────────────┐
   │  健康度.json      │      │  场景私有记忆.md       │   │  进化台账.json        │
   │  （派生·聚合）     │      │  （L3 记忆·只追加）     │   │  （L3 进化·登记回滚）   │
   │  _source=派单台账 │      │  各场景自己写          │   │  target 指向记忆文件   │
   └────────┬─────────┘      └──────────┬───────────┘   └──────────┬───────────┘
            │ 健康哨兵判定               │ 封存集.mjs 校验           │ 观察期后判定
            ▼                           ▼                          │
   ┌──────────────────┐      ┌──────────────────────┐              │
   │ 中枢看板（消费）   │      │  封存集历史.json      │              │
   └──────────────────┘      │  （记忆完整性快照）     │◄─────────────┘
                             └──────────────────────┘
```

**核心闭环是线性的、方向清晰的**：派单 → 台账 → 回执 →（派生）健康度 →（触发）进化 → 写回场景记忆 →（校验）封存集。

流向本身**没有环、没有反向写**。问题不在「方向」，在「同一事实散落在多个文件」。

## 二、单一真源违规（同一事实多处存在）

### 违规 1：场景清单有 4 份，且已经打架

「系统里有哪些场景、每个场景叫什么、面板是谁、记忆在哪」这一个事实，同时存在 4 个文件：

| 文件 | 字段 | 场景数 |
|---|---|---|
| `索引.json` | `areas[]`（id/name/owner/memory/file/panel） | 9 |
| `索引.md` | 表格（场景/面板/私有记忆） | 9 |
| `记忆地图.json` | `areas[]`（panel/scene/privateMemory） | 9 |
| `身份索引.json` | `rows[]`（scene/name/context/sessionId） | 9 |

**它们已经不一致了**——「中枢」的面板是谁：

- `索引.json`：`"panel": "hub-neuron"`（owner 是 `shell-side`）
- `索引.md`：`中枢 | shell-side`
- `记忆地图.json`：`"panel": "shell-side"`

同一个「中枢面板」，一份说 `hub-neuron`，两份说 `shell-side`。这就是单一真源被破坏后必然出现的后果：改了一处，另外三处不知道。

### 违规 2：派单统计是「原始记录 + 物化副本」两份

「每个场景派了多少单、回执了几单、首次通过率多少」这个事实有两份：

- **真源**：`派单台账.json` 的 `dispatches[]`（30 条原始记录，含 state/ackedAt/closedAt）
- **副本**：`健康度.json` 的 `scenes[].tasks/acked/firstPass/evidenceIds[]`

`健康度.json` 自己招认了它是派生品：
```json
"_source": "派单台账.json",
"_windowRecords": 30
```
每个 `evidenceIds` 里的 `d-202611xx-xxx` 就是台账里的 dispatch id。**一旦台账追加了新单而健康度没重算，两边的「派单数」就会分叉**——健康度是一个需要手工/定时再生的缓存，而不是随真源原子更新。

### 违规 3：进化台账里，同一个记忆文件有两套路径

`进化台账.json` 两条记录指向**同一个文件**（`场景私有记忆.md`），路径写法却不同：

- `ev-20261109-110831`：`"target": "引擎数据/.dsh/场景记忆/架构梳理/场景私有记忆.md"`
- `ev-20261111-173315`：`"target": "数据/.dsh/场景记忆/架构梳理/场景私有记忆.md"`

`引擎数据/` vs `数据/` —— 同一事实（进化落在哪个记忆文件）用两套坐标表示。回滚时按路径找文件，就可能有一半记录指错地方。

### 违规 4：`索引.json` 和 `索引.md` 是同一内容两种格式

两份都是「总索引」，一份 JSON 给程序读，一份 Markdown 给人读，内容同构。**这是最典型的手工双写**：改索引要同时改两处，任何一处漏改，机器和人看到的就是两个世界。

## 三、结论

**数据流的「方向」是清晰的，但「单一真源」没立住。**

- **清晰的部分**（依据）：核心闭环 `派单→台账→回执→健康→进化→记忆` 是单向线性，没有环、没有反向写；每类数据有明确的产生方和消费方，台账的 `from/to/state` 字段把生命周期串起来了。

- **不清晰的部分**（反例，见上四条）：
  1. 场景清单散在 4 个文件，且「中枢面板」已经出现 `hub-neuron` vs `shell-side` 的分歧。
  2. 派单统计是「原始记录 + 派生物化副本」两份，`健康度.json` 需再生、不随台账原子更新。
  3. 进化台账里同一记忆文件有 `引擎数据/` 和 `数据/` 两套路径。
  4. 索引 JSON 与 Markdown 手工双写。

**一句话判断：流向画得出来，但「谁是真源」没定死。** 一旦某处需要改（比如场景改名、面板调整），没有任何机制保证另外几份跟着变——现在它们已经因为没人统一而对不上了。

## 四、最便宜的修法（不动流向，只收口）

1. **定「场景清单」唯一真源**：保留 `身份索引.json`（它是从引擎实际会话 `engine-scan` 生成的，天然最新）或 `索引.json` 中的一个为真源，其余三个改成「由真源生成」——`索引.md` 和 `记忆地图.json` 让 `mem-map.mjs` 从真源重生成，删掉手工维护。
2. **健康度改成「读台账即时算」或「每次追加台账就重算」**：不再单独存 `tasks/acked/evidenceIds`，或给它加 `_at` 校验，发现台账 `_at` 更新而健康度没更新就报红。
3. **进化台账的 `target` 统一用一个路径基准**（都带或不带 `引擎数据/` 前缀），写入时规范化。
4. **索引双格式合一**：只留 JSON，Markdown 由工具生成。

> 与上一轮「七层评估」的联动：七层问题是「有图没结构」，数据流问题是「有流向没真源」。两者根因相同——**机制靠自觉，没有生成器/校验器把派生品锁在真源上。**
