# 七层架构评估：它真的分层了吗？

> 生成：2026-11-12 · 场景：架构梳理（arch-review）
> 判据：说「分层良好」要给依据；说「没分层」要给反例。

## 一、七层各自应该包含什么

定义取自 AGENTS.md §8 + 各工具的层头注释（层头注释是唯一的逐层定义源）：

| 层 | 名称 | 应该包含什么 | 定义源 |
|---|---|---|---|
| L0 | 平台层 | 数据目录结构：`数据/.dsh`（sessions / 场景记忆 / skills / AGENTS.md 注入层） | `platform-init.mjs` |
| L1 | 执行层 | 工具注册表：`工具/*.mjs`、`TOOLS.md`、`外壳/scripts` | `tools.mjs` |
| L2 | 场景层 | 六件套完整性 + 会话绑定：`外壳/scenarios/*.json`、定位卡、身份卡、技能 | `scene-audit.mjs` |
| L3 | 记忆层 | 三层结构 + 注入机制：场景记忆三文档（§〇/主文件/§五） | `memory.mjs` |
| L4 | 协作层 | 四块板 + 派单回执：派单台账、回执 | `collab.mjs` |
| L5 | 管线层 | 产物治理：产物校验 | `artifact.mjs` |
| L6 | 验证层 | 架构自检 + 哨兵 + selftest：机制体检 | `arch.mjs` |

依赖方向：L0 → L1 → … → L6，「下层坏，上层全假」。

## 二、实际代码是否按此分层 —— 三个硬反例

### 反例 1：`tools.json` 的 `layer` 字段只有两个值

95 个工具，`layer` 字段的分布是：

```
L1：15 个
L6：80 个
L0/L2/L3/L4/L5：0 个
```

**七个层在数据模型里只落地了两个。** 注册表根本没有 L0/L2/L3/L4/L5 这五个桶。而 `platform-init.mjs`——它头注释明明写「L0 平台层初始化」——在 `tools.json` 里被登记成 `"layer": "L1"`。

结论：分层的「登记」本身就没做完，也做错了。

### 反例 2：代码不是按层组织，是平铺在一个目录里

所有工具都堆在**同一个平的 `工具/` 目录**（95 个 `.mjs`），没有 `工具/L0/`、`工具/L1/` 这样的子目录。「层」只是一行 `purpose` 注释字符串，不是任何结构边界。

### 反例 3：七层定义自己就不止一版

当前 `AGENTS.md §8` 写的是「L0 平台 / L1 执行 / L2 场景 / L3 记忆 / L4 协作 / L5 管线 / L6 验证」；但 `产物/架构评估.md`（2026-11-09）写的是「L0 宪法 / L1 共享 / L2 场景 / L3 进化 / L4 归档 / L5 运行时 / L6 验证」。

两版里 **L0、L1、L3、L4、L5 全都不一样**，只有 L2（场景）和 L6（验证）稳定。一个「架构」如果连层叫什么、每层装什么都没定，它更像口号，不是架构。

## 三、跨层调用与层内混杂（实锤）

| 现象 | 具体证据 |
|---|---|
| **L4 协作层直接下探 L0** | `派单.mjs`（L4）直接调引擎 RPC：`session/list`、`session/create`、`session/prompt`（L0 平台） |
| **L4 协作层直接读写 L3** | `派单.mjs` 读 `场景记忆/_共享记忆/派单台账.json`，还写对方「记忆文件」（这正是 11-10 那个「把公告当派单、只写记忆不唤醒」的 bug 现场） |
| **L6 验证层通吃所有层** | `arch.mjs`（L6）逐层检查 L0~L5，`记忆哨兵`（L6）直接读 L3 的 `.md` 文件 |
| **层头注释 vs 注册表打架** | `platform-init.mjs` 头写 L0，`tools.json` 记 L1；`arch.mjs` 头写 L6，`tools.json` 记 L6（这条对），但 L2/L3/L4/L5 的工具有一半在注册表里根本找不到层 |

关键：**没有任何 import / 依赖规则约束「谁可以调谁」。** L4 能直接伸手到 L0，L6 能通吃全局，全靠自觉。所谓「下层坏上层全假」是**检查顺序**（arch.mjs 从下往上跑），不是**隔离边界**——没有任何机制防止 L3 反过来依赖 L6。

## 四、结论

**七层是「概念分层」+「检查顺序」，不是「结构分层」。**

- **它成立的部分**（说分层良好，依据是这些）：
  1. 七个层名被一致地写在 7 个工具的头部注释里，且 `arch.mjs` 确实按 L0→L6 顺序自检、报「下层坏上层全假」。
  2. 存在一条真实的逻辑依赖链：先有数据目录（L0）才有工具（L1）才有场景（L2）才有记忆（L3）才有协作（L4）。

- **它不成立的部分**（说没分层，反例在上面三条）：
  1. 代码**平铺**在一个目录，没有按层划分的模块边界。
  2. `layer` 字段**退化**成只有 L1/L6 两个值，L0/L2/L3/L4/L5 没落地。
  3. 七层定义**有两版且互相矛盾**（L0/L1/L3/L4/L5 全变）。
  4. **跨层调用无约束**，L4 直接调 L0、L6 通吃全局，没有任何依赖规则挡着。

**一句话判断：这个项目有一张「七层」的图，但没有「七层」的结构。** 分层目前只在两处是实的——「检查跑的顺序」和「工具头部那行注释」。其余（目录、注册表、依赖约束）都没跟上。

## 五、如果要让它「真分层」，最便宜的一步

不重排目录（动 95 个文件风险大），先做三件不搬代码的事：

1. **统一七层定义**：删掉 11-09 那版旧 taxonomy，只留 AGENTS.md §8 一版，并给每层写一行「装什么」。
2. **修 `tools.json` 的 `layer` 字段**：把 95 个工具的真实层填对（现在只有 L1/L6 两个值）。
3. **给 arch.mjs 加一条「层序检查」**：扫描每个工具的 import/引用，凡是从高层反引低层（如 L6 的文件被 L3 import）就报「越层依赖」——把「下层坏上层全假」从口号变成会红的检查。
