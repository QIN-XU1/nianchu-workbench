# 启动性能分析

> 分析对象：`workbench\外壳`（Electron 外壳 + DSH 引擎）
> 数据来源：`workbench\外壳\server.log`（2026-11-11 启动日志）+ `main.js` 启动流程
> 判据：仅用日志里的真实耗时数字，不凭感觉。

## 一、耗时阶段总览

| 阶段 | 耗时 | 是否瓶颈 | 优化空间 |
|---|---|---|---|
| 窗口创建 / 可见 | 174ms | 否 | 已很快，无需 |
| 引擎启动（engine ready） | 2.2s（就绪总耗时 2.3s） | 中等（固定成本） | 已优化到直接 node 跑 CLI，空间有限 |
| 场景渲染（渲染器注册 / 中枢 / 主 Agent 挂载） | 无独立耗时数字（含在 174ms 窗口内） | 否 | 无需 |
| webview 加载 | **日志无耗时数字** | 未知 | 需补埋点（见 §三） |
| pc.toplarge 磁盘大户排行面板 | 2291ms / 2122ms（两次） | **是（最大瓶颈）** | 大，见 §二 |

## 二、关键发现：pc.toplarge 是最大瓶颈

server.log 里唯一的「面板级」耗时告警：

```
[renderer][WARN] [api] pc.toplarge 耗时 2291.1ms
[renderer][WARN] [api] pc.toplarge 耗时 2122.8ms
```

- **耗时 ≈ 2.2s，与引擎启动（2.3s）几乎一样长**，等于「打开工作台后，磁盘大户排行这个面板自己又跑了整整一次全盘扫描」。
- 根因（见 `main.js:6439` 的 `pc:toplarge` 处理器）：每次渲染都调用 `pcWalk(root, { maxDepth:6, budgetMs:15000, topN:20 })`，对盘符根目录做**全盘递归遍历**，C 盘越满越慢。
- 该面板在启动时即渲染（`ui/panels/_generic.js:1205`），所以这个 2.2s 直接叠加在启动总耗时上。

**优化方向：**
1. **懒加载 / 按需刷新**：面板首次渲染不扫描，等用户点「刷新」或切到该面板再扫，避免启动期白付 2.2s。
2. **结果缓存**：上次扫描结果落盘（如 `pc-cleanup` 台账旁存一份 `toplarge-cache.json`），启动先显缓存、后台异步更新。
3. **换更快的扫描源**：全盘递归很慢，可改用 Windows Search 索引 / Everything SDK / MFT 读取，或后台增量扫描（只扫新增大文件）。

## 三、日志埋点缺口（webview 阶段无法量化）

本次按「窗口创建 / 引擎启动 / 场景渲染 / webview 加载」四阶段归类时，发现：

- 日志有 `窗口可见耗时 174ms`（`main.js` 启动计时基准）、`engine ready in 2.2s`、`引擎就绪总耗时 2.3s`。
- 但 **webview 加载阶段没有任何耗时打点**——renderer 只有「已注册渲染器 10/10」「启动完成」这类无时间戳的相对顺序日志，无法得知 webview 从 `did-start-loading` 到 `did-finish-load` 花了多久。

## 四、结论

**最该优化的一步：`pc.toplarge` 磁盘大户排行面板的全盘递归扫描（≈2.2s）。**

理由：它是启动链路里唯一能与引擎启动（2.3s）匹敌的单点耗时，且完全可以通过「懒加载 + 结果缓存」近乎消除，代价低、收益直接（启动感知时长可减少约 2 秒）。

**怎么优化（按性价比排序）：**
1. 面板改为「首次不扫，点刷新才扫」—— 一行改动的即时收益。
2. 结果写缓存文件，启动先显缓存、后台异步重扫。
3. 中长期：接入 Everything/Windows 索引替代全盘递归。

**次要看点：** 补 webview 加载耗时埋点，否则下一轮仍无法量化该阶段。
