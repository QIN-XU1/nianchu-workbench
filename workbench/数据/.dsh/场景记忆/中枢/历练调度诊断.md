# 历练调度诊断

> 对象：`工具/场景历练.mjs` + `工具/历练任务库.mjs` + `工具/_经验识别.mjs` + `数据/.dsh/历练轮次.json`
> 方法：逐行读源码，评估「任务分配」合理性，并找「场景能敷衍/作弊」的漏洞
> 诊断日期：2026-11-12

## 一、任务分配逻辑评估

### 1. 轮次机制：是「单调计数器」，不是「派过哪些」的去重

- 台账 `历练轮次.json` 每个场景存一个整数（当前全 5）。
- `--run` 里：`const done = Number(rounds[scene] || 0); buildPrompt(scene, done)`，投递成功后 `rounds[scene] = done + 1`（场景历练.mjs:618-641）。
- `buildPrompt` 直接用 `idx = Math.min(round, list.length - 1)`（历练任务库.mjs:1909）。

**问题**：任务库头注释声称「历练工具会记录『已派过哪些』，下次自动挑没派过的」（历练任务库.mjs:31-32），但代码里**没有任何「已派 id」去重**——它只认「投递成功就 +1」。所以「有没有真完成」和「下次派什么」是脱钩的。

### 2. 任务库天花板 bug：耗尽后永远重复最后一个任务

- `idx = Math.min(round, list.length - 1)` 在 round 超过库长时**钳制到最后一个任务**，不是循环。
- 但控制台却打印「已用完，将重头循环」（场景历练.mjs:642），与实际行为（重复末任务）**自相矛盾**。
- 后果（已实测）：场景 agent 正确判断「任务已完成无需重做」→ 0 条新经验。铁证在 历练任务库.mjs:12-15（引用三轮后回复「任务已完成…无需重做」）与 实施计划/经验积累推进计划.md:29。

### 3. 难度递进：名义有、实质没有

- 任务库宣称「难度递进：先盘点现状 → 再分析问题 → 再给方案」（历练任务库.mjs:29）。
- 实际每个任务都是「read/glob → 写一张 md 表格」，难度几乎持平，不存在可度量的递进。竞品拆解 ca-1(功能矩阵)/ca-2(功能缺口)/ca-3(交互模式) 只是换了主题，不是换了难度。

### 4. 任务数严重不均衡

按 `id:` 统计每场景任务数（历练任务库.mjs）：

| 场景 | 任务数 | 证据 |
|---|---|---|
| 竞品拆解 | **4**（ca-1~ca-4） | 历练任务库.mjs:67/83/102/640 |
| 逆向分析 | 12（re-1~re-12） | :121…:1053 |
| 调研 | 12（rs-1~rs-12） | :187…:1164 |
| 其余 6 场景 | 各 12 | :240…:1863 |

竞品拆解只有 4 个任务，其余 8 个场景 12 个。目标是每场景 ≥12 条经验，竞品拆解在任务库层面就**先天凑不够**（4 任务 × 每任务 1 条经验 = 4 条上限）。

## 二、「场景应付了事」的漏洞（可作弊/敷衍处）

### 漏洞1：verify 字段从不执行，只被打印

- 每个任务都带 `verify`（如「功能缺口分析.md 存在且 ≥6 行偏差」），任务库头注释宣称「结果必须可验证（落到文件）」。
- 但 `deliver()` 只发任务、判 `ok: !!(ok && ok.result && ok.result.ok)`（场景历练.mjs:577），**从不读回执、从不跑 verify**。
- `verify` 只是被 `console.log('验收: ' + prompt.verify)` 打印出来（场景历练.mjs:626），给谁看？给控制台看，不喂给任何校验逻辑。
- **→ 场景可以回一句「好的，已了解」就完事，轮次照样 +1，经验照样可能被算进去。**

### 漏洞2：经验写入无人验真，countExperience 只看文本长度

- `countExperience` → `isRealExperience`（_经验识别.mjs:126-141）的判据只有三条：有日期 + 非占位符 + **去标点后正文 ≥20 字**。
- 去标点：`body.replace(/[—\-:：→>\s]+/g, '')`（:139）再 `>= 20`（:140）。**不校验「是否真干过活」，不校验症状/根因/修法是否齐全、是否真踩到。**
- 而且这个 ≥20 字判据与任务提示里宣传的「≥30 字、粗体标题≥10 字、症状/根因/修法至少两项」**不一致**——识别器放宽到 20 字。
- **→ 场景写一句 20 字的泛泛而谈（如「今天做了功能盘点，学到要认真读源码」）就能 +1 条经验，封存集拿它出题也测不出是编的。**

### 漏洞3：轮次 +1 只认「投递成功」，不认「真干完」

- `--run` 里 `if (r.ok) { rounds[scene] = done + 1; writeRounds(rounds); }`（场景历练.mjs:639-641）。
- `r.ok` 只是 HTTP 投递成功（queue 进队列），**不代表场景真跑了、更不代表产出了**。
- **→ 场景回「无需重做」/ 敷衍 / 甚至根本没执行，轮次照样虚增，任务库提前耗尽。**（此 bug 已被 实施计划/一周收敛清单.md:14 记为「轮次虚增 bug」，但 实施计划/计划执行核对.md:16 确认「没改代码」仍存在。）

### 漏洞4：`mode:'queue'` 假成功（与派单断点同源）

- `deliver` 用 `mode: 'queue'`（场景历练.mjs:557），HTTP 200 即 ok，不解析回复里的「余额不足 / EPERM 卡死」。
- **→ 任务投进了队列但可能根本不执行**，而历练工具已把轮次 +1。

### 漏洞5：会话选取 `find` 第一个非空，可能投到旧会话

- `const hit = cands.find((s) => !s.blank) || cands[0]`（场景历练.mjs:544）——取「第一个非空」而非「最新」。
- **→ 同场景多个会话时，可能投进旧会话、读到旧回复，把旧任务的结论当新任务的成果。**

## 三、结论

1. **最致命的是漏洞1+3 的组合**：verify 从不执行（漏洞1）+ 轮次只认投递不认真干完（漏洞3）＝「宣称可验证的历练，实际是可零成本敷衍的刷轮次」。
2. 任务分配逻辑的**根问题**是「轮次=单调计数器」这个模型错配了「要派不同任务」的需求——正确模型应是「记录已完成的 task id，下次挑列表里第一个未完成的」，而不是 `rounds[scene]` 整数 + `min(round, len-1)` 钳制。
3. 任务库还有两个结构性欠账：竞品拆解任务数只有 4（先天凑不够 12 条），以及「难度递进」是口号不是机制。
4. 修法优先级：① `deliver` 后 `wait-reply` 回读，用 `verify` 断言产物存在/行数达标，达标才 `rounds+1`；② `buildPrompt` 改「按已完成 id 去重挑任务」；③ 给竞品拆解补齐任务库；④ 经验识别器与任务提示的格式口径对齐。
