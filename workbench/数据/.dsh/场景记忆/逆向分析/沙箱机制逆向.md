## 一、三档沙箱模式

模式是全局单例（`SANDBOX_MODES`，sandbox-policy/index.js L26-30），只有三个枚举值：

| 模式 | 写文件语义 | 读文件语义 |
|---|---|---|
| `read-only` | 一律拒绝 | 放行 |
| `workspace-write` | 仅允许写「会话工作区 + 显式额外目录 + 平台临时区」 | 放行 |
| `danger-full-access` | 不限制 | 放行 |

模式由 Config schema 声明（L114-122）：`mode` 默认 `read-only`，`workspaceRoot` 必填，`additionalWritableRoots` 默认空数组 `[]`。

每调用一次能力时，`resolve()` 决定「本次调用的有效模式」（L166-174），优先级是：

```
request.mode（已批准的显式升级） > session 的 sandbox/mode 事件 > 部署默认 mode
```

会话工作区根 = `session.header.cwd`（场景 agent 的 cwd 就是它自己的记忆目录），没有 cwd 才回退到配置的 `workspaceRoot`（L170）。

> 关键结论：**模式不是「全局一个值」，而是每次能力调用都重新 resolve 一次**，所以同一进程里中枢和场景 agent 可能各自落在不同的有效模式/根上。

## 二、为什么 workspace-write 下场景写不了跨目录

文件写的栅栏在 `dsh-fs-sandbox/lib/index.js` 的 `checkedTarget()`（L176-189）。逻辑是：

```js
// L179-188（语义摘录，非逐字）
if (mode === "danger-full-access") return target;              // 放行
if (mode === "read-only") throw  FS_SANDBOX_DENIED;            // 全拒
// workspace-write：目标必须落在 writableRoots 某个根之下
for (const root of writableRoots(policy))
  if (await isPathUnder(target, root)) contained = true;
if (!contained) throw FS_SANDBOX_DENIED("under workspace-write mode");
```

「能写哪些根」由 `writableRoots()` 推导（dsh-sandbox/index.js L239-246）：

```js
// L239-246
function writableRoots(policy) {
  if (policy.mode !== "workspace-write") return [];
  return [...new Set([
    ...workspaceWritableRoots(policy),   // workspace 根 + additionalWritableRoots
    canonicalPath("/tmp"),
    canonicalPath(tmpdir())              // 平台临时区
  ])];
}
```

而 `workspaceWritableRoots()`（L225-228）只含两样：

```js
// L225-228
if (policy.mode !== "workspace-write") return [];
return [...new Set([
  canonicalPath(policy.workspaceRoot),                 // 会话 cwd
  ...(policy.additionalWritableRoots ?? [])            // 显式额外目录
])];
```

判定「是否在根下」走 `isPathUnder()`（fs-sandbox L53-65）：先做词法前缀比对，拼写不一致时回退到「逐级祖先的文件系统身份（dev+ino）比对」，覆盖 Windows 8.3 短名和大小写别名。

所以链条是：

```
场景 agent 的 cwd = 数据/.dsh/场景记忆/<场景名>
→ resolve() 把 workspaceRoot 定为这个目录（L170）
→ writableRoots = { 该目录, /tmp, %TEMP% }
→ 共享台账 _共享记忆/派单台账.json 不在这些根下
→ isPathUnder 返回 false
→ checkedTarget 抛 FS_SANDBOX_DENIED
```

**根因一句话：场景 agent 的会话工作区被钉死在自己的记忆目录，而共享文件在别的目录，`writableRoots` 允许集里根本没有它。**

补充：读永远放行（fs-sandbox 注释 L68-82「Reads pass through untouched」），所以场景 agent 能「看」共享文件，只是「写」被拦。

## 三、引擎对 additionalWritableRoots 的处理逻辑

这是本项目踩过、且被堵死的一条路，分两层：

**① 策略层（收下并校验，但不做物理授权）**

`sandbox-policy` 的 `resolveAdditionalWritableRoots()`（L79-83）：

```js
// L79-83
if (roots === void 0 || roots.length === 0) return void 0;
for (const root of roots)
  if (!isAbsolute(root) || root.includes("\0"))
    throw new Error("... entries must be absolute execution-world paths");
return Object.freeze([...new Set(roots)]);
```

它只做三件事：非空判断、绝对路径 + 无 NUL 校验、去重后冻结。**注释明确说（L72-75）：这些目录保持「执行世界拼写」，由执行主机逐个物理校验后才授权，策略层不 canonicalize。** 也就是 schema 层「认」这个配置项，但真正的授权在 enforcing 后端。

`resolve()` 原样带出（L171）：`additionalWritableRoots` 非 undefined 时才挂到解析结果上。

**② 执行层（Windows ACL 后端直接拒绝）**

Windows ACL 后端组装 runner argv 时（dsh-sandbox-local/index.js L359-360）：

```js
// L359-360
if (policy.mode === "workspace-write" && (policy.additionalWritableRoots?.length ?? 0) > 0)
  throw new SandboxUnsupportedPolicyError(
    "Windows ACL confinement does not support additional writable directories; ...");
```

**这是致命点**：只要处于 `workspace-write` 且配置了任何额外目录，后端在 spawn 前就抛 `SandboxUnsupportedPolicyError`。所以「给共享目录加额外写权限」这条路在本机 Windows ACL 后端上是**硬编码不可用**，不是权限没配好，而是后端能力边界。

这与事故档案 `事故-DSH沙箱工具失效.md` 记录的另一点呼应：Windows 后端靠「受限令牌降级为 Low 完整性 + 目录打 Low 标签」来实现隔离，它只对 workspace 根和私密临时区 grant 了能力 SID，额外目录的 grant 模型根本没实现（见 runner.js L21-30 注释：两种模式只差 capability SID 的 grant 集合）。

## 四、本项目的绕法（中枢代写）为什么可行

既然 `additionalWritableRoots` 被堵死，项目采用「**把跨目录写从场景侧移到中枢侧**」（见 `cordis.patch.yml` L60-83 的复盘注释）。

为什么这招成立？三个原因：

1. **写栅栏是按「当前会话的 workspace 根」判定的，不是全局开关。** 中枢的会话 cwd 覆盖 `_共享记忆/`（见 `外壳/scenarios/hub-context.md` L126-132：中枢写 `_共享记忆/派单台账.json`、`_共享记忆/索引.json`），所以这些共享文件落在中枢的 `writableRoots` 内，`isPathUnder` 为真，写自然放行。

2. **场景 agent 只「做和说」，不「记账」。** 场景 agent 把结果回复在会话里，中枢用投递通道等待并读取，再由中枢自己的工具去写台账。写操作发生时，执行主体是中枢会话而非场景会话，于是绕开了场景工作区的根限制。

3. **读是全局放行的。** 场景 agent 读共享索引没问题（fs-sandbox 只栅栏五种写操作），所以「读对方定位卡、读索引」这类跨目录读本来就不受 workspace-write 限制，唯一被拦的就是「写」。

一句话总结：**沙箱拦的是「谁（哪个会话的 cwd 根）在写什么路径」，不是「这个进程能不能写」——把写动作交给根更大的中枢会话，就从机制上规避了场景侧写不了跨目录文件的限制。**

## 五、它怎么做到的（结论 + 代码证据）

### 结论 1：写权限是「白名单根集合」而非「黑名单路径」

沙箱不是拦某几条具体路径，而是算出「允许写的根集合」`writableRoots`，再要求目标路径 `isPathUnder` 落入其中之一。证据：dsh-sandbox/index.js L239-246 用 `Set` 去重拼出 workspace + extra + /tmp + tmpdir 四类根；fs-sandbox L183-187 对每个根跑 `isPathUnder`，有一个命中即放行。

### 结论 2：策略层「认配置」与执行层「真授权」是两套人，存在能力缺口

`sandbox-policy` 的 schema 和 `resolveAdditionalWritableRoots`（L79-83）接受并校验 `additionalWritableRoots`，但真正的 grant 在 enforcing 后端。Windows ACL 后端在 L359-360 直接抛 `SandboxUnsupportedPolicyError`。**这就是「配置了没用」的根因：上层 schema 开放了选项，下层后端没实现。**

### 结论 3：有效模式是「每次调用重算」的投影，不是进程级常量

`resolve()`（L166-174）每次能力调用都按 `request.mode → session 事件 → 部署默认` 重算，且工作区根来自 `session.header.cwd`（L170）。这解释了为什么中枢和场景 agent 能在同一进程内各有各的可写范围。

### 结论 4：读与写被刻意分开处理，读永远放行

fs-sandbox 注释（L68-82）明确「只在五种 mutation 上加策略栅栏，读放行」。所以跨目录「读共享文件」从来不是问题，问题只在「写」。这也是中枢代写可行的前提之一。
