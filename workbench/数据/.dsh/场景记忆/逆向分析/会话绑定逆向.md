# 会话绑定逆向

> 目标：查清「场景 AI 面板」如何绑定到指定会话——会话 ID 从哪来、怎么进 webview、谁在用。
> 素材：`外壳/ui/panels/harness.js`、`外壳/preload.js`、`工具/会话绑定.mjs`、`工具/投递通道.mjs`，并顺藤到 `外壳/main.js` 与场景 json。

## 一、一句话结论

**配置侧（场景 json 三字段）是齐的，但「把 sessionId 灌进 webview 让引擎打开对应会话」这一段链路是断的——真正的注入函数是死代码，宣称的负责人文件不存在。**

## 二、会话 ID 的三个来源（file:line）

| 来源 | 位置 | 说明 |
|---|---|---|
| 场景 json `panels[].sessionId` | `外壳/scenarios/*.json`（例 reverse-eng.json L53） | 每个场景 harness 面板都写了 `sessionTitle`/`pinTarget`/`sessionId` 三字段，且是真实 id（非占位符） |
| 引擎 RPC 创建 + 回写 | `外壳/main.js` `ensureSceneSession` L1865-1958 | 无 id 时 `session/create`（cwd=注入目录），拿到 id 回写场景 json（L1935-1937） |
| 身份索引兜底补齐 | `工具/会话绑定.mjs` `fixScene` L198-231 | 从 `身份索引.json` 读真实 id，补齐三字段 |

> `harness.js` 读字段时兼容了 `p.sessionId || p.session`（L140），但全仓库只有 `sessionId` 被写，`session` 是无人生成的空兜底。

## 三、意图上的完整链路（每个环节 file:line）

```
场景 json sessionId
  → harness.js 读出  harness.js L140
  → 写进 webview 的 localStorage['dsh.sessions.current']  harness.js pinScript L311-337
  → webview 引擎前端读 localStorage 打开该会话   harness.js 注释 L248-256
```

- 读出：`harness.js L140` `const sessionId = String(p.sessionId || p.session || '')`
- 写入：`harness.js L311-337` `pinScript()` 生成一段注入脚本，写 `localStorage['dsh.sessions.current'] = {sessionId}`，返回 `{stable}` 或 `{needReload}`
- 使用终点：引擎前端读 `localStorage['dsh.sessions.current']`（`harness.js` 注释 L248-256 实测证实该 key 决定打开哪条会话）

另有一条**旁路**（走引擎 HTTP RPC、不经 webview，链路是通的）：

```
工具/投递通道.mjs EngineClient → session/list → session/create → session/prompt → session/page
main.js engine:prompt L4861 / ma:page L4976 / ma:send L4992
```

## 四、断点清单（4 处）

### 断点 1（主断点）：`pinScript()` 是死代码，从未被调用

- `harness.js L140` 读出了 `sessionId`，但后续只在 `L142` 用它 `setState('绑定会话')` 显示文字。
- `pinScript(sessionId)` 定义在 `L311-337`，全文 grep 无任何调用点（仅 L234/L263 注释里提到）。
- 结果：sessionId 从未被写进 webview 的 localStorage，所谓「绑定」只是状态栏一个字符串。

### 断点 2：主进程注入只做布局，不钉会话；且调用方无人调用

- `main.js L1649` `harness:wv:inject` 注入的是 `HARNESS_FIX_JS`（`L1517-1641`），内容全是「grid 铺满/隐藏侧栏」的布局 CSS/JS，不含任何按 sessionId 钉会话逻辑。
- 它匹配的是 `pinTarget`（标题名，`L1675-1678`），不是 sessionId。
- preload 暴露的 `injectHarnessPanel`（`preload.js L72` → `main.js L1649`）在渲染层**没有任何调用点**（grep 仅见定义与 re-export 名单 `ui/api/index.js L109`）。

### 断点 3：占位符替换是空操作，宣称的负责人文件不存在

- `main.js L1678` 做 `HARNESS_FIX_JS.split('__DSH_PIN_TARGET__').join(...)`，但 `HARNESS_FIX_JS` 正文（`L1517-1641`）里根本没有 `__DSH_PIN_TARGET__` 占位符，`pinDiag` 里硬编码 `'oa系统运维'`（`L1627`）——替换是空操作。
- `main.js L1642` 注释宣称「钉住会话已移交 `renderer/renderers.js` 的 HARNESS_PIN_JS」，但整个 workbench 里 `renderers*.js` 一个都不存在（glob 无结果）。

### 断点 4：partition 单一共享，多面板互抢「当前会话」键

- `harness.js L149` 所有 harness 面板统一 `partition="persist:harness"`，共享同一份 localStorage。
- 与 `工具/会话绑定.mjs L31` 自己引用的硬结论「一个 AI 面板一个独立分区（否则多面板抢同一个『当前会话』键）」直接矛盾。
- 即使断点 1 修好，8 个面板也会互相覆盖 `dsh.sessions.current`，最终都显示最后写入的那条会话。

## 五、判定

- **看懂**：三字段语义与来源（会话绑定.mjs L10-26 表）、引擎 RPC 创建会话（main.js L1865-1958）、RPC 投递通道（投递通道.mjs）——都有真实代码 + 实测注释支撑。
- **断点判定依据**：全部用 grep 调用点 + 读占位符正文 + glob 文件存在性三个动作交叉确认，非猜测。
- **最关键的坑**：链路里「有读取 + 有写入函数」≠ 链路通；必须再 grep 一次「谁调用了写入函数」，否则会把死代码当成活实现。
