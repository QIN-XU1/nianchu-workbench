# 跨文件一致性分析

> **这一类故障的共性**：同一个事实在两个地方各写了一遍，慢慢走样。
> 判据来自项目铁律 §1「两处判据 = 两份结论 = 早晚打架」。
> 已知实例：token 正则长度下限 `{30,}` vs `{20,}`（见 `中枢/闭环断点诊断.md` 断点 2）。

本次分析范围：`外壳/`（6 个 .js/.mjs）+ `工具/`（约 130 个 .mjs，不含 `_归档/`）。
数据源可用一条命令复核，逐项列出。

## 二、**没有检查**的（本次新增发现，按风险排序）

### ★ 风险 1：`DSH_PORT` 同一个环境变量，两个默认值

```
外壳/main.js:15        const DSH_PORT = String(process.env.DSH_PORT || '3083');
工具/scene-bind.mjs:34 const PORT = Number(process.env.DSH_PORT || 3080);
```

- **同一事实**：「引擎端口默认是多少」。
- **两个值**：3083 / 3080。`scene-bind.mjs:20` 和 `:277` 的注释/帮助也写的是 3080，即**注释跟着代码一起走样**（两处都错得一致，更隐蔽）。
- **后果**：不设 `DSH_PORT` 时 `scene-bind` 连 3080，其余全部工具连 3083。若 3080 上另有引擎实例 → 绑到错实例、写错会话，且**不报错**（HTTP 连得上就继续）。
- **检查覆盖**：无。`文档命令体检` / `闭环断点体检` / `口径对齐` 都不比对端口常量。
- **置信度**：高（代码直读，两侧都在注释里明写默认值）。

### ★ 风险 2：token 正则**只对齐了长度下限，没对齐字符集**

检查用 `/token=\(\[[^\]]*\]\{(\d+),\}\)/`（`文档命令体检.mjs:330`）—— 只抓 `{N,}` 这个数字，字符类整体被 `[^\]]*` 吞掉。于是下面这些差异**永远绿**：

| 位置 | 正则 | 与标准形的差异 |
|---|---|---|
| `外壳/main.js:513` | `[A-Za-z0-9_\-]+` | **无长度下限** |
| `外壳/main.js:732` | `[A-Za-z0-9_\-]+` | 无长度下限 |
| `外壳/main.js:1424` | `[A-Za-z0-9_\-]+` | 无长度下限 |
| `外壳/main.js:4679` | `[A-Za-z0-9_\-]+` | 无长度下限 |
| `工具/整体体检.mjs:54`、`沙箱体检.mjs:126` | `[A-Za-z0-9_-]+` | **无长度下限** |
| 工具其余 10 处 | `[A-Za-z0-9_-]{20,}` | 标准形 |

- **同一事实**：「token 长什么样」。**同一条正则 `外壳/main.js` 内部就写了 4 遍**，工具里写了 12 遍。
- **未覆盖的差异**：① 有无长度下限；② `_\-` 与 `_-`（同一个字符类的两种写法，语义相同但文本不同，不利于批量比对）。
- **置信度**：高（正则与代码逐条读过）。

### ★ 风险 3：`工作台根路径` 有 4 处写死绝对路径

约 130 个工具用 `const WB = path.resolve(HERE, '..')`（可换盘符），但这 4 个写死：

```
工具/全场景检查.mjs:15   const BASE = 'D:/file/AI Temp/DeepSeek/Agent自研';
工具/切换provider.mjs:12 const WB = 'D:/file/AI Temp/DeepSeek/Agent自研/workbench';
工具/管线写入.mjs:5      const WB = 'D:/file/AI Temp/DeepSeek/Agent自研/workbench';
工具/闭环验证.mjs:34     const WB = 'D:/file/AI Temp/DeepSeek/Agent自研/workbench';
```

- **同一事实**：「项目根在哪」。设计上已明确改成按「与本工作台同级」推导（`外壳/main.js:95-97` 注释、`项目信息.md §39` 换电脑一比一复制）。
- **后果**：换盘符/换机器后这 4 个工具连到旧路径 —— 或更糟，旧路径**仍存在**（旧副本），于是读的是过期数据却不报错。
- **检查覆盖**：`废弃路径体检.mjs` 存在，是否覆盖这 4 个**需实跑确认**（我未执行，不写成结论）。

### ★ 风险 4：场景列表在工具里手写了一遍

```
工具/全场景检查.mjs:20-30  const SCENES = [{id:'hub',name:'中枢'}, ... 共 10 项];
```

- **同一事实**：「有哪些场景」。真源是 `数据/.dsh/场景记忆/_共享记忆/索引.json`（`外壳/main.js:842` 已按此读），`三方一致.mjs` 也在对账。
- **后果**：新建场景后该工具仍只检查那 10 个，**漏检且显示全绿**。这是典型的「清单写死 → 检查面慢慢落后于现实」。
- **检查覆盖**：`口径对齐.mjs` 查的是「场景数」多源一致，但**不查工具内数组**；`三方一致.mjs` 也不看 `SCENES` 字面量。

### 风险 5：同一个判据两处实现（作者自己已标注）

`工具/会话选择体检.mjs:48-50` 原文注释：

> `// 评分函数（与 main.js 的 ensureSceneSession 保持一致）`
> `// ⚠ 两处实现同一个判据是危险的（项目铁律 §1）。`

- 「同一事实」= 如何从 `session/list` 里挑会话。真源在 `外壳/main.js:4903-4962`（含 2026-11-11 那次「0 条不许新建」的关键修复）。
- **风险点**：那次修复只改 `main.js` 一侧；`会话选择体检` 若未同步，体检会按**旧判据**判「合格」，从而掩盖 main.js 的真实行为。
- **检查覆盖**：有（`会话绑定验证.mjs`），但它核对的是「期望 sessionId vs 实际 current」的结果，**不比对两份评分函数是否等价**。

### 风险 6：`turn/end` 判定 7 处各写一遍

同一事实「这一轮到底结束没有」，在 7 个文件各自实现：`投递通道.judgeTurnState:457`、`中枢代写:225`、`整体体检:237`、`自动回执:151`、`端到端闭环:177`、`封存集判分:285`、`沙箱体检:240`。

- 现有检查只断言「文本里出现过 `reason.kind`」（`文档命令体检:343` 的 `c.includes("lastEvent.type === 'turn/end'")`）。
- **漏洞**：写了 `reason.kind` 但判断条件不同（例如 `kind !== 'completed'` vs `kind === 'error'`）**照样通过**；`kind` 取值也不统一（`投递通道` 用 `completed`，其自测里又用 `done`，见 `:628`）。

## 三、结论

1. **本项目对「跨文件一致性」已有 5 个专用工具**（三方一致 / 口径对齐 / 工具去重体检 / 文档命令体检 / 闭环断点体检），说明这一类已被识别，不是盲区。
2. **但现有检查有一个共同盲点：只查「形式上有没有」，不查「实质是否等价」**。
   - token 正则：查长度数字，不查字符集。
   - `reason.kind`：查是否出现该字符串，不查判断逻辑。
   - 会话评分：查结果对不对，不查两份实现是否同构。
   - 与「机制盲区全是同一模式：只查存在不查效果」是同一个病根，只是搬到了跨文件层面。
3. **最危险的三个是「没检查」的那三个**：`DSH_PORT` 默认值（3083/3080）、写死的绝对路径（4 处）、工具里手写的场景列表。它们的共同点：**错了两边也都"看起来正常"，不会报错**。

## 四、建议（三档 + 归属）

### 立即可做

**建议 1：`DSH_PORT` 默认值统一到一处**
- 做什么：全部改为读同一个常量来源（如 `外壳/main.js:15` 或一个共享常量文件），`scene-bind.mjs` 的注释与帮助同步。
- 为什么有效：消除「不设环境变量就连错端口」这条静默失败路径。
- 怎么验证：不设 `DSH_PORT` 跑 `scene-bind.mjs`，观察它连 3083；把它临时改回 3080 应能复现失败。
- 代价：低（改 2 个文件 + 2 处注释）。
- 归属：**外壳/工具维护场景**（非故障分析，我只提不改）。

**建议 2：把 token 正则提取成单一常量，并让检查比对整个正则文本**
- 做什么：工具侧统一 `const TOKEN_RE = /token=([A-Za-z0-9_-]{20,})/`；`文档命令体检` 的判据从「抓 `{N,}`」改成「比对去掉空白后的正则字面量全等」。
- 为什么有效：字符集/下限/写法三类差异一次性覆盖，且检查本身也只有一处判据。
- 怎么验证：把任一工具的 `{20,}` 改成 `{30,}` 应红（现有行为保持）；再把字符集 `_-` 改成 `_\-` 也应红（**新能力**，改造前不会红）。
- 代价：中（12 个工具各改一行 + 检查器重写正则比对）。
- 归属：**外壳/工具维护场景**。

**建议 3：`全场景检查.mjs` 的 `SCENES` 改为读注册表**
- 做什么：删掉硬编码数组，改读 `索引.json`，与 `main.js:listScenarios()` 同源。
- 为什么有效：新场景自动纳入检查，不会漏检还显示全绿。
- 怎么验证：加一个临时场景 → 该工具应自动多检查一项；删掉数组但仍写死时不会。
- 代价：低。
- 归属：**外壳/工具维护场景**。

### 需要调查

**建议 4：先确认 `废弃路径体检.mjs` 是否覆盖 4 处写死路径**
- 做什么：读该工具判据，或实跑一次看是否报出 `全场景检查.mjs:15`。
- 为什么需要调查：我未执行该工具，不能断定「没检查」——可能是已覆盖但我没读到。
- 归属：**故障分析（我）下一轮自查**，或直接由工具维护场景实跑确认。

**建议 5：给「同一判据两处实现」加一个可执行的等价性检查**
- 做什么：对 `会话选择体检` 与 `main.js` 的评分函数，用同一批构造数据分别跑，比对排序结果。
- 为什么有效：这是唯一能证明「两份实现真的等价」的方法，比读代码可靠。
- 怎么验证：故意把一侧的排序改错，检查应红。
- 代价：高（需要构造数据 + 两侧可被 import）。
- 归属：**外壳/工具维护场景**。

### 可忽略

**建议 6：`_\-` 与 `_-` 写法差异**
- 为什么可忽略：语义完全相同，不影响抓取；若建议 2 落地会顺带统一。
- 单独为它做检查不值得。
