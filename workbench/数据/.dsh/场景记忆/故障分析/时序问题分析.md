# 时序问题分析

> 时序问题 = 依赖「某个东西先就绪」，但实际还没就绪（或等的方式不对）。
> 与「假成功」的区别：假成功是「返回成功但没做」，时序问题是「前提没满足却继续/或瞎等」。

## 一、三张「等」的地图

### 1. 等引擎（端口就绪）

| 位置 | 方式 | 判据 |
|---|---|---|
| `外壳/main.js` `startServer()` L753-771 | 轮询 `probe()`（300ms） | 端口 3080 是否 listen，budget 45s/90s，提前退出 |
| `外壳/main.js` `startServer()` L726 复用分支 | 不轮询，`probe()` 一次即判「复用外部引擎」 | 端口已 listen → 直接走 foreign 分支 |
| `工具/全场景验证.mjs` `waitEngineReady()` L91-101 | 轮询 `Get-NetTCPConnection -LocalPort 3083`（500ms） | 60s deadline |
| `工具/全场景检查.mjs` L96-102 | 轮询 CDP `document.title`（1s × 60，但 `i>50 break` 实际只到 51s） | 标题能读到即认为「引擎+渲染就绪」 |

### 2. 等 token

| 位置 | 方式 | 判据 |
|---|---|---|
| `外壳/main.js` `captureToken()` L512-517 | 事件驱动：正则解析引擎 stdout 里的 `?token=…` | 引擎自己启动时，从输出流实时抓 |
| `外壳/main.js` `startServer()` L730-734 | 复用分支：从 `LOG_FILE` 历史 `hist.match(/token=…/)` 找 | 仅当「我们自己曾拉起过它」才对 |
| `外壳/main.js` `getHarnessUrl` L1420-1428 | 三来源 fallback：env → harnessToken → 再读日志（`matchAll` 取最后一个） | AC-017 的修复 |
| `外壳/main.js` `ensureSceneSession` L1893-1896 | **没等**：`if (!token) return 报错` | token 不在就直接失败 |

### 3. 等会话（sessionId）

| 位置 | 方式 | 判据 |
|---|---|---|
| `外壳/main.js` `ensureSceneSession` L1865-1881 | ② 场景 JSON 里的 sessionId **只缓存不验证** | 占位符 sessionId 会被当真的用（不查引擎） |
| `外壳/main.js` `ensureHubSession` L4903-4951 | 先 `session/list`，**0 条=引擎没就绪→返回 retry，不新建** | 2026-11-11 修：旧代码 0 条就新建→每次重启丢历史 |
| `外壳/main.js` `ma:ensure-session/page/send` L4966-5019 | `hubSessionId || ''`，空则 `missing sessionId`，**没等** | 不轮询不重试 |
| `工具/scene-bind.mjs` | `session/create` 试 4 种参数 + 8s/20s timeout | 靠 HTTP timeout 兜底 |

## 二、三类等待策略（核心结论）

### A. 固定 sleep —— 最容易错，最该消灭

| 位置 | 固定值 | 问题 |
|---|---|---|
| `工具/全场景验证.mjs` L182 `等渲染` | `setTimeout 15000` | 无条件 15s：引擎快则白等，慢则不够，截图可能拍到半成品 |
| `工具/全场景检查.mjs` L105 `sleepMs(3000)` | 3s | 「等面板数据加载」但无判据，面板慢于 3s 就拍到空 |
| `工具/全场景检查.mjs` `sleepMs()` L32-34 | 用 `spawnSync(node,'-e','setTimeout')` 真睡 | 每处都要另起 node 进程，本身就是「没有真正等待机制」的补丁 |
| `工具/投递通道.mjs`（旧） | `sleep(waitMs||8000)` | 已修（见 §三 断点5）：固定 8s 必在跑，又白等又不够 |

### B. 轮询（有条件退出）—— 正确做法

| 位置 | 轮询间隔 | 退出条件 |
|---|---|---|
| `startServer()` | 300ms | `probe()` 端口就绪，或进程早退 |
| `waitEngineReady()` | 500ms | 端口 3083 Listen |
| `全场景检查.mjs` | 1s | CDP 读到标题 |
| `投递通道.mjs` ④ | 2s | `turn/end` + `reason.kind==='completed'`，上限 180s |

### C. 没等（直接失败/降级）—— 隐形的时序 bug

| 位置 | 后果 |
|---|---|
| `ensureSceneSession` L1894 无 token 直接 return | AI 面板「token 缺失」，且**没有 retry 语义** |
| `ensureSceneSession` ② 只缓存不验证 sessionId | 占位 sessionId 被当真的 → 面板空/发错会话 |
| `ma:send/page` 空 sessionId 直接 `missing sessionId` | 面板先于会话就绪时直接失败 |
| `harness:ready` L1435 只返回布尔快照 | 只表示「那一刻」状态，不阻塞等待 |

## 三、已出事故事例（时序类）

- **AC-017（AI 面板 token 缺失）**：引擎先于工作台启动 → `probe()` true → 走 foreign 分支 → 只认 `DSH_ENGINE_TOKEN`，没 token 就返回无 token URL。修复即 `getHarnessUrl` 的三来源 fallback（main.js L1408-1428）。
- **断点5（投递通道固定 sleep 8s）**：`await sleep(waitMs||8000)` 判状态，AI 任务 1-5 分钟，8s 必还在跑 → 误判「仍在运行」。修复即轮询 `turn/end`（投递通道.mjs L502-549）。
- **中枢会话丢历史（main.js L4934-4945 注释）**：面板比引擎先就绪 → `session/list` 返回 0 条 → 旧代码误当「确实没有会话」→ 新建 → 每次重启丢对话。修复：0 条/listOk=false 时返回 `retry:true` 让调用方继续等。

## 四、结论与改进建议

1. **固定 sleep 是时序问题的头号来源**：3 处仍在使用（全场景验证 15s、全场景检查 3s、`sleepMs` 机制本身）。它们的共同缺陷是「不知道等到没有」，只能赌一个时长。
2. **正确范式 = 轮询 + 明确的退出条件 + 上限**：`startServer` 的 300ms probe、`投递通道` 的 `turn/end` 是范本。
3. **「没等」比「瞎等」更隐蔽**：`ensureSceneSession` 无 token 直接 return、sessionId 只缓存不验证，都属于「前提没满足却不当回事」，症状上表现成别的故障（token 缺失、面板空），所以更该在编码时显式区分「引擎未就绪」和「确实没有」。
4. **复用外部引擎的 token 依赖日志历史，是脆弱假设**：token 是否在日志里、日志是否被截断/清空，决定了 token 能否找回——本质仍是时序（token 先出现 vs 我们后读）。
