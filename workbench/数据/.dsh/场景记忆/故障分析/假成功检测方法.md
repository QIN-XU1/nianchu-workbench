# 假成功检测方法

> 场景：故障分析 ｜ 日期：2026-11-12
> 主题：**假成功** = 返回成功 / 显示通过，但实际没做到。
> 素材：`数据/.dsh/事故档案/事故档案.json`（26 条）+ 前几轮红队发现。

---

## 1. 定义与判据

- **静默失败**：什么都没返回，悄悄失效（无信号）。
- **假成功**：**明确返回了成功信号**（PASS / ok:true / 已投递 / 已完成 / 文件在），但事实没做到。

判据：**「成功信号」和「事实」是两套独立状态机。** 假成功 = 这两套状态脱钩：信号为真，事实为假。检测的唯一入口，是**检查「成功信号」有没有绑定一条可反查的证据**，而不是检查结果本身。

## 3. 检测方法（每种落到具体代码）

### 方法 1：反例强制 —— 检查必须带一条「应当失败」的样本

**对付 A 类（检查永远 PASS）。** 检查显示 PASS 不算数，必须证明「有坏数据时它会红」。

落地：`工具/机制审计.mjs` 第 4 步逐项检查是否有 ≥2 处「反例」，缺则判「口号」；每个哨兵带 `.selftest` 跑固定坏样本。

```js
// 反例写法：故意造一条不含 §五 的记忆，确认内容哨兵会 push diff
if (!hasLearn) {
  diffs.push('场景记忆缺 §五（坑与决策）');   // ← 必须进 diffs
  stats['noLearn_' + name] = true;           // ← 只写 stats = 装饰，不算拦截
}
// 判据：这段代码执行后 diffs 会不会变长？不变长就是装饰（AC-001 的根因）
```

### 方法 2：真实执行验证 —— 用「真 import/真运行」替代「语法检查」

**对付 A 类（`node --check` 造假成功）。** 语法检查只查括号配平，查不出「变量未定义 / 模块加载失败」（AC-019、AC-022）。

落地：把 `node --check` 换成真实 import：

```bash
# 坏：只查语法，AC-022 的多余 } 和 AC-019 的未定义都查不出
node --check 工具/xxx.mjs

# 好：真实执行，加载失败会 catch 到
node --input-type=module -e "import('./外壳/xxx.mjs').then(m=>console.log('OK',Object.keys(m))).catch(e=>console.log('FAIL',e.message))"
```

### 方法 3：解包校验 —— 读 api 返回值先 dump keys，再解包

**对付 B 类（`ok:true` 但 value 空）。** AC-023 的根因是读成顶层字段。

落地：统一解包函数 + 使用前先 dump 结构：

```js
// 包装层 { ok, value, error } —— 拿到手先看 keys
const raw = await api.drives();
if (raw && 'value' in raw) return raw.value;   // ← 正确解包
// 反例：return raw.drives;  ← 读到 undefined（AC-023 的坑）
```

### 方法 4：fail-open 审计 —— 抓「空 catch / catch 无日志」

**对付 B 类（异常被吞却返回成功）。** AC-009、AC-010 都是 `catch {}` 吞掉 `require`/`SCEN_DIR` 错误，流程继续走、数据照样丢/没写。

落地：grep 所有静默 catch：

```bash
# 命中空 catch 或 catch 块内无 console.error 的，逐个查
grep -rn "catch\s*{" 工具/ 外壳/  | grep -v "console.error"
```

判据（AC-010 的教训）：写 `catch {}` 时问一句——**如果这里抛的是我自己的 bug，我多久能发现？** 持久化/归档/备份类操作的 catch 不能 fail-open，失败必须阻断。

### 方法 5：声明绑定证据 —— 状态翻转必须带可反查证据

**对付 C 类（「已投递/已回执/已完成」是自我声明）。**

落地：`派单.mjs` 只在真实投递成功后才翻状态：

```js
const r = await deliverDispatch(client, d, { waitMs: 8000 });
if (!r.ok) { console.error('投递失败'); process.exit(2); }  // 失败不翻状态
d.state = STATE.DELIVERED;      // 只有 r.ok 才走到这（派单.mjs 361 行）
d.deliveredSession = r.sessionId;  // 绑定真实会话证据
```

回执同理：`派单.mjs --ack` 强制 `evidence` 且 `≥ MIN_EVIDENCE_LEN(20)` 字符，否则 exit 2。

### 方法 6：存在 ≠ 功能 —— 三层体检（大小 / 真数据加载 / 无占位字样）

**对付 D 类（文件在 / 面板在 ≠ 功能有）。** AC-018 的三个判据直接可落地：

```bash
# 1) 文件大小：转发壳只有 0.2KB，真实现 > 1KB
Get-ChildItem 外壳/scenarios/*.js | Sort-Object Length | Select-Object Name,Length

# 2) 真数据加载：源码里必须有 await api.xxx() / fetch(，不能只有 emptyState()
grep -rn "await api\.\|fetch(" 外壳/ | Select-String -NotMatch "emptyState"

# 3) 占位字样：不能出现「待接入/未配置/TODO」
grep -rn "待接入\|未配置\|TODO" 外壳/
```

### 方法 7：观测先行 —— 前端报错必须可见

**对付 D 类（「没报错」其实是看不到）。** AC-025 的结论：没有日志的调试就是猜谜。

落地：`main.js` 里转发渲染进程 console：

```js
app.on('web-contents-created', (_e, wc) => {
  wc.on('console-message', (_ev, level, msg) => { /* 写 server.log 带 [renderer] 前缀 */ });
});
```

查：`Select-String -Path workbench/外壳/server.log -Pattern "\[renderer\]"`；或 `工具/Cdp.mjs --eval / --dump` 直查 DOM 状态。

## 5. 结论

假成功的共同根因一句话：**成功信号是「声明」，事实是「状态」，两者之间缺一条反查。**

检测的统一原则：**给每一个「成功信号」配一条「必须真实执行的反查」**——
- 检查 PASS → 配「会失败的反例」
- `ok:true` → 配「dump keys 后解包」
- `--check` 通过 → 配「真 import」
- 状态已投递 → 配「投递回执 sessionId」
- 文件在 → 配「>1KB + 有真数据加载 + 无占位字样」

**风险最高的是 D 类**：报错至少知道坏了，「待接入」看起来像功能，用起来才发现什么都没有（AC-018）。
