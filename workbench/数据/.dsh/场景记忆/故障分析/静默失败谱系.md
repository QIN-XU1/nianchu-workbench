# 静默失败谱系

> 场景：故障分析 ｜ 日期：2026-11-12
> 主题：**静默失败 = 不报错，但功能没生效。**
> 来源：`数据/.dsh/事故档案/事故档案.json`（25 条）、`数据/.dsh/机制盲区.json`（49 条机制盲区）、`工作区/工具/` 下的检查工具。

---

## 0. 定义与范围

静默失败有两类来源，本谱系都纳入：

1. **代码层的静默失败**：功能代码执行了、没抛错，但结果没生效（事故档案里的一类）。
2. **检查层的静默失败**：检查器「通过」了，但没抓住真实问题——这是「永远通过」的检查（`机制盲区.json` 49 条全是这种：只查 A 不查 B）。

**共性**：两类都是「**表面正常，实质没生效**」。前者骗使用者，后者骗检查者自己。

## 1. 谱系表（6 类根因）

| 类型 | 典型表现 | 真实案例 | 检测方法 | 预防措施 |
|---|---|---|---|---|
| **① 结果没被使用**（写了但没人读） | 值写进了某个结构，但下游判定读的是另一个结构，于是「记录」≠「判定」，检查永远通过 | AC-001 内容哨兵 `stats['noLearn_'+name]=true` 只写统计对象、从不 push 进 `diffs`，体检只看 `diffs` → 永远 PASS；机制盲区「健康哨兵」「进度判定」同款 | 变异测试：故意造一条违规输入，看 `diffs`/判定结果会不会变；grep 写入口与判定读取入口是否同一变量 | 写检查先造反例（`.selftest.mjs`）；「记录」和「判定」必须指向同一数组；跑 `工具/变异测试.mjs` 注入 bug 看检查红不红 |
| **② 异常被吞**（fail-open 的 `catch{}`） | try/catch 吞掉 ReferenceError/TypeError，程序继续跑，功能静默失效且无日志 | AC-009 归档 `catch` 吞 `require is not defined`，看板照删、数据真丢；AC-010 画像段 `catch { /* fail-open */ }` 吞 `SCEN_DIR` 未定义，体积纹丝不动 | 静态扫描所有 `catch {}` 空块 / catch 内无 `console.error` 的块；注入 undefined 变量看是否被吞 | fail-open 的 catch 必须至少 `console.error` 一次；持久化操作失败必须**阻断**（原子操作）；判据「这里抛的是我自己的 bug，我多久能发现」 |
| **③ 值没被正确读取/解包**（层级或来源错） | 数据其实在、也传过来了，但读错了层/读错了字段，拿到 undefined 或空数组，界面显示「0」或空白 | AC-023 api 包一层 `{ok,value}`，面板读 `r.drives`（顶层字段），永远空；AC-020 `reviewDir` 是全局单例，所有场景「审查文档」都指向「自我复盘」目录 | 底层确认数据对后，`dump` 上层对象的 `Object.keys()`；扫描 `await api.` 后面是否跟着 `Unwrap`/`.value` | 调用 api 先问「这层有没有包」，统一 `rvUnwrap` 解包；「数据对不对」和「数据在哪一层」是**两个独立问题**，分开查 |
| **④ 失败回调/监听器缺失**（错误无处发声） | 底层确实失败了，但没有任何回调把错误传出来，界面纯黑空白或假正常 | AC-021 `<webview>` 没监听 `did-fail-load`，加载失败一片黑；AC-025 渲染进程 console 从未转发，前端 ReferenceError 全部无声 | 对每个异步/嵌入组件问「失败时走哪个回调」；grep `did-fail-load`/`console-message`/`render-process-gone` 是否注册 | embed/webview/进程边界必须注册失败事件；渲染进程 console 转发是**基础设施**，先建观测再排查 |
| **⑤ 占位/假实现**（看起来像功能） | 界面元素齐全、状态正常，点进去却是「待接入」占位，或产出的是空话 | AC-018 9 个面板 8 个是占位，只有 embed 真；机制盲区「自动回执」「场景互问」（「已修复」实际没修、答非所问也能过闸） | 逐面板走真实用例，验证「有没有产出实质结果」，而非只看「是否注册」；界面回归 + 截图 | 验收标准要「能看到真数据/真效果」，不能只看「面板挂载成功」；占位必须显式标 TODO 且**不进入验收** |

## 2. 关键发现：检查层的静默失败是「同一条模式重复 49 遍」

`机制盲区.json` 的 49 条，**几乎每一条都是同一个句式**：

> 「只查 X（字段存在/格式对/数量够），不查 Y（内容对不对/效果有没有）。」

例子：

| 机制 | 只查（能通过） | 不查（静默失败点） |
|---|---|---|
| 内容哨兵 | 关键节是否存在 | 写得对不对、是否过时 |
| 记忆哨兵 | 字节数 | 内容质量（4096 字节废话也过） |
| 派单哨兵 | 台账字段自洽 | 是否真投递到对方会话 |
| 备份完整性 | 文件数量/hash | 备份能不能真恢复（没演练过） |
| 场景互问 | 问答流程 | 回答质量（答非所问也过闸） |

**结论**：这些检查「永远通过」的原因，不是没写检查，而是**检查只覆盖了「可枚举的表层条件」，没有覆盖「实际效果」**。表层条件永远能满足 → 检查永远绿 → 出问题时它一声不吭。

## 3. 结论：怎么系统性地发现静默失败

静默失败的本质是「**没报错**」，所以靠「等它报错」是永远发现不了的。必须反过来——**默认假设「通过」是要被证伪的**。

五条系统性发现方法（按优先级）：

1. **反例强制**：每个检查器上线前，必须能写出一条「应当失败的反例」。写不出反例 = 规则没搞清 = 装饰。落地成 `.selftest.mjs`，和检查器同目录同跑。

2. **变异测试**：故意往系统里注入已知 bug（改一个字段名、删一个变量、换一个路径），看检查器会不会红。不红 = 检查是摆设。参考 `工具/变异测试.mjs`。

3. **失败路径审计**：对每处 `catch{}`、每个异步/嵌入组件、每个进程边界，问一句「失败时它会说什么」。空 `catch{}` 和缺失的 `did-fail-load`/`console-message` 就是静默失败的温床，用 grep 扫出来。

4. **观测先行**：先建三层观测能力（渲染进程 console 转发 → CDP 直连查状态 → 截图看效果），再动手排查。没有观测，一切「没反应」都只能靠猜。

5. **效果验收，而非存在验收**：把验收判据从「面板注册了吗 / 字段填了吗 / 数量够吗」升级成「能拿到真数据吗 / 点下去有真反应吗」。占位、空话、假数字全部在这一关被挡下。

**一句话总纲**：静默失败杀不掉，是因为所有检查都在查「有没有」，没在查「对不对」。把每个「存在性检查」换成「反例 + 变异」这两个会真的失败的检查，静默失败就无处藏身。
