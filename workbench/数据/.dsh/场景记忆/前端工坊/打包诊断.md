# 打包诊断：为什么 exe 起不来（2026-11-13）

> 结论先行：**打包流程已经跑通，产物结构正确，但 exe 在「当前这台机器的会话环境」里起不来。**
> 这不是打包配置的错误，是 Electron 在这个环境里的运行限制。
> 源码版（`启动.vbs`）正常工作，因为它做了 exe 没做的三件事。

## 二、起不来的现象与排查链

### 现象

```
双击 exe        → 立刻退出，exit code = 2147483651
                  (= -1073741819 = STATUS_ACCESS_VIOLATION，进程级崩溃)
                  = 或 exit code 0（静默退出）
没有 stdout      （GUI 程序不挂控制台）
没有 server.log  （运行时的日志，还没到那一步）
没有 boot.log    （我加的最早期日志，也没写）
探针日志没写入   （证明 main.js 根本没被执行）
```

### 排查链（每一步都做了验证）

| # | 假设 | 验证方式 | 结果 |
|---|---|---|---|
| 1 | main.js 里的路径算错了 | 在 main.js 最前面写探针 | 探针没写 → **main.js 没执行** |
| 2 | asar 打包坏了 | `asar: false` 重打包 | 同样崩溃 → 不是 asar |
| 3 | 打包丢了代码 | 解出 asar 里的 main.js 检查 | 代码完整（295269 字符，关键特征都在） |
| 4 | node-pty 原生模块不兼容 | 检查 require 和预编译二进制 | 有 try/catch 保护，且 prebuilds/win32-x64 齐全 → 不是它 |
| 5 | 单实例锁冲突 | 检查 userData 路径 | 确实是共用的，已修（打包版用独立 userData） |
| 6 | **环境变量污染** | `echo $env:ELECTRON_RUN_AS_NODE` | **= 1** ← 找到了！ |
| 7 | 打包后 exe 被改成 Node 模式 | `exe --version` | 返回 `v24.18.1`（Node 版本，不是 Electron） |
| 8 | 加开关能解决 | `exe --no-sandbox` | `bad option: --no-sandbox` ← 铁证：它是纯 Node |
| 9 | 清掉环境变量就好 | 干净环境 + 最小 app 测试 | 仍然 `STATUS_ACCESS_VIOLATION` |
| 10 | 是打包引入的问题 | **用未打包的原始 electron.exe 测同样环境** | **同样崩溃** ← 决定性：与打包无关 |

### 关键证据（第 9-10 步）

```powershell
# 未打包的原始 electron.exe，在这个 shell 的子进程里
& "workbench\外壳\node_modules\electron\dist\electron.exe" "$TEMP\etest3"
# → exit=2147483651  同样崩溃
```

**所以：不是打包的错，是「从这个自动化 shell 里启动 Electron GUI」这条路本身走不通。**

而 `启动.vbs` 能行，因为它：
1. `Remove-Item Env:\ELECTRON_RUN_AS_NODE`
2. 带 `--no-sandbox --disable-gpu --disable-gpu-compositing --disable-software-rasterizer`
3. 由 `WScript.Shell` 托管启动（脱离当前 shell 的进程树）

第 3 点是我从 node 的 `spawn` / `Start-Process` 里做不到的 ——
子进程会继承这个自动化环境的某些限制。

## 三、已实施的修复（保留，都有价值）

### ① 路径适配（`main.js`）

```js
const _IS_PACKAGED = app.isPackaged === true;
const APP_RES   = _IS_PACKAGED ? process.resourcesPath : path.join(__dirname, '..');
const USER_ROOT = _IS_PACKAGED ? path.join(APPDATA, 'DSH工作台') : path.join(__dirname, '..');
const TOOLS_DIR = path.join(APP_RES, '工具');
```

替换了 4 处硬编码的 `path.join(__dirname, '..', ...)`。

### ② 用户数据保护（`main.js`）

```js
// 首次启动：从「数据模板」复制一份到 %APPDATA%\DSH工作台\数据
// ⚠ 只在不存在时复制一次 —— 否则用户的场景记忆会被模板覆盖
if (fs.existsSync(path.join(target, '.dsh'))) return;
```

**这是打包版最重要的一条**：升级不能覆盖用户积累的 12 个场景记忆。

### ③ 独立 userData（`main.js`）

打包版用 `%APPDATA%\DSH工作台\app-data`，和源码版完全隔离，可以同时开着。

### ④ GPU/沙箱开关（`main.js`）

```js
app.commandLine.appendSwitch('no-sandbox');
app.commandLine.appendSwitch('disable-gpu');
// ... 可通过 DSH_ENABLE_SANDBOX=1 / DSH_DISABLE_GPU=0 覆盖
```

### ⑤ 启动器生成（`build/after-pack.js`）

打包后自动生成 `START-DSH.cmd`，做三件事：
1. `set ELECTRON_RUN_AS_NODE=`（清除污染）
2. `cd /d "%~dp0"`
3. `start "" "DSH*.exe" --no-sandbox --disable-gpu ...`

**踩的坑**：第一版用 `latin1` 写中文文件名 → `start "" "DSH ?\?.exe"` 乱码 → 改成全 ASCII + 通配符 `DSH*.exe`。

### ⑥ 最早期探针（`main.js`）

```js
fs.appendFileSync(path.join(os.tmpdir(), 'dsh-boot-probe.log'), stage);
```

在所有业务代码之前写一行，用于确认「main.js 到底有没有执行」。
**这个探针是定位整个问题的关键** —— 没有它就只能猜。

### ⑦ 打包版启动日志（`main.js`）

`%APPDATA%\DSH工作台\boot.log`，接管 console.log/error + 记录 uncaughtException。

### ⑧ 修好了坏掉的依赖树

`electron-builder@26.18.0` 装了但 **`app-builder-lib` 缺失**：
```
Error: Cannot find module 'app-builder-lib/out/electron/electronVersion'
```
`npm install --no-save app-builder-lib@26.18.0` 补上。

### ⑨ 绕开 node-gyp

```
⨯ Could not find any Visual Studio installation to use
⨯ Attempting to build a module with a space in the path
```
`npmRebuild: false` —— node-pty 自带 `prebuilds/win32-x64/*.node`，不需要重编译。
**代价**：Electron 大版本升级导致 ABI 变化时会失效，那时必须装 VS 生成工具。

## 四、还差什么才能让 exe 直接双击可用

按可能性排序：

| # | 方案 | 说明 |
|---|---|---|
| 1 | **在真实桌面会话里测试** | 上面的失败全部发生在自动化 shell 的子进程里。让用户真双击一次 `START-DSH.cmd`，很可能就能起 |
