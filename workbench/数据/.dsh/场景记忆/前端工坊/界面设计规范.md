# 界面设计规范 · 2025 AI Agent 产品对标

> 场景：前端工坊｜产出物：可直接写进 CSS 的设计规范 + 12 场景重设计建议
> 调研时间：2026-11-13｜抓取方式：Invoke-WebRequest / HttpClient（未用 web_search）
> 适用：`workbench/外壳/ui/styles/*.css`（Electron 工作台，默认暗色，12 场景网格）

---

## 〇 结论先行（5 条规则）

1. **层次靠明度差，不靠阴影**。7 级表面，相邻层对比度 **1.10–1.16**。低于 1.05 = 看不见，高于 1.30 = 塑料卡片感。我们当前只有 **1.02–1.11**，所以"面板糊成一片"。
2. **圆角只走小阶梯**：`0 / 4 / 6 / 8` 四档，**面板 6px、控件 4px、浮层 8px**。28px 那种大圆角是 marketing 页的，密集工具界面用了就废。
3. **一个强调色，最多加两个状态色**。2025 的成品页面全部是"近黑底 + 单色强调 + 语义色只做小面积"。我们的青/黄/赤/朱殷四色并列 + warn 与 err 色相差仅 **3°**，人眼分不清。
4. **AI 对话不做气泡，做通栏流**。Assistant 消息无背景无边框、通栏；只有用户消息有 8px 圆角浅底。流式输出用**块级插入 + 光标**，不用打字机抖动。
5. **多面板用「主从」不用「均匀网格」**。主流（Cursor / Windsurf / Linear / Claude）全是 **主工作区 + 固定宽右栏**。均匀网格只适合同质面板（仪表盘），不适合"预览 / 代码 / 文档 / AI"这种异质面板。

### 1.3 一个架构事实（决定了整套配色）

`外壳/ui/panels/harness.js:163-167` 显示 AI 面板是 **Electron `<webview>` 内嵌 DSH 前端**：

```js
wv = document.createElement('webview');
wv.style.cssText = '...;background:#fff;...';   // ← 白底！
wv.setAttribute('src', url);                     // 127.0.0.1:3080
```

而 `外壳/ui/core/theme.js` **没有任何 `insertCSS` / `executeJavaScript` 注入主题的代码**（已 grep 确认：无 `insertCSS`）。

⇒ **我们改不了 AI 面板内部的样式**。它按 DSH 自己的亮/暗主题渲染。
⇒ **推论：外壳的色板必须和 DSH 暗色对齐**，否则 AI 面板和周围面板是两个世界。这是本次规范把表面梯改成 DSH 数值的**硬理由**，不是审美偏好。

## 二 设计语言共识（2025 通行标准）

### 2.1 配色

**底色不是纯黑，是"近黑带一点点蓝"**：`#0A0B0D ~ #151517`。纯黑 `#000` 会产生 OLED 拖影 + 边界消失。

**层次 = 7 级明度，相邻差 1.10–1.16**（实测三个系统都在这区间）：

| 来源 | 相邻层对比度 |
|---|---|
| Linear level0→3 | 1.05 / 1.04 / 1.05 |
| **DSH 暗色** | **1.16 / 1.13 / 1.15** |
| 我们 guoxue（现状） | 1.02 / 1.03 / 1.06 / 1.07 / 1.10 / 1.11 |

Linear 的 1.05 是因为它靠**描边**辅助分隔；DSH 不靠描边所以拉到 1.13+。我们既没有够强的明度差也没有足够清晰的描边，两头不靠 → 糊。

**强调色只有一个**。Linear `#7170ff`（紫蓝）、DSH `#5686FE`（蓝）、Raycast 用中性白。**没有一家用青色**。
我们用的 `#6FB0DC` 石青本身没问题（对比度 8.2:1 够），但**同时还有藤黄/赤/朱殷**，四色并列就是 2019 年的"彩色仪表盘"。

**语义色必须色相分离 ≥30°**：

| 我们的状态色 | 色相 | 问题 |
|---|---|---|
| `--gu-huang` `#C9A227` | 46° | 黄 = ok |
| `--gu-chi` `#E68069` | 11° | **warn** |
| `--gu-err` `#EC6B58` | 8° | **err** |
| `--gu-qing` `#6FB0DC` | 204° | info |

**warn(11°) 与 err(8°) 只差 3°** → 红橙色盲 + 正常视力都难区分。必须拆开。

### 2.2 字体

- **UI 字体**：系统字体栈。2025 没人再在工具界面加载 Inter webfont 当正文（Linear 只在 marketing 用 `Inter Variable`）。中文环境用 `system-ui` 走 Segoe UI / PingFang / 微软雅黑。
- **等宽**：用于**数字、ID、代码、状态标签**，不用于正文。Cursor 出现 135 次 `--font-monospace` 就是这个用法。
- **字号**：密集工具界面集中在 **11 / 12 / 13 / 14 / 16**。Linear 最多的是 13px（24 次）和 12px（21 次）。**正文 13px，不是 14 或 16**。
- **字重**：只用 `400 / 500 / 600`。Linear 里 500 最多。**不要 700**（除了极少数标题）。
- **字距**：大字号用负值 `-0.02em`，小字号 0，全大写标签 `+0.06em`。中文**永远不要**负字距。

### 2.3 圆角

共识是**小阶梯、按控件尺寸分级**：

| 尺寸档 | 取值 | 用于 |
|---|---|---|
| 0 | `0` | 分割线、满宽容器、表格行 |
| XS | `4px` | 按钮、输入框、标签、下拉 |
| SM | `6px` | **面板、卡片** |
| MD | `8px` | 浮层、弹窗、消息气泡 |
| Full | `999px` | 头像、开关、状态胶囊 |

**反例**：Linear 虽然有 24px，但那是 marketing 卡片；DSH 有 28px 是聊天 App 的输入框。**我们的多面板工作台用 6px 面板 / 4px 控件**，超过 8px 就"每块面板像一张卡片"，12 个面板 = 12 张卡片 = 视觉噪音。

### 2.4 间距

**4 基，但核心是 8 的倍数**：`2 / 4 / 6 / 8 / 12 / 16 / 24 / 32 / 48`。
Linear 频次：8px(59) > 6px(44) > 12px(37) > 4px(35)。
**面板内边距 8px，面板间距 8px，分组间距 12px，区块间距 16px。**

### 2.5 阴影

2025 的共识是：**阴影极淡 + 亚像素描边 + 内高光**。

```css
/* Linear */
box-shadow: 0 1px #0006;                      /* 1px 硬边，不是模糊 */
box-shadow: 0 4px 32px #08090a99;             /* 只有浮层 */
/* Raycast */
box-shadow: inset 0 1px #ffffff1a;            /* 内高光，最常用 */
/* DSH */
box-shadow: 0 0 0 .5px <border>, 0 3px 8px #00000008, 0 0 16px #00000005;
```

**规则**：面板层次**不用阴影**（用明度）；阴影只给浮层（菜单/弹窗/toast），且 alpha ≤ 0.08。

### 2.6 动效

| 场景 | 时长 | 缓动 |
|---|---|---|
| 颜色/边框变化 | `90–140ms` | `ease-out` |
| 位移/展开折叠 | `180–240ms` | `cubic-bezier(.22,1,.36,1)` |
| 浮层进出 | `200–260ms` | `cubic-bezier(.32,.72,0,1)` |
| 流式光标 | `1000ms` | `steps(2)` 或 `linear` 循环 |

**没有一家用 >300ms 的界面动效**。缓动值集中在 `(.22,1,.36,1)`、`(.4,0,.2,1)`、`(.23,1,.32,1)`。`ease` / `linear` 已经是过时写法。

### 3.4 强调与语义（色相分离，全部 ≥30°）

```css

  --accent-line:   rgba(122,170,255,.40);

  /* 语义（色相：ok 149° / warn 36° / err 2° / done 255°；两两间距 ≥34°） */
  --ok:        #4EC98A;   /* 149°  panel 7.51:1 / raised 6.67:1 */
  --ok-soft:   rgba(78,201,138,.14);
```

### 3.9 动效

```css
:root {
  --dur-1: 90ms;    /* 颜色、背景、边框 */
  --dur-2: 140ms;   /* 主过渡（hover/active 全套） */
  --dur-3: 200ms;   /* 展开/折叠、面板出现 */
```

## 四 布局规范

### 4.1 我们的现状：为什么"一言难尽"

`fe-preview(3×5) + fe-files(2×2) + fe-board(1×2) + fe-ai(2×7)` = **5 列 × 7 行均分网格**。
`panels/grid.js:199-202` 实际写入：

```js
gridEl.style.gap = 'var(--sp1, 4px)';            // → --space-2 = 4px
gridEl.style.gridTemplateColumns = 'repeat(5, minmax(0,1fr))';
gridEl.style.gridAutoRows = 'minmax(0, 1fr)';    // ★ 行高均分，无最小值
```

**实测后果**（chrome = 标题栏 40 + 场景栏 34 + 底栏 24 = **98px**；gap 4px、padding 4px、7 行 5 列）：

| 分辨率 | 每列宽 | 每行高 | 1 行面板 | 2 行面板 | 2 行面板内容区（减 26px 头） |
|---|---|---|---|---|---|
| 1920×1080 | 379px | 135px | 135px | **274px** | 248px |
| 1600×900 | 315px | 110px | 110px | 224px | 198px |
| 1366×768（主流笔记本） | **268px** | 91px | 91px | **186px** | **160px** |
| 1280×720 | 251px | 84px | 84px | 172px | 146px |

- 1366 下**每列 268px < 280px 可读下限**；1280 下更差（251px）
- **2 行面板在 1366 下只有 186px**，扣掉面板头 26px = **160px 内容区** ≈ 8 行 12px 文字 / 5 行表格 → 面板基本没法用
- `gridAutoRows: minmax(0,1fr)` 意味着**窗口越矮面板越矮，没有下限**，缩到 600 高时面板头（26px）都放不下

### 4.2 主流怎么做

| 产品 | 组织方式 |
|---|---|
| Cursor / Windsurf | **主编辑区（可上下分屏）+ 右侧固定宽 AI 栏**；左活动栏 44px 图标；底部终端抽屉 |
| Linear | 左侧导航栏（可收起 240→44）+ 主列表 + **右侧详情栏（按需出现）** |
| Claude | 左侧会话列表 260px + 主对话流（max-width 720px 居中） |
| Raycast | 单窗口命令面板，**无多面板**（唯一例外） |

**结论：没有一家用「均匀网格」放异质面板。** 均匀网格只适合同质卡片（监控大盘、图片墙）。

## 六 12 个场景重新设计（每个一句话 + 落点）

> 统一前提：**AI 面板永远在右侧固定栏**（`--w-ai: clamp(320px,34vw,480px)`），不参与网格；`hub` 例外（见 6）。

**12 场景的统一结构**：

```
场景 = 主区（8/12）+ 辅区（4/12）+ AI 右栏（固定）
      主区 = 该场景的核心产出物（预览/文档/源码/表格）
      辅区 = 元信息（看板/文件树/证据/状态）
     AI 右栏 = 恒定，不随场景变
```

这样做的收益：**12 个场景的肌肉记忆一致**——用户永远知道"主产出在左、AI 在右"，切换场景不用重新找位置。这比"每个场景定制一套网格"重要得多。

## 七 反例（2025 已过时）

| ❌ 过时做法 | 为什么不行 | ✅ 正确做法 |
|---|---|---|
| **重阴影分层**（`0 4px 16px rgba(0,0,0,.5)`） | 多面板场景下每块都投影 = 12 层脏影，边界反而糊 | 明度差分层 + 1px alpha 描边；阴影只给浮层且 alpha ≤.08 |
| **渐变按钮**（`linear-gradient(135deg,…)`） | 2025 头部产品按钮全是实心单色；渐变 = 2013 拟物残留 | `background: var(--accent)` 单色 |
| **过度圆角**（面板 16–28px） | 密集面板用了像"卡片流marketing页"，且圆角吃内容区 | 面板 6px / 控件 4px / 浮层 8px |
| **全圆胶囊标签**（`border-radius:999px` 用于所有 badge） | 胶囊只适合"计数/头像"；状态标签用胶囊显得幼稚 | badge 4px 圆角；只有开关/头像用 full |
| **纯黑底 `#000`** | OLED 拖影、边界消失、明度阶梯做不出 7 级 | 近黑 `#0F1115`–`#1B1B1C`，带极轻蓝 |
| **彩色顶部渐变条 / 金色标题** | 我们 `refined.css:314` 有 `linear-gradient(217,184,74)` 金色面板头 | 一律 `--color-raised` + `--inset-hi` |
| **正文 14–16px 铺满工具界面** | 工具界面要密度，16px 正文一屏只能放 20 行 | 正文 13px，表格 12px，标签 11px |
| **气泡式 AI 对话（两侧都带气泡）** | 气泡边框吃掉横向空间，长回答变窄柱状 | 用户消息浅底圆角，AI 消息通栏无底 |
| **打字机逐字动画** | 每字触发重排，长回答卡顿；且用户想跳过 | 块级插入 + 光标 blink |
| **`transition: all`** | 会把 `display`/`height` 也带上，产生意外动画 | 明确列出 `background-color, border-color, color, transform` |
| **`ease` / `linear` 过渡** | 头部产品全部用自定义 bezier | `cubic-bezier(.22,1,.36,1)` |
| **动效 >300ms** | 界面动效要"无感"，>300ms 就等 | 90/140/200/260ms |
| **`outline` 做焦点环** | 各浏览器样式不一，且方角与圆角控件不匹配 | 双层 `box-shadow` ring |
| **四色并列状态体系** | 我们的青/黄/赤/朱殷 + warn/err 差 3° | 1 强调 + 4 语义（ok/warn/err/done），色相 ≥30° 分离 |
| **图标栏 + 顶栏 + 侧栏三层导航** | 12 个场景本来就多，再加层级会迷路 | 顶栏 tab 平铺 + 44px 图标栏只放 pin |

## 八 我们界面的四个最大问题（带证据）

### 问题 1：**三套色板并存，实际生效的是最差的那套**

`index.html` 加载顺序：

```
tokens.css       ← 定义 --color-*（注释写「实测 13.30/6.76/4.59」）
guoxue-tokens.css← 定义 --gu-*
compat.css
base.css / layout.css / components.css / animations.css
refined.css      ← 最后加载，定义 --rf-*，且第 348-367 行把 --rf-* 重绑到 --gu-*
```

`refined.css` 的 `.wb-panel / .wb-panel-head / .wb-panel-title / .wb-panel-body` 全部用 `--rf-*`。
⇒ **`tokens.css` 里那些精心实测过的 `--color-*` 实际上被旁路了**——组件读的是 `--rf-*` → `--gu-*`。

实测生效值（`--gu-*`）：

| 文字 | 对 7 级表面最差对比度 | 结论 |
|---|---|---|
| `--gu-su` `#E9E4DC` | 11.12:1 | ✓ |
| `--gu-su-2` `#A8AEB8` | 6.31:1 | ✓ |
| `--gu-su-3` `#6E7580` | **3.03:1** | ✗ **不达 AA 4.5:1** |
| `--gu-su-4` `#4A505A` | **1.73:1** | ✗ 几乎不可见 |

而 `tokens.css` 声明的 `--color-txt-3: #8A94A3` 是 4.59:1（达标）——**但没人用它**。

**修法**：删掉 `refined.css` 的整段调色板（第 26-44 行）与国色桥接（第 348-367 行），`--rf-*` 全部 alias 到新 token；`guoxue-tokens.css` 从 `index.html` 移除（或只保留作为"国色参考表"，不参与渲染）。**色板有且只有一个真源。**

### 问题 2：**网格均分行高，低分辨率下面板不可用**

`grid.js:200-202` 写 `gridAutoRows = 'minmax(0,1fr)'` + `gap 4px`，5 列 × 7 行。

实测：1366×768 下每列 **268px**（低于 280px 可读下限），2 行面板仅 **186px**（内容区 160px）。`pc-cleanup`（5 面板 4×7）和 `frontend-craft`（AI 2×7）最惨——AI 对话面板在 1366 下**只有 186px 高**，放不下 3 条消息。

同时 `--w-panel-min` 根本不存在于代码里，面板无最小宽度，表格列被压到折行。

**修法**：`grid-auto-rows: minmax(180px, 1fr)`；面板加 `min-width: 280px / min-height: 160px`；把 AI 面板迁出网格进右栏（见 4.3）。

### 问题 3：**面板之间露出「深色网格纹理」，看起来像粗黑分割线**

`layout.css` 里 `.wb-grid` 出现两次（后者覆盖前者）：第一次 `background: var(--color-line) #22272D`，第二次在 `.wb-main--canvas .wb-grid` 之外又有一段：

```css
.wb-grid {
  background-color: var(--color-base);
  background-image:
    linear-gradient(var(--color-line) 1px, transparent 1px),      /* 横线 */
    linear-gradient(90deg, var(--color-line) 1px, transparent 1px); /* 竖线 */
  background-size: 32px 32px;
}
```

而 `grid.js:199-200` 又把 `gap` 和 `padding` 内联成 **4px**（覆盖 CSS 的 `--hairline` 1px）。
⇒ **4px 的缝里透出的是 32×32 的深色网格纹理**，视觉上就是"面板之间一条粗黑线 + 底纹"。

这解释了 `界面诊断.md` P0-5 说的"分割线是粗黑实线"——**它其实不是 border，是 gap 背景**。

**修法**：`.wb-grid` 只保留纯色底（`background: var(--color-void)`），**删掉网格纹理**（神经元面板要纹理就在该面板内部自己画）；`gap` 统一 8px，不再用内联 4px。

### 问题 4：**AI 面板是 Webview，且外壳与它不同色 —— 拼贴感**

`panels/harness.js:167` 写死 `background:#fff`；`theme.js` 无 `insertCSS`。
⇒ AI 面板内部样式**我们改不了**，它按 DSH 自己的主题渲染（DSH 暗色底 `#151517`）。
而外壳生效底是 `--gu-xuan #0C0E11` —— 两者并排时，**AI 面板明显偏灰偏亮，像贴上去的一块**。

外加 DSH 圆角是 `4/8/12/16/20/28`，外壳是 `0/4/10` —— 圆角语言也不一致。

> 这一条与 `界面诊断.md` 第一章（"两套视觉体系被硬拼在一起"）是同一个问题，我这里给的是**可落地的分步修法**。

**修法**（按优先级）：
1. 立刻：`wv.style.background` 从 `#fff` 改成 `var(--color-panel)`（`#232324`），消除白闪与边框亮边；
2. 短期：外壳表面梯改用 DSH 同族数值（本规范第三章已按此取色），把拼贴感降到最低；
3. 中期：`wv.addEventListener('dom-ready')` 后 `wv.insertCSS()` 注入少量变量覆盖（`--dsw-alias-bg-layer-*` / `--dsw-radius-*`）——Electron `<webview>` 支持 `insertCSS` 返回 Promise，webview 是宿主进程内容器，可行；`theme.js` 目前没做这件事，这是可补的缺口；
4. 长期：让 DSH 前端支持 `?theme=dark&density=compact` 参数，上下文由外壳传入。

## 十 自检（本规范的证伪条件）

本规范**不是**"看着舒服"的主观描述，下列每一条都可以被打假：

1. **层级可验**：取任意相邻两层表面，算 WCAG 对比度，必须落在 `1.08–1.20`。若某个取值算出 <1.05，说明我在第三章抄错了数。
2. **文字可验**：`--text-3` 对 7 级表面**全部**表面 ≥4.5:1（实测最差 4.49:1，卡在线上，故标注"30px 以下勿再降"）。若有人拿 `--text-4` 当正文用，是本规范被误用，不是规范错。
3. **语义色可验**：ok(149°) / warn(36°) / err(2°) / done(255°)，最小间距 warn↔err = 34° ≥30°。若有人加回 `#E68069`(11°) 与 `#EC6B58`(8°)，即违反本条。
4. **布局可验**：1366×768 下，任一场景不出现 `<280px 宽`或`<160px 高`的面板。当前 `pc-cleanup` 与 `frontend-craft` 会**违反**这一条——这正是问题 2 的证据。
5. **反例存在**：本规范第七章列了 15 条过时做法，其中「金色面板头」正是我们 `refined.css:314` 的现状。若改完还能在界面里找到金色渐变头，说明第 2 步没做。
