>
> 依据：参考项目 `04-工作台搭建/事故复盘-三起.md`
> 「比起『我搭了个工作台』，『我搞坏过、这样救回来』通常更有用。」

## 为什么要有这个

参考项目里几条看起来「过分小心」的规矩：

> ⛔ 永不打包 · ⛔ 不许动启动器里的 exe · ⛔ 改文本不许用 PowerShell 往返读写

**它们不是洁癖，是真事故留下的。**

## 三起事故的共同点（最值得抄的部分）

| 共同点 | 含义 | 对应做法 |
|---|---|---|
| **都不报错** | 灰白、乱码、静默丢失 —— 没有任何一条错误提示 | 体检必须有「应当失败的反例」 |
| **都是「看起来很小」的操作** | 改个版本号 / 跑个替换 / 写一次文件 | 危险操作按**后果**分级，不按代码量 |
| **救回来的都不是靠「小心」** | 靠日志、靠重启、靠事先的联接设计 | 关键路径要留**可回溯的东西** |
| **事后都变成了机械抓手** | 不能停留在「下次注意」 | 一条规矩 ⇒ 一个**会失败的检查** |

## 四条要求

1. 写「我当时以为」—— 不写这段，复盘就变成炫耀
2. 写「没救回来」的部分 —— **真实感来自这里**
3. 一定要落到「抓手」—— 没有抓手的复盘 = 故事
4. 只追加，不改写 —— 事故档案是证据，不是宣传稿

### AC-001：内容哨兵的检查永远不会失败（写成「装饰」）

| | |
|---|---|
| 严重程度 | **严重** — 功能不可用 / 错误结论 |
| 可信度 | 已确认 — 复现过 / 日志证实 |
| 日期 | 2026-11-11 |

**现象**

> 内容哨兵在机制体检里一直显示 PASS。9 个场景在「已积累经验」上是 9/9。我以为它真的在把关。
> 但用五步法审计（工具/机制审计.mjs）一看，它在第 4 步「有应当失败的反例」上是 ✗——它没有任何 selftest，也没有一条反例。

**我当时以为**

> 我当时以为：只要代码里写了 if 判断、push 了 diff，这个检查就是有效的。
> 
> 更具体的误判：我看到 `stats['noLearn_' + name] = true;` 这行，以为它是在「记录问题」。实际上它只写进了统计对象，从来没进 diffs 数组——而机制体检只看 diffs 是否为空。

**真实原因**

> 代码里两处不同性质的处理被混在了一个 if 分支里：
> 
> ```js
> if (!hasLearn) {
>   // 这不是硬违规，但提示：还没有积累任何经验
>   stats['noLearn_' + name] = true;   // ← 只记统计
> }
> ```
> 
> stats 是给「报告末尾的统计数字」用的，不参与判定。所以这个分支执行了、也记录了什么，但**不会让检查失败**。
> 
> 按参考项目的判据：「如果一个检查永远通过，它就不是检查，是装饰。」

**怎么救的**

> 改成真的生成 diff：
> 
> ```js
> if (!hasLearn) {
>   diffs.push('场景「' + name + '」场景记忆缺 §五（坑与决策）或 §六（归因）：还没有积累任何经验');
>   stats['noLearn_' + name] = true;
> }
> ```
> 
> 改完立刻写反例验证：故意造一条不含 §五 的记忆，确认它会报。
> 
> 然后又跑了一次真实数据——9/9 场景都有 §五。说明之前那些记忆是真的，只是这个检查从来没验证过它们。

**🔴 没救回来的**

> 没救回来的是「信心」。
> 
> 在此之前我一直在报告「41/41 通过」，但其中 17 项其实从没被证明会失败。这个数字当时给的是虚假的确定感。
> 
> 已经报告出去的数字无法收回，只能现在补上说明。

**现在的抓手**

> 工具/机制审计.mjs —— 它会逐项检查每个体检工具是否有「反例」二字（第 4 步），缺了就判为「口号」。

同时工具/机制清单.mjs 强制要求每项填「已知盲区」。

**教训**

> 「记录了」不等于「会失败」。写检查时必须问一句：**这段代码执行了之后，diffs 会不会变长？** 不会变长就是装饰。

### AC-002：5 个哨兵全部没有自测，也不知道它们是不是装饰

| | |
|---|---|
| 严重程度 | **严重** — 功能不可用 / 错误结论 |
| 可信度 | 已确认 — 复现过 / 日志证实 |
| 日期 | 2026-11-11 |

**现象**

> 机制审计显示：记忆哨兵、身份哨兵、派单哨兵、越界哨兵、内容哨兵——这 5 个最核心的哨兵，全部没有 --selftest，也没有一条反例。
> 
> 它们每轮体检都在跑、都报告 PASS。但我从来不知道它们会不会失败。

**我当时以为**

> 我当时以为：这些哨兵是从具体问题出发写的（先发现了问题，再写检查），所以它们天然是有效的。
> 
> 更深的误判：我以为「检查真实数据通过」就等于「检查有效」。但真实数据通过可能只是因为没有违规，不能证明有违规时它会报。

**真实原因**

> 写的时候只想着「现在数据是好的」，没想着「造一个坏数据试试」。
> 
> 参考项目把这叫「90% 的人会漏，也是最容易自欺的地方」。我确实漏了，而且漏了 5 个。

**怎么救的**

> 给 5 个哨兵逐个补 selftest + 反例：
> 
> | 哨兵 | 补的反例 | 结果 |
> |---|---|---|
> | 记忆哨兵 | AGENTS超限 / 主文件超限 / §〇超限 | 9/9 |
> | 身份哨兵 | 占位 sessionId / 索引缺场景 | 5/5 |
> | 派单哨兵 | id格式 / 无证据 / 非法状态 / 作废无原因 | 8/8 |
> | 越界哨兵 | 核心资产无归属 / A档改动未确认 | 5/5 |
> | 内容哨兵 | 缺定位卡 / 缺§五 / 缺技能 | 6/6 |
> 
> 写反例的过程中踩了 5 个坑（见下条事故）。

**现在的抓手**

> 工具/机制审计.mjs 的第 4 步会检查每项是否有 ≥2 处「反例」。低于就判「口号」。

**教训**

> 写检查的第一件事不是写检查逻辑，是**先写一个应该让它报错的样本**。写不出来说明规则还没搞清。

### AC-003：写反例时连续 5 次写错，暴露出我没搞清规则

| | |
|---|---|
| 严重程度 | **轻微** — 体验问题 / 返工 |
| 可信度 | 已确认 — 复现过 / 日志证实 |
| 日期 | 2026-11-11 |

**现象**

> 给 5 个哨兵补反例时，自测一次次失败：
> 
> - 记忆哨兵 2/9 → 9/9（4 轮）
> - 身份哨兵 0/5 → 5/5（3 轮）
> - 派单哨兵 1/8 → 8/8（2 轮）
> - 越界哨兵 0/5 → 5/5（3 轮）
> - 内容哨兵 报错 → 6/6（4 轮）
> 
> 每次都是「合规样本被判不合规」。

**我当时以为**

> 我当时以为：反例只是「故意造一个坏样本」，坏样本随便造就行，关键在于检查逻辑对不对。
> 
> 误判的核心：我以为我了解这些规则（毕竟代码是我写的），所以样本凭印象造。

**真实原因**

> 真实规则比我的印象严格得多：
> 
> ① §〇 必须含「上次交接 / 当前项目 / 下一步 / 全貌」四小节——我以为只要有个 §〇 标题就行
> ② sessionId 必须匹配 `session-<8>-<4>-<4>-<4>-<12>` 的 UUID 格式——我以为 `session-abc123` 这种就行
> ③ 回执证据必须 ≥20 字符，且 acked 前必须有 deliveredAt
> ④ 索引字段是 `id` 不是 `scene`
> ⑤ 技能必须有「流程」和「验收」两节
> ⑥ AGENTS.md 实际在 `数据/.dsh/` 下，不在 workbench 根
> ⑦ 越界哨兵 `ROOT_DYNAMIC = dirname(wbRoot)`，样本要用 `<tmp>/workbench/` 结构
> 
> 另外两个纯技术坑：
> - `require` 在 ESM 里不可用
> - selftest 函数被插进了 `if` 块内部，报 `selftest is not defined`

**怎么救的**

> 一条条去读真实代码，把规则抄下来再改样本。
> 
> 这个过程反而成了最有价值的部分：**它逼我搞清了自己写的规则到底是什么。**

**现在的抓手**

> 没有直接抓手——这类问题只能靠「写反例时必须读源码确认规则」。

但有一个间接效果：现在 5 个哨兵都有 selftest，以后改规则时自测会立刻红。

**教训**

> **反例写不出来，往往不是因为检查有问题，是因为你不了解规则。**

写反例的过程 = 校验自己对规则的理解。这比读文档有效得多。

### AC-004：「引擎数据」路径已废弃，24 处仍在引用（含 8 个 AI 直接读的定位卡）

| | |
|---|---|
| 严重程度 | **严重** — 功能不可用 / 错误结论 |
| 可信度 | 已确认 — 复现过 / 日志证实 |
| 日期 | 2026-11-11 |

**现象**

> 做记忆精简时，偶然在剥离出来的项目信息里看到 `引擎数据\.dsh\场景记忆\架构梳理`。
> 
> 全库排查：真实命中 43 处（排除备份/快照/引擎内部），其中 24 处会影响 AI 行为。

**我当时以为**

> 我当时以为：路径迁移那次已经改干净了——我做的是全局替换。
> 
> 而且我以为：文档里的旧路径不会有实际影响，反正 AI 会自己找对地方。

**真实原因**

> 两个层面的问题：
> 
> ① 迁移时只替换了当时「正在被读」的文件，没有替换「虽然现在不读、但将来可能被读」的文件
> ② 8 个场景定位卡（`外壳/scenarios/*-context.md`）里有旧路径——这些是 AI 每次开场就读的文件，写错地址会让它去错地方找东西

**怎么救的**

> 写脚本批量替换 24 个文件，含 8 个定位卡 + 6 个工具代码 + hub 技能 + 9 个项目记忆。
> 
> 替换后逐个确认语法正常（6 个 .mjs 全部 node --check 通过）。
> 
> 剩下 5 处是历史产物（A档确认.json / 待办 / 进化台账 / arch-report.json / memory-audit.json）——它们记录的是「当时的路径」，属于历史事实，不该改。

**🔴 没救回来的**

> 没救回来的是「迁移时以为改干净了」这个判断。实际上「替换当时在用的文件」和「替换所有文件」是两件事，我当时没区分。

**现在的抓手**

> 工具/文档体检.mjs 会扫密集目录，但**不查路径有效性**。

真正的抓手应该是：体检里加一项「全库搜旧路径关键字」。这条还没做。

**教训**

> **路径迁移不是「替换当前引用的」，是「替换所有引用」+「搜索禁用关键字」。**

判据应该是：全库搜旧路径，命中 0 才算完。不是「我记得改过了」。

> 工具/六件套.mjs —— 把「场景是否成立」变成可判定的检查，缺必需件就红。

> **「配置齐了」不等于「场景成立」。** 判断标准要按对方体系里最严的那条，不是按自己觉得够的那条。

### AC-008：把视频里两个人的立场搞反了，据此得出反向结论

| | |
|---|---|
| 严重程度 | **严重** — 功能不可用 / 错误结论 |
| 可信度 | 已确认 — 复现过 / 日志证实 |
| 日期 | 2026-11-11 |

**现象**

> 我把「我不放心让全部程序去干」记成 UP 主 luanyujia 的话，写进了笔记、成册和代码注释。
> 
> 用户指出：「不不不，这句话是视频里另一个人的提问」

**我当时以为**

> 我当时以为：转写文本里没标说话人，但「读起来像谁说的」就能判断。
> 
> 更深的误判：我以为这句话和他的其他观点是自洽的（他确实强调人工验收），所以没去核对上下文。

**真实原因**

> 
> ```
> [02:00] 观众：对，我是偏向于去对话
> [02:03] 观众：因为我不太放心让全部程序去干

### AC-010：给中枢卡加画像段，体积没变——fail-open 吞掉了 ReferenceError

**现在的抓手**

> 暂无直接抓手——这是一个**真实的缺口**。

**教训**

> **fail-open 会吞掉编程错误。**

同一个模式我犯了两次（另一次是任务看板的 `require is not defined`，导致归档静默失败、数据丢失）。

### AC-011：用 PowerShell 测文件字节数，把 LF 换成 CRLF 造出假超限

| | |
|---|---|
| 严重程度 | **轻微** — 体验问题 / 返工 |
| 可信度 | 已确认 — 复现过 / 日志证实 |
| 日期 | 2026-11-11 |

**现象**

> 检查 AGENTS.md 是否超 2048 B 上限，用这条命令：
> 
> ```powershell
> [System.Text.Encoding]::UTF8.GetByteCount((Get-Content $f -Raw))
> ```
> 
> 结果：**2600 B**，比上限多 552 B。我以为发现了真实超限。
> 
> 同一时刻 Node 那边报的是 1955 B。两个数字差 645 B。

**我当时以为**

> 我当时以为：文件真的超限了，AGENTS.md 有 2600 字节。
> 
> 而且我以为：两种测量方式都读同一个文件，结果应该一致，差这么多说明有编码问题。
> 
> 最开始的怀疑方向是 BOM，但查了前 8 字节是 `23 20 E5 85 A8`——`# 全局` 的 UTF-8，没有 BOM。

**真实原因**

> **`Get-Content -Raw` 把 LF 换行转成了 CRLF。**
> 
> 文件本身：1955 字节，LF 换行（`\n`）
> 经 Get-Content -Raw 读进 PowerShell 后：变 CRLF（`\r\n`）
> 
> AGENTS.md 有 9 个章节 + 若干行，每行多一个 `\r`，累计多出 645 字节。
> 
> 验证：
> - `[System.IO.File]::ReadAllBytes($f).Length` → **1955**（原始字节，不转换）
> - `(Get-Item $f).Length` → **1955**
> - `Get-Content -Raw` + UTF8.GetByteCount → **2600**（换行被改了）

**怎么救的**

> 改用 `[System.IO.File]::ReadAllBytes($f).Length` 或 `(Get-Item $f).Length`，都返回 1955。
> 
> 确认 AGENTS.md 实际 1955 B / 2048，余量 93 B——**没有超限，是测量方法错了。**

**🔴 没救回来的**

> 没救回来的是**差点基于假数字做改动**。如果我真去「压缩」AGENTS.md，会在已经合规的文件上白改一遍，还可能压掉重要内容。

**现在的抓手**

> 工具/事故档案.mjs 记录了这条。

更深一层：参考项目有一条一模一样的规矩——「⛔ 改文本不许用 PowerShell 往返读写」。我这次是**测量**踩的同一个坑，说明这类问题的边界比「改」更宽。

**教训**

> **测量工具本身可能是污染源。**

判据：量字节数只认 `ReadAllBytes().Length`。任何经过 `Get-Content` 的数字都要怀疑——它会转换行、可能转编码、可能去尾空行。

这和参考项目说的「⛔ 改文本不许用 PowerShell 往返读写」是同一个根因：**PowerShell 的文本管道会静默改变内容。**

> ```

> ...

**现在的抓手**

> 工具/界面回归.mjs 能检出「亮点数明显少于场景数」。

⚠ 但它当前的**已知盲区**（已写进 机制盲区.json）：
· 阈值敏感（620 时只剩 2 个，480 时又混进工具栏按钮）

两个具体教训：
1. 布局算法里「声明不聚类」和「实际按组算坐标」必须统一，不能各说各话

### AC-017：AI 面板全部「token 缺失」—— 只要引擎先于工作台启动就触发

| | |
|---|---|
| 严重程度 | **致命** — 数据丢失 / 系统起不来 |
| 可信度 | 已确认 — 复现过 / 日志证实 |

**现象**

> 启动到「架构梳理」场景，4 个面板里：

> 
> **整个场景的 AI 对话功能是坏的。**

**我当时以为**

> 我当时以为：这是「外部引擎模式」的正常限制。
> 
> main.js 的注释写着「复用外部引擎时，主界面改走本机保命入口」，所以看到这个分支并不意外。
> 
> **但我没意识到触发条件有多容易满足**：
> 只要引擎已经在监听 3083，`probe()` 就返回 true → `engineIsForeign = true` → 走那个分支。
> 
> 而「引擎已经在跑」的常见情况：
> · 上次没退干净
> · 手动先起了引擎
> · 连续双击了两次启动
> · **我自己刚才重启工作台时没杀干净**
> 
> 所以这不是「特殊场景」，是**很容易踩的常规路径**。

**真实原因**

> 代码逻辑（main.js 第 1324 行）：
> 
> ```js
> if (engineIsForeign && process.env.DSH_EXTERNAL_VIA_CHAT !== '1') {
>   const extTok = process.env.DSH_ENGINE_TOKEN || '';
>   return extTok ? (BASE + '/?token=' + extTok) : (BASE + '/');   // ← 没 token 就返回裸 URL
> }
> ```
> 
> 而 `engineIsForeign` 是这样设的（第 672 行）：
> ```js
> if (await probe()) {              // 端口已监听
>   engineIsForeign = true;         // ← 就这一句
> }
> ```
> 
> **问题在于：虽然标了「外部」，但 token 其实能拿到** ——
> `startServer()` 里已经尝试从日志历史找了（第 676-680 行），找到后会存进 `harnessToken`。
> 
> **但 `harness:url` 那个分支只认 `DSH_ENGINE_TOKEN` 环境变量，不认已经找到的 `harnessToken`。**
> 
> 两处代码各写了一半，合起来是断的。

**怎么救的**

> **已修复并验证（2026-11-11）。**
> 
> **真正的根因是两处：**
> 
> **① 主进程只认环境变量，不认已经找到的 token**
> 
> `main.js` 的 `startServer()` 里已经尝试从日志历史找 token 并存进 `harnessToken`。
> 但 `harness:url` 那个分支只认 `DSH_ENGINE_TOKEN` 环境变量 —— 两者没接上。
> 
> 修法：依次尝试三个来源

> const extTok = process.env.DSH_ENGINE_TOKEN   // ① 外部显式传入

>   || 从日志重新找一次;                          // ③ 兜底
> ```
> 
> **② 面板只请求一次，拿不到就永久失败**
> 
> 场景在 boot 早期就渲染了，那时引擎还在启动（冷启动 5~10 秒），
> `harnessToken` 还没被捕获 → 返回不带 token 的 URL → 面板显示「token 缺失」
> → **而且再也不会自动恢复**（除非手动刷新）。

> （面板里正常加载出 DeepSeek Harness 界面）
> ```

**现在的抓手**

> **两个抓手**：

① 界面回归工具（待加）：检测「token 缺失」「引擎 URL 缺少 token」这类明确文字特征。

② harness.js 现在会等待 20 秒 —— 这本身是一层保护（引擎慢启动也不会立刻失败）。

⚠ 但盲区仍在：如果 20 秒后引擎还没起来，面板还是会显示错误，且不会自动恢复。
用户需要手动点 ⟳ 刷新。

**教训**

> **「两个地方各写一半」比「完全不写」更危险。**

本案里：
· `startServer()` 写了「从日志找 token」
· `harness:url` 写了「用环境变量」
· 两者**没有接上**

单独看每处代码都像是对的，合起来是断的。

**判据：写「取某个值」的逻辑时，必须确认「所有消费方都能拿到」。**
不能一处存了、另一处不认识。

### AC-023：api 包装层返回 { ok, value }，我读成了顶层字段 —— 面板一直空

| | |
|---|---|
| 严重程度 | **严重** — 功能不可用 / 错误结论 |
| 可信度 | 已确认 — 复现过 / 日志证实 |
| 日期 | 2026-11-11 |

**现象**

> 本地电脑场景的 4 个 pc 面板，我从「待接入」改成了真实 UI（有状态栏、刷新按钮、错误提示），但数据永远显示「0 个 / 没有读到」。
> 
> 主进程 handler 返回正确数据（加了日志确认）：
> ```
> [pc:drives] 返回 [{"drive":"C:","ok":true,"total":214748360704,"used":103037517824}, ...]
> ```
> 但面板显示「0 个可用分区」。

**我当时以为**

> 我当时以为：主进程 handler 没注册成功，或者 Electron 里 fs 行为和 Node 不一样。
> 
> 为此我花了很多时间：
> · 加了注册日志 → 确认注册了
> · 加了调用日志 → 确认调用了、数据对了
> · 在纯 Node 里跑同样的逻辑 → 完全正常
> · 检查 preload 有没有暴露 pc → 有
> · 检查 api/index.js 白名单 → 一开始漏了，补上后还是空
> 
> **全都是死路。因为我一直在查「数据从哪来」，从没查「数据怎么被包了一层」。**

**真实原因**

> `api/index.js` 的 `wrap()` 是这样：
> 
> ```js
> function wrap(fn, label, timeout) {
>   return async function (...args) {
>     const raw = await fn(...args);
>     return { ok: true, value: raw, error: null, ms: dt };   // ← 包了一层
>   };
> }
> ```
> 
> 所以：
> ```js
> const r = await api.pc.drives();
> // r = { ok: true, value: { ok: true, drives: [...] } }
> //                    ↑ 真正的数据在这里
> ```
> 
> 而我面板里写的是：
> ```js
> const rows = r.drives || r.rows || r.disks || [];   // ← r.drives 是 undefined
> ```
> 
> **`r.ok` 是 true（包装层的 true），`r.drives` 是 undefined。所以我的 `if (!r || r.ok === false)` 判断通过了，然后拿到空数组。**

**怎么救的**

> 所有走 `api.xxx()` 的地方都要解包：
> 
> ```js
> /** 解包 api 返回值（wrap 会包一层 {ok,value}） */
> function rvUnwrap(wrapped) {
>   if (wrapped && typeof wrapped === 'object' && 'value' in wrapped) return wrapped.value;
>   return wrapped;
> }
> 
> const raw = await api.pc.drives();
> const r = rvUnwrap(raw);
> const rows = r.drives || [];
> ```
> 
> pc 的 4 个面板 + review 的 2 个面板 + sf-board 全都改了这个。

**🔴 没救回来的**

> **没救回来的是「我以为改完了」。**
> 
> 我第一次提交 pc 面板时说「4 个面板全部接上真实数据」——
> **那是错的**。当时只有 UI 骨架是真的，数据是空的。
> 
> 而且我在那个 commit message 里写了「实测：C: 200GB / D: 733.66GB」，
> **那是后来才看到的**。这种「先用结论、后补证据」的写法很危险。

**现在的抓手**

> **判据：调用 api.* 时，先问一句「这层有没有包」。**

具体抓手（已落地到 `_generic.js`）：
1. 顶部放 `rvUnwrap(wrapped)` / `sfUnwrap(wrapped)` 两个解包函数，所有面板统一调用
2. 面板里如果出现 `r.rows` / `r.items` / `r.drives` 直接读，一律怀疑没解包
3. 调试时打印 `Object.keys(raw)` —— 如果看到 `["ok","value","error","ms"]` 就是没解包

**可加进 `工具/面板体检.mjs` 的检查项**：扫描面板源码，
如果 `await api.` 后面没有 `Unwrap` / `.value`，报「可能少解包一层」。

**教训**

> **「数据对不对」和「数据在哪一层」是两个独立问题，要分开查。**

我这次的错误链条：
1. 看到面板空 → 假设「数据没拿到」
2. 查数据源 → 数据是对的 → 假设「传输出问题」
3. 查传输链路 → 链路是通的 → 假设「handler 没注册」
4. 加日志 → 注册了、调用了、返回对了 → **卡住**

真正的答案是第 0 步就该问的：**「我拿到的是不是我想要的那层？」**

**具体的判据：如果底层确定没问题但上层还是空，先 dump 出上层对象的 keys。**

> **`=` 赋值把 `flex:1 1 auto` 抹掉了。**
> 
> body 不再是 flex 子项 → 高度不再由父容器分配 → 它自己撑开或塌陷 →
> 内部 grid 的行高分配错乱 → 元素的实际渲染位置和 getBoundingClientRect 报的不一致。

**怎么救的**

> 改成追加：
> 
> ```js
> // ⚠ 用 += 而不是 =：makeShell 给 body 设了 flex:1 1 auto，
> //   直接覆盖会让它不再是 flex 子项 → 高度塌陷 → 点击区域错位。
> body.style.cssText += 'display:flex;flex-direction:column;height:100%;overflow:hidden;';
> ```
> 
> 三处（review-doc / review-files / 其他）都改了。

**🔴 没救回来的**

> **没救回来的是「我误以为是坐标问题」。**
> 
> 我为此写了一个 `工具/点击.mjs`（按百分比点击），还试了 4 个不同坐标。
> **那个工具本身没白写（后面 Cdp.mjs 也用了类似思路），但方向是错的。**
> 
> 真正该做的是：先确认元素在不在、坐标对不对（CDP 一下就出来了），
> 而不是盲试坐标。

**现在的抓手**

> **判据：面板里改 `body.style.cssText` 时必须用 `+=`，不能用 `=`。**

具体抓手：
1. `grep -n "body.style.cssText =" workbench/外壳/ui/panels/_generic.js`
   —— 看到 `=` 而不是 `+=` 就要怀疑（这条可以写进 `工具/面板体检.mjs`）
2. 用 `工具/Cdp.mjs --dump` 看元素的真实 `getBoundingClientRect`，
   和截图肉眼位置对比 —— 不一致就是布局被改坏了
3. `makeShell` 返回的 body 带 `flex:1 1 auto`，这是父容器的约定，不能覆盖

**教训**

> **「点击没反应」有四种可能，必须按顺序排除：**

1. 元素存在吗？ → CDP `document.querySelector`
2. 坐标对吗？ → CDP `getBoundingClientRect()`
3. 事件绑定了吗？ → 加 console.log 看有没有触发
4. 处理逻辑对吗？ → 看处理结果

**我跳过了 1 和 2，直接改 3 和 4，浪费了大量时间。**

而且这些问题**用 CDP 一次就能全答**，不需要改代码试。

### AC-025：想看前端报错却看不到 —— 花了很久才想到加 console 转发

| | |
|---|---|
| 严重程度 | **严重** — 功能不可用 / 错误结论 |
| 可信度 | 已确认 — 复现过 / 日志证实 |
| 日期 | 2026-11-11 |

**现象**

> 在整个 review-doc 调试过程中，我遇到的所有前端问题都是「看起来没反应」：
> · 点击文件 → 右侧空白
> · 面板显示「未知面板类型 未注册」
> · 数据一直是 0
> 
> **这些都应该有 JS 错误，但我一个都看不到。**
> `server.log` 里只有主进程的日志。

**我当时以为**

> 我当时以为：Electron 默认会把渲染进程的 console 打到 stdout。
> 
> **不会。** 渲染进程是独立的 Chromium 进程，console 输出只在 DevTools 里。

**真实原因**

> `main.js` 里从来没有监听 `console-message` 事件：
> 
> ```js
> // 原来完全没有这段
> app.on('web-contents-created', function (_evt, wc) {
>   wc.on('console-message', ...);
> });
> ```
> 
> 所以渲染进程的 `console.error`、未捕获异常、`ReferenceError` 全部无声无息。

**怎么救的**

> 在 main.js 加：
> 
> ```js
> app.on('web-contents-created', function (_evt, wc) {
>   wc.on('console-message', function (e, level, message, line, sourceId) {
>     const tag = level >= 3 ? 'ERR' : level === 2 ? 'WARN' : 'LOG';
>     if (level < 2 && String(message).length < 2) return;
>     const src = String(sourceId || '').split(/[\\/]/).pop();
>     log('[renderer][' + tag + '] ' + String(message).slice(0, 500) +
>         (src ? '  @' + src + ':' + line : ''));
>   });
>   wc.on('render-process-gone', function (e, d) { log('[renderer] 进程挂了: ' + JSON.stringify(d)); });
>   wc.on('preload-error', function (e, p, err) { log('[renderer] preload 出错: ' + p + ' → ' + err); });
> });
> ```
> 
> 加完之后立刻看到：
> ```
> [renderer][LOG] [ui] 已注册渲染器 10/10: neuron, harness, embed, sf-board,
>                 review-doc, review-files, pc-drives, pc-toplarge, pc-junk, pc-ledger
> [renderer][LOG] [review-doc] 挂载, panel.docDir=数据/.dsh/场景记忆/架构梳理/文档
> ```
> **第一次确认了「面板真的挂载了、docDir 真的传进去了」。**

**🔴 没救回来的**

> **没救回来的是「前面几小时的盲猜」。**
> 
> 如果一开始就有这个转发，很多问题会快得多：
> · 「未知面板类型」→ 会看到模块加载失败的报错
> · 「点击没反应」→ 会看到事件处理里的异常
> · 「数据是 0」→ 会看到 `undefined` 相关错误
> 
> **这是一项「基础设施缺失」的成本，不是某个 bug 的成本。**

**现在的抓手**

> **现在有了，写在 `main.js` 里（`app.on('web-contents-created')` → `console-message`）。**

具体抓手：
1. `Select-String -Path workbench/外壳/server.log -Pattern "\[renderer\]"`
   —— 能看到前端所有 console.log/warn/error
2. `工具/Cdp.mjs --eval "<js>"` —— 直接在渲染进程执行代码，查任意状态
3. `工具/Cdp.mjs --dump` —— 看页面结构和元素真实坐标

**判断标准：如果发现自己在「改一版 → 重启 → 看界面 → 猜为什么」的循环里超过 2 轮，
就该停下来去建观测能力，而不是继续猜。**

**教训**

> **没有日志的调试就是猜谜。先建观测能力，再排查问题。**

具体判断标准：**如果你发现自己在「改一版 → 重启 → 看界面 → 猜为什么」的循环里超过 2 轮，就该停下来去建观测能力。**

观测能力的优先级顺序：
1. 渲染进程 console 转发（最基本的）
2. CDP 直连（能执行任意 JS，查 DOM 状态）
3. 截图（最终效果，但信息密度最低）

**我建这三个的顺序是反的** —— 先做了截图工具，最后才做 CDP 和日志。
