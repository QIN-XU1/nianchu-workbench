# 子智能体任务分派规则

> 2026-11-16 立。起因：一次并行派 3 个写权限子智能体，结果**帮了倒忙** ——
> 每次 verify-goal 失败项都不一样（在 A5 / A13 / A11 之间漂移），而且
> `survey.mjs` 被留下 `import` → `imporo` 的未还原故障注入，无人认领。

## 一句话

**并行只在「写作用域不相交 且 互不依赖验证结果」时才安全。否则串行。**

## 派活前的三道检查

### 检查 1：写作用域是否真的不相交

不许只看「改哪个文件」，要看**间接写入**：

| 陷阱 | 例子 |
|---|---|
| 共享台账 | 两个 agent 同时 `evolve record` → 互相覆盖 |
| 生成产物 | 改 `matrix-data.json` 会连带改 `evidence-grade.json` |
| 突变检验 | agent A 在改 `X.mjs` 做突变时，agent B 正在跑依赖 `X.mjs` 的验收 |
| 缓存/临时文件 | 同一个 `%TEMP%` 路径被两个 agent 用 |

**做法**：派活时明确列出「你可以写这 N 个文件」，并加上
「不许写：<其它 agent 的全部文件> + research/改进台账.json + .gitignore」。

### 检查 2：是否有人会跑全量验收

**只要有一个 agent 在跑 `verify-goal` / `measure-verifier-efficacy` / `size-guard`，
其它 agent 就不许写任何文件。**

原因：这些工具会读全仓状态，任何并发写都会让结果漂移。
实测症状：失败项在 A5/A13/A11 之间随机漂移，看起来像"代码坏了"，实际是"文件正在被改"。

**做法**：要么全部只读并行，要么全部写串行。**不许混。**

### 检查 3：谁负责还原突变

**每个做突变检验的 agent 必须在报告里列出一个表**：

```
| 文件 | 注入的标记 | 是否已还原 | 验证方式 |
|---|---|---|---|
| tools/x.mjs | [fault] | ✅ | grep 无输出 |
```

漏还原的后果：`imporo fs` 这种语法损坏会一直躺在仓库里，
下一轮谁跑验收都会莫名其妙地红，而且**没人知道是谁干的**。

**做法**：主线程在提交前**独立扫一遍**：
- `[fault]` / `fault-probe` 标记
- `imporo` / `functio` / `retrun` 等语法损坏
- 与 HEAD 对比：**任何未被报告的改动都要查**

## 分派模板

```
## 你可以写（只有这些）
- <文件 1>
- <文件 2>

## 你不许写
- research/改进台账.json   （append-only，主线程独占）
- .gitignore
- 其它 agent 的文件：<逐个列出>
- 任何你在做突变检验时没打算还原的文件

## 你不许做
- git add / git commit      （主线程统一提交，并行会冲突）
- 跑全量 verify-goal        （会和别人的写冲突）
- 改 tools/memory/store.mjs 与 tools/evolve/evolve.mjs（已触及 32KB 红线）

## 突变检验必须交付
| 文件 | 注入标记 | 已还原 | 验证方式 |

## 收尾必须做的三件事
1. `Select-String -Pattern "\[fault\]"` 你改过的文件 → 必须无输出
2. 跑一次 `node <你改的文件> --selftest` → 必须全绿
3. 报告里写「我没动过哪些明确不该动的文件」
```

## 已知的「看起来并行、实际串行」场景

以下任务**天然有依赖，不能并行**：

1. **改验收器 + 跑该验收器** —— 同一条链
2. **统一口径 + 补基于该口径的断言** —— 后者的期望值依赖前者
3. **改 `evolve.mjs` + 任何调 `evolve` 的 agent** —— 台账是单写者
4. **改矩阵数据 + 重算证据分级** —— 后者读前者

## 一次事故的完整复盘（2026-11-16）

**派了什么**：3 个写权限 agent
- A：`verify-evolve.mjs` + 报告
- B：3 个 `tools/benchmark|evolve` 验收器
- C：5 个验收器含 `verify-goal.mjs`

**表面看**：作用域不相交 ✅

**实际发生的**：
1. 三个 agent 都在做突变检验，其中某次走到 `survey.mjs`（**不在任何人的声明作用域内**），
   注入 `imporo` 后没还原 —— 于是全量验收开始随机红
2. C 改 `verify-goal.mjs` 时，A 正好在跑 `verify-evolve.mjs`（C 的依赖），两次结果不一样
3. 我中途跑了 3 次 `verify-goal`，得到 3 个不同答案（A5 / A13 / A11 各红一次）

**代价**：约 30 分钟排查，一度以为自己的改动引入回归。

**根因**：声明了「不许改的文件」，但**没有声明「不许做突变检验的文件」**。
`survey.mjs` 就被当成"顺便测一下"的靶子。

**修法**：把「不许写」升级成「不许写 **也不许对它做突变注入**」，
并且主线程提交前**独立扫残留**，不依赖 agent 自报。

## 什么时候该用多智能体

**适合**：
- 只读审查（找 bug、找假绿）—— 上一轮就是靠这个抓到 2 条「空集恒真」
- 互不相交的独立文件补断言
- 深读外部仓库、调研

**不适合**：
- 有共享写入（台账、生成产物）
- 任何一边要跑全量验收
- 需要互相参考结果的链式修改

## 效率与正确性的取舍

**串行 5 件小事 = 5 轮；并行 5 件但花 2 轮排查冲突 = 7 轮。**

> **并行只在「冲突概率接近 0」时才真正省时间。**
> 判断标准不是「看起来不重叠」，而是「**即使它们同时写，也不会互相影响**」。
