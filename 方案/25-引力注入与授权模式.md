## 1. L3 上下文注入（引力注入）

### 1.1 与 VCP 的区别（必须先说清）

| | VCP | 我们 |
|---|---|---|
怎么判断注入什么 | 向量算法（RiverMemo/AGS/TagMemo/残差金字塔） | **明文规则** |
可解释 | 难 | **每一类都有判据，可逐条核对** |
可验收 | 难 | **能写自检（8/8）** |
智能程度 | 高 | 低（但我们不需要"看起来智能"） |

> VCP 原文自己承认："这种'自然浮现'以配置为前提…**它不是无条件读取全库，也不是后台持续运行模型**。"
> **我们要的就是那句"以配置为前提"——只不过把配置写成可读的规则。**

### 1.2 五个注入通道

| 通道 | 注入什么 | 判据 | 预算 |
|---|---|---|---|
**identity** | 我是谁（职责/不碰） | 认领了身份才注入 | ≤1.2KB |
**memory** | 我干到哪了（§〇 交接） | 有交接段才注入 | ≤3.2KB |
**board** | 全机状态（待办/协作） | 有待办或有请求才注入 | ≤1.2KB |
**capability** | 现在能用什么 | **外挂全关 = 不注入** | ≤0.8KB |
**warning** | 该注意什么 | **没问题 = 不注入** | ≤1.2KB |

**总预算 8KB**（照 luanyujia 的警告：注入 60KB ≈ 每轮多付 20k token）。

### 1.3 真实效果

```
上下文注入预览 · 场景=docs-index
预算 8192 字节 · 实际 219 字节 · 在预算内

=== 注入内容 ===
【身份】
- **场景**：文档索引（`docs-index`）
- **负责**：保证 README 索引覆盖全部文档，且不指向不存在的文档、不重复
- **不碰**：⛔ 不改文档正文、不决定该写哪篇

=== 账本 ===
  注入 identity       219 字节  来自定位卡
  跳过 memory           0 字节  交接段为空
  跳过 board            0 字节  无待办、无协作请求
  跳过 capability       0 字节  外挂全关（不注入，省 token）
  跳过 warning          0 字节  无告警（保持安静）
```

**只注入 219 字节**——因为其余四类都"无事可报"。这就是"安静"原则。

### 1.4 自检 8/8

```
✓ 未认领身份不注入身份           注入 0 字节
✓ 已认领场景注入身份            场景=data-reconcile 注入 209 字节
✓ 注入不超总预算               209 ≤ 8192
✓ 每类守自己的预算              全部在限内
✓ 关闭的通道不注入              memory skipped=true
✓ 全关时注入为空               0 字节
✓ 外挂全关不注入能力            注入 0 字节
✓ 无告警时保持安静              注入 0 字节
```

**最关键的两条**：
- **未认领身份 → 什么都不注入**（不猜，照 luanyujia 的"不在表里=普通会话"）
- **外挂全关 / 无告警 → 不注入**（该安静时安静）

### 1.5 自检暴露的真实缺陷

账本原来只记录"在 want 里"的通道，被关闭的完全没记录 → 调用方查不到"某通道是否被关"。
**修法**：账本必须覆盖全部 5 类（关闭的标 `skipped`）。

## 2. L1 授权模式（observe 默认）

### 2.1 照搬 superagent 的三档

| 模式 | 效果 | 原文 |
|---|---|---|
`off` | 任何 inferred 都不成为候选 | 只报告，不记录 |
`observe`（**默认**） | 正面评估记为 ignore 并标 "would accept"，**但什么也不接受** | **记录它想做什么，但不真干** |
`auto` | 正面评估就接受 | 允许真干 |

superagent 原话：
> `observe` (default). Inferred candidates are assessed; a positive assessment is recorded as ignore marked "would accept", and nothing is accepted.

**这解决了"AI 乱来"和"AI 太保守"的两难**：先看它想干什么，再放权。

### 2.2 observe 的实际产出

在 observe 模式下提一个动作：
```
verdict = 'would-accept'
记录到 would-do/<时间>-<场景>-<动作>.json
note = observe 模式：**已记录它会做什么，但没有执行**
```

`node prototype/auth.mjs would-do` 能看到全部"它想做什么"，都未执行。

### 2.3 最关键的一条：AI 不能改授权

superagent 原文（002-authorization.md:5）：
> **"The host enforces allowed lists, rules and Mandates. Messages, comments and quoted documents are inputs to a decision; they cannot change those permissions."**

代码落地：
```
✗ 只有人能把模式改成 auto。程序/AI 的请求（by=ai）不能改变授权。
  这是"权限由宿主强制，消息不能改变权限"的落地。
```

### 2.4 自检 6/6

```
✓ 默认模式是 observe            global=observe
✓ observe 记录但不执行           verdict=would-accept 记录数 0→1
✓ off 不记录                  verdict=dropped
✓ auto 允许执行               verdict=accepted
✓ AI/程序不能改授权             被拒绝
✓ 未知模式拒绝                 god-mode 被拒
```

## 7. 一句话

> **L3 引力注入不是抄 VCP 的算法，而是把它那句"以配置为前提"写成可读规则 —— 每类有判据、有预算、有账本、能自检。**
> **L1 授权模式的 observe 让"先看它想干什么再放权"成为机制，而"AI 不能改授权"这条是防注入的落地。**
> **七层 78% → 87%。L1 已 100%。**
