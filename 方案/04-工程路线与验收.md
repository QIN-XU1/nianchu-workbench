# 04 · 工程路线、验收与风险

> 本文把 `02`/`03` 的架构落成**可执行计划**：分阶段、每阶段的交付物、验收标准、风险与对应动作。
> 原则：**每个阶段必须有一个"会失败的验收"**，否则不算完成（乱雨家五步法）。

---

## 0. 三条工程总律

### 总律 1：先证明"能失败"，再证明"能跑通"

> 每个里程碑的验收，都必须包含一个**故意让它失败**的测试。

理由：乱雨家原文"反例不报 = 这个检查是假的"；arXiv:2607.13083 证明自进化 Agent 会**幻觉出不存在的失败**；arXiv:2609.02246 证明自评会失效。

**工程含义**：验收清单里，每条"通过"都必须配一条"我知道它怎么才能不通过"。

### 总律 2：不写不能回滚的东西

任何改动（代码/配置/D 档资产）都必须能在 **60 秒内回滚**。
- 代码：git + 分支
- 配置：版本化文件
- D 档资产：`asset_version` 表
- 数据库：迁移必须向前兼容（加列不删列）

### 总律 3：先测地基，再谈上层

**R-1（能否唤醒持久化会话并投递）** 是所有架构的前提。**这个不验证，不写任何上层代码。**

## 1. 阶段划分

```
P0 地基验证（1-2 周）      → 只做 spike，不写产品代码
P1 最小内核（3-5 周）      → 单场景、单 Worker、能跑通真活
P2 多场景 + 编排（6-9 周）  → 三层、场景契约、并发
P3 记忆 + 上下文（10-12 周）→ 五层记忆、七通道、生命周期标签
P4 进化面（13-16 周）      → 观察→提案→沙箱→灰度→回滚
P5 持久与安全（17-20 周）  → 存算分离、daemon、凭据 Broker
P6 打磨（持续）            → 面板、指标、成本
```

**为什么要这个顺序**：每个阶段都**为下一个阶段提供可信的地基**。特别是 P4 必须等 P3（记忆）和 P1-P2（有真活可观察）之后——**没有真实失败样本的进化面，就是幻影工厂**。

## 2. P0 地基验证（第 1-2 周）

### 2.1 目标：回答 5 个"能不能"

| id | 问题 | 为什么致命 | 验证方法 |
|---|---|---|---|
| **R-1** | 能否创建/持久化一个 Session，销毁其内存态，**之后被外部事件唤醒并投递消息**？ | 双层的 Router 都必须常驻；若不能，架构要改成"每次新建 Session + 重放状态"，成本大增 | 写最小 Cordis 插件：`agentLoop.create` → 拿 sessionId → 等待 disposal → `agentLoop.resume` → 注入消息 → 观察 `agent/inbox/claimed` **[实测]** 事件 |
| **R-1b** | `subagents.sendMessage` 的父子邻接限制是否可用？（它要求"direct parent or direct continuable child" **[实测]**） | 若只能父子通信，Router↔Worker 就必须用 subagent 关系，而非平级 | same spike：测平级 Session 之间能否投递；不能则测"Router 作为 Scene 的 parent"是否可用 |
| **R-2** | `tools/post-execute` **[实测]** 能否实现"progress 结果不进历史"？ | 决定 VCP 生命周期标签能否真落地 | spike：工具返回 10KB + spill；观察 history 体积与 `toolResultPruner` 行为 |
| **R-3** | `agentPresets.register` **[实测]** 能否**运行时**注册新 preset 并立即 `mount`？ | 决定"新增场景零重启"能否成立 | spike：注册一个 `sea-scene-test` preset，`select` 到它，观察是否生效 |
| **R-4** | `webhookRuntime.register` **[实测]** 的自定义规则能否**只做"投递到已存在 Session"**？（它的内置动作只有 "Session creation" **[实测]**） | 决定外部事件（GitHub/邮件/webhook）能否进已有会话 | spike：注册规则，`run()` 返回 null（不建 Session），在回调里自己调 `agents.get(id)` 并投递 |

## 3. P1 最小内核（第 3-5 周）

### 3.1 目标
**一个真实场景、一个 Worker、端到端跑通一件真活，且能证明它做完了。**

建议选**第一个场景**：优先选**有确定性 DoneSpec 可用**的，不要选纯创作类。

推荐候选（按可判定性排序）：
1. **运维巡检**（check：跑脚本，diff-set 输出）
2. **数据核对**（check：比对两份数据，输出差异）
3. **文档一致性检查**（check：链接/术语/版本号校验）
4. **客服工单分派**（evidence：分类结果 + 分派记录）
5. ❌ 暂时不要选"写文案/做设计"（无客观判据）

### 3.2 交付物（代码）


### 3.4 P1 验收

| 类 | 项 | 标准 |
|---|---|---|
| **功能** | 端到端 | 外部事件 → Ticket → Worker 执行 → DoneSpec 通过 → 一条消息给到人 |
| **功能** | 失败路径 | check 不通过 → 回 Worker 带 diff-set → 二次修复 |
| **可靠性** | 杀进程恢复 | 执行中 kill -9，重启后工单继续或正确标记，**不重复外部动作** |
| **可靠性** | 幂等 | 同一事件重放 10 次，无重复副作用 |
| **机制** | 反例测试 | 故意把 check 改坏（让它永远 exit 0）→ **verify 必须判 fail**（这条证明 verify 不是装饰） |
| **成本** | 单工单 | token 与时长有记录；p50/p95 有基线 |

**P1 的 Go/No-Go**：
> **"反例测试"这一条不过，不进 P2。** 因为它意味着 DoneSpec 是假的，而 DoneSpec 是整个方案"通用性"的基石。

## 4. P2 多场景 + 三层编排（第 6-9 周）

### 4.1 目标
- 3 个场景并行
- 三层（Router/Scene/Worker）
- 场景间协作（通知/派单/裁决）
- 懒启动与降级

### 4.2 关键交付

| # | 机制 | 验收 |
|---|---|---|
| 1 | SceneContract 全字段（含 `assets.forbidden` 硬边界） | 越界写 ⇒ **存储层拒绝**（不是提示词拒绝） |
| 2 | 场景判定（快路径：Source 绑定；慢路径：Router） | 10 个混合事件 → 归属正确率 ≥95% |
| 3 | Scene 懒启动 + idle 挂起 | 空闲 30 min 后内存态释放；再次事件能恢复 |
| 4 | 场景间三种协作（通知不带唤醒 / 派单必回执 / 裁决交 Router） | 通知不产生 worker；派单必须在 5 min 内被签收 |
| 5 | 场景记忆隔离（E 档） | A 场景写 B 场景路径 ⇒ **拒绝 + 审计记录** |
| 6 | 注意力账本 + 三上限 | 同一件事第 4 条消息 ⇒ **被代码拒绝** |
| 7 | 消息信道适配（IM ≤100 词 / GitHub 结构化） | 代码级长度检查，不是提示词 |

### 4.3 P2 核心实验（回答 R-2 风险）

**目的**：验证"3 层是否比 2 层在**多场景**下更划算"。

| 组 | 配置 |
|---|---|
| A | 单 Router（Super-agent 式 2 层），所有场景塞进 Router |
| B | 三层（本方案） |
| C | 每场景一个独立单层（无 Router，人类直连 Scene） |

**负载**：3 个场景 × 50 个合成 Trigger（20% 工作请求）+ 跨场景事件 20 条。每组跑 5 次，随机任务顺序（照 arXiv:2608.18066 的教训）。

**指标**：
| 指标 | 期望 |
|---|---|
| p50 / p95 完成时间 | B ≤ A，且 B 的 p95 显著优于 A |
| Token 总量（读缓存） | B 可能高于 A（多一层），但**每完成项的 token** 应更低 |
| 路由错误率 | B 显著低于 A（A 把 N 个场景的记忆塞在一个上下文里会混淆） |

**预期（我的假设，需实测）**：B 在**场景数 ≥3** 时明显更优；**场景数 = 1** 时 A 更优。因此架构必须支持**降级到 2 层**（§4.2 第 3 条）。

### 4.4 P2 验收
- 3 场景端到端无串台（A 的消息不落到 B）
- E 档禁止：跨场景写记忆被拒（**必须能失败**：构造一个跨写尝试，必须被拒并留审计）
- 上限：第 4 条消息被拒（**必须能失败**）
- 成本：注意力税 < 1.0

## 5. P3 记忆 + 上下文（第 10-12 周）

### 5.1 目标
- 五层记忆 + 三红线
- 七通道上下文
- 工具结果生命周期标签
- 自报心跳（带上限）

### 5.2 交付

| # | 机制 | 验收 |
|---|---|---|
| 1 | M0–M5 分层与权限（谁能写哪层） | E 档跨写被拒；L0/L1 非人写被拒 |
| 2 | §〇 交接 ≤4 KB、主文件 ≤25 KB 的**自动检查** | 超限 ⇒ check 失败（**必须能失败**） |
| 3 | 记忆"先快照再减肥"，可证"没丢" | 减肥脚本输出差异集合；人为造一个丢失 ⇒ **必须报** |
| 4 | 七通道装配（顺序稳定 → cache 命中） | 断言 system prompt 分节顺序稳定；cache_read_tokens 有提升 |
| 5 | 生命周期标签（result/progress/status/notice） | 大进度结果**不进历史**（history 体积不增长） |
| 6 | 自报心跳 `[[NextHeartbeat::N]]` + 三重上限 | N=100000 ⇒ 被截断为 max_heartbeat_s |
| 7 | 压缩保留 DoneSpec/Evidence 指针 | 压缩后仍能跑 check（**关键回归**） |

### 5.3 关键实验：长程记忆（回答 Super-agent 8.1 的 open question）

**方法**：构造一个 30 天的模拟项目历史（300+ 事件、50 工单），测试：
- 第 30 天提出"第 2 天定过的方案是什么" → 能否找回（**准确率**）
- 跨场景提起旧任务 → 能否定位
- 上下文 token 是否随天数**线性增长**（应接近常数，靠归档+摘要）

**判据**：
| 指标 | 标准 |
|---|---|
| 30 天旧事召回准确率 | ≥80% |
| 每轮固定注入 token | 不随天数增长（±20% 内） |
| 存储增长 | 线性但可归档 |

### 5.4 P3 验收
- 30 天模拟历史的召回测试达标
- 压缩后 DoneSpec 仍可执行（**必须能失败**：压缩掉 check 引用 ⇒ 回归测试必须红）
- 记忆超限检查能失败
- 减肥可证没丢

## 6. P4 进化面（第 13-16 周）

### 6.1 目标
按 `03-自进化机制.md` 落地，**分三小步**：

| 小步 | 周 | 能力 |
|---|---|---|
| P4a | 13 | **只观察**：事件、指标、人的纠正记录、失败聚类 |
| P4b | 14-15 | **半自动**：提案 + 沙箱 + 人批才能应用 |
| P4c | 16 | **自主应用**（仅技能/记忆），灰度 + 自动回滚 |

### 6.2 交付

| # | 机制 | 验收 |
|---|---|---|
| 1 | Observe：失败聚类、纠正 diff、打回率、确认循环、缺口发现 | 每个信号源可产出候选 |
| 2 | Hypothesize：事件绑定（≥2 个真实 id） | 无事件 id 的提案 ⇒ 拒 |
| 3 | Propose：patch + counterexample + regression | 缺一 ⇒ 拒 |
| 4 | Sandbox：反例红→绿 / 回归绿→绿 / 成本增量 ≤10% | 造一个"假修复" ⇒ **必须拒** |
| 5 | 空提案奖励（phantom 检测） | 喂"从不失败"场景 ⇒ **提案数 = 0**（T1） |
| 6 | 过拟合检测（principle 不含日期/对象名） | 造一个含日期的 principle ⇒ 拒（T2） |
| 7 | 封存集（Agent 不可见）+ 三重指标 | 造一个"自评升、封存降"的补丁 ⇒ 拒（T3） |
| 8 | 灰度三档 + 严重负面清单 | 造一个"发错消息"的改动 ⇒ 立即回滚 |
| 9 | 回滚 60 秒 | 计时验证 |
| 10 | 记忆投毒防御 R1-R5 | 注入不可信内容 → 权威等级不升（T4） |

### 6.3 P4 验收（核心是 T1–T6 全过）

| 测试 | 通过标准 |
|---|---|
| **T1 幻影** | 提案数 = 0（对从不失败的场景） |
| **T2 过拟合** | principle 无日期/对象名；generalization_test 非空 |
| **T3 退化** | "自评升真降"的补丁必须被判拒 |
| **T4 投毒** | 权威等级保持 A0；后果性动作被拦 |
| **T5 回滚** | 60 秒内恢复 |
| **T6 噪声** | 5 次不同顺序的评估报告方差；结论在多数顺序成立 |

**P4 的 Go/No-Go**：
> **T1 + T3 + T4 三条不过，禁止开启自主应用（P4c）。** 只能停留在半自动（P4b）。

## 7. P5 持久与安全（第 17-20 周）

### 7.1 交付

| # | 机制 | 验收 |
|---|---|---|
| 1 | 存算分离：无状态 Host + 持久 Session/内核账本 | 杀进程 → 换一台机 → 恢复全部状态 |

### 7.2 安全专项测试（我们自己的 red team 清单）

| 攻击 | 期望 |

| Watchdog 被绕过（模型卡死但自报"在跑"） | W2 查"实质产出" ⇒ 抓出 |

### 7.3 P5 验收

- daemon 白名单拒绝测试能失败

- 跨机恢复成功

## 8. 备选方案（如果 P0 的 R-1 不可行）

| 方案 | 做法 | 代价 | 何时用 |
|---|---|---|---|
| **主案** | 持久 Router/Scene Session + 事件唤醒 | — | R-1 可行 |
| **备选 A** | **每次新建 Session + 从内核状态重建上下文** | 每事件重建 prompt，token +40%；冷启动 +2s | R-1 不可行但 R-4 可行 |
| **备选 B** | **单个常驻 Session + 严格分层角色**（靠 preset 切换） | 失去上下文隔离；Worker 与 Router 上下文会混 | 二者都不可行（最后手段） |
| **备选 C** | 改为 **"定时唤醒轮询"**（牺牲主动性换可靠性） | 失去"事件驱动"，变成"定时批处理"；Grok Bot 明确反对（成本高） | 仅当外部事件通道完全不可用时 |

**决策点**：P0 结束（第 2 周末）必须选一个并写进 ADR（架构决策记录）。

## 12. 度量面板：上线后看什么

### 12.1 第一屏（人只看这一屏）

| 指标 | 含义 | 目标 |
|---|---|---|
| **需要我做的事数** | 待验收 + 待回答 + 受阻 | 越少越好（不是越多越好） |
| **注意力税** | 主动消息 / 被采纳工作 | < 1.0 |
| **健康** | W1 基础设施是否全绿 | 全绿时不占空间（Super-agent `005-panel.md:57`：健康态不占空间） |
| **本周进化** | 提案数 / 应用数 / 回滚数 | 提案少而准 |

### 12.2 第二屏（排查用）

| 指标 | 用途 |
|---|---|
| 每场景 p50/p95 完成时间 | 发现退化 |
| `tokens_per_success` | 发现成本漂移 |
| check 失败率 + diff-set | 发现 DoneSpec 质量问题 |
| 确认循环轮次分布 | 发现"来回扯皮" |
| `phantom` 提案数 | 发现幻影失败 |
| 封存集 vs 自评差距 | 发现 reward hacking |

### 12.3 警戒线（自动降档）

| 条件 | 动作 |
|---|---|
| attention_tax > 1.0 连续 3 天 | `proactive: auto → observe` |
| check 失败率 > 40% | 该场景暂停派单，进人工排查 |
| 封存集与自评差距 > 10% | 进化面暂停 |
| 确认循环均值 > 3 | 触发"契约/澄清策略"提案 |
| 任何"严重负面" | 立即回滚 + 告警 |

## 15. 一句话收尾

> **SEA 的成败不取决于模型多强，而取决于三件事：**
> **① DoneSpec 能不能在非编码场景真的判定"做完了"；**
> **② 进化面能不能证明"真的变强"而不是"看起来更勤劳"；**
> **③ 注意力税能不能压到 1 以下。**
>
> 这三件事都过了，架构就成立；任何一件不过，"通用自进化 Agent"就仍然是一个叙事，不是一个产品。
