# 69 · 场景规模化的编排问题（用户质疑的正解）

> 用户原话：
> 「**简直就是在胡乱拼凑，如果有几百几千个场景需要融入，你又该怎么编排呢**」

---

## 一、我必须先承认的错误

### 1.1 我一直在做「调参」，不是「设计」

| 我做的 | 应该做的 |
|---|---|
10 个场景挤在环上 → 调半径、调角度 | 先问：**场景数量上限是多少？** |
节点颜色混 → 换调色板、改 HSL | 先问：**颜色要有意义还是只是区分？** |
标签太小 → 改字号 | 先问：**何时该显示标签，何时该隐藏？** |

**"调参"只能解决当前这 10 个场景。第 11 个开始失效，100 个彻底崩。**

### 1.2 具体会怎么崩

```
当前实现：
  angle = (i / 场景总数) * 2π        ← 均分圆环
  r = R * 0.66                      ← 固定半径

10 个场景   → 间隔 36°，清晰
50 个场景   → 间隔 7.2°，开始挤压
100 个场景  → 间隔 3.6°，标签完全重叠
1000 个场景 → 间隔 0.36°，全部糊成一圈

结论：这个布局算法的复杂度是 O(1/场景数) 的空间利用率，
      本质上是「不能扩展」的。
```

## 二、正确的思路：先回答三个问题

### 2.1 场景数量到底会到多少？

用户说的是「**不可估量**」「几百几千」。

所以设计目标必须是：**支持 10,000 个场景**（不是 100 个）。

### 2.2 用户会同时关心多少个场景？

**关键洞察**：用户不会同时关心 10,000 个场景。
任何时候，他关心的只有：
- 正在跑的（个位数）
- 最近的（十几个）
- 出问题的（几个）

**所以正解不是「全部显示」，而是「按需展开」。**

### 2.3 什么维度能让场景自然成组？

场景不是随机出现的。它有：
- `role`（职责描述）
- `inputs/outputs`（依赖关系）
- 执行频率、最后活跃时间

**这些天然形成聚类结构。**

## 三、解法：仿中国古代星官体系的三层 LOD

### 3.1 为什么用星官体系

用户是国学爱好者，而星官体系恰好解决这个工程问题：

```
中国古代把星空分为：
  三垣（紫微垣、太微垣、天市垣） —— 中央区域
  二十八宿（分四象：苍龙、玄武、白虎、朱雀） —— 外围环带

每宿是一个「星官」，内含若干「星」。
这正是一个**两级分区 + 数量可变**的结构。
```

### 3.2 三层 LOD（Level of Detail）

```
┌─ LOD 0：场景 ≤ 8 个 ────────────────────────────────┐
│  直接显示为「星」                                        │
│  布局：均分环（当前实现就够）                              │
│  ← 当前的 10 个场景就在这一层（去掉 hub 剩 10，边界）       │
└──────────────────────────────────────────────────────┘

┌─ LOD 1：场景 9 ~ 200 个 ─────────────────────────────┐
│  按「四象二十八宿」分区                                  │
│  每个宿 = 一个扇区，扇区角度 ∝ 该宿场景数                  │
│  宿内场景按径向树排列                                    │
│  外圈显示宿名 + 星数，内圈显示重要场景                     │
└──────────────────────────────────────────────────────┘

┌─ LOD 2：场景 > 200 个 ───────────────────────────────┐
│  再往上一层：只显示「宿」聚合节点                        │
│  点击宿 → 展开显示该宿内场景（按需加载）                   │
│  支持搜索直达（不用展开）                                │
└──────────────────────────────────────────────────────┘
```

### 3.3 关键算法：扇区角度 ∝ 场景数（面积正比）

这是解决「挤成一圈」的核心。

```
传统做法（错）：
  每个场景固定角度 = 2π / N
  → N 越大越挤，最终糊成一圈

正解：
  每个「宿」的角度 = (该宿场景数 / 总场景数) * 2π
  宿内每个场景的角度 = (宿角度) / (宿内场景数)
  → 每个场景占据的**面积恒定**，N 再大也不挤
```

**这就像地图上的行政区**：大省面积大，小省面积小，但每块地都能看清。

### 3.4 宿内布局：径向树

一个宿内有 N 个场景时，不能又挤成一圈。用**径向树**：

```
        ┌─ 场景1（内圈）
        │
  宿 ────┼─ 场景2（中圈）
        │
        └─ 场景3（外圈）

第 i 个场景的半径 = R_inner + (i / N) * (R_outer - R_inner)
第 i 个场景的角度 = 宿中心角 + 微小偏移（避免直线排列）
```

**效果**：宿内场景呈「放射状」展开，N 越大，径向往外延伸。

### 3.5 宿的分配规则（有依据，不是随机）

按场景 `role` 的语义归入二十八宿。映射表：

```

  角 ─ 架构设计      亢 ─ 接口定义      氐 ─ 基础建设
  房 ─ 数据存储      心 ─ 核心逻辑      尾 ─ 边界处理
  箕 ─ 部署发布

  斗 ─ 记忆管理      牛 ─ 索引检索      女 ─ 知识整理
  虚 ─ 缓存优化      危 ─ 故障诊断      室 ─ 环境配置
  壁 ─ 依赖管理

西方白虎（肃杀、审查）
  奎 ─ 代码审查      娄 ─ 质量检测      胃 ─ 性能分析
  昴 ─ 安全漏洞      毕 ─ 逆向分析      觜 ─ 竞品拆解
```

## 四、实现计划

### 4.1 数据层：给场景加「宿」归属

```json
// sceneboard/scenes/hub.json
{
  "id": "hub",
  "xiu": "ziwei",        // 归属宿（可选，缺省自动推断）
  "role": "..."
}
```

自动推断：扫 `role`/`name`/`description` 的关键词，匹配二十八宿映射表。

### 4.2 布局层：`ui/panels/constellation.js`

```js
computeConstellation(scenes)
  → 判断 LOD 层级
  → 分配宿
  → 计算每个宿的扇区角度（∝ 场景数）
  → 计算宿内场景的径向位置
返回 { lod, xius: [{name, angle, span, scenes: [{angle, radius}]}] }
```

### 4.3 渲染层：按 LOD 渲染

```
LOD 0: 均分环（当前实现）
LOD 1: 二十八宿扇区 + 宿内径向树
LOD 2: 只画宿聚合节点 + 星数徽标
```

### 4.4 交互层：展开/收起

```
点击宿（LOD 2）→ 进入该宿（LOD 1）
点击场景 → 详情
ESC → 返回上一层
```

## 六、一句话

> **我之前的错：用固定角度均分，本质不可扩展。**
>
> **正解：**
> **① 按场景数选 LOD 层级（<8 直接画 / 9-200 分宿 / >200 只画宿）**
> **② 每个宿的扇区角度 ∝ 该宿场景数（面积正比，永不被挤）**
> **③ 宿内用径向树展开（N 越大向外延伸，不重叠）**
> **④ 按 role 关键词自动归入二十八宿（有依据，可解释）**
>
> **验证：造 1000 个测试场景，跑帧率和可达性。**
