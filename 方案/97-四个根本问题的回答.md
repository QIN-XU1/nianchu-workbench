> 1. 该领域顶尖专家会做哪些我没有要求的事情？

## 问题 1 · 顶尖专家会做哪些我没有要求的事情

### 专家会做 1：先证明系统能跑，再讨论机制

**我会做：** 设计七层架构、五套机制、三级进化。
**专家会先做：** 跑一个最小真实任务，看哪一步断了。

**为什么：** 一个从未跑过真实任务的系统，"设计文档"和"实际需要"之间可能有巨大鸿沟。
原项目的所有机制，**都是被事故逼出来的**（原文："这三套机制不是设计出来的，是被事故逼出来的"）。

**具体动作：**
```
① 造一个真实任务：完成 challenges/c4-xxx（新的真实场景任务）
② 用现在的 11 个场景之一去跑它
③ 记录：哪一步断了、卡在哪、为什么
④ 这个断点才是机制该解决的第一优先级
```

### 专家会做 2：先建立"能重复的失败"

**我会做：** 说"必须造反例"。
**专家会做：** 把反例变成**自动化脚本**，每次 CI 都跑。

`challenges/*/selftest.mjs` 就是范例：
```js
// 自动做法：
// ① mkdtemp 建临时目录
// ② 复制基线数据
// ③ 注入一个具体错误
// ④ 跑 check.mjs，断言 exit 非 0 且输出包含特定项
// ⑤ 清理临时目录
// ⑥ SHA256 校验原始数据未被污染
```

**关键洞察：** 变异测试本身也要被测试（"临时目录已清理"、"原始数据 SHA256 未变" 就是元测试）。

### 专家会做 3：先给"正确"下可执行的定义

**我会做：** 写"机制必须能 exit 非 0"。
**专家会问：** 那么，**什么算"正确"？谁来判定？**

`BRIEF.md` 的做法值得学习：
```markdown
## 你必须保证的不变量

- completeness            ← 完整性
- uniqueness              ← 唯一性
- referential-integrity   ← 引用完整性
- required-field          ← 必填字段
```

**这四个词是数学化的、可判定的**，不是"数据要一致"这种形容词。

### 专家会做 4：把"证据"做成不可伪造的东西

**我会做：** 写"回执要带证据"。
**专家会做：** 让证据**可复算**。

| 弱的证据 | 强的证据 |
|---|---|
"我跑完了，通过了" | `PASS c3: 差异集合 = 0` + exit 0（可复跑） |
"我改了 3 个文件" | `SHA256 前 = abc123 / 后 = def456`（可校验） |
"没有副作用" | 临时目录已清理 + 原始数据哈希未变（可验证） |

### 专家会做 5：区分"机制"和"策略"

**我会做：** 把所有东西都写成机制。
**专家会区分：**

| 类型 | 要不要机制化 | 例子 |
|---|---|---|
**客观可判定** | ✅ 机制化 | §〇 超 4KB、sessionId 不存在、差异集合 > 0 |
**主观判断** | ❌ 留给人 | "这个架构好不好"、"这段文案有没有感染力" |
**一次性** | ❌ 不机制化 | 这次特殊处理 |

原项目原文：**"判断类（好不好、该不该做）没有客观判据，硬写成检查会误杀。"**

### 专家会做 6：给系统建"体检基线"

**我会做：** 设计健康度指标。
**专家会先做：** 记录当前基线，否则不知道"变好"是相对什么。

```
基线 = 现在所有可测指标的当前值
  · 场景数 11
  · 真实使用场景数 0        ← 这是最重要的一条
  · 技能覆盖率 1/11 = 9%
  · 平均 §〇 大小 1387 字节
  · 检查工具数 7/20

没有基线，"进化"无法验证。
```

### 专家会做 7：先设"逃生门"再谈进化

**我会做：** 三级进化 + 三条安全阀。
**专家会先问：** 如果进化把系统搞坏了，**怎么 5 分钟内回到可用状态？**

**我们的现状：无 git → 没有回滚能力。**

```
专家做的第一件事可能是：git init + 首次提交
这比任何机制设计都优先，因为没有它，一切改动都是不可逆的。
```

### 专家会做 8：把"文档"变成"可执行的规约"

**我会做：** 写 100 篇方案。
**专家会做：** 每篇方案必须附带一个**能跑的检查**，否则不进主分支。

```
判据：一份文档，如果去掉"论证过程"，剩下的"结论"能不能变成一个检查？
  能 → 它有价值
  不能 → 它是感想，不是规约
```

## 问题 3 · 他们会用什么具体方法和工具

### 方法 1：变异测试（Mutation Testing）

**这是 challenges/ 已经证明有效的核心方法。**

```javascript
// 标准骨架
function runCase(name, mutate, expect) {
  const tmp = fs.mkdtempSync(path.join(os.tmpdir(), 'test-'));
  try {
    copyBaseline(tmp);          // ① 复制基线
    mutate(tmp);                // ② 注入错误
    const r = execSync('node check.mjs test', { env: { SEA_DATA_DIR: tmp } });
    assert(r.status !== 0);     // ③ 断言失败
    assert(r.stdout.includes(expect));  // ④ 断言命中具体项
  } finally {
    fs.rmSync(tmp, { recursive: true });  // ⑤ 清理
    assert(hash(baseline) === originalHash);  // ⑥ 元测试：原始数据未污染
  }
}
```

**工具：**
```
· Node 内置 fs / path / os / crypto（无第三方依赖 —— challenges 明确规定）
· mkdtempSync + SHA256
```

### 方法 2：不变量优先设计（Invariant-First Design）

**先写不变量，再写实现。**

```markdown
## 不变量（必须永远为真）

- completeness           每个 A 必须有对应 B
- uniqueness             主键不重复
- referential-integrity  外键必须存在
- required-field         必填字段非空
- bound                  §〇 ≤ 4096 字节
```

**工具：** `BRIEF.md` 模板

### 方法 3：可复算的证据链

```
每个断言都要能独立复算：
  · 断言"§〇 没超限" → 输出实际字节数
  · 断言"sessionId 存在" → 输出查表结果
  · 断言"没越界" → 输出 mtime 与归属对照
```

**工具：** SHA256 / 字节数 / 时间戳

### 方法 4：git 作为进化基础设施

```
· 每次机制改动一个 commit
· commit message 写清"改了什么判据"
· 进化台账直接引用 commit hash
· 回滚 = git revert
```

**这是我们最缺的。没有 git，一切"版本化/回滚"都是空话。**

### 方法 5：Property-Based Testing（性质测试）

**区别于"给例子测试"，而是"给性质测试"。**

```
传统：测"输入 {a:1} 应该输出 2"
性质：测"对任意输入，输出必须 ≥ 输入"（跑 1000 个随机输入）
```

**用在机制上：**
```
性质：对任意场景，§〇 大小 ≤ 4096
  测法：生成 100 个随机大小的 §〇，全部必须通过或被拦
```

**工具：** Node 内置 + 简单随机生成器（不引第三方库，保持零依赖）

### 方法 6：基线快照（Baseline Snapshot）

```
每次改动前后各拍一次快照：
  · 所有可测指标的当前值
  · 文件哈希
对比，证明"只改了想改的"
```

## 问题 4 · 除了你我之外，还有什么能证明结果是正确的

这是最关键的一问。**自我验证永远不可信**（我可能就是错的）。

### 证明源 1：可复跑的第三方脚本

```
不依赖 AI 判断的东西：
  · check.mjs 输出 PASS/FAIL + 差异集合
  · exit code
  · SHA256 哈希

任何人（包括未来的我）在同一台机器上跑，结果必须一致。
```

### 证明源 2：变异测试（证明"检查真的会失败"）

```
最强的证明：
  不是"检查通过了"，而是"我造了 6 个错误，检查全部捕获了"。

这证明了：
  · 检查不是装饰
  · 检查的判据是对的
  · 检查没有漏掉情况
```

### 证明源 3：文件系统的不变式

```
· 原始数据 SHA256 未变（证明测试没污染）
· 临时目录已清理（证明没有泄漏）
· git diff 只包含预期改动（证明没有误伤）
```

### 证明源 4：真实任务结果

```
最强的证明：系统真的完成了一个真实任务。
  · 一个真实的需求
  · 一个真实的产物
  · 用户真实说"这个有用"

这是唯一不能伪造的证明。
我们现在 0 个真实任务完成记录。
```

### 证明源 5：独立复现者

```
让另一个 AI（或另一个模型）在没有我解释的情况下：
  · 只按文档操作
  · 跑出同样的结果
如果做不到 → 文档不完整或系统不可复现
```

### 证明源 6：时间

```
机制是否有效，最终看：
  · 一个月后框架还在用吗？
  · 场景记忆里有没有真实内容？
  · 崩溃日志有没有减少？

时间是唯一无法伪造的证明。
```

### 证明源 7：反例清单

```
"能证明正确"的最强形式之一是：
  · 列出所有已知的失败方式
  · 逐条证明已处理
  · 承认未处理的

challenges/SELFTEST.md 就是这种形式。
```

## 结论：这不是"更大的版本"，而是"方向完全不同"

### 我原来的方向（更大）

```
七层架构 → 五套机制 → 三级进化 → 六个哨兵 → 场景工厂 → 11 个场景
提供 100 篇文档，证明设计很完备
```

### 应该的方向（更深）

```
第 1 步：git init（让一切可回滚）
第 2 步：跑通一个真实任务（证明系统能用）
第 3 步：把断点变成机制（被事故逼出来的机制才是真机制）
第 4 步：用变异测试证明机制有效（造错误，必须捕获）
第 5 步：基线快照，证明"变好"是相对的
第 6 步：把 challenges/ 范式抽象成机制模板
第 7 步：逐个机制照此实现
```

**"深入"不是层数更多、机制更多、文档更多。
"深入"是每一层都真的能跑、每一个机制都真的被证明有效。**
