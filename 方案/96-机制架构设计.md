# 96 · 机制架构设计（含自进化）

> 用户三点确认：
> ① 机制架构首要斟酌搭建
> ② 机制形式怎么更好怎么完善怎么来
> ③ 场景必须支持**自进化**，越来越完善

---

## 零、先想清楚一件事：什么是"机制"

原项目给了一条最狠的判据：

> **「没有'会失败的检查'的规矩 = 一句口号。」**
> 如果一个检查**永远通过**，它就不是检查，是装饰。

**所以本设计的每一条机制，都必须回答五个问题：**

```
① 违规长什么样？        （可判定，不是形容词）
② 判据的唯一出处在哪？  （两处判据 = 早晚打架）
③ 哪个检查会 exit 非 0？ （必须能说出差异集合）
④ 它的反例是什么？      （故意造违规，必须报）
⑤ 挂在什么节奏上？      （手动跑的检查 = 没跑）
```

**回答不全的，本设计里一律标为「口号」，不进机制层。**

## 一、总体架构：七层 + 一条主轴

### 1.1 七层（比原项目六层多一层"进化层"）

```
L0  宪法层    铁律，只有宿主能改，版本化
L1  共享层    宿主画像 / 索引 / 台账 / 通知待办 / 体检
L2  场景层    六件套：配置 / 定位卡 / 记忆 / 技能 / 面板 / 身份绑定
L3  进化层    ★ 新增：健康度 / 归因 / 三级进化 / 版本回滚
L4  归档层    备份 / 冷备 / 场景归档（只进不改）
L5  运行时层  引擎 / 外壳 / 工具 / 插件
L6  验证层    所有能 exit 非 0 的检查
```

**为什么"进化层"要单独成层：**
```
它不属于任何单个场景（要横向对比多个场景的健康度）
也不属于共享层（共享层记"发生了什么"，进化层记"变好了没有"）
它需要自己的数据、自己的判据、自己的检查。
```

**L6 独立成层的原因：**
```
原项目把检查散在各处，结果"谁都能写检查，谁都不知道有没有重复判据"
L6 集中管理，一个检查一处出处。
```

### 1.2 主轴：每个东西只有一个"真源"

```
判据：这个东西第二次出现在别处，必须是**指针**，不能是副本。

反例（我们现在就有的问题）：
  · 项目名同时出现在 索引.json、_共享记忆/项目.json、记忆地图.json
  · 三处内容不一致时，没人知道信哪个
```

## 二、五套基础机制

### 机制 1｜身份系统（防串台）

**为什么必须有：**
```
AI 不知道自己是谁 → 会猜 → 猜错就串台
原项目："三个字段少写一个不会报错，只会悄悄退化成'随便显示一条'"
```

**结构：七列身份索引表**

| 列 | 内容 |
|---|---|
① 场景 id | `arch-review` |
② 场景名 | 架构梳理 |
③ 面板 id | `ar-ai` |
④ 会话标题 | 真实完整标题（`sessionTitle`） |
⑤ 会话 id | 引擎真实 id（`sessionId`） |
⑥ 定位卡 | `scenarios/arch-review-context.md` |
⑦ 记忆目录 | `场景记忆/架构梳理/` |

**存放位置（唯一真源）：**
```
workbench/引擎数据/.dsh/场景记忆/_共享记忆/身份索引.md
```

**五步落地：**

| 步 | 内容 |
|---|---|
① 违规长什么样 | 身份索引表某行的 `sessionId` 在引擎里不存在；或某个场景 json 里有 AI 面板但表里没这行 |
② 判据唯一出处 | 身份索引表本身（工具只读它，不另判） |
③ 会失败的检查 | `node 工具\身份哨兵.mjs` → 列出"表里有但引擎没有" / "引擎有但表里没有" → exit 1 |
④ 反例 | 手工把某行 sessionId 改成一个不存在的 → 必须报 |
⑤ 节奏 | 每次新建/换会话后必跑；挂进全量体检 |

**开场认领（30 秒，写进 AGENTS.md）：**
```
① 取本会话 id
② 查身份索引表 → 得场景/定位卡/记忆目录
③ 读定位卡（职责/边界/触发词/上次进度）
④ 读 §〇 交接（干到哪/下一步/卡点）
```

### 机制 2｜记忆系统（防失忆 + 防肥胖）

**结构：三层 + 三条红线**

```
注入层  AGENTS.md        ≤ 2 KB   （我们已达标：1709 字节）
私有层  §〇 交接          ≤ 4 KB   （实测全部 1085~1594 字节，达标）
       主文件            ≤ 25 KB
项目层  项目记忆/<id>.md  ≤ 8 KB
```

**为什么红线是硬指标（原项目真实数据）：**
```
§〇 涨到 40 KB → 没人读 → 交接形同虚设
注入层 60 KB   → 每轮多付 20k token → 一天几十轮 = 灾难
```

**五步落地：**

| 步 | 内容 |
|---|---|
① 违规长什么样 | 文件字节数 > 红线；或 §〇 里出现"只追加不覆盖"的痕迹（多份"上次交接"） |
② 判据唯一出处 | `工具\记忆哨兵.mjs`（其他工具不许各自判一次） |
③ 会失败的检查 | 逐文件量字节，超限列出 `文件名 + 实际 + 红线 + 超出量` → exit 1 |
④ 反例 | 往某个 §〇 里灌 5 KB → 必须报 |
⑤ 节奏 | 每次写回后自动跑（写回工具内置调用） |

**关键：写回要**在工具里强制检查**，不是靠人记得跑。**
```
node 工具\memory.mjs write --scene "<名>" --file xxx.md
  → 内部先算字节 → 超限直接拒绝写入并报错
```

### 机制 3｜协作系统（防派单进黑洞）

**核心区分（原项目最贵的教训）：**

| | 公告 | 派单 |
|---|---|---|
对方要做什么 | 只是知道 | **动手** |
要不要唤醒 | ❌ 不唤醒（只落盘） | ✅ **必须唤醒** |
预期回复 | 无（收到知悉不许回） | **一条带证据的回执** |

**原项目真实数据：一天发 36 条"通知"，只有 8 条真投递 = 22% 执行率。**

**状态机（五态，缺"未回执"就等于扔进黑洞）：**
```
① 想出派单
     ├─ 不用动手 → 公告（只落盘）
     └─ 要动手   → ② 已投递（真唤醒）
                     ├─ 有回执 → ③ 已回执 → ⑤ 销账
                     └─ 超时   → ④ 未回执（进台账）
```

**派单正文四件套（缺一件对方就得追问）：**
```
① 现象    ：现在是什么样子（可观察，不要形容词）
② 照哪做  ：哪份文档哪一节 / 哪个工具
③ 怎么验  ：做完跑什么、看到什么算通过
④ 回一句  ：明确要回执
```

**回执三条硬规矩：**
```
① 只在自己窗口说"我做完了" = 没交付
② 只说"好了"等于没说（必须带证据）
③ 收到"知悉"不许回
```

**台账结构：**
```json
// _共享记忆/派单台账.json
{
  "dispatches": [
    {
      "id": "d-20261109-001",
      "from": "hub",
      "to": "research",
      "type": "dispatch",          // dispatch | announce
      "subject": "搜集同类项目架构",
      "evidenceRequired": true,
      "createdAt": "2026-11-09T18:30:00+08:00",
      "state": "delivered",        // created | delivered | acked | unacked
      "ackedAt": null,
      "receipt": null,
      "deadlineHours": 24
    }
  ]
}
```

**五步落地：**

| 步 | 内容 |
|---|---|
① 违规长什么样 | ① 派单 type=dispatch 但没真唤醒；② 派出 >24h 无回执；③ 回执无证据（小于 20 字或没有"证据"字样） |
② 判据唯一出处 | `派单台账.json`（工具只读它） |
③ 会失败的检查 | `node 工具\派单哨兵.mjs` → 列三张单：我发出没回的 / 别人在等我回的 / 回执无证据的 |
④ 反例 | 造一条 type=announce 但标成 dispatch 的记录 → 必须出现在"未回执" |
⑤ 节奏 | 每次派单后立即写台账；每日体检扫一次 |

### 机制 4｜修改权分档（防互相污染）

**五档（照原项目，不简化）：**

| 档 | 范围 | 谁能改 | 越界后果 |
|---|---|---|---|
**A** | 共享·宪法（AGENTS.md / 铁律） | 只有宿主 | 规矩互相打架 |
**C** | 共享·工具运行时（工具/插件/技能目录） | 管理员场景；别人只能提请求 | 一人改工具，全员静默失效 |
**B** | 共享·板与台账（派单/通知/索引） | 各场景写自己那些行 | 删别人行 = 别人活消失 |
**D** | 自己的专属（自己场景配置/记忆/技能） | 自己改 | 改自己规矩不告知 ⇒ 分叉 |
**E** | 别人的专属 | ⛔ **一个字都不许写** | 真实事故：两场景互写记忆，一周后互相引用错误结论 |

**判据一句话：**
```
这东西改了会影响别人吗？
  ├─ 会  → A 或 C（⛔ 我不能改，只能提请求）
  └─ 不会 → 是别人的吗？
        ├─ 是 → E（⛔ 只许写请求）
        └─ 否 → D（自己改）
```

**E 档请求格式（不能只说"这里有问题"）：**
```
现象 + 该谁做 + 怎么做 + 做完怎么验
```

**五步落地：**

| 步 | 内容 |
|---|---|
① 违规长什么样 | 场景 A 的进程写了场景 B 的记忆目录；或非管理员写了 AGENTS.md |
② 判据唯一出处 | `场地地图.json`（一份文件定义"谁的地盘是哪些路径"） |
③ 会失败的检查 | `node 工具\越界哨兵.mjs --since 24h` → 扫文件修改时间 + 归属表 → 列出越界写 → exit 1 |
④ 反例 | 故意让某场景写一次别人的记忆 → 必须报 |
⑤ 节奏 | 每次多场景协作后跑；每日体检扫 |

**注意：这是最难做的一条。** 因为前端/脚本没有"我是谁"的上下文。
**折中方案：** 先做"事后审计"（按文件 mtime + 归属表推断），不做"事前拦截"。

### 机制 5｜场景六件套（防场景泛滥）

**六件（照原项目，补齐到 6）：**

| # | 组件 | 我们现状 | 缺了会怎样 |
|---|---|---|---|
① | 场景配置 `<id>.json` | 11/11 ✅ | 标签栏不出现 |
② | **定位卡** `<id>-context.md` | **10/11** ⚠ | AI 不知道干什么 |
③ | **场景记忆** | 11/11 ✅ | 换会话断片 |
④ | 专属技能 `SKILL.md` | **1/11** ✗ | 用通用办法硬干 |
⑤ | 专属面板（可选） | 有 | 只能靠聊天 |
⑥ | **会话 + 身份索引行** | **10/11** ⚠ | 串台 |

**"2、3、6 是不可省的三件。"**

**"该不该开"的判定判据（原项目，直接采用）：**

**开：**
```
✅ 这类活会反复回来（不是一次性）
✅ 有自己的资产目录
✅ 有自己的专业流程
✅ 有明确的边界（知道不碰什么）
```

**不开：**
```
❌ 一次性的活 → 记当次笔记
❌ 只是大项目里的一个功能 → 属于现有场景的子项
❌ 说不出"不碰什么" → 边界没想清
```

**一句话判据：**
> **「半年后我还会为它单独打开一个窗口吗？」答不上来就别开。**

**五步落地：**

| 步 | 内容 |
|---|---|
① 违规长什么样 | 六件套缺件；或新场景的"不碰什么"字段为空或 ≤5 字 |
② 判据唯一出处 | `scene-validate.mjs`（已有，需增强） |
③ 会失败的检查 | 检查六件，缺件列出 + 判定"不可省三件"是否齐全 → exit 1 |
④ 反例 | 造一个缺定位卡的场景 → 必须报 |
⑤ 节奏 | 每次 scene-hatch 后自动跑；挂进体检 |

**给 scene-hatch 加 `--should` 参数：**
```
node 工具\scene-hatch.mjs --should --id x --name "..." \
  --repeat yes --assets yes --process yes --boundary "..."

四个答案任一为 no → 拒绝创建，并说明原因。
```

## 三、机制 6｜自进化（本次核心新增）

### 3.1 先定义：什么叫"自进化"

**不是"AI 自己改自己" —— 那是失控。**

**自进化 = 场景在运行中变好，且这个"变好"是可验证的。**

**三个必要条件（缺一则退化）：**

| 条件 | 含义 | 我们现在 |
|---|---|---|
**有信号** | 场景知道自己做得好不好 | ✗ 没有 |
**有归因** | 知道为什么好/不好 | ✗ 没有 |
**有改进** | 能把归因变成可验证的改动 | ✗ 没有 |

**没有信号 → 进化就是随机漂移。**
**没有归因 → 只会打补丁治标。**
**没有改进 → 知道问题也改不了。**

### 3.2 信号层：场景健康度

**三个指标（都能自动采集，不需要人工打分）：**

| 指标 | 定义 | 数据来源 |
|---|---|---|
**一次通过率** | 首次交付被接受 / 总交付 | 回执里的 `accepted: true/false` |
**返工次数** | 同一任务被要求重做的次数 | 派单台账里同 subject 的重复派单 |
**越界次数** | 动了不该动的东西的次数 | 越界哨兵的历史记录 |

**存放：**
```json
// _共享记忆/健康度.json
{
  "scenes": {
    "arch-review": {
      "windows": [
        {
          "from": "2026-11-01", "to": "2026-11-08",
          "tasks": 12, "firstPass": 9, "firstPassRate": 0.75,
          "rework": 3, "crossBoundary": 0
        }
      ],
      "trend": "improving"     // improving | stable | degrading
    }
  }
}
```

**采集时机：** 每次任务收尾（写回执时），由回执工具自动追加。

**五步落地：**

| 步 | 内容 |
|---|---|
① 违规长什么样 | 一次通过率 < 60%；或趋势连续两窗 `degrading`；或越界 > 0 |
② 判据唯一出处 | `健康度.json` |
③ 会失败的检查 | `node 工具\健康哨兵.mjs` → 列出低于阈值的场景 + 具体指标 → exit 1 |
④ 反例 | 手工写一个 firstPassRate=0.3 的窗口 → 必须报 |
⑤ 节奏 | 每周体检 |

### 3.3 归因层：场景画像

**每 N 次任务（建议 N=10），生成一份归因摘要。**

**归因四问（必须回答，不能空泛）：**
```
① 哪类任务总失败？      → 技能缺口
② 哪类判断总被纠正？    → 身份卡边界模糊
③ 哪类交付总要返工？    → 流程缺失
④ 哪类操作总越界？      → 权限理解错误
```

**写回位置：**
```
场景记忆/<场景名>/场景私有记忆.md 的 §六 归因摘要
```

**示例（真实的、可判定的）：**
```markdown
## §六 归因摘要（2026-11-09 第 3 期）

- 任务 12 次，一次通过 9 次（75%）
- 失败 3 次，全在"竞品功能矩阵"这类任务
  → 归因：技能里没有"功能矩阵怎么拆"的流程
  → 动作：L2 技能进化（建议新增 §3 功能矩阵拆法）
- 判断被纠正 1 次：把"架构方案"理解成"技术选型"
  → 归因：身份卡"职责边界"没写清这两者的区别
  → 动作：L3 身份进化（需人工确认）
- 越界 0 次
```

### 3.4 改进层：三级进化（风险从低到高）

#### L1 记忆进化（自动，不需要审批）

```
触发：任何一次任务收尾
动作：把"坑与决策"追加进 §五
限制：只追加不修改；单条 ≤ 200 字；总长受 25KB 红线约束
回滚：不需要（只追加，不会破坏已有）
```

**这是最安全的，也是最有价值的 —— 经验就是这样一点点攒起来的。**

#### L2 技能进化（半自动，需要回测）

```
触发：同类问题在 30 天内出现 ≥3 次，且技能文件里没有对应节
动作：
  ① 生成技能补丁（新增一节）
  ② 用历史案例回测（把过去 3 次失败案例当测试用例）
  ③ 回测通过才写入
限制：每次只加一节；技能文件 ≤ 15KB
回滚：技能文件带 version 和 changelog，可回退
```

**"回测"是关键 —— 没有回测的技能改造是赌博。**

**回测怎么做（具体）：**
```
把过去 3 次失败的任务描述 + 当时的错误做法 记成一份"回测集"
新技能写好后，用新技能重走这 3 个案例：
  · 新技能里有没有这一步？      （静态检查）
  · 如果按新技能做，会不会避开原来的错？  （人工判定或 AI 判定）
两个都过才算通过。
```

#### L3 身份进化（人工确认，最谨慎）

```
触发：同一类判断被纠正 ≥2 次；或越界 ≥2 次
动作：修订身份卡的"职责边界"或"不做什么"
限制：必须人工确认后才写入
回滚：身份卡带 version，可回退
```

**为什么必须人工：身份卡定义"我是谁"，改错了整个场景都会跑偏。**

### 3.5 安全阀（防止"进化"变成"退化"）

**三条保护：**

```
① 版本化
   技能/身份卡都带 version + changelog
   changelog 记：什么时候、因为什么、改了什么、回测结果

② 对比验证
   每次进化后，观察 3 次任务
   如果一次通过率下降 > 15% → 触发警报

③ 自动回滚 + 停止
   连续 2 次进化导致指标下降
   → 自动回滚到上一个版本
   → 冻结该场景的 L2/L3 进化
   → 写进待办，等人处理
```

**五步落地（自进化机制的检查）：**

| 步 | 内容 |
|---|---|
① 违规长什么样 | ① 技能进化后没有 changelog；② 进化后 3 次任务窗口内指标跌 >15% 但没回滚；③ L3 身份改动没有人工确认记录 |
② 判据唯一出处 | `进化台账.json` |
③ 会失败的检查 | `node 工具\进化哨兵.mjs` → 列出违规进化 + 建议回滚 → exit 1 |
④ 反例 | 造一条"技能改了但无 changelog"的记录 → 必须报 |
⑤ 节奏 | 每次进化后立即跑；每周体检 |

### 3.7 为什么这套自进化不会失控

**四个约束：**

```
① 只有 L1 是自动的（只追加，不破坏）
② L2 必须回测通过（有历史案例把关）
③ L3 必须人工确认（最关键的改动）
④ 每一级都有版本 + 可回滚 + 自动冻结
```

**换句话说：进化是"有刹车的加速"。**

## 四、机制如何互相咬合

原项目说：**"少任何一套，另外两套都会退化。"**

```
身份系统  →  知道"我是谁"
              ↓ 才能
记忆系统  →  知道"我干到哪"
              ↓ 才能
协作系统  →  知道"该找谁"
              ↓ 才能
修改权    →  知道"我能碰什么"
              ↓ 才能
六件套    →  场景成立
              ↓ 才能
自进化    →  场景变好
```

**反过来验证：**
```
没有身份 → 记忆不知道该读哪份 → 串台
没有记忆 → 协作时不知道进度 → 重复干活
没有协作 → 修改权不知道边界在哪 → 越界
没有修改权 → 六件套的"不碰什么"无法执行
没有六件套 → 自进化没有可改的对象
```

A4 | **六件套校验** | 增强 `scene-validate.mjs` | 造一个缺定位卡的场景 → 必须报 |

### 阶段 B：立住权限与判定

| 序 | 机制 | 产出 | 验收 |
|---|---|---|---|

## 六、需要你确认的四个决策

### 决策 1：检查工具的组织方式

| 选项 | 说明 |
|---|---|
**A** 一个哨兵一个文件（身份哨兵 / 记忆哨兵 / 派单哨兵 / 越界哨兵 / 健康哨兵 / 进化哨兵） | 职责清晰，但要跑 6 次 |
**B** 一个总哨兵 `机制体检.mjs`，内部调 6 个检查 | 一次跑完，推荐 |

### 决策 2：越界检查的范围

| 选项 | 说明 |
|---|---|
**A** 只做事后审计（按 mtime + 归属表推断） | 可行，但不能阻止 |
**B** 做事前拦截（写文件时检查归属） | 需要改所有写文件工具，成本高 |

### 决策 3：自进化的 L2 回测由谁判定

| 选项 | 说明 |
|---|---|
**A** 静态检查（新技能里有没有对应步骤） | 快，但浅 |
**B** AI 用历史案例重跑一遍 | 准，但费 token |
**C** A + 人工抽查 | 折中，推荐 |

### 决策 4：健康度指标的采集精度

| 选项 | 说明 |
|---|---|
**A** 只记"接受/不接受" | 简单，但归因困难 |
**B** 记"接受/不接受/原因分类" | 归因清晰，推荐 |

## 七、一句话

> **机制 = 会失败的检查。不是文档，是能 exit 非 0 的东西。**
>
> **七层结构：宪法 / 共享 / 场景 / 进化 / 归档 / 运行时 / 验证。**
>
> **五套基础机制：身份（防串台）/ 记忆（防失忆+防肥胖）/
> 协作（防派单进黑洞）/ 修改权（防互相污染）/ 六件套（防场景泛滥）。**
>
> **自进化的核心：**
> **有信号（健康度三指标）→ 有归因（四问摘要）→ 有改进（三级进化）**
> **L1 记忆（自动）/ L2 技能（回测通过才写）/ L3 身份（人工确认）**
> **外加三条安全阀：版本化 / 对比验证 / 自动回滚冻结。**
>
> **进化是"有刹车的加速"。**
