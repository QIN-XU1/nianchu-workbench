# 08b · 二次开发可行性实测（回答"直接改这两个仓库是否更快"）

> 问题：**直接用 `dsh-superagent-prototype` 和 `luanyujia-workbench` 做二次开发，进度是不是会快些？**
> 方法：不猜，**在隔离环境里真的构建、链接、启动**，看卡在哪。
> 环境：`dsh` 0.2.2-rc.1，Windows，`DSH_HOME=verification/sea-home`。
> 结论先说：**两个仓库一个不能跑（平台不兼容），一个不是框架（是定制外壳）。但 superagent 的"源码级价值"极高。**

---

## 0. 一句话结论

| 仓库 | 能否作为二开底座 | 实测结论 |
|---|---|---|
**dsh-superagent-prototype** | ⚠️ **不能直接跑（Windows 致命），但可"移植"** | 构建只需改**1 行**；链接成功；进配置树成功；**运行时因 POSIX 路径假设崩在 `mkdir 'D:\D:\...'`** |
**luanyujia-workbench** | ❌ **不是框架，是成品外壳** | 43 个代码文件里，`main.js` 257 KB + `renderers.js` **1.1 MB**，全是 Electron 定制壳；无法迁移 |

**所以答案是**：
> **"直接二开"不会更快，但"源码级移植 superagent"会非常快**——因为它的**领域模型/授权/执行恢复是 JS 代码，可以直接抄结构**（实测证明它能编译、能进树、只差平台适配）。

### 0.1 【重要修正】superagent 的 core 层其实是**解耦**的，可移植性比预想高得多

这是本轮最有价值的一处发现，它**推翻了 `06` §1.1 里"S-1 单场景绑定"的严重程度判断**。

我用 grep 统计 `src/core/*.ts` 与 `src/sources/*.ts` 各自对 `github` / `feishu` 的提及次数：

| 目录 | 文件 | GitHub/Feishu 提及 |
|---|---|---|
| **`src/core/`** | `tickets.ts`（27 KB，Ticket 状态机） | **0** |
| | `stage.ts`（阶段机） | **0** |
| | `evals.ts`（21 KB，评估） | **0** |
| | `memory.ts`、`part.ts`、`ports.ts`、`reasons.ts`、`replies.ts` | **0** |
| | `engine.ts` | 4（**全是注释**："Normalize source timestamps (such as GitHub whole seconds)"） |
| | `model.ts` | 5（**注释**："Source-native attributes needed by channels or readers (for example a Feishu thread id)"） |
| | `assignments.ts` | 1（`RECOVERY_NOTE` 提到 worktree，是通用语义） |
| **`src/sources/`** | `github.ts` | **85** |
| | `feishu-loops.ts` | **47** |
| | `feishu-read.ts` | **48** |
| | `github-trigger.ts` | 28 |

**结论：**
> **`core/` 是与 Source 无关的纯领域层；所有 GitHub/飞书语义都在 `sources/` 里。**
> 这意味着：**移植 `core/` + 丢掉 `sources/` + 写自己的 Source，是一条干净的路。**
> "单场景绑定"不是在领域模型层，而是在 Source 实现层——**这正是可替换的层**。

**这条修正直接影响 `06` 的评分**：`S-1`（单场景绑定）从"必须替换实现"降级为"**只需替换 `sources/`**"。

### 1.2 第二步：版本差 —— `0.2.1-alpha.2` vs `0.2.2-rc.1`

`package.json` 的 `engines.dsh: ^0.2.1-alpha.2`，且 25 个 peerDeps 全钉 `^0.2.1-alpha.2`。

> **这是关键数据**：版本迁移的成本 = **一次 `pnpm install`（3 分钟）**，不是"重写"。

### 1.3 第三步：构建 —— ✅ 只改 1 行就成功

**改完立刻构建成功**：

**结论：从 `0.2.1-alpha.2` 迁到 `0.2.2-rc.1`，源码改动量 = 1 行。**

### 1.5 第五步：进配置树 —— ✅ 完整

`dsh --profile sea --dump-config`（exit 0，52,047 字节）里，superagent 的全部行都在：


### 1.6 第六步：真实启动 —— ❌ **Windows 致命**

启动两次，Web 服务都起来了（`http://127.0.0.1:35067`），但 superagent 本体**没激活**：

**第一次（没给 stateDir）**：
```
dsh: warning: 2 entries did not activate
dsh-superagent: ValidationError: invalid config:
  - $.stateDir missing required value
```

**第二次（给 `D:/...`）**：
```
- $.stateDir expect string to match regexp /^\//     ← 要求 POSIX 绝对路径
```

**第三次（给 `/D:/...` 绕过正则）**：
```
dsh-superagent: Error: ENOENT: no such file or directory,
  mkdir 'D:\D:\file\AI Temp\DeepSeek\Agent自研\verification\sa-state'
```

**根因**：它把 POSIX 风格路径与 Windows 盘符拼接，得到 `D:\D:\...` 这种非法路径。

**这不是配置问题，是平台假设问题**。`src/deployment.ts` 里明确：
```ts
const absolute = (description: string) =>
  s.string().pattern(/^\//).description(`${description} Absolute path.`)
```

## 2. superagent 在 Windows 上还差多少（诚实评估）

| 项 | 状态 | 修法 | 成本 |
|---|---|---|---|
`stateDir` 正则 `^\//` | ❌ 致命 | 改成同时接受 `C:\` 与 `/` | 1 行 |
`mkdir` 的路径拼接（POSIX 假设） | ❌ 致命 | 用 `path.resolve` 而非手工拼 | 2-3 处 |
worker 用 `sh` 跑 prepare 命令 | ❌ | 改 `pwsh` / `cmd`（它已有 `pwsh` 分支意识，见 `sessions.ts:61` 的 `WORK_TOOLS` 含 `pwsh`） | 中等 |
`git worktree` 创建检出 | ⚠️ | Windows 上可用，但路径/符号链接可能有问题 | 低 |
`gh` / `lark-cli` CLI 包装器 | ⚠️ | Windows 上是 `.cmd` 包装，`chmod +x` 行不通 | 低 |

**估算：要让 superagent 在 Windows 跑起来，需要改 6-10 处，约 1-2 人天。**
这比"从零写一个"便宜得多（后者是 3-6 个月）。

## 4. 回答你的问题：会不会更快？

### 4.1 分四种"二开"意图来判断

| 你的意图 | 用 superagent 二开 | 用 luanyujia 二开 | SEA 方案（当前路线） |
|---|---|---|---|
**A. 要一个能在 Windows 跑的 GitHub 编码 Agent** | ✅ **最快**（改 6-10 处，1-2 人天） | ❌ 无关 | ⚠️ 需自己实现 |
**B. 要多场景通用 Agent** | ⚠️ 它是单场景（GitHub/飞书） | ❌ 无框架代码 | ✅ **本方案** |
**C. 要"领域模型 + 授权 + 执行恢复"这套骨架** | ✅ **极快**（源码可直接移植，已实测能编译） | ❌ | ✅ 已在方案里继承 |
**D. 要"场景方法论 + 记忆约定 + 派单回执"** | ❌ 它没有 | ✅ **极快**（93 篇文档直接抄） | ✅ 已在方案里吸收 |

### 4.2 我的实际建议（基于实测）

> **最快路径 = "superagent 的源码骨架" + "luanyujia 的方法论文档" + "官方宿主"，三样拼起来。**
> 而不是"二开某一个"。

具体分工：

| 来源 | 拿什么 | 怎么拿 |
|---|---|---|
**superagent** | Ticket / Mandate / Eval / Assignment 的类型与状态机；授权三层；执行恢复（幂等/重启/槽位/顺序）；router/worker 两个 preset | **直接读 `src/core/*.ts` 与 `src/executor/dsh.ts`，按 v3 方案改写**（不要让它跑，抄它的设计） |
**luanyujia** | 场景六件套、《把规矩变成机制》、派单/回执宪法、记忆三层与红线 | **抄文档里的规则表**，变成我们自己的 check 脚本与 prompt 分节 |
**官方宿主** | 其余一切（session/tools/session-persistence/preset/extensions/guard/deliverables/feedback/team/goal） | 已实测可用 |

### 4.3 什么时候"直接二开 superagent"是对的

如果你的第一个场景就是**"一个 GitHub 仓库的编码协作"**，那就**直接二开它**：
1. 改 6-10 处 Windows 兼容（约 1-2 人天）
2. 写 `stateDir` 等 3 个配置项（已完成验证：`/D:/...` 会被拼成 `D:\D:\...`，需改代码）
3. 它自带 GitHub/飞书 Source、router/worker preset、完整恢复逻辑

**代价**：你被绑在"单场景 + PR 闭环"上。想加第二个场景时，会撞上它的 `Ticket.follows` / `pullsOf` 等 GitHub 耦合（`06` §1.1 S-1 已指出）。

### 4.4 什么时候不该二开

如果你要的是**"多场景 + 可进化"**，那么：
- superagent 是**单场景实现**，改造成多场景 = 重写它的 Source/Ticket 层（比新写更贵，因为它把 GitHub 语义渗进了领域层）
- luanyujia 没有可跑框架
- **只有官方宿主 + 我们自己的 40 行 select + DoneSpec 是干净起点**
