### 1.1 DSH Client 插件规范（源码级）

由子 agent 完成，产出 `_research/DSH-client-plugin-spec.md`（69 KB，1529 行，全部结论附原文+行号）。

**六项关键修正**（我之前都写错了）：

| 项 | 我之前以为 | 实测真相 |
|---|---|---|
`dsh.client` 字段 | 5 个 | **4 个**（platform/immediately/inject/external），唯一校验器在 `dsh-client-modules/lib/client.js:61-75` |
require 白名单 | 4 项 | **11 项**（多出 react-dom/client、cordis、zod、react-virtual、client-store、ui-slots、dockkit） |
primitives 需 external | 必须 | **不需要**（已在 seed 表，写了无害但冗余） |
`slots.inject` 语法 | 必须 generator | **两种都对**，语义不同：箭头函数=1 个 disposer；generator=多项合成事务；无 return=危险 |
`styles.insert` | builtin 但不可用 | **是 cordis-client-runner 动态包的闭包参数**，`factory(require)` 根本收不到 |
主题 token | 14 个 | **56 个**（`Theme.listTokens` inspect 超时导致我之前只看到部分） |
图标数 | 100 个 | **194 个 Icon\* + 8 PermissionIcon\*** |

**决定性证据**：`factory(require)` 只收到 `require` / `require.asset` / `require.async` 三个成员（`client.js:819` + `makeRequire`）。所以 `styles` 不在这个 lane 上，用它必然失败——这正是之前整包静默失活的根因。

### 1.2 星图可视化（用真实数据做像素级验证）

由子 agent 完成，产出 `research/star-map-lab/`（1121 行实现 + 3 张实拍截图 + 可复跑的自检脚本）。

**五个核心结论**：

**① 布局必须用分层，不能用力导向**

同一份数据实测对照：

| 布局 | 边长 min/中位/max | 交叉数 |
|---|---|---|
分层（选它） | 235/238/705 | **0** |
二维力导向 | 108/122/142 | 无法避免 |

力导向把 9 个节点收成边长 122px 的团，`调研→竞品→架构→实施` 这条主干全看不出。
**黄金角螺线更糟**——只保证不重叠，不保证位置有意义，换个排序就换位置，这是"看起来在乱动"的根源。

具体做法：
- x = Kahn 最长路径分层（4 列，间距 `clamp(usableW/maxLayer, 150, 235)`，**不要铺满**否则长边拉成 705px 横线）
- y = 一维力松弛（同列排斥 62px + flow 边吸引 + 向中线收拢，240 次迭代，线性退火必然收敛）
- 列内用**重心法**（Sugiyama 第 2 步），交叉数 3→0，交叉数是真数出来的

**② 边默认直线，只在需要绕行时加弧度**

一开始给所有长边加 `longBow=14`，结果每条边都轻微弯曲，整张图"抖"。
现在只有跨 ≥2 层且直线穿节点时才加弧度（本项目仅 1 条，弧度 22）。

箭头用 7×7 **开口 V 形** + `markerUnits="userSpaceOnUse"`（用默认 strokeWidth 会让箭头随线宽跳）。
**箭头堆积是真问题**：4 条边射向 hub 会叠成 `>>>`，按到达角沿圆周扇开解决。

**③ "丑"的三个真因（全部实拍抓到）**

- **常驻的 `ring` 是最大丑源**：每个节点套一个 `opacity:0.28` 的环，导致所有节点看起来一样大，把"按度数分大小"的信息全吃掉。改成默认 `opacity:0`、仅 hover/选中显示后，节点立刻大小分明。
- **颜色不要按类型分**：9 节点 × 4 种边 = 13 色相，图变调色盘。方案是**单色 + 线型编码**（实线/长虚线/点线/短虚线），节点只用 `brand-primary`，靠大小区分主次。
- **节点尺寸区间必须够宽**：`6+5*t`（1.8×）肉眼看不出差别，改 `5.5+8*t`（2.45×）后 1 度 9.5 / 4 度 13.5 才分得开。用 √ 归一化（面积对应度数）。

**④ 动画：只留两种**
260ms 淡入 + 120~160ms 属性过渡。砍掉：节点飞出/scale 弹入（scale 会让 stroke 变粗）、沿边流动粒子（会让"间接依赖"看起来也是数据流）、呼吸脉冲、悬停画布缩放、连线渐变（方案 82 已踩过"断断续续"）。

**⑤ 参考实现（可查证）**
- Obsidian Graph View：节点大小=被引用次数；Forces 暴露四参数；Text fade threshold 按缩放淡出文字。**可抄"参数可调"，不要抄 Time-lapse**（那是笔记增长叙事，场景图没这语义）。
- d3-force 官方文档：力只改速度不改位置；每 tick 顺序固定（alpha→force→velocityDecay→position），顺序错会抖。

**三个自己写出来又抓到的 bug（值得警惕）**：
1. `routes` 用对象身份做 Map key，但 `groupEdges` 会 spread 出副本 → 路由静默失效。改字符串 key。**这类静默失效最危险，因为不报错。**
2. `placeLabels` 的 `hitsEdge` 排除了与自身相连的边 → `reverse-eng` 的出边正好朝下，标签骑在线上。
3. `routes` 在 `placeLabels` 之后才算 → 标签按直线采样、边却画成曲线，窄容器下漏判。

修完：960/800/720/680 四种宽度**全部 0 处标签被边穿过**，11/11 边不穿节点，6 种尺寸无重叠无越界，空/单节点/环/自环全部不崩不 NaN，三次布局逐位相同。

### 1.3 布局容器约束（我自己实测出来的）

用注入式诊断条读到真实 DOM：

```json
{
  "rootW": 1002, "rootH": 782, "rootX": 280,
  "parentTag": "DIV.", "parentW": 0, "parentH": 0,
  "parentDisplay": "contents",   ← 关键！
  "parentPos": "static",
  "bodyScrollW": 1282, "winW": 1282, "dpr": 1.25
}
```

**父容器是 `display:contents`**（不产生盒子，子元素直接参与祖先布局）。
配合从 `dsh-client-ui-layout` 源码读到的：

```css
mainPanel { display:flex; flex-direction:column; flex:1; min-width:0; min-height:0 }
[data-global-panel] { padding-top: max(0, 48px - var(--dsh-frame-top-clearance)) }
```

结论：
- 根容器用 **纯 `flex:1 1 auto` + min-width/height:0**
- **不要同时设 `width:100%`**（在 flex 容器里两者打架，width 按父内容宽度算，容易溢出）
- 全子树 `box-sizing:border-box`（溢出最常见的原因）
- 概览卡用 **flex-wrap 而非 auto-fit grid**（grid 的 auto-fit 在测量有偏差时会溢出）

## 六、方法论收获

### 6.1 写 API 前先读真实源码，不要猜

这轮最有价值的三个发现，全部来自读源码而非猜测：
1. `factory(require)` 只收 3 个成员 → 解释了 `styles.insert` 为什么必然失败
2. `mainPanel` 是 flex 容器且外层 `display:contents` → 解释了宽度计算
3. `slots.inject` 的三种返回形态语义 → 解释了为什么 generator 和箭头函数都对

### 6.2 静默失效比报错更危险

三个例子：
- `styles.insert()` 让整包静默失活，不报错，只是什么都不出现
- `routes` 用对象身份做 Map key 失效，不报错，只是路由不生效
- `dsh.client.inject` 写错包名静默忽略

**对策**：隔离测试必须覆盖"该出现的有没有出现"，而不只是"有没有报错"。

### 6.3 像素级验证不可替代

子 agent 的做法值得学习：它不满足于"代码写完了"，而是：
- 用真实数据跑出 PNG
- 用脚本数交叉数（3→0 是真数出来的）
- 测四种宽度（960/800/720/680）
- 测六种尺寸
- 测边界情况（空/单节点/环/自环）

**"交叉数 0"这种可量化的断言，比"看起来不错"有价值一万倍。**

### 6.4 用户的批评都是对的

| 批评 | 我的问题 | 修正 |
|---|---|---|
「胡乱拼凑」 | 5 个 token 循环上色 | 单色 + 线型编码 |
「界面完全不对」 | 用了不存在的 token、力导向收成团 | 17 个真实 token、分层布局 |
「有三处写错了 API」 | 猜 API | 读源码 |
「记得做隔离测试」 | `apply({})` 假测试 | 65 项真实渲染测试 |
