## 二、原项目真正的价值（不是"场景"也不是"面板"）

### 2.1 核心结构：六层

```
L0 宪法    铁律（版本化，只有宿主能改）
L1 共享层  宿主画像/区域表/项目清单/通知待办/索引台账/体检
L2 场景私有 §〇交接/身份卡/画像/项目记忆/技能/归档
L3 个人层  个人档案（刻意不进共享层）
L4 运行时  引擎/外壳/工具/MCP/插件
L5 归档    备份/冷备/场景归档（只进不改）
```

**判据：每个东西只属于一层，只在一个地方是"真源"，其他地方只放指针。**

### 2.2 三套核心机制（跑三个月还乱不乱）

| 机制 | 一句话 | 不搞会怎样 |
|---|---|---|
**协作机制** | 谁说了算、谁改哪里、怎么交活、怎么算交付 | 互相踩、客套烧 token、活没人干 |
**记忆机制** | 会话会被换掉，记忆必须留在文件里 | 一换会话失忆；记忆越写越肥没人读 |
**场景体系** | 一个场景 = 一类会反复回来的活（六件套） | 上下文互挤、权限混乱 |

**"场景划分地盘，记忆记着干到哪，协作规定该谁做。少任何一套，另外两套都会退化。"**

### 2.3 我漏掉的三个机制

#### ① 派单机制（最贵的浪费）

```
公告（只落盘，不唤醒）
派单（必须真唤醒 + 四件套 + 回执带证据）
未回执（进台账，否则扔进黑洞）
```

**真实数据：一天发 36 条"通知"，只有 8 条真投递 = 22% 执行率。**

#### ② 修改权分五档

```
A 共享·宪法   只有规则负责人改
C 共享·工具   同上，别人只能提请求
B 共享·台账   各场景写自己那些行
D 自己专属    自己改
E 别人专属    ⛔ 一个字都不许写
```

**真实事故：两个场景互写记忆，一周后互相引用错误结论。**

#### ③ 场景即人的一面

```
同一个机主在不同场景是不同的人：
  OA运维：急、烦、事多
  个人站：松、随手、句子短
  复盘：  认真、愿意说细

五字段表：场景 / 常见语气 / 典型原话(带日期出处) / 雷区 / 应对
四条硬边界：只记表达不推原因 / 一个场景一个面 / 原话必须有出处 / 禁区
```

**"只做前半句（一类活），AI 就会用一套腔调应对所有事。"**

### 2.4 最关键的一句判据

出自 08-升级与改造清单《把规矩变成机制》：

> **"没有'会失败的检查'的规矩 = 一句口号。"**
>
> **注意"会失败"三个字**：如果一个检查永远通过，它就不是检查，是装饰。

**五步法：**
```
第1步 写清"违规长什么样"（可判定，不是形容词）
第2步 找到唯一判据出处（两处判据 = 早晚打架）
第3步 写一个能 exit 非 0 的检查（必须能说出差异集合）
第4步 给它一个"应当失败的反例"（90% 的人会漏，最易自欺）
第5步 挂到节奏上（手动跑的检查 = 没跑）
```

## 三、我们项目的实测对照

### 3.1 已有的（质量不低）

| 项 | 状态 | 实测 |
|---|---|---|
**L0 宪法** | ✅ 有 | `AGENTS.md` 1709 字节（原项目 15.8KB，我们更精简） |
**L1 共享层** | ✅ 有 | 9 个文件（待办/通知/索引/项目/记忆地图/体检/冲突/areas） |
**L2 场景记忆** | ✅ 11/11 | 实测大小 1085~1594 字节（**全部远低于 4KB 红线**） |
**L2 身份卡** | ✅ 11/11 | |
**L2 定位卡** | ⚠ 10/11 | 缺 1 |
**L2 会话绑定** | ⚠ 10/11 | 缺 1 |
**场景归档** | ✅ 8 个场景有 `归档/` | |
**工具链** | ✅ 完整 | 20 个 mjs 工具，共约 6000 行 |

### 3.2 缺失的（实测确认）

| # | 机制 | 实测结果 | 后果 |
|---|---|---|---|
① | **身份索引表** | `索引.md` 471 字，**不含 sessionId** | AI 无法认领身份 → 串台 |
② | **派单机制** | **无台账、无回执闭环** | 中枢派单 = 扔进黑洞 |
③ | **修改权分档** | 只有"不许越界"一句，**无五档明示** | 边界模糊，容易越界 |
④ | **记忆体量检查** | 有 7 个相关工具，但**无能 exit 非 0 的检查** | 红线靠自觉 |
⑤ | **场景判定判据** | scene-hatch 有创建功能，**无"该不该开"判定** | 场景会泛滥 |
⑥ | **场景即人的一面** | **完全没有** | 一套腔调应对所有场景 |
⑦ | **L5 备份层** | 无 `备份/` 目录 | 升级不可回滚 |
⑧ | **专属技能** | **1/11**（原项目 20+） | 用通用办法硬干专业活 |

### 3.3 最关键的三个差距

#### 差距 1：没有"会失败的检查"

**我们的 AGENTS.md 写了很好的规矩：**
```
§1 记忆在文件不在会话（§〇 ≤4KB）
§2 场景是地盘不许越界
§3 报错先查三件事
§4 自证必须是真证
```

**但：**
```
· §〇 ≤4KB 有检查工具吗？有 mem 系列工具，但没看到 exit 非 0 的红线检查
· 场景越界有检查吗？没有
· 身份认领有对照表吗？没有（索引.md 不含 sessionId）
```

**按原项目判据：这些全是"口号"，不是"机制"。**

#### 差距 2：场景之间没有协作机制

**我们有：**
```
· 11 个场景
· 每个有记忆文件
· 神经元显示关系
```

**但没有：**
```
· 派单怎么发、怎么确认（无台账）
· 未回执怎么办（无状态）
· 别人的地盘怎么请求（无格式）
```

**结果：中枢说"派给调研场景"，但调研场景怎么知道？怎么确认做完？全部无解。**

#### 差距 3：技能只有 1 个

```
原项目：20 余个技能（每个场景有专业流程）
我们：1 个
```

**"缺技能 → AI 用通用办法硬干专业活"。**

## 五、正确的建设顺序（我的建议）

### 阶段 1：把规矩变成机制（不是写文档，是写能 exit 非 0 的检查）

| 顺序 | 做什么 | 验收标准（会失败的检查） |
|---|---|---|
1 | **身份索引表** | 七列表；工具检查"哪个面板的 sessionId 不存在"→ exit 1 |
2 | **派单台账** | 检查"派出未回执 >24h"→ 列出清单 → exit 1 |
3 | **记忆体量哨兵** | §〇 >4KB 或主文件 >25KB → exit 1 |
4 | **场景越界检查** | 改动了非自己地盘的记忆 → 报告 |
5 | **场景判定判据** | scene-hatch 加 `--should` 判断，答不上来拒绝创建 |

**每一条都有"应当失败的反例"验证。**

### 阶段 2：补六件套

```
· 补 1 个定位卡
· 补 1 个会话绑定
· 补 10 个专属技能
· 加场景即人的一面（五字段表）
```

### 阶段 3：做场景工厂

**有了机制，它生成的才是"符合六件套的部门"，不是"一个 json"。**

### 阶段 4：再做真实场景

只做有真实后端能力的。

## 六、需要你确认

### 确认 1：优先级

**是否同意"先立机制（阶段1），再做场景"？**

理由：现在做场景 = 没有法律先建城市。

### 确认 2：机制的形式

| 选项 | 说明 |
|---|---|
**A** 只写文档 | 靠自觉，三个月退化 |
**B** 文档 + 能 exit 非 0 的检查 | 原项目做法，推荐 |
**C** 全做进工作台界面 | 最重，但最不容易忘 |

### 确认 3：场景即人的一面要不要

原项目说这能"减少来回：说对一次比说错三次再道歉便宜"。
但涉及记录用户表达习惯，需要你同意。
