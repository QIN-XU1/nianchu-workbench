# 16 · 信任链不能谎报 + 性能与基线分离（第六轮实测）

> 本轮修好了三个真实缺陷，其中一个是**安全性质**的：
> ① check 被改坏时，首屏仍说"没事要你做"（**谎报**）
> ② 首屏 5.7 秒太慢 → 缓存后 **287ms**
> ③ 改业务数据会误触发"不可信"（信任链与业务数据耦合）

---

## 1. 缺陷 ①：最严重的一个

### 1.1 现象

我把 `docs-index` 的 check 故意改坏（删掉一条检查），然后跑首屏：

```
sea · 现在没事要你做
  5 个场景全部通过 · 门禁自检 19/20 · 不变量下限 4/4 · check 认证 4/5
exit=0        ← 退出码 0，表示"一切正常"
```

**两行都自相矛盾**：`check 认证 4/5` 说明有一个没通过，但标题说"没事要你做"，退出码还是 0。

### 1.2 为什么这是最严重的

我做了三层信任链（门禁自检 / 不变量下限 / check 认证），**目的就是防止 check 被改坏**。
结果 check 真的被改坏时，三层都正确报了警，**但首屏最后一步没把它当回事**。

> 这等于：警报响了，但值班的人说"没事"。

### 1.3 修法

把"信任链是否完整"提升为**最高优先级的判定**：

```js
if (trustBroken.length > 0) {
  console.log('sea · 我的检查本身不可信');
  for (const b of trustBroken) console.log(`  ✗ ${b}`);
  return 2;   // 退出码 2 = 不可信，比"有活要干"(1) 更严重
}
```

**退出码语义**（现在是明确的三档）：

| 退出码 | 含义 |
|---|---|
`0` | 一切正常 |
`1` | 有活要干（但检查可信） |
`2` | **检查本身不可信**（结论不可用） |

### 1.4 实测

```
sea · 我的检查本身不可信
  ✗ 门禁自检 19/20 —— 它可能放过坏 check
  ✗ check 认证 4/5 —— 未通过：docs-index
  含义：下面的结论不可信，先修信任链
exit=2
```

**这是本轮最重要的修复。**

## 2. 缺陷 ③：改业务数据被误判为"不可信"

### 2.1 现象

修好缺陷①后，我改**业务数据**（从 roster 删掉 alice），结果：

```
sea · 我的检查本身不可信
  ✗ check 认证 4/5 —— 未通过：support-assign
```

**但这次 check 没被改坏，改的是数据。**

### 2.2 根因

demo 场景的 `data/` 同时充当了门禁的基线。
门禁 G1 要求"基线必须通过"——而 data 被改坏了，所以 G1 失败。

**这是信任链与业务数据的耦合错误**：业务数据变了，不该影响"检查本身是否可信"。

### 2.3 修法

给 4 个 demo 场景都补 `baseline/`（data/ 与 baseline/ 分离）：

```
scenes/support-assign/
├── data/         ← 业务数据（可以有问题）
└── baseline/     ← 干净基线（门禁用它证明 check 不是恒定失败）
```

### 2.4 实测

| 操作 | 修复前 | 修复后 |
|---|---|---|
改业务数据 | ❌ "检查不可信"（exit 2） | ✅ **"1 件事需要你 · 差 T-1->alice"**（exit 1） |
改 check | — | ✅ "检查不可信"（exit 2） |

**语义现在正确了**：数据问题 → 可执行的待办；检查问题 → 不可信。

## 3. 缺陷 ②：首屏 5.7 秒

### 3.1 性能画像（实测）

| 环节 | 耗时 |
|---|---|
5 个 check（串行） | ~200ms |
`gate-cli selfcheck` | **3856ms** ← 最大头 |
`invariant-floor` | 53ms |
`gate validate × 5` | 1336ms |
**合计** | **5455ms** |

### 3.2 修法：两级缓存

| 缓存 | 缓存什么 | 失效条件 |
|---|---|---|
`selfcheck-cache.mjs` | 门禁自检 / 不变量下限结果 | 门禁代码或场景文件 mtime 变化 |
`validation-cache.mjs` | 每个 check 的认证结果 | 该 check / scene.json / baseline / 门禁代码变化 |

**指纹机制**：文件 mtime+size 的 SHA256 → 任一变化即失效。

### 3.3 实测

| 状态 | 耗时 |
|---|---|
冷启动（重算） | 5,637ms |
**热启动** | **276–287ms** |

**20 倍提速**，且缓存不会撒谎 —— 已验证：

- 改 check → 缓存失效 → 重算 → 正确 REJECT（`U12` 覆盖）
- 改数据 → baseline 未变 → 认证仍 ACCEPT，业务判定变红（`U3` 覆盖）

### 3.4 顺手修的一个 bug

拆分缓存时发现 `gate.mjs` 的 CLI 靠比较 `import.meta.url` 与 `argv[1]` 判断是否直接运行，
在不同调用路径下会误判 → `node gate.mjs selfcheck` 只打印用法。

修法：**拆成 `gate.mjs`（只导出）+ `gate-cli.mjs`（只做 CLI）**，彻底消除歧义。

## 5. 这轮的技术债

| # | 债 | 影响 |
|---|---|---|
**F1** | 缓存是**进程内文件缓存**，多实例并发写可能冲突 | 单机单用无碍，但多开会有竞态 |
**F2** | 冷启动仍 5.6s | 首次打开慢；可后台预热 |
**F3** | `U1` 的 274ms 是**热启动**，冷启动不达标 | 需要区分"首值"定义 |
**F4** | baseline 需要人工维护 | 场景修改后忘记同步 baseline 会失真 |

**F4 最实际**：如果用 `sea` 管理真实项目，改了 check 的判定逻辑后必须同步更新 baseline，
否则可能出现"check 是对的但 baseline 过时"的误判。
