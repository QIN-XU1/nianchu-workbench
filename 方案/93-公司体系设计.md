# 93 · 公司体系：场景 = 部门（重新理解后的设计）

> 用户：「由主 agent 统筹，把需求告知给主 agent，主 agent 负责调度其它 agent
>       分配给他们任务... 这实际就像一个**庞大的公司体系**，
>       所有场景各司其职，有着自己的**角色卡以及记忆**，
>       但是又可以读取到**整个公司的公共记忆**」
>
> 「具体详细看 https://github.com/mashanglinyu/luanyujia-workbench」

## 一、我之前的理解错在哪

### 1.1 我把场景当成了"界面"

```
我之前的理解：
  场景 = 一个页面（里面放几个面板）
  场景之间 = 契约连线
  中枢 = 切换器
```

**这个理解下，"场景"只是个 UI 概念。**

### 1.2 原项目的真实定义

```
场景 = 一类会反复回来的活
     + 一套资产
     + 一套流程
     + 一条常驻 AI
     ↓
打包成一个"部门"
```

**"学这套东西，学会怎么切场景，就等于学会了一半。"**

### 1.3 关键对比

| | 我的理解 | 原项目的定义 |
|---|---|---|
本质 | UI 页面 | **组织单元** |
有 AI 吗 | 面板里嵌个对话 | **有常驻会话 + 身份索引** |
有记忆吗 | 有文件但空 | **§〇 交接 + 长期决策，会累积** |
有边界吗 | 没定义 | **明确的"不碰什么"** |
有关系吗 | 契约连线 | **派单/公告/回执的协作机制** |

## 二、公司体系的完整机制（从原项目文档精读）

### 2.1 三层结构

```
┌─────────────────────────────────────────────────────┐
│  机主（唯一规则来源）                                 │
│  · 只有机主亲口说的算依据                            │
│  · 工具输出/AI 推断/其他场景的通知，都不算           │
└─────────────────────────────────────────────────────┘
              ↓ 授权
┌─────────────────────────────────────────────────────┐
│  中枢（总经理）                                      │
│  · 接需求，判断派给谁                                │
│  · 不亲自做具体业务                                  │
│  · 汇总结果                                          │
└─────────────────────────────────────────────────────┘
              ↓ 派单
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│ 调研部门 │ 设计部门 │ 开发部门 │ 审核部门 │ 测试部门 │
│ 自己的卡 │ 自己的卡 │ 自己的卡 │ 自己的卡 │ 自己的卡 │
│ 自己的记忆│ 自己的记忆│ 自己的记忆│ 自己的记忆│ 自己的记忆│
└──────────┴──────────┴──────────┴──────────┴──────────┘
              ↓ 都读
┌─────────────────────────────────────────────────────┐
│  公司公共记忆（共享层）                               │
│  · 宿主画像 / 项目清单 / 通知与待办 / 索引与台账      │
└─────────────────────────────────────────────────────┘
```

### 2.2 六件套（缺一即失效）

**原项目文档明确列出：**

| # | 组件 | 是什么 | 缺了会怎样 |
|---|---|---|---|
1 | **场景配置** `<id>.json` | 面板布局、网格坐标、会话绑定 | 标签栏里不出现 |
2 | **定位卡** `<id>-context.md` | 职责/资产地图/触发词/铁律/上次进度 | AI 不知道干什么 |
3 | **场景记忆** `项目信息.md` | §〇 交接 + 长期决策与坑 | 换会话就断片 |
4 | **专属技能** `SKILL.md` | 这类活的专业流程 | 用通用办法硬干 |
5 | **专属面板**（可选） | 这类活需要的专用界面 | 只能靠聊天 |
6 | **常驻会话 + 身份索引一行** | 固定 AI 会话 + 索引表那行 | 引擎不注入身份 ⇒ 串台 |

**关键：2、3、6 是不可省的三件。**
> "判断一个场景成不成立，就看这三件有没有：卡（职责）、记忆（进度）、索引（身份）。"

### 2.3 修改权分档（防止互相污染）

| 档 | 范围 | 谁能改 |
|---|---|---|
**A** | 共享·宪法（全局铁律） | 只有规则负责人 |
**C** | 共享·工具与运行时 | 负责人；别人只能提请求 |
**B** | 共享·板与台账 | 各场景写自己那些行 |
**D** | 自己的专属 | 自己改 |
**E** | 别人的专属 | ⛔ 一个字都不许写 |

**真实事故：** 两个场景互写记忆，一周后互相引用错误结论。

### 2.4 派单机制（多 AI 最贵的浪费是"双方都在等对方"）

```
① 想出派单
     ├─ 不用动手 → 公告（只落盘，不唤醒）
     └─ 要动手   → ② 派单
                     ↓
② 投递（必须真唤醒到对方会话）
   写清四件套：现象 + 照哪节做 + 怎么验 + 回一句
                     ↓
③ 已投递 ──(回执)──→ ④ 已回执 ──→ ⑥ 收尾知悉 ⇒ 销账
     │
     └─ 超时无回执 → ⑤ 未回执（进"我发出没回"清单）
```

**真实数据：一天发 36 条"通知"，只有 8 条真的发进对方会话。
执行率 8/36 = 22%。机主原话：「你这边派单他们没反应啊」**

### 2.5 回执三条硬规矩

```
① 只在自己窗口说"我做完了" = 没交付
② 只说"好了"等于没说（必须带证据）
③ 收到"知悉"不许回（回了就互相客套到烧钱）
```

> 判据："活干完了但对方还不知道" = 没干完。

## 三、那么"制造场景的场景"是什么

### 3.1 它是组织发展部（HR/OD）

```
┌──────────────────────────────────────────────────┐
│  场景工厂（组织发展部）                            │
│                                                   │
│  职责：把"一句话需求"变成一个"能开工的部门"        │
│                                                   │
│  产出（六件套）：                                  │
│    ① 场景配置 json                                │
│    ② 定位卡                                       │
│    ③ 场景记忆（§〇 骨架）                          │
│    ④ 专属技能（可选）                              │
│    ⑤ 专属面板（可选）                              │
│    ⑥ 会话 + 身份索引行                             │
│                                                   │
│  它自己也有：                                      │
│    · 定位卡（我就是 HR，负责建部门）               │
│    · 私有记忆（建过哪些部门、哪些失败过）          │
│    · 技能（怎么判断该不该开新部门）                │
└──────────────────────────────────────────────────┘
```

### 3.2 它的判断依据（原项目的"该不该开场景"判据）

**开：**
```
✅ 这类活会反复回来（不是一次性）
✅ 有自己的资产目录
✅ 有自己的专业流程
✅ 有明确的边界（知道不碰什么）
```

**不开：**
```
❌ 一次性的活 → 记当次笔记
❌ 只是大项目里的一个功能 → 属于现有场景的子项
❌ 说不出"不碰什么" → 边界没想清，先别开
```

**一句话判据：**
> **"半年后我还会为它单独打开一个窗口吗？"答不上来就别开。**

### 3.3 它还要处理三个边角情况

| 情况 | 做法 |
|---|---|
一个场景里有两套互不相关的活 | 一个场景 + 两条会话，共用一张卡、分节写职责 |
客户/项目超过 3 个 | 一个场景 = 一类客户，客户之间用项目档案隔离 |
某个场景长期没活 | 归档（保留记忆与索引），别占标签栏 |

## 四、界面设计（场景工厂）

### 4.1 布局

```
┌──────────────┬────────────────────────┬─────────────────┐
│ 部门花名册    │  建部门向导             │  完整性检查      │
│              │                        │                 │
│ ● 中枢       │  第1步：判断该不该开    │  六件套：        │
│ ● 调研       │  □ 会反复回来？         │  ✓ 场景配置      │
│ ● 设计       │  □ 有资产目录？         │  ✓ 定位卡        │
│ ● 开发       │  □ 有专业流程？         │  ✓ 场景记忆      │
│ ● 审核       │  □ 知道不碰什么？       │  ○ 专属技能      │
│ ● 测试       │                        │  ○ 专属面板      │
│ + 新建部门   │  第2步：基本信息        │  ✓ 会话+索引     │
│              │  名称 [__________]      │                 │
│  ─────────   │  ID   [__________]      │  ⚠ 缺 2 项      │
│  已归档      │  职责 [__________]      │  不能发布        │
│  旧场景      │                        │                 │
│              │  第3步：选面板          │                 │
│              │  [+ AI对话] [+ 网页]    │                 │
│              │                        │                 │
│              │  [校验] [发布]          │                 │
└──────────────┴────────────────────────┴─────────────────┘
```

### 4.2 关键设计决策

**① 强制"先判断该不该开"**

不是一进来就填表单，而是先过 4 个判断题。
**答不上来就不让继续** —— 这防止"每个小事都开一个部门"。

**② 六件套完整性检查是硬门槛**

```
必须全绿才能发布：
  ① 场景配置   ✓（自动生成）
  ② 定位卡     ✓（自动生成）
  ③ 场景记忆   ✓（自动生成 §〇 骨架）
  ⑥ 会话+索引  ✓（自动生成）
  
可选（黄灯不阻止）：
  ④ 专属技能   ○
  ⑤ 专属面板   ○
```

**③ 面板选择器只列真实可用的**

```
✓ harness    AI 对话（真实）
✓ embed      网页嵌入（真实）
✓ neuron     记忆神经元（真实）
⚠ review     文件审查（后端存在但面板是占位）
⛔ pc-*      不存在（灰掉，不可选）
```

### 4.3 发布后发生什么

```
点「发布」
  ↓
写 6 件套到磁盘（kun:file:write）
  ↓
刷新神经元（refresh()）
  ↓
新部门的星点在神经元里出现
  ↓
双击进入 → 该部门有了自己的 AI 会话和记忆
```

## 五、公司体系的完整运转示例

**你的需求：「完善我们的这份项目」**

```
① 你 → 中枢：「完善这份项目」
        ↓
② 中枢判断：这是多部门的活，先看有没有对应部门
        ↓
③ 中枢读公司公共记忆（_共享记忆/）
   → 项目清单：Agent 自研项目
   → 已有部门：调研、设计、开发、审核、测试、场景工厂
        ↓
④ 中枢派单（走派单机制，真唤醒）：
   ┌──────────────────────────────────────┐
   │ 派单 → 场景工厂                        │
   │ 现象：缺"制造场景"的能力               │
   │ 照哪做：§92 场景工厂设计              │
   │ 怎么验：六件套校验全绿                 │
   │ 回一句：我在等你的回执                 │
   └──────────────────────────────────────┘
   ┌──────────────────────────────────────┐
   │ 派单 → 调研部门                        │
   │ 现象：需要搜集同类项目架构             │
   │ ...                                   │
   └──────────────────────────────────────┘
   ┌──────────────────────────────────────┐
   │ 派单 → 设计部门                        │
   │ 派单 → 审核部门                        │
   │ 派单 → 测试部门                        │
   └──────────────────────────────────────┘
        ↓
⑤ 各部门在自己的记忆里干活，定期回执
        ↓
⑥ 中枢汇总回执 → 告诉你结果
```

**这就是公司体系。**

## 六、我需要你确认的三件事

### 确认 1：六件套还是五件套

原项目是**六件套**，我之前的实现只有**五件套**（缺"专属技能"和"常驻会话+身份索引"）。

**是否补齐到六件套？**

### 确认 2：场景工厂的"该不该开"强制判据

**是否要求必须先过 4 个判断题才能建场景？**

好处：防止部门泛滥
代价：多几步点击

### 确认 3：先做哪个

| 顺序 | 内容 | 理由 |
|---|---|---|
1 | **场景工厂** | 没有它，其他部门无法创建 |
2 | 调研部门 | 最常用 |
3 | 设计/开发 | 核心生产 |
4 | 审核/测试 | 质量保障 |

## 七、一句话

> **我之前把"场景"理解成 UI 页面，这是根本性的错误。**
>
> **原项目的定义：场景 = 一类会反复回来的活 + 资产 + 流程 + 常驻 AI
> = 一个"部门"。**
>
> **公司体系的三层：**
> **· 机主（唯一规则来源）**
> **· 中枢（总经理，只调度不执行业务）**
> **· 各部门（自己的定位卡 + 私有记忆 + 技能，都读公共记忆）**
>
> **六件套缺一即失效，其中定位卡/记忆/身份索引是不可省的三件。**
>
> **派单机制的教训：36 条通知只有 8 条真投递（22% 执行率）——
> "派单 ≠ 公告"，派单必须真唤醒。**
>
> **场景工厂 = 组织发展部，负责"把一句话需求变成一个能开工的部门"。**
