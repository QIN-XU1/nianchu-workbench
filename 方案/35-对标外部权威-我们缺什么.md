## 一、外部权威的明确结论（一手引用）

### 1.1 Electron 官方：不要用 `<webview>`

来源：[Electron 官方文档 `<webview>` Tag](https://www.electronjs.org/docs/latest/api/webview-tag)

> **Warning** — Electron's `webview` tag is based on Chromium's `webview`, which is **undergoing dramatic architectural changes**. This impacts the **stability** of webviews, including rendering, navigation, and event routing.
> **We currently recommend to not use the `webview` tag** and to consider alternatives, like `iframe`, a `WebContentsView`, or an architecture that avoids embedded content altogether.

**这个项目有 6 个 webview。** 官方明确说：不稳定、不推荐。

**这不是"优化建议"，是"架构风险"。**

### 1.2 Chromium 进程模型原理

每个 webview = 独立的 renderer 进程（除非同源同 site instance 复用）。
这解释了实测数据：

```
warmCount=4 → 11 个 renderer 进程，992MB
warmCount=0 →  6 个 renderer 进程，381MB
```

**每个进程约 60-90MB 起步**，这是 Chromium 的固有成本，不是本项目的问题。

### 1.3 VS Code 的方法论（Electron 标杆）

来源：[VS Code Performance Issues](https://github.com/microsoft/vscode/wiki/Performance-Issues)

VS Code 处理性能问题的标准流程：

| 步骤 | 具体做法 | 我们有没有 |
|---|---|---|
**① Process Explorer** | `Help > Open Process Explorer` 实时看所有进程 | ❌ 没有 |
**② CPU Profile** | DevTools Performance 录制，导出 `.cpuprofile` | ❌ 没做 |
**③ `code --status`** | 命令行取进程快照 | ⚠ 我用 PowerShell 近似做了 |
**④ Extension Bisect** | 二分法禁用扩展，定位元凶 | ❌ 没做 |
**⑤ 启动计时** | Startup Timers 分析 | ❌ 没做 |

**最有价值的借鉴**：**④ 二分法**。
我们有 6 个 webview、13 个进程，用二分法能精确找出哪个最吃资源，而不是靠猜。

### 1.4 Electron 官方性能文档的核心建议

来源：[Electron Performance](https://www.electronjs.org/docs/latest/tutorial/performance)

摘录的关键原则：

> - **"Do not block the main process"** — 主进程和 UI 线程是控制塔，阻塞它整个应用冻结
> - **"Loading code is expensive"** — 模块加载有成本，避免启动时加载不需要的
> - 建议用 CPU profile / heap profile 验证模块加载成本

### 2.2 缺的（按价值排序）

#### **P0 · 架构风险：6 个 `<webview>` 官方不推荐**

**这是一个"没人提醒、但官方明确说危险"的问题。**

Electron 官方原文说 webview 的"渲染、导航、事件路由"都不稳定。
我们的项目：
- 6 个 webview
- 全部用于核心功能（引擎界面 + 4 个 AI 站）
- 且已经观测到过异常（A/B 时注入坏地址，webview 回了 `did-finish-load` 而不是 `did-fail-load` —— **这正是官方说的"事件路由不稳定"**）

**这不是理论风险，我们已实测撞到过。**

改法（官方给的三条路）：
| 方案 | 说明 | 代价 |
|---|---|---|
`WebContentsView` | 主进程管理，把 webContents 贴到指定区域 | 需要重写面板挂载逻辑 |
`iframe` | 简单，但跨域受限、无法隔离进程 | AI 站会因 X-Frame-Options 打不开 |
规避内嵌 | 不嵌网页，改成"外链打开" | 失去"内置"体验 |

**我的判断**：`WebContentsView` 是唯一能保留"内置"体验又符合官方建议的路。
项目里已有先例 —— `scripts/sidebar.js` 就是用 `WebContentsView` 贴到窗口。

#### **P0 · 缺"二分定位"能力**

VS Code 的标准做法。我们有 6 个 webview，但不知道**哪一个**最耗资源。

改法：加一个模式，逐个禁用 webview → 量内存差 → 给出排行。

#### **P1 · 缺 CPU profile**

现在只知道"GPU 进程 CPU 累计 69 秒"，不知道为什么。
DevTools 的 Performance 面板能录火焰图。

#### **P1 · 缺启动耗时归因**

325ms 是什么组成的？没有拆过。

#### **P2 · 缺"用完即销毁"的 webview 生命周期**

现在预热后常驻，即使你不用它。
理想：点开才建，闲置 N 分钟销毁。
原代码有 `noWarm`，但没有"闲置销毁"。

## 四、诚实的边界

1. **`webview → WebContentsView` 是大工程**，不是本轮能完成的。本轮只做**代价评估**，不动实现。
2. **CPU profile 需要 DevTools 手动操作**，我只能用 CDP 的 `Profiler` 域抓数据，没有图形化火焰图。
3. **所有外部文档都按"建议"处理，不是"必须"** —— Electron 说 webview 不推荐，但它已在此项目跑了很久，没有立刻炸。
