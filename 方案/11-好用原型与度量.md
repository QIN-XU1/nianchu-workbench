# 11 · "好用"的可执行原型（sea v0）

> 这一篇不是设计，是**能跑的东西 + 能反对它的数字**。
> 位置：`prototype/`，入口 `node prototype/sea.mjs`。
> 目的：把方案 10 篇的 U1–U7 从形容词变成**可测量的指标**，并证明它成立。

---

## 1. 它长什么样（三个真实输出）

### 1.1 健康时（无参数，零配置）

```
sea · 现在没事要你做
  3 个场景全部通过 · 我的检查本身：反例 6/6 被拦下
```

**两行。** 没有"正在初始化"、没有"已连接 12 个服务"、没有进度条。

### 1.2 有问题时

```
sea · 1 件事需要你
  FAIL 客服分派         每单有 owner、owner 在值班表、无重复单
       差 未分派 1(T-2)
  细节：sea check <场景> · 自检：sea verify
  没有撤销点：这次我只读、没改动任何东西。
```

**第二行就说了差什么（`T-2`），第四行说清了"为什么不能退"。**

### 1.3 单场景深看

```
PASS  数据核对
      差异集合 = 0
      验证：check exit 0（机器结论，不是我的判断）
```

**第三行是关键**：它明确区分"机器结论"与"我的判断"。

## 4. 一个产品级细节：没有撤销点时必须说清原因

原设计的失败提示是：

```
撤销点：无（这次只是读，没改动任何东西）
```

我改成了两行：

```
没有撤销点：这次我只读、没改动任何东西。
如果问题不是它造成的，请人工修正后重跑 sea。
```

**为什么改**：用户看到错误时，最想知道的是"**这能不能退回去**"。
"撤销点：无" 会被读成"它坏了"，而真相是"**它没碰你的东西**"。这两者的信任天差地别。

> 这正是"现象级好用"与"功能实现"的差别：**同样的信息，说给用户的方式决定信任。**
