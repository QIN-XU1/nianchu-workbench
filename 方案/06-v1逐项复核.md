# 06 · v1 方案逐项复核（对着官方宿主）

> 目的：**主动给自己挑错**。拿 v1 的每一个"新增概念/新增部件"，对照官方仓库判断：
> 是需要、是重复造轮、是撞已有的、还是根本不该做。
> 结论分四档：**保留 / 改造 / 删除 / 降级**。
> 依据全部来自 `deepseek-ai/deepseek-harness`（master @ 2026-11-04）。

## 0.1 【实测补充】"官方有" ≠ "能直接用"

`09-实机验证记录.md` 用真实 `dsh` 跑出了三条 v2 未考虑的事实。它们把"复用清单"的可靠性打了个折扣：

| 事实 | 证据 | 对复核的影响 |
|---|---|---|
**`webhookRuntime` 是 experimental 且 web profile 默认不含** | `packages/experimental/webhook`；`--dump-config` 0 命中 | #G1/#13 的"复用官方 webhook"→ 需自己装 bundle，且承担"可能被撤走"的风险 |
**`agent-team` 需 experimental bundle** | `@deepseek-ai/dsh-experimental-agent-team-profile` | #5 "复用官方任务板"→ 成立但要写安装步骤 |
**preset 的插件是惰性解析，`dump` 与启动都不校验包** | 源码 `plugins: z.array(z.any())` + `EntryGroup.key` | 所有"官方有 X"的核对方法**升级为：必须让会话真的选中它并跑一轮** |
**顶层坏包只 warning 不 fatal** | `warning: 1 entry did not activate` + 完整 err + 会话照常跑完 | **推翻**我引用的 `AGENTS.md`「Misconfiguration fails loud」在 patch 场景下的适用性 |

**结论**：v2 的"复用官方"清单里，每一条都必须重新标注三个属性：
`group`（product/experimental）· `shipped_in_web`（默认装否）· `maturity`（有产品承诺否）。
已在 `02b` 的复用表中加入这三列。

## 1. 逐项复核详述（只展开最关键的 10 项）

### 1.1 【降级】#1 三层编排

**v1 断言**：多场景必须三层（Router → Scene → Worker），否则 Router 上下文污染。

**官方事实**：
- `subagent/`："Subagent capability family: provider-registry contract and model-facing delegation tools"；`subagents` service 有 `startActivation`（两种重载）、`sendMessage`（**"an idle target starts a turn, and an absent direct child cold-resumes from persistence"**）、`interrupt`、`listChildren`、`listDescendants`
- `docs/architecture.zh.md`：**"添加模型可见上下文 → 调用 `agent.inject()`；它会落到下一次获准的请求中"**
- `benchmarks/agent-continuation`：已在测"冷启动工具密集续跑 + 反复发现不活跃 fork 子代"，说明**续跑是已被优化的路径**

**结论**：`agent.inject()`（不唤醒、注入上下文）+ `subagent` continuable child（可冷恢复并开新 turn）**已经能实现两层编排**。
三层是否必要，**必须用官方已有基准实测**（见 §2）。

**改法**：
```
v2 默认：Router（常驻）→ Worker（subagent continuable child）
v2 可选：Router → Scene（当且仅当实测证明场景隔离带来的收益 > 多一层的成本）
判据：扩 benchmarks/agent-continuation，加"多场景 2 层 vs 3 层"对比，同预算
```

### 1.2 【待证伪】#2 SceneContract

**v1 断言**：新增场景 = 写 `scene.yaml`，零代码。

**官方事实**：
- `preset/`："Per-session agent composition from preset `cordis.yml` files"
- `docs/architecture.zh.md`：**"让某个会话拥有不同的能力集合 → 组装一个 agent preset；其中的服务行需要 `isolate` realm"**
- `bundle/`："Installable `dsh --profile` patch layers"
- profile：列出 bundle + 树外插件 + `cordis.patch.yml`

**结论**：**一个 preset 就能给"场景"一套独立能力集合**。`scene.yaml` 可能只是 preset 的薄包装。

**改法（证伪优先）**：
```
步骤 1：用纯 preset（零新概念）实现场景 A（如"数据核对"），跑一个真任务
步骤 2：若成功 → scene.yaml 只在"多场景 + 跨场景协作"时引入，且必须回答"比 preset 多了什么"
步骤 3：若失败 → 记录失败点（是 preset 表达不了？还是组织管理需要？）
验收：新增第二个场景时，改动的文件数必须 ≤1 个（preset 或 scene.yaml）
```

### 1.3 【保留】#3 DoneSpec

**这是唯一我认为必须新造的东西。** 理由：
- 官方 `deliverables`：`present` 工具**声明**交付文件；`workspace-changes` **记录**改了哪些文件 → 都是"记录交付物"，不是"判定完成"
- 官方 `plan/`：计划模式的退出审批 → 是"过程审批"，不是"完成判据"
- 官方 `goal/`：durable objective + `goal-round-driver` 自动续跑 → 是"目标存在性"，不是"目标达成判定"

**但必须先排除一种可能**：`verify-*` 类门禁 + `test:snapshot` **在编码场景下就是 DoneSpec**。
所以 DoneSpec 的价值主张必须精确为：
> **"把编码场景已有的 `check` 形态，推广到非编码场景，并强制它在开工前声明。"**

**验收**（可证伪）：
```
给 3 类非编码场景（客服分派 / 文档一致性 / 数据核对）各写一条 check
成功率 < 50% → DoneSpec 主张失败，退回"evidence + review"为主
```

### 1.4 【改造】#4–#7 领域内核（最重要的一处）

**v1**：自建 `Ticket / Assignment / Evidence / Attention` 的 SQLite 表（§12 数据模型）。

**官方事实（决定性）**：
> `docs/architecture.zh.md`：**"模型可见 ⟺ 已记录。每个模型请求都必须能从日志重建。新增模型可见输入需要会话事件。"**
> `AGENTS.md`（同名规则）："**Model-visible ⟺ logged**: anything that reaches a model request must be reconstructable from the session log; a new model-visible input requires a session event."
> 会话格式纪律："已提交的 generation 路径绝不重命名、替换或删除；迁移只能追加版本命名的后继"

**这意味着 v1 的数据模型设计是错的**：
- Ticket 的 stage 若会被模型看到（例如放在提示词里）→ **必须是 `SessionEventMap` 的扩展 + 投影**
- Mandate 若会进提示词 → 同上
- Attention Ledger 若只给运维看 → 可以独立存储（这不违反 I4）

**改法**：
```
模型可见的状态（Ticket stage / Mandate 摘要 / DoneSpec 摘要）：
  → 扩展 SessionEventMap（新事件类型），注册纯消息投影（pure message projection）
  → 通过 session/projection 的 fold 折叠
  → 绝不另起一张"影子表"

仅运维可见（审计、注意力计数、进化的历史快照）：
  → storage/ 的非会话存储（官方有 storage hub + domain form）
```

并且必须遵守：**新增模型可见输入需要会话事件** → 我们每加一个"提示词分节"，都要问"它从哪个会话事件重建？"

### 1.5 【降级】#13 上下文七通道

**v1**：七条通道（宪法/身份/契约/工作集/环境感/状态台账/通知栏/召回）。

**官方事实**：
- `context/` 组："Model-visible request context: workspace instructions, time context, references" —— **这已经是三通道**
- `tool-fs-search` 有 `sampleOverCapGlobResults`；`spill` 有 `spill-policy`
- `systemPrompt`：`section` / `context` / `variable` / `tools` / `refreshContext` / `assemble`
- 事件 `system-prompt/assemble` 是 **waterfall**："Presentation waterfall over assembled sections, contexts, and variables"
- `AGENTS.md`："**Keep compiler faces explicit**"、以及 `docs/cookbook/adding-a-tool.md`

**结论**：七通道**不该是七个新机制，而是七个 `systemPrompt.section`/`context` 注册点**，并且**顺序稳定以命中 prompt cache**（v1 这条是对的）。

**改法**：
```
不新造 ContextAssembler；改为在 systemPrompt 上注册 7 个分节
每一节声明：来源（哪个会话事件/哪个 provider）、预算（字符数）、可省略性
用 'system-prompt/assemble' waterfall 做最终呈现变换（如按信道裁剪）
```

### 1.6 【改造】#17/#18/#19 存算分离 / 端侧 daemon / 凭据 Broker

**官方事实**：

| 需求 | 官方已有 | 我们应该做的 |
|---|---|---|
| **存算分离** | `SessionPersistence` seam（`create`/`open`/`stat`/`list`/`export`）+ "在新后端存储会话 → 基于共享句柄脚手架实现 SessionPersistence" | **只实现一个 provider**，不造新抽象 |
| **多机执行** | `ssh/`："POSIX remote connection with paired filesystem, subprocess and sandbox providers" | **复用**；不是另造 daemon 协议 |
| **沙箱** | `sandbox/`："Process-confinement seam; bwrap/Landlock/Seatbelt backends"；`sandbox-policy`、`fs-sandbox`、`bash-sandbox`、`pwsh-sandbox` | **复用**；`cmd_key` 白名单**是不必要的自造** |
| **凭据** | `credentials/`："Credential-reference and credential-record seam + env-over-.env provider + authorization flows that ask a human" | **复用**；只加"扫描消息流断言无凭据明文"的门禁 |

**结论**：v1 的"端侧 daemon + cmd_key 白名单"是**解决已经解决的问题**，并且引入了新的攻击面（自造协议）。
唯一该保留的是**目标**：凭据不进上下文。实现方式是**门禁 + 复用 credentials seam**。

### 1.7 【改造】#21–#23 自进化

**官方事实（这是 v2 最重要的一条）**：

`packages/extensions/README.md`：
> `cordis-host-runner`：**Host half: definition registry, sandboxed host-half lifecycle, and the inspect registry**；提供 `ctx.dynamicCordisRunner` 和 `ctx.cordisInspect`
> `cordis-client-runner`：**Browser half: evaluates a browser-half source into a live plugin**
> `tool-cordis`：**Two read-only tools for runtime API discovery**

`packages/extensions/README.md`（组总结）：
> "**Agent runtime self-modification**: live plugin/service inspection and model-written mount/unmount"

**这意味着：官方已经把"Agent 运行时自我修改"做成了一个 seam（带沙箱化生命周期）**。
v1 把"进化"当成"我发明的七步闭环"，而官方已有：
1. 能被模型写的插件挂载/卸载（`dynamicCordisRunner`）
2. 沙箱化 host-half 生命周期
3. 只读的运行时 API 发现（`cordisInspect`，我一直在用）

**改法**：
```
进化的"应用"环节  = 官方 dynamicCordisRunner（模型写插件 → 沙箱化加载 → 可卸载）
进化的"观察"环节  = 官方 feedback/（人类信号，明确不进模型）+ session-query/（lineage 与检索）
进化的"验证"环节  = 官方 test:snapshot（回放）+ benchmarks（预算）
进化的"回滚"环节  = 卸载 plugin（注册是 effect，卸载即撤销 —— 这是官方第一公民）
我们只加：提案格式 + 反例要求 + 配额 + 灰度策略
```

**注意一个强约束**（`AGENTS.md`）：
> **"Registrations are effects"**：every contribution goes through `ctx.effect()` / `ctx.on()`; a registry's `register()` returns the disposer.

**所以"可回滚"在官方架构里是**天然成立**的——这不是我要设计的，而是要**利用**的。

### 1.8 【改造】#22 封存集

**v1**：S3 封存集（Agent 不可见），每季度轮换。

**官方事实**：`docs/testing.md` 已给出分层：
- `test:snapshot`：**录制会话回放**（"a top-level scenario's highest recorded parent generation supplies user input and model replay, then serves as the expected persisted result"）
- `test:expected`：无 key 的装配期望
- `test:bench`：**"环境变量不得覆盖预算"**
- 以及 `snapshots/` 有 1968 个文件（session 1213 / web 390 / sdk 298 / acp 66）

**结论**：封存集不该是"我发明的一个数据集"，而应是**"一批不进入模型上下文、只在 CI 跑的 snapshot 场景"**。
差别是：v1 的封存集没法被机器执行；官方的 snapshot 可以。

**改法**：
```
封存集 = snapshots/ 下的专用目录（不进任何模型上下文）
轮换   = 修改 snapshot 的 parent 生成（官方已有 test:snapshot:record / :refresh）
判据   = CI 红/绿，而非"我算出一个分数"
```

### 1.9 【保留】#24 反例纪律 —— 但用官方更强的表述

**v1**：任何提案必须带"真实事件 id + 反例 + 回归集"。

**官方**（`docs/testing.md`）：
> **"A guard only guards if the regression fails it."** ……并**证明它**：引入回归 → 看它变红 → 回退。
> "`verify-*` 门禁：把机械可检的不变量接进一条会执行的门禁，并**证明每条改动过的验收路径都拒绝一个非法用例**。"

**结论**：v1 的主张是对的，但表述弱。v2 采用官方表述："**引入回归、看红、回退**"作为验收流程的**必须步骤**。

### 1.10 【删除】#8 Effects 队列 / 【删除】#9 Outbox

**官方替代**：

| v1 | 官方 | 说明 |
|---|---|---|
| Effects（持久副作用队列） | `schedule/`（"Host-owned scheduled follow-ups"）+ `jobs/`（"Generic background-job runtime and model-facing job control tools"） | 官方已有后台作业与定时 |
| Outbox（跨 Channel 保序） | 各 Channel provider + `session/event` 顺序 | 顺序保证应由信道实现负责，不在内核再造 |

**结论**：删。但要保留一个目标：**"先存后做"**（at-least-once）。检查官方是否已有：`docs/architecture.zh.md` 说 "**Registrations are effects**"、"Session event 是 post-commit"、"Effects 的 `enqueue` 在事务内、执行在 commit 后"（这是 Super-agent 的描述）。
→ **需在 P0 核实官方 jobs/schedule 是否已保证 at-least-once**。这是 v2 的一个开放问题。

## 2. v2 的验收必须接官方门禁（可证伪表）

| 我们的主张 | 用哪条官方门禁证伪 | 失败则 |
|---|---|---|
| 三层编排值得 | 扩 `benchmarks/agent-continuation`：2 层 vs 3 层，同预算 | 退回两层 |
| SceneContract 必要 | 纯 preset 实现场景 A，测"新增第二场景改动文件数 ≤1" | 退回"preset 库 + 约定" |
| DoneSpec 让非编码可判定 | 3 类非编码场景各写一条 `check`，成功率高/低 | 退回 evidence+review |
| Ticket 状态模型正确 | `test:snapshot`：新事件类型 + 投影能回放 | 改事件设计 |
| "模型可见 ⟺ 已记录" 不违反 | 任何新增提示词分节，若无可重建来源，`test:snapshot` 会红 | 撤销该分节 |
| 凭据不进上下文 | `test:e2e` 扫描完整消息流断言无凭据明文 | 直接判失败 |
| 自进化可回滚 | 卸载 plugin 后 `test` 的 HMR 安全测试必须绿 | 说明注册不可逆 |
| 自报心跳省 token | `test:bench` 对比 自报 vs 固定轮询 | 撤销该机制 |
