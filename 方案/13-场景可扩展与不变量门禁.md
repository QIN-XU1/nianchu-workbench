# 13 · 场景可扩展 + 不变量驱动门禁（第三轮实测）

> 本轮解决了两个"可用性"的真正阻塞：
> ① **场景硬编码** → 改成"放文件即新增"
> ② **门禁误杀正确 check** → 改成"场景声明不变量，门禁据此生成变异"

---

## 1. 问题 1：场景硬编码

### 1.1 之前

```js
const SCENES = [
  { id: 'data-reconcile', ... },
  { id: 'doc-consistency', ... },
  { id: 'support-assign', ... },
];
```

新增场景要改代码 → **不是通用工具，是演示**。

### 1.2 现在：放文件即新增

```
scenes/<id>/
├── scene.json   { id, name, desc, check, protects }
├── check.mjs    exit 0=通过；非0=失败且输出差异集合
└── data/        该场景的数据
```

**`protects` 是场景声明的「它保护哪些不变量」** —— 这是门禁生成变异的依据。

### 1.3 实测：新增第 4 个场景，零代码改动

我只写了 3 个文件（`scene.json` / `check.mjs` / `data/*.json`），然后：

| 验证 | 结果 |
|---|---|
自动发现 | ✅ `inventory-ledger` 出现在场景列表 |
首屏自动包含 | ✅ 且**立刻抓到一个真实错误**：`SKU-3:账面 75 ≠ 仓库 78` |
门禁认证 | ✅ 最终 ACCEPT（6/6 变异全捕获） |

**"零代码改动"被写成 U9 指标，实测通过。**

## 2. 问题 2：门禁误杀正确 check

### 2.1 走过的弯路（三代设计）

| 版本 | 做法 | 结果 |
|---|---|---|
**v1** | 硬编码变异计划（我手写给每个场景） | 12/12 通过，但**每加一个场景都要手写变异** → 不可持续 |
**v2** | 自动猜变异，分 strict / advisory | 10/12。**门禁猜错**：把"删一张工单"当 strict，但业务上确实没问题 |
**v3（当前）** | **场景声明不变量，门禁只生成违反已声明不变量的变异** | **16/16，4 场景** |

### 2.2 v2 的根本错误

门禁**不知道业务语义**，却试图判断"这个改动算不算错"。
例子：从 `support-assign` 删一张工单 —— 业务上完全没问题（少一张单不是错误）。但门禁把它标成 strict，于是正确 check 被误判为"漏报"。

**v3 的解法**：把判断权交回场景自己声明。

```json
// scene.json
{ "id": "support-assign", "protects": ["referential-integrity", "required-field", "uniqueness"] }
```

门禁只生成违反这几个不变量的变异，**且要求全部被捕获**。这样：
- 提案者无法挑选有利反例（变异由门禁按不变量生成）
- 也不会误杀（只测"你声明保护的东西"）

### 2.3 不变量目录（门禁认识 6 种）

| 不变量 | 含义 | 生成的变异 |
|---|---|---|
`completeness` | 集合成员必须完整 | 从某集合删一项 |
`uniqueness` | 集合内 id 不得重复 | 复制一项（同 id） |
`referential-integrity` | 引用必须能解析 | 悬空引用 / 删被引用目标 |
`required-field` | 必填字段不得为空 | 把必填字段清空 |
`term-presence` | 登记的词必须在正文出现 | 从正文删掉一个词 |
`no-unregistered-token` | 正文不得出现未登记缩写 | 追加一个外来缩写 |

**未声明不变量 = check 不可认证**（G0 门）。这是刻意的：**不声明保护什么的检查，不能被信任。**

## 3. 门禁又一次抓到了真 bug（这次两个）

### 3.1 第 4 个场景的对称性漏报

`inventory-ledger` 的 check 一开始只从 `items` 出发查（账面→仓库方向）。
门禁的 `completeness:drop-from-items.json` 变异（从账面删一条）**没被捕获**。

**真实缺陷**：如果仓库有而账面没有，check 完全不知道。

修法：补对称方向
```js
const whOnly = warehouse.filter(w => !items.some(i => i.id === w.sku)).map(w => w.sku);
if (whOnly.length) problems.push(`仓库多出记录 ${whOnly.length}(${whOnly.join(', ')})`);
```

### 3.2 `data-reconcile` 缺唯一性检查

`uniqueness:duplicate-id-sourceA.json` 没被捕获 —— check 只比较 A/B 之间，没查各自内部重复。
补上后 ACCEPT。

### 3.3 门禁自己的一个 bug

`no-unregistered-token` 变异把 `GATEALIENX`（10 个字母）追加进正文，而 check 的正则是 `\b[A-Z]{2,5}\b`（2–5 字母）→ 匹配不到 → 误判 check 漏报。
改成 `GXZ`（3 字母）后正确。

> **这条也说明门禁需要自己的"误报"检查。** 已在 `13` §5 记为待办。

## 5. 这轮暴露的、仍未解决的问题

| # | 问题 | 严重性 | 下一步 |
|---|---|---|---|
**P1** | **门禁自身没有"误报"检查** | 中 | 应该加：对一个**故意写坏的 check**（只报不该报的），门禁要能识别它"乱报" |
**P2** | **`protects` 由人声明**，Agent 可能声明一个很弱的不变量集（只声明最容易满足的） | **高** | 需要"最小不变量基线"：某些场景类型必须至少声明某几项 |
**P3** | **场景变多后，人工维护 `check.mjs` 仍是负担** | 中 | 这正是下一轮"Agent 自写 check"要解决的 |
**P4** | **U1 首值 4314ms**（4 场景就 4.3 秒） | 中 | 场景到 10 个会到 10 秒+，需要并行或缓存 |

**P2 是我认为最危险的一条**：如果 Agent 自己写 `scene.json`，它可能声明
`protects: []` 或只声明最容易的不变量，从而让门禁形同虚设。

**计划**：加一条"不变量下限"规则 —— 例如：
- 有两个数据集合的场景，必须至少声明 `completeness` 或 `referential-integrity` 之一
- 有 id 的场景，必须声明 `uniqueness`
- 有必填字段的场景，必须声明 `required-field`

并且**下限检查本身也要可测**（"声明过弱"必须被拒）。

---

## 6. 一句话

> **让门禁"不懂业务也不误杀"的唯一办法，是让场景自己声明它保护什么，然后门禁只测那些。**
> 这不是把判断权还给提案者（Agent 仍不能提供反例），而是把"语义"和"生成"分开：
> **场景声明语义，门禁生成反例。**
