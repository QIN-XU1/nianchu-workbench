## 一、engine token 阻塞：追查到真正根因

### 1.1 我原本以为

token 过期了，需要用户重新提供。

### 1.2 实际追查过程

**第一步：找到 token 的产生机制**
```js
// main.js
const token = harnessToken || process.env.DSH_ENGINE_TOKEN || '';
// → fetchEngineCookie()  token 换 cookie
// → engineRpcCall()       cookie 调 RPC
// → 失败时报 'no cookie (token 可能失效)'
```

**第二步：看 server.log 发现真因**
```
[err] 'C:\Users\15282\AppData\Roaming\npm\pnpm.cmd' 不是内部或外部命令
[server exited] code=1
[engine] start failed, consecutive=32
```

**关键：不是 token 过期，是引擎根本没启动。**

**第三步：找到 pnpm 路径硬编码**
```js
// main.js:113-114
const NPM_BIN = path.join(os.homedir(), 'AppData', 'Roaming', 'npm');
const PNPM_CMD = path.join(NPM_BIN, 'pnpm.cmd');   // ← 写死
```

实测：
```
C:\Users\15282\AppData\Roaming\npm\pnpm.cmd  → 不存在
D:\file\env\nodejs\pnpm.cmd                  → 实际位置
```

### 1.3 修复 1：pnpm 路径动态解析

```js
function resolvePnpmCmd() {
  const cands = [
    process.env.NODE_HOME ? ... : null,     // 环境变量
    path.join(path.dirname(process.execPath), 'pnpm.cmd'),  // node 旁边
    (用 where/which 反推),                    // PATH 里的
    path.join(HOME, 'AppData', 'Roaming', 'npm', 'pnpm.cmd'),  // 老路径
    'C:\\Program Files\\nodejs\\pnpm.cmd',
    'D:\\file\\env\\nodejs\\pnpm.cmd',
  ];
}
```

**修复后日志：** `[engine] pnpm 路径: D:\file\env\nodejs\pnpm.cmd` ✓

### 1.4 但修好 pnpm 后暴露下一层问题

```
[ERR_PNPM_NO_IMPORTER_MANIFEST_FOUND] 
No package.json was found in "引擎数据"
```

**引擎数据目录只有数据，没有引擎源码。**

诊断结果：
```
harnessDir:      workbench/引擎数据
hasDsh:          true       （数据目录存在）
hasCliBuilt:     false      （apps/cli/lib/bin.js 不存在）
hasPackageJson:  false      （pnpm 无法启动）
```

### 1.5 结论：架构事实，不是 bug

本项目设计为**复用外部引擎**：
- 引擎由 DeepSeek Harness 主程序拉起
- 通过 `DSH_ENGINE_TOKEN` 传入 token
- 代码里保留的"自己 spawn 引擎"路径在本项目环境走不通

### 1.6 修复 2：启动失败时给出可诊断提示

**修复前：**
```
[engine] start failed, consecutive=34
startServer failed — 保留窗口，等待用户重试
```
（重试 34 次，但不知道为什么）

**修复后：**
```
[engine] 诊断: {"harnessDir":"...","hasDsh":true,"hasCliBuilt":false,
                "hasPackageJson":false,"pnpmCmd":"D:\\file\\env\\nodejs\\pnpm.cmd",...}
[engine] 修复建议:
[engine]   · 本项目的「引擎数据」目录只有数据，没有引擎源码。
[engine]   · 应让 DeepSeek Harness 主程序拉起引擎，然后通过 DSH_ENGINE_TOKEN 传入。
```

### 1.7 本轮自己引入的一个 bug

我在加 pnpm 诊断 log 时，把 `log()` 调用放在了 `logTail` 初始化之前：
```
Cannot access 'logTail' before initialization
  at log (main.js:217)
  at Object.<anonymous> (main.js:168)
```

立即修复：把 log 调用延后到 `log()` 可用之后。

**教训：脚本顶层代码的执行顺序很重要，尤其是日志函数这种"到处都用"的。**

## 二、拆分 neuron.js

### 2.1 保守策略

**只抽零依赖纯函数，不动核心逻辑。**

| 部分 | 行数 | 是否拆 |
|---|---|---|
纯数学（rotate3d 等） | 30 行 | ✅ 拆 |
颜色工具（hexA/esc） | 26 行 | ✅ 拆 |
`render()` | **599 行** | ❌ 不动（风险太高） |
`layout()` | 204 行 | ❌ 不动（与 S 状态耦合） |
`loadData()` | 267 行 | ❌ 不动（与 api 耦合） |
interaction | ~300 行 | ❌ 不动（与 cv/S 耦合） |

### 2.2 结果

```
neuron.js:       2788 → 2736 行（-52）
neuron-math.js:  57 行（新建）
neuron-color.js: 35 行（新建）
```

### 2.3 最重要的收益：从"无法测试"变成"19 个单元测试"

**这些函数之前藏在 2788 行的闭包里，完全无法单测。**

现在可以脱离浏览器直接测：
```
✓ inverseRotate3d 正逆往返误差 = 2.22e-16（浮点极限精度）
✓ rotate3d 旋转保持模长
✓ rotate3d Y轴90°: (1,0,0) → (0,0,-1)
✓ project3d z=0 时 scale=1
✓ project3d z>0 时向中心收缩
✓ normalize3 零向量不崩溃
✓ hexA 支持 #RGB / #RRGGBB / rgb()（曾 NaN）
✓ esc 转义 <script> / 引号 / &
✓ 反例验证：rotate3d 确实做了旋转（不是空壳）
```

**19/19 全部通过。**

### 2.4 拆分踩到的坑

**坑 1：抽出的函数缺 export**
```js
function esc(s) { ... }   // 原文件同文件内用，不需要 export
```
导出到新文件后必须加 `export`。

**坑 2：hexA 前面有注释块，正则没匹配到**
需要手动加 export。

**坑 3：拆完后神经元加载失败**
```
The requested module './neuron-color.js' does not provide an export named 'esc'
```
修复后重启验证：`scenes: 8, edges: 19, flow: 12` —— 与拆分前完全一致。

## 五、这一轮的三个认识

### 认识 1：报错的表面原因往往是错的

```
表面：engine.rpc 报 "no cookie (token 可能失效)"
真相：引擎根本没启动（pnpm 路径写死）
```

**"token 可能失效"这个错误信息本身是误导。**
它的意思是"拿不到 cookie"，但没说为什么。
真正的排查必须往上追一层：为什么拿不到 cookie → 因为引擎没启动。

### 认识 2：拆分的价值不只是"行数变少"

```
拆分前：30 行数学函数藏在 2788 行闭包里 → 无法测试
拆分后：同样的函数 → 19 个单元测试 → 发现往返误差是 2.22e-16
```

**拆分的真正价值是"让代码可验证"。**

### 认识 3：中文路径 + PowerShell 是个坑窝

```
cmd 乱码 → PS 脚本 → 没 pwsh 7 → BOM 问题 → schtasks 参数解析失败
```

四个坑连着踩。**下次遇到类似问题，直接用 PowerShell cmdlet + UTF-8 BOM，跳过 cmd 和 schtasks。**
