## 1. DSH Super-agent

### 1.1 它的四特征（这是需求，不是方案）[原文]

微信文章开篇定义了 Super-agent 的四个基础特征，我认为这四个恰好就是本项目的验收标准：

| 特征 | 原文定义 | 对本项目的含义 |
|---|---|---|
| **连续** | 用户在 IM、GitHub 评论等熟悉界面交互，"感觉始终只存在一个 Agent"，不需要想"Session X 里有没有 Y 信息" | 我们对外的接口应当**没有 Session 概念** |
| **高效** | 响应迅速，并行且高质量完成多个复杂任务，不必等上一个完成就能接新指令 | 需要异步 ReAct + Worker 并发 |
| **主动** | 无需逐条下达指令，持续观察环境事件并主动推进，不需要介入时保持安静 | 事件驱动 + 两级过滤 + 静默策略 |
| **持久** | 始终在线，接入真实工作环境，长期运行中异常自愈 | 存算分离 + Watchdog |

**[推断] 关键洞察**：文章没有说"能力最强"，而是"注意力成本最低"。它的哲学文档把这一点写成了唯一判准：

> **Take as little human attention as possible, and give as much value as possible.**
> 每个消息、通知、问题、设置、面板元素、文档段落都在花别人的注意力，必须给出超过其成本的价值，否则删掉。
> — `research/repos/superagent/docs/000-philosophy.md:5-7`

这是我认为**最该抄的一条**，而且它是一条"减法判准"，能防止我们把架构做成瑞士军刀。

### 1.2 五模块：哪些是真架构，哪些是场景补丁

| 模块 | 原文内容 | 我的判断 |
|---|---|---|
| **2. 双层架构**（Router / Worker） | 常驻 Router Session 承接人类交互与分派，**不执行具体任务、甚至可以不配 Bash**；Worker 上下文隔离、挂全工具、**不与人类交互**，只向 Router 汇报 | **真架构**。这是全篇最硬的贡献：它把"连续 vs 吞吐"的矛盾从"提示词祈祷模型分工"变成**系统层强制分工**。文章给了消融实验：Super-agent p50=12.4min / p95=15.7min；单 Session+Subagent 中性提示 p95 达 29.5min，且 5 次运行**一次都没调用** Subagent。[原文 7.1] |
| **3. 事件驱动** | Trigger 概念；两级过滤（程序 Fast Path + 语义 Slow Path）；订阅与直通（已订阅 Thread 的事件直接发 Worker、不经 Router）；Inline & Spill + 链式召回；投机执行 | **真架构**，但**四件事成熟度不同**。两级过滤、订阅直通、Inline&Spill 是可落地的；链式召回依赖全局 ID 图，工程量被低估；投机执行是"高成本优化"，建议后置 |
| **4. 面向人的交互** | 全双工（start/stop 异步 ReAct，不等工具结束）；多信道输出规范（IM 单次 ≤100 词，GitHub 结构化交付） | **真架构 + 一条极实用的硬规则**。"IM ≤100 词"这条我建议直接抄成硬约束，因为它是唯一能用代码挡住的信道适配 |
| **5. 计算/状态/环境分离** | 5.1 计算与状态分离（Loop 上云无状态、Session 落库）；5.2 计算与执行环境分离（重状态环境留在原地，端侧只放**不保存会话状态的轻量 daemon**，即 BYOM） | **真架构**，而且是对"本地 Agent 一休眠就停"这个根本缺陷的唯一正解。与 Anthropic "脑手分离"同源 |
| **6. Watchdog** | 主系统**之外**的独立 Agent Session，定时消息驱动构成外部 Control Loop；不只监控进程存活，还**用模型判断 Worker 是否实质进展、是否偏离目标** | **真架构**，且是我认为整个方案里最容易被忽略、但对"长期在线"最关键的一块 |

### 1.3 领域模型：这是最值钱的资产 [代码]

`docs/001-domain.md` 用一张表把 **11 个概念**（Source / Trigger / Thread / Correlation / Channel / Policy / Eval / Mandate / Ticket / Assignment / Subscription）的**规则**（不只是字段）定义得极严密，其中 Source、Thread、Eval、Mandate、Subscription 被明确称为"核心域"。我认为这是我们最应该**整段继承**的东西：

```
Source ──Trigger──▶ Thread ──┬── (订阅扇出) ──▶ Ticket
                             └── (批量) ──────▶ Eval ──accept(带 Mandate)──▶ Ticket
                                                                              │
                                                              Assignment ──────▶ Executor
                                                              Channel ─────────▶ Source
```

关键规则（每条都值得抄）：

| 概念 | 规则 | 为什么重要 |
|---|---|---|
| **Source** | 持有读位置与**自己的 bot 身份**；定义"什么算一个事件"（含只在时间上成立的条件）；在进入领域前**丢掉 bot 自己的消息**与监听范围外的事件 | `A restart must not replay events`（`001-domain.md:27`）——**重启不回放**，这是"持久"的前提 |
| **Trigger** | 不可变；**"接受同一个 Trigger 两次只产生一个 Ticket"** | 幂等。分布式系统里最重要的性质 |
| **Thread** | 时间序的 Trigger；**同一时刻最多跑一个 Eval**；可挂多个 Ticket；持有订阅、运行中的 Eval 与决策历史 | 给 Eval 一个一致视图。这是"批处理"能成立的结构前提 |
| **Policy** | **版本化**的评估规则 + 每个 Source 的部分（谁可发起、名单如何同步、哪些 bot 可产候选） | 规则变更是**一等公民**，不是一个配置项 |
| **Eval** | **无状态**；输入 = Trigger 批次 + Thread 快照 + 该 Thread 上所有 Ticket（含已结束）+ 当前 Policy；输出 = Decision | 无状态才能重放、才能"策略变更后作废重跑" |
| **Mandate** | accept 授予的东西：Policy 版本、范围、强度、命中的规则、发送者身份；**不可变**；只有人 stop 才撤回，Policy 失效才撤销 | 把"为什么这件事可以做、能做多远"变成**数据**，而不是模型记忆里的印象 |
| **Ticket** | 只有 Eval 能创建；`open → ended`，人的消息可恢复（除非被人 stop）；**定义自己的状态，不跟随 Executor Session 状态** | 后半句是关键：执行会话会被换掉（崩溃、重启），工单不能跟着消失 |
| **Assignment** | Ticket ↔ 一个 Executor 实例的绑定；Ticket 一生可有多个；`pending → running → ended` **独立于 Ticket** | 把"谁在干"和"这件事"分开——重试/重启/换人都不改变工单 |
| **Subscription** | Ticket ↔ Thread 多对多，**由 Thread 持有**；匹配的 Trigger 扇出给**所有**存活订阅的 Ticket，**不检查谁发的**；纯上下文订阅**不授予任何权限** | 后半句是安全设计：**上下文 ≠ 授权** |

还有一张我认为必须抄的表——**Rejected concepts**（`001-domain.md:45-60`）。它记录了作者**明确拒绝**的概念和理由，例如：
- 拒绝"跨 Source 身份映射"（同一个人在不同 Source 上是 prompt 文本，不是实体）
- 拒绝"Eval 自己调度延迟 Trigger"（需要等待的条件就是一个 Source）
- 拒绝"一个 Thread 最多一个 Ticket"
- 拒绝"策略变更时取消运行中的 Ticket"（**"A cancelled change leaves half-finished work"**）
- 拒绝"从报告自由文本推断'在等人'"（**"The classification needs structured facts"**）

**[推断] 为什么这张表比概念表更值钱**：一个架构的质量，取决于它**拒绝**了多少东西以及拒绝的理由是否可辩护。我们做自己的架构时应当照做——把"我们决定不做的 X"和"为什么"写进文档，这比功能清单有用。

### 1.4 授权模型：全篇最被低估的部分 [代码]

`docs/002-authorization.md` 是我读过的最严密的中文/英文 Agent 授权设计。三层结构：

**第一层：gate（确定性准入，不调模型）**
- Source 记录这条消息**是否指向 Agent**：`mention` / `direct`
- 强度只有两档：`explicit`（明确请求）/ `inferred`（推断候选）
- 依据只有四类 `via`：`addressed`（名单内的人点名）/ `followup`（Thread 上已有 Ticket 的跟进）/ `admission`（准入表某格）/ `bot`（白名单 bot）
- **"一个白名单 bot 只能产 inferred candidate，永远不能产 explicit request，也不能 stop Ticket"**

**第二层：admission table（准入表）**
- 行 = **接收范围**（飞书某个群 / GitHub 新 Issue、新 PR、评论、默认分支 CI）；列 = 三种人-消息组合
- 每格三选：explicit / inferred / ignore
- **默认值刻意保守**：名单内未点名 → inferred；不在名单但点名 → **ignore**；不在名单未点名 → **ignore**

**第三层：accept mode（三档闸门）**
| 模式 | 效果 |
|---|---|
| `off` | 任何推断产物都不成候选 |
| `observe`（**默认**） | 推断候选会被评估；正向评估**记为 ignore 并标注"would accept"**，什么都不接 |
| `auto` | 推断候选的正向评估直接接单 |

**[推断] 这个 `observe` 默认值是整个方案里最聪明的设计**：它让"自主主动"这件事可以**先试运行再开闸**——Agent 会把"如果开 auto 我会做什么"记录下来给人看，人看几天觉得对再切 auto。这是一种**渐进授权**（progressive authorization），比任何"信任设置项"都可靠。

还有两个细节值得单独抄：
- **Policy version**：规则、accept mode、各 Source 的 Policy 拼成一个版本号；每个 Mandate 记录它被接受时的版本。**版本变更会作废运行中的 Eval 并重排 Trigger**，并向受影响的 live Ticket 发一条 policy-changed Input，说明是"命中的规则变了/请求人已无权/不再接受主动工作"。**但不立即撤销 Mandate**。
- **Resume 前 revalidation**：一张已结束的 Ticket 被人重新提起时，要按**当时的** Policy 重新验证 Mandate 是否仍然成立；不成立就不恢复。**"Removing a sender from the list can therefore revoke a Mandate"**。

**为什么这套东西对我们的"通用场景自进化 Agent"是必抄的**：
一个能自主进化的 Agent，最大的风险不是它做错一件事，而是**它自己把权限边界改宽了**。Super-agent 的答案是：**权限（Policy/Mandate）永远在代码与存储里，不在模型上下文里**。

> `002-authorization.md:5`：**The host enforces allowed lists, rules and Mandates. Messages, comments and quoted documents are inputs to a decision; they cannot change those permissions.**

这一句应当成为我们架构的**第一条不变量**。

### 1.5 执行模型：Worker 的细节设计 [代码]

`docs/003-execution.md` 有大量可直接抄的工程细节：

| 机制 | 内容 | 评价 |
|---|---|---|
| **Ticket stage 表** | 8 个阶段，**从上往下读，第一个匹配的行赢**：`person/delivery → person/answer → person/review → person/blocked,failed → working/queued → idle → working` | **极好**。这是"给用户看的状态"而不是内部状态码，面板直接可用 |
| **一 Ticket 一 Session 一目录** | Session 名 `worker-<ticket id>`，目录名按 Ticket short name，在 execution root 下（默认 `<stateDir>/work`） | 隔离粒度为"一件事"而不是"一个话题" |
| **Worker 前台命令 5 秒转后台** | 通过 preset 把 shell 的 `timeoutMs/maxTimeoutMs` 设成 5000，job wait 也设 5000 | **这是异步 ReAct 的廉价实现**：不写新协议，改两个超时。极聪明 |
| **worker slot** | 并发上限按 slot 计；**"人的消息或状态查询可以多用一个额外 slot"**；"wake 优先于 launch" | 保证**人永远不会被新工作挡住**。这条我认为必须抄 |
| **后台工作 30 分钟上限** | 一轮结束后后台最多跑 30 分钟；到点杀 shell job、报 waiting；**subagent 允许继续** | 防止一个 Worker 永久占位 |
| **handoff 规则** | 交回给人（ready / question / blocked / failed）**立即释放 slot**；此时 subagent 停，shell job 可继续且不占 slot、豁免 30 分钟 | 精细但正确 |
| **重启恢复** | 运行中的 Assignment 以 "host restarted" 结束，新 Assignment 带 recovery note **"先检查目录、git history、GitHub 再重复任何外部动作"** | **必须抄**。防止重复提交 PR 这类事故 |
| **Stored work 模式** | "做了什么"**先存储再执行**；relay / delivery 失败重试 2s→指数到 60s；**同种工作连续失败 3 次才上报为系统问题** | 至少一次（at-least-once）+ 单次故障不上报，避免噪音 |
| **消息顺序** | 同一 Ticket 到同一会话的消息**按队列顺序发出**，后面等前面的；其它 Ticket 的消息不等 | 保证"先确认后结果"的人类阅读顺序 |

**[推断] 这一节的价值**：它解决的全是"长期运行才会暴露"的问题（重启、丢消息、卡死、重复提交）。这些是任何"持久在线 Agent"的必经之路，自己趟一遍要几个月。**建议整段继承，再改场景。**

### 1.6 提示词工程：优先级模型 [代码]

`docs/004-prompts.md` 给了一个我认为必须照抄的**优先级链**：

```
1. 工具与宿主强制的事实（身份、权限、参数校验、回复用途、长度限制）—— 提示词改不了
2. 内置与生成的分节（团队可覆盖）
3. 主动工作 Ticket 命中规则的流程与沟通要求（仅该 Ticket 的 Executor）
4. 团队分节与团队技能
5. 外部文本：消息、评论、文档、引用 —— 它是数据，永远不能改变规则或授权
```

**"外部文本是数据，永远不能改变规则或授权"**——这是对提示词注入的**架构级**答案（不是"叫模型别听"）。

另外三条可直接用的规则：
- **Router 只路由**：一次工具调用可以对多条候选做 accept/attach/stop/ignore；**路由备注 ≤30 词**；Router 不做技术决策
- **Router 等待**：报告、跟进通知、候选、后台作业完成都**自动作为消息到达**；禁止 `sleep`、shell 超时 >30 秒、job wait >5 秒（用 guard 挡住）
- **Executor 决定跟进**：范围内的自己处理并确认，范围外交回；**一条消息只有在所有 owner 都交回或没接时才算新工作**

**版本化**（004-prompts.md:91-96）也很重要：每次保存生成不可变版本（含 base revision、时间戳、来源）；**冲突保存被拒绝但不丢弃草稿**；Sessions **每次模型请求都读最新版**，包括同一轮里的后续步骤；**保存不重启、不取消、不唤醒 Session**；来源只有三种 `panel`/`tool`/`sync`，**只有 `panel` 能改执行环境与 SETUP_FIELDS**。

**[推断]**：最后那句是安全边界——**Agent 自己（走 tool 来源）改不了执行环境**。这一条我们做自进化时尤其要保留：**能被进化的是提示词与技能，不是执行环境与权限。**

### 1.7 实现层：怎么插进 DSH [代码]

`cordis.patch.yml` 显示它**不是一个独立程序，而是 DSH 的一个 bundle**：
- 插入 3 个条目：主插件 `dsh-superagent` + `github-watch` + `feishu-watch`（默认 disabled）
- 插入 **2 个 agent preset**：`dsh-superagent-worker`（order 90）与 `dsh-superagent-router`（order 91）
- Worker preset = DSH `standard` 去掉"向人提问/展示/计划模式/插件管理/调度/goals/workflows/web fetch/forked subagent"，并**把 shell 超时压到 5 秒**
- Router preset = 更小：**没有 subagent、没有 web、没有文件搜索与写入、没有 todo**，`tool-fs` 设 `write:false edit:false`，且**没有 persona 分节**（因为 Router 的 prompt 是完整的）

**[推断] 这是本方案落地的关键情报**：在 DSH 上做"双层架构"，**不需要自己造运行时**，只需要一个 bundle + 两个 preset + 一个 Service 注入（`orchestrator`）。这是我能给出"C 方案"（见 02 文档第 0 节）成本评估的底气。

副作用也要记下：`006-deployment.md:19` 明说两个 preset **以 `danger-full-access` 和操作者 OS 用户身份运行**，"Account wrappers choose the agent's credentials by default; **they do not isolate the process**. A worker can execute programs by path and read the operator's home directory."——**这不是安全边界**，作者自己在 `003-execution.md:80` 也写了 "These wrappers and directories establish defaults, not a security boundary."

### 1.8 不可取 / 必须改造的部分

| # | 部分 | 问题 | 证据 | 我们的处理 |
|---|---|---|---|---|

## 2. 乱雨家工作台（luanyujia-workbench）

### 2.1 它到底解决了什么问题 [原文]

`总纲.md:12` 一句话：

> 同一台机器上常驻多个 AI 场景（相当于同事）：**共用一套规则与台账，各自有独立记忆；活按项目派给 owner，干完必须留证据和回执。**

`总纲.md:13` 给出了它的核心命题：

> **记忆在文件里，不在会话里** —— 所以会话可以无限换，场景不会失忆。

**[推断] 为什么这句话重要**：这直接回答了 Super-agent 的 open question 8.1（长程记忆）。Super-agent 的解法是"引用图 + 链式召回"（工程化，重）；乱雨家的解法是"**让模型每轮从文件重建状态**"（朴素，但极其可靠）。两者的差别是：

| | Super-agent 链式召回 | 乱雨家文件化记忆 |
|---|---|---|
| 机制 | 对象 ID 图 + 按需内联/溢出 | 固定结构的 Markdown + 每轮注入 + 覆盖写交接 |
| 上限 | 受 Router 上下文窗口约束 | 受"注入层必须极短"约束 |
| 可靠性 | 依赖 ID 不断链 | **不依赖任何图，重读即可** |
| 成本 | 图维护 + 工具往返 | 每轮固定 token（且很小） |
| 弱点 | 跨月失忆 | 需要人写交接；没有自动归纳 |

**结论：v1 应当用乱雨家的文件化记忆（便宜、可靠、够用），v2 再叠加语义检索。**

### 2.2 六层总纲：一个可以直接抄的存储分层 [原文]

`总纲.md:17-25`：

| 层 | 放什么 | 谁能写 |
|---|---|---|
| **L0 宪法** | 铁律与附则（**版本化；改一次 +1，旧版留档**） | 只有宿主 |
| **L1 共享层** | 宿主画像 / 场景区域表 / 项目清单 / 通知与待办 / 总索引与文档台账 / 体检快照 | **分区写，各 owner 只写自己的** |
| **L2 场景私有** | 场景私有记忆（§〇 交接）/ 身份卡 / 场景画像 / 项目记忆 / 专属技能 / 归档 | **只有本场景** |
| **L3 个人层** | 个人档案与知识库 | 只有本人与授权者，**不进共享层**（图里刻意不画线：隔离本身是规矩） |
| **L4 运行时** | 引擎 / 外壳 / 工具 / MCP / 插件 / 计划任务 | 专人维护；**工具放代码仓外，升级不破坏数据** |
| **L5 归档** | 备份 / 会话冷备 / 场景归档 / 历史文档 | **只进不改，可恢复** |

判据只有一句（`总纲.md:26`）：

> **每个东西只属于一层，只在一个地方是"真源"**；其他地方只放指针。

**[推断] 这六个层恰好可以一一映射到我们架构的存储子系统**（见 02 文档 §5）。尤其 L4 那句"**工具放在代码仓外，升级不破坏数据**"——这是"自进化"必须遵守的物理前提：**进化产物（技能/提示词/记忆）必须与运行时二进制分离**，否则一次升级就把学到的全丢了。

我认为应当**再加一层 L-1：不可变审计层**（只追加、不可改），因为我们要做自主进化，必须有"谁在什么时候改了什么"的不可否认记录。

### 2.3 场景 = 一类会反复回来的活 [原文]

`三-场景体系.md:4`：

> 它不是一个文件夹，也不是一个标签页 —— 它是**"一类活 + 一套资产 + 一套流程 + 一条常驻 AI"** 的打包。

**场景六件套**（`三-场景体系.md:55-62`）——这是全套材料里我最欣赏的一张表，因为它**每一件都写了"缺了会怎样"**：

| # | 组件 | 缺了会怎样 |
|---|---|---|
| 1 | 场景配置 `<id>.json`（面板布局、网格、会话绑定） | 标签栏里根本不出现这个场景 |
| 2 | 定位卡 `<id>-context.md`（职责/资产地图/触发词/铁律/上次进度） | AI 不知道自己该干什么、能碰什么 |
| 3 | 场景记忆（§〇 交接 + 长期决策与坑） | 换会话就断片 |
| 4 | 专属技能 `SKILL.md` | AI 用通用办法硬干专业活 |
| 5 | 专属面板（可选） | 只能靠聊天，效率低 |
| 6 | 常驻会话 + 身份索引一行 | **引擎不注入身份 ⇒ AI 会猜，一猜就串台** |

并且它明确给了"不可省的三件"：**② 卡（职责）、③ 记忆（进度）、⑥ 索引（身份）**。

**[推断] 这是本项目最重要的抽象**。用户要"适应所有场景"，而"场景"正是**场景化通用**的正确粒度：**不是做一个万能 Agent，而是做一个能长出无数个专职 Agent 的机制。** 这与 Grok Bot 的 "one bot, one job" 结论完全一致（两个独立来源互相验证，可信度高）。

但它的"身份"落地方式需要分开看，这是我在初读时判断过快、后来校正的地方：

| 层 | 实现 | 谁保证 |
|---|---|---|
| **面板 ↔ 会话的绑定**（哪块面板显示哪条会话） | **宿主注入 JS 到内嵌网页**：优先"写键直达"（把 `sessionId` 写进该面板独立分区的 `localStorage` 当前会话键 → reload），兜底"点行"（按标题在会话列表里点中那一行） | **代码强制**（`02-会话定位与跟随/二-会话绑定三字段.md:73-83`）。而且它做得很细：键里带**面板 id + 绑定签名**（配置一变旧记忆立刻失效，防"鬼绑定"）；脚本**幂等**（宿主会周期性重注入，重复装定时器会攒出几十个循环，表现为"每隔一会跳一下"） |
| **"我是哪个场景"的语义身份**（我该读哪份记忆、守哪些铁律） | **开场 30 秒认领**：读自己的会话 id → 查身份索引表 → 读定位卡 → 读 §〇（`三-场景体系.md:135-144`） | **依赖模型自觉执行** |

也就是说：**会话绑定的机械层它是认真的（用代码钉死），但"我是谁"的语义层仍靠模型自觉。**
它的 `六-记忆分三层.md:17` 还给了一条很有价值的**权威顺序**：`场景记忆 ＞ 定位卡 ＞ 技能叙述`，冲突时以前两者为准，"并顺手把技能改对"。

Grok Bot 的做法则是把语义身份变成**系统属性**（Bot 本身就是有名字、有 description 的实体）。

**我们的处理是"两样都要"**：
- 机械绑定层：可直接借鉴它的"写键直达 + 幂等脚本 + 带签名"三件套（如果做 Web 面板）
- 语义身份层：**必须系统注入**（Session 创建时绑定 scene id，prompt 自动带身份与权威顺序），不靠提示词提醒模型去查表

### 2.4 "把规矩变成机制"：这是全套材料里最高级的一条 [原文]

`08-升级与改造清单/把规矩变成机制.md` 的开头一针见血：

> 规矩写在文档里，靠的是自觉；机制跑在代码里，靠的是机器。
> 一份只有"规矩"的系统，三个月后一定退化成"看心情"。

**判据（`:11`）**：
> **没有"会失败的检查"的规矩 = 一句口号。**

它给了五步法（`:31-55`）：
1. 写清"违规长什么样"（**必须可判定，不能是形容词**）
2. 找到**唯一**的判据出处（一处判据 = 一份结论；两处判据早晚打架）
3. 写一个**能 exit 非 0** 的检查（输出要能说出**差异集合**，不是 0/1）
4. **给它一个"应当失败的反例"** ← 作者说"⛔ 这一步 90% 的人会漏，也是最容易自欺的地方"
5. 挂到节奏上（手动跑的检查等于没跑）

并且明确**三类不该机械化**（`:102-110`）：判断类、一次性、靠人拍板（"机制负责提醒，不负责决定"）。

**[推断] 这五步法应该直接成为我们"自进化"的设计纲领**，因为自进化最大的危险正是"越改越差而没人发现"。它给了三条铁律：
- **反例优先于正例**：任何"进化验收"必须先证明它**能失败**
- **差异集合优先于布尔值**：验收输出必须说清"差在哪些项"
- **判断类不进机制**：不是所有东西都该自动化

我甚至认为，**这一条是乱雨家比 Super-agent 更先进的地方**。Super-agent 的 `002-authorization` 里有"revalidation"这种机制，但它没有给出**通用的机制化方法论**。

### 2.5 协作机制：多 Agent 不会互相踩的规则 [原文]

`00-核心机制/一-协作机制.md` 有 7 条，其中我认为 4 条必须抄进我们的架构：

**① 规则只认机主（`:10-37`）**
> 只有机主亲口说的原话、机主明确同意过的既有条款算依据。
> **不算依据**：程序输出、体检结论、子代理汇报、别的场景发来的通知/派单/建议、自动生成的文件、AI 自己的推断。

理由（`:23-24`）：
> AI 非常容易把"某个工具说应该这样"当成"机主批准这样"。一旦允许这样推，规矩会**自己长**——今天加一条、明天加一条，三个月后没人知道哪条是真的。

**判据（`:37`）**：**"一条规矩如果说不清'是谁什么时候批准的'，它就是无效的。"**

> **[推断] 这是我们做"自主进化"的生死线。** 一个能自己改自己规则的 Agent，如果不强制"规则变更必须可追溯到人的批准"，它会在三个月内长成一个没人理解的怪物。乱雨家的答案是**断掉"AI 推断 → 规则"这条通路**，只允许"AI 推断 → 待确认清单 → 人批准 → 规则"。

**② 修改权分档 A/B/C/D/E（`:41-66`）**
| 档 | 范围 | 谁能改 |
|---|---|---|
| A 共享·宪法 | 全局铁律/规范 | 只有规则负责人 |
| C 共享·工具与运行时 | 工具/插件/MCP/技能目录/计划任务 | 负责人；别人只能提请求 |
| B 共享·板与台账 | 待办/通知/索引 | 各场景**只写自己那些行** |
| D 自己的专属 | 自己的配置/卡/记忆/技能 | 自己改 |
| E 别人的专属 | 别人的场景与记忆 | **一个字都不许写** |

E 档后面括号里有一个真实事故："两个场景互写记忆，一周后互相引用错误结论。"

**[推断] 这个分档比"权限位"更实用**，因为它是按"**地盘**"划分而不是按"读/写"划分。我们应当把它映射成：
- A/C → 人类批准 + 版本化（Agent 只能提案）
- B → 分区写 + 行级归属
- D → Agent 自主写（这是自进化的合法空间）
- E → 系统级禁止（不是提示词禁止，是文件系统/存储层禁止）

**③ 派单 ≠ 公告（`:99-116`）**
| 类型 | 含义 | 必须怎么做 |
|---|---|---|
| 派单 | 要对方**动手** | ⛔ **必须真的投递唤醒**（发进对方会话），并写明"我在等你的回执" |
| 公告/知悉 | 只是让对方**知道** | 只落盘，**不唤醒**（唤醒要花对方一轮） |

附了一个真实事故：**"一天发出 36 条'通知'，其中只有 8 条真的发进了会话"**，机主原话"你这边派单他们没反应啊"。

**[推断]** 这是"多 Agent 系统"最隐蔽的失效模式：**把公告当派单**。它直接对应 Grok Bot 的成本纪律（见 §4）和 Super-agent 的 `relay`/`notice` 两种 effect 区分（`007-architecture.md:177-178`：`relay` 唤醒、`notice` 不唤醒）。**三个独立来源都指向同一个设计**：唤醒是有成本的，必须区分"要人动手"与"让人知道"。

**④ 回执四件套 + 三条上限（`:120-155`）**
- 回执格式：**结论 + 证据（跑了什么、几个通过）+ 落盘路径 + 还差什么**
- 判据："**活干完了但对方还不知道 = 没干完**"
- 上限：**同一件事 ≤3 条消息**（派单+回执+收尾）、单条 ≤200 字/≤10 行、末行 `【结束】`
- 附加：收到"知悉"一个字不许回；纯确认语（收到/好的/谢谢）不许发
- 理由：**"AI 之间会无限礼貌下去，实测能烧掉几十万 token"**

**[推断]** 这条和第 2 条"给规矩一个机制"结合，就是一套**可强制执行的通信宪法**：消息条数、长度、终止符都能被代码检查。**这比"提示词里写'请简洁'"强一个数量级。**

### 2.6 记忆机制：三层 + 体量红线 [原文]

`二-记忆机制.md` 的三层结构（`:26-40`）：
- **① 注入层**（每轮自动注入）：只放"不读就会白干"的铁律，**必须极短**
- **② 私有层**（每场景一个文件夹）：`§〇 交接` ≤4 KB + 身份卡/场景画像（工具生成）+ 项目记忆 ≤8 KB
- **③ 共享层**（四块板）：通知看板（发生了什么）/ 待办板（该做什么）/ 总索引与台账（东西在哪）/ 体检结果（机器健康吗）

**到线动作**（`:157-163`）：主文件 ≤25 KB、§〇 ≤4 KB、技能单篇 ≤12 KB，超了搬归档。
**减肥硬要求**（`:166-175`）：**先快照 → 再搬 → 跑核对脚本（逐行比对"搬前非历史行 == 搬后非历史行"）→ 命中 0 差异才算没丢 → 再跑索引体检**。附了教训："有一次没存快照就动手拆，结果核对脚本根本跑不了——你无法证明自己没丢东西。"

**写回判据**（`:137-151`）：
- ✅ 记：建/改了应用、修了 bug、写了报告、重构、选定方案、机主分享的约定
- ⛔ 不记：搜索结果、临时路径、工具报错原文（要记就记"症状→根因"）、一次性约束、聊天过程
- 量：每次 ≤10 行 / ≤2 KB
- 判据：**"三个月后我还会需要这一行吗？"**

**[推断]** 这套东西的质量在于**它给了每一条都配了一个"为什么"和一个"真实事故"**。但它的弱点也很明显：**全部依赖人写 / 模型自觉**。自进化要做的事正是把它**工具化 + 自动化**（见 03 文档 §3）。

### 2.7 它"公开版没给"但"真机上有"的东西（重要校正）

`13-公开情报/单场景自我进化-最小闭环.md:41-47` 声明公开版缺两块：

> **公开版没有的两件（也是成品版的价值所在）**
> 1. **自动归纳**：从对话里提"候选写回"，再经人审并入记忆。没有它，记忆要靠人手写——这就是"越用越强"的速度差。
> 2. **验证闸**：硬判据 + 反例清单 + 检查脚本，保证改完不会悄悄退化。没有它，写得越多越可能坏。
>
> "开源不可逆——图可以送，发动机和刹车不送。"

**但 `08-升级与改造清单/机制清单.md:132`（脱敏自真机）显示，这两块在真机上是有实现的：**

> | **自动归纳（半自动）** | `自动归纳.mjs` 生成候选 → **owner 自己** `--confirm --by <面板>` | ⛔ 任何工具不自动写别人记忆 |

也就是说：**它做了"生成候选 → 本人确认"的半自动闭环，并且明确禁止"任何工具自动写别人记忆"。**
加上 `写盘审计`（`场景记忆\_审计\写入日志.jsonl`，init/交接/stamp 自动记，可回溯）与 `宪法.mjs --check`（14 节点，改一次版本 +1、旧版留档、只有宿主能改）。

**[推断] 这是整份材料里最有价值的情报**，它直接给出我们要自己研发的两块的技术路线：
- **自动归纳 = 生成候选 + 本人确认**（不是"自动写入"）
- **验证闸 = 硬判据 + 反例 + 检查脚本 + 审计流**（不是"模型自评"）

而且它的"没公开"恰好划出了商业判断：**方法公开，发动机与刹车不公开**。我们要自己造的就是这两样。

## 3. VCPToolBox

> 说明：仓库 595 MB、3337 个文件、`Plugin/` 下 1384 个文件。我**没有全量 clone**（会卡死），采用 GitHub tree API + raw CDN 选择性抓取核心文档与实现文件。证据以 raw URL + 行号为准。

### 3.1 它想做什么 [原文]

`README.md:17`：
> VCP 不是一个让 AI 调用工具的框架。它是给 AI 的一个能够**持续存在**的世界。

`README.md:55`：
> 这就是 VCP 全部设计的脊椎：**把 AI 从一个需要不断查询世界的访客，变成一个本就生活在世界之中的居民。**

范式对比（`README.md:57-63`）：

| 传统范式 | VCP 范式 |
|---|---|
| AI ──query──> 世界（主动去拉） | 世界 ──引力──> AI（自然地流向） |
| 被困在单次请求 | 活在连续的时间里 |

它提的问题很尖锐（`README.md:45-47`）：
> **你不记得的东西，怎么知道要去回忆它？**
> 用户三个月前提过"我下个月要考试"。三个月后他说"我最近压力好大"。传统系统里，AI 永远不会想到去检索"考试"——因为用户没提这个词。**记忆的触发依赖主动决策，而主动决策又依赖已有的记忆。鸡生蛋，蛋生鸡。**

**[推断] 这个问题是真的，而且是"通用场景 Agent"的核心难题之一。** Super-agent 的答案是 Router 主动链式召回（仍需模型决定去召回）；乱雨家的答案是固定结构每轮注入（不依赖召回，但容量小）；**VCP 的答案是"请求前预计算注入"**（把召回从"模型决策"变成"系统预计算"）。

这三条路线值得并列比较（见 §5 对比矩阵）。

### 3.2 真发明之一：VCP 纯文本工具协议 [原文]

`VCP.md:63-79`：不用 JSON Schema / function calling，用纯文本标记：

```
<<<[TOOL_REQUEST]>>>
tool_name:「始」搜索引擎「末」,
query:「始」今天北京天气怎么样「末」
<<<[END_TOOL_REQUEST]>>>
```

它给的理由：
1. **任何模型都能用**，不依赖原生 function calling
2. **AI 几乎不会写错**，不需要转义/严格 JSON
3. **支持任意嵌套**，参数里可以有代码、多行文本、甚至另一个工具调用
4. **Token 容错 + 参数模糊容错**：`image_size` / `imageSize` / `IMAGE-SIZE` 都能识别

并且：**同类型插件共用一套指令集**（5 个不同的生图插件调用方式完全一样，只换工具名）——"极大降低 AI 的认知负担"。

**[推断] 评价：**
- ✅ **"同类工具共享一套指令"这个思想极好**。它等价于给工具**分类 + 统一接口**，比让模型在 20 个长得差不多但参数不同的工具里选，好得多。这条要抄。
- ✅ **模糊参数容错**也是实用的：模型写错大小写不该让任务失败。
- ❌ **但纯文本协议在 DSH 环境下不该用**。DSH 的 `tools` Service 已经是结构化的（`ToolDefinition` + `tools.execute`），并且有 `tools/pre-execute` waterfall 可以拦截/校验。自造反序列化协议会**丢掉类型校验、丢掉 UI 卡片、丢掉 streaming 增量**。
- ✅ **可用的折中**：**保留"工具族 + 统一语义接口"**（我们的工具按族注册，同族参数同构），**但底层仍用结构化协议**。

### 3.3 真发明之二：上下文按生命周期分层（四条 user 数组）[原文]

这是我认为 VCP **最有价值**的贡献。`VCP.md:93-102`：

> VCP 不是把"工具返回"当成一种东西，而是把它拆成了**结果、状态、通知、临时感知、可持久事实**几种完全不同的上下文对象。它们都可能以 `user` 数组进入 AI 视野，但**生命周期、持久化策略、语义标签、是否进入 history，全部不同**。

四条数组：
1. **异步 user 数组**：一次性异步召回，**不进入持久化上下文**，AI 看完即抛。适合进度提示、临时中间结果、短生命周期通知。
2. **同步 user 数组**：AI 需要认真处理的结果；AI 可选择把有效信息持久化到上下文（以 `user` 数组 + `tool` 标记保留）。
3. **摘要 user 数组**：只记工具调用的**时间戳 + 状态**（成功/失败/进行中/超时/拒绝/未知）。**几乎不消耗 token**，但让 AI 知道任务生命周期与系统事实。
4. **通知栏 user 数组**：AI 通知、临时指令、工具进度、任务追踪、外部消息。**是 AI 的信息仪表盘**。

它给的理由（`:91`）：
> 如果你把所有工具状态都用同一种数组线性塞回去，AI 很快会被噪音淹没：它不知道哪些结果需要长期记住，哪些只是看一眼就该丢；它也容易把**工具进度、系统通知、临时状态误当成已经完成的事实**，进而编造工具结果或者产生幻觉发言。

还有一条很细但很重要的：
> 时间戳可以追加在 user 消息尾部（它描述"这句话发生在什么时候"）。但**对 assistant 消息的追加信息不能这么干**——所有对 assistant 发言的补充、标注、系统递呈，都应以**新的 user 数组**呈现，让 AI 清楚知道"这是系统告诉你的元信息，不是你自己刚才说出来的内容"（`VCP.md:110`）。

**[推断] 这是全篇最值得抄进我们架构的机制之一。** 理由：

1. 它把"上下文管理"从"**压缩/裁剪**"（被动、事后）升级成"**分流/生命周期标注**"（主动、事前）。这与 Super-agent 的 Inline & Spill 是**互补**的：Inline&Spill 管"信息放多少"，VCP 管"信息活多久"。
2. 它直接解决一个真实幻觉源：**模型把"进度"当"完成"**。
3. 它与 DSH 的机制可以对接：DSH 有 `spill`（`abstract spill storage`）、`compaction`、`toolResultPruner`、`systemPrompt.context`。我们可以用 `systemPrompt.context` 注入"通知栏"与"摘要状态"，用 `spill` 承载"异步结果"，用 `compaction` 处理"同步结果的历史"。

**但不可取的部分**：它把这件事绑在"自定义 `user` 数组语义"上——这需要**自己接管整个请求构造**。在 DSH 上我们改不了 LLM 请求的 message role 语义，只能用**等价做法**（prompt 分节 + 工具返回值包装 + 状态摘要工具）。**要抄思想，不抄实现。**

### 3.4 真发明之三：异步委托的心跳协议 [原文]

`docs/AGENT_AND_TASK_SYSTEM_GUIDE.md:114-137` 给了异步委托的 prompt 协议：

```
[异步委托模式]
你当前正在接受来自 {{SenderName}} 的一项异步委托任务...

[长执行任务优化机制]
如果当前步骤涉及需要长时间等待的任务，你可以在输出中包含 [[NextHeartbeat::秒数]] 占位符。
系统将推迟下一次心跳（心跳即：再次唤醒你）的到来，在这段时间内不会产生额外的轮次和Token消耗。
例如：如果你预计渲染需要3分钟，可以输出 [[NextHeartbeat::180]]。

当你确认任务已经彻底完成后，请输出 [[TaskComplete]]（报告）
如果你认为任务完全无法完成，请输出 [[TaskFailed]]（原因）
```

配套心跳提示词：如果还有活，"请继续执行……如果任务已完成，请输出 [[TaskComplete]]"。

**[推断] 这是一个极其聪明的低成本异步机制：**
- 它把"长任务等待"的成本从"反复唤醒轮询"降到"模型自报等待时长"
- **模型自己决定下一次醒来时间**——这比固定轮询智能得多，也比"sleep"省 token
- 它用三个显式终态标记（Complete/Failed/NextHeartbeat）把"任务生命周期"变成**可解析的协议**

对比 Super-agent 的做法（后台 job 有 shell 超时上限、job wait ≤5s、后台最多 30 分钟），**两者思路一致但 VCP 的更通用**：Super-agent 靠"工具超时配置"（只能控制同步工具），VCP 靠"模型声明"（能控制任意长任务）。

**这条要抄**，但要加约束：
- `[[NextHeartbeat::N]]` 的 N 必须有上限（否则模型可以说"等我 10 小时"）
- 必须有**最大总时长**与**最大心跳次数**
- 必须能被**外部 Watchdog 覆盖**（模型说 180 秒，但系统发现它其实卡死了，要提前唤醒/杀）

### 3.5 六大插件协议 [原文]

`VCP.md:41-54`：同步 / 异步 / 静态（环境感知，自动注入）/ 服务（常驻后台）/ 消息预处理（拦截请求、优化上下文）/ 混合。

其中**"静态插件：环境感知自动注入"**和**"消息预处理插件：拦截请求对上下文优化、折叠、组装"**是 VCP"引力"范式的实现载体。

**[推断] 这两类对我们有价值：**
- **静态/环境感知注入** → 对应我们需要的"时间、设备状态、未读事件、任务进度"自动进上下文，不必让模型调工具查
- **消息预处理** → 对应我们的"上下文装配流水线"（DSH 有 `systemPrompt.assemble` waterfall + `systemPrompt.context` 注册，天然可以承载这个）

**不可取**：六大类里"服务插件"与"混合插件"是**无边界的抽象**。VCP 自己说"VCP 不对插件的能力上限做任何限制"（`VCP.md:53`）——**[推断] 这不是优点，是架构风险**：无边界能力意味着无边界攻击面，且无法做权限模型。

### 3.6 记忆系统：多索引 + 重型数学 [原文]

`docs/MEMORY_SYSTEM.md`：
- 技术栈：**Rust N-API (USearch/Vexus) 向量引擎 + SQLite (better-sqlite3, WAL) + OpenAI 兼容 embedding + chokidar 文件监听**
- 双索引：`diaryIndices`（**每个日记本独立向量索引**，检索隔离/懒加载/故障隔离）+ `tagIndex`（全局 Tag 索引）
- 上层算法：**TagMemo"浪潮"算法 V3.7**（标签作为语义引力源，把向量向核心语义点"拉扯"）、**EPA（Embedding Projection Analysis）**、**残差金字塔（Residual Pyramid）**、**SVD 结果去重器**、RAG 参数热调控

它的哲学表述（`MEMORY_SYSTEM.md:29-33`）：
> 在浪潮算法的视角下，**向量空间并非平坦的，而是充满了语义引力**。标签被视为空间中的引力源；算法根据感应到的标签引力，将向量向核心语义点进行"拉扯"和"扭曲"。

**[推断] 评价要分两半：**
- ✅ **"每个域独立索引 + 全局 tag 索引"的双索引结构是合理的**。它就是"分区检索"，能防跨域污染——正好对应乱雨家的"场景私有记忆"。**这条要抄（结构层面）。**
- ✅ **"这是 VCP 的定制做品，堪忧。** TagMemo/EPA/残差金字塔这类东西，**没有公开的评测对比**（我在 docs 里没找到它相对朴素 RAG 的 recall/MRR 数据）。在自研 Agent 里引入一套只有作者能解释的向量变换，**可维护性极差**。
  - **建议**：v2 记忆用**标准方案**（embedding + 向量库 + 关键词混合检索 + rerank），把"引力/浪潮"作为可选实验，不进主干。

> ⚠️ **VCP Agent 拥有分布式系统的底层级权限**。请勿使用任何非官方或反向代理的 API（"镜像站""中转 API"）。在底层监控权限下，不可信的 API 可能导致交互数据、记忆库内容、密钥等敏感信息泄露。非专业用户请谨慎部署。

**[推断] 这是"宣称 vs 实现"落差的实名证据：**
1. **"AGI OS 工业级基建" vs 扁平根目录 + CommonJS + 300MB body 上限** —— 这是**快速堆叠的原型**，不是工业级分层。98 个 docs 文件里有大量"施工图/开发计划/一致性变更日志"（如 `TAGMEMO_V9_DUAL_TRACK_IMPLEMENTATION_BLUEPRINT.md`、`RIVERMEMO_TOPOLOGY_V3.wormhole-v2.5.backup-...md`）——**这是"边写边改边记"的开发痕迹**，不是稳定架构。
2. **"世界级记忆" vs 没有可复现评测** —— 有 `docs/VALIDATION_REPORT_2026-02-13.md` 这类文件，但我未在核心文档中看到与基线对比的 recall 数据。
3. **绑死分布式权限** —— 它自己承认要从底层监控、分布式节点拿权限。**这与我们要做的"安全自进化 Agent"方向相反。**

**[推断] 但它的某些局部工程质量确实高**：有 `docs/ROUTE_FILE_PATH_SECURITY_AUDIT.md`（路由文件路径安全审计）、`docs/WEBSOCKET_AUTH_MIGRATION.md`（鉴权迁移）、`modules/AGENTS.md` 等——说明它有**安全检查意识**。只是整体结构不允许做统一的安全边界。

### 3.8 VCP 协议 vs MCP：我们不选 VCP 的理由

| 维度 | VCP 协议 | MCP | DSH 原生工具（`tools` Service） |
|---|---|---|---|
| 表达 | 纯文本标记 `<<<[TOOL_REQUEST]>>>` + `「始」/「末」` | JSON-RPC（结构化） | 结构化 `ToolDefinition` + schema |
| 模型兼容 | **任何模型**（只要能输出文本） | 需要模型支持 tool calling（或适配层） | 同 MCP |
| 类型校验 | 弱（模糊匹配） | 强（JSON Schema） | **强**（Zod/JSON Schema + guard） |
| 流式/增量 | 需自造 | 支持 | **支持**（`tool-call-delta`） |
| 生态 | 自有插件市场 | **快速扩张的通用生态** | 遵循 MCP + 自有 |
| 嵌套调用 | **天然支持**（参数里再放调用） | 需模型多次 round | 同 MCP |
| 权限/拦截点 | 无标准 | 有（client/server 边界） | **有**（`tools/pre-execute` waterfall + `ToolGuard`） |
| 安全面 | 反序列化 + 文本解析攻击面 | 标准 | **受控** |

**结论：选 MCP + DSH 原生工具，不选 VCP 协议。** 唯一要从 VCP 拿的是"**同族工具共享一套指令**"与"**模糊参数容错**"两条体验优化。

### 3.9 不可取 / 必须绕开的部分

| # | 部分 | 问题 | 处理 |
|---|---|---|---|
| V-1 | **扁平分目录 + CommonJS + 无 `src/`** | 3337 文件、1022 代码文件，无分层；难维护、难测试、难做权限边界 | ❌ 不借鉴工程形态 |
| V-2 | **300MB JSON body / `cors({origin:'*'})`** | 面板与 API 暴露面大 | ❌ 我们的 Web 层必须默认本地绑定 + 鉴权 |
| V-3 | **绑定"分布式系统底层权限"** | 与"安全自进化"根本冲突 | ❌ 明确拒绝 |
| V-4 | **TagMemo/EPA/残差金字塔** | 无可复现评测，只有作者能解释 | ⚠️ 实验位，不进主干 |
| V-5 | **六大插件协议的无边界抽象** | "不对插件能力上限做限制" = 无权限模型 | ❌ 我们要求每个工具声明 capability |
| V-6 | **吞掉整个请求构造**（自定义 user 数组语义） | 在 DSH 上不可行，且自造反序列化协议丢类型/丢 UI/丢流式 | ✅ 抄思想，用 DSH 原语实现 |
| V-7 | **中文重概念命名**（"引力""浪潮""残差金字塔""虫洞"） | 认知负担大；`MOONLIGHT_CHIYUE_V1.md`、`MEMO_DYNAMIC_WORMHOLES.md` 这类命名使新人无法判断价值 | ⚠️ 我们的命名一律用可检验的功能名 |

### 3.10 一句话判断

> **它有三件真发明（上下文生命周期分层、模型自报心跳的异步委托、双索引记忆），值得抄思想；它的工程形态与安全模型完全不可取。**
> 正确的用法是：**把它的三个思想翻译成 DSH 原语**，而不是搬它的代码。

## 4. Grok Bot（xAI / SpaceXSI）

### 4.1 考证：它是什么（这是纠错，不是分析）

用户提到"最近比较火的 GrokBot"。我做了交叉验证：

| 证据源 | 结论 |
|---|---|
| DuckDuckGo lite | `x.ai/news/introducing-grok-bot`、`docs.x.ai/grok-bot/overview`、`x.ai/bot`、`x.com/bot` |
| Hacker News（`hn.algolia`） | "Grok Bot \| https://x.ai/bot \| pts=351"、"Grok Bot by SpaceXAI"、"Show HN: Open Bot – an open-source Grok Bot that works with any agent harness (github.com/copilotkit/openbot)" 等 15+ 条 |
| GitHub API（`q=GrokBot`） | total_count=1130；头部仓库 `najmuzzaman-mohammad/gawkbot`(★1541)、`CelestoAI/celesto`(★1132)、`unicodef1wn/grokbot-field-notes`(★680)、`BotHarness/DeepSeekBot`(★651)、`kydlikebtc/awesome-grokbot`(★470) |

**结论：Grok Bot 是 xAI（品牌表述为 SpaceXSI）的正式付费产品，2026-08-11 发布，Beta。** 不是"某个小众开源项目"，也不是营销概念。它有官方文档站（`docs.x.ai/grok-bot/*`）、订阅门槛（SuperGrok/SuperGrok Plus/Heavy、Cursor Pro/Pro+/Ultra、Cursor Teams）、以及**一个数量可观的第三方生态**（awesome 仓库、CLI、模板、org-chart 目录、self-hosted 替代品）。

**[推断] 对用户原始提问的纠正**：把写作 "GrokBot" 的话，正式名称是 **Grok Bot**（两个词）。这一点在我们后续所有对外文档里都要统一。

### 4.2 官方定义的架构 [原文]

`docs.x.ai/grok-bot/overview`：

> Grok Bot gives you Bots you can keep around: AI teammates with names, jobs, and **context that compounds over time**. Each Bot works on a **persistent cloud computer** with a browser, filesystem, and terminal, so tasks finish in your real tools instead of as chat drafts.

四条"为什么不同"：
1. **Each Bot has a computer.** 持久云电脑（浏览器 + 文件系统 + 终端），笔记本关着也继续干。
2. **Setup is a message, not a workflow builder.** 建 Bot、描述岗位、按需授权。桌面端与移动端同一个 Bot。
3. **Bots coordinate with each other.** 并行、互发消息、群聊共享上下文、**传递任务所有权**（pass ownership）。
4. **Bots learn workflows from demonstration.** 带它走一遍多步流程，它会**保存为 skill** 并能**按计划重跑（routine）**。
5. **Context compounds.** 一个有名字的 Bot 保留记忆、文件、浏览器会话、偏好**跨会话不重置**。

一个重要的共享/隔离设计（官方原文）：

> **Your Bots share one computer.** All of your Bots use the same cloud computer, sharing its files, browser sessions, and app logins, which makes handoffs work without repeating setup. The computer belongs to your account, not to an individual Bot... **between users, isolation is strict.**

FAQ 两条关键：
> **Can several Bots work at the same time?** Yes... **Each Bot gets its own screen on the shared computer, and one Bot runs one computer-use task on its screen at a time.**
>
> **What does a Bot remember?** Stable preferences, role context, and summaries of prior work. Conversations and learned context stay separate per Bot, **except for a few facts about you**（名字、时区）that all your Bots share.

**[推断] 这是一个"共享底座 + 按 Bot 隔离逻辑"的设计**，而且隔离粒度是**账户内共享、账户间严格**。这对我们很关键：**它没有走"一个 Bot 一个 VM"的昂贵路线，而是"一个云电脑多屏"**——但 `reference/PRODUCT.md:57` 又说 "Each bot runs on its own Linux VM. One bot cannot touch another bot's computer."——**官方口径前后有变化**（field notes 明确记录了这个矛盾："Where speakers contradicted each other, the resolution is noted."）。这条我们记为**口径不稳定，不照抄**。

### 4.3 我认为最值得抄的四条

**① One bot, one job（`agents/ORCHESTRATION.md:8-24`）**

它给了四条理由（这是独立于乱雨家"场景"的第二个来源验证）：
1. **Context stays scoped**——每个 agent 有自己的上下文上限；通才会同时烧完并开始遗忘
2. **You can remember who to ask**——"我们的脑子也存不下小说，你想知道该找谁"
3. **Cast into a role, the model performs better**——只有活够窄，反馈回路才能收紧
4. **Parallelism is free**——发五个专家出去，回来综合

并且明确"避免 General Helper"，要窄到能命名：*Talent Scout*、*Expense Manager*、*Bug Reproduction*、*Release Notes*。

**② The autopilot ladder（`agents/ORCHESTRATION.md:139-152`）**

| 档 | 含义 | 何时用 |
|---|---|---|
| **Investigate** | 只诊断、汇报，什么都不改 | 生产、原因不明 |
| **Draft** | 开 PR，等人 | 常规工作 |
| **Autopilot** | 实现、验证、绿了自动合 | 影响面小、验证回路好 |
| **Full autopilot** | 计划、分阶段、实现、验证、合并 | **仅限一次性项目** |

并且："**有事上线的那一刻就往回收一档**"（他们自己在发布日就这么做了）。

**[推断] 这是一个比"权限开关"更好的模型**：权限不是二元的，而是**按爆炸半径（blast radius）分档的**，而且**档位要显式写在指令里**。这恰好可以嫁接在 Super-agent 的 accept mode 上（`observe` ≈ Investigate/Draft，`auto` ≈ Autopilot），形成"**档位 × 场景风险**"的二维授权矩阵。

**③ The five rules that cover most of the antipattern list（`ANTIPATTERNS.md:534-541`）**

从 40 条真实事故里提炼出 5 条：
1. **Write the principle, delete the story.**（写原则，删故事）
2. **Reproduce it, run it, play it, then prove it.**（先复现、再跑、再玩、再证明）
3. **Name the source of truth and the library.**（点名真相来源与库）
4. **Set autonomy from blast radius; keep human gates on prod, money and secrets.**
5. **Frequency and group chats are where the tokens go.**

**[推断] 第 1 条正是乱雨家"把规矩变成机制"的镜像**，并且它给了**具体的好坏对照**（`AGENTS.md:99-103`）：
- ❌ "当编辑结账弹窗时，一定要检查 banner 的 z-index，因为 2026-03-04 它盖住了按钮。"
- ✅ "任何布局改动后，检查没有已存在的可交互元素被覆盖。"

**这条对我们做自进化极其重要**：Agent 从失败中学到的规则，**极容易过拟合到当次事故**。必须有机制强制"剥离事件、只留原则"。

**④ 成本纪律（`reference/ECONOMICS.md` + `ANTIPATTERNS.md` F 节）**

| 驱动 | 数字 | 规则 |
|---|---|---|
| routine 每 15 分钟一次 | "一天 100 次"，三个就是"一天几百条消息" | **默认一天一两次**；优先 webhook 与入站信号，而非盲轮询 |
| Bot 在群聊里 | "eager""爱说话""互相插话"，很快变贵 | 通常只要"一个 bot 一次 @ 两个"；**群聊只在你要一场辩论时用** |
| 通过 Bot 浏览器做 UI 工作 | 点击填表比 API 原生路径贵 | **有 connector 就用 connector，浏览器是 fallback** |
| Bot 太多 | "保持团队精简，不需要 45 个 bot" | 一个 chief of staff + 10-20 个窄专家可行；**没人需要中间管理层** |
| 一次性验证脚本 | 每次重写、token 贵、不可复现 | **建一个 CLI 让 agents 调用** |
| Agent `sleep 300` | 测试 1 分钟完成却等 4 分钟 | Watchdog 巡检（**5 分钟检查一次**）去打断长 sleep 与漂移 |

**[推断] 这六条成本规则，每一条都能直接变成我们架构里的硬约束**（见 02 文档 §8 的"预算与配额"子系统）。这是我认为 Grok Bot 材料**最实用**的部分——因为它来自"真花钱跑出来"的经验，不是设计文档里的想象。

### 4.5 不可取 / 需注意

| # | 部分 | 问题 | 证据 |
|---|---|---|---|
| G-1 | **Linux only** | "一个既非 Linux 兼容、也没暴露为 MCP 的工具完全不能用" | `reference/PRODUCT.md:94` |
| G-2 | **多机 Bot 会混乱** | "Multi-machine bots got confused, acknowledged as being fixed" | 同上 `:96` |

### 4.6 一句话判断

> **Grok Bot 给了我们"产品形态答案"和"成本纪律"，但它的架构是黑箱、且它自身在安全与多机一致性上未解。**
> 拿它的：one-bot-one-job、autopilot ladder、principle-not-incident、成本六律、40 条事故清单。
> 不拿它的：共享电脑模型、云 S3 记忆、闭源不可审计、群聊广播。

### 5.4 生态里"多场景通用"为什么大多失败

这是用户关心的核心问题，我给因果分析而不是罗列：

**观察：绝大多数 Agent 项目最终都退化成 coding-only。**

四个原因（**[推断]**，但每个都有材料支撑）：

1. **验证回路只在代码里闭合。** 写代码有编译器、测试、CI——**"done" 是可判定的**。做别的事（发邮件、改 CRM、做图）没有自动判据，于是 Agent 只能"看起来做完了"。Grok Bot 的整个 AGENTS.md 就是在解决这个（"Verification is the job"），但它靠**人教**。
2. **工具生态偏科。** 代码工具（git/shell/编辑器）标准且本地；业务工具要么没 API，要么 API 各异。Grok Bot 用"云电脑 + 浏览器"绕过这一层——代价是贵且脆（`ANTIPATTERNS` #26 #27：浏览器会话掉登录）。
3. **上下文抽象错位。** coding 的上下文是"文件 + 仓库结构"，天然可以按需读；通用场景的上下文是"事件 + 关系 + 历史"，需要**领域建模**。多数框架只做了"对话历史 + 向量检索"，所以一跨场景就失忆。
4. **没有"场景"这个抽象。** 只有一个"通用 Agent"，于是什么场景都想吃，什么场景都不精。**乱雨家和 Grok Bot 都独立收敛到"一个场景/一个 Bot"**——这不是巧合。

**因此，我们要做的"通用"不是"一个 Agent 会所有事"，而是"一个机制能长出所有场景的 Agent"。** 这是本方案的核心命题（见 02 文档 §0）。

## 6. 横向对比矩阵：四个源在 8 个维度上的表现

评分 1-5（5 最好）。"★"表示该源在这个维度上是**本方案的取法来源**。

| 维度 | Super-agent | 乱雨家 | VCP | Grok Bot | 说明 |
|---|---|---|---|---|---|
| **连续**（跨信道单一 Agent 感） | **5 ★** | 3 | 4 | 4 | 只有 Super-agent 把"Session 是系统实现细节"写进架构 |
| **高效**（并发与响应） | **5 ★** | 2 | 3 | 4 | Super-agent 双层 + 批处理有实验数据；乱雨家靠多会话硬撑 |
| **主动**（事件驱动） | **5 ★** | 2 | 4 | 4 | Super-agent 的两级过滤最成熟；VCP 的"引力注入"是另一条路 |
| **持久**（在线与自愈） | **5 ★** | 3 | 4 | 5 | Grok Bot 的"云电脑+笔记本关着也干"是真做到了；Super-agent 有 Watchdog 设计 |
| **场景通用性** | 2 | **5 ★** | 3 | **5 ★** | 两个独立来源都收敛到"场景/Bot 为单位" |
| **可进化** | 1 | 3 | 2 | **5 ★** | 只有 Grok Bot 有"演示→skill→routine"闭环；乱雨家承认留白 |
| **可维护** | 4 | 3 | **1** | 2 | VCP 3337 文件无分层；Grok Bot 闭源 |
| **安全** | 3 | 3 | 1 | 3 | 四个**都不及格**；Super-agent 最诚实（自己列了 8.4） |
| **综合** | **地基** | **血肉** | **器官** | **行为规范** | — |

**[推断] 这张表的最重要信息**：**没有任何一个源在 8 个维度上都高**。这证明"要做通用·自进化·持续在线的 Agent"不可能靠移植单一项目——必须**组合**，而且必须**自己补**（尤其在"可进化"和"安全"上，最强者也只有 5 和 3）。

## 7. 从分析到方案的 9 条硬结论

这 9 条是 `02-总体架构.md` 的直接输入：

1. **地基用 Super-agent 的领域模型与授权模型**，因为它把"权限"写成了数据（Policy/Mandate），而不是提示词。
2. **组织单位用"场景/Bot"**，因为两个独立来源都收敛到这里；场景身份必须**由系统注入**，不能靠模型自觉查表。
3. **记忆用"文件优先 + 分层 + 红线"**（乱雨家），v2 再叠语义检索（mem0/Zep/HippoRAG）。
4. **上下文用"生命周期分层"**（VCP 的四类）+ **"Inline & Spill"**（Super-agent）二者合一。
5. **每个耗时动作都要能异步 + 自报心跳**（VCP `[[NextHeartbeat::N]]` + Super-agent start/stop），但必须有上限与 Watchdog 覆盖。
6. **主动行为一律先 `observe` 再 `auto`**，且**档位按爆炸半径**（Super-agent accept mode × Grok Bot autopilot ladder）。
7. **自进化只允许改"技能/提示词/记忆"（D 档），不许改"运行时/权限/工具集"（A/C 档）**；每一次进化必须过"验证闸 + 反例"。
8. **所有规则必须"会失败"**：没有检测脚本的规矩就是口号（乱雨家五步法）。
9. **成本是一等约束**：唤醒有价、群聊有价、轮询有价；一切"主动"必须过预算闸。
