# 05 · 方法论与专家基线

> 这份文档回答四个问题：
> 1. 该领域顶尖专家会做哪些**我没有要求**的事？
> 2. 他们会从哪些**最原始的素材**入手，而不是我已经整理好的部分？
> 3. 他们会用**什么具体方法和工具**？
> 4. 除了你我之外，**还有什么可以证明结果是正确的**？
>
> 写作方式：每条判断都绑定到**可核验的证据**（官方仓库路径 / ADR / 基准 / 门禁），不写"专家大概会"。

---

## 0. 先说结论：我上一版最根本的失误

我上一版把 `dsh-superagent-prototype` 当成"地基"，把本机 asar 当成"运行时事实"。
**这两者都错了。**

真相是：**DeepSeek Harness 本身（`deepseek-ai/deepseek-harness`，274,034 stars，MIT）就是一个为"可换装的自主 Agent 系统"设计的生产级宿主**，而超级 Agent 原型只是它的一个单片场景应用。

我上一版方案里"要自研"的六个部件，**官方仓库已经有了**：

| 我上版说要造的 | 官方已有的包 | 证据 |
|---|---|---|
| 运行时自修改（进化落点） | `packages/extensions/`：`tool-cordis`、`cordis-host-runner`、`cordis-client-runner`、`ui-cordis` | `packages/extensions/README.md` |
| 循环卫生护栏 | `packages/guard/`：`repeat-tool-reminder`（3/5/8 阈值）、`timeout-policy` | `packages/guard/README.md` |
| 证据自动采集 | `packages/deliverables/`：`tool-present`、`workspace-changes`（turn 首尾 git 快照 + 首次编辑前整文件捕获） | `packages/deliverables/README.md` |
| 人类纠正信号 | `packages/feedback/`：会话备注 + 逐消息评分，**明确"永不进入模型"** | `packages/feedback/README.md` |
| 任务板 / DAG | `packages/team/agent-team`：`blockedBy` DAG、`writeScopes` 咨询式作用域、`revision` CAS | `docs/subsystems/agent-team.md` |
| 长目标自动续跑 | `packages/goal/` + `goal-round-driver`：durable objective + 顺序 Round | `packages/goal/README.md` |
| 多人共享会话 | `packages/experimental/liveshare`：owner/viewer/bounded write + fork 开关 | `packages/experimental/liveshare/README.md` |
| 上下文注入而不唤醒 | `agent.inject()`：落到下一次获准请求，不唤醒 driver | `docs/architecture.zh.md` / `dsh-agent` README |
| 自适应沙箱/凭据/审批 | `packages/sandbox/*`、`credentials/*`、`user-approval` | `docs/capability-seams.zh.md` |

**这不是"我方案写错了方向"，是"我把地基看浅了"。** 真正的架构工作不是"造这些部件"，而是**在这套宿主之上做正确的组合（composition）、正确的契约（contract）与正确的门禁（gate）**。

## 1. 顶尖专家会做、而我没被要求做的事

### 1.1 他们会先建立"这个仓库自己怎么决定事情"的元规则

官方仓库有 **`.agents/notes/` 共 4037 份 Agent Note**，其中：

| 生命周期 | 数量 | 含义 |
|---|---|---|
| `implemented/` | **364** | 已落地的决策 |
| `proposed/` | 138 | 已评审、未实现 |
| `rejected/` | **8** | **明确被否决的提案**（保留理由以防再犯） |
| `archived/` | 2783 | 已封档（**永久冻结，不得编辑**） |

而且格式是被**门禁强制**的（`scripts/verify-agent-note-format.ts`，属 `doc-sync`）：

```
# Agent Note: <title>
Status: implemented | proposed | rejected — <一行理由>

## Problem            ← 动机，必须能脱离方案独立成立
## Proposal / Decision
## Alternatives considered   ← 备选方案
## Consequences / What we give up  ← 我们放弃了什么
## Acceptance criteria / Risks
```

**专家会做的第一件我没要求的事：先读懂它的 ADR 制度，再按同样的制度写自己的设计。**
因为一个架构的可信度，取决于它**能不能说出自己拒绝了什么、放弃了什么**。

> 对照我自己：上一版我写了"不可取部分"，但写的是**别人的**不可取；我没写"我自己的方案放弃了什么"。这是方法论上的缺口。

### 1.2 他们会读"被拒绝的提案"

8 份 `rejected/` 全部值得读。举一例（`2026-06-20-drop-durable-step-boundaries.md`）：

> **Status: rejected** — `step/end` 是"一个模型步骤已完成"的持久指示；保留对称的 `step/start`/`step/end`，让崩溃修复、不变量检查、transcript 检视都比"从相邻事件推断完成"更清晰。
>
> **What we give up**: 日志不再把"一个模型请求已开始但进程死掉前没产出任何事件"记为一个持久事实……

**这条否决告诉我们的东西比任何"最佳实践"都有用**：在事件溯源系统里，**"边界事件"不是仪式，是崩溃修复的证据**。

> 专家做的第二件我没要求的事：**把"被拒绝的方案"当成一等学习材料**，而不是只看成功案例。

### 1.3 他们会区分"三层测试"并且知道每层证明什么

`docs/testing.md` 的分层不是"单元/集成/端到端"这种教科书分法，而是**按"它能证明什么"分**：

| 层 | 官方定位 | 能证明 |
|---|---|---|
| Unit（`pnpm run test`） | 每个注册表必须有 HMR 安全测试（卸载贡献 fiber，断言清理） | 可逆性 |
| **Coverage gate**（`test:coverage`） | **每文件 100%**，且"未覆盖的行往往是被门禁抓出的死代码，而不是缺测试" | 无死代码 |
| Real-API e2e（`test:e2e`） | 有 key 就跑真模型 | 真模型下能工作 |
| **Owner-local expected**（`test:expected`） | 无 key 的装配输出期望 | 装配正确 |
| **Performance benchmarks**（`test:bench`） | 用户路径的墙钟/内存/扩展预算，**环境变量不得覆盖预算** | 性能不退化 |
| **Snapshot**（`test:snapshot`） | **录制的会话回放**，父代提供用户输入与模型回放，儿子代是期望的持久结果 | **装配后的完整 transcript** |
| Web browser snapshot（`test:web`） | Chromium 比对会话驱动的 Web 输出 | 真实 UI |

最狠的一条在 `docs/testing.md`：

> **"Verify the world, not the self-report."**
> 一个 e2e 断言必须**重跑命令或从外部重读文件**；对 Agent 自己输出的关键词探针会让作弊的 Agent 通过。断言未触碰的文件字节完全相同。

**这正是我上一版"封存集 + 不接受自评"的设计所想要的，但官方已经把它写成了测试哲学。**
差别在于：我只是"主张"，他们是"已经这样跑了两年"。

### 1.4 他们会把"门禁能否失败"本身做成测试

`docs/testing.md`：

> **"A guard only guards if the regression fails it."**
> ……并且要**证明它**：引入回归 → 看它变红 → 回退。
>
> `verify-*` 系列：把机械可检的不变量接进一条会执行的门禁，**并证明每条改动过的验收路径都拒绝一个非法用例**。

这与我引用乱雨家"反例优先"是同一个原则。但官方版本更硬：**不是"建议有反例"，是"证明你的门禁会红"**。

### 1.5 他们会维护"能力 seam"的三角色纪律

`docs/capability-seams.zh.md` 与 ADR `2026-06-13-capability-seams.md` 定义：

> 一个可换装能力有**三个角色**：**Service Definition**（拥有 `ctx.<key>` 与词汇类型的 Cordis `Service`，永不是 TypeScript interface）、**Service Provider**（实现者）、**Consumer**（模型与插件编程的对象，只 inject 服务键、永不 import 提供方类型）。

并且给了**什么时候不拆**的判据：

> "不要预防性拆分——一个只有一个可设想提供方、一个 Consumer 的能力，保持一个包，直到第二个出现。"

**专家会做的第三件我没要求的事：为"可换装性"建立三角色纪律，并明确"不该拆"的条件。**
我上一版说"工具族化""能力族授权"，但没给"什么算一个可换装能力、什么时候该拆包"的判据。

### 1.6 他们会明确承认"这套东西不是安全的"

`SAFETY.md` 原文：

> DeepSeek Harness is experimental developer-preview software. **It has not undergone a security audit and must not be treated as secure or production-ready.**
> Sandboxing, approval prompts, and permission controls can reduce risk, **but they do not guarantee isolation or prevent damage.** Even correctly enforced restrictions cannot protect resources that the project is allowed to access.
> **Do not rely on DeepSeek Harness as the sole security control for untrusted workloads.**

**专家会做的第四件我没要求的事：给自己的方案写"SAFETY.md"，明确它挡不住什么。**
我上一版写了"六道防线"，读起来像"安全了"。这是危险的表述。正确的表述是：**六道防线降低风险，但不构成隔离保证**。

### 1.7 他们会把"性能"当产品约束而不是优化项

`benchmarks/AGENTS.md` 与 `benchmarks/agent-continuation/README.md`：

- 基准**按"被测的用户路径"组织**，不按包树镜像
- **"合成输入来自受评审的常量。绝不用录制的 Session、用户材料、环境仓库或网络服务"**
- 每个计时端点必须 `recordTimings`，并声明"它测什么、影响哪个用户场景"
- **"环境变量不得覆盖性能预算"**
- 内存受限基准在**无 swap 的 cgroup 里以 4/8 GiB 重跑，预算不变**

而 `agent-continuation` 基准测的正是我一直担心的 R-1：

> 测**长历史请求处理、冷启动工具密集续跑、反复发现不活跃 fork 子代**，不用网络服务或录制用户数据。SDK 变体通过**官方 sdk-minimal profile 驱动 100 轮、800 次真实文件读取**，并固定预算（hosted CI 期望 + 1.25× 余量）。

**专家会做的第五件我没要求的事：把"能不能续跑"做成一个带预算的基准门禁，而不是一句待验证假设。**
我上一版把它列为"R-1 风险，第 1 周 spike"。**它已经有基准了。**

## 3. 他们会用什么具体方法和工具

### 3.1 认知工具：把这套仓库的"扩展点地图"当第一张纸

`docs/architecture.zh.md` 末尾给了一张**"新行为的归属位置"**表，这是整个仓库最实用的一页。摘录（原文）：

| 目标 | 机制 |
|---|---|
| 添加面向模型的能力 | 在 `ctx.tools` 上注册；其 schema 加入提示词组装 |
| 让某个会话拥有不同的能力集合 | 组装一个 **agent preset**；其中的服务行需要 `isolate` realm |
| 从外部 webhook 启动 Session | 在 **`ctx.webhookRuntime`** 上注册可信规则，并挂载提供方适配器 |
| 拦截请求、工具或轮次 | 用 `agent/*` 或 `tools/*` 事件；**`agent/turn-stopping` 会停止轮次** |
| 添加模型可见上下文 | 调用 **`agent.inject()`**；落到下一次获准请求 |
| 拦截工具调用 | `tools/pre-execute`（allow/deny/cancel/ask）、`tools/post-execute`（accept/replace/enrich/block） |
| 在轮次边界 fork 会话 | `ctx.agents.create({ sessionId, seed, inheritedEventCount, meta: { isSeeded: true } })` |
| 在新后端存储会话 | 实现 `SessionPersistence`（`create`/`open`/`stat`/`list`/`export`） |
| 将注册项限定到单个 agent | 用该 agent 的 `agent.ctx` |

**专家做的第一件事：先在这张表上定位自己的需求，再写代码。**
而不是先设计架构，再找接口。

### 3.2 工程工具链（官方门禁，可直接复用为"正确性证明"）

| 目的 | 命令/门禁 | 能证明什么 |
|---|---|---|
| 不可逆注册（内存泄漏） | `test` 内的 **HMR 安全测试**（卸载 fiber 后断言清理） | 每个注册表可逆 |
| 死代码 | `test:coverage`（**每文件 100%**） | 无未执行行 |
| 装配正确 | `test:snapshot`（**录制会话回放**） | 完整 transcript 与持久结果 |
| 真实 UI | `test:web`（Chromium/WebKit 比对） | 界面无回归 |
| 性能不退化 | `test:bench`（**环境变量不可覆盖预算**） | 墙钟/内存/扩展在预算内 |
| 文档与设计同步 | `doc-sync`（含 `verify-agent-note-format`、`verify-doc-budgets`、`verify-translation-pairing`） | 设计文档格式与事实一致 |
| 跨文件重复 | `duplication`（TS clone 检测） | 没有复制粘贴式"第二套实现" |
| 发布物真实 | `build:check` + 内置 bin 的 `lib-mode` smoke | 跑的是**发布产物**，不是 tsx 掩盖后的源码 |
| 文档门禁 | `website:build`（兼死链检查） | 链接不腐 |
| **反例证明** | `verify-*` 门禁 + "引入回归看它变红再回退" | **门禁真的会失败** |

### 3.3 设计工具：三件套

**(a) Agent Note（带格式门禁的 ADR）** —— 405 份活跃 + 2783 份封档，格式被脚本强制。

**(b) Capability seam 三角色** —— Definition / Provider / Consumer，并把"不该拆"写成判据。

**(c) 事件分三域**（`docs/architecture.zh.md`）：
- **会话事件**：追加进日志、经 `session/event` 广播的**持久事实**——需要 reload 后仍存在时用
- **`agent/*` 事件**：携带活跃 `Agent`，观察或拦截进行中的工作
- **能力事件**（`fs/*`、`tools/*`、`telemetry/*`）：无需 import 循环即可挂策略与适配器

**专家会用"这个事实需不需要活过 reload"来选事件域**，而不是随手挂 `ctx.on`。

### 3.4 会话日志的硬纪律（我认为这是全仓最重要的一条）

> **模型可见 ⟺ 已记录。**
> 每个模型请求都必须能从日志重建。新增模型可见输入需要**会话事件**。修改现有消息内容需要注册**纯消息投影**。

以及格式纪律：
> 已提交的 generation 路径**绝不重命名、替换或删除**；迁移只能追加版本命名的后继；**前代不隐含回退或降级支持**。

**专家会用这两条来否掉我方案里的东西**：我上一版设计里的 `Evidence Store`、`Attention Ledger`，如果是"模型能看到的"，就**必须是会话事件**，而不是我另起一张 SQLite 表。这是实质性的架构更正。

## 4. 除了你我，还有什么能证明结果是对的

这是最重要的一个问题。我之前只答了"封存集 + 人类盲评"，那**太弱**。

### 4.1 五类外部证据，按强度排序

| # | 证据 | 强度 | 为什么它不能被我糊弄 |
|---|---|---|---|
| **E1** | **官方仓库已有的基准与快照** | ★★★★★ | `benchmarks/agent-continuation` 已经在测"100 轮 + 800 次真实文件读取的冷启动续跑"，带固定的 CI 预算。我的方案若声称某种编排更快，可以**直接扩这个基准**，而不是自造指标 |
| **E2** | **录制会话回放（`test:snapshot`）** | ★★★★★ | 我在方案里加的任何"模型可见输入"，只要不是可回放的会话事件，**回放就会红**。这是机器判据，不是我或你说了算 |
| **E3** | **官方门禁（coverage 100% / doc-sync / duplication / build:check）** | ★★★★ | 我要"另起一套实现"而不复用，`duplication` 与 `coverage` 会先红；我的设计文档与代码不同步，`doc-sync` 会红 |
| **E4** | **e2e 的"验世界不验自报"** | ★★★★ | 断言必须重跑命令/外部重读文件/断言未触碰文件字节相同。**Agent 自评不算数** |
| **E5** | **真模型 e2e（有 key 就跑）** | ★★★ | "无 key 只证明管道；有 key 才证明 agent 真能用" |
| **E6** | **第三方可复现** | ★★★ | MIT 仓库 + 固定 Node/pnpm 版本 + 锁文件；任何人可复跑 |

### 4.2 我的方案里，哪些主张能被上述哪一条证伪

这是"诚实版本"的表——**我主动给自己挑刺**：

| 我的主张 | 能证伪它的外部证据 | 若证伪会怎样 |
|---|---|---|
| 三层编排优于两层 | E1（扩 `agent-continuation` 基准：多场景 2 层 vs 3 层，同预算） | 退到 2 层（官方 §4 已给降级路径） |
| "完成契约（DoneSpec）让非编码场景可判定" | E2（把它做成会话事件 + 快照场景：没有 DoneSpec 的工单必须无法进入 `working`） | 说明 DoneSpec 只是提示词，不是机制 |
| "注意力税能压到 1.0 以下" | E4 + E5（真模型 e2e 里统计主动消息/被采纳项） | 说明我在用工程指标掩盖产品失败 |
| "自进化只改 D 档" | E3（`fs/write-intent` 拦截 + 门禁：越界写必须红） | 说明权限只在文档里 |
| "凭据不进上下文" | E4（e2e 里扫描完整消息流，断言无任何凭据明文） | 直接判失败 |
| "新增场景零代码" | E2（新增一个 scene 契约后，必须能录一个会话回放场景并绿） | 说明还是得改代码 |
| "自报心跳省 token" | E1（基准：自报 vs 固定轮询，同任务集比 token 与时延） | 说明省的是我的想象 |

### 4.3 还缺的一类证据：**别人的复现**

E6 是我上一版完全没提的。官方仓库的可靠性恰恰来自：

- `pnpm-lock.yaml` 1.2 MB（**依赖完全钉死**）
- `native/`、`vendor/`（Cordis 供应并记录 upstream SHA）
- 固定的 Node ≥24.9 / pnpm workspaces
- `test:snapshot` 的**已提交期望文件**（不是"跑一遍看看"）
- CI 上 `test:coverage` 才是门禁（`test` 不是）
- `test:bench` 用 `support/machine-profiles.ts` 记录参考机，**并把参考机期望与共享 CI 时间尺度分开**

**结论：证明"结果正确"的最强方式，不是我写更多文档，而是让我的方案**能生成一个被别人复跑的门禁**。

## 7. 按官方格式，写本方案自己的「What we give up」

> 我在 §1.1 批评自己"只写了别人的不可取，没写自己的"。这一节补上。
> 格式照 `.agents/notes/README.md`：`## Problem` 必须**脱离方案独立成立**；`## What we give up` 必须**具体到能力**。

### 7.1 用 Agent Note 格式写本方案的核心决策

```markdown
# Agent Note: 场景契约以 preset 为底座，DoneSpec 为唯一新增概念

Status: proposed

## Problem
（脱离方案也成立）
"通用 Agent"的失败不是因为模型不会做事，而是因为非编码场景的"做完了"
无法被机器判定；于是 Agent 只能交付"看起来完成"的结果，
人类被迫承担全部验收费。任何试图覆盖多场景的方案都必须先回答这个问题，
否则它只是在增加上下文与工具的宽度。

## Proposal
在官方 preset 机制之上，只增加两件：
1) DoneSpec（check / evidence / review 三形态）：开工前声明、完工后机器执行；
2) 场景 = preset + DoneSpec + 自治上限 的三元组（仅在"纯 preset 证伪失败"时引入）。

## Alternatives considered
- A. 造完整领域内核（Ticket / Mandate / Policy 引擎 / Effects / Outbox）
  —— 否决：官方 core/session（事件溯源）+ approval + schedule + jobs + team 已覆盖，
  自造会变成第二套实现（`duplication` 门禁会红）。
- B. 只做提示词工程（教模型"要交付证据"）
  —— 否决：arXiv:2607.24300 / 2609.02246 证明自评与 LLM 裁判不可信；
  且乱雨家原文："没有会失败的检查的规矩 = 口号"。
- C. 纯 preset（零新概念）
  —— 保留为 P0 证伪实验 F-1：若它能实现第一个场景，则 A 与 B 都不需要。

## What we give up
1. **放弃"自研运行时"的控制感**：我们不再拥有 loop、不再能改它。
   代价：必须接受官方 API pre-stable（升级会破，见 R-13）；
   设计只能在"文档化扩展点"内表达。
2. **放弃"一套统一架构"的美感**：本方案最终可能只是
   "一批 preset + 一个 DoneSpec 工具 + 一堆组织约定"，
   没有"SEA 分层架构"这样的整体叙事。这是**有意接受的**（见 R-14）。
3. **放弃"Agent 自主改运行时"的能力**：即使官方 `extensions` 允许模型写插件挂载，
   我们也只在 D 档（技能/记忆/提示词）开放自治；A/C 档必须人批。代价：进化更慢。
4. **放弃"全场景覆盖"的承诺**：DoneSpec 的 `check` 形态在创作类场景
   （写文案/做设计）大概率写不出来，那类只能靠 `evidence + review`，
   也就是**要人类签字**。所以本方案的"通用"**不等于"无人值守"**。
5. **放弃"注意力税"作为价值判据**：它只作降档触发器。
   代价：我们无法用一个数字宣称产品价值。

## Acceptance criteria
- 纯 preset 实现场景 A 的证伪实验完成（F-1）；
- DoneSpec 在 3 类非编码场景的 `check` 成功率 ≥ 50%（F-3）；
- 任何新增"模型可见输入"都能被 `test:snapshot` 回放（I4）；
- 任何注册都可被 HMR 安全测试证明可逆（I5）。

## Risks
- 若 F-1 成功，本方案瘦身到"约定 + DoneSpec"，可能被认为"不够深入"（R-14）；
- 若 F-3 成功率 < 50%，"通用"退化为"半自动"，需重新定义产品定位；
- 官方 pre-stable API 变更会使方案需要重写（R-13）。
```

### 7.2 这个格式为什么值得采用

| 特性 | 效果 |
|---|---|
| `Problem` **必须脱离方案独立成立** | 防止"先有方案再编动机" |
| `Alternatives considered` **必须列备选** | 防止"只有一条路"的假必然 |
| `What we give up` **必须具体** | 多数设计文档会删掉这部分，但**它决定文档三个月后还有没有用** |
| `Status` 三态 + `archived` 冻结 | 决策有生命周期，不会"永远正确" |
| 路径编码 `{lifecycle}/{class}/日期-标题.md` | 可按生命周期与类型检索，无需中心索引 |
| 格式被 `verify-agent-note-format` **机器强制** | 制度不靠自觉 |
