# 34 · 内存真相与大改造（实测闭环）

> 本轮把上一轮遗留的"2328MB 不知道为什么"彻底查清，并做了一次**有实测对照的改造**。

---

## 一、先纠正上一轮的两个错误结论

| 上一轮的错误结论 | 实测真相 |
|---|---|
**"4 个免费 AI 站只占 52MB"** | **错误**。重做 A/B（等 30 秒让进程回收）后：**省 323MB**。上一版只等 6 秒，renderer 进程还没回收完 |
**"GPU 进程 389MB 不可压缩"** | **错误**。把 4 个站全关掉后，**GPU 进程直接消失（0 个）**，不是"压缩不了" |

**教训**：A/B 实验的等待时间不足，会得出完全相反的结论。

## 二、内存去向终于查清了

### 2.1 逐进程账单（实测）

| PID | 私有MB | 线程 | CPU秒 | 角色 |
|---|---|---|---|---|
**11904** | **420** | 36 | 69.7 | ★ **GPU 进程** |
5468 | 95 | 49 | 24.3 | 主进程（有窗口） |
15552 | 234 | 22 | 3.7 | 渲染进程（免费AI站） |
3368 | 193 | 20 | 3.1 | 渲染进程（免费AI站） |
7296 | 186 | 22 | 2.7 | 渲染进程（免费AI站） |
13084 | 145 | 23 | 2.9 | 渲染进程（免费AI站） |
其余 | ~160 | | | 引擎页面 + 界面 |

**关键结论**：
- **GPU 进程占 420MB（28%）** —— 这是 Chromium 的合成基础设施
- **4 个免费 AI 站的渲染进程占约 758MB（51%）** —— 这才是大头

### 2.2 为什么上一轮误判

上一轮我把 GPU 进程当成"不可压缩的固定开销"。
实际上：**当 4 个站全部不加载时，GPU 进程根本不创建**。

```
warmCount=4 → GPU 进程存在，420MB
warmCount=0 → GPU 进程不存在，0 个
```

**GPU 内存不是"固定开销"，是"那 4 个站的合成层撑起来的"。**

## 三、找到项目里已有的解法

### 3.1 原代码早就有 `noWarm`

`renderers.js:11579` 的 `WEB_AI` 站点表：

```js
{ key: 'deepseek', ..., noWarm: true, ... },   // ← 只有它配了
{ key: 'doubao', ... },                         // ← 其余 3 个都没配
{ key: 'tongyi', ... },
{ key: 'chatglm', ... },
{ key: 'kimi', ... },
```

预热循环（L12016-12019）：
```js
WEB_AI.forEach(function (s, k) {
  if (s.noWarm) return;    // ← 已支持"不预热"
  setTimeout(function () { webAiEnsure(s.key, 'warm'); }, k * 700);
});
```

**项目作者已经想到"不预热省内存"，只是默认把 3 个站都开了。**

> 这不是"缺功能"，是"默认值不经济"。

### 3.2 我做的最小改造

把"预热几个"变成**可配置**（不改核心体验，点开仍会加载）：

**新增配置** `外壳/data/webai-warm.json`：
```json
{
  "warmCount": 1,
  "note": "0=全不预热（最省内存）；1=只预热第一个（默认）；4=全部预热（最快但占约 1502MB）"
}
```

**改动链路**：
| 层 | 改什么 |
|---|---|
`main.js` | 加 `ipcMain.handle('webai:warm-config')` 读配置 |
`preload.js` | 暴露 `app.webaiWarmConfig()` |
`renderers.js` | 预热循环加 `warmLimit` 判断 |

## 四、实测对照表（决定性证据）

| warmCount | 私有内存 | 工作集 | 进程数 | GPU 进程 | 渲染进程 | 相对 4 站 |
|---|---|---|---|---|---|---|
**0**（全不预热） | **457 MB** | 759 MB | **7** | **0 个** | 6 个 / 381MB | **省 1045MB（70%）** |
**1**（默认推荐） | **722 MB** | 1136 MB | **8** | 0 个 | 7 个 / 633MB | **省 780MB（52%）** |
**4**（原默认） | **1502 MB** | 2554 MB | **13** | 1 个 / 420MB | 11 个 / 992MB | — |

**这是本轮最强的证据：配置改一个数字，内存差 1045MB。**

### 4.1 为什么 warmCount=1 时 GPU 进程是 0 个

因为只预热 1 个站时，它的合成负载还不足以触发独立的 GPU 进程（Chromium 用软件合成也能撑）。
到 4 个站时才需要独立 GPU 进程。

## 八、诚实的局限

1. **warmCount=0 的体验代价我没实测**：点开时应有一次加载等待（约 3-10 秒），我没量。
2. **GPU 进程存在与否的边界没精确探**：可能是 2 个站、3 个站的临界点，我没逐档测。
3. **没在低内存机器上验证**：1045MB 的节省对 32GB 机器意义不大，对 8GB 机器意义大。
4. **配置是"改文件 + 重启生效"**，不是热更新。
5. **界面最终样子仍需你确认**。

## 九、一句话

> **上一轮我说"GPU 420MB 不可压缩"，实测证明那是错的 —— 把 4 个站关掉，GPU 进程直接不创建。**
