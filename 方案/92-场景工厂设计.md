# 92 · 场景工厂（造场景的场景）

> 用户：「请你先构建一个**用于做其它场景的场景**」

---

## 一、我的理解（先确认我懂对了）

你要的不是"再造一个普通场景"，而是**元场景**：

```
中枢（对话）
  ↓ 发现需要新场景
场景工厂（造场景的地方）
  ↓ 产出
新场景（可以被神经元看到、双击进入、有记忆）
```

**场景工厂是"所有场景的母亲"。**

---

## 二、为什么必须是它先做

### 2.1 逻辑依赖

```
没有场景工厂 → 每个新场景都要手工改 json + 建目录 + 写记忆
            → 你说"不可预估的场景"永远无法实现
有场景工厂   → 场景可以按需生成（AI 或用户都能触发）
```

### 2.2 你说过的话

> 「我既然想的是打造一个超级智能体或是 agent，
>   就**必然会产出不可估量的场景**，
>   而这些都全权交给 AI 在执行任务时**自行选择要调度哪些场景**」

**"不可估量的场景" = 必须能自动生成 = 必须有场景工厂。**

### 2.3 当前状态：工具链存在，但用户看不见

**审计发现，后端已有完整工具链：**

| 工具 | 行数 | 能力 |
|---|---|---|
`scene-hatch.mjs` | 534 | `--create`（建场景）/ `--check`（校验）/ `--list` |
`scene-edit.mjs` | 545 | `--layout` / `--set` / `--add` / `--remove` |
`mem-init.mjs` | 157 | 初始化记忆骨架 |
`scene-validate.mjs` | 286 | 校验五件套 |
`sceneflow.mjs` | 491 | 流程编排 |
`scene-bind.mjs` | 282 | 绑定会话 |

**但这些工具只有 AI 会调用（通过 bash），用户完全看不见。**

**场景工厂 = 把这些能力变成可见、可操作的界面。**

---

## 三、技术可行性（审计后确认）

### 3.1 能做什么

```
✅ kun:file:read    读任意文件
✅ kun:file:write   写文件（限 D:/E: 盘）
✅ kun:pick-folder  系统选文件夹
✅ kun:file:stat    文件状态
✅ scenarios:list   列场景
✅ scenario:get     读场景
✅ engine:prompt    调 AI
```

### 3.2 不能做什么

```
✗ 没有 spawn/exec  → 前端不能直接跑 .mjs 脚本
```

**这意味着：场景工厂必须"用文件操作模拟 scene-hatch 的逻辑"，而不是调用它。**

**好消息：** scene-hatch 本质就是写 5 个文件，前端完全能做。

## 四、场景五件套（工厂要产出的东西）

审计确认的实际结构：

```
① 场景定义     workbench/外壳/scenarios/<id>.json
               { id, name, description, layout, panels[], meta }

② 场景契约     workbench/sceneboard/scenes/<id>.json
               { id, name, role, description, inputs[], outputs[] }

③ 身份卡       workbench/引擎数据/.dsh/场景记忆/<中文名>/身份卡.md
               我是谁 / 职责边界 / 输入输出 / 方法来源 / 边界

④ 私有记忆     workbench/引擎数据/.dsh/场景记忆/<中文名>/场景私有记忆.md
               §〇 交接四问 + 主体

⑤ 注册表       workbench/引擎数据/.dsh/场景记忆/_共享记忆/索引.json
               areas[] 里追加一条
```

**工厂的产出 = 这 5 个东西。**

## 五、场景工厂的界面设计

### 5.1 布局（三栏，每栏职责明确）

```
┌──────────────┬────────────────────────┬──────────────┐
│              │                        │              │
│  ① 场景列表   │  ② 编辑器              │  ③ 预览       │
│              │                        │              │
│ ✓ 调研        │  名称: [___________]   │  ┌─────────┐ │
│ ✓ 审阅        │  ID:   [___________]   │  │ 神经元里 │ │
│ + 新建...     │  职责: [___________]   │  │ 的样子   │ │
│              │  领域: [下拉▼]         │  │  ●       │ │
│              │                        │  └─────────┘ │
│              │  面板:                 │              │
│              │  ┌──────────────────┐  │  五件套状态:  │
│              │  │ [AI对话] [删除]   │  │  ✓ 定义      │
│              │  │ [网页  ] [删除]   │  │  ✓ 契约      │
│              │  │ [+ 添加面板 ▼]    │  │  ✓ 身份卡    │
│              │  └──────────────────┘  │  ✓ 私有记忆  │
│              │                        │  ✓ 注册表    │
│              │  [保存] [校验] [发布]  │              │
└──────────────┴────────────────────────┴──────────────┘
```

### 5.2 关键设计：为什么这样分

**① 场景列表**
- 看到所有场景（真实读取 `scenarios:list`）
- 可以选中编辑
- 可以新建

**② 编辑器**
- 改元信息（名称/ID/职责/领域）
- **可视化编辑面板**（不是编辑 JSON）
- 加/删面板，选类型
- 实时校验

**③ 预览**
- 显示该场景在神经元里的样子（星点）
- 五件套完整性检查（✓/✗）
- **发布前必须全绿**

### 5.3 面板类型选择器（只用真实可用的）

**审计确认：10 种面板里只有 4 种真能用。**

```
可选类型（真实）：
  ✓ harness    AI 对话
  ✓ embed      网页嵌入
  ✓ neuron     记忆神经元
  ✓ main-agent 主 Agent

不可选（占位，会警告）：
  ⚠ sf-board / review-doc / review-files / pc-*
```

**关键：不允许用户选择"占位面板"，避免造出空场景。**

## 六、工作流程（用户视角）

### 6.1 场景 A：AI 主动建议

```
用户在中枢说：「帮我做一份竞品分析报告」
  ↓
AI: 现在没有「竞品分析」场景，要我建一个吗？
  ↓
用户: 好
  ↓
AI 调用场景工厂（生成五件套）
  ↓
神经元里出现新节点
  ↓
用户双击进入
```

### 6.2 场景 B：用户主动创建

```
用户打开场景工厂
  ↓
点「+ 新建」
  ↓
填：名称=竞品分析，职责=对比竞品功能矩阵，领域=内容
  ↓
选面板：embed（看竞品）+ harness（AI 分析）
  ↓
点「校验」→ 五件套检查
  ↓
点「发布」→ 写入 5 个文件
  ↓
神经元自动刷新出现新节点
```

## 七、实现范围（诚实评估）

### 7.1 必须做（P0）

| 项 | 依赖 | 工作量 |
|---|---|---|
**读场景列表** | `scenarios:list` ✅ | 小 |
**读场景详情** | `scenario:get` ✅ | 小 |
**编辑元信息** | 前端状态 | 中 |
**可视化编辑面板** | 前端状态 | 中 |
**写入五件套** | `kun:file:write` ✅ | **大**（要精确复刻 scene-hatch 逻辑） |
**校验** | 前端逻辑 | 中 |
**发布后刷新神经元** | `refresh()` ✅ | 小 |

### 7.2 关键技术点

**① 复刻 scene-hatch 的产出格式**

必须精确知道 5 个文件的格式。审计已有样本：
```
scenarios/arch-review.json     ← 场景定义样本
sceneboard/scenes/arch-review.json  ← 契约样本
场景记忆/架构梳理/身份卡.md     ← 身份卡样本
场景记忆/架构梳理/场景私有记忆.md ← 私有记忆样本
_共享记忆/索引.json            ← 注册表样本
```

**② 注册表写入要小心**

```json
// 索引.json 结构
{
  "areas": [
    { "id": "arch-review", "name": "架构梳理", ... }
  ]
}
```
追加时要**读出来 → 追加 → 写回**，不能覆盖。

**③ 神经元刷新**

前端已有 `refresh()` 方法，发布后调用即可。

## 八、我建议的实现顺序

```
第 1 步：读 + 展示（只读）
   - 场景列表（左栏）
   - 场景详情（中栏只读显示）
   - 五件套检查（右栏）
   → 验证：能真实读到现有 11 个场景

第 2 步：编辑（不写文件）
   - 改元信息
   - 加删面板
   - 实时预览
   → 验证：改动只在内存，刷新后恢复

第 3 步：写入（新建场景）
   - 写五件套
   - 刷新神经元
   → 验证：新建的场景真的出现在神经元里

第 4 步：编辑已有场景
   - 改现有场景
   → 验证：改动能持久化
```

**每步都要跑通再进下一步。**

## 九、这个场景自身的记忆

**场景工厂也要有身份卡和私有记忆：**

**身份卡要点：**
```
我是谁：场景的创造者
职责：把一句话需求变成可运行的场景（五件套）
方法：
  ① 判断任务性质（看/改/比/盯/跑）→ 决定交互范式
  ② 选择真实可用的面板类型
  ③ 生成身份卡（不能空，要有职责边界和方法来源）
  ④ 写私有记忆骨架（§〇 四问）
边界：
  · 不创建占位面板（避免空场景）
  · 不重复创建同名场景
  · 发布前必须五件套校验通过
```

**私有记忆可以累积：**
```
· 用户偏好什么类型的场景
· 哪些面板组合最常用
· 哪些场景建了但没用起来（可清理）
```
