| 判据 | 判断 |
|---|---|
① 会反复回来？ | ✅ 崩溃 96 条，且会持续产生 |

### 2.2 它的边界（关键）

```

  · 读 crash-log.jsonl

  · 找共同模式（什么操作触发）
  · 提出修复建议（不自己改）

我不做：
  · 不改代码（那是开发场景）
  · 不重启 GUI（那是用户操作）
  · 不删崩溃日志（那是证据）
```

## 四、场景分支是什么

用户说「先做我们这份项目的场景分支」。

**"分支"我理解为两层含义：**

### 4.1 狭义：场景之间的关系树

```
hub
 ├─ 产出线：research → arch-review → build-plan
 ├─ 质量线：incident-analysis → （提修复） → build-plan
 ├─ 维护线：pc-cleanup
 └─ 自省线：self-review
```

### 4.2 广义：每个场景是一个"分支"，可以独立开发

```
场景 A 有自己的：定位卡 / 记忆 / 技能 / 资产
改场景 A 不影响场景 B
```

**这正是六件套的意义。**

## 六、故障分析场景的具体设计

### 6.1 它分析什么

**数据源：** `workbench/外壳/data/crash-log.jsonl`（96 条）

```json
{"at":"2026-11-06T13:20:24.720Z","kind":"render-process-gone","reason":"crashed","exitCode":-1,"url":"http://127.0.0.1:31238/chat"}
{"at":"...","kind":"child-process-gone","details":{"type":"Utility","reason":"crashed",...}}
{"at":"...","kind":"uncaughtException","message":"EPIPE: broken pipe, write"}
```

### 6.2 分析流程（四步）

**第 1 步：分类统计**
```
按 kind 分组：render-process-gone (40) / child-process-gone (38) / uncaughtException (18)
按时间分布：集中在哪天？哪个时段？
按 url 分布：集中在哪个页面？
```

**第 2 步：找模式**
```
· 崩溃是否与特定操作相关？
· 是否集中在某个版本？
· 是否有时序关系（先 uncaughtException 再 crash）？
```

**第 3 步：归因**
```
每个模式给出可能原因（标注置信度）
区分：
  · 应用自身 bug
  · Electron 环境问题
  · 硬件/驱动问题
  · 无法判断
```

**第 4 步：提建议（不改代码）**
```
· 立即可做的（降低崩溃影响）
· 需要调查的（进一步取证）
· 可忽略的（已知无害）
```

### 6.3 产出

```
workbench/产物/崩溃分析报告.md
```

**必须包含：**
- 分类统计表
- 发现的模式（每个标置信度）
- 归因（能确定 / 存疑 / 无法判断）
- 建议清单（按优先级）
