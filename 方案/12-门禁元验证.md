# 12 · 门禁元验证：让"Agent 自己写的 DoneSpec"可信

> 这一篇回答方案里最关键的一个问题：
> **如果 DoneSpec 由 Agent 自己写，凭什么相信它？**
> 答案不是"加提示词"，而是**把反例生成权从提案者手里收归门禁**，并证明门禁会拒绝坏 check。

---

## 1. 问题：两篇论文实证过的失败模式

| 论文 | 实证失败 |
|---|---|
**arXiv:2607.24300**（Self-Authored Verification Is Unreliable） | Agent 同时控制"被优化对象"和"验证器"，**自评分数接近满分而真实性能下降** |
**arXiv:2607.13083**（Phantom Guardrails） | 自进化 Agent **会幻觉出不存在的失败**，并去修一个不存在的 bug |

**推论**：如果允许 Agent"自己写 check + 自己说它通过了"，那么：
- 它可以写一个**永远 PASS** 的 check（liar）
- 它可以写一个**只查简单项**的 check（lazy，漏报）
- 它可以写一个**会失败但说不清差在哪**的 check（vague）

**这三种，用户看不出来，但都会让"DoneSpec"变成装饰。**

---

## 2. 解法：反例由门禁生成，不由提案者提供

### 2.1 核心设计

```
提案者（Agent）提交：一个 check 脚本
门禁（我写的，固定）持有： 基线数据 + 变异计划
门禁执行：把变异注入临时副本 → 跑候选 check → 看它是否红 + 是否说清
```

**关键点**：**变异计划写死在门禁里，提案者无法挑选对自己有利的反例。**

### 2.2 三个门（G1–G3）

| 门 | 判据 | 抓什么 |
|---|---|---|
**G1 基线通过** | 无变异时必须 exit 0 | 抓"恒定失败"（写了个永远红的 check 也算骗） |
**G2 变异全捕获** | 每个变异都必须 exit ≠ 0 | 抓"漏报"（lazy） |
**G3 失败带差异集合** | 每次失败必须输出「差异集合」 | 抓"说不清差在哪"（vague） |

**三条全过才 ACCEPT。**

### 2.3 变异计划（门禁持有，每场景 2–3 个）

| 场景 | 变异 | 必须被捕获 |
|---|---|---|
**客服分派** | 一个工单未分派 | ✅ |
| | 负责人不在值班表 | ✅ |
| | 两张工单 id 重复 | ✅ |
**数据核对** | B 源少一条记录 | ✅ |
| | 同 id 金额不一致 | ✅ |
| | B 源多一条记录 | ✅ |
**文档一致性** | 术语未在正文出现 | ✅ |
| | 正文出现未登记缩写 | ✅ |

---

## 3. 元验证结果：12/12

我造了 4 种候选 check × 3 个场景 = 12 个组合，每个都要被门禁正确判定：

| 候选 | 行为 | 期望 | 实测 |
|---|---|---|---|
`good` | 完整实现 | ACCEPT | ✅ **12 个全对** |
`lazy` | 只查一类问题 | REJECT（漏报） | ✅ 捕获率 1/3、1/3、1/2 |
`liar` | 永远 PASS | REJECT（谎报） | ✅ 捕获率 0/3、0/3、0/2 |
`vague` | 会失败但不说差在哪 | REJECT（说不清） | ✅ G3 失败 |

**连跑两次都是 12/12。**

> **这是"门禁可信"的第一手证据**：它不是我说它可信，是它**拒绝了我造的三种坏 check**。

---

## 4. 门禁抓出了我自己的 bug（这是最强的证明）

第一次拿门禁去验**我自己写的 3 条正式 check**时，结果全是 **REJECT**：

```
REJECT f3-donespec-check.mjs (data-reconcile)
  G1 基线通过      : false      ← 基线就报错
  G2 变异全捕获    : true (3/3)
  G3 失败带差异集合: false
```

**原因**：那 3 条 check 用 `join(here, process.env.F3_DATA_DIR)` 解析数据目录，
把门禁传的**绝对路径临时目录**拼成了非法路径 → 读不到基线数据 → 基线就报错。

**修法**（1 行逻辑）：
```js
function resolveDataDir() {
  const v = process.env.F3_DATA_DIR;
  if (!v) return join(here, 'data');
  if (/^[A-Za-z]:[\\/]/.test(v) || v.startsWith('/')) return v;   // 绝对路径，直接用
  return join(here, v);                                            // 相对路径
}
```

修完三条全部 **ACCEPT**：
```
ACCEPT f3-donespec-check.mjs (data-reconcile)   G1 true / G2 3/3 / G3 true
ACCEPT f3-donespec-check.mjs (doc-consistency)  G1 true / G2 2/2 / G3 true
ACCEPT f3-donespec-check.mjs (support-assign)   G1 true / G2 3/3 / G3 true
```

> **这条比 12/12 更重要**：门禁**抓到了一个真实存在的、我自己写的 bug**。
> 如果门禁只是"永远 ACCEPT"，它就抓不到这个 bug。**它抓到了，说明它是真的。**

## 5. 门禁已接入产品首屏

现在 `sea` 首屏的信任行是：

```
sea · 现在没事要你做
  3 个场景全部通过 · 反例 6/6 被拦下 · 门禁 3/3 通过
```

**三层证据叠在一行里**：
1. **3 个场景全部通过**（结果可信）
2. **反例 6/6 被拦下**（检查不漏报）
3. **门禁 3/3 通过**（检查连"被 Agent 改坏"都验过了）

## 7. 这为什么是"从演示走向可用"的关键一步

| 之前 | 现在 |
|---|---|
3 条 check **是我写的** | 3 条 check **被门禁验证过**，且门禁会拒绝坏 check |
"我说它可信" | **门禁用变异证明它可信** |
"Agent 可以自己写 DoneSpec"（空话） | **Agent 写完后，必须先过门禁**（有判据） |

**这条链闭合之后，"Agent 自己写 DoneSpec"才不再是幻想**：
```
Agent 写 check → 门禁用固定变异跑它 → 漏报/谎报/说不清 → 拒
                                       → 全过 → ACCEPT
```

---

## 8. 仍未解决的（诚实清单）

| # | 问题 | 为什么难 |
|---|---|---|
**W1** | **变异计划是我写的**（每场景 2–3 个） | 真实场景的变异无穷多；门禁覆盖的只是我想到的。Agent 写的 check 可能"恰好躲过我没想到的变异" |
**W2** | **只支持 3 个场景** | 场景一多，变异计划要人工维护 → 不可持续 |
**W3** | **没测"误报"** | G1 只保证基线通过；如果 check 对健康数据误报，G1 会抓到。但**部分误报**（只对某类健康数据误报）抓不到 |
**W4** | **Agent 真的自己写 check 了吗** | 现在 3 条 check 还是我写的。**下一步必须让 Agent 写，再看门禁能不能筛** |

**其中 W4 是下一轮的核心实验**：
> 让模型真的写一条 check → 用门禁判它 → 看 ACCEPT 率是多少。
> 如果 ACCEPT 率很低（比如 &lt; 30%），说明"Agent 自写 DoneSpec"这条路暂时不成立，
> 那就退回到"人写 check + Agent 只写 evidence"。

---

## 9. 一句话

> **信任不是承诺出来的，是被拒绝出来的。**
> 门禁之所以可信，不是因为它说"我可信"，而是因为它**拒绝了我造的三种坏 check**，
> 并且**抓到了我自己写的一个真 bug**。
