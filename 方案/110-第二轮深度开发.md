## 三、修掉的 3 个 bug

### bug 1：React 替身丢了 props.children（最严重）

测试报「基线区块含 4 项指标 0 项」，但代码逻辑完全正确。

**根因**：
```js
// 我的替身
return { $$typeof: 'element', type, props: props || {}, children: flat };
```
真实 React 会**同时**把 children 放进 `props.children`。
组件内部 `function OpsBlock({ title, children })` 拿到的是 `props.children`，
在替身环境里永远是 undefined。

**影响**：之前所有依赖 `props.children` 的断言都不可靠。

**修正**：
```js
const p = Object.assign({}, props || {});
p.children = flat;
return { $$typeof: 'element', type, props: p, children: flat };
```

### bug 2：直接函数调用组件 → 白屏

加场地地图后，点击插件**主面板完全白屏**。

**根因**：
```js
// 错
blocks.push(SiteMapTiers({ key: 'sitemap', siteMap }));
```
而 `SiteMapTiers` 内部用了 `useState`。

直接调用会让 hook 注册到 `OpsSection` 的上下文，
造成 hook 顺序错乱 → 整个 React 树崩溃 → 白屏。

**修正**：`h(SiteMapTiers, {...})`

**为什么测试没抓到**：我的测试也是直接调用，与错误代码同构。

**改进**：加静态检查扫描全文件，禁止 `Xxx({...})` 形式调用本地定义的组件。
**带反例验证**：临时注入违规 → 立刻报 `XX 无「直接函数调用组件」HealthBar (行 1730)`；恢复 → OK。

### bug 3：两处判据都写错了（方向相反）

会话绑定一直显示 7/9，查了才发现两个工具各写各的：

**mem-map.mjs 太严**：
```js
const p = (sc.panels || []).find(x => x.type === 'harness');
```
中枢的对话由外壳固定挂载，配置里只有 neuron 面板 → 漏判。

**基线.mjs 太松**：
```js
if ((sc.panels || []).some(p => p.sessionId)) coverage.会话绑定++;
```
配置里**根本没有 sessionId 字段** → 永远为假 → 全都不算。

**修正**：两处统一为同一套判据
```js
hasHarness || note.includes('shell') || (hasNeuron && sc.first)
```

**结果**：会话绑定 7/9 → 9/9，六件套覆盖率 95.6% → **100%**

## 六、这一轮的三个方法收获

### 6.1 「数据使用率审计」应该成为常规动作

写个脚本对比「后端返回什么」和「前端用了什么」，
能立刻发现「数据在但没展示」的浪费。

这次一审计就找出 6 块完全没用的数据。

### 6.2 测试与错误代码同构 = 测不出来

白屏 bug 之所以测试没抓到，是因为**测试用了和错误代码一样的调用方式**。

对策：加**静态检查**（扫描源码模式），而不是只依赖运行时测试。
静态检查能抓「写法错误」，运行时测试能抓「行为错误」，两者互补。

### 6.3 同一件事被多处实现时，判据必然漂移

会话绑定的判据在两个工具里各写了一遍，结果一个太严一个太松，
都是错的，但错的方向相反。

**判据必须单一来源**。现在两处都改成同一套逻辑。
