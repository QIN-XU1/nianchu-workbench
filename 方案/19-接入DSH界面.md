## 1. 做了什么

把 sea 的体检结果搬进 DSH 界面：

```
sea.mjs（命令行）
   ↓ 宿主插件调用
plugins/sea-workbench（DSH bundle）
   ├── index.js   → 跑 sea.mjs，解析结果，注册 HTTP 路由
   └── client.js  → 界面状态条，fetch 那个路由
```

**用户看到的样子**（对话输入框上方的状态条）：

```
● 现在没事   5 场景  门禁 20/20  下限 4/4  认证 5/5              ⟳
```

有事时：

```
● 有事待办   5 场景  门禁 20/20  下限 4/4  认证 5/5  资产 1 问题  ⟳
```

不可信时：

```
● 检查不可信  ...
```

颜色语义：绿（没事）/ 黄（有事）/ 红（不可信/配置错）/ 灰（无场景）。

## 2. 安装与验证（全部实测）

### 2.1 安装

```
plugin_manager install_bundle → application: "applied"
```

第一次失败，诊断很有价值：
```
sea-workbench (@local/sea-workbench): Error:
  cannot set property "seaWorkbench" without provide
```

**原因**：Cordis 不允许直接往 `ctx` 上塞自定义属性，必须先声明 `provide`。
**修法**：本插件只需要 HTTP 路由，不需要对外暴露服务，所以去掉 `ctx.seaWorkbench = ...`。

### 2.2 三条独立验证

| # | 验证 | 结果 |
|---|---|---|
1 | 插件登记在 profile | ✅ `installed: true, enabled: true`，rowId `sea-workbench` |
2 | Host 路由可达 | ✅ `GET http://127.0.0.1:42152/sea-workbench/pulse` → **HTTP 200** |
3 | 数据正确 | ✅ `kind=idle scenes=5 gate=20/20 cert=5/5 asset=0` |

**三条全部通过**——这不是"文件写好了"，是**运行时真的在跑**。

## 3. 一个必须承认的验证边界

| 能证明的 | 不能证明的 |
|---|---|
Host 路由返回正确 JSON | ❌ **界面是否真的渲染了状态条** |
插件已 enabled | ❌ **用户是否看得见** |
数据解析正确 | ❌ **Client 的 slot 注册是否插到了正确位置** |

**Client side 需要页面连接才能验证**（`Slots.listSubTree` 需要活动页面），本会话没有可用的 Client Inspect Provider。

> **诚实标注**：Host 半边已实测通过；Client 半边只验证了"文件已随 bundle 下发"，未验证"界面渲染"。需要一次真实的页面刷新确认。
