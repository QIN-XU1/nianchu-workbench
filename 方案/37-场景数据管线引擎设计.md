# 37 · 场景数据管线引擎（Sceneflow）

> 用户要的是一个"神"：**场景不是孤岛，产物能在场景之间流转**。
> 例子：调研场景搜到竞品 → 自动汇入竞品拆解场景 → 拆完传给架构分析场景 →
> 逆向场景的产出也能汇入架构分析。

---

## 一、现有机制的根本缺陷（实测）

### 1.1 场景之间只有"留言板"

`工具/发消息.mjs` 的全部能力：

```
给另一个场景的 场景私有记忆.md 追加一行
+ 在 _跨场景通知.md 追加一条
```

**这只是贴纸条，不是传数据。** 产物不能结构化流转，下游场景不知道上游产出了什么。

### 1.2 没有"产物"概念

现有场景 json 只有 `panels`（界面），没有：
- 这个场景**产出什么**
- 这个场景**需要什么**
- 产出的**格式**
- 产出的**接收方**

### 1.3 实测：4 个场景的 AI 面板全是空的

```
bilibili / bv-ai    (harness): 无 sessionId
command / cmd-chat  (harness): 无 sessionId
pc-cleanup / pc-ai  (harness): 无 sessionId
self-review / sr-ai (harness): 无 sessionId
```

`_场景身份索引.md` 里写着 `__待填__` —— **从未被填过**。

### 1.4 我之前的误判（诚实说明）

我说"29 个失效路径"，实测核查：
- `索引.json` 8 条 → **全部有效**（我把基准路径搞错了，误报）
- `renderers.js` 资源引用 → 6 个占位符（`<你的GitHub账号>` 之类，是模板设计）
- 场景 json 路径 → 有效

**真正"虚"的不是路径，是场景之间的连接。**

## 二、借鉴的成熟架构

### 2.1 Airflow 的 DAG 模型

来源：[Airflow DAG 文档](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html)

| 概念 | 含义 | 我们借用什么 |
|---|---|---|
**DAG** | 有向无环图 | 场景间的流转不能成环 |
**Task** | 离散工作单元 | = 一个场景的一次产出 |
**upstream/downstream** | 上下游依赖 | 调研 → 拆解 → 架构 |
**XCom** | 任务间传递的小数据 | = 场景间传递的产物引用 |
**trigger_rule** | 触发规则（all_success/all_done） | 上游没完成能不能跑 |
**retry** | 重试次数 | 场景失败可重试 |

### 2.2 Temporal 的 Event History

来源：[Temporal Workflow](https://docs.temporal.io/workflows)

> The Event History is **the source of truth** for everything that happens in the Workflow.

**关键思想**：不存"当前状态"，存"事件序列"，可以从头重放。

**我们借用**：每次场景产出都记一条事件，可以重建整条链路。

## 三、Sceneflow 设计

### 3.1 三个核心概念

```
场景（Scene）    = 一个工作单元，有自己的记忆和面板
产物（Artifact） = 场景的产出，有 id / 类型 / 内容 / 来源
管线（Flow）     = 场景之间的流转关系，DAG
```

### 3.2 产物模型

```json
{
  "id": "artifact-<uuid>",
  "name": "竞品清单",
  "type": "competitor-list | architecture | reverse-report | research | design",
  "fromScene": "research",
  "toScenes": ["competitor-analyze", "arch-review"],
  "path": "产物/竞品清单-2026-11-07.md",
  "summary": "...",
  "createdAt": "...",
  "status": "ready | consumed | stale",
  "consumedBy": []
}
```

### 3.3 管线模型

```json
{
  "id": "build-software",
  "name": "造一个软件",
  "nodes": [
    { "scene": "research",          "role": "调研：搜架构/竞品/资料" },
    { "scene": "competitor-analyze","role": "拆解竞品：功能矩阵/技术栈" },
    { "scene": "reverse-eng",       "role": "逆向成熟作品：实现细节" },
    { "scene": "arch-review",       "role": "架构梳理：汇总结论" }
  ],
  "edges": [
    { "from": "research", "to": "competitor-analyze", "artifact": "competitor-list" },
    { "from": "research", "to": "reverse-eng",        "artifact": "candidate-repos" },
    { "from": "competitor-analyze", "to": "arch-review", "artifact": "feature-matrix" },
    { "from": "reverse-eng",        "to": "arch-review", "artifact": "impl-details" }
  ]
}
```

### 3.4 与项目现有机制的对接（不推翻，只增强）

| 现有 | 增强 |
|---|---|
`场景记忆/<场景>/场景私有记忆.md` | 保留，加"接收产物"段 |
`_共享记忆/_跨场景通知.md` | 保留，作为通知 |
`工具/发消息.mjs` | 保留，作为轻量通知 |
**新增** `产物/` 目录 + `flow.mjs` | 结构化产物流转 |

## 四、实现清单

### 4.1 核心引擎（零依赖）

| 文件 | 作用 |
|---|---|
`workbench/工具/sceneflow.mjs` | 产物发布 / 领取 / 查询 / 管线定义 |
`workbench/工具/scene-registry.mjs` | 场景注册表（含 in/out 契约） |
`workbench/scenes/*.json` | 场景契约（产出什么、需要什么） |
`workbench/pipelines/*.json` | 管线定义（DAG） |

### 4.2 关键设计原则

1. **产物是不可变的**：一旦发布就带时间戳，要改就发新版
2. **产物是文件**：不存数据库，就是 `产物/<名字>-<时间>.md`
3. **领取要留痕**：下游说"我用了这个"，记 `consumedBy`
4. **失败不阻断**：一个场景失败，管线标记而不是全挂
5. **可重放**：事件日志能重建整条链路

---

## 五、验证方式

必须能证明"产物真的流转了"：

1. 调研场景发布产物 → 文件真的出现
2. 拆解场景能看到"待领取"
3. 领取后状态变成 consumed
4. 下游能读到内容
5. 整条链路的事件日志完整

---

## 六、一句话

> **现有的"跨场景协作"只是留言板；Sceneflow 要把它变成真正的数据管线：**
> **每个场景产出结构化产物，下游能领取、能追溯、能重放。**
> **这才是"神"的骨架 —— 不是一个万能场景，而是让任意场景能串成一条链。**
