## 二、我实际做了什么（不是文档，是能跑的）

### 2.1 git 基础设施

### 2.2 变异测试框架（工具/变异测试.mjs）

**核心机制：**
```
① 复制基线到临时目录（mkdtemp）
② 注入一个具体错误
③ 跑检查脚本，指向临时目录
④ 断言：exit 非 0 且输出含期望文本
⑤ 清理临时目录
⑥ 元测试：原始数据 SHA256 未变（证明没污染）
```

**框架自测 5/5 通过：**
```
OK  原始数据应 PASS
OK  变异1: count 改成 0 → 必须 FAIL
OK  变异2: 删掉 count 字段 → 必须 FAIL
OK  变异3: 文件损坏 → 必须 FAIL
OK  变异4: 期望"应通过"但实际失败 → 框架必须报 XX
```

**第 5 个用例特别重要**：它证明框架**不会盲信自己的断言**。

### 2.3 记忆哨兵（工具/记忆哨兵.mjs）

**5 个不变量：**
```
INV-1  注入层 AGENTS.md ≤ 2048 字节
INV-2  每个场景 §〇 交接 ≤ 4096 字节
INV-3  每个场景私有记忆 ≤ 25600 字节
INV-4  §〇 里只能有 1 份"上次交接"（多份 = 没覆盖写）
INV-5  §〇 四问齐全
```

**变异测试 8/8 通过：**
```
OK  原始基线应 PASS                                    exit=0
OK  INV-1 灌到 3000 字节 → 必须 FAIL                   exit=1
OK  INV-1 刚好 2048 字节 → 必须 PASS（边界）            exit=0  ← 关键
OK  INV-2 §〇 灌到 6000 字节 → 必须 FAIL               exit=1
OK  INV-3 主文件 30000 字节 → 必须 FAIL                exit=1
OK  INV-4 塞两份"上次交接" → 必须 FAIL                 exit=1
OK  INV-5 删掉小节 → 必须 FAIL                         exit=1
OK  整个 §〇 段被删 → 必须 FAIL                        exit=1

反例验证：框架正确识别错误期望 ✓
```

**边界测试（2048 刚好 PASS）证明判据不是"随便报"。**

### 2.4 身份哨兵（工具/身份哨兵.mjs）

**7 个不变量：**
```
INV-1  有 AI 面板的场景必须在索引里有行
INV-2  索引里的场景必须存在
INV-3  sessionId 格式必须合法
INV-4  sessionId 不能是占位符（0000…/xxxx…）
INV-5  定位卡必须真实存在
INV-6  场景 json 的 id = 文件名
INV-7  ★ sessionId 必须在引擎会话库里真实存在
```

**INV-7 是核心**：原项目警告"格式合法 ≠ 指向真实会话"。

**变异测试 9/9 通过。**

### 2.5 身份索引（工具/身份索引.mjs + 数据）

**从真实数据生成，不编造：**
```
共 11 行
· 10 个场景有真实 sessionId（从场景 json 读取）
· hub 无 AI 面板（对话由 shell.sideEl 固定挂载）
· 全部通过身份哨兵

实测：引擎会话库 167 个真实会话，场景指向的 10 个全部命中。
```

**这里我一度判断错误**：以为 sessionId 指向不存在的会话。
原因是扫描逻辑只处理了一种命名格式（`session-xxx`），
而引擎同时用 `session-xxx` 和裸 `uuid` 两种。
修正后确认：**10 个 sessionId 全部真实存在**。

## 三、过程中抓到的两个真 bug（都是变异测试抓到的）

### bug 1：PowerShell BOM 导致 JSON 解析失败

```
现象：手工造的测试 JSON 全部"解析失败"
根因：Set-Content -Encoding UTF8 写 BOM (EF BB BF)
     JSON.parse 对 BOM 敏感
修复：所有 readJson 剥离 BOM
```

**这个坑 AGENTS.md 里其实写过**（"不要用 PowerShell 往返读写文本"），
但我自己又踩了一次。

### bug 2：变异测试形同虚设（最危险）

```
现象：7 个变异用例全部"未捕获"
根因：测试用例的 env 指向原始目录，不是临时目录
     mutate 改了 tmp → check 读 BASE → 永远 PASS
     
讽刺：这是变异测试框架**自己**发现的
     （框架报 XX："期望失败但 exit=0"）

修复：env 支持 {{DIR}} 占位符
```

**这个 bug 极其危险 —— 它让"变异测试通过"变成假象。
如果没有反例验证机制，我会以为检查有效。**

**这也印证了原项目那句话：**
> **"没有'会失败的检查'的规矩 = 一句口号。"**

我一开始的测试用例，就是一个"永远通过"的检查。

## 六、方法论沉淀（可复用的）

### 6.1 开发顺序（本次验证有效）

```
① 写 BRIEF：声明不变量（可判定，不是形容词）
② 写 check：能 exit 非 0，输出差异集合
③ 写 selftest：造变异，证明 check 会失败
④ 加反例：故意写错期望，证明框架不盲信
⑤ 跑真实数据：确认不误报
⑥ 挂节奏：每次改动后跑
```

### 6.2 每条机制必须回答的五个问题

```
① 违规长什么样？        （可判定）
② 判据的唯一出处？      （两处 = 早晚打架）
③ 哪个检查会 exit 非 0？ （能说出差异集合）
④ 它的反例是什么？      （必须故意验证）
⑤ 挂在什么节奏上？      （手动跑 = 没跑）
```

### 6.3 最容易自欺的地方

```
"检查通过了" ≠ "检查有效"
  → 必须：造错误，证明它会报

"变异测试通过" ≠ "测试有效"
  → 必须：加反例，证明框架不盲信（本次就踩了）
```
