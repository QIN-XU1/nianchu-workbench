## 0. 核心命题：我们要做的不是"万能 Agent"

### 0.1 重新定义问题

用户的原话是"适应所有场景的工作或是对话"。这句话有两种解法，差别是根本性的：

| 解法 | 形态 | 为什么走不通 / 为什么该走 |
|---|---|---|
| **A. 万能 Agent** | 一个模型 + 一堆工具 + 超长提示词，声称什么都会 | ❌ 上下文会爆；验证回路无法闭合（见 01 §5.4）；能力越宽越不精；一旦出错无法定位是哪个能力坏了 |
| **B. 场景生长机制** | 一套内核 + 场景契约，**每个场景长出一个专职 Agent**，共用规则与底座 | ✅ 三个独立来源（乱雨家、Grok Bot、以及 Super-agent 的 Source 抽象）都收敛到这个方向 |

**SEA 选 B。** 因此：

> **SEA 的"通用"，指的不是一个 Agent 会所有事，而是"新增一类场景 = 写一份契约，零代码改动"。**

这是本方案和所有"通用 Agent 框架"的分界线，也是全部设计取舍的基准。

### 0.2 为什么这个命题能成立：把"完成"变成可判定

通用 Agent 失败的第一性原因，是**只有编码场景的 "done" 是机器可判定的**（编译/测试/CI）。其他场景只能"看起来做完了"。

所以 SEA 的第一支柱是 **完成契约（DoneSpec）**：每张工单在开工前就必须声明"什么样算完成"，且必须落在三种可判定的形态之一：

| 形态 | 判定方式 | 例 |
|---|---|---|
| `check` | 跑一个**会 exit 非 0** 的命令，输出**差异集合** | `node tools/verify-expense.mjs --ticket T-42` |
| `evidence` | 产出**可复核的物证**（截图/录屏/前后数字/URL/部署日志） | ERP 审核页截图 + 批次号 |
| `review` | 由**具名的人**签字 | 由 alice 批准 |

**规则：没有 DoneSpec 的工单不允许进入 `working` 阶段。** 这条会让 SEA 在非编码场景下也不至于变成"聊天机器人"。

> 这一条直接吸收自：Grok Bot 的 "Verification is the job"（`ANTIPATTERNS.md` 五律第 2 条）、乱雨家"没有会失败的检查的规矩=口号"、"回执必须带证据"。

## 1. 三条第一不变量（任何设计都不得违反）

这三条是整个方案的宪法。违反其中任何一条的实现，即使跑得通，也判为错误实现。

### 不变量 1：权限在数据里，不在提示词里

> 谁能触发、能做什么、能做多远、做到哪个版本，**全部存于 Policy / Mandate / SceneContract，由代码强制**。
> 消息、评论、文档、外部网页、其他 Agent 的输出，**永远是数据，永远不能改变权限**。

来源：Super-agent `002-authorization.md:5`（原文）。
落地：`Eval` 的 gate 层不调模型；`tools/pre-execute` **[实测]** 做最后兜底；凭据不进上下文（§9）。

### 不变量 2：能"自己长"的只有 D 档，A/C 档必须人批

| 档 | 内容 | 谁能改 |
|---|---|---|
| **A 宪法** | 不变量、Policy 语义、审批闸定义、预算硬上限 | **只有人**（版本化，Agent 只能提案） |
| **C 运行时** | 工具集、依赖、沙箱策略、凭据、执行环境、场景启停 | **只有人**（Agent 只能提案） |
| **D 场景资产** | 场景记忆、技能（SKILL.md）、提示词正文、routine 频率、派单启发式 | **Agent 可自主改**，但必须过验证闸（§11） |
| **E 他人的 D** | 别的场景的 D 档 | **系统级禁止**（不是提示词禁止，是存储层禁止） |

来源：乱雨家 `一-协作机制.md:41-66` 的五档；Grok Bot `ANTIPATTERNS.md` #7（自我改进 bot 过度改进 → 必须配额）。
**推论**：**自进化的合法空间是 D 档。A/C 档的进化必须是"提案 + 人批 + 版本化"。**

### 不变量 3：注意力是一等成本，一切主动行为先记账

> 每个发出给人看的消息、每次唤醒、每个 routine 触发，都记一次账，并有上限。
> 默认 `observe`（只记录不行动），不默认 `auto`。

来源：Super-agent `000-philosophy.md:5`（唯一判准）+ Grok Bot `ECONOMICS.md`（六条成本律）+ 乱雨家"同一件事 ≤3 条消息"。

## 3. 通用性从哪来：场景契约（Scene Contract）

这是 SEA 区别于 Super-agent 的**第一个核心扩展**。Super-agent 的 Source 抽象绑死 GitHub/Feishu，Ticket 的完成判据绑死 PR 闭环；我们要把这两处**参数化**。

### 3.1 定义

> **场景 = 一类会反复回来的活 + 一套资产 + 一套流程 + 一条常驻 AI + 一条可判定的完成契约 + 一个授权上限。**

新增一个场景 = 写一份 `scene.yaml`。**不改代码，不重启宿主**（`agentPresets.register` 可运行时注册 **[实测]**）。

### 3.2 契约 Schema（v1）

```yaml
# scenes/expense-audit/scene.yaml
scene: expense-audit                 # 全局唯一 id
name: 费用审核                        # 人类可读
owner: alice                         # 具名负责人（用于 review 与 A 档提案）
version: 3                           # 契约版本，改动 +1，旧版留档
enabled: true

identity:
  role: 你是费用审核专员，负责审核报销单的合规性。      # 定位卡正文（≤2 KB）
  not_responsible:                                    # 明确不碰什么（必填，≥1）
    - 代码与仓库
    - 付款执行
    - 采购申请
  trigger_words: [报销, 发票, 差旅单]

sources:                             # 事件从哪来（可多条）
  - kind: mail
    config: { mailbox: ap@example.com, filter: "subject ~ 报销" }
  - kind: schedule                   # 定时本身就是一个 Source（见 §4.3）
    config: { cron: "0 9 * * 1-5", name: daily-sweep }
  - kind: fs-watch
    config: { path: D:/work/expense/inbox/, debounce_ms: 2000 }

assets:
  roots:      [ D:/work/expense/ ]
  forbidden:  [ D:/work/code/, D:/secrets/ ]          # 硬边界，越界由存储层拒绝

skills:        [ expense-policy, invoice-parse, erp-query ]
tools:
  families:    [ fs, jobs, web, mcp:erp ]
  denied:      [ bash, computer-use ]                 # 显式拒绝清单

done_when:                                           # ★ 完成契约（必填，见 §3.3）
  all_of:
    - check:    { cmd: "node tools/verify-expense.mjs --ticket {ticket_id}",
                  expect_exit: 0, report: diff-set }
    - evidence: { kind: artifact, accept: [screenshot, json-report] }
  review_by: alice                                   # 可空；空则 all_of 满足即完成

autonomy:
  ceiling: draft          # investigate | draft | autopilot | full（Grok Bot ladder）
  proactive: observe      # off | observe | auto（Super-agent accept mode）
  merge_or_publish: never # 对外不可逆动作的上限

memory:
  handoff_kb: 4           # §〇 交接上限
  contract_kb: 8          # 项目记忆上限
  retention_days: 180

budget:
  per_ticket_tokens: 60000
  per_day_tokens: 2000000
  max_concurrent_workers: 2
  routines:
    - { id: daily-sweep, max_runs_per_day: 1 }
```

### 3.3 DoneSpec 的三形态与"反例要求"

| 形态 | 字段 | 强制要求 |
|---|---|---|
| `check` | `cmd`（可含 `{ticket_id}` 等占位）、`expect_exit`、`report`（必须 `diff-set`） | 命令必须能在**反例下 exit 非 0**；SEA 会用"变异测试"验证这条（见 03 §5.2） |
| `evidence` | `kind`、`accept`（物证类型白名单） | 物证必须可复核（有 URL / 有哈希 / 有前后对比） |
| `review` | `reviewer`（具名） | 只能是人，不能是另一个 Agent |

**为什么必须 `diff-set`**：布尔输出无法定位退化。乱雨家原文（`把规矩变成机制.md:43-45`）：
> ❌「体检通过」 ✅「⛔ 3 项：未登记 2（a.md / b.md）· 死条目 1（c.md）」

### 3.4 三个"通用性"难题的解法

| 难题 | 解法 |
|---|---|
| **事件该进哪个场景？** | ① Source 在契约里声明 → 确定性绑定（快路径）；② 未绑定的进 `Global Router` 判定（慢路径）；③ 人主动发起的走默认场景或显式指定 |
| **完成怎么判定？** | DoneSpec 三形态。**`check` 优先**，`evidence` 次之，`review` 兜底 |
| **场景之间怎么协作？** | 场景间**只允许三件事**：`通知`（不唤醒）、`派单`（唤醒，必须回执）、`请求裁决`（交 Router）。**禁止直接读写对方记忆**（E 档，见 §1 不变量 2） |

### 3.5 契约的版本与生效

- 契约版本号参与 **Policy version** 计算（同 Super-agent）：变更 → 作废运行中的 Eval 并重排 Trigger，向受影响的 live Ticket 发 `contract-changed` Input，**但不立即撤销 Mandate**
- 契约变更的**来源**只有三种：`panel`（人）、`proposal`（Agent 走进化面，须批准）、`sync`（外部源）
- **`sync` 与 `proposal` 不能改 `autonomy` / `budget` 的硬上限 / `tools.denied`**（这三样是 A/C 档）

## 4. 领域内核（L2）：继承 Super-agent 并最小扩展

### 4.1 实体与关系（保留原模型）

```
 Source ──Trigger──▶ Thread ──┬── 订阅扇出 ─────▶ Ticket ──Assignment──▶ Executor
                              └── 批量 ─▶ Eval ──▶ Decision ──accept+M...▶ Ticket
 Ticket ──▶ DoneSpec ──▶ Evidence
 Source ◀── Channel（写回）
```

**逐条继承的规则**（详见 `01` §1.3，此处只列 SEA 的**增量**）：

| 实体 | Super-agent 原规则 | SEA 增量 |
|---|---|---|
| **Source** | 持读位置与自身 bot 身份；定义"什么算事件"；进门前丢弃自身消息与范围外事件；**重启不回放** | 新增 kind：`schedule` / `fs-watch` / `metric-alert` / `agent-peer` / `manual`。**每种 kind 必须声明自己的 `done_capability`**（能否提供 check/evidence） |
| **Trigger** | 不可变；接受两次只产一个 Ticket | 增加 `seed`（可被进化面复用来"重放历史事件"做回归测试） |
| **Thread** | 时间序；同一时刻最多一个 Eval；可挂多 Ticket | 无 |
| **Policy** | 版本化规则 + 各 Source 部分 | **并入 SceneContract 的授权段**；Policy version = 场景契约版本 + 各 Source 部分 + accept mode |
| **Eval** | 无状态：batch + Thread 快照 + 该 Thread 全部 Ticket + 当前 Policy | 无 |
| **Mandate** | accept 授予的：版本/范围/强度/命中规则/发送者身份；不可变；只有人 stop 撤回 | 增加 `done_spec_snapshot`（授权时锁定完成契约，防止中途被改宽） |
| **Ticket** | 只有 Eval 能创建；自带状态，不跟随 Executor | 增加 `stage` 中的 `working/verifying`（新增阶段，见 §4.2）；增加 `done_spec` |
| **Assignment** | Ticket ↔ Executor 实例绑定；独立生命周期 | 无 |
| **Subscription** | 多对多，由 Thread 持有；扇出不查发送者；**上下文订阅不授任何权** | 无（这条设计极好，原样保留） |

### 4.2 Ticket 阶段机（在 Super-agent 的 7 行阶段表上**加 1 行**）

Super-agent 的规则是"**从上往下读，第一个匹配的行赢**"（`003-execution.md:7-17`）。SEA 版共 **8 行**（原 7 行 + 新增 1 行）：

| # | 阶段 | 条件 | 面板显示 |
|---|---|---|---|
| 1 | `person/delivery` | Input 投递失败，重试中 | 投递未达 |
| 2 | `person/answer` | 有未回答的提问 | 等待回答 |
| 3 | `person/review` | 最新报告 `ready` 且 DoneSpec 需 review | **等待验收** |
| 4 | `person/blocked`·`person/failed` | 报告 blocked/failed 且此后无人发消息 | 受阻 · 失败 |
| 5 | `working/queued` | 无 Assignment 或 pending | 排队中 |
| 6 | **`working/verifying`** ★ | Assignment 已报 `ready`，正在跑 DoneSpec 的 `check`/收集 `evidence` | **核验中** |
| 7 | `idle` | 最新报告 `waiting`，或 Assignment 已结束 | 等待触发 |
| 8 | `working` | 其余 | 执行中 |

**新增第 6 行的理由**：`ready` 是**模型的自我判断**；DoneSpec 是**机器的判断**。两者之间必须有一个可观测的状态，否则"假完成"会直接落到人面前，把验收费转嫁给人类——这恰恰违反不变量 3。

### 4.3 "等待条件本身就是一个 Source"（关键设计保留）

Super-agent 在 Rejected concepts 里拒绝了"Eval 自己调度延迟 Trigger"，理由：

> `A condition that needs waiting is an ordinary Source, so Eval never depends back on Sources.`（`001-domain.md:50`）

**这条必须保留**。它带来三个好处：
1. Eval 永远不需要睡眠/定时器 → 无状态、可重放
2. "N 小时没人接单就提醒"这类条件有唯一归属（`metric-alert` Source）
3. 所有"等待"都能被 Watchdog 独立审计

### 4.4 内核新增：三个账本

Super-agent 有 Outbox 与 Effects，但没有"注意力账簿"和"证据账簿"。SEA 新增（都在 L2）：

**① Attention Ledger（注意力账簿）**
每次对外消息/唤醒/routine 触发记一行：`{id, kind: notice|dispatch|dispatch_wake|routine|card, target, target_scene, cost_class, awaiting: bool, outcome: acknowledged|acted|ignored|expired, ts}`

用途：
- 计算**注意力税**（§10.2 的核心指标）
- 识别"发了 36 条只回 8 条"这类浪费（乱雨家真实事故）
- 支撑 `observe` 模式下的"would accept"记录

**② Evidence Store（证据账簿）**
`{evidence_id, ticket_id, kind, hash, source_uri, captured_at, verified_by, diff_set?}`
- 物证**不可变**
- 每个 Ticket 结束时必须有 ≥1 条（除非 `dropped` 且规则允许无物证）

**③ Provenance Graph（溯源图）**
Super-agent 用 ID 图做链式召回；SEA 把它升级成**双用途**：
- 召回：`trigger → thread → ticket → assignment → evidence → artifact`
- **进化免责**：某条 D 档改动导致了问题 → 能反查"哪次进化、依据哪个失败样本、谁批的"

数据结构：`{node_id, node_type, edges: [{to, rel}], created_at, provenance_of?}`

> 这一条直接服务 §11 的可回滚，也把 Super-agent 的"链式召回"从纯检索升级为**责任链**。

## 5. 编排面（L3）：三层而非两层

### 5.1 为什么要第三层

Super-agent 是 **2 层**（Router → Worker），因为它是**单场景**（一个 GitHub 仓库的编码协作）。SEA 是**多场景**，直接套 2 层会出两个问题：

1. **Router 上下文污染**：N 个场景的定位卡、记忆、规则全进 Router，Router 就不再"轻量"。而 Router 一旦变重，它的批处理优势（文章 7.2：单决定分摊推理时间从 6.4s 降到 1.6s）就消失了。
2. **场景记忆无处安放**：场景记忆（§〇 交接、项目记忆）必须是"本场景常驻"，放进全局 Router 就变成全局垃圾。

因此 SEA 用三层：

```
      ┌──────────────────────────────────────────────┐
      │  Global Router（全局路由，常驻，轻量）        │
      │  · 对外人类交互的唯一出口                     │
      │  · 判定"这是哪个场景的事"                      │
      │  · 跨场景协调、投递、裁决请求                  │
      │  · 不做技术决策；不配 Bash；路由备注 ≤30 词    │
      └───────────────┬──────────────────────────────┘
                      │ 派单（一次调用可含多条）
        ┌─────────────┴─────────────┬──────────────────────┐
        ▼                           ▼                      ▼
┌──────────────────┐      ┌──────────────────┐    ┌──────────────────┐
│ Scene Session A  │      │ Scene Session B  │    │ Scene Session N  │
│ 常驻·懒启动      │      │                  │    │                  │
│ · 持有本场景记忆  │      │                  │    │                  │
│ · 本场景内分派    │      │                  │    │                  │
│ · 回执汇聚        │      │                  │    │                  │
│ · 不执行具体任务  │      │                  │    │                  │
└────────┬─────────┘      └──────────────────┘    └──────────────────┘
         │ 一事一 Worker
    ┌────┴────┬─────────┐
    ▼         ▼         ▼
┌────────┐┌────────┐┌────────┐
│Worker-1││Worker-2││Worker-3│   ← 并发生效区
│独立目录 ││独立目录 ││独立目录 │     上下文隔离
│全工具   ││全工具   ││全工具   │     不与人类直连
└────────┘└────────┘└────────┘
```

### 5.2 三层的职责硬边界

| 角色 | 必须 | 禁止 | 模型档位 |
|---|---|---|
| **Global Router** | 人类交互出口；场景判定；跨场景裁决；投递 | 执行具体任务；写文件；跑命令；保存场景记忆 | **轻量**（文章原文："Router 层的任务常常没有想象中复杂，使用较轻量的模型往往就能兼顾速度与效果"） |
| **Scene Session** | 场景记忆读写；本场景内工单派发与合并；回执汇总；场景内 routine 调度 | 跨场景直接指挥；改别的场景记忆；执行具体任务 | 中 |
| **Worker Session** | 具体执行；产出证据；报告；交回 | **与人类直接交互**（一律经 Scene→Router 统一出口）；改场景契约 | **最强**（"Worker Session 直接决定任务结果与代码质量"） |

> **Worker 不与人类直连**这一条是 Super-agent 的原文设计（`002`/`003`）。它的收益：避免多个会话各自回复造成混乱，并让"信道教"集中在一处可审计。

### 5.3 懒启动与降级（控制成本）

常驻 N 个 Scene Session 很贵。SEA 用三条规则控制：

1. **懒启动**：Scene Session 只在**本场景有 open ticket 或待派单**时创建；空闲超过 `idle_ttl` 后挂起（保留持久状态，释放内存）
2. **降级**：单场景、低风险、`ceiling: investigate` 的场景，允许 **Router 兼任 Scene**（省一层）
3. **升格**：场景 open ticket 数 > `promote_threshold`（默认 3）时，强制创建专用 Scene Session

### 5.4 Worker 槽位（继承 Super-agent 的三条精髓）

| 规则 | 原文依据 | SEA 落地 |
|---|---|---|
| **人的消息可多用一个 slot** | `003-execution.md:59`："with one extra slot for a person's message or a status request" | 保留。保证新工作不挡人 |
| **wake 优先于 launch** | `003-execution.md:59`："Such a wake can use the extra slot when normal slots are full, and takes the next free slot before a new launch" | 保留 |
| **后台工作 30 分钟上限** | `003-execution.md:35` | 保留；**但叠加 VCP 的模型自报心跳**（§6.4） |

### 5.5 事件路由：Fast/Slow Path（保留）

| 路径 | 机制 | 落地方式 |
|---|---|---|
| **Fast Path（确定性）** | Source 已在 SceneContract 中声明 → 直接投递给对应 Scene 的 Worker，**不经 Router** | 我们自己的路由代码在交付前决定"投不投"，不投就不注入会话 |
| **Slow Path（语义）** | 未绑定的事件 → 投给 Global Router，由它判定归属或忽略 | `agent/inbox/inserted` **[实测]**（emit，可观测）→ 我们的策略决定投递 |

> **注意**：`agent/pre-step` **[实测]** 是 waterfall（"Reject a proposed step or replace the messages that enter it"），但它发生在模型已运行之后，因此它是**兜底护栏**（例如禁 `sleep`），**不是快路径**。快路径必须在**投递之前**。
> 这个区分很重要——文章说的"程序层策略在调用模型之前滤除噪音"，在 DSH 上对应的就是"**不要往 inbox 里投**"，而不是"进了 inbox 再拦"。

### 5.6 静默规则（可被代码检查的部分）

| 场景 | 行为 |
|---|---|
| 处理中 | **不说话**（不发进度） |
| 完成且需验收 | 一条消息 + 物证链接 |
| 需要决策 | **一条消息 + 一个结构化问题**（不允许把问题埋在报告里——Super-agent 明确拒绝"从自由文本推断在等人"，`001-domain.md:60`） |
| 无法完成 | 一条消息 + 原因 + 建议 |
| `observe` 模式的"会做但没做" | **静默**，只进面板 |

所有主动消息**必须**过 §10 的预算闸与三上限（同一件事 ≤3 条、单条 ≤200 字、末行 `【结束】`）。

## 6. 上下文面（L1）：把两个真发明合成一个

### 6.1 合成公式

> **Super-agent 的 Inline & Spill 管"信息放多少"；VCP 的四类 user 数组管"信息活多久"。**
> SEA 的上下文面 = 两者相乘。

### 6.2 七条上下文通道（Context Channels）

每轮装配的 system-prompt 按固定顺序（顺序稳定 → prompt cache 命中率最高）：

| # | 通道 | 内容 | 预算 | 来源映射 |
|---|---|---|---|---|
| 1 | **宪法** | 三条不变量 + 本场景的 A 档铁律 | ≤300 字 | 乱雨家"注入层必须极短" |
| 2 | **身份** | 我是谁（Router/Scene/Worker）、哪个场景、`not_responsible` | ≤600 字 | **系统注入**（不靠模型查表，纠正乱雨家 L-1 缺陷） |
| 3 | **契约** | 本场景 DoneSpec、autonomy 档位、预算余量 | ≤800 字 | 动态生成（每次请求重算，同 Super-agent policy section 置于末尾） |
| 4 | **工作集** | 当前 Thread/Ticket 的近邻内容（**Inline**） | ≤40% 窗口 | Super-agent Inline & Spill |
| 5 | **环境感** | 时间、时区、设备在线态、未读计数、健康告警摘要 | ≤400 字 | VCP 静态插件思想 |
| 6 | **状态台账** | 进行中任务/后台作业/等待中的事，**只记时间戳+状态** | ≤300 字 | VCP 摘要 user 数组 |
| 7 | **通知栏** | 新到的系统通知、工具进度、外部消息 | ≤600 字 | VCP 通知栏 |
| 8 | **召回** | **不在 prompt 里**；由 `recall(id)` 工具按需拉取 | 0 | Super-agent 链式召回 |

> **通道 8 是故意缺席的**：`Inline & Spill` 的纪律是"从最少信息开始，需要再拉"（文章 3.3）。召回不该预注入。

### 6.3 工具结果的"生命周期标签"（把 VCP 真发明翻译成 DSH 原语）

VCP 的四类数组是它接管请求构造的产物，DSH 做不了。**但 DSH 有 `tools/post-execute` waterfall [实测]**（"Accept, replace, enrich, or block a normalized dispatch result"）。SEA 用它给每个工具结果打标签：

| 标签 | 处置 | 对应 VCP |
|---|---|---|
| `result` | 保留在历史（进 compaction 视野） | 同步数组 |
| `progress` | 只进**状态台账**（通道 6），主体**丢弃** | 异步数组 |
| `status` | 只进状态台账，一行时间戳+状态 | 摘要数组 |
| `notice` | 进**通知栏**（通道 7），不进历史 | 通知栏数组 |

**收益**：直接消灭 VCP 点名的那个幻觉源——"把工具进度误当成已完成的事实"（`VCP.md:91`）。

**实现约束（诚实标注）**：DSH 的 `tools/post-execute` 能替换/丰富结果，但**不能让结果不入历史**。所以 `progress` 的正确落法是：**工具本身不返回长内容**（长内容 `spill` 出去，只回 `spill_id` + 一行摘要），由上下文装配器决定下次装多少。这是 **`spill`（`abstract spill storage`，`saveText`）[实测]** 与 post-execute 的组合，不是纯 VCP 做法。

### 6.4 异步执行与心跳（两源合成）

| 机制 | 来源 | SEA 做法 |
|---|---|---|
| 耗时命令转后台 | Super-agent（shell `timeoutMs: 5000`，job wait `5000`） | Worker preset 直接照抄这两个数 |
| 模型自报下次唤醒 | VCP `[[NextHeartbeat::N]]` | **采纳，但加三重上限**：单次 N ≤ `max_heartbeat_s`（默认 300）、累计心跳 ≤ `max_heartbeats`（默认 40）、总时长 ≤ `max_ticket_wall`（默认 2 h） |
| 外部可覆盖 | ——（我们新增） | Watchdog 检测到"心跳期间无实质产出"可**提前唤醒或终止**（§8.3） |
| 显式终态 | VCP `[[TaskComplete]]` / `[[TaskFailed]]` | 采纳为**协议**，映射到 Report 的 `ready` / `failed` |

> **为什么必须加上限**：Grok Bot 事故 #36 就是 `sleep 300` 白白烧 4 分钟。模型自报唤醒如果不设上限，等于把 `sleep` 合法化。

### 6.5 压缩与业务的无缝衔接（DSH 现成）

| 需求 | DSH 原语 **[实测]** |
|---|---|
| 上下文压力观测 | `tokenMeter.contextPressure(session)` / `measure(session)` |
| 长工具结果裁剪 | `toolResultPruner.pruneSession(session)`（配置 threshold/head/tail 字符） |
| 历史压缩 | `compaction.compactIfNeeded / compactNow / compactRegion` |
| 长内容外置 | `spill.saveText(input)` → `SpillRef` |
| 按请求重算的分节 | `systemPrompt.context(...)` / `section(...)` / `variable(...)` / `refreshContext` |

**SEA 的增量**：压缩策略必须**保留 DoneSpec 与 Evidence 指针**。压缩掉"任务完成判据"是灾难。

## 7. 能力面（L1）：工具、技能、记忆

### 7.1 工具：族化（抄 VCP 的好思想，不抄它的协议）

**VCP 的真发现**：同类型插件共用一套指令集，5 个生图插件调用方式完全一样，只换工具名 → "极大降低 AI 的认知负担"（`VCP.md:79`）。

**SEA 的落地 —— 工具族（Tool Family）**：

```yaml
family: fs
members: [fs_read, fs_write, fs_edit, fs_glob, fs_grep]
shape: { path: string, ... }        # 同族参数同构
```

| 规则 | 说明 |
|---|---|
| **族内参数同构** | 同族工具的参数名与语义一致，模型只需换成员名 |
| **族级权限** | SceneContract 声明 `families: [fs, jobs, web, mcp:erp]`，**按族授权**，不逐个工具授权 |
| **族级开关** | `denied: [bash, computer-use]` 拒绝整族 |
| **族级预算** | 每族可单设 token/调用次数上限（Grok Bot：浏览器贵、API 便宜） |

**为什么不用纯文本协议**：DSH 的工具层是结构化的（`ToolDefinition` + `tools.execute` **[实测]**），自造反序列化会丢类型校验、丢 UI 卡片、丢 streaming 增量。**但保留 VCP 的两条体验优化**：族化命名 + 参数模糊容错（在 `tools/pre-execute` 里做归一化）。

### 7.2 技能：SKILL.md 家族 + 三级

| 级别 | 位置 | 谁能改 | 加载方式 |
|---|---|---|---|
| L1 内置 | 插件内 | 只有人（C 档） | 常驻或按需 |
| L2 团队 | `<root>/skills/team/` | 人（经审批）/ Agent 提案 | 按需（`skill` 工具） |
| L3 场景 | `<root>/scenes/<id>/skills/` | **Agent 可自主改（D 档）** | 按需 |

**技能体量红线**（乱雨家 `二-记忆机制.md:161`）：单篇 ≤12 KB，超了拆"主文件 + reference 子文件"。
**技能必须带自检**：每个场景技能至少附一条"这个技能错了怎么发现"（对应 DoneSpec 的 check）。

### 7.3 记忆：五层 + 三红线 + 语义检索（v2）

| 层 | 存储 | 谁写 | 是否每轮注入 | 上限 |
|---|---|---|---|---|
| **M0 宪法** | `memory/00-constitution.md` | 只有人 | ✅ 是 | ≤1 KB |
| **M1 场景契约** | `scenes/<id>/scene.yaml` | 人 / 提案批准 | ✅（生成的分节） | ≤8 KB |
| **M2 场景记忆** | `scenes/<id>/memory/` | 本场景 Agent | 开场注入 | §〇 ≤4 KB；主文件 ≤25 KB |
| **M2a 项目记忆** | `scenes/<id>/memory/projects/<pid>.md` | 本场景 Agent | 按需 | ≤8 KB |
| **M3 工单记忆** | `<stateDir>/tickets/<tid>/` | 该 Worker | 该 Worker 内 | 无（受磁盘预算） |
| **M4 全局索引** | SQLite（见 §12） | 内核 | 工具查询 | — |
| **M5 归档** | `archive/`（**只进不改**） | 系统 | ❌ | 受保留策略 |

**三条红线**（继承乱雨家）：
1. **一个事实只有一个真源**，其他地方只放指针（`总纲.md:26`）
2. **先快照，再动手**；减肥必须能证明"搬前非历史行 == 搬后非历史行"（`二-记忆机制.md:166-175`）
3. **只记结论，不记过程**（≤10 行 / ≤2 KB / 次）

**v2 语义层**（不 v1 做）：
- 写入：抽取"事实/偏好/事件/决策"，冲突时 update/delete（借鉴 mem0）
- 时序：事实带有效时间窗，新事实失效旧事实（借鉴 Zep/Graphiti）
- 检索：向量 + 关键词混合 + rerank；多跳用图（借鉴 HippoRAG，对应 Super-agent 链式召回）
- **禁止**：不可解释的向量变换（VCP 的 TagMemo/EPA/残差金字塔不进主干，见 `01` §3.6）

## 8. 持久面（L6）：存算分离 + Watchdog

### 8.1 第一层解耦：计算与状态分离

| 组件 | 类型 | 说明 |
|---|---|---|
| **Host（DSH 进程）** | **无状态弹性容器** | 可重启、可水平替换；不持有不可重建的状态 |
| **Session/Event 存储** | 持久库 | DSH 原生有 session log（`session/event` **[实测]** 是 post-commit feed）；我们额外持久化内核账本 |
| **内核状态** | SQLite（WAL） | Triggers/Threads/Tickets/Decisions/Mandates/Assignments/Evidence/Attention |
| **文件记忆** | 文件系统（可挂对象存储） | M0–M3 |
| **归档** | 对象存储 / 冷备 | M5，只进不改 |

启动序列必须做到：**杀进程 → 重启 → 无事件丢失、无重复执行**（幂等靠 Trigger id + Ticket 状态 + Effects 队列）。

### 8.2 第二层解耦：计算与执行环境分离（BYOM）

Super-agent / Anthropic 的"脑手分离"（`005` §5.2）。SEA 的端侧组件：

```
┌─────────────────────────┐        ┌──────────────────────────────┐
│ 云端 Host（Agent Loop）  │        │ 端侧 daemon `sea-agentd`     │
│  · 会话状态              │◄──────►│  · 不保存任何会话状态         │
│  · 决策                  │  受控   │  · 只执行白名单命令与文件操作  │
│  · 上下文                │  协议   │  · 返回结果 + 审计记录        │
└─────────────────────────┘        └──────────────────────────────┘
```

**daemon 协议（v1，最小面）**：

| 方法 | 入参 | 出参 |
|---|---|---|
| `exec` | `{req_id, cmd_key, args[], cwd, timeout_ms, env_allow[]}` | `{stdout, stderr, exit, duration_ms}` |
| `fs.read` / `fs.write` / `fs.stat` / `fs.list` | 路径 + 范围 | 内容 / 元信息 |
| `pty.open` | 尺寸 | 双向流 |
| `health` | — | `{uptime, load, mounts}` |

**关键设计：`cmd_key` 而非裸命令**。daemon 只认**预注册的命令名**（`git-status`、`npm-test`、`node-verify`…），不接受任意 shell 串。这是 Super-agent 明确承认的漏洞所在：

> `These wrappers and directories establish defaults, not a security boundary. A worker can still execute a program by absolute path.`（`003-execution.md:80`）

SEA 把它补上：**端侧只跑白名单命令，任意命令需要人批（A 档提案）。**

### 8.3 Watchdog（独立 Control Loop）

Super-agent 的 Watchdog 设计（文章 §6）：
> 主系统**之外**的独立 Agent Session，定时消息驱动；不只监控进程存活，还**用模型判断 Worker 是否有实质进展、方向是否偏离**。

SEA 的 Watchdog **三层**：

| 层 | 检查什么 | 手段 | 频率 |
|---|---|---|---|
| **W1 基础设施** | 进程、DB 锁、Effects 积压、凭据过期、daemon 心跳 | 确定性代码 | 30 s |
| **W2 进展** | Ticket 是否实质推进（有新证据/新报告/新提交） | 确定性指标：`last_progress_at`、evidence 增长、token 消耗 vs 产出 | 5 min |
| **W3 方向** | 是否偏离目标、是否陷入无效循环 | **模型判断**（独立 Session，读 Report 摘要 + 证据指针） | 15 min 或按告警 |

**关键规则（互补于 VCP 心跳）**：
- 模型自报 `NextHeartbeat::300` → W2 在 **`min(N, 300s)`** 后复查一次；若无实质产出 → **提前唤醒**并要求解释
- 连续 2 次"唤醒后无产出" → **终止该 Assignment** 并报告 `blocked`（附"我尝试了什么"）
- W3 **不得修改 A/C 档**；它的修正手段只有：增删 D 档提示词、调整 routine 频率、终止/重排工单

**W3 自己也是被监控对象**：Watchdog 的成本与消息量同样进预算账本（防止"看门狗自己变成狼"）。

## 9. 安全（L6）：四个源都不及格，我们必须超越

### 9.1 四个源的安全现状

| 源 | 是否隔离 | 凭据处理 | 证据 |
|---|---|---|---|
| Super-agent | ❌ 明确声明不隔离 | ⚠️ 靠 CLI 包装（`gh-agent`/`lark-bot`），**不隔离进程** | `006-deployment.md:19`、`003-execution.md:80` |
| Grok Bot | ⚠️ 账户内共享电脑/文件/登录态；账户间严格 | ✅ 凭据过表单/1Password，**Bot 看不到密码** | `docs.x.ai/grok-bot/overview` FAQ、`PRODUCT.md:75-77` |
| VCP | ❌ 自述"拥有分布式系统底层级权限" | ❌ 未见凭据进上下文的设计 | `README.md:11` |
| 乱雨家 | ⚠️ 靠"规矩"（E 档不许写别人） | ❌ 无 | `一-协作机制.md:51` |

Super-agent 自己把问题摊得很清楚（文章 8.4）：
> 一旦云端的 Agent Loop 遭遇服务端入侵或提示词注入而被攻破，其连接的全部端侧设备都面临被控制的潜在风险。此外，即使云端未被攻破，**只要端侧环境中的凭据能够进入模型的上下文，正常执行过程中同样存在凭据泄露的风险**。

### 9.2 SEA 的六道防线

| # | 防线 | 机制 | 对应威胁 |
|---|---|---|---|
| **D1** | 数据/指令分离 | 外部文本永在 user/工具结果位置，**永不进 system-prompt**；权限判定在代码；`tools/pre-execute` **[实测]** 兜底 | 提示词注入 |
| **D2** | 凭据不进上下文（Broker） | Agent 调 `use_credential(key, intent)`；**Broker 在受控进程执行**，Agent 只见到结果摘要与审计号；凭据明文永不出现在任何 message | 凭据泄露（Super-agent 原话） |
| **D3** | 端侧白名单命令 | daemon 只跑 `cmd_key`；任意命令需 A 档批准 | 端侧被控 |
| **D4** | 出站审计 | 所有对外写（消息/PR/邮件/API 变更）记录 `{actor, action, target, evidence, mandate_id}`；**不可撤销地落审计流** | 不可追责 |
| **D5** | 爆炸半径分档 | `autonomy.ceiling` 由场景契约定；**`prod` / `money` / `secret` / `migration` / `permission` 五类动作强制 `review`**（无论 ceiling 多高） | 生产事故（Grok Bot #29） |
| **D6** | 进化隔离 | 进化只能改 D 档；A/C 档改动必须人批 + 版本化 + 可回滚 | 自我权限膨胀 |

**D5 的硬编码清单**（不可被场景契约放宽，只能收紧）：
```
always_require_review:
  - 数据库迁移 / 删表
  - 生产部署 / 回滚
  - 任何资金动作
  - 权限与凭据变更
  - 对外发布（公开发布、群发、PR merge 到主干）
  - 删除非本场景资产目录以外的任何东西
```

> 这份清单直接来自 Grok Bot 事故 #29（自主修复的坏 SQL 把生产打挂）与 Super-agent 的 Mandate 机制。

## 10. 预算与成本（L6）

### 10.1 四类预算

| 预算 | 粒度 | 超限行为 |
|---|---|---|
| **Token** | 每 Ticket / 每场景每日 / 全局每日 | 软限：降档（禁浏览器、禁大检索）；硬限：暂停派单并告警 |
| **唤醒** | 每场景每小时 / 每日 | 超限：新唤醒降级为"只落盘不唤醒"（乱雨家派单/公告区分） |
| **主动消息** | 每场景每日 / 每件事 ≤3 条 | 超限：静默，只进面板 |
| **Routine** | 每个 routine `max_runs_per_day` | 超出不跑（Grok Bot：频率按输入变化率定，不按焦虑定） |

### 10.2 核心指标：注意力税（Attention Tax）

> **注意力税 = 主动发出的消息数 / 被采纳（acted）的工作项数**

- 目标：**< 1.0**（每条主动消息至少要换来一件被人接受的事，否则就是噪音）
- 面板第一屏显示这个数字（Grok Bot/乱雨家都强调"面板先显示需要人的"）
- 超过阈值 → 自动降档：`proactive: auto → observe`

这个指标直接编码 Super-agent 的哲学："每个消息都在花别人的注意力"（`000-philosophy.md:5-7`）。

### 10.3 成本纪律六律（Grok Bot 实证，写成硬约束）

| # | 规则 | 落地 |
|---|---|---|
| 1 | routine 默认**一天一两次**，优先事件/webhook | 契约里 `max_runs_per_day` 默认 1-2 |
| 2 | 群聊/多方讨论**只在要辩论时**用 | 场景间默认 1:1；群聊需显式 `mode: debate` 且计费更高 |
| 3 | 有 connector 用 connector，**浏览器是 fallback** | 工具族 `mcp:*` 优先；`computer-use` 计入高成本类 |
| 4 | **团队要精简**，先问"能不能加一个技能而不是加一个场景" | 新场景需 `justification` 字段 + 人批 |
| 5 | **建一个 CLI，不要每次重写验证脚本** | DoneSpec 的 `check` 必须指向已入库的命令 |
| 6 | Watchdog 巡检长 sleep / 漂移 / 无法解释的活动 | W2/W3 |

## 11. 进化面（横切）：概览

> 完整设计见 `03-自进化机制.md`。此处只给它在架构中的位置与约束。

### 11.1 位置

进化面**不新增一层**，它是穿过 L1（技能/记忆）、L2（契约 D 档）、L3（派单启发式）的**横切动作**。

### 11.2 七步闭环

```
Observe ──▶ Hypothesize ──▶ Propose ──▶ Sandbox Verify ──▶ Budget Gate ──▶ Apply ──▶ Monitor
   ▲                                                                                     │
   └─────────────────────── Rollback（不达标或退化）◀─────────────────────────────────────┘
```

### 11.3 五条硬约束（在本文层面必须钉死）

| # | 约束 |
|---|---|
| E-1 | **只能改 D 档**。A/C 档改动一律走"提案 → 人批 → 版本化" |
| E-2 | 每个提案**必须带一个会失败的反例**（没有反例 = 提案无效）|
| E-3 | 每个提案**必须过回归集**（不许为了修 A 弄坏 B）|
| E-4 | **每次只改一处**，改动必须可回滚（不可回滚的改动不允许）|
| E-5 | **配额**：每场景每周 ≤ N 个提案（默认 1，抄 Grok Bot #7 的教训）|

### 11.4 进化落点（DSH 原语映射）

| D 档资产 | 落点 | DSH 原语 **[实测]** |
|---|---|---|
| 技能 | `<scenes>/<id>/skills/*/SKILL.md` | `skills/change` 事件；`skill` 工具 |
| 场景记忆 | `<scenes>/<id>/memory/` | 文件 + `storageDomain` |
| 提示词正文 | 场景契约的 `identity.role` | `systemPrompt.section/context` |
| 派单启发式 | 路由规则表 | `agentPresets.register`（**可运行时注册**） |
| Routine 频率 | 契约 `budget.routines` | `schedule` 服务 + `timer` |

        sender_identity, via, done_spec_snapshot_json, revoked_at, revoked_reason)

eval_batch(thread_key, trigger_ids_json, started_at, deadline_at, attempt)
decision(id PK, thread_key, batch_json, outcome, reason_code, reason_values_json,
         decided_by, decided_at, ignored_from_card)

-- 工作
ticket(id PK, scene_id, title, short_name, mandate_id, state, stage, done_spec_json,
       opened_at, ended_at, ended_by, outcome, latest_report_id)
ticket_input(id PK, ticket_id, kind, payload_ref, delivered_at, read_at, disposition)
assignment(id PK, ticket_id, executor_session_id, directory, state,

done_check(id PK, ticket_id, spec_id, cmd, exit_code, diff_set_ref, ran_at, verdict)
evidence(id PK, ticket_id, kind, hash, source_uri, captured_at, verified_by)

-- 订阅（多对多，由 thread 持有）
subscription(thread_key, ticket_id, mode, /* context | own */, created_at, dropped_at)

-- 账本
attention(id PK, kind, scene_id, ticket_id, target, cost_class, awaiting, outcome, created_at)

outbox(id PK, ticket_id, channel, purpose, body_ref, state, attempts, sent_at, dropped_reason)

## 14. 关键流程时序

### 14.1 一次外部事件从进入到交付

```
外部系统 ──webhook/轮询──▶ Source(kind) 
                              │ ①过滤自身消息/范围外（确定性）
                              ▼
                          Trigger（不可变，幂等 id）
                              │ ②Source 已绑定场景？
                              ├─是──▶ Scene Session（Fast Path，不经 Router）
                              │           │ ③gate：人/强度/准入表（不调模型）
                              │           ▼
                              │        Eval（batch + Thread快照 + Ticket列表 + Policy）
                              │           │ ④语义判定（模型，慢路径）
                              │           ▼
                              │        Decision(accept + Mandate + DoneSpec快照)
                              │           │
                              └─否──▶ Global Router ──判定场景──▶ 回到上面 ↑
                                          │
                                          ▼
                                     Ticket(open) ──Assignment──▶ Worker Session
                                          │                         + 独立目录
                                          │                         + prepare 命令
                                          ▼
                                     Report(ready) ──▶ DoneSpec ⑤verify(check/evidence)
                                          │                    │
                                          │              失败 ──▶ 回到 Worker（带 diff-set）
                                          │                    │
                                          ▼                    ▼
                                     person/review（若需 review）──▶ 人验收
                                          │
                                          ▼
                                     写回 Source（Channel）+ 记 Evidence + 记 Attention
```

### 14.2 一个自进化提案的生命周期（摘要）

```
W2 观察：某场景"打回率"连续 3 天 > 30%，且失败集中在"发票金额识别"
   │
   ▼
Evolver 提案：修改场景技能 invoice-parse/SKILL.md 增加"双人复核金额"步骤
   │ 必须夹带：① 反例（一个会被旧技能判错的样本）② 回归集（历史 20 单）
   ▼
沙箱验证：反例过去 → 通过；回归集全过 → 通过；成本增量 < 5% → 通过
   │
   ▼
Budget Gate → 配额检查（本周该场景已有 0 个提案）→ 通过
   │
   ▼
Apply（D 档，Agent 可自主）：写新版本 asset_version，旧版本留档，路由切换
   │
   ▼
Monitor 7 天：打回率是否下降；若上升 > 10% → Rollback（切回旧 asset_version）
   │
   ▼
报告：写入场景记忆 §〇，并把"原则而非事件"写进 commit message
```

### 14.3 一个"人被打断"的最小化路径

```
Worker 发现需要人的决策
   │ 结构化提问（一个具体问题 + 选项 + 为什么需要）
   ▼
Scene 汇总 → Router 按信道适配
   │
   ├─ IM    ：≤100 词 / 一条 / 直接问
   ├─ GitHub：结构化评论（背景 + 改动 + 验证结果 + 待决点）
   └─ 面板  ：卡片，放在第一屏"需要你"
   ▼
人回答 → Attention 记 outcome=acted → 派回 Worker
```

**每件事最多 3 条消息**（派单 + 回执 + 收尾），末行 `【结束】`。

## 16. 已知风险与待验证假设

> 诚实标注。这些都会进 `04-工程路线与验收.md` 的验证清单。

| id | 风险 / 假设 | 影响 | 验证方式 | 时间点 |
|---|---|---|---|---|
| **R-1** | **能否"唤醒一个已持久化但不活跃的 Session 并投递消息"**。`subagents.sendMessage` 要求父子邻接；`webhookRuntime` 只给"新建 Session" | **架构地基**。若不成立，Router 常驻方案要改 | **v0.5 spike**：写最小插件，持久化一个 session id，销毁，再 resume + 投递，观察是否被处理 | 第 1 周 |
| **R-2** | 3 层编排的真实成本（多一层 Session = 多一层 token） | 可能让"多场景"不划算 | 用 3 个场景、50 个合成 Trigger 做 A/B（2 层 vs 3 层），比对 p50/p95 与 token | 第 4 周 |
| **R-3** | DoneSpec 的 `check` 在非编码场景的覆盖率 | 若覆盖率 < 50%，"通用"会退化 | 抽 5 类场景（客服/运维/文档/数据/财务），尝试各写一条 check，统计成功率 | 第 2 周 |

## 17. 术语对照（内部统一）

| 英文 | 中文 | 一句话 |
|---|---|---|
| Scene | 场景 | 一类会反复回来的活 + 资产 + 流程 + 契约 |
| SceneContract | 场景契约 | 声明的场景定义（含 DoneSpec / autonomy / budget） |
| DoneSpec | 完成契约 | 什么样算完成，三形态（check/evidence/review） |
| Source | 来源 | 事件流；kind + instance |
| Trigger | 触发 | 一条不可变事件 |
| Thread | 线程 | 时间序触发流 |
| Eval | 评估 | 一批触发 → 一个决定（无状态） |
| Mandate | 授权 | 这次允许做到哪、依据哪个版本 |
| Ticket | 工单 | 一件被授权的工作 |
| Assignment | 派工 | 工单绑到某个执行器实例 |
| Evidence | 物证 | 可复核的完成证明 |
| Attention Tax | 注意力税 | 主动消息数 / 被采纳工作数 |
| Autopilot Ladder | 自主档位 | investigate → draft → autopilot → full |
| Proposal | 提案 | 一次 D 档改动请求 |
| Counterexample | 反例 | 证明检查"会失败"的样本 |
