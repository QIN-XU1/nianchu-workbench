#### 0.5 三次同构错误（本轮最该记住的）

| 版本 | 我的错误 | 正确说法 |

### 结论 5：【F-3 完成】DoneSpec 在 3 类非编码场景全部成立，且反例 6/6 都能红

### 结论 1：F-4 通过，但发现一个方案未考虑的真实风险

`dsh --profile web --dump-config` **成功**（exit 0，46,976 字节），说明：
- ✅ 真实配置树可读取，我引用的 32 个包**29 个直接命中**
- ✅ 未命中的 3 个是**包名不同**，不是不存在（`webserver` → 真实条目 `@deepseek-ai/dsh-host-webserver`）
- ⚠️ **但发现了 v2 未考虑的风险 R-15**：yaml 里 `dsh-purge` 的 patch 引用了 6 个不存在的条目（`redteam-store`、`redteam-ui`、`redteam-mode`…），**启动并没有失败**

原话（实测输出）：
```
dsh: [dsh-purge] patch: entry "redteam-store" not found
dsh: [dsh-purge] patch: entry "redteam-ui" not found
dsh: [dsh-purge] patch: entry "redteam-mode" not found
dsh: [dsh-purge] patch: entry "redteam-mode-store" not found
dsh: [dsh-purge] patch: entry "redteam-mode-ui" not found
dsh: [dsh-purge] patch: entry "dsh-purge" not found
```
**exit code 仍然是 0。**

这直接挑战 `AGENTS.md` 里我引用的那条纪律（"**Misconfiguration fails loud**：misconfiguration fails loud at load when self-contained"）。

**[推断] 为什么这次没失败**：这些 patch 来自第三方插件 `dsh-purge`（一个"破甲"插件）的 patch 层，它引用的条目标的是**它自己本该插入但被用户禁用/未启用的条目**。也就是说：**patch 的"目标不存在"在某些路径上是容忍的**（可能是 cursor 式 patch 允许 target 缺失时 no-op）。

**对方案的含义**：
- 我 v2 把"F-4 引用不存在的包 → 启动必须报错"作为 P0 的 Go/No-Go 判据，**这条判据本身是错的**（对 patch 不成立）
- 必须改成：**"引用的包名必须在 `--dump-config` 输出中真实存在"**，而不是"不存在就报错"
- 并且要区分两类错误：**entry 缺失（容忍）** vs **包无法解析（fatal）**

### 结论 2：**【推翻 v2】`webhookRuntime` 不在 web profile，且它是 experimental**

这是本轮最重要的发现。

| 我 v2 的说法 | 实测 |

`experimental` 组的整体定位 | "not a product-support commitment... may be withdrawn" | 我们方案的地基有一部分站在可能被撤走的东西上 |

### 结论 4：【修正】preset 的插件是**惰性**的，`dump` 与启动都不校验

这是 F-1 的反例测试暴露的事实，**推翻了我原本的 P0 判据**。

**实测**：

| 测试 | 预期（我原以为） | 实测 |
|---|---|---|
preset 里引用不存在的包 `@deepseek-ai/dsh-tool-THIS-DOES-NOT-EXIST` → `--dump-config` | 应报错 | ❌ **exit=0**（无报错） |
同一个反例 → **真实启动** | 应报错 | ❌ **exit=0，服务正常起在 :5286** |
preset 里引用 experimental 包 `@deepseek-ai/dsh-experimental-webhook` → 真实启动 | 应报错或警告 | ❌ **exit=0，服务正常起在 :54888** |

**源码解释**（`research/repos/dsh-src/@deepseek-ai__dsh-agent-preset/lib/index.js`）：

```js
static Config = z.object({
  id: z.string().required(),
  ...
  plugins: z.array(z.any()).required()   // ← 任意数组，不做包解析
});
static [EntryGroup.key] = true;          // ← 作为 EntryGroup，子条目延迟到激活时才解析
```

注释原文：**"Preserve child expressions until their own plugins activate."**

**对方案的含义（三条，都很硬）**：
1. **`--dump-config` 不能作为"包存在性"的验证手段** —— 它只做 YAML 组装
2. **启动也不校验未激活的 preset** —— 错误会延迟到"某个会话真的选中这个 preset 时"才爆
3. **所以 F-4 的正确判据必须改为**：
   - 静态核对：包名在 `--dump-config` 的**全量输出**里存在（我做法有效，但只能证明"别处有人引用过"）
   - **动态核对**：让一个会话**真的选中**该 preset 并跑一轮 → 这才是唯一能证明"包可解析"的方法
   - 这需要模型 key（`DEEPSEEK_API_KEY`）或 mock adapter

**这条修正让我 v2 的"复用官方清单"验证方法升级**：
> **不能靠"我 grep 到它在 tree 里"来断言可复用；必须让一个会话真的用它跑一轮。**

这也解释了为什么我 v2 的"复用清单"会漏掉 `webhook` 是 experimental —— **我从未真正让一个会话选中过任何 preset。**

## 2. 因此方案必须改的三处

### 2.1 改 P0 的 Go/No-Go 判据（F-4）

| v2 原判据 | 改为 |
|---|---|
| "引用一个不存在的包 → `dsh` 启动必须报错" | ① **"引用的包名必须在 `--dump-config` 输出中存在"**（静态核对）<br>② **"引用的 bundle 必须在当前 profile 的 `dsh.profile.bundles` 里"**（真实挂载核对）<br>③ 区分 **entry 缺失（可能容忍）** vs **包解析失败（fatal）**——需实测确认 |

### 2.2 改"复用官方"的清单：加一列"成熟度"

v2 的复用清单里，"官方有" ≠ "能直接用"。必须加三列：

| 列 | 含义 |
|---|---|
`group` | `packages/<组>`（product vs experimental） |
`shipped_in_web` | web profile 默认是否挂载（**实测**） |
`maturity` | 官方 `packages/experimental/README.md` 的定义：**product-support commitment** 与否 |

**新增的三条硬结论**：
- **`webhookRuntime` 是 experimental** → SEA 的"外部事件驱动"**必须自己承担"它可能被撤走"的风险**，或改为订阅更稳定的入口（`schedule` / `fs-watch` / `webServer.register`）
- **`agent-team` 需要显式装 bundle** → "复用官方任务板"成立但**要写安装步骤**，不能假装默认可用
- **experimental 组 = pre-stable** → 与 R-13（官方 API pre-stable）叠加，**方案的地基有相当一部分是"官方自己不承诺"的东西**

### 2.3 新风险 R-15 / R-16

| id | 风险 | 证据 | 缓解 |
|---|---|---|---|
**R-15** | patch 引用不存在的 entry **可能静默容忍**，导致"配置坏了但不知道" | 实测 6 条 warning + exit 0 | 自建 `sea doctor` 命令：静态核对 + 真实 dump 核对；不依赖官方 fail-loud |
**R-16** | **核心能力（webhook / agent-team）是 experimental 或默认不装**，可能被撤走 | 实测 web profile 无命中 + `packages/experimental/README.md` 原文 | 每个"复用的实验能力"必须有**降级路径**；在方案里标注 maturity，不能混为一谈 |

## 5. 一条方法论收获

> **"官方仓库里有" 和 "你的 profile 里跑得起来"是两个不同的事实。**
> 我 v2 犯的错误与 v1 同构：**v1 把"原型"当"地基"，v2 把"仓库里有"当"能复用"。**
> 两者都是**把"资料存在"误当成"能力可用"**。
>
> 正确做法：**任何"复用官方"的主张，必须跑一次 `--dump-config` 核对它在当前 profile 的真实挂载点。**
> 这就是 F-4 的价值——它不是"验证技术可行性"，而是**验证我的清单是不是真的**。
