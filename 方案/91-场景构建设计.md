# 91 · 场景构建设计（从 0 开始）

> 用户：「除了一直打磨的记忆神经元场景全部做删除，从 0 构建」
>       「具体的场景可以通过双击对应节点跳转，
>         而里面具体的场景设计其实**针对不同的应用场景设计的应该都是不同的**」
>       「优先接：引擎对话」

---

## 一、先回答一个根本问题：场景到底是什么

### 1.1 如果场景 = 页面，那它没有存在价值

**因为中枢本身就是一个对话页。**

```
用户在中枢提需求 → AI 回答
这已经完成了「对话」这个交互
```

**那么「对话场景」就是多余的重复。**

### 1.2 场景的真正定义

> **场景 = 当对话不够用时，需要的专门界面。**

什么情况下对话不够用？

| 情况 | 为什么对话不够 | 需要什么 |
|---|---|---|
**要看大量结构化信息** | 对话里只能用文字描述 | 能承载表格/树/图表的界面 |
**要精确操作某个对象** | 对话里只能用自然语言说 | 能点/拖/标注的界面 |
**要并列对比** | 对话只能依次展示 | 左右并排的界面 |
**要持续观察** | 对话只能问答 | 自动刷新的仪表盘 |
**要长时间执行** | 对话会超时/上下文溢出 | 能跑着并看日志的界面 |

**这正是你说的「不同应用场景设计应该不同」的含义 ——
不是换配色换布局，而是交互范式根本不同。**

---

## 二、场景设计的三个决定因素

### 2.1 因素一：任务性质（决定交互范式）

```
看 —— 只读大量信息      → 高密度展示
改 —— 精确操作对象      → 直接操纵
比 —— 并列对照          → 分栏对齐
盯 —— 持续观察状态      → 自动刷新
跑 —— 长任务执行        → 日志流 + 进度
```

**这 5 种任务性质，决定了 5 种根本不同的界面范式。**

### 2.2 因素二：真实能力（决定能做到什么）

**审计结论：后端只有 5 类真实可用的能力。**

| # | 能力 | 通道 | 能支撑什么场景 |
|---|---|---|---|
① | AI 对话 | `engine:prompt` `harness:*` | 深度对话、分析 |
② | 终端 | `tui:*` | 命令执行、日志观察 |
③ | 文件审查 | `review:files` `review:read` `review:root` | 审阅文件 |
④ | 文件系统 | `kun:file:*` `kun:sys:disks` | 浏览本地文件 |
⑤ | 网页/站点 | `embed` `site:preview` | 浏览外部资料 |

**5 类能力 → 最多 5 类场景。**

**绝不能再编造（之前 `pc:toplarge` / `pc:junk` / `pc:ledger` 后端根本不存在）。**

### 2.3 因素三：场景的记忆（决定「场景」和「普通页面」的区别）

**一个场景必须有：**
```
① 身份卡    —— 我是谁、职责边界、方法来源
② 私有记忆  —— 做过的判断、踩过的坑、积累的结论
③ 可累积    —— 用得越多越懂你的偏好
```

**没有这三样，它就只是一个静态页面，不配叫「场景」。**

## 三、五个场景的具体设计

### 场景 1：深研（Deep Research）

**任务性质**：看 + 比
**真实能力**：`embed`（网页）+ `engine:prompt`（AI 提炼）
**存在理由**：对话里说「帮我研究 X」，AI 只能凭记忆回答；
          这个场景能真的打开网页，边看边提取。

**布局（独创）**
```
┌────────────────────────┬──────────────────┐
│                        │                  │
│   网页浏览区           │   笔记提取区     │
│   （webview，可多标签） │   （AI 逐条提取  │
│                        │    可勾选采纳）  │
│                        ├──────────────────┤
│                        │   已采纳清单     │
│                        │   （可导出为     │
│                        │    产物）        │
└────────────────────────┴──────────────────┘
```

**关键设计：**
- 左边浏览，右边**不是对话**，是「结构化提取列表」
- 每条提取可勾选 → 采纳后进清单
- 清单可导出为 markdown 产物 → 交给其他场景
- **记忆**：记住你常看哪些站点、偏好哪种提取粒度

**与对话的区别**：对话是「问一句答一句」；这里是「边看边积累清单」。

---

### 场景 2：审阅（Review）

**任务性质**：看 + 改
**真实能力**：`review:files` `review:read` `review:root`
**存在理由**：review 通道真实存在但从未被前端使用（审计发现）。

**布局（独创）**
```
┌───────────┬──────────────────────┬──────────┐
│ 文件树    │   文件内容            │ 批注栏   │
│           │   （行号 + 高亮）      │          │
│ ▸ src/    │                      │ 第 42 行 │
│   ▸ a.js  │   42 │ const x = ...  │ 「这里   │
│   ▸ b.js  │   43 │ if (x) {       │  应该…」 │
│           │                      │          │
│  [已审 3] │                      │ [采纳][忽略]│
└───────────┴──────────────────────┴──────────┘
```

**关键设计：**
- 左树、中内容、右批注（三栏，固定比例）
- 批注锚定到**具体行**
- 「采纳/忽略」决定是否写回
- **记忆**：记住你关注什么类型的代码问题

**与对话的区别**：对话里说「第二段有问题」，AI 不知道指哪；这里能精确锚定。

---

### 场景 3：执行（Run）

**任务性质**：跑 + 盯
**真实能力**：`tui:*`（终端）`engine:prompt`（AI 解释）
**存在理由**：长任务（构建、测试、批量处理）在对话里会超时。

**布局（独创）**
```
┌──────────────────────────────────────────┐
│  任务：npm run build          [运行中 42%]│
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━        │
├──────────────────────────────────────────┤
│  日志流（实时滚动，可暂停）               │
│  ▸ Compiling...                          │
│  ✓ 12 modules                            │
│  ▸ Bundling...                           │
├──────────────────────────────────────────┤
│  AI 解读：[这里只在出错或有异常时出现]     │
└──────────────────────────────────────────┘
```

**关键设计：**
- 上方进度条、中间日志流、下方 AI 解读（仅异常时出现）
- **AI 不参与正常流程**，只在出错/超时时介入
- **记忆**：记住每个任务的典型耗时、常见错误

**与对话的区别**：对话是同步等结果；这里是异步跑着，你可以去干别的。

---

### 场景 4：本地（Local）

**任务性质**：看（文件系统）
**真实能力**：`kun:file:*` `kun:sys:disks`
**存在理由**：`kun:sys:disks` 真实存在，能列真实磁盘。

**布局（独创）**
```
┌──────────────┬───────────────────────────┐
│ 磁盘          │  目录树                   │
│              │                           │
│ C:  ████ 78% │  ▸ D:\project             │
│ D:  ██   32% │    ▸ src/                 │
│ E:  ███  61% │    ▸ docs/                │
│              │                           │
│              ├───────────────────────────┤
│              │  文件预览（选中文件内容）  │
└──────────────┴───────────────────────────┘
```

**关键设计：**
- 只做「真实存在的能力」：列磁盘、列文件、读文件
- **不编造**「垃圾清理」「大文件扫描」（后端没有）
- **记忆**：记住你常访问的目录

---

### 场景 5：终端（Shell）

**任务性质**：跑 + 操作
**真实能力**：`tui:*`（完整终端）
**存在理由**：dsh-TUI 已经是完整终端，但作为场景可独立使用。

**布局**：全屏终端（无分割）

**关键设计：**
- 纯终端，不做多余装饰
- **记忆**：记住常用命令历史

## 四、神经元的定位（保留 + 优化）

**神经元不是场景，是场景的导航层。**

```
神经元（中枢场景里）
  ↓ 双击节点
进入对应场景
  ↓ 场景内 ESC / 返回
回到神经元
```

**要优化的两点（你说过）：**
1. **美观度**：星点细节、连线层次
2. **操作手感**：旋转/缩放的跟手程度

**不需要改的**：整体架构（星图 + 场景节点）已经对了。

| | 旧设计（11 个场景） | 新设计（5 个场景） |

## 六、我需要你确认的三点

### 确认 1：场景划分依据

**换成「任务性质」而非「业务领域」** —— 你认可吗？

理由：业务领域是无穷的（架构、命理、写作、投资…），
     但任务性质只有 5 种（看/改/比/盯/跑）。

### 确认 2：5 个场景是否够

我提议：**深研 / 审阅 / 执行 / 本地 / 终端**

你之前提过「命理」等国学场景 ——
那应该是**深研场景里的一次具体任务**，而不是单独的场景。

### 确认 3：先做哪一个

我建议顺序：
1. **深研**（最常用，embed + engine 都可用）
2. **审阅**（review 通道真实存在但从未用过）
3. **执行**（tui 已可用）
4. **本地**（kun 能力）
5. **终端**（最简单）
