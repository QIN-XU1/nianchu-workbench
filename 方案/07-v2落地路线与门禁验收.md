> 本文替代 `04-工程路线与验收.md` 的阶段部分。**区别**：v1 的验收是我自造的标准；v2 的验收**必须接官方已有门禁**，因为只有它们能独立证伪我的主张（见 `05` §4）。

## 0. 三条例外原则

### 原则 1：先证伪"我不需要造"，再动手造

每个新增概念（SceneContract / DoneSpec / 三层编排 / 场景记忆）都必须先做**"用官方现成机制能不能实现"**的证伪实验。证伪成功（即官方够用）是好结果——省一整个子系统。

### 原则 2：每个主张必须绑定一条官方门禁

| 门禁 | 官方定义 | 能证伪什么 |
|---|---|---|
| `pnpm run test` | 单元测试 + **每个注册表的 HMR 安全测试**（卸载 fiber 断言清理） | 注册不可逆 |
| `pnpm run test:coverage` | **每文件 100%** 覆盖（CI 真门禁） | 死代码 / 未执行分支 |
| `pnpm run test:snapshot` | **录制会话回放**，父代提供输入与模型回放，儿子代是期望的持久结果 | **任何"模型可见但不可重建"的输入** |
| `pnpm run test:expected` | 无 key 装配期望 | 装配错误 |
| `pnpm run test:bench` | 用户路径墙钟/内存/扩展预算，**环境变量不得覆盖** | 性能退化 |
| `pnpm run test:web` | Chromium/WebKit 比对（Linux PR 必需门禁） | UI 回归 |
| `pnpm run test:e2e` | 有 `DEEPSEEK_API_KEY` 就跑真模型 | 真模型下不能用 |
| `pnpm run doc-sync` | 文档门禁（含 `verify-agent-note-format`、`verify-doc-budgets`、`verify-translation-pairing`） | 设计与事实不一致 |
| `pnpm run duplication` | 跨文件 TS clone 检测 | **第二套实现** |
| `pnpm run build:check` | 用 `build:artifacts` 产物做类型检查 | 发布物坏 |
| `verify-application-entrypoints` | 拒绝任何绕过 `dsh` profile 的 Node 应用路径 | 绕过启动器 |

### 原则 3：不 fork、不打补丁、不做第二套实现

`AGENTS.md`：「**Plugins, not loop changes**」。
能复用官方包就不自造；一旦自造，`duplication` 会先红。

## 2. P0 证伪期（第 1-2 周）

### 2.1 R-1 已被官方证据解决，不再是风险

**v1 的 R-1**："能否外部事件唤醒一个已持久化的 Session？" 我列为"架构地基、决定 40% 形态"。

**官方证据（三条独立）**：

| # | 证据 | 原文 |
|---|---|---|
| 1 | `docs/architecture.zh.md` | **"输入通过同一个 inbox 到达驱动器；注入的上下文等待一条唤醒消息。AgentLoop 的持久 `inbox` 投影使待处理输入在没有活跃 Agent 时仍可读取。"** |
| 2 | `docs/subsystems/core.md` / `dsh-agent` README | `ctx.agents.resume()` **"loads a persisted session and rebuilds the agent on it"**；`handle.followup()` **"queues an ordinary next-turn prompt and wakes the driver"**；`handle.steer()` **"submits next-step input and wakes it"**；`handle.inject()` **"adds model-facing context without waking the driver"** |
| 3 | `benchmarks/agent-continuation/README.md` | 专门测"**冷启动工具密集续跑**（cold tool-heavy continuation）+ 反复发现不活跃 fork 子代"，SDK 变体驱动 **100 轮 / 800 次真实文件读取**，带 **hosted CI 预算 5,500ms + 1.25× 余量 = 7,000ms** |

**结论**：
- ✅ **可以唤醒**：`resume()` + `followup()`
- ✅ **可以不唤醒只注入**：`inject()`
- ✅ **代价已被官方量化**：冷续跑预算 7 秒（sdk-minimal 变体，含 checkpoint）

**所以 P0 不再验证 R-1，而是验证下面四件事。**

> **状态更新（2026-11-06 实机）**：F-1 / F-1b / F-4 **已完成**；结论与证据见 `09-实机验证记录.md`。

### 2.2.1 F-1 的实测结论（四重证据）

| # | 证据 | 实测 |
|---|---|---|
1 | 正向 select 成功 | `[sea-preset-probe] selected 'sea-data-reconcile' for session session-eb932e07-…` |
2 | 反向探针（不存在的 preset） | `NEGATIVE PROBE OK: bogus preset rejected: RemoteError: Unknown agent preset: …` |
3 | 会话日志事件 | `agent-preset/selected` 存在（5 个会话里唯一一个） |
4 | **system prompt 真的变了** | `你是"数据核对"场景的专员。只产出差异集合，不改任何数据。…` |

**因此**：`02b` §2.2 的 `scene.yaml` **删除**；我们的"场景层"缩到**约 40 行胶水代码**；DoneSpec 成为**唯一**新造物。

### 2.2.2 F-1b 的教训（比 F-1 重要）

> **preset 写进 `--dump-config` ≠ 会话用了它。**
> 不显式 `select`，headless 完全忽略；`default:` 只是"没有请求时用哪个"，而 headless 路径根本不请求。
> 官方选择入口只有 `ui-agent-preset`（Web UI）+ 程序化 `agentPresets.select()`；**SDK 无 `/preset` 命令，headless 无 flag**。
>
> **验证方法必须改为：读会话日志的 `agent-preset/selected` + system prompt 内容，而不是看配置文件。**

## 4. P2 场景抽象（第 6-8 周）—— 仅在 F-1 证伪失败时启动

### 4.1 启动条件
P0 的 F-1 显示"纯 preset 表达不了多场景"，**并且**能说清"多解决的是什么"（例如：跨场景协作、场景级预算、场景间隔离）。

### 4.2 交付

| # | 机制 | 官方挂载 | 验收 |
|---|---|---|---|
| 1 | SceneContract（薄层） | 一个 preset 引用 + DoneSpec + 自治上限 | 新增第二场景，**改动文件数 ≤ 1** |
| 2 | 场景判定（快/慢路径） | `webhookRuntime` 规则 + `agent.inject()` | 10 个混合事件归属正确率 ≥95% |
| 3 | 场景隔离 | preset 的 `isolate` realm | 场景 A 的工具看不到场景 B 的服务 |
| 4 | 跨场景协作 | **官方 `team/agent-team`**（`blockedBy` DAG + `writeScopes` 咨询式） | 复用，不自造 |
| 5 | 场景记忆 | **`skill/` 提供方** + `context/` | 记忆是"按需加载的 skill"，不是新存储 |

### 4.3 P2 验收
- 新增场景改动文件数 ≤1（**可证伪：若需改 2 个文件，说明抽象错了**）
- 场景隔离：A 的 preset 里没有 B 的工具（**必须能失败**：故意放进去 → `test` 应断言到）
- 跨场景写被拒：用 `fs/*-intent` waterfall 或 `writeScopes` 检查

## 5. P3 上下文与记忆（第 9-11 周）

### 5.1 核心动作：**把 v1 的"七通道"映射成官方分节注册**

| ⑧ 召回 | **不进 prompt**，由工具按需取 | `session-query/`（lineage、语义过滤、FTS） |

### 5.2 记忆：复用官方三件
- **会话历史**：`core/session`（事件溯源，已是最强记忆）
- **检索**：`session-query/`（"logical corpus, bounded reads, **lineage**, semantic filtering, SQLite full-text search"）
- **技能**：`skill/`（provider registry + local provider + catalog/loader）
- **外置**：`spill/`（locator + retrieval hint）
- **压缩**：`compaction/`（Service Definition + basic provider）

**我们只加**：场景级的"记忆文件约定"（`§〇 交接 ≤4 KB` 之类），**并且必须是 skill/context 提供方的实现细节**，不是新存储。

### 5.3 P3 验收
- 任何新增提示词分节 → `test:snapshot` 能回放（**I4**）
- 压缩后 DoneSpec 仍可执行（**关键回归**）
- 30 天模拟历史的召回：用 `session-query/` 的 lineage + FTS，准确率 ≥80%

- 判据 = **CI 红/绿**，不是我算的分数

|---|---|---|
| 存算分离 | `SessionPersistence` seam（`create`/`open`/`stat`/`list`/`export`） | 一个远端 provider（对象存储） |
| 多机执行 | `ssh/`（paired filesystem/subprocess/sandbox providers） | 复用 |
| 沙箱 | `sandbox/`（bwrap/Landlock/Seatbelt）、`sandbox-policy`、`fs-sandbox` | 复用；**删掉 v1 的"cmd_key 白名单"** |
| 凭据 | `credentials/`（reference/record seam + human authorization flow） | 加"扫描消息流断言无明文"的门禁 |
| 审批 | `ctx.approval`（closed outcome，**fail-closed**） | 把 D5 五类映射成 `permission-presets`（"bundles sandbox mode with an approval policy into one user-facing Permissions selector"） |

### 7.2 安全表述必须改正

v1 说"六道防线"，读起来像"安全了"。
**官方 `SAFETY.md` 的表述才是对的**：

> Sandboxing, approval prompts, and permission controls **can reduce risk, but they do not guarantee isolation or prevent damage.**
> Even correctly enforced restrictions cannot protect resources that the project is allowed to access.
> **Do not rely on DeepSeek Harness as the sole security control for untrusted workloads.**

**v2 必须写一份自己的 `SAFETY-<我们的层>.md`**，逐条说明"我们挡不住什么"。这是 `05` §1.6 的落地。
