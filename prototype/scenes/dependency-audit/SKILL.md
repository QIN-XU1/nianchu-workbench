# 依赖审计 技能

> 依赖审计最容易犯的错：**只看 CVE 数量**。
> 一个 0 CVE 的依赖可能已经三年没更新、维护者跑路、许可证是 AGPL；
> 一个 5 CVE 的依赖可能全是 devDependency 里的低危、根本不进生产包。
> 所以判据是**三维并行**：漏洞 × 许可证 × 维护性，缺一不可。

## 什么时候用

- 引入新依赖前
- 定期体检（每季度）
- 要发布/开源前
- 出现供应链安全事件后

## 什么时候**不**用

- 只看单个包的 API 用法 → 直接查文档
- 要升级依赖的具体步骤 → `dep-upgrade`
- 要看整个项目的架构 → `source-dive`

## 第 1 步：先分清「进不进生产」

这是最重要的一步，因为它决定了后面所有风险的权重。

| 类型 | 进生产包吗 | 风险权重 |
|---|---|---|
| **dependencies** | 是 | 全部适用 |
| **devDependencies** | 否（构建期） | 漏洞只在构建机，许可证仍要看 |
| **peerDependencies** | 由使用者提供 | 需声明版本范围 |
| **optionalDependencies** | 可能 | 要验「缺失时能降级」 |

⛔ 最常见误判：把 devDependency 的高危 CVE 报成「生产风险」——
它根本不进用户的机器。

## 第 2 步：漏洞维度（不只看数量）

### 2.1 三个问题

| 问题 | 为什么 |
|---|---|
| 漏洞在**实际调用的代码路径**上吗？ | 一个 XML 解析库的 XXE 漏洞，如果你只解析 JSON，就不可达 |
| 是**直接依赖**还是**传递依赖**？ | 传递依赖你无法直接升级，要等上游 |
| 有没有**修复版本**？ | 没有修复版本 = 只能换或自己打补丁 |

### 2.2 可达性判定（降噪的关键）

大部分扫描器报的 CVE 是不可达的。判据：

| 情况 | 风险 |
|---|---|
| 漏洞函数在你调用的路径上 | 高 |
| 漏洞函数在你的依赖里，但你没调用 | 中（可能被未来的代码调用） |
| 漏洞在 devDependency | 低（除非 CI 会执行外部输入） |
| 漏洞在可选功能里且你没启用 | 低 |

⛔ 不做可达性分析就报「有 37 个高危」= 噪音，会让人无视真风险。

## 第 3 步：许可证维度（最常被忽略）

### 3.1 许可证分级

| 级别 | 许可证 | 对闭源商用 |
|---|---|---|
| **宽松** | MIT / ISC / BSD / Apache-2.0 | ✅ 可以 |
| **弱 copyleft** | LGPL / MPL / EPL | ⚠ 动态链接可，静态链接需开源 |
| **强 copyleft** | GPL / AGPL | ❌ 传染，AGPL 连 SaaS 都算 |
| **不可用** | 无许可证 / 商业限制 / SSPL | ❌ 默认不能用 |

### 3.2 三个陷阱

1. **传递依赖的许可证也算**：你的直接依赖 MIT，但它的依赖是 GPL → 你也被传染
2. **AGPL 的 SaaS 条款**：AGPL 的软件，只要你通过网络提供服务，就要开源——很多人以为「我不分发」就没事
3. **无许可证 ≠ 免费**：没有 LICENSE 文件 = 保留所有权利 = 法律上不能用

⛔ 「这个包很流行肯定没问题」是最危险的假设。

## 第 4 步：维护性维度（未来的风险）

### 4.1 五个信号

| 信号 | 危险阈值 |
|---|---|
| 最后发布日期 | > 2 年 |
| 未处理 issue 数 | > 100 且无响应 |
| 单维护者 | bus factor = 1 |
| 已声明 deprecated | 任何 |
| 版本 0.x | 任何（API 不稳定） |

### 4.2 「幽灵依赖」检查

依赖还在但你其实没在用 → 直接删掉，减少攻击面。

## 第 5 步：三档处置

| 档 | 条件 | 动作 |
|---|---|---|
| **必须换** | 强 copyleft 且闭源商用 / 无许可证 / 高危且不可达性无法排除 | 找替代或自己实现 |
| **必须锁** | 有中危 / 维护性差但功能必要 | 锁版本 + 监控 + 计划替换 |
| **可以留** | 宽松许可 + 低危或不可达 + 维护活跃 | 定期复查即可 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 三维都过，无「必须换」
- WARN = 有「必须锁」项
- FAIL = 有「必须换」项
- UNKNOWN = 拿不到依赖清单/许可证信息

**1. 依赖清单分类**
| 依赖 | 类型（prod/dev） | 版本 |
|---|---|---|

**2. 漏洞**
| 依赖 | CVE | 可达吗 | 有修复版吗 | 风险 |
|---|---|---|---|---|

**3. 许可证**
| 依赖 | 许可证 | 级别 | 传染？ |
|---|---|---|---|

**4. 维护性**
| 依赖 | 最后发布 | bus factor | 结论 |
|---|---|---|---|

**5. 处置**
| 依赖 | 档位 | 理由 |
|---|---|---|

**6. 判不了的部分**
- <拿不到许可证/可达性无法分析>

## 假阳性清单（这些不算「有风险」）

- devDependency 的漏洞（不进生产）
- 不可达的漏洞函数
- 宽松许可证的 copyleft 误报
- 已声明 deprecated 但你本来就要删的包

## 假阴性清单（最常漏的 8 类）

1. **只看 CVE 数量**不看可达性
2. **忽略传递依赖的许可证**
3. **AGPL 的 SaaS 条款**（以为不分发就没事）
4. **无许可证**当成免费
5. **devDependency 漏洞**报成生产风险
6. **bus factor = 1** 的包没有备份方案
7. **0.x 版本**的 API 不稳定风险
8. **幽灵依赖**没清理

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs        # 提交前跑（含体量/空catch等）
node tools/evolve/evolve.mjs verify       # 台账完整性
```

## 与其他技能的关系

- `dep-upgrade`：决定要换之后的具体升级步骤
- `security-review`：代码级安全（本技能是依赖级）
- `supply-chain`：供应链攻击（本技能是已知漏洞）
- `release-gate`：发布前把依赖审计作为一道闸
- `tech-selection`：选型时把许可证作为硬条件

## 边界（如实说清）

- 漏洞数据库有滞后，0 CVE ≠ 安全
- 可达性分析需要读代码，工具只能做启发式
- 许可证的传染性有法律解释空间，最终要法务确认
- 维护性判断是概率性的，活跃项目也可能突然跑路
- 本技能不产出修复代码，只产出「该不该用」
