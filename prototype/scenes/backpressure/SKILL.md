# 背压（Backpressure）技能

> 没有背压的系统：上游猛灌，下游处理不过来，队列无限涨 → 内存爆 → 全挂。
> 判据：**上游产生的速度持续大于下游处理速度时，系统是「优雅拒绝」还是「耗尽崩溃」？**

## 什么时候用

- 生产/消费速率不匹配
- 流量突增
- 队列/内存无限增长
- 异步处理链

## 什么时候**不**用

- 同步请求-响应（天然有背压：响应慢客户端就等）

## 第 1 步：先认出「无背压」的征兆

| 征兆 | 说明 |
|---|---|
| 队列长度持续增长 | 消费跟不上 |
| 内存随流量涨 | 缓冲无上限 |
| 延迟随负载指数上升 | 排队积压 |
| 上游超时但下游还在处理 | 请求堆积 |

## 第 2 步：四种背压手段

| 手段 | 做法 | 代价 |
|---|---|---|
| **限流** | 拒绝超过处理能力的请求 | 拒绝部分用户 |
| **丢弃** | 丢掉不重要的（如旧数据） | 丢数据 |
| **缓冲** | 队列（但必须有上限） | 延迟、内存 |
| **降级** | 返回简化结果 | 功能缩水 |

★ 核心：**必须有「上限」**。无上限的缓冲不是背压，是定时炸弹。

## 第 3 步：丢弃策略（当必须丢时）

| 策略 | 适用 |
|---|---|
| **丢最新**（尾部丢弃） | 数据快照类 |
| **丢最旧**（头部丢弃） | 实时监控（只要最新） |
| **优先级丢弃** | 先丢低优先级 |
| **随机丢弃** | 均匀降载 |

⛔ 「丢哪个」是业务决策，不能随便丢。

## 第 4 步：给上游反压信号

| 机制 | 说明 |
|---|---|
| 队列满 → 拒绝 | 明确告诉上游慢点 |
| 响应 429/503 | 带 Retry-After |
| TCP 背压 | 缓冲满自然阻塞（同进程） |
| 拉模式 | 消费者按能力拉（Kafka） |

## 第 5 步：监控

| 指标 | 告警 |
|---|---|
| 队列长度 | 持续增长 |
| 丢弃率 | 上升 |
| 拒绝率 | 上升 |
| 处理延迟 | 上升 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 有上限 + 明确丢弃策略 + 给上游信号 + 监控
- WARN = 有队列但无丢弃策略
- FAIL = 无上限缓冲 / 内存随流量涨 / 无拒绝机制
- UNKNOWN = 拿不到流量模型

## 假阳性清单（这些不算「有背压」）

- 有队列但无上限
- 有内存缓冲但不清
- 从不拒绝

## 假阴性清单（最常漏的 8 类）

1. **无上限缓冲**（内存爆）
2. **无丢弃策略**
3. **拒绝但无 Retry-After**
4. **队列长度无监控**
5. **丢弃不按优先级**
6. **上游不知道要慢点**
7. **同步处理里无超时**
8. **延迟上涨无告警**

## 与其他技能的关系

- `rate-limit-design`：限流是背压的一种
- `queue-design`：队列容量与死信
- `circuit-breaker`：过载保护
- `graceful-degradation`：降级

## 边界（如实说清）

- 背压必然牺牲（拒绝/丢弃/延迟），要选牺牲什么
- 分布式下背压传递困难（跨服务）
- 本技能不实现，只设计策略
