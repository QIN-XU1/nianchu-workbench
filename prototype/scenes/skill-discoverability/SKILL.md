# 技能可发现性 技能

> 写了 100 个技能，用户问「怎么限流」，模型却选了「性能优化」——这不是技能不够，是**发现不了**。
> 判据：**用真实话术测，第 1 命中率 ≥80%、前 3 = 100% 吗？技能名会不会互相包含导致误选？**

## 什么时候用

- 技能/插件/工具库超过 20 个
- 要评审「可发现」这类声明
- 出现「明明有技能却没被用上」

## 什么时候**不**用

- 只有几个技能

## 第 1 步：造真实用户话术（不是关键词）

- 好：「怎么防止研报编造数字」→ 应命中 provenance
- 差：「provenance」→ 这是关键词不是话术，测不出真实场景

**话术要像用户会怎么问**，不能是技能名本身。

## 第 2 步：测两个指标

| 指标 | 要求 |
|---|---|
| 第 1 命中率 | ≥ 80% |
| 前 3 命中率 | = 100% |

第 1 命中差 = 排序有问题；前 3 差 = 目录里根本没覆盖。

## 第 3 步：技能名不能互相包含

`api-contract` 是 `api-error-contract` 的子串——用户问错误语义时可能两个都命中，排序错乱。**名字要唯一可辨**。

## 第 4 步：目录大小要可控

把全部技能的 name+desc 拼成常驻目录，**有字数上限**（如 12000）。超了要截断 desc 或精简。

## 反例（写下来防复发）

- ✗ 用技能名当测试话术 → 测不出真实发现
- ✗ 只看前 3 不看第 1 → 排序差但「命中」了
- ✗ 名字互相包含 → 排序错乱
- ✗ 目录无限长 → 上下文爆

## 自检清单

- [ ] 真实话术（非关键词）
- [ ] 第 1 命中 ≥80%、前 3 =100%
- [ ] 技能名无互相包含
- [ ] 目录 < 字数上限
