# 通知设计 技能

> 通知的失败两面：**发太多**（用户关通知/卸载）、**发丢了**（重要事件没收到）。
> 判据：**用户收到这条通知，会觉得「幸好告诉我」还是「又烦我」？**

## 什么时候用

- 站内信/推送/短信/邮件
- 用户抱怨通知太多/太少
- 重要事件通知不可靠

## 什么时候**不**用

- 无用户通知需求

## 第 1 步：分级（决定怎么发）

| 级别 | 渠道 | 打扰 |
|---|---|---|
| **紧急**（安全/资金） | 短信+推送 | 可即时 |
| **重要**（订单/审批） | 推送+站内 | 聚合 |
| **一般**（动态/推荐） | 站内/摘要 | 不即时 |
| **营销** | 可关 | 明确 opt-in |

⛔ 所有事都用短信/推送 = 用户关掉一切 = 真紧急也收不到。

## 第 2 步：去重与聚合（防淹没）

| 手段 | 说明 |
|---|---|
| **去重** | 同一事件不重复通知 |
| **聚合** | 「3 人赞了你的帖子」而非 3 条 |
| **节流** | 一段时间内最多 N 条 |
| **静默时段** | 夜间不发非紧急 |

## 第 3 步：可靠投递

| 问题 | 处理 |
|---|---|
| 发失败 | 重试（有限次）+ 降级渠道 |
| 必达通知 | 多渠道路由（推送失败转短信） |
| 状态追踪 | 已发/已读/失败 |
| 幂等 | 不重复发（见 `idempotency-design`） |

## 第 4 步：用户控制

| 项 | 说明 |
|---|---|
| 退订/开关 | 每类可单独关 |
| 免打扰 | 时段/勿扰模式 |
| 合规 | 营销需 opt-in（同意） |

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 营销混进交易通知 | 用户漏看重要通知 |
| 无去重 | 重复轰炸 |
| 无静默时段 | 半夜响 |
| 只有一条通道 | 通道挂全丢 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 分级 + 去重聚合 + 可靠投递 + 用户控制
- WARN = 有分级但无去重/节流
- FAIL = 全走一通道 / 无去重 / 营销混交易
- UNKNOWN = 拿不到通知需求

## 假阳性清单（这些不算「通知设计好」）

- 所有通知一个渠道
- 无去重（重复发）
- 营销和交易混一起

## 假阴性清单（最常漏的 8 类）

1. **不分级**（全短信/推送）
2. **无去重聚合**（淹没）
3. **无静默时段**（半夜响）
4. **单通道**（挂全丢）
5. **无降级渠道**
6. **营销混交易**（漏看）
7. **无用户开关**
8. **必达不保证**

## 边界（如实说清）

- 各渠道有平台限制（推送/短信成本）
- 打扰控制与业务目标常冲突，要平衡
- 本技能不实现，只设计
