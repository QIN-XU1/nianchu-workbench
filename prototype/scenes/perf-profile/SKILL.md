# 性能剖析 技能

> 性能优化的第一条纪律：**没有测量就没有优化**。
> 「看起来更快了」不是结论，是感觉。唯一有效的结论是「同环境、同输入下，X 从 A 变成 B」。
> 第二条纪律：**先判断是算法级还是常数级**。O(n²) 改常数是白费力气，这是最常见的浪费。

## 什么时候用

- 响应慢、页面卡、CPU 高、内存持续上涨
- 想优化但不确定瓶颈在哪
- 优化过了，想确认「真的变快了」
- 怀疑某处是热点但没有证据

## 什么时候**不**用

- 是功能 bug（返回错结果）→ `debug-repro`
- 只是「代码看起来可以更快」但没有实测 → 先测，别猜
- 要做容量规划/架构选型 → `design-review`

## 第 0 步：先把「慢」定义成数字

### 0.1 三问定目标

| 问题 | 为什么必须答 |
|---|---|
| 哪个操作慢？ | 「系统慢」无法定位；要具体到「打开某页面」「执行某命令」 |
| 多慢算慢？ | 没有阈值就无法判断「优化完了没有」 |
| 谁的体验受影响？ | 单用户本地 vs 100 并发，瓶颈完全不同 |

把目标写成可验证形式：

- 差：「让它快一点」
- 好：「`/api/host-status` 的 P95 从 800ms 降到 200ms 以下，在本机、冷缓存下测得」

### 0.2 先确认「不是测量方式的问题」

在开始优化前，排除这三种假慢：

1. **首次运行开销**（JIT 预热、缓存未建、模块加载）→ 要测**热态**
2. **环境差异**（开发机 vs 生产、有无 SSD、有无并发）→ 要固定环境
3. **测量本身的开销**（日志、profiler、调试器）→ 要对比「关掉测量」时的数字

⛔ 最常见浪费：优化了半天，发现慢在「每次请求都重新扫描目录」——
那不是常数问题，是**重复工作**问题。

## 第 1 步：建立基线（跑 3 次取中位，记录完整条件）

### 1.1 基线必须记录的条件

- **环境**：OS / 运行时版本 / CPU 核数 / 内存
- **输入**：数据规模（多少条记录、多大文件）
- **状态**：冷缓存还是热缓存 / 首次还是第 N 次
- **方式**：怎么测的（命令、脚本、profiler）
- **结果**：3 次分别多少 + 中位数

缺任何一项，后续对比都不可信。

### 1.2 为什么要跑 3 次取中位

单次测量受 GC、调度、磁盘缓存影响，波动可达数倍。
取中位数能过滤掉偶发尖峰；**同时记录最大最小值**能暴露不稳定性。

　　`for i in 1 2 3; do /usr/bin/time -f "%e s  %M KB" <命令>; done`

### 1.3 建立「可重复的最小输入」

优化时要用**同一份输入**，否则数字没有可比性。

- 数据太大 → 造一份小的但**结构相同**的
- 数据是随机的 → 固定随机种子
- 数据来自网络 → 先存成本地文件

本仓库实例：`size-guard.mjs` 扫 373 个源文件；`coverage-matrix` 跑 16 家对手。
这些规模固定，适合做基线。

## 第 2 步：找热点（用 profiler，不用直觉）

### 2.1 三种手段，按精度递增

| 手段 | 精度 | 成本 | 适用 |
|---|---|---|---|
| **打点计时** | 函数级 | 低（改代码） | 已怀疑某几个函数 |
| **CPU profiler** | 行级 | 中 | 不知道慢在哪 |
| **采样分析** | 行级 + 调用栈 | 中 | 需要看调用链 |

### 2.2 Node.js 的两种常用方式

　　`node --cpu-prof --cpu-prof-dir=./prof <脚本>`（生成 .cpuprofile）
　　`node --prof <脚本> && node --prof-process isolate-*.log`（生成可读报告）

### 2.3 打点计时的最小实现

在可疑区间前后取时间，输出耗时。**不要用日志级别判断**，要真的输出数字：

- 开始时间用 `process.hrtime.bigint()`（纳秒精度，不受系统时钟调整影响）
- 结束时间同样，相减转毫秒
- 关键：**打点本身要便宜**，否则测出来的是打点开销

### 2.4 判定「算法级 vs 常数级」

这是本技能最重要的判断。方法：**改变输入规模，看耗时怎么变**。

| 输入翻倍时耗时 | 结论 | 优化方向 |
|---|---|---|
| 约 2 倍 | **线性 O(n)** | 常数优化有意义（减少每单位开销） |
| 约 4 倍 | **平方 O(n²)** | 常数优化**无用**，必须改算法 |
| 基本不变 | **常数 O(1)** | 已是最优，别动 |
| 约 1.5 倍 | O(n log n) | 常数优化空间有限 |

⛔ 不做这一步就开始微优化（减少字符串拼接、换循环写法），是最常见的浪费。
本仓库踩过：`size-guard` 曾把目录当 0 字节文件（展平只下钻两层），
那不是性能问题，是**逻辑错误导致统计错误** —— 优化前先确认「算得对不对」。

### 2.5 热点排序，只改前 3

profiler 会给出很长的列表。按耗时降序，**只处理前 3 个**。

理由：前 3 个通常占 70%+ 的时间；改第 10 个对整体几乎无影响，但风险和成本一样高。

## 第 3 步：小步改（一次只改一处）

### 3.1 一次只改一处的原因

如果一次改 3 处，快了不知道是哪处起的作用，慢了也不知道是哪处拖的。
更糟：某处变快、另一处变慢，净效果为正，你会把**有害改动**当成有效保留下来。

### 3.2 常见的四类优化（按性价比排序）

| 类型 | 例子 | 风险 |
|---|---|---|
| **消除重复工作** | 同一份数据只读一次、结果缓存 | 低（但要处理失效） |
| **减少数据量** | 只取需要的字段、提前过滤 | 低 |
| **换数据结构** | 数组查找 → Map 查找（O(n)→O(1)） | 中（要改调用方） |
| **改算法** | 嵌套循环 → 一次遍历 | 高（要重写逻辑） |

⛔ 微优化（减少字符串拼接、内联函数、避免闭包）**放最后**，且只在算法已最优时做。

### 3.3 每改一处，立刻重测

改完立刻跑基线命令，记录新数字。不通过就回滚，别攒着。

## 第 4 步：给可对比的数字（这一步决定结论可信度）

### 4.1 对比表必须同环境同输入

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 耗时中位数 | 800ms | 210ms | -73.8% |
| 耗时最大值 | 1200ms | 350ms | -70.8% |
| 内存峰值 | 420MB | 180MB | -57.1% |

### 4.2 必须报告「没变好」的情况

如果优化后数字没变或变差，**如实说「没优化到」**，并给出可能原因：

- 热点判断错了（改的不是真瓶颈）
- 瓶颈在别处（I/O、网络、GC）
- 优化引入了新开销，抵消了收益

⛔ 「理论上应该更快」不是结论。数字没变就是没变。

### 4.3 检查「有没有把问题挪走」

优化后要确认：

- 总耗时降了，但**某处变慢了**？（把工作挪到了别的地方）
- 内存降了，但**CPU 涨了**？（用计算换内存）
- 单次快了，但**首次变慢了**？（预计算挪到启动）

净效果才是结论。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 有基线、有热点证据、有对比数字、且确实变快
- WARN = 变快了但未达目标阈值
- FAIL = 没变快 / 变慢 / 把问题挪到别处
- UNKNOWN = 无法建立稳定基线（环境波动大、输入不可控）

**1. 目标**
- 哪个操作：<>
- 阈值：<>
- 可验证形式：<>

**2. 基线**
- 环境：<OS/运行时/CPU/内存>
- 输入规模：<>
- 状态：<冷/热缓存>
- 3 次结果：<数值> · 中位：<>

**3. 热点**
- 手段：<打点/profiler>
- 前 3 热点：<函数 + 占比>
- 算法级判定：输入翻倍 → 耗时变为 <X 倍> → 结论 <O(n)/O(n²)/O(1)>

**4. 改动**
| 步 | 改了什么 | 类型 | 改后数字 |
|---|---|---|---|

**5. 对比**
| 指标 | 前 | 后 | 变化 |
|---|---|---|---|

- 是否把问题挪走：<检查结果>

## 假阳性清单（这些不是性能问题）

- 首次运行比后续慢（JIT/缓存预热，正常）
- 单次尖峰但中位数稳定（GC 或调度，正常）
- 加了日志后变慢（测量开销）
- 不同机器上的绝对数值差异（环境不同）
- 数据量小的时候「优化」看不出差别（正常，规模不够）

## 假阴性清单（最常漏的 8 类）

1. **不测基线就优化**（改完无法证明变快了）
2. **只跑 1 次**（波动被当成真实差异）
3. **不区分冷/热缓存**
4. **不做规模测试就微优化**（O(n²) 改常数，白费）
5. **一次改多处**（无法归因）
6. **只看平均值不看 P95/最大值**（少数慢请求被平均掩盖）
7. **把问题挪到别处**（总耗时降了但某处变慢）
8. **报告「应该更快」而没有数字**

## 本仓库可用的命令

```bash
node --cpu-prof --cpu-prof-dir=./tmp/prof tools/evolve/coverage-matrix.mjs
node tools/quality/size-guard.mjs      # 扫 373 个源文件，可作为固定规模的基线样本
```

## 与其他技能的关系

- `debug-repro`：如果是「慢到超时/报错」，先用它定位是不是 bug
- `design-review`：优化需要改架构时，先评审方案
- `refactor-plan`：优化涉及大范围改结构时，按分期计划做
- `test-writing`：优化后补性能回归测试（阈值断言）
- `evidence-audit`：怀疑「优化数字」不可信时复核

## 边界（如实说清）

- 本机测量不等于生产环境表现；本地快了不代表线上快
- profiler 本身有开销，绝对数值会偏大（相对占比仍可信）
- 无法测量的部分（如用户感知的「卡」）需要真实用户数据
- 性能与正确性冲突时**优先正确性**；不能为了快而改变语义
- 拿不到稳定基线时（环境波动 > 优化幅度），结论只能是 UNKNOWN
- 本技能不判断「该不该优化」（那是收益/成本问题）
