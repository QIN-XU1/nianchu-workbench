# 功能开关 技能

> 开关最大的问题不是「怎么加」，而是**永远不删**。
> 一个系统跑三年，会有几百个开关，没人知道哪个还能关、哪个已经写死。
> 判据：**每个开关有没有「什么时候删」？** 没有的就是技术债。

## 什么时候用

- 灰度发布新功能
- 开关控制实验组
- 紧急关闭某个功能（kill switch）
- 长期的功能差异（套餐）

## 什么时候**不**用

- 一次性上线且不打算灰度（直接发）
- 只是配置项 → 用配置管理

## 第 1 步：四类开关（生命周期完全不同）

| 类型 | 用途 | 存活期 | 删法 |
|---|---|---|---|
| **发布开关** | 灰度新功能 | 短（天/周） | 全量后删 |
| **实验开关** | A/B 实验 | 中（实验期） | 实验结束删 |
| **运维开关** | kill switch / 降级 | 长 | 一直留（但是少数） |
| **权限开关** | 套餐/白名单 | 长 | 业务决定 |

⛔ 把「发布开关」当「权限开关」留着 = 技术债。**类型决定该不该删**。

## 第 2 步：生命周期（每个开关必须写）

| 阶段 | 动作 |
|---|---|
| 创建 | 登记：谁建的、为什么、什么类型、预计何时删 |
| 灰度 | 1% → 10% → 50% → 100% |
| 全量 | 发布开关到期 |
| **清理** | 删代码里的 if、删配置、删登记 |

⛔ 清理这一步必须有**负责人+日期**，否则永远不会发生。

## 第 3 步：评估点在哪（性能与正确性）

| 评估位置 | 问题 |
|---|---|
| 每个请求都远程查开关 | 延迟/依赖抖动 |
| 开关缓存多久 | 太长则关闭不及时 |
| 关闭后多久生效 | kill switch 要秒级 |
| 评估失败回退到哪 | 默认开还是关 |

⛔ kill switch 依赖远程且缓存 5 分钟 = 关闭要等 5 分钟 = 不是 kill switch。

## 第 4 步：灰度策略

| 策略 | 说明 |
|---|---|
| 按百分比 | 随机分流 |
| 按用户 ID 哈希 | 同一用户稳定 |
| 按属性（地区/套餐） | 定向 |
| 白名单 | 内部先行 |

⛔ 按百分比但每次请求随机 = 用户体验割裂（一会新一会旧）。要按用户稳定哈希。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 每个开关有类型+生命周期+清理计划 + 评估点合理
- WARN = 有开关无清理计划
- FAIL = 开关无类型 / kill switch 不即时 / 无负责人
- UNKNOWN = 拿不到开关清单

**1. 开关清单**
| 开关 | 类型 | 负责人 | 预计删除 |
|---|---|---|---|

**2. 评估点**
| 开关 | 评估位置 | 缓存 | 失败回退 |
|---|---|---|---|

**3. 灰度**
| 开关 | 策略 | 分桶 |
|---|---|---|

**4. 判不了的部分**
- <哪些开关归属不明>

## 假阳性清单（这些不算「开关管理好」）

- 有开关框架但从不删
- 没有类型标注
- kill switch 不即时

## 假阴性清单（最常漏的 8 类）

1. **发布开关不删**（技术债）
2. **无负责人/删除日期**
3. **kill switch 依赖远程缓存**（不即时）
4. **按请求随机分流**（体验割裂）
5. **评估失败无默认值**
6. **开关散落无登记**
7. **嵌套开关组合爆炸**
8. **开关改了代码但没删 if**

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁
```

## 与其他技能的关系

- `experiment-design`：实验开关的搭档
- `ci-pipeline`：开关要能在 CI 里被检查
- `release-pipeline`：灰度是发布的一部分
- `refactor-plan`：开关清理属于重构

## 边界（如实说清）

- 开关不是配置的替代品（配置是数据，开关是代码分支）
- 长期开关（权限/运维）合理存在，但应是少数
- 本技能不实现 SDK，只设计生命周期
