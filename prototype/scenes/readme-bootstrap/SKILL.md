# README 起手 技能

> README 只有一个任务：**让一个陌生人（或三个月后的你）在 2 分钟内判断「这是什么、我要不要用、怎么跑起来」。**
> 判断失败的 README，写得再长也没人读第二段。
> 所以本技能的纪律是：**第一段必须能独立成立，命令必须真跑过，缺口必须诚实写。**

## 什么时候用

- 新项目没有 README
- 旧 README 与现状脱节（命令过时、结构变了）
- 新人反复问「怎么跑」「代码在哪」

## 什么时候**不**用

- 已有 README，只是补一节 → `doc-write`
- 写 API 参考文档 → `doc-write`（参考型）
- 写版本更新 → `changelog` / `release-notes`
- 内部小脚本（一个文件、无依赖）→ 顶部注释足够

## 第 1 步：一句话说清「是什么」（最重要的 30 字）

### 1.1 一句话的公式

> **<做什么> 的 <形态>，用于 <谁> 在 <什么场景>。**

三个要素缺一不可：**做什么 / 是什么形态 / 给谁用**。

| 差 | 为什么差 |
|---|---|
| 「一个强大的工具集」 | 没说做什么 |
| 「基于 Node 的项目」 | 没说给谁、解决什么 |
| 「念初的代码仓库」 | 没说给谁用、解决什么 |

| 好 | 为什么好 |
|---|---|
| 「把多个工作区的改动合成一份报告的命令行工具，给需要跨仓库统一更新的维护者用」 | 做什么 + 形态 + 给谁 |
| 「本地优先的笔记系统，给不想把数据交给云服务的人用」 | 三个要素齐 |

### 1.2 一句话之后立刻给「要不要用」

紧接着一句话，说明**什么情况下你不该用它**：

> 如果你只是要管一个仓库，用 `git` 自带的就够了，不需要它。

⛔ 只写「适合谁」不写「不适合谁」，读者会误用，然后来提 issue。

### 1.3 第一屏的检验

把 README 前 20 行单独截出来，问：

- 我知道这是什么吗？
- 我知道该不该用吗？
- 我知道怎么跑吗？

**三个都是「是」才算过。**

## 第 2 步：30 秒跑起来（命令必须真跑过）

### 2.1 最少步骤原则

只写「从零到看见结果」的最少命令。不要写：

- 完整的环境配置（链到 `docs/setup.md`）
- 所有可选参数（链到参考文档）
- 开发环境搭建（单独一节或链出去）

### 2.2 标准三段

```bash
# 1. 装
pnpm install

# 2. 跑
pnpm start

# 3. 看到
# 打开 http://127.0.0.1:3000，应该看到首页
```

### 2.3 每条命令的三个要求

| 要求 | 说明 |
|---|---|
| **可复制** | 不带 `...`、不带占位符（除了明确标注的） |
| **真跑过** | 在干净环境跑过，不是「大概这样」 |
| **有预期输出** | 贴真实输出，或说清「应该看到什么」 |

⛔ **命令没跑过就写进 README，是 README 最常见的失败原因。**
你本地因为装了某个全局包所以能跑，读者跑就报 `command not found`。

### 2.4 前置条件必须写

在命令之前列出：

- 运行时版本（`Node >= 24`）
- 包管理器（`pnpm`，不是 npm）
- 系统依赖（`git`、`python` 等）
- 需要的凭证/服务（数据库、API key）

⛔ 把前置条件藏在「安装」一节中间，读者会在第 3 步才失败。

## 第 3 步：目录地图（一张表说清代码在哪）

### 3.1 表格形式

| 目录 | 放什么 | 什么时候会看 |
|---|---|---|
| `src/` | 源码 | 改功能 |
| `tools/` | 构建/校验脚本 | 改流程 |
| `docs/` | 文档 | 查用法 |
| `tests/` | 测试 | 加测试 |

### 3.2 只列「会看」的目录

- 不要列 `node_modules`、`.git`、`dist`
- 不要列到第三层（除非项目很小）
- 每个目录一句话说清「放什么」

### 3.3 给「我想改 X」的指路

比目录表更有用的是**按任务指路**：

| 我想… | 去哪 |
|---|---|
| 加一个命令 | `src/commands/` |
| 改配置项 | `src/config.mjs` |
| 加测试 | `tests/`，参考 `tests/example.test.mjs` |

⛔ 目录表是「按结构找」，任务表是「按目的找」。**后者对新人更有用。**

## 第 4 步：当前状态（诚实写缺口）

### 4.1 必须写的三样

| 项 | 例子 |
|---|---|
| **做到哪了** | 「核心功能可用，暂不支持多用户」 |
| **还差什么** | 「Windows 下路径含中文时可能失败（#124）」 |
| **稳定性** | 「实验性，API 可能变」/「生产可用」 |

### 4.2 为什么必须诚实

- 不写缺口 → 用户踩坑后认为你不可信
- 写了缺口 → 用户知道边界，反而更信任

本仓库原则：**「拿不到证据标 UNKNOWN，不因为写好了就说完成了」**。
这条同样适用于 README —— 没验证过的能力不要写成「支持」。

### 4.3 稳定性声明要具体

- 差：「仍在开发中」
- 好：「v0.x，API 可能不兼容变更；数据格式暂无迁移工具，升级前请备份」

## 第 5 步：文档索引（深内容链出去）

### 5.1 索引原则

README 只放「决定要不要用」的信息，深内容链出去：

| 内容 | 去哪 |
|---|---|
| 完整配置项 | `docs/config.md` |
| API 参考 | `docs/api.md` |
| 架构说明 | `docs/architecture.md` |
| 常见问题 | `docs/faq.md` |
| 贡献指南 | `CONTRIBUTING.md` |
| 变更历史 | `CHANGELOG.md` |

### 5.2 链接必须有效

- 站内链接用相对路径
- 每个链接都要能点开（本仓库用 `docs-index` 技能校验）
- 链接文字要有意义（不用「点这里」）

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 一句话成立 + 命令真跑过 + 目录/任务指路 + 缺口诚实 + 索引有效
- WARN = 有未覆盖项（如某些平台未验证）
- FAIL = 命令跑不通 / 只写优点不写缺口 / 一句话说不清是什么
- UNKNOWN = 无法验证（缺环境/缺权限）

**1. 一句话**
> <做什么> 的 <形态>，用于 <谁> 在 <什么场景>。不适合：<>

**2. 30 秒上手**
| 步骤 | 命令 | 真跑过 | 预期输出 |
|---|---|---|---|

**3. 前置条件**
- 运行时：<>
- 包管理器：<>
- 系统依赖：<>
- 凭证/服务：<>

**4. 目录地图**
| 目录 | 放什么 |
|---|---|

**5. 任务指路**
| 我想… | 去哪 |
|---|---|

**6. 当前状态**
- 做到哪：<>
- 还差什么：<>
- 稳定性：<>

**7. 判不了的部分**
- <哪些平台/场景未验证>

## 假阳性清单（README 不必写这些）

- 完整的环境配置（链出去）
- 所有可选参数（链出去）
- 贡献者名单（`CONTRIBUTORS.md`）
- 许可证全文（`LICENSE` 文件）
- 详细架构（`docs/architecture.md`）
- 截图（除非是产品的核心价值）
- 徽章墙（除了 CI 状态，其他意义不大）

## 假阴性清单（README 最常漏的 8 类）

1. **命令没跑过**（本地有全局包所以能跑）
2. **前置条件没写**（读者第 3 步才失败）
3. **只写适合谁不写不适合谁**（误用）
4. **目录表列到第三层**（信息过载）
5. **没有任务指路**（新人不知道从哪改）
6. **缺口藏着**（用户踩坑后不信你）
7. **链接失效**（文档链到不存在的文件）
8. **一句话说不清是什么**（「强大的工具集」）

## 本仓库可用的命令

```bash
node tools/quality/verify-docs.mjs   # 文档索引/数字/链接一致性
```

## 与其他技能的关系

- `doc-write`：README 里的深内容（配置/API）用它写
- `docs-index`：README 索引必须覆盖全部文档且不重复
- `changelog` / `release-notes`：版本相关文档
- `project-verdict`：项目整体状态判断（README 的「当前状态」应和它一致）
- `adr`：架构决策记录（README 链过去）

## 边界（如实说清）

- README 只能让读者「开始」，不能让他「精通」；精通需要参考文档
- 无法验证「读者能否理解」—— 需要真实用户测试
- 多平台/多运行时无法全部验证，未验证的必须标 UNKNOWN
- 截图会过期，无法自动校验
- 本技能不写「为什么这么设计」（那是 `adr`）
