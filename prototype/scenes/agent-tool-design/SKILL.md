# Agent 工具设计 技能

> 工具是 agent 的手。设计差的工具（描述模糊、参数含糊、错误无信息）会让模型反复调错。
> 判据：**模型只看工具描述，能不能判断「何时该用、怎么传参、失败了怎么办」？**

## 什么时候用

- 给 agent 加工具
- 模型频繁误用工具
- 设计 MCP/function calling

## 什么时候**不**用

- 给人类用的 API（那看 `api-doc`）

## 第 1 步：工具描述（决定模型用不用对）

| 要素 | 要求 |
|---|---|
| **一句话做什么** | 精确，不含糊 |
| **何时用 / 何时不用** | 划清边界（防误用） |
| **参数说明** | 类型/是否必填/范围 |
| **返回值** | 返回什么形状 |

⛔ 描述写「处理数据」= 模型不知道何时用。「读取某技能的完整正文（分步流程、判据、反例），当用户任务属于某技能类别时先调用」= 清楚。

## 第 2 步：参数 schema（少而明确）

| 原则 | 说明 |
|---|---|
| **参数少** | 越多越易错 |
| **必填明确** | required 列清 |
| **枚举优于自由文本** | 能枚举就用 enum |
| **默认值** | 可省的给默认 |
| **不要"万能参数"** | 一个参数塞 JSON = 模型易错 |

⛔ 参数太多或塞嵌套 JSON = 模型拼错。

## 第 3 步：返回格式（模型要能读）

| 原则 | 说明 |
|---|---|
| **结构化** | JSON 而非模糊文本 |
| **简洁** | 不要把海量数据全塞回（挤占上下文，见 `context-management`） |
| **有成功/失败明确标志** | ok/error 字段 |
| **错误可行动** | 告诉模型「为什么错、怎么改」 |

⛔ 返回一整页 HTML 塞进上下文 = 挤爆且模型抓不住重点。

## 第 4 步：错误反馈（工具好不好用的一半）

| 错误类型 | 反馈给模型 |
|---|---|
| 参数错 | 「参数 X 非法，应为 ...」 |
| 权限/不存在 | 「找不到 Y，可选：...」 |
| 瞬时失败 | 「暂时失败，可重试」 |

★ 好的错误信息让模型**自己纠正**；坏的（「error」）让模型瞎猜重试。

## 第 5 步：工具边界与安全

| 项 | 要求 |
|---|---|
| 幂等标注 | 让模型知道能不能重试 |
| 危险操作明示 | 「会删除」要写清 |
| 越界拦截 | 路径穿越/权限（工具侧兜底，不全靠模型守规矩） |
| 粒度 | 一个工具做一件事（别 CRUD 全塞一个） |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 描述含何时用/不用 + 参数精简 + 结构化返回 + 可行动错误
- WARN = 有描述但无「何时不用」
- FAIL = 万能参数 / 返回海量数据 / 错误无信息
- UNKNOWN = 拿不到工具定义

**1. 工具描述**
| 工具 | 一句话 | 何时不用 |
|---|---|---|

**2. 参数**
| 工具 | 参数数 | 有枚举 | 有无万能参数 |
|---|---|---|---|

**3. 返回与错误**
| 工具 | 结构化 | 错误可行动 |
|---|---|---|

**4. 判不了的部分**
- <拿不到的工具实现>

## 假阳性清单（这些不算「工具设计好」）

- 有描述但含糊
- 参数可行但太多
- 返回文本大杂烩

## 假阴性清单（最常漏的 8 类）

1. **描述不含「何时不用」**（误用）
2. **万能参数**（塞 JSON）
3. **参数太多**
4. **返回海量数据**（挤上下文）
5. **错误只说 error**（模型瞎试）
6. **无幂等标注**（重复副作用）
7. **危险操作不提示**
8. **一个工具做太多事**

## 边界（如实说清）

- 工具设计对模型能力有依赖（弱模型更需明确）
- 描述长度与清晰度要平衡
- 本技能不实现工具，只设计接口
