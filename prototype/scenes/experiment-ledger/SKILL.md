# 改进台账 技能

> 改进不是「改完就完了」。没有台账，三个月后没人知道「当时为什么改、有没有效、后来退了没」。
> 判据：**每条改进都能回答：假设是什么、改前基线多少、改后多少、验证器是谁、有没有回退？**

## 什么时候用

- 持续做工程改进/优化
- 要复盘「哪些改动真的有效」
- 要证明「不是拍脑袋改」

## 什么时候**不**用

- 一次性小修补（无复盘价值）

## 第 1 步：一条记录要有的字段

| 字段 | 作用 |
|---|---|
| 假设 | 你认为改什么会带来什么效果（可被证伪） |
| 基线 | 改前的可测量值 |
| 预期 | 改后应该到多少 |
| 判定标准 | 什么算成功、什么算失败 |
| 结果 | 改后实测值 |
| 结论 | 保留 / 回退 / 需观察 |
| 验证器 | 哪条命令能复算这个结论 |

**没有验证器的结论不算结论**——它只是说法。

## 第 2 步：失败也要记（负结果同样有价值）

改坏了、没效果、回退了——都要记，并写清为什么。**只记成功的台账是宣传，不是台账。**

## 第 3 步：可复算 + 可追溯

- 每条记录带时间戳与执行者
- 验证器是真实可跑的命令（不是「见某文档」）
- 台账本身有完整性检查（条数、id 唯一、字段齐全）

## 反例（写下来防复发）

- ✗ 只有「改了什么」，没有「改前多少、改后多少」 → 无法判断有没有效
- ✗ 只记成功，失败/回退不记 → 下次重蹈覆辙
- ✗ 结论没有验证器 → 无法复算
- ✗ 台账与代码脱节（记录了但代码没改） → 台账成摆设

## 自检清单

- [ ] 每条有假设/基线/预期/判定/结果/结论/验证器
- [ ] 失败与回退也记录
- [ ] 验证器是可跑命令
- [ ] 台账有完整性检查
