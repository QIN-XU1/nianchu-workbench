# 模型服务（ML Serving）技能

> 模型服务的难点不在「跑起来」，而在**版本、灰度、监控、以及「线上效果悄悄变差」**。
> 判据：**模型效果下降了，你能不能发现？能快速回滚到上一版吗？**

## 什么时候用

- 部署 ML 模型到线上
- 模型迭代/多版本
- 线上效果监控

## 什么时候**不**用

- 离线批量预测

## 第 1 步：模型版本管理

| 项 | 要求 |
|---|---|
| 版本标识 | 每个模型版本可追溯（含训练数据/超参） |
| **制品存储** | 模型文件可复现加载 |
| 灰度 | 多版本并存 |

## 第 2 步：在线推理

| 项 | 注意 |
|---|---|
| 延迟 | 推理可能慢（要异步/批） |
| 资源 | GPU/内存 |
| 预热 | 冷启动慢 |
| 批处理 | 合并请求提吞吐（tradeoff 延迟） |

## 第 3 步：灰度与回滚

| 项 | 要求 |
|---|---|
| 影子 | 新模型只打日志不返回（对比） |
| 金丝雀 | 小流量新模型 |
| **回滚** | 效果差秒级切回旧版 |

★ 模型回滚必须快——上线新模型可能让效果变差，要能立刻退。

## 第 4 步：监控（最关键）

| 指标 | 说明 |
|---|---|
| **数据漂移** | 输入分布变了 |
| **概念漂移** | 输入→输出关系变了（效果降） |
| 预测分布 | 输出分布突变 |
| 业务指标 | 点击率/转化率 |
| 延迟/错误 | 服务健康 |

⛔ 只看服务健康（延迟/错误）不看效果 = 模型悄悄变差无人知。

## 第 5 步：特征一致性（训练/服务偏差）

| 问题 | 说明 |
|---|---|
| 训练用离线特征、服务用在线特征 | 计算逻辑不一致 → 效果崩 |
| 防法 | 特征store共享（见 `feature-store`）、一致性校验 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 版本可追溯 + 灰度回滚 + 漂移监控 + 特征一致
- WARN = 有部署但无漂移监控
- FAIL = 无版本 / 不能回滚 / 特征不一致
- UNKNOWN = 拿不到模型部署

**1. 版本**
| 项 | 有吗 |
|---|---|

**2. 灰度**
| 项 | 有吗 |
|---|---|
| 影子 | |
| 回滚 | |

**3. 监控**
| 指标 | 有吗 |
|---|---|

**4. 判不了的部分**
- <拿不到的模型信息>

## 假阳性清单（这些不算「serving 好」）

- 能推理但无版本
- 只看延迟不看效果
- 无漂移监控

## 假阴性清单（最常漏的 8 类）

1. **无版本追溯**
2. **不能快速回滚**
3. **无漂移监控**（效果悄悄降）
4. **特征训练/服务不一致**
5. **冷启动慢无预热**
6. **无灰度**
7. **只看服务健康不看效果**
8. **模型文件不可复现**

## 本仓库可用的命令

```bash
node tools/cost/meter.mjs        # 推理成本
node tools/quality/commit-gate.mjs
```

## 与其他技能的关系

- `feature-store`：特征一致
- `deployment-strategy`：灰度
- `observability-design`：监控
- `evaluation-design`：效果评估

## 边界（如实说清）

- 漂移检测是统计问题，有误报
- GPU 资源管理是独立问题
- 本技能不实现，只设计
