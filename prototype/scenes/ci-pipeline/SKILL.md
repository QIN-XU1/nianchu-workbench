# CI 流水线 技能

> CI 的核心价值不是「自动跑测试」，而是**「让失败无法被忽略，让成功值得相信」**。
> 一条会假绿的流水线比没有 CI 更糟：它训练团队「红了也照合」。
> 所以本技能的判据只有一条：**本地能复现 CI 的每一步，失败能定位到具体阶段。**

## 什么时候用

- 新建 CI
- CI 经常假绿/假红
- 流水线太慢（想加缓存/并行）
- 要在合入前加门禁

## 什么时候**不**用

- 只是本地脚本跑不起来（那是环境问题，不是 CI）
- 要审代码质量 → `code-review`
- 要做发布（不是合入）→ `release-pipeline`

## 第 1 步：分阶段（每阶段一个可判定的结果）

### 1.1 标准四阶段

| 阶段 | 做什么 | 失败意味着 | 典型耗时 |
|---|---|---|---|
| **装依赖** | `install`（含锁文件） | 环境/依赖问题 | 秒~分 |
| **构建** | 编译/打包/类型检查 | 代码不合法 | 分 |
| **测试** | 单测/集成/端到端 | 行为不符预期 | 分~十分 |
| **门禁** | 体量/文档/残留/安全 | 违反仓库约定 | 秒~分 |

**顺序原则**：便宜的放前面（快速失败），贵的放后面。

⛔ 常见错误：把门禁和测试放在同一阶段 —— 门禁失败了但测试还在跑，浪费好几分钟。

### 1.2 每阶段必须能独立判定

判据：**这一阶段失败，能不能一句话说清是什么问题？**

- 好：「构建失败：`toolkit.mjs:120` 类型不匹配」
- 差：「CI 挂了」

实现方式：每阶段有明确的**退出码约定**（见第 4 步）。

### 1.3 阶段间不共享可变状态

- 每阶段从**干净环境**开始（或明确恢复）
- 产物通过**显式路径**传递（不是「上一步留在某个全局目录」）
- 不依赖「上一步没清理的临时文件」

为什么：共享可变状态会导致「单独跑失败、一起跑成功」这类无法复现的问题。

## 第 2 步：钉版本（避免「昨天还好今天挂」）

### 2.1 三类必须钉的版本

| 对象 | 怎么钉 | 不钉的后果 |
|---|---|---|
| **运行时** | `node-version: 24.18.0`（精确） | 新版本行为变化导致失败 |
| **依赖** | 提交锁文件（`pnpm-lock.yaml`） | 每次装到不同版本 |
| **CI 动作/镜像** | `actions/checkout@v4`（不用 `@main`） | 上游改行为，你的 CI 突然变 |

⛔ `@latest` / `@main` 是定时炸弹：它今天能过，明天可能就不能过，而你没改任何代码。

### 2.2 锁文件必须「一致安装」

| 命令 | 行为 | 何时用 |
|---|---|---|
| `pnpm install` | 可能更新锁文件 | 本地开发 |
| `pnpm install --frozen-lockfile` | 锁文件不一致就**失败** | **CI 必须用这个** |

⛔ CI 里跑 `install` 而非 `--frozen-lockfile`，等于允许 CI 用不同版本依赖跑 ——
那本地绿、CI 红（或反之）就无法解释。

### 2.3 检查版本钉住了没有

　　`grep -nE "node-version|image:|uses:" .github/workflows/*.yml | grep -vE "@[0-9]|: *[0-9]+\.[0-9]+\.[0-9]+"`

输出为空 = 全部钉住了；有输出 = 有浮动版本。

## 第 3 步：缓存（要快，但不能错）

### 3.1 缓存键必须包含「会影响结果的一切」

| 缓存什么 | 键应包含 | 漏了会怎样 |
|---|---|---|
| 依赖 | 锁文件哈希 + 运行时版本 + OS | 用了不兼容的二进制依赖 |
| 构建产物 | 源码哈希 + 依赖哈希 + 构建配置 | 用了旧产物 |
| 测试数据 | 生成脚本哈希 + 种子 | 用了旧数据导致假绿 |

⛔ **缓存不失效 = 用了旧依赖**。这是「本地过了 CI 挂」的常见原因（CI 缓存了旧依赖）。

### 3.2 缓存的正确性检查

改一次依赖版本，看 CI 是否真的重新装：

- 重新装 → 缓存键正确
- 没重新装 → 缓存键漏了锁文件哈希

### 3.3 缓存不值得的时候

- 装依赖只要 5 秒 → 不要缓存（缓存本身有下载/上传成本）
- 缓存命中率低 → 不要缓存

判据：**缓存节省的时间 > 缓存维护成本**才加。

## 第 4 步：失败可见（本技能最重要的一步）

### 4.1 退出码约定（四态）

本仓库统一用四态，CI 必须遵守：

| 退出码 | 含义 | CI 行为 |
|---|---|---|
| **0** | PASS | 继续 |
| **1** | FAIL（明确失败） | 停止，报错 |
| **2** | UNKNOWN（环境问题/无法判定） | 停止，标注「需人工」 |
| **3** | WARN（未覆盖项，非阻断） | 继续，但记录 |

⛔ 把 UNKNOWN 当成 PASS 是最危险的：环境坏了却显示绿灯。

### 4.2 每阶段必须输出

| 输出 | 为什么 |
|---|---|
| 阶段名 | 知道卡在哪 |
| 完整错误信息 | 不用点进去猜 |
| 退出码 | 机器可判定 |
| 失败的具体文件:行号 | 能直接跳过去 |

### 4.3 禁止 `continue-on-error`

```yaml
# ⛔ 这是静默失败
- run: npm test
  continue-on-error: true
```

为什么禁止：它让失败**看起来成功**。如果某步可以失败，应该显式标记为「非阻断」并走 WARN（退出码 3），而不是静默吞掉。

本仓库实例（正面）：`commit-gate.mjs` 5 项快检查里，
`audit-doc-numbers` 返回 exit 3 被标成 `⚠ WARN（未覆盖项，非阻断）`，
其余 4 项 exit 0。**WARN 是显式的，不是被吞掉的**。

### 4.4 日志要能复现问题

失败时日志必须包含：

- 完整命令（含参数）
- 运行时版本
- 工作目录
- 完整 stderr（不只最后一行）

## 第 5 步：本地可复现（CI 可信的前提）

### 5.1 判据

**CI 跑的每一步，本地都能用同样命令跑出来。**

做不到的后果：CI 红了，本地没法复现，只能靠「再推一次试试」——那是赌博。

### 5.2 实现方式

- 命令写进 `package.json` scripts（CI 与本地用同一个）
- 环境差异用配置文件显式声明（不是靠 CI 的隐式环境变量）
- 提供「一键跑全量」的入口

　　`node tools/quality/commit-gate.mjs`（本地等同 CI 的完整检查）

### 5.3 环境差异清单

必须显式记录 CI 与本地可能不同的地方：

| 项 | CI | 本地 | 是否影响 |
|---|---|---|---|
| OS | Linux | Windows | **是**（路径分隔符/大小写敏感） |
| Node 版本 | 24.18.0 | 24.18.0 | 否 |
| 时区 | UTC | +08:00 | **是**（日期断言） |
| 文件系统大小写 | 敏感 | 不敏感 | **是**（导入路径） |

⛔ Windows 开发 + Linux CI 是最常见的「本地过我不过」来源。
路径要用 `path.join`（不用字符串拼 `/`），文件名大小写要一致。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 分阶段清晰 + 版本钉住 + 缓存正确 + 失败可见 + 本地可复现
- WARN = 有非阻断项（列出）
- FAIL = 有静默失败 / 版本浮动 / 本地无法复现
- UNKNOWN = 无法确认 CI 环境（拿不到配置）

## 假阳性清单（这些不是 CI 问题）

- CI 比本地慢（环境/网络差异，正常）
- 首次跑慢（缓存未命中，正常）
- 不同 OS 的绝对路径不同（用 path 处理即可）
- 测试并行执行导致顺序不同（只要结果一致）
- 缓存未命中但结果正确

## 假阴性清单（最常漏的 8 类）

1. **`continue-on-error` 静默吞掉失败**
2. **CI 用 `install` 而非 `--frozen-lockfile`**
3. **动作/镜像用 `@main`/`@latest`**
4. **缓存键漏了锁文件哈希**（用了旧依赖）
5. **UNKNOWN 被当成 PASS**
6. **日志只有最后一行**（无法定位）
7. **本地无法复现 CI**（只能重推试）
8. **Windows 开发 + Linux CI 的路径/大小写问题**

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs          # 5 项快检查（可作 CI 门禁阶段）
node tools/quality/size-guard.mjs           # 体量红线（373 文件，退出码 1）
node tools/quality/scan-mutation-residue.mjs  # 调试残留
node tools/quality/verify-docs.mjs          # 文档一致性
```

## 与其他技能的关系

- `release-pipeline`：CI 管合入，发布流水线管上线
- `release-gate`：发布前的完整门禁
- `code-review`：CI 绿了仍需人工审（CI 只覆盖已测路径）
- `test-writing`：CI 里跑的测试必须「改坏会红」
- `perf-profile`：CI 变慢时用它测量

## 边界（如实说清）

- CI 只能证明「已配置的检查通过」，不能证明代码正确
- 本地与 CI 的环境差异无法完全消除（OS/时区/文件系统），只能显式记录
- 缓存优化有收益上限；超过后加机器比加缓存划算
- 无法验证「CI 配置本身是否正确」（比如门禁规则写错了，CI 会一直绿）
- 没有 CI 日志访问权限时，结论只能是 UNKNOWN
- 本技能不涉及部署（那是 `release-pipeline`）
