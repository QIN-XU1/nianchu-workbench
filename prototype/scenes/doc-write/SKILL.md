# 文档撰写 技能

> 文档里最贵的不是「写得长」，而是**「写了但跑不通」**。
> 一条跑不通的命令，会让读者在第一个 5 分钟就放弃，并且**再也不信这份文档**。
> 所以本技能的核心纪律只有一条：**贴进文档的每条命令，都必须真的跑过。**

## 什么时候用

- 新功能需要用户文档
- 旧文档与代码脱钩（命令过时、截图过期、数字变了）
- 用户反复问同一个问题（说明文档没写清）

## 什么时候**不**用

- 从零写项目 README → `readme-bootstrap`
- 写版本更新 → `changelog` / `release-notes`
- 记录「为什么这么设计」→ `adr`
- 面向新人的入门教程 → 可用本技能，但结构要加「学习路径」

## 第 0 步：先确定文档类型（不同类型结构不同）

| 类型 | 读者 | 目的 | 结构 |
|---|---|---|---|
| **参考**（reference） | 已上手的人 | 查参数/接口 | 全面、可检索、少叙述 |
| **教程**（tutorial） | 新人 | 学会用 | 线性步骤、每步可验证 |
| **指南**（how-to） | 有目标的人 | 解决具体问题 | 问题 → 步骤 → 验证 |
| **解释**（explanation） | 想理解的人 | 建立心智模型 | 概念 → 关系 → 为什么 |

⛔ 四种混在一篇里，是文档难读的第一原因。
**先选一种**，其他类型的内容链出去。

## 第 1 步：固定结构（是什么 → 怎么用 → 注意什么）

### 1.1 三节结构

　　`# <功能名>` → `## 是什么`（解决什么问题、什么时候需要）→
　　`## 怎么用`（最少步骤，每步有可跑命令与真实输出）→ `## 注意什么`（坑/边界/限制）。

### 1.2 「是什么」的写法

- 差：「本模块提供了一系列工具函数用于……」
- 好：「把多个工作区的改动合成一份报告。当你需要跨仓库统一更新依赖时用它。」

判据：**读者能不能在 10 秒内判断「我需不需要它」？**

### 1.3 「怎么用」的写法

每个步骤必须包含：

1. **命令**（可复制）
2. **预期输出**（真实输出，不是「输出正常」）
3. **失败了怎么办**（常见错误）

　　`$ node tools/quality/verify-docs.mjs`

　　预期输出（真实）：
　　`文档自检：7 篇 · 验证文件 31 个 · 台账 326 条`
　　`四态: PASS —— 文档与仓库一致`

⛔ 预期输出必须**真的贴**。写「应该会输出成功」等于没写。

## 第 2 步：命令必须真跑过（本技能最硬的纪律）

### 2.1 跑过才算

| 做法 | 判定 |
|---|---|
| 复制命令到终端，回车，看到输出 | ✅ 合格 |
| 凭记忆写命令 | ❌ 不合格 |
| 命令是「大概这样」 | ❌ 不合格 |
| 用了 `...` 省略参数 | ❌ 不合格（读者无法复制） |

### 2.2 三种必须验证的东西

1. **命令能跑**（语法/参数/路径正确）
2. **输出与文档一致**（不是「以前是这样」）
3. **在干净环境能跑**（不是依赖你本地某个未提交的文件）

⛔ 第三条最常被忽略：你本地因为有个临时文件所以能跑，读者跑就报错。

### 2.3 拿不到真实输出的情况

如果命令需要真实环境（生产数据/凭证），不能编造输出。此时：

- 写「输出形如：」并标注**这是示例**
- 或用占位符 `<你的 token>` 并说明怎么获取
- 或提供本地可跑的替代方案

⛔ 编造输出是**最严重的文档错误** —— 它比没有输出更糟（读者会以为是真的）。

## 第 3 步：数字与路径必须与仓库一致

### 3.1 会过期的数字

| 数字类型 | 例子 | 怎么保证不过期 |
|---|---|---|
| 文件数 | 「373 个源文件」 | 由 `size-guard.mjs` 实测 |
| 条目数 | 「台账 326 条」 | 由 `evolve.mjs verify` 实测 |
| 通过数 | 「103/103 通过」 | 由验证脚本实测 |
| 版本号 | 「Node 24.18.0」 | 由 `package.json` engines |

### 3.2 校验方式

本仓库有专门的校验：

　　`node tools/quality/verify-docs.mjs`（数字/路径/验证文件一致性）
　　`node tools/quality/audit-doc-numbers.mjs`（更细的数字审计，exit 3 = 未覆盖项）

⛔ **改了台账/文件数，一定要重跑 `verify-docs.mjs`**，否则文档里的条数会过期。
这是本仓库最高频的文档失效原因。

### 3.3 路径必须真实存在

文档里写的每个路径，都要能用 `Test-Path` / `ls` 验证存在。

　　`node -e "console.log(require('fs').existsSync('tools/quality/verify-docs.mjs'))"`（返回 true 即存在）

⛔ 「大概在 tools 下面」这种路径等于没有。

## 第 4 步：格式规范（可读性）

### 4.1 中文标点

- 正文用**全角**：，。！？：；「」
- 代码/命令/路径用**半角**
- 中英文之间加空格（可选，但全篇要一致）

### 4.2 代码块标注语言

　　围栏开始行写语言名：三个反引号 + `bash`，结尾单独三个反引号。

- 中文文档里的代码块**必须标语言**（`bash` / `javascript` / `json` / `markdown`）
- 不标语言会导致高亮错误、复制时带错字符

### 4.3 表格优于长列表

对比类信息用表格（一眼能比），步骤类用有序列表（顺序重要）。

### 4.4 链接

- 站内链接用相对路径（`./docs/xxx.md`）
- 外部链接带完整 URL
- 链接文字要有意义（不用「点这里」）

## 第 5 步：修订旧文档（比写新文档更常见）

### 5.1 先判断「该修还是该重写」

| 情况 | 做法 |
|---|---|
| 结构对，个别命令/数字过时 | **修**（小改） |
| 结构对，但整节内容过时 | **重写该节** |
| 结构本身不对（比如是教程但读者是查参数） | **重写** |
| 文档描述的功能已不存在 | **删除并重定向** |

### 5.2 修订时不要做的事

- ⛔ 不要「保留旧内容只是标记为过时」—— 读者会读
- ⛔ 不要只改一半（改了命令没改输出）
- ⛔ 不要删掉「为什么」的部分（那是解释文档的价值）

### 5.3 修订后必须重跑

改了命令/数字，就要重跑验证：

　　`node tools/quality/verify-docs.mjs`

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 结构固定 + 命令真跑过 + 数字经校验 + 格式规范
- WARN = 有未覆盖项（如某些命令无法在当前环境跑）
- FAIL = 有编造输出 / 命令跑不通 / 数字过期
- UNKNOWN = 无法验证（缺环境/缺数据）

**1. 文档类型**：<参考/教程/指南/解释>（读者：<>）

**2. 命令验证**
| 命令 | 跑过吗 | 真实输出（贴） |
|---|---|---|

**3. 数字与路径校验**
- `verify-docs.mjs`：<结果>
- 路径存在性：<全部存在/哪些不存在>

**4. 格式检查**
- [ ] 中文全角标点
- [ ] 代码块标语言
- [ ] 表格/列表使用得当
- [ ] 链接有效

**5. 判不了的部分**
- <哪些内容无法验证>

## 假阳性清单（这些不算文档问题）

- 中英文间没加空格（风格问题，全篇一致即可）
- 行宽超过 80 字符（Markdown 不需要硬折行）
- 用了「你」而非「用户」（看文档风格，一致即可）
- 没有目录（短文档不需要）
- 截图不是最新（如果截图只是示意，可标注）

## 假阴性清单（最常漏的 8 类）

1. **命令没跑过就写进去**
2. **编造输出**（比没有更糟）
3. **数字过期**（改了台账没重跑 verify-docs）
4. **路径不存在**
5. **用了 `...` 省略**（读者无法复制）
6. **文档类型混杂**（教程+参考混在一起）
7. **只写「支持 X」不指出实现文件**（空话）
8. **修订后没重跑验证**

## 本仓库可用的命令

```bash
node tools/quality/verify-docs.mjs        # 文档自检（7 篇 · 31 个验证文件 · 台账 326 条）
node tools/quality/audit-doc-numbers.mjs  # 数字审计（exit 3 = 未覆盖项，非阻断）
```

## 与其他技能的关系

- `readme-bootstrap`：从零写 README 时用它
- `changelog` / `release-notes`：版本相关文档
- `adr`：决策类文档
- `docs-index`：文档索引一致性
- `code-review`：文档改动也要审（尤其命令是否真跑过）

## 边界（如实说清）

- 本技能保证「命令跑过」，**不保证「读者能理解」** —— 可理解性需要真实用户测试
- 无法验证「读者需要什么」，只能按文档类型推断
- 需要特定环境（生产凭证/大数据）的命令无法在此验证，结论只能是 UNKNOWN
- 截图无法自动校验是否过期
- 本技能不做翻译（多语言文档需要独立的术语表）
