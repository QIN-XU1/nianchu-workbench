# 优雅降级 技能

> 降级的本质是**优先级取舍**：出事时先保核心，牺牲非核心。
> 判据：**下游挂了一半的时候，用户还能完成最重要的那件事吗？**

## 什么时候用

- 有强依赖（第三方/下游服务）
- 要保证核心可用
- 做熔断/兜底

## 什么时候**不**用

- 无依赖的单体简单服务
- 要设计重试 → `retry-strategy`

## 第 1 步：功能分级（先定核心）

| 级别 | 定义 | 降级策略 |
|---|---|---|
| **P0 核心** | 不给就完全不能用（登录/下单） | 绝不降，宁可限流保 |
| **P1 重要** | 影响体验但能用（推荐） | 降为默认/缓存 |
| **P2 锦上添花** | 有更好（评论数/头像） | 直接隐藏 |

⛔ 不分级就降级 = 一出事全站砍，用户以为产品挂了。

## 第 2 步：降级动作（按从轻到重）

| 动作 | 说明 |
|---|---|
| **缓存兜底** | 返回旧缓存而非报错 |
| **静态默认** | 返回默认值 |
| **功能开关关闭** | 隐藏非核心功能 |
| **限流保核心** | 砍非核心流量保 P0 |
| **只读模式** | 停止写，保留读 |

## 第 3 步：触发方式

| 方式 | 说明 |
|---|---|
| **自动（熔断）** | 错误率/超时到阈值自动降 |
| **手动** | 人工开关（要秒级生效） |
| **定时** | 已知高峰预先降 |

## 第 4 步：恢复（最常漏）

| 要点 | 说明 |
|---|---|
| **自动恢复** | 下游恢复后自动切回（要有试探） |
| **半开** | 先放少量流量试探，成功再全量 |
| **防抖** | 别在好坏之间反复横跳 |

⛔ 只降不恢复 = 降级变常态，没人记得开回来。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 功能分级 + 降级动作 + 触发 + 恢复
- WARN = 有降级无自动恢复
- FAIL = 无分级 / 只降不恢复 / 降级后核心也不可用
- UNKNOWN = 依赖关系不明

**1. 功能分级**
| 功能 | 级别 | 降级动作 |
|---|---|---|

**2. 触发**
| 方式 | 阈值 |
|---|---|

**3. 恢复**
| 项 | 方式 |
|---|---|

**4. 判不了的部分**
- <依赖关系不清的>

## 假阳性清单（这些不算「有降级」）

- 出错就全站 500
- 有开关但不自动
- 只降不恢复

## 假阴性清单（最常漏的 8 类）

1. **不分级**（一刀切）
2. **核心也被降**（本末倒置）
3. **只降不恢复**（变常态）
4. **无半开试探**（恢复即雪崩）
5. **降级无监控**（不知道降了）
6. **降级后没提示用户**
7. **开关不秒级**
8. **缺省值不安全**（降级返回错数据）

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁
```

## 与其他技能的关系

- `retry-strategy`：重试失败后降级
- `rate-limit-design`：限流保核心
- `caching-strategy`：缓存兜底
- `observability-design`：降级触发监控

## 边界（如实说清）

- 降级是取舍，必有牺牲
- 降级逻辑本身也可能出错（要测试）
- 本技能不实现，只设计策略
