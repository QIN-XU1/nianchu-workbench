# 领域建模 技能

> 领域建模的价值是把**业务规则放到正确的抽象位置**，而不是散落在各处 if-else。
> 贫血模型 = 实体只有字段，所有逻辑在 service，业务规则没有归属。
> 判据：**一条业务规则，能不能指出它属于哪个领域对象/边界？** 指不出=没建模。

## 什么时候用

- 业务逻辑复杂、规则散落
- 要从业务梳理系统结构
- 要拆限界上下文

## 什么时候**不**用

- 简单 CRUD 系统（不必上 DDD）

## 第 1 步：先识别限界上下文（Bounded Context）

| 概念 | 说明 |
|---|---|
| **限界上下文** | 一个明确的业务边界，其内概念一致 |
| 边界内 | 术语一致 |
| 边界间 | 通过明确接口协作 |

| 常见边界 | 例 |
|---|---|
| 订单 | 下单、支付、履约的边界 |
| 库存 | 库存数量、出入库 |
| 用户 | 用户信息、认证 |

⛔ 把「订单、库存、用户」所有概念塞进一个模型 = 术语冲突、规则互相渗透。

## 第 2 步：识别实体、值对象、聚合

| 类型 | 特点 | 例子 |
|---|---|---|
| **实体** | 有唯一标识、有生命周期 | 订单（按 ID 区分） |
| **值对象** | 描述、无标识、不可变 | 地址、金额 |
| **聚合根** | 一组实体的根、一致性边界 | 订单（含订单项） |

| 判断 |
|---|
| 有 ID 且会变 → 实体 |
| 没 ID、整体比较 → 值对象 |
| 一致性边界 → 聚合根 |

★ 建模的核心是给**一致性边界**：一个聚合内数据强一致，聚合间通过事件/接口。

## 第 3 步：领域规则归属（避免贫血）

| 反模式 | 后果 |
|---|---|
| 实体只有字段，逻辑全在 service | 业务规则无归属、难维护 |
| 规则散落多处 if-else | 易改错 |

**做法**：行为方法放实体上（如 `order.cancel()` 校验取消条件），领域规则内聚。

## 第 4 步：领域事件

| 概念 | 说明 |
|---|---|
| 领域事件 | 业务发生的重要事实 |
| 触发 | 聚合内状态变化时 |
| 协作 | 跨上下文通过事件 |

⛔ 跨上下文直接调方法 = 耦合。用领域事件解耦（见 `event-driven`）。

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 没分边界 | 概念冲突 |
| 贫血模型 | 规则无归属 |
| 过度设计 | 小系统上 DDD 反而复杂 |
| 把表当领域 | 领域是业务概念，不是数据表 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 边界清晰 + 实体/值对象/聚合合理 + 规则内聚
- WARN = 有建模但贫血/边界模糊
- FAIL = 无边界 / 贫血 / 表当领域
- UNKNOWN = 拿不到业务描述

**1. 限界上下文**
| 边界 | 核心概念 |
|---|---|

**2. 领域对象**
| 名称 | 类型 | 标识 |
|---|---|---|

**3. 规则归属**
| 规则 | 归属对象 |
|---|---|

**4. 判不了的部分**
- <拿不到的业务流程>

## 假阳性清单（这些不算「领域建模好」）

- 有实体但逻辑全在 service（贫血）
- 没分边界
- 把表当领域对象

## 假阴性清单（最常漏的 8 类）

1. **没分限界上下文**（概念冲突）
2. **贫血模型**（规则无归属）
3. **聚合边界不清**
4. **值对象当实体**（或反之）
5. **跨边界直接调**（未用事件）
6. **过度设计**（小系统硬上 DDD）
7. **把数据库表当领域**
8. **规则散落无归属**

## 边界（如实说清）

- DDD 有学习成本，简单系统不必
- 建模要与业务沟通，不能闭门造车
- 本技能不实现，只设计
