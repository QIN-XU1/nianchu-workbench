# 工作流引擎 技能

> 工作流的核心是**状态机 + 持久化 + 可恢复**。没有持久化的流程，进程一挂全丢。
> 判据：**流程走到一半进程挂了，重启后能不能从断点继续，而不是从头或卡死？**

## 什么时候用

- 多步骤业务流程（审批/订单/开户）
- 长流程（跨天/跨服务）
- 要可视化/可恢复

## 什么时候**不**用

- 简单几步（顺序代码即可）

## 第 1 步：状态机（先定状态与转移）

| 要素 | 说明 |
|---|---|
| **状态** | 流程处于哪（待支付/已支付/已发货…） |
| **转移** | 什么条件从 A 到 B |
| **事件** | 触发转移的动作 |
| **守卫** | 转移的前置校验 |

⛔ 状态定义不清 = 流程卡在「中间态」不知下一步。

## 第 2 步：持久化（工作流引擎的关键）

| 项 | 要求 |
|---|---|
| **流程状态落库** | 每步转移持久化 |
| 可恢复 | 重启从最后状态继续 |
| 幂等 | 重复驱动不重复执行 |

★ 内存里的流程 = 进程挂了就丢。必须持久化。

## 第 3 步：编排模式

| 模式 | 说明 |
|---|---|
| **编排**（orchestration） | 中心协调者驱动各步 |
| 协同（choreography） | 各服务靠事件协作，无中心 |

## 第 4 步：长流程的坑

| 坑 | 处理 |
|---|---|
| 步骤超时 | 每步超时+补偿 |
| 死循环 | 最大步数/环检测 |
| 人工节点 | 等待人审批（见 `guardrails`） |
| 版本升级 | 运行中的流程用旧版还是新版 |

## 第 5 步：可观测

| 项 | 要求 |
|---|---|
| 流程视图 | 当前在哪个状态 |
| 历史 | 走过哪些步骤 |
| 卡住检测 | 长时间未推进告警 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 状态机清晰 + 持久化 + 可恢复 + 幂等
- WARN = 有状态机但恢复不全
- FAIL = 内存流程 / 无持久化 / 中间态卡死
- UNKNOWN = 拿不到流程定义

**1. 状态机**
| 状态 | 转移 |
|---|---|

**2. 持久化**
| 项 | 有吗 |
|---|---|

**3. 长流程**
| 坑 | 处理 |
|---|---|

**4. 判不了的部分**
- <拿不到的流程>

## 假阳性清单（这些不算「工作流引擎」）

- 内存流程不持久化
- 状态不清
- 无恢复

## 假阴性清单（最常漏的 8 类）

1. **内存流程**（挂了丢）
2. **状态定义不清**（卡中间态）
3. **无幂等**（重复驱动）
4. **无超时**（卡死）
5. **无死循环保护**
6. **版本升级混乱**
7. **无流程视图**（不知到哪）
8. **无卡住告警**

## 与其他技能的关系

- `distributed-transaction`：跨服务一致性
- `event-driven`：事件协作
- `idempotency-design`：幂等
- `scheduler`：定时驱动

## 边界（如实说清）

- 工作流引擎有学习成本
- 长流程版本管理是难点
- 本技能不实现，只设计
