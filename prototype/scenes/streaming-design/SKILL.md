# 流式输出设计 技能

> 流式的价值是**首字节快**（用户不用等全部生成）。但流式引入新问题：
> **中途出错怎么办、连接断了、客户端怎么知道结束、流式内容能否重放**。
> 判据：**流到一半断了，客户端知道是失败还是正常结束吗？**

## 什么时候用

- LLM 逐字输出
- 大文件/大数据分块传输
- 要低首字节延迟

## 什么时候**不**用

- 响应小且快（普通响应够）

## 第 1 步：传输方式

| 方式 | 说明 |
|---|---|
| **SSE**（Server-Sent Events） | 单向服务端推，简单 |
| **chunked**（HTTP 分块） | 通用 |
| **WebSocket** | 双向，重 |

## 第 2 步：结束与错误的信号（关键）

| 信号 | 说明 |
|---|---|
| **明确的结束标记** | `[DONE]` 或 event: end |
| **错误事件** | 中途失败要发 error event（不是静默断） |
| 心跳 | 防中间层超时断 |

⛔ 流断了但客户端以为是正常结束 = 用户拿到半截数据还以为完整。**必须有明确结束/错误标记。**

## 第 3 步：断线处理

| 情况 | 处理 |
|---|---|
| 客户端断 | 服务端停止生成（省资源） |
| 服务端断 | 客户端可重连续传（如支持） |
| 中途超时 | 心跳保活 + 长超时 |

## 第 4 步：可靠性

| 问题 | 处理 |
|---|---|
| 流式内容要持久化吗 | 是（结束后存完整结果） |
| 中途失败要重来吗 | 看业务（可从头或续传） |
| 幂等 | 重试不重复副作用 |

★ 流式只是「传输方式」，**最终结果要落库**，不能只存在流里（断了就没了）。

## 第 5 步：中间层坑

| 坑 | 说明 |
|---|---|
| 代理/Nginx 缓冲 | 缓冲会让流式变批量（关 buffering） |
| 超时 | 中间层超时比业务短 → 断流 |
| gzip | 可能缓冲 |
| CDN | 可能不支持流 |

⛔ Nginx 默认 `proxy_buffering on` 会缓冲流式响应 = 用户看不到「逐字」。要关。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 明确结束/错误标记 + 断线处理 + 落库 + 中间层不缓冲
- WARN = 有流但无错误事件
- FAIL = 无结束标记 / 中间层缓冲 / 结果不落库
- UNKNOWN = 拿不到流式实现

## 假阳性清单（这些不算「流式好」）

- 有流但无结束标记
- 中间层缓冲了
- 结果只在流里不落库

## 假阴性清单（最常漏的 8 类）

1. **无结束标记**（半截当完整）
2. **中途错误静默断**
3. **中间层缓冲**（看不到逐字）
4. **无心跳**（中间层超时）
5. **结果不落库**（断了丢）
6. **客户端断服务端还生成**（浪费）
7. **无幂等**（重试重复）
8. **CDN/代理不支持流**

## 边界（如实说清）

- 流式不降低总时长，只降低首字节延迟
- 中间层配置常是最大障碍
- 本技能不实现，只设计
