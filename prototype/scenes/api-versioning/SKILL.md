# API 版本管理 技能

> API 的价值在稳定，成本在兼容。**破坏性变更 = 调用方炸**。
> 判据：**这次改完，老调用方不改代码还能不能用？** 不能就是破坏性，要谨慎。

## 什么时候用

- 改对外/对多方的 API
- 要下线旧版本
- 判断某改动是否破坏兼容

## 什么时候**不**用

- 完全内部且能同步改调用方
- 私有方法

## 第 1 步：什么算破坏性变更

| 变更 | 破坏性？ |
|---|---|
| 加可选字段 | ❌ 不破坏 |
| 加必填入参 | ✅ 破坏 |
| 删字段/接口 | ✅ 破坏 |
| 改字段类型 | ✅ 破坏（多半） |
| 改字段语义 | ✅ 破坏（隐性） |
| 改默认值 | ⚠ 可能破坏 |
| 改错误码含义 | ✅ 破坏 |
| 收紧校验（更严） | ✅ 破坏（原来合法现在不合法） |
| 放宽校验 | ❌ 不破坏 |

⛔ 最隐蔽的破坏：**改字段语义或收紧校验**——字段名没变但行为变了。

## 第 2 步：版本策略

| 策略 | 说明 |
|---|---|
| **URL 版本**（/v1/） | 最常见、清晰 |
| **Header 版本** | 同一 URL 切版本 |
| **字段演进**（不升版本） | 只做向后兼容改动 |
| **日期版本**（Stripe 式） | 按日期固定行为 |

⛔ 不是每次改动都升大版本——**向后兼容的改动不升版本**，只有破坏性才升。

## 第 3 步：弃用流程（下线要讲武德）

| 阶段 | 动作 |
|---|---|
| 1 标记 | 文档标 deprecated + 响应头/邮箱通知 |
| 2 并行 | 新旧并存一段时间 |
| 3 监控 | 看旧版还有谁在调 |
| 4 下线 | 到期关停 |

⛔ 直接下线旧版 = 半夜电话。

## 第 4 步：弃用要给出路

| 项 | 要求 |
|---|---|
| 替代方案 | 旧版对应新版怎么用 |
| 迁移时间 | 给足（月级） |
| 迁移指南 | 具体步骤 |
| 沟通 | 主动通知到调用方 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 破坏性判定 + 版本策略 + 弃用流程 + 迁移指南
- WARN = 有版本但弃用无流程
- FAIL = 破坏性变更直接上线 / 直接下线旧版
- UNKNOWN = 拿不到调用方情况

## 假阳性清单（这些不算「处理了兼容」）

- 只加了版本号但还是直接改行为
- 「通知了」但没给迁移期

## 假阴性清单（最常漏的 8 类）

1. **改字段语义**（名字没变行为变了）
2. **收紧校验**（原合法现不合法）
3. **改默认值**
4. **改错误码含义**
5. **直接下线旧版**
6. **破坏性改动不升版本**
7. **无迁移指南**
8. **无调用方监控就下线**

## 边界（如实说清）

- 版本太多也是债（维护多份）
- 「不改行为」的约束需要契约测试保证
- 本技能不实现，只定策略
