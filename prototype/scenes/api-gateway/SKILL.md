# API 网关 技能

> 网关的价值是**统一横切关注点**（认证/限流/路由/日志），但也容易**变成巨型单体和单点**。
> 判据：**网关挂了整个系统挂吗？它做的事是不是太多该拆了？**

## 什么时候用

- 多服务统一入口
- 统一认证/限流/监控
- 内外网隔离

## 什么时候**不**用

- 单服务（直接暴露即可）

## 第 1 步：网关该做什么（横切）

| 职责 | 适合网关 |
|---|---|
| 认证/鉴权（token 校验） | ✅ |
| 限流/熔断 | ✅ |
| 路由/负载均衡 | ✅ |
| 日志/追踪注入 | ✅ |
| SSL 终止 | ✅ |
| **业务逻辑** | ❌ 不该进网关 |

⛔ 网关里写业务逻辑 = 所有服务都受它拖累、无法独立演进。

## 第 2 步：可靠性（网关是单点风险）

| 风险 | 防法 |
|---|---|
| 网关挂全挂 | 多实例 + 高可用 |
| 网关成瓶颈 | 水平扩展（无状态） |
| 网关慢拖垮全 | 超时、熔断 |

⛔ 网关必须是最稳的组件，它比你所有后端都关键。

## 第 3 步：性能

| 项 | 注意 |
|---|---|
| 每请求开销 | 认证/限流都要快 |
| 连接池 | 到后端的连接复用 |
| 缓冲 | 大响应别全缓冲 |
| 无状态 | 才能水平扩 |

|---|---|
| 路径/域名路由 | |
| 灰度（按权重/header） | |
| 版本路由（/v1→服务） | |

## 第 5 步：「网关变胖」反模式

| 症状 | 后果 |
|---|---|
| 业务逻辑进网关 | 难维护、全耦合 |
| 每个需求都改网关 | 成为瓶颈 |
| 网关聚合多服务返回 | 网关承担了 BFF 职责，耦合 |

★ 网关只做「横切」，业务聚合用 BFF/GraphQL 单独层。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 只做横切 + 高可用 + 无状态可扩 + 不含业务
- WARN = 有网关但单实例
- FAIL = 业务进网关 / 单点 / 无超时熔断
- UNKNOWN = 拿不到架构

| 职责 | 在网关 |

## 假阳性清单（这些不算「网关好」）

- 网关单实例
- 业务逻辑进网关
- 无超时

## 假阴性清单（最常漏的 8 类）

1. **网关单点**
2. **业务逻辑进网关**
3. **无超时/熔断**
4. **有状态不能扩**
5. **大响应全缓冲**
6. **每请求开销大**
7. **认证在下游重复做**
8. **无灰度能力**
