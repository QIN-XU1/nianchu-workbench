# 负载均衡 技能

> 负载均衡最容易被忽略的是**状态**：无状态服务随便轮询，有状态服务（连接/会话/缓存）
> 用错算法会造成热点或缓存失效。
> 判据：**加一台机器，流量真的分过去了吗？减一台，会不会雪崩？**

## 什么时候用

- 多实例部署
- 负载不均/热点
- 健康检查与摘除
- 有状态服务（缓存/会话）

## 什么时候**不**用

- 单实例（无均衡问题）
- 纯无状态且流量均匀（简单轮询够）

## 第 1 步：选算法（按服务状态）

| 算法 | 适用 | 陷阱 |
|---|---|---|
| **轮询** | 无状态、同构 | 慢节点也被平均分 |
| **加权轮询** | 异构机器 | 权重需维护 |
| **最少连接** | 长连接/请求耗时差异大 | 需维护连接数 |
| **一致性哈希** | 有缓存/分片 | 节点变动影响面要控 |
| **IP/URL 哈希** | 会话保持 | 分布可能不均 |

⛔ 有缓存的服务用轮询 = 每个请求打到不同节点 = 缓存全 miss。

## 第 2 步：一致性哈希（有状态必看）

| 要点 | 说明 |
|---|---|
| 哈希环 | 节点和 key 映射到同一个环 |
| **虚拟节点** | 每个物理节点映射多个虚拟点（防数据倾斜） |
| 节点增减 | 只影响相邻区间的 key（不是全部重分布） |

⛔ 不用虚拟节点 = 数据严重倾斜（某节点分到很多 key）。

## 第 3 步：健康检查

| 项 | 要求 |
|---|---|
| 检查方式 | 主动探测（HTTP/TCP）+ 被动（错误率） |
| 间隔 | 不要太频繁（压力）也不要太慢（发现晚） |
| 摘除 | 连续 N 次失败摘除 |
| 恢复 | 半开试探后再放量（防抖动） |
| **慢节点** | 存活但慢（不是挂），要不要摘？ |

⛔ 只探「活着」不探「够快」= 慢节点拖垮整体。

## 第 4 步：会话保持

| 方式 | 说明 |
|---|---|
| 粘性会话（Cookie/来源 IP） | 同用户固定节点，但故障会掉会话 |
| **会话外置**（Redis） | 推荐：无状态化 |
| Token 无状态 | JWT 等 |

⛔ 依赖粘性会话 = 节点故障时用户掉线。

## 第 5 步：节点增减的流量重分布

| 场景 | 风险 |
|---|---|
| 扩容 | 一致性哈希下只迁移部分，好；轮询下立刻均分 |
| 缩容/故障 | 流量瞬间压到剩余节点 → 雪崩 |
| 灰度 | 按权重慢慢切 |

⛔ 缩容太快 = 剩余节点被打垮。要平滑下线（先摘流量，处理完存量请求）。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 算法匹配状态 + 健康检查含慢节点 + 会话外置 + 平滑上下线
- WARN = 健康检查只探存活
- FAIL = 有缓存用轮询 / 依赖粘性会话 / 无平滑下线

## 假阳性清单（这些不算「均衡好」）

- 有轮询但节点异构
- 健康检查只 ping
- 粘性会话当无状态

## 假阴性清单（最常漏的 8 类）

1. **有缓存用轮询**（缓存全 miss）
2. **一致性哈希无虚拟节点**（倾斜）
3. **健康检查只探存活**（慢节点拖垮）
4. **依赖粘性会话**（故障掉线）
5. **缩容太快**（雪崩）
6. **无半开恢复**（抖动）
7. **跨可用区不分流**
8. **长连接不排空**（下线丢请求）

## 与其他技能的关系

## 边界（如实说清）

- 均衡器本身可能成单点（要冗余）
- 一致性哈希的迁移期仍有短暂不一致
- 本技能不实现代理，只设计策略
