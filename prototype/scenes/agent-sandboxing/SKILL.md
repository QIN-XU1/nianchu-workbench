# Agent 工具执行沙箱 技能

> agent 能跑命令，是它有用的一半，也是它危险的一半。
> 判据：**工具执行前，你能否说清「它在什么进程、什么环境、哪个目录里跑，超时怎么收尸」？**
> 说不清 = 没有沙箱，只是没出事。

## 什么时候用

- 给 coding agent 接 bash / shell 工具
- agent 要在用户机器上读写文件、跑构建
- 评审一个 agent 产品的「终端执行」是否安全

## 什么时候**不**用

- 工具只读且无副作用（纯计算函数）
- 已在容器/VM 级隔离里跑（那属于下一层，但白名单仍值得做）

## 第 1 步：进程模型——每次调用一个新进程

不要让 agent 的工具共享一个常驻 shell 会话。每次调用 spawn 新进程：副作用边界清楚、超时好收、崩溃不污染下一次。

验证它真的每次新进程：连续两次调用，比 PID 是否不同。相同 = 你其实复用了会话。

## 第 2 步：环境变量白名单，而不是全量继承

默认 `env: process.env` 会把宿主的密钥全交给 agent 跑的命令。改白名单：

- 只放行 PATH、HOME、LANG、TZ 这类无害项
- **剥掉**名称像密钥的：含 KEY / TOKEN / SECRET / PASSWORD / CREDENTIAL / AUTH 的一律剔除
- 白名单比黑名单可靠：黑名单永远漏

验证：在命令里 `echo` 一个已知的 `*_API_KEY`，必须为空。

## 第 3 步：目录约束

- `cwd` 必须强制生效（不是「建议」）
- 拒绝 `../` 越界到工作目录之外
- 路径先规范化再判定，防 `a/../../etc` 绕过

## 第 4 步：超时杀**整棵进程树**，不是只杀父

这是最容易错的一步：

| 做法 | 后果 |
|---|---|
| 只 kill 父进程 | 子进程变孤儿继续跑，端口被占、文件被写 |
| 杀整棵进程树 | 干净 |

POSIX 用进程组（`detached` + `kill(-pid)`）；Windows 用 `taskkill /T /F /PID`（/T 才是树）。

## 反例（写下来防复发）

- ✗ 只杀父进程：`sh -c "sleep 999 &"` 的子进程活下来
- ✗ 全量继承 env：agent 跑 `printenv` 就把宿主密钥打出来
- ✗ cwd 只是「传给 spawn 的参数」但没校验：`cd` 命令本身就绕过了

## 自检清单

- [ ] 连续两次调用的 PID 不同
- [ ] env 白名单外的一律不可见
- [ ] 超时后没有残留子进程（再查一次进程表）
- [ ] 越界路径被拒，且有明确报错（不是静默失败）
