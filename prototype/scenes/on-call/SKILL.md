# 值班（On-call）技能

> 值班制度的失败模式：**告警太多 → 值班员麻木 → 真事故被忽略 → 人跑路**。
> 判据：**值班员一晚上被叫醒几次？每次都能采取行动吗？** 叫醒多且无用 = 制度坏了。

## 什么时候用

- 建立/改进值班制度
- 告警疲劳
- 值班员 burnout
- 事故响应慢

## 什么时候**不**用

- 无线上服务
- 只设计告警 → `observability-design`

## 第 1 步：轮值设计

| 项 | 要求 |
|---|---|
| 周期 | 一周或几天轮一次（太长会 burn out） |
| 交接 | 明确交接清单（在处理的、已知问题） |
| 备份 | 每个值班有次级 backup |
| 时区 | 跨时区轮流，别只让一个时区熬夜 |

## 第 2 步：告警分级（只叫醒该叫醒的）

| 级别 | 叫醒？ | 例子 |
|---|---|---|
| **P0** | 立即叫醒 | 用户可感知故障 |
| **P1** | 工作时间 | 趋势恶化 |
| **P2** | 不叫人，看板 | 偶发异常 |

★ **每条 P0/P1 告警必须有对应 runbook**（见 `runbook`），没有的告警不该叫醒人。

## 第 3 步：升级路径（15 分钟规则）

| 时间 | 动作 |
|---|---|
| 0 min | 值班员收到，确认 |
| 15 min | 未解决 → 升级到 backup |
| 30 min | 未解决 → 升级到负责人/专家 |
| — | 有明确决策人（谁能叫停/回滚） |

⛔ 没有升级路径 = 值班员硬扛到天亮。

## 第 4 步：值班员权限与减负

| 项 | 要求 |
|---|---|
| **权限** | 能直接回滚/扩容/切流量（不必层层审批） |
| **减负** | 值班周减少其他工作（别让值班+满负荷） |
| **补偿** | 值班津贴/调休 |
| **事后** | 每次被叫醒的告警要复盘（该不该叫） |

## 第 5 步：健康度指标

| 指标 | 健康 |
|---|---|
| 每晚叫醒次数 | < 1 |
| 行动率（告警后真做了事） | 高 |
| 误报率 | 低 |
| 升级及时率 | 高 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 轮值合理 + 分级 + 升级路径 + 有减负
- WARN = 有值班但告警未分级
- FAIL = 无升级路径 / 值班员无权限 / 每晚叫醒多次
- UNKNOWN = 拿不到告警数据

## 假阳性清单（这些不算「有值班」）

- 排了人但告警不分级
- 值班员无回滚权限
- 没有升级路径

## 假阴性清单（最常漏的 8 类）

1. **告警不分级**（P2 也叫醒）
2. **无升级路径**
3. **值班员无权限**（要等审批）
4. **值班+满负荷**（burn out）
5. **无 backup**
6. **交接不清**
7. **告警无 runbook**
8. **被叫醒的告警不复盘**

## 与其他技能的关系

- `runbook`：告警对应的处置
- `observability-design`：告警从哪来
- `incident-comms`：事故中的沟通
- `postmortem`：复盘与减负

## 边界（如实说清）

- 小团队可能无法 7×24，要接受更长响应时间
- 值班文化比制度更难建立
- 本技能不排班，只设计制度
