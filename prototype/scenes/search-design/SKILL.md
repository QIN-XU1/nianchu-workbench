# 搜索设计 技能

> 搜索最容易做错的是**把它当数据库查询**：`LIKE '%关键词%'` 在大数据量下既慢又搜不准（无相关性、无分词）。
> 判据：**用户搜「苹果手机」，能搜到「iPhone」吗？搜错字能纠吗？** 不能，就不是搜索是精确匹配。

## 什么时候用

- 要做全文搜索/模糊搜索
- 搜索结果不准
- 搜索慢

## 什么时候**不**用

- 精确匹配（按 ID/唯一键查）
- 数据量小（LIKE 够用）

## 第 1 步：为什么不能用 LIKE

| LIKE '%x%' 的问题 |
|---|
| 前导通配 → 索引失效 → 全表扫 |
| 无分词（「苹果手机」不会匹到「iPhone 手机」） |
| 无相关性排序（结果顺序随机） |
| 无同义词/纠错 |

## 第 2 步：倒排索引（搜索的核心）

```
文档 → 分词 → 每个词 → 包含它的文档列表
搜索「手机」→ 查倒排表 → 命中文档
```

引擎：Elasticsearch / OpenSearch / Meilisearch / Typesense / pg 全文检索。

## 第 3 步：分词（中文尤其难）

| 语言 | 分词挑战 |
|---|---|
| 英文 | 空格分词（简单） |
| **中文** | 无空格，要分词器（jieba/IK） |

| 中文分词方式 | 效果 |
|---|---|
| 单字切分 | 召回高但噪音大 |
| 词级（jieba/IK） | 均衡 |
| 自定义词典 | 加业务词（品牌/型号） |

⛔ 中文搜索不做分词 = 搜不准。

## 第 4 步：相关性排序

| 因素 | 说明 |
|---|---|
| **TF-IDF / BM25** | 词频 + 逆文档频率 |
| **字段权重** | 标题比正文重要 |
| **新鲜度** | 新的排前 |
| **业务权重** | 销量/评分 |

## 第 5 步：索引更新与一致性（最易漏）

| 问题 | 说明 |
|---|---|
| 数据改了索引没更新 | 搜到旧数据 |
| 索引更新延迟 | 刚创建的搜不到 |
| 全量 vs 增量 | 全量重建 vs 实时增量 |

方案：
- 双写（写 DB + 写索引，但可能不一致）
- **binlog/CDC 同步**（从数据库变更驱动，最可靠）
- 定时重建（兜底）

⛔ 只在写入时双写索引，失败一次就永远不一致。要有**对账机制**。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 倒排索引 + 分词 + 相关性 + CDC 同步 + 对账
- WARN = 有搜索但索引同步靠双写无对账
- FAIL = LIKE 全表扫 / 无分词 / 无双写同步
- UNKNOWN = 拿不到搜索实现

## 假阳性清单（这些不算「有搜索」）

- LIKE '%x%'
- 有引擎但无分词
- 双写无对账

## 假阴性清单（最常漏的 8 类）

1. **LIKE 前导通配**（全表扫）
2. **中文不分词**
3. **无相关性排序**（结果乱）
4. **索引同步无双写/CDC**
5. **无双边对账**（不一致无人知）
6. **无同义词/纠错**
7. **字段无权重**
8. **索引更新延迟未处理**

## 边界（如实说清）

- 搜索质量需要真实语料调优
- 引入搜索引擎增加运维成本
- 本技能不实现引擎，只设计
