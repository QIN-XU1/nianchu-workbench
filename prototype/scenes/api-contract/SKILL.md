# 接口契约核对 技能

> 契约不是「文档上写的形状」，而是**调用方实际依赖的东西**。
> 判断 breaking 的唯一标准：**旧调用方不改代码，还能不能正确工作**。
> 只看字段名对不对是远远不够的 —— 语义变了、错误表达变了、时序变了，都是 breaking。

## 什么时候用

- 改了函数签名 / API 路径 / 返回结构 / 错误码
- 怀疑「调用方和实现对不上」
- 要给一个改动做「会不会破坏兼容」的判定
- 合并两套实现前，确认契约能否对齐

## 什么时候**不**用

- 是纯内部重构（无对外契约变化）→ `refactor-plan`
- 要看代码质量问题 → `code-review`
- 是数据结构设计（还没有契约）→ `schema-design`

## 第 1 步：写出完整契约（四要素，缺一不可）

把契约**显式写出来**，而不是「心里知道」。四个要素：

### 1.1 入参

| 项 | 要写清 |
|---|---|
| 名称与类型 | `path: string` 还是 `path: string \| null`？ |
| 必填性 | 缺了会怎样？（报错 / 用默认值 / 静默当成空） |
| 取值范围 | 空串算合法吗？0 合法吗？负数？超长？ |
| 别名 | 同一含义接受多个键名吗？（如 `path` / `file` / `relPath`） |
| 互斥/依赖 | 哪些参数必须同时给？哪些不能同时给？ |

⛔ 别名是契约的隐形部分：本仓库 `git_get_file_content` 曾因 `path` 同时被当仓库路径和文件路径，导致读文件永远失败 —— 单测没抓到，端到端才暴露。

### 1.2 出参

| 项 | 要写清 |
|---|---|
| 结构 | 有哪些字段？嵌套几层？ |
| 字段可选性 | 哪些字段可能缺失？缺失代表什么？ |
| 空值语义 | `null` / `undefined` / `[]` / `{}` 分别代表什么？**不许混用** |
| 单位与量纲 | 字节还是字符？毫秒还是秒？ |
| 顺序 | 有语义吗？（数组顺序会影响调用方吗） |

空值语义混用是重灾区。本仓库实例：`repositoryStatus` 对「非仓库」返回 `clean: null`，
对「干净仓库」返回 `clean: true` —— 如果两者都用 `false`，调用方就无法区分「不是仓库」和「有改动」。

### 1.3 错误

| 项 | 要写清 |
|---|---|
| 错误表达方式 | 抛异常 / 返回 `{ok:false}` / HTTP 状态码 / 退出码？ |
| 错误分类 | 有哪些错误码？各自含义？ |
| 错误 vs 空结果 | 「查不到」是错误还是正常空结果？ |
| 部分失败 | 批量操作中一半成功怎么办？ |

⛔ 本仓库踩过：`/api/memory` 的 put 被 store 拒绝时，曾返回 **HTTP 200 + 外层 `ok:true`**，
真实失败藏在 `result.ok:false` 里 —— 调用方看外层就以为成功。这是契约层面的**假成功**。

### 1.4 副作用与时序

| 项 | 要写清 |
|---|---|
| 写盘/网络 | 调用一次会改什么？可重入吗？ |
| 幂等性 | 调两次结果一样吗？ |
| 顺序依赖 | 必须先调 A 再调 B 吗？ |
| 并发 | 两个调用同时进行会怎样？ |

## 第 2 步：找全所有调用点（漏一个就白做）

```bash
# 按函数名/方法名找
grep -rn "methodName" --include=*.mjs --include=*.js --include=*.ts .
# 按 API 路径找
grep -rn "/api/endpoint" .
# 按前端 invoke 名找（本项目宿主方法）
grep -rn "git_get_status\|get_skill_configs" apps/ tools/
```

三个容易漏的地方：

1. **前端 bundle 里的调用**（编译产物里名字可能不同 —— 查 `.js` 产物或映射表）
2. **测试里的调用**（测试也是调用方，改了契约测试会红）
3. **文档/脚本里的调用**（README 示例、CI 脚本）

判据：**能列出调用点的完整清单（文件:行号）才算找全**。列不出就是没找全。

## 第 3 步：判定 breaking（五类，逐类查）

| 类别 | 兼容 | Breaking |
|---|---|---|
| **字段** | 加**可选**字段 | 删字段、改字段名、改字段类型、把可选改必填 |
| **语义** | 同名同义 | 同名字段含义变了（如 `count` 从「总条数」变「本页条数」） |
| **错误表达** | 错误码不变 | 200+内层失败 → 4xx；退出码 0/1/2 语义变；错误信息从可解析变自由文本 |
| **默认值** | 显式传值行为不变 | 默认值改了（不传参数时行为变）；阈值调大/调小 |
| **时序/副作用** | 副作用不变 | 原本幂等变成非幂等；原本同步变成异步；新增必填的前置调用 |

⛔ 最容易漏的是「语义」和「默认值」：字段名完全没变，但含义变了，编译器/类型检查全绿，运行时静默出错。

本仓库实例（语义 breaking）：`commitLog(start, limit)` 原写法 `Number(limit) || 50`
把「显式传 0」当成「没传」→ 静默返回 50 条。字段名没变、类型没变，但**语义变了**。

## 第 4 步：给迁移方案（三选一，必须明确选）

### 方案 A：直接改（仅当所有调用点都能同步改）

适用：内部函数、调用点 ≤ 3 个、能一次性改完。
必须附：调用点清单 + 每个改了什么 + 改完跑的验证。

### 方案 B：兼容层（新旧都支持，逐步迁移）

适用：调用方无法同步改（外部集成、前端已发布版本）。
做法：新参数优先，旧参数兜底并**打 deprecation 日志**（不是静默兼容）。

⛔ 兼容层必须有**退出条件**（什么时候删旧路径），否则会永久留下两套逻辑。

### 方案 C：版本化（并存两套接口）

适用：对外 API、破坏性变更无法避免。
做法：新路径 `/v2/` 或新方法名，旧路径标记 deprecated 并给出下线时间。

## 第 5 步：验证契约真的对上了

光读代码不够，要跑：

1. **调用点逐个跑**：改完后，第 2 步列出的每个调用点都要能正常工作
2. **错误路径也跑**：不只测成功，非法输入的错误形态也要对
3. **跨端验证**：前端调 → 宿主接 → 底层执行，全链路跑一遍（单测过不代表端到端过）

本仓库实例：`git_get_file_content` 的单测直接调用函数（显式传参）全过，
但通过 WS 传 `{file:'x'}` 时失败 —— 因为 `pickPath` 把 `path` 当仓库路径。
**契约在单测和真实调用之间不一致**，只有端到端能发现。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 兼容（旧调用方不改也能跑）
- WARN = 兼容但有隐患（如新增字段影响下游断言）
- FAIL = breaking（必须给迁移清单）
- UNKNOWN = 调用点没找全 / 拿不到某端代码

**1. 契约（改前 → 改后）**
- 入参：<逐项对比，标出变化>
- 出参：<逐项对比，标出变化>
- 错误：<错误码/表达方式的变化>
- 副作用/时序：<变化>

**2. 调用点清单**
| 文件:行号 | 怎么用的 | 受影响？ |
|---|---|---|

**3. Breaking 判定**
- 类别：<字段/语义/错误表达/默认值/时序 中的哪几类>
- 结论：兼容 / breaking
- 依据：<为什么>

**4. 迁移方案**
- 选 A/B/C：<哪个>
- 具体步骤：<逐条>
- 验证：<跑了什么，结果如何>

**5. 判不了的部分**
- <缺什么>

## 假阳性清单（这些不是 breaking）

- 加了可选字段且默认不影响旧行为
- 内部函数改名但所有调用点已同步改
- 错误信息措辞变化（错误码/类型没变）
- 新增了新的错误码（旧错误码语义未变）
- 性能变快/变慢（除非有明确 SLA）

## 假阴性清单（最常漏的 8 类）

1. **字段名没变但语义变了**（最危险）
2. **默认值被改了**（不传参时行为变）
3. **错误表达方式变了**（200+内层失败 → 4xx）
4. **空值语义混用**（`null` 和 `[]` 和 `false` 混着用）
5. **只找了源码里的调用点，漏了前端 bundle / 测试 / 文档**
6. **别名冲突**（同一个键在不同方法里含义不同）
7. **时序变化**（原本同步、现在异步；原本幂等、现在不幂等）
8. **单测过了但端到端没过**（契约在两层之间不一致）

## 本仓库可用的命令

```bash
node tools/workbench/verify-api-error-contract.mjs   # 29 条：7 个吃 action 的端点 + 4 个拼错路由 + 字段级 + messageQuality
node tools/workbench/verify-ws-e2e.mjs               # WS 端到端（真实调用链路）
node tools/workbench/verify-http-e2e.mjs             # HTTP 端到端
```

## 与其他技能的关系

- `schema-design`：设计新数据结构时定契约（本技能是核对已有契约）
- `code-review`：第 4 层「契约」就是查这个
- `test-writing`：契约变化后补/改测试
- `dep-upgrade`：升级依赖时对方契约变了，用本技能核对影响
- `release-gate`：breaking 变更需要发布说明与迁移指引

## 边界（如实说清）

- 只能核对**能找到的调用点**；动态调用（`obj[name]()`、反射、字符串拼接路径）可能漏
- 前端编译产物里的调用名可能被压缩，需要对照映射表或源码
- 「语义兼容」无法自动判定，必须人工读调用方怎么用这个值
- 本技能不做运行时兼容性测试（那要靠端到端验收）
- 拿不到某一端代码时（如闭源客户端），结论只能是 UNKNOWN
