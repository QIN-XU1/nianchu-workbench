# GraphQL 设计 技能

> GraphQL 的优势是「按需取数据」，但代价是：**每个查询都可能触发 N+1、或恶意深查询打垮服务**。
> 判据：**一个恶意客户端能用一个查询打垮你的服务吗？**

## 什么时候用

- 客户端需要灵活取数
- 多端（web/mobile）字段需求不同
- 聚合多个数据源

## 什么时候**不**用

- 简单 CRUD（REST 更简单）
- 缓存要求高（REST 用 HTTP 缓存更简单）

## 第 1 步：N+1（GraphQL 头号性能问题）

```
查询 { posts { author { name } } }
→ 1 次查 posts + N 次查 author（每个 post 一次）
```

| 解法 | 说明 |
|---|---|
| **DataLoader**（批处理） | 把 N 次合批成 1 次 |
| 预取 | 一次 join |

⛔ 不用 DataLoader = 列表一长就 N+1 = 慢。

## 第 2 步：查询复杂度控制（安全）

| 风险 | 防护 |
|---|---|
| 深嵌套查询 | **最大深度限制** |
| 大列表 | 强制分页（禁止无限） |
| 复杂度爆炸 | **查询复杂度打分**，超限拒绝 |
| 循环引用 | 限制 |

★ 没有复杂度限制 = 一个查询 `{ users { friends { friends { ... } } } }` 打垮服务。

## 第 3 步：分页

| 方式 | 说明 |
|---|---|
| **游标分页**（Relay connection） | 推荐（稳定） |
| offset | 简单但深翻差 |

## 第 4 步：授权（易漏）

| 问题 | 说明 |
|---|---|
| 字段级授权 | 不同字段不同权限 |
| **N+1 式越权** | 从父对象拿子对象要校验 |
| 内省泄露 | 生产关内省 |

⛔ 只在查询入口校验权限 = 字段级可能越权。

## 第 5 步：其他

| 项 | 说明 |
|---|---|
| 错误处理 | partial error（部分成功） |
| 缓存 | 难用 HTTP 缓存，用客户端缓存/持久化查询 |
| 版本 | 弃用字段而非版本号 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = DataLoader + 复杂度限制 + 分页 + 字段级授权
- WARN = 有 schema 但无复杂度限制
- FAIL = N+1 / 无深度限制 / 字段级越权
- UNKNOWN = 拿不到 schema

## 假阳性清单（这些不算「GraphQL 好」）

- 有 schema 但 N+1
- 无复杂度限制
- 字段级不校验

## 假阴性清单（最常漏的 8 类）

1. **N+1 无 DataLoader**
2. **无深度限制**（深查询打垮）
3. **无复杂度打分**
4. **不限分页**
5. **字段级越权**
6. **生产开内省**
7. **无部分错误处理**
8. **循环引用**
