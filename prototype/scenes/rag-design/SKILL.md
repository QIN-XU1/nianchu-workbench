# RAG 设计 技能

> RAG 的失败大多不在「模型不会答」，而在**检索没找到对的内容**，或**找到了但塞太多把关键淹了**。
> 判据：**正确答案在知识库里，检索能不能把它排进前几条？** 不能，模型再强也答不对。

## 什么时候用

- 知识库问答
- 要让模型回答私有知识
- 检索质量差

## 什么时候**不**用

- 知识能放进 prompt（小量）
- 需要实时推理而非检索

## 第 1 步：切块（chunking，影响最大）

| 策略 | 说明 |
|---|---|
| 固定长度 | 简单，但可能切断语义 |
| **按结构**（段落/标题） | 保留语义完整 |
| 重叠窗口 | 防切断（overlap） |
| 父子块 | 小块检索、大块喂模型 |

⛔ 切太大 → 噪音多；切太小 → 语义不全。要按文档结构调整。

## 第 2 步：嵌入与索引

| 项 | 要点 |
|---|---|
| 嵌入模型 | 与语言/领域匹配 |
| 向量库 | 按规模选 |
| **混合检索** | 向量（语义）+ 关键词（精确）都好过单一 |

★ 纯向量检索对「精确词/编号/人名」常常不如关键词。混合检索（hybrid）更稳。

## 第 3 步：检索→重排（rerank）

| 阶段 | 作用 |
|---|---|
| 粗检索（召回） | 取 Top 20-50 |
| **重排（rerank）** | 用更强模型精排 Top 5 |

⛔ 只召回不重排 = 前几条不一定最相关。

## 第 4 步：喂给模型（别淹了关键）

| 问题 | 处理 |
|---|---|
| 塞太多块 | 只给最相关的几条 |
| 无关块干扰 | 重排后截断 |
| 无出处 | 带来源（可追溯） |
| 上下文冲突 | 标注/按时间选 |

## 第 5 步：评估（RAG 最容易糊弄的地方）

| 指标 | 含义 |
|---|---|
| **检索召回** | 正确内容有没有被召回 |
| **检索精度** | 前几条是否相关 |
| **答案忠实度** | 答案是否基于检索内容（不编） |
| **答案相关性** | 是否回答了问题 |

★ 要分开评「检索」和「生成」——否则答错了不知道是检索没找到还是模型乱答。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 合理切块 + 混合检索 + 重排 + 带出处 + 分开评估
- WARN = 有检索但无重排/无评估
- FAIL = 切块粗暴 / 纯向量无关键词 / 塞太多 / 无出处

## 假阳性清单（这些不算「RAG 好」）

- 有向量库但检索不准
- 无重排
- 答错了不区分是检索还是生成

## 假阴性清单（最常漏的 8 类）

1. **切块切断语义**
2. **纯向量无关键词**（精确词检索差）
3. **无重排**
4. **塞太多块淹没关键**
5. **无出处**（不可追溯）
6. **不分开评估检索与生成**
7. **嵌入模型与语言不匹配**
8. **知识更新后索引不更新**

## 与其他技能的关系

- `search-design`：倒排/分词基础
- `agent-memory`：长期记忆的检索
- `context-management`：喂入预算
- `evaluation-design`：RAG 评估

## 边界（如实说清）

- 检索质量上限决定 RAG 上限
- 嵌入模型有领域偏差
- 本技能不实现，只设计
