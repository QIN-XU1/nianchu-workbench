# Schema 演进 技能

> 线上改 schema 的危险在于**新旧代码同时在跑**（滚动发布期间）。
> 新代码假设有字段 X，老代码不知道 X——所以改动必须**同时兼容新旧代码**。
> 判据：**在滚动发布的那几分钟，新旧代码读同一个库，会不会报错？**

## 什么时候用

- 线上改表结构
- 要删/改字段
- 滚动发布期间的兼容

## 什么时候**不**用

- 新表（无兼容问题）
- 可停机维护

## 第 1 步：兼容性分级（先行判断）

| 改动 | 向后兼容？ | 说明 |
|---|---|---|
| **加可空字段** | ✅ | 老代码忽略它 |
| **加非空字段（带默认）** | ✅ | 但有锁表风险 |
| **加索引** | ✅ | 在线建索引 |
| **改字段类型（兼容）** | ⚠ | int→bigint 通常可以 |
| **改字段类型（不兼容）** | ❌ | string→int 会炸 |
| **删字段** | ❌ | 老代码还在读 |
| **重命名字段** | ❌ | 老代码找不到 |

⛔ 「删字段」不是一步能做的——要先让所有代码停止使用，再删。

## 第 2 步：安全改动的模式（扩展-收缩）

任何不兼容改动都拆成多步（Expand-Migrate-Contract）：

| 阶段 | 动作 |
|---|---|
| **1 Expand** | 加新字段（可空），双写新旧 |
| **2 Migrate** | 回填旧数据到新字段 |
| **3 Switch** | 读切到新字段，代码不再依赖旧 |
| **4 Contract** | 确认无引用后，删旧字段 |

⛔ 直接一步「改名/改类型/删字段」= 滚动发布时新旧代码打架。

## 第 3 步：在线 DDL 的锁（性能陷阱）

| 操作 | 锁风险 |
|---|---|
| 加非空字段带默认 | 可能全表重写（锁表） |
| 加索引（非 online） | 锁表 |
| 改列类型 | 常全表重写 |

对策：
- 用 online DDL（`ALGORITHM=INPLACE` / `pt-online-schema-change`）
- 加字段先加可空
- 大表分批次

## 第 4 步：回填（大表要分批）

| 要点 | 说明 |
|---|---|
| 分批 | 每次几千行，别一次全表 |
| 可暂停 | 高峰能停 |
| 幂等 | 重复回填不出错 |
| 监控 | 进度与对数据库压力 |

## 第 5 步：校验

| 项 | 检查 |
|---|---|
| 双写一致 | 新旧字段值一致 |
| 无残留引用 | 没有代码再读旧字段 |
| 回滚可行 | 出问题能退回上一步 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 兼容性判断 + 扩展收缩分步 + online DDL + 回填可暂停
- WARN = 有分步但回填未分批
- FAIL = 一步删/改名/改类型 / 无 online DDL / 无回滚
- UNKNOWN = 拿不到表结构与代码引用

**1. 改动兼容性**
| 改动 | 兼容 | 风险 |
|---|---|---|

**2. 分步计划**
| 阶段 | 动作 | 可回滚 |
|---|---|---|

**3. DDL/回填**
| 项 | 方式 |
|---|---|
| online DDL | |
| 回填分批 | |

**4. 判不了的部分**
- <拿不到的引用关系>

## 假阳性清单（这些不算「安全演进」）

- 一步删字段
- 大表直接加非空字段
- 没有双写就切读

## 假阴性清单（最常漏的 8 类）

1. **一步删/改名/改类型**
2. **大表加非空字段锁表**
3. **无 online DDL**
4. **回填不分批**
5. **回填不幂等**
6. **切读前没双写**
7. **无残留引用检查**
8. **无回滚路径**

## 与其他技能的关系

- `data-migration`：数据迁移（本技能是表结构）
- `schema-design`：新表设计
- `consistency-model`：双写一致性
- `rollback-plan`：回滚

## 边界（如实说清）

- 不同数据库 online DDL 能力差异大
- 极热大表的 DDL 可能需要专门工具
- 本技能不执行 DDL，只设计步骤
