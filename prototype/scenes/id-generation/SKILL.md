# 全局 ID 生成 技能

> 分布式 ID 的难点：**既要全局唯一，又要趋势递增（利于索引），还不能依赖单点**。
> 最致命的问题：**雪花算法的时钟回拨** —— 服务器时间往回调，可能生成重复 ID。
> 判据：**服务器时钟被 NTP 调回 1 秒，你的 ID 还会唯一吗？**

## 什么时候用

- 分库分表需要全局 ID
- 订单号/消息 ID
- 需要趋势递增的主键

## 什么时候**不**用

- 单库自增够用（别过度设计）
- ID 不需要有意义的

## 第 1 步：方案对比

| 方案 | 唯一 | 递增 | 长度 | 依赖 |
|---|---|---|---|---|
| **数据库自增** | ✅ | ✅ | 短 | 单点/段 |
| **UUID** | ✅ | ❌ 无序 | 长(36) | 无 |
| **雪花 Snowflake** | ✅ | ✅ 趋势 | 64bit | 时钟 |
| **号段模式** | ✅ | ✅ | 短 | DB（批量取） |
| **Redis INCR** | ✅ | ✅ | 短 | Redis |

⛔ UUID 作主键：无序 → 索引插入随机 → B+ 树频繁分裂 → 写性能差。

## 第 2 步：雪花算法结构

```
| 1bit 符号 | 41bit 时间戳 | 10bit 机器ID | 12bit 序列号 |
```

- 41 位毫秒 ≈ 69 年
- 10 位机器 = 1024 台
- 12 位序列 = 每毫秒 4096 个

## 第 3 步：时钟回拨（雪花的致命点）

| 情况 | 处理 |
|---|---|
| 回调量小（如 <5ms） | 等待追平 |
| 回调量大 | **拒绝生成**（抛错），别硬生成重复 |
| 长期 | 报警 + 人工 |

⛔ 时钟回拨时继续生成 = 可能产生重复 ID。**宁可拒绝也不能重复。**

## 第 4 步：号段模式（推荐，避免时钟依赖）

| 步骤 | 说明 |
|---|---|
| 应用启动 | 从 DB 取一段（如 1-1000）到本地 |
| 用完 | 再取下一段 |
| 双 buffer | 提前异步取下一段（无等待） |

优点：不依赖时钟、性能高、趋势递增。

## 第 5 步：机器 ID 分配（雪花的另一坑）

| 问题 | 解决 |
|---|---|
| 机器 ID 重复 | 用注册中心/ZK 分配，或从 IP/MAC 派生 |
| 扩容 | 动态分配 |
| 容器漂移 | 别用固定的 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 方案合理 + 时钟回拨有处理 + 机器 ID 唯一
- WARN = 用雪花但时钟回拨处理不全
- FAIL = 时钟回拨不处理 / 机器 ID 可能重复 / UUID 当索引主键
- UNKNOWN = 拿不到 ID 方案

## 假阳性清单（这些不算「ID 安全」）

- 用雪花但不处理回拨
- 机器 ID 手动配（可能重复）
- UUID 当主键

## 假阴性清单（最常漏的 8 类）

1. **时钟回拨生成重复**
2. **机器 ID 重复**
3. **容器漂移机器 ID 冲突**
4. **UUID 当聚簇索引**（写慢）
5. **号段双 buffer 缺失**（取号卡顿）
6. **序列号溢出无等待**
7. **ID 泄露信息**（如自增暴露业务量）
8. **无单调性保证**

## 边界（如实说清）

- 任何方案都有取舍（长度/依赖/递增性）
- 号段模式的 DB 是弱依赖（缓存段）
- 本技能不实现，只设计
