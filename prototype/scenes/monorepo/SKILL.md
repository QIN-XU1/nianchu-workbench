# Monorepo 技能

> Monorepo 的好处是**原子提交跨包改动、统一工具链**；代价是**构建慢、依赖地狱、权限难分**。
> 判据：**改一个包，会不会因为依赖关系触发全仓重建？**

## 什么时候用

- 多包强相关（共享代码频繁）
- 要原子提交
- 统一 CI/工具链

## 什么时候**不**用

- 包之间独立、团队独立
- 仓库大到不可控

## 第 1 步：工具与依赖

| 项 | 要点 |
|---|---|
| **工作区**（workspaces） | 统一管理多包依赖 |
| 依赖提升 | 共享依赖（但可能版本冲突） |
| **内部包引用** | 用 workspace 协议而非发布 |

⛔ 内部包用「发布到 npm 再引用」= monorepo 白搭（应直接 workspace 引用）。

## 第 2 步：构建缓存（monorepo 性能关键）

| 手段 | 说明 |
|---|---|
| **只构建变更的包**（affected） | 依赖图分析 |
| **远程缓存** | 构建结果共享（Nx/Turborepo） |
| 增量 | 不变的不重建 |

★ 没有「只构建受影响包」= 改一个包建全仓 = 慢到不可用。

## 第 3 步：版本策略

| 策略 | 说明 |
|---|---|
| **统一版本**（fixed） | 所有包同版本（简单） |
| **独立版本**（independent） | 各自版本（灵活） |

## 第 4 步：CI 策略

| 项 | 说明 |
|---|---|
| 只测受影响的包 | 快 |
| 全量定期跑 | 兜底 |
| 缓存依赖 | 快 |

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 依赖提升导致「幽灵依赖」 | 用了没声明的包 |
| 无 affected 构建 | 慢 |
| 包边界不清 | 循环依赖 |
| 权限不分 | 谁都能改所有 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = workspace 引用 + affected 构建 + 缓存 + 边界清
- WARN = 有 monorepo 但全量构建
- FAIL = 内部包走发布 / 循环依赖 / 无缓存
- UNKNOWN = 拿不到仓库结构

## 假阳性清单（这些不算「monorepo 好」）

- 有 workspace 但全量构建
- 内部包走发布
- 循环依赖

## 假阴性清单（最常漏的 8 类）

1. **无 affected 构建**（慢）
2. **无构建缓存**
3. **内部包走发布**（应 workspace）
4. **幽灵依赖**（提升导致）
5. **循环依赖**
6. **包边界不清**
7. **CI 全量测**
8. **权限不分**

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁
```

## 与其他技能的关系

- `ci-pipeline`：CI 优化
- `dependency-audit`：依赖
- `cross-repo-refactor`：重构
- `api-contract`：包接口

## 边界（如实说清）

- monorepo 工具链学习成本高
- 超大仓库仍可能不可控
- 本技能不实现，只设计
