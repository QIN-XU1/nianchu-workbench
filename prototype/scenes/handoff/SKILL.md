# 工作交接 技能

> 交接失败的典型表现是：接手的人**重新踩一遍你已经踩过的坑**。
> 所以交接的核心不是「说明进度」，而是**把「你已经知道的、但对方还不知道的」全部倒出来** ——
> 尤其是那些「看起来该这样、其实是那样」的反直觉发现。

## 什么时候用

- 要休假/换人接手
- 会话要结束了，工作没完
- 把任务交给另一个 agent/另一个上下文
- 接手别人的工作时，用它检查「接得对不对」

## 什么时候**不**用

- 任务已经完成 → 那是 `changelog` / 交付说明
- 只是同步进度（不换人）→ 口头同步即可
- 任务还没开始 → 那是 `task-breakdown`

## 第 0 步：先确认「交接的最小充分集」

交接不是写日记。写太少，对方要重新摸索；写太多，对方读不完。

**最小充分集 = 五件事**：

| # | 内容 | 缺了会怎样 |
|---|---|---|
| 1 | **做到哪了**（可验证的状态） | 对方不知道从哪开始 |
| 2 | **为什么这样做**（关键决策与理由） | 对方会推翻重做，或重复已否掉的方案 |
| 3 | **还差什么**（剩余工作） | 对方不知道终点 |
| 4 | **接手第一件事** | 对方要花半天才能进入状态 |
| 5 | **坑**（反直觉的发现） | 对方会重新踩一遍 |

⛔ 第五项最有价值，也最常被漏 —— 因为它「不像是进度」。

## 第 1 步：写「做到哪了」（必须是可验证的）

### 1.1 三种状态描述

| 写法 | 判定 |
|---|---|
| 「做了一大半」 | ❌ 不可验证 |
| 「核心功能写完了，测试没写」 | ⚠ 半可验证 |
| 「`install.mjs` 56/56 通过；`market.mjs` 还没写」 | ✅ 可验证 |

### 1.2 必须附「怎么自己确认」

　　`状态：install.mjs 完成，verify-install.mjs 56/56 PASS`
　　`自己确认：node tools/skills/verify-install.mjs`

⛔ 只写「已完成」，对方无法区分「真完成」和「你以为完成」。

### 1.3 已提交 vs 未提交

| 状态 | 必须写清 |
|---|---|
| 已提交 | commit hash（对方能查到） |
| 未提交 | 改了哪些文件（对方要知道工作区有脏改动） |
| 有临时文件 | 哪些是临时的、能不能删 |

⛔ 「工作区有未提交改动」不写，对方可能 `git checkout` 一下就全丢了。

## 第 2 步：写「为什么这样做」（关键决策）

### 2.1 只写「不写会被推翻」的决策

不是所有决策都要写。筛选标准：**如果对方不知道理由，会不会改成另一种做法？**

该写的：
- 选了方案 A 而不是 B（否则对方会试 B）
- 用了一个看起来绕的做法（否则对方会「简化」掉）
- 明确不做某事（否则对方会以为是漏了）

不必写的：
- 命名习惯
- 代码风格
- 显而易见的实现

### 2.2 每条决策写三段

　　**决策**：用轮询而不是事件推送
　　**理由**：目标环境没有可靠的推送通道，轮询延迟（2s）在可接受范围内
　　**如果你要改**：先确认推送通道是否可用，否则会退回同样的问题

⛔ 第三段「如果你要改」是交接的精髓 —— 它防止对方重走老路。

## 第 3 步：写「还差什么」（剩余工作）

### 3.1 剩余工作的写法

每条要有：**做什么 + 完成判据 + 已知障碍**

| 剩余 | 完成判据 | 已知障碍 |
|---|---|---|
| 写 market.mjs 的索引损坏处理 | 索引写坏后 search 仍返回池内技能 | 无 |
| 接进 RPC | verify-skill-rpc 全过 | 需要先确认方法名不被前端占用 |

### 3.2 分清「必须做」与「可以不做」

| 类型 | 标记 |
|---|---|
| 不做就不算完成 | **必须** |
| 做了更好，不做也行 | 可选 |
| 明确不做（目标外） | 已排除（写明原因） |

⛔ 「已排除」这一项要写 —— 否则接手的人会把「明确不做的事」当成漏掉的事重新做一遍。

## 第 4 步：写「接手第一件事」

### 4.1 为什么要写这个

接手的人最大的成本是「进入状态」：读代码、理解上下文、找到切入点。
给他一个**明确的第一个动作**，能省掉半天。

### 4.2 写法

　　`1. 跑 node tools/skills/verify-install.mjs，确认 56/56 通过（先验证环境）`
　　`2. 读 tools/skills/install.mjs 头部注释（六条设计规矩）`
　　`3. 从「剩余工作」第 1 条开始`

⛔ 第一步应该是**验证环境**，不是直接干活 —— 环境不对时干什么都白费。

## 第 5 步：写「坑」（最有价值的部分）

### 5.1 什么算「坑」

**看起来该这样、其实是那样**的发现。三类：

| 类型 | 例子 |
|---|---|
| **反直觉的约束** | 「这个 API 文档说支持 X，实际不支持」 |
| **踩过的错** | 「我先试了 A 方案，失败原因是…」 |
| **隐式依赖** | 「必须先跑 B，否则 C 会静默失败」 |

### 5.2 写法

　　**坑**：`docs-index` 的 data 文件是快照
　　**表现**：check 报 PASS，但实际有 71 个文档没索引
　　**原因**：data/docs.json 是过期子集，不是实时扫的
　　**怎么发现**：拿真实目录数跟 data 里的条数对比
　　**现状**：已改成实时同步

五项：**现象 + 原因 + 怎么发现 + 现状 + 关联提交**。

⛔ 只写「注意 X」不写「为什么」，对方还是会踩 —— 因为「注意」无法指导判断。

## 交接自检

- [ ] 状态可验证（附了确认命令）
- [ ] 已提交/未提交说清了（含临时文件）
- [ ] 关键决策写了「如果你要改」
- [ ] 剩余工作有完成判据
- [ ] 标了「必须/可选/已排除」
- [ ] 接手第一件事是「验证环境」
- [ ] 坑写了「怎么发现」（不只是「注意」）
- [ ] 没有只写「进度顺利」这类无信息内容

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 八项自检全过
- WARN = 有决策没写「如果你要改」
- FAIL = 状态不可验证 / 未提交改动没说明 / 没有坑
- UNKNOWN = 交接者自己也不确定状态

```markdown
# 交接：<任务名>

## 1. 做到哪了
<状态>（可验证）
自己确认：<命令>
提交状态：<已提交 hash / 未提交文件列表 / 临时文件>

## 2. 关键决策
### <决策 1>
- 决策：
- 理由：
- 如果你要改：

## 3. 还差什么
| 剩余 | 完成判据 | 障碍 | 必须/可选 |
|---|---|---|---|

已排除（明确不做）：<>

## 4. 接手第一件事
1. <验证环境>
2. <读什么>
3. <从哪开始>

## 5. 坑
### 坑 1：<一句话>
- 现象：
- 原因：
- 怎么发现：
- 现状：
```

**判不了的部分**
- <哪些状态自己也确认不了>

## 假阳性清单（这些不算交接缺陷）

- 决策没写「如果你要改」（如果这个决策不可能被改）
- 剩余工作没估时间（估不准就不估，好过假精确）
- 坑很少（如果确实顺利）
- 没写代码结构说明（代码本身可读时不需要）

## 假阴性清单（最常漏的 8 类）

1. **状态不可验证**（「做了一大半」）
2. **未提交改动没说明**（对方一 checkout 就丢）
3. **决策只写「用了 A」不写「为什么不用 B」**
4. **没写「如果你要改」**（对方会重走老路）
5. **剩余工作没完成判据**
6. **没标「已排除」**（对方重做已否掉的事）
7. **接手第一件事是「读代码」而不是「验证环境」**
8. **坑只写「注意 X」不写「怎么发现」**

## 本仓库可用的命令

```bash
git status --short              # 看未提交改动
git log --oneline -5            # 看最近提交
node tools/quality/commit-gate.mjs  # 确认门禁状态
```

## 与其他技能的关系

- `task-breakdown`：交接前先确认剩余工作的拆解
- `changelog`：已完成部分写进变更日志
- `adr`：关键决策应留 ADR（交接里只写摘要）
- `debug-repro`：坑里的 bug 用它的格式记录
- `self-review`：交接后自己复盘是否漏了什么

## 边界（如实说清）

- 交接**无法传递「手感」**：对方仍要自己踩一些坑才能熟练
- 无法传递「你没想到要写的东西」—— 这永远是交接的固有损失
- 对方的知识背景不同，同一份交接的有效性不同
- 交接者自己状态不确定时，结论只能是 UNKNOWN（不许编一个「已完成」）
- 本技能不产出代码，只产出「怎么交」的判断
