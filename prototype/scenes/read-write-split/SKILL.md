# 读写分离 技能

> 读写分离最典型的事故：**写完立刻读，读的是从库，读不到刚写的数据**（主从延迟）。
> 判据：**用户更新完资料，刷新看到的是新的还是旧的？**

## 什么时候用

- 读多写少、读压力大
- 要用从库分担读
- 主从架构

## 什么时候**不**用

- 读压力不大（简单更好）
- 强一致要求高（分离增加复杂度）

## 第 1 步：主从架构与延迟

```
写 → 主库 → 复制(异步) → 从库 → 读
```

| 复制方式 | 延迟 | 一致性 |
|---|---|---|
| **异步**（默认） | 有延迟 | 最终 |
| 半同步 | 较小 | 较强 |
| 同步 | 低延迟 | 强（但慢） |

⛔ 异步复制的延迟不可控（毫秒到秒），这就是「读不到刚写」的根因。

## 第 2 步：读己之写（最常见的用户投诉）

| 方案 | 说明 |
|---|---|
| **写后短时读主** | 写完 N 秒内该用户的读走主 |
| **粘主会话** | 会话内读走主 |
| **版本号/gTID** | 等到从库追到该版本再读 |

★ 「读己之写」比「全局强一致」便宜得多，能解决大多数投诉。

## 第 3 步：路由策略

| 读类型 | 走哪 |
|---|---|
| 强一致读（余额） | 主库 |
| 一般读（列表） | 从库 |
| 写后读 | 主库（短时） |

⛔ 所有读都走从库 = 关键数据读到旧值。

## 第 4 步：从库故障与压力

| 问题 | 处理 |
|---|---|
| 从库挂 | 读降级回主（但主压力大） |
| 复制的单点 | 多从库 |
| 从库延迟大 | 监控 + 剔除延迟大的 |

## 第 5 步：监控

| 指标 | 告警 |
|---|---|
| 主从延迟（秒） | 超阈值 |
| 从库复制中断 | 是 |
| 读命中从库比例 | 过低 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 关键读走主 + 读己之写 + 延迟监控
- WARN = 有分离但无读己之写
- FAIL = 全走从库 / 无延迟监控 / 写后读从库
- UNKNOWN = 拿不到架构

## 假阳性清单（这些不算「读写分离好」）

- 分离了但全读从库
- 无延迟监控
- 写完读从库

## 假阴性清单（最常漏的 8 类）

1. **写后读从库**（读不到）
2. **无读己之写**
3. **强一致读走从库**
4. **无延迟监控**
5. **从库挂无降级**
6. **从库延迟大未剔除**
7. **复制中断无告警**
8. **事务内读写分离混乱**

## 与其他技能的关系

- `consistency-model`：一致性级别

## 边界（如实说清）

- 读写分离解决读压力，不解决写压力
- 强一致读牺牲分离收益
- 本技能不实现中间件，只设计
