# 服务网格 技能

> 服务网格把「服务间通信的横切能力」（mTLS/重试/熔断/可观测/流量管理）从代码挪到 sidecar。
> 但它**增加延迟、运维复杂度、资源开销**。很多团队上了发现不值得。
> 判据：**你的服务通信治理问题，真的需要 mesh 才能解决，还是库/SDK 就够？**

## 什么时候考虑

- 多语言服务（库方案每语言都要实现）
- 需要统一 mTLS/可观测
- 复杂流量管理（灰度/故障注入）

## 什么时候**不**用

- 单一语言（用成熟库更简单）
- 少量服务（复杂度不值）
- 团队无 K8s/运维能力

## 第 1 步：mesh 给什么

| 能力 | 说明 |
|---|---|
| **mTLS** | 服务间加密+身份 |
| 流量管理 | 灰度/镜像/故障注入 |
| 重试/熔断/超时 | 统一策略 |
| 可观测 | 自动 metrics/tracing |
| 访问控制 | 谁能调谁 |

## 第 2 步：成本（别忽略）

| 成本 | 说明 |
|---|---|
| **延迟** | 每跳多一次 sidecar 转发 |
| 资源 | 每个 pod 一个 sidecar（内存/CPU） |
| 复杂度 | 控制面/数据面运维 |
| 调试难 | 问题在 mesh 还是应用？ |

## 第 3 步：与库方案对比

| 维度 | Mesh | 库/SDK |
|---|---|---|
| 多语言 | ✅ 透明 | ❌ 每语言实现 |
| 延迟 | 高（sidecar） | 低 |
| 复杂度 | 高 | 低 |
| 落地 | 运维支持 | 侵入代码 |

★ 单语言、团队小 → 库方案（如各语言的 resilience 库）通常更划算。

## 第 4 步：渐进落地

| 阶段 | 做法 |
|---|---|
| 1 | 只上可观测（mTLS） |
| 2 | 加流量管理 |
| 3 | 全量 |

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 盲目上 mesh | 复杂度压垮团队 |
| sidecar 资源未估 | 成本超预期 |
| 延迟未测 | 性能下降 |
| 与现有 LB 冲突 | 流量错乱 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 明确需要（多语言/复杂流量）+ 成本可接受 + 渐进
- WARN = 上了 mesh 但团队能力不足
- FAIL = 单语言/少服务却上 mesh / 成本未估

## 假阳性清单（这些不算「需要 mesh」）

- 单语言团队
- 少量服务
- 只是想用新东西

## 假阴性清单（最常漏的 8 类）

1. **盲目上 mesh**（复杂度爆）
2. **sidecar 资源未估**
3. **延迟未测**
4. **单语言却用 mesh**（库更简单）
5. **与 LB 冲突**
6. **调试能力不足**
7. **一步全量上**
8. **控制面单点**

## 与其他技能的关系

- `circuit-breaker`：mesh 提供
- `load-balancing`：流量
- `observability-design`：可观测
- `mTLS`/`auth-design`：安全

## 边界（如实说清）

- mesh 不是银弹，多数团队不需要
- 运维成本常被低估
- 本技能不实现，只评估
