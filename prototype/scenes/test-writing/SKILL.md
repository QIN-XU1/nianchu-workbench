# 写测试 技能

> 一条永远绿的测试等于没有测试，甚至更糟 —— 它让人**误以为**这里被守住了。
> 本技能的核心判据只有一条：**把被测实现改坏，这条测试必须变红**。做不到就不算测试。

## 什么时候用

- 新功能要补测试
- 修了 bug 要加回归用例
- 现有测试「一直是绿的」，想确认它是否承重
- 覆盖率数字看着还行，但不确定守住了什么

## 什么时候**不**用

- 根因还没定位 → 先 `debug-repro`
- 要审别人的代码 → `code-review`
- 要做发布前整体门禁 → `release-gate`

## 第 1 步：先想清「这条测试守什么」

动笔前用一句话写下来，格式必须是：

> **如果 <某个具体行为> 坏了，这条测试会红。**

举例（好）：
> 如果 `applyPatch` 在上下文不匹配时仍然写入文件，这条测试会红。

举例（坏）：
> 如果 `applyPatch` 有问题，这条测试会红。 ← 「有问题」太模糊，无法设计断言

⛔ 写不出这句话，说明你还不知道该测什么，先别写。

## 第 2 步：红 → 绿 → 红（顺序不能变）

### 2.1 先写测试，确认它失败（红）

在**还没实现**（或故意改坏）的情况下跑一次，必须看到失败。

为什么必须先红：只有红过一次，才能证明「这条断言真的在读那个值」。
从没红过的测试，很可能是断言写错了位置（比如断言了一个常量、或断言了 mock 自己的返回值）。

### 2.2 让实现通过（绿）

实现后跑，通过。

### 2.3 再改坏一次，确认它又红（第二次红）

这一步最常被跳过，但它是**唯一能证明测试承重的方法**：

1. 把被测逻辑改坏（改返回值、删掉校验、把边界改成 `<` 换 `<=`）
2. 跑测试 → **必须红**
3. 恢复实现 → 必须绿

⛔ 如果改坏了还是绿，这条测试是装饰品。要么断言不对，要么断言的位置在 mock 上。

## 第 3 步：覆盖四类，缺一不可

| 类别 | 要问的问题 | 最少条数 |
|---|---|---|
| **正常路径** | 典型输入下，输出对不对？ | 1 |
| **边界** | 空 / 0 / 1 / 超大 / 超长 / 负数 / 边界相等 | 2 |
| **错误路径** | 非法输入、缺参数、类型错、外部失败 | 1 |
| **反例（关键）** | 构造一个**必须被拒绝**的输入，断言它真的被拒 | 1 |

关于「反例」的特别说明：**反例不是「跑一下不出错」，而是「断言它被明确拒绝」**。

- 差：`expect(() => parse('bad')).not.toThrow()` ← 这叫「没崩」，不叫「被拒绝」
- 好：`expect(parse('bad')).toEqual({ ok: false, error: 'invalid_input' })` ← 断言了明确的拒绝形态

为什么强调：错误被**静默吞掉**（返回 undefined、返回空数组、返回 ok:true 但没做事）是最难发现的 bug 形态。反例测试是唯一能守住它的东西。

## 第 4 步：断言要守「契约」而不是「实现细节」

| 该断言 | 不该断言 |
|---|---|
| 返回值的关键字段与值 | 内部私有变量的值 |
| 错误码 / 错误类型 | 错误信息的完整文案（会随翻译/措辞变化） |
| 对外可见的副作用（文件被写、记录被加） | 调用了几次内部函数 |
| 顺序有语义时的顺序 | 无序集合的遍历顺序 |

⛔ 断言错误文案全文，会让「改个措辞」就红 —— 那种红不是回归，是噪音。

### 关于「写死数字」

写死数字有两种：

- **该写死**：测试要的正是精确值（如「压缩后恰好 1489 tokens」在测算法时）
- **不该写死**：数字来自外部、会自然增长（如「技能总数 = 30」）

判断方法：**这个数字会不会因为「无关改动」而变化？** 会 → 别写死，改成从源头读。

本仓库的实例：`verify-skills.mjs` 曾断言「list 的键名恰好是 description,name」，
后来 loader 加了 `category` 字段就红了 —— 那不是回归，是断言守错了东西（守键名而非守意图）。
修法是改成「必须有 name/description、必须没有 body」。

## 第 5 步：测试自身的质量检查

写完跑这三条：

1. **独立运行**：单独跑这条测试能过吗？（不依赖别的测试先跑）
2. **可重复**：连跑 3 次结果一致吗？（不依赖时钟/随机/网络）
3. **快**：单条测试应在秒级完成（慢测试会被跳过，等于没有）

不稳定的测试比没有测试更糟：它会训练人「红了就重跑」。

## 测试数据的三条纪律

1. **不依赖真实外部服务**：网络、模型网关、第三方 API 一律 mock 或跳过并标 UNKNOWN
2. **不污染真实数据**：写文件用临时目录（`os.tmpdir()` + 进程号），`finally` 里清理
3. **不依赖执行顺序**：每个测试自己准备前置状态

本仓库实例：`verify-git-status.mjs` 在 `os.tmpdir()` 建临时 git 仓库造 4 种状态
（干净/未跟踪/已修改/重命名），跑完 `fs.rmSync` 清理，从不碰主仓库。

## 输出格式

写完按这个报告：

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`

**1. 守什么**
- 「如果 <行为> 坏了，这条测试会红」：<一句话>

**2. 三段验证**
- 红（实现前/改坏后）：<贴失败输出摘要>
- 绿（实现后）：<贴通过输出>
- 再红（二次改坏）：<贴失败输出摘要> ← 缺这条说明没验承重

**3. 覆盖**
- 正常路径：<条数>
- 边界：<列出边界值>
- 错误路径：<列出错误输入>
- 反例：<构造了什么必须被拒的输入，断言了什么拒绝形态>

**4. 测试自身**
- 独立运行：是/否
- 连跑 3 次一致：是/否
- 单条耗时：<ms>

**5. 判不了的部分**
- <缺什么>

## 假阳性清单（这些红不是回归）

- 断言了错误信息全文，改措辞就红
- 断言了无序集合的顺序
- 断言了会自然增长的总数（技能数、文件数）
- 断言了耗时阈值（机器快慢不同）
- 断言了日志格式

## 假阴性清单（最常漏的 8 类）

1. **从没红过的测试**（写完直接绿，没验证过它真的在读值）
2. **只测正常路径**（happy path 100% 覆盖，错误路径 0%）
3. **反例写成「不抛异常」**（没断言明确的拒绝形态）
4. **断言 mock 的返回值**（测的是 mock，不是实现）
5. **改坏实现仍然绿**（断言位置错，或根本没断言）
6. **写死会自然变化的数字**（下次无关改动就红，然后被人删掉）
7. **测试之间有顺序依赖**（单独跑挂，整批跑过）
8. **测完不清理**（临时文件残留，污染后续运行）

## 本仓库可用的命令

```bash
node tools/quality/scan-mutation-residue.mjs    # 变异残留（调试代码/故意改坏没恢复）
node tools/quality/commit-gate.mjs              # 提交前门禁（确认没弄坏别的）
node tools/evolve/verify-mutation.mjs           # 突变承重验证：证明断言真的会红
```

## 与其他技能的关系

- `debug-repro`：最小复现直接变成回归用例（这是最自然的来源）
- `code-review`：第 5 层「可测性」就是查这个
- `refactor-plan`：重构前先补测试（没有测试的重构是赌博）
- `release-gate`：发布前跑全量验收
- `evidence-audit`：怀疑「测试通过」不可信时复核

## 边界（如实说清）

- 测试只能守住**你想到的情况**；没想到的输入它守不住
- 覆盖率数字不等于保护力 —— 100% 行覆盖仍可能一条断言都不承重
- 依赖外部服务/模型的测试必然不稳定，只能标 UNKNOWN，不能当绿
- 「二次改坏验证」需要能安全地改代码；在只读环境里做不到，此时应如实说明
- 本技能不判断「该不该有这条测试」（那是需求问题），只判断「写了的是不是真测试」
