# 限流设计 技能

> 限流最容易做错的是**只在一个维度限**：只限 IP，则分布式代理绕过；只限用户，则未登录流量不设防。
> 判据：**被恶意打的时候，限流是不是最后一道墙？** 是的话它要能自己扛住，不能被绕过。

## 什么时候用

- 对外 API 防滥用
- 登录/短信/下单等敏感接口
- 防爬虫/防刷
- 保护下游不被打垮

## 什么时候**不**用

- 纯内网可信调用（但有 DDoS 仍需前置防护）
- 只查一次流量异常 → `observability-design`

## 第 1 步：选算法

| 算法 | 特点 | 适用 |
|---|---|---|
| **固定窗口** | 简单，但窗口边界有 2 倍突发 | 粗粒度 |
| **滑动窗口** | 平滑，内存稍多 | 常用 |
| **令牌桶** | 允许突发（桶容量） | 允许短突发 |
| **漏桶** | 恒定速率，不允许突发 | 严格平滑 |

⛔ 固定窗口的「边界 2 倍突发」：窗口 1 末尾打满 + 窗口 2 开头打满 = 瞬时 2 倍。

## 第 2 步：定限流维度（要多维组合）

| 维度 | 防什么 | 绕过风险 |
|---|---|---|
| **IP** | 单来源刷 | 代理池绕过 |
| **用户/Token** | 单账号刷 | 多账号 |
| **接口** | 单接口被打 | — |
| **全局** | 整体过载 | — |
| **设备指纹** | 换 IP 换账号 | 指纹伪造 |

⛔ 只限单维必被绕过。**至少 IP + 用户 + 全局 三层**。

## 第 3 步：超限后的响应

| 响应 | 说明 |
|---|---|
| **状态码 429** | 标准「Too Many Requests」 |
| **Retry-After 头** | 告诉客户端多久后可重试 |
| **降级** | 返回缓存/默认值而非报错 |
| **排队** | 削峰（异步场景） |

⛔ 超限直接 500 或静默丢弃，客户端会疯狂重试。

## 第 4 步：实现要点

| 要点 | 说明 |
|---|---|
| **原子性** | 计数用 Redis INCR/Lua 保证原子 |
| **时钟** | 分布式限流用中心化计数，别用各机器本地时间 |
| **预热** | 重启后令牌桶是空的，冷启动会限死 |
| **白名单** | 内部/健康检查要豁免 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 多维限流 + 算法合理 + 429+Retry-After + 原子计数
- WARN = 单维限流 或 无降级
- FAIL = 无限流 / 超限返回 500 / 计数非原子
- UNKNOWN = 拿不到流量模型

## 假阳性清单（这些不算「有限流」）

- 只有单维 IP 限流
- 超限返回 500
- 本地计数（分布式下不准）

## 假阴性清单（最常漏的 8 类）

1. **只限单维**（易绕过）
2. **固定窗口边界 2 倍突发**
3. **超限返回 500**（客户端狂重试）
4. **计数非原子**（并发超发）
5. **本地时钟**（分布式不准）
6. **重启令牌桶空**（冷启动限死）
7. **无 Retry-After**
8. **健康检查被限流**

## 边界（如实说清）

- 限流防不住大流量 DDoS（需要前置清洗）
- 阈值要靠压测与真实流量定，不能拍脑袋
- 本技能不实现，只设计规则与响应
