# 多模型路由 技能

> 一个模型挂了你得有备用，但「有备用」不等于「降级正确」。
> 判据：**换到备用时，你知道换成了谁、为什么换、试了几次吗？全挂时你敢说 FAIL 吗？**

## 什么时候用

- agent 要接多个模型供应商
- 某模型限流/宕机，要自动降级
- 评审「多模型」「故障转移」这类声明

## 什么时候**不**用

- 单模型够用且无 SLA 要求

## 第 1 步：按用途（role）建注册表

不要一个全局默认模型。按用途分：对话、工具调用、摘要、审阅。每个 role 有一串候选，按优先级排。

## 第 2 步：顺序故障转移，记录每一次尝试

`callWithFailover` 依次试候选，每次尝试都记：

| 字段 | 含义 | 为什么要有 |
|---|---|---|
| model | 这次用的哪个 | 知道换成了谁 |
| ok | 成没成 | 失败点在哪 |
| state | 状态 | 四态可审计 |
| ms | 耗时 | 定位慢模型 |
| reason | 失败原因 | 不是「挂了」而是「429 限流」 |

返回里带 `servedBy`（最终谁服务）、`failoverIndex`（第几个候选生效）、`attempts`（完整尝试列表）。

## 第 3 步：全挂时如实 FAIL，绝不返回空 content 假装成功

这是最危险的一步。所有候选都失败 → 返回 `state: FAIL` + 原因，**不要**返回 `content: ""` 冒充模型说了空话。

## 反例（写下来防复发）

- ✗ 备用候选不满足该用途的最低能力：能对话但不支持 function calling 的模型，不能拿来当「工具调用」的备用——换过去就静默失败
- ✗ 全挂返回空字符串：上层以为成功，产出物是空的
- ✗ 只记「失败」不记原因：429 和 500 的处置完全不同
- ✗ 坏候选排前面就不试了：坏在前、好在后时，必须能跳过坏的继续试

## 自检清单

- [ ] 坏候选在前，好候选在后 → 仍能成功且 `failoverIndex=1`
- [ ] 全挂 → `state=FAIL`、`attempts` 完整、不返回 content
- [ ] 每次尝试有 model/ok/state/ms/reason 五件套
- [ ] 备用候选满足该 role 的最低能力

## 参考实现指路

本仓库 `tools/agent/models.mjs`：按 role 的模型注册表 + `callWithFailover` 顺序链、返回 `servedBy` / `failoverIndex` / `attempts`、全挂如实 FAIL。`tools/agent/verify-models.mjs` 是它的反例测试。
