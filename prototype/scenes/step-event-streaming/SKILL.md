# 步骤事件流 技能

> 用户看着 agent「转圈」20 秒，不如让每一步过程即时出现。但「流式」最容易造假：把结果攒到最后一起返回，也叫「返回了」。
> 判据：**第一条事件的时间，远早于最终返回的时间吗？还是跑完才一起到？**

## 什么时候用

- agent 有多步工具调用，用户想看到进度
- 要降低「看起来卡住」的焦虑
- 评审「流式/过程可见」这类声明

## 什么时候**不**用

- 单步秒级任务

## 第 1 步：每一步都推事件，不要攒到最后

工具每执行完一步，就推一条事件（step done / tool result）。不要等整个 run_task 结束才把一堆事件一次性吐出。

## 第 2 步：用「首事件时间 vs 最终返回时间」自证

这是区分真假流式的硬判据：

- 记录**收到第一条事件的时间** `t_first`
- 记录**最终返回的时间** `t_final`
- 真流式：`t_first` 明显小于 `t_final`（过程在跑就可见）
- 假流式：`t_first ≈ t_final`（攒到最后一起给）

## 第 3 步：事件要有序、可关联

- 事件带序号或步骤标识，能按序拼接成完整过程
- 失败也要推一条事件（不是静默）

## 反例（写下来防复发）

- ✗ 全部跑完才一起返回事件 → 不是流式，是「批量返回」
- ✗ 首事件时间 == 最终返回时间 → 自证是假的
- ✗ 只推开始和结束，中间步骤不推 → 用户还是看不到过程
- ✗ 失败不推事件 → 卡住时不知道卡在哪

## 自检清单

- [ ] 每步推一条事件（不是只开始/结束）
- [ ] t_first 明显 < t_final（真流式自证）
- [ ] 事件有序可拼接
- [ ] 失败也推事件

## 参考实现指路

本仓库 `tools/agent/verify-streaming.mjs`：用「收到第一条事件的时间」对比「最终返回的时间」来证明 run_task 期间工具步骤真的边跑边到（不是等全部跑完才一起到）。四态：0 PASS / 1 FAIL / 2 UNKNOWN。
