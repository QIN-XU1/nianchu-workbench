# 分布式缓存 技能

> 单机缓存和应用缓存（见 `caching-strategy`）不同：分布式缓存要处理**分片、热点、节点增减、集群一致性**。
> 判据：**一个爆款商品打到单个缓存节点，会不会把那个节点打挂？**

## 什么时候用

- 缓存数据超单机内存
- 要高可用缓存集群
- 有热点

## 什么时候**不**用

- 单机缓存够用

## 第 1 步：分片

| 方式 | 说明 |
|---|---|
| **一致性哈希** | 节点增减影响小（推荐） |
| 取模 | 简单但扩容全迁 |
| 客户端分片 / 代理分片 | 谁负责路由 |

★ 一致性哈希 + 虚拟节点：节点增减只影响相邻区间，且分布均匀。

## 第 2 步：热点 key（分布式缓存的头号问题）

| 问题 | 一个 key 访问极高 → 打爆所在节点 |
|---|---|
| 解法 | **本地缓存**（多副本） |
| | **key 拆分**（加随机后缀，分散） |
| | 读多写少用多级缓存 |

⛔ 热点 key 只靠分片解决不了——它就在一个节点上。要本地缓存/拆分。

## 第 3 步：多级缓存

```
本地缓存（L1，进程内，快）→ 分布式缓存（L2）→ DB
```

- L1 命中快，但要处理一致性（多实例 L1 不同步）
- L2 共享

## 第 4 步：集群一致性

| 问题 | 处理 |
|---|---|
| 主从复制延迟 | 见 `read-write-split` |
| 节点故障 | 副本/哨兵/集群 |
| 脑裂 | quorum |

## 第 5 步：与源一致

| 策略 | 说明 |
|---|---|
| 失效 | 写 DB 后删缓存 |
| TTL | 兜底过期 |
| binlog 驱动 | 最可靠 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 一致性哈希 + 热点方案 + 多级 + 集群高可用
- WARN = 有分片但无热点方案
- FAIL = 热点打爆 / 取模扩容 / 无副本
- UNKNOWN = 拿不到缓存规模

**1. 分片**
| 项 | 方式 |
|---|---|

**2. 热点**
| 方案 | 有吗 |
|---|---|

**3. 集群**
| 项 | 方式 |
|---|---|

**4. 判不了的部分**
- <拿不到的访问分布>

## 假阳性清单（这些不算「分布式缓存好」）

- 有集群但无热点方案
- 取模分片
- 无副本

## 假阴性清单（最常漏的 8 类）

1. **热点 key 打爆**
2. **取模扩容**（全迁）
3. **无副本**（节点挂全丢）
4. **一致性哈希无虚拟节点**（倾斜）
5. **L1 多实例不一致**
6. **无 TTL 兜底**
7. **脑裂无 quorum**
8. **与源不一致无驱动**

## 与其他技能的关系

- `caching-strategy`：应用缓存
- `load-balancing`：一致性哈希
- `read-write-split`：复制延迟
- `data-partitioning`：分片

## 边界（如实说清）

- 分布式缓存有一致性/网络开销
- 热点是业务特征，难完全消除
- 本技能不实现，只设计
