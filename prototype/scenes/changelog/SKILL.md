# 变更日志 技能

> 变更日志不是「commit 列表换排版」。
> 它的读者是**要决定「要不要升级」的人**，所以他需要的是：
> **这次改了什么、会不会坏我的东西、有问题怎么回退。**
> 一条写不出「影响」的条目，就不该出现在日志里 —— 它属于 commit message。

## 什么时候用

- 发版前整理本次范围的改动
- 想回顾「某个版本到底改了什么」
- 用户问「最近更新了什么」

## 什么时候**不**用

- 面向**非技术用户**讲更新 → `release-notes`（讲影响，不讲类别）
- 记录「为什么这么决定」→ `adr`
- 写「怎么用」→ `doc-write`
- 只改了一行内部实现 → 不必进日志

## 第 0 步：先划清三个「日志类」文档的分工

这是本技能最容易跑偏的地方，先定死：

| 文档 | 读者 | 回答的问题 | 单位 |
|---|---|---|---|
| **changelog** | 维护者 / 集成方 | 这次**改了什么**？会不会影响我？ | 版本 |
| `release-notes` | 终端用户 | 这次更新**对我有什么好处**？ | 版本 |
| `git log` | 提交者自己 | 这行为什么改的？ | 提交 |

判据：**如果一条内容在 changelog 和 release-notes 里写法完全一样，说明其中一个写错了。**

- changelog 写「`parseConfig` 现在拒绝空字符串（此前静默回退默认值）」
- release-notes 写「修复：配置写空时不再悄悄用默认值，会明确报错」

## 第 1 步：确定范围（这次包含哪些改动）

### 1.1 范围来源

| 来源 | 命令 | 注意 |
|---|---|---|
| 提交 | `git log v1.2.0..HEAD --oneline` | 要按 tag 界定，不是「最近 50 条」 |
| 台账 | `research/改进台账.json` 里 `at` 落在范围内的条目 | 本仓库的主要来源 |
| PR/合并记录 | 合并标题 | 常缺细节，需回读 diff |

⛔ 范围必须**可复算**：写出「从哪个 tag 到哪个 tag」或「台账 id 区间」，
否则后人无法核对「有没有漏」。

### 1.2 排除噪声

这些不该进 changelog：

- 纯格式化/重命名（无行为变化）
- 依赖小版本升级（无 API/行为变化）
- 测试代码改动
- 文档错别字

判据：**对使用者有可观测影响吗？** 没有 → 不进。

## 第 2 步：按五类归档

### 2.1 五类定义（必须严格）

| 类别 | 定义 | 反例（容易错放） |
|---|---|---|
| **新增** | 此前不存在的能力 | 把一个内部函数导出成公开 API → 是「变更」 |
| **修复** | 此前行为与预期不符，现在符合 | 改了个错别字 → 不算 |
| **变更** | 行为变了但不算修复（含默认值、输出格式、性能） | 默认值从 A 改成 B → **必须标「变更」** |
| **移除** | 删除了公开能力 | 删了内部函数 → 不算 |
| **安全** | 修复了漏洞 | 加了输入校验但同时改变了行为 → 两类都写 |

⛔ 最常见的错误：**把「变更」写成「修复」**。
「以前输出 `a`，现在输出 `b`」如果以前不是 bug，那就是变更 —— 标成修复会让人以为旧版本错了。

### 2.2 不兼容变更必须显著

不兼容（breaking）必须有**独立区块**，不能混在列表里：

> **改了什么**：`parseConfig()` 不再接受 `null`，传入会抛 `TypeError`
> **此前行为**：静默返回默认配置
> **怎么迁移**：把 `parseConfig(null)` 改成 `parseConfig({})`

三项缺一不可：**改了什么 / 此前行为 / 怎么迁移**。

## 第 3 步：每条写「影响」而不是「实现」

### 3.1 写法对照

| 差（实现） | 好（影响） |
|---|---|
| 把 `for` 循环改成 `map` | （不写，无影响） |
| 重构了 `ConfigLoader` 类 | 配置加载失败时会给出具体字段名，不再只说「配置错误」 |
| 升级了 `zod` 到 v4 | 校验错误信息格式变化：`errors[]` 变成 `issues[]`（**影响解析错误的调用方**） |
| 修复了 `pickPath` 的 bug | 修复：工作区路径为空时不再把参数当路径（此前会写错文件） |

### 3.2 每条必须能追溯

格式建议：`- <影响描述>（<提交 hash 或 台账 id>）`

⛔ 只贴 commit hash 不算 changelog（那是 `git log --oneline`）；
**但完全没有追溯链接的条目也不算合格** —— 后人无法查证。

### 3.3 数字要具体

- 差：「性能提升」
- 好：「`/api/host-status` P95 从 800ms 降到 210ms（-73.8%）」

- 差：「修了很多问题」
- 好：「修复 3 个路径穿越问题（`..`、`~` 展开、Windows 盘符）」

## 第 4 步：维护方式（追加式，不改历史）

### 4.1 追加式原则

- 已发布的版本**不再修改**（改了要发新补丁版本）
- 未发布的版本可以持续补充
- 格式 `## [版本] - 日期`

### 4.2 未发布区（Unreleased）

　　`## [Unreleased]` 区先放未发布改动，发版时整体移到 `## [版本] - 日期` 下。

好处：随时可发版，不必临时整理。

### 4.3 版本语义要一致

| 变更类型 | 版本位 |
|---|---|
| 不兼容 | major |
| 新增能力 | minor |
| 修复/变更 | patch |

⛔ 有了不兼容变更却发 patch，等于埋雷。

## 第 5 步：自检（发版前逐条过）

- [ ] 范围可复算（tag 区间 / 台账 id 区间）
- [ ] 每条都有「影响」，没有纯实现描述
- [ ] 五类归类正确（尤其「变更」没被写成「修复」）
- [ ] 不兼容变更独立成块，含「此前行为 + 迁移方法」
- [ ] 每条可追溯到提交或台账 id
- [ ] 数字具体（无「优化了」「提升了」）
- [ ] 版本号语义正确（breaking → major）
- [ ] 已发布版本未被修改

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 五项自检全过
- WARN = 有未覆盖项（如某些提交没查到）
- FAIL = 有不兼容变更未标注 / 条目无影响描述 / 范围不可复算
- UNKNOWN = 拿不到提交历史或台账

```markdown
## [版本] - YYYY-MM-DD

### ⚠ 不兼容变更
- <改了什么>（此前：<旧行为>）（迁移：<怎么改>）（<id>）

### 新增
- <影响>（<id>）

### 修复
- <影响>（<id>）

### 变更
- <影响>（<id>）

### 移除
- <影响>（<id>）

### 安全
- <影响>（<id>）
```

**范围**：`<tag A>..<tag B>` 或 台账 `<id 起>..<id 止>`（共 N 条）

**判不了的部分**
- <哪些提交无法判断影响>

## 假阳性清单（这些不必进 changelog）

- 代码格式化、重命名（无行为变化）
- 依赖 patch 升级（无 API 变化）
- 测试补充（除非修复了「测试没测到」的漏洞）
- 注释、文档错别字
- 内部重构（对外行为完全一致）
- CI 配置调整（除非影响发布产物）

## 假阴性清单（最常漏的 8 类）

1. **默认值变化**被当成「修复」（其实是变更）
2. **错误信息/格式变化**（调用方解析会坏）
3. **性能显著变化**（用户可感知）
4. **依赖升级带来的 API 变化**（传递依赖也算）
5. **不兼容变更混在小修复里**
6. **条目只有 commit hash 没有影响描述**
7. **范围用「最近 N 条」而非 tag 区间**（不可复算）
8. **改了已发布的版本条目**（历史被篡改）

## 本仓库可用的命令

```bash
git log --oneline <tagA>..<tagB>          # 界定范围
node tools/evolve/evolve.mjs verify        # 台账完整性（条目可追溯）
node tools/quality/verify-docs.mjs         # 文档里的数字与仓库一致
```

## 与其他技能的关系

- `release-notes`：面向用户的版本，从 changelog 派生（但重写语言）
- `adr`：记录「为什么」，changelog 记录「改了什么」
- `doc-write`：changelog 里的迁移说明可链到详细文档
- `release-gate`：发版前门禁会检查 changelog 是否齐备
- `dep-upgrade`：依赖升级的 breaking 要同步进 changelog

## 边界（如实说清）

- changelog 只能记录**已知的**影响；未预见的副作用不会出现
- 「影响」的判断依赖对使用者的了解；内部项目与公开库的写法不同
- 无法追溯的改动（如压缩后的合并提交）只能标 UNKNOWN
- 大量微小改动不适合逐条列；应聚合（但要说明聚合了什么）
- 本技能不判断「该不该发版」；那是 `release-gate` 的事
