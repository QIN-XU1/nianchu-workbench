# 错误处理 技能

> 错误处理最坏的两种：**吞异常**（出错了假装没事，故障蔓延）和**乱抛**（用户看到堆栈）。
> 判据：**出错了，系统知道吗？用户看得懂吗？还能恢复吗？**

## 什么时候用

- 设计错误处理策略
- 异常被吞/故障难查
- 错误提示混乱

## 什么时候**不**用

- 纯脚本（简单 try/catch 够）

## 第 1 步：错误分类（决定怎么处理）

| 类型 | 例子 | 处理 |
|---|---|---|
| **可恢复**（瞬时） | 超时、网络抖 | 重试/降级 |
| **永久** | 参数错、404 | 直接失败，不重试 |
| **编程错误** | 空指针、逻辑错 | 记录+告警（不该发生） |
| **用户错误** | 输入非法 | 友好提示 |
| **系统错误** | 依赖挂、磁盘满 | 告警+降级 |

⛔ 所有错误同样处理 = 该重试的没重试、不该重试的死循环。

## 第 2 步：绝不吞异常（最常见的坏习惯）

| 反模式 | 后果 |
|---|---|
| `catch {}` 空 | 出错了无人知 |
| `catch { return null }` 无日志 | 故障静默蔓延 |
| 只 log 不处理 | 没恢复 |
| 只处理不 log | 难查 |

★ **吞异常是万恶之源**。要么处理、要么记录并抛出、要么转成可理解的错误。别「假装没事」。

## 第 3 步：错误传播（在哪层处理）

| 原则 | 说明 |
|---|---|
| **就近处理能处理的** | 能重试就在调用处重试 |
| **不能处理的往上抛** | 带上上下文 |
| **边界层转换** | 底层异常转成业务错误（不泄露内部） |
| **不重复记日志** | 每层都记=噪音，边界记一次 |

## 第 4 步：用户提示（安全与可用）

| 项 | 要求 |
|---|---|
| 可理解 | 不是堆栈 |
| 可行动 | 告诉用户怎么办 |
| **不泄露** | 不暴露 SQL/路径/密钥/堆栈 |
| 有错误码 | 便于排查 |

⛔ 直接把异常 message 返回给用户 = 泄露内部结构 + 用户看不懂。

## 第 5 步：可观测

| 项 | 要求 |
|---|---|
| 结构化日志 | 含 trace id/错误类型 |
| 告警 | 系统错误告警 |
| 错误率指标 | 突增发现 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 错误分类 + 不吞 + 正确传播 + 安全提示 + 可观测
- WARN = 有不吞但有层重复记日志
- FAIL = 吞异常 / 返回堆栈给用户 / 无分类
- UNKNOWN = 拿不到错误处理代码

## 假阳性清单（这些不算「错误处理好」）

- 有 try/catch 但空 catch
- 返回异常 message 给用户
- 只 log 不处理

## 假阴性清单（最常漏的 8 类）

1. **空 catch 吞异常**
2. **catch 返回 null 无日志**
3. **返回堆栈给用户**（泄露）
4. **不分类全重试**（永久错死循环）
5. **每层重复记日志**（噪音）
6. **无错误率监控**
7. **编程错误不告警**
8. **错误信息不可行动**

## 边界（如实说清）

- 「不吞异常」有时与「不让用户看到错误」冲突，要平衡
- 本技能不实现，只设计策略
