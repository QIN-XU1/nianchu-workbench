# 假绿检测 技能

> 最危险的测试不是失败的，是**永远通过的**。它给你虚假的安全感。
> 判据：**每个检查脚本，都有一个「故意造错必须被抓到」的反例吗？**

## 什么时候用

- 写/审检查脚本、验收脚本
- 发现「测试从来没红过」
- 评审「0 失败」这类结论

## 什么时候**不**用

- 纯信息性脚本（不判对错）

## 第 1 步：给每个检查配一条反例

反例 = **故意构造一个错误输入/状态，检查必须报失败**。例如：

- 造一个不存在的路径 → 路径检查必须 FAIL
- 造一个 200+HTML 的错误响应 → 错误语义检查必须 FAIL
- 注入一个真 bug → 测试必须变红

**反例不过 = 这个检查是假的**（它永远 PASS，什么也没验）。

## 第 2 步：堵住三类假绿

| 假绿类型 | 表现 | 堵法 |
|---|---|---|
| 永远通过 | 检查逻辑写错，任何输入都 PASS | 反例必须 FAIL |
| 撞预算算成功 | 步数/预算用尽却判 PASS | 撞预算 → 至少 WARN |
| 空实现也能过 | 函数是空壳但断言只查「不报错」 | 断言要查「真做了什么」 |

## 第 3 步：把「0 失败」的强度写清楚

「0 失败」可能意味着「全部通过」，也可能意味着「全部跳过」。报告里必须区分：**通过 N / 失败 M / 跳过 K / UNKNOWN J**。

## 反例（写下来防复发）

- ✗ 检查脚本没有反例自检 → 可能永远 PASS
- ✗ 撞预算判 PASS → 半成品当完成
- ✗ 只报「0 失败」不报「跳过几个」 → 掩盖未验证
- ✗ 反例用「本该失败」的模糊断言 → 反例本身也可能假绿

## 自检清单

- [ ] 每个检查有明确反例，且反例真能触发 FAIL
- [ ] 撞预算不判 PASS
- [ ] 断言查「真做了什么」而非「没报错」
- [ ] 报告区分 通过/失败/跳过/UNKNOWN

## 参考实现指路

本仓库 `tools/verify-all.mjs`（区分 通过/失败/UNKNOWN/WARN，按 0/1/2/3 退出码归类）；`verify-e2e-scripted.mjs`、`verify-api-error-contract.mjs` 等都内置「反例自测」段（造错必须判不合格）；`stop.mjs` 的 `assertNotFalseGreen` 专门堵「撞预算判 PASS」。

## 实战记录（本仓库真实事件，2026-11-22）

**事件**：我连续几轮向用户报「全量 verify 63 个脚本 0 失败」。
实际上 `verify-changeset-rpc` / `verify-streaming` / `verify-evidence-completeness`
三个脚本一直在 `exit 1`（真失败），只是被报成了 UNKNOWN——**这就是标准的假绿**：
报告说「0 失败」，但确实有失败。

**为什么没被发现**：我的统计口径是「有『通过N失败M』行的脚本才算数」+「无四态默认 UNKNOWN」。
两个口径叠加，把 3 个不打印标准行的失败脚本同时漏掉。

**修法**：
1. 用退出码归类（0/1/2/3），而不是靠解析文字；
2. 报告里同时列出「有失败 / UNKNOWN / WARN / 无通过行」四个数，缺一个都可能掩盖问题。

**复算**：`node tools/verify-all.mjs`（当前 63 脚本 · 有失败 0 · UNKNOWN 3 · WARN 1）。

**教训**：**「0 失败」必须和「UNKNOWN 几个」「跳过几个」一起报**。只报一个数，就是给假绿留门。
