# 变更集跨进程持久化 技能

> 内存里的变更集，进程一重启就没了——用户想回滚，发现「没有可回滚的变更」。
> 判据：**换一个全新进程，还能按 setId 找到变更集并回滚吗？回滚后文件逐字节一致吗？**

## 什么时候用

- agent 会改文件，且用户可能重启后再回滚
- 要评审「变更集持久化」这类声明
- 出现「重启后无法回滚」

## 什么时候**不**用

- 变更集只活在一次会话内

## 第 1 步：变更集写盘

每次记录 before/after 时，同步写到一个持久位置（带 setId），返回 `persisted=true`。

## 第 2 步：跨进程按 setId 找回

新进程内存为空，仍要能从盘上按 `setId` 加载变更集。这要求盘上结构带 setId 索引。

## 第 3 步：回滚逐字节恢复

回滚后文件内容必须**逐字节**等于原始（before）。不是「差不多」，是字节级。

## 第 4 步：重复回滚要报 WARN，不能装作又成功一次

已回滚状态也要持久化。再次回滚同一变更集 → **WARN**（说明已回滚），不是静默再删一遍。

## 反例（写下来防复发）

- ✗ 只存内存 → 重启后丢失
- ✗ 盘上无 setId 索引 → 找不回
- ✗ 回滚后内容差几字节 → 脏数据残留
- ✗ 重复回滚静默成功 → 掩盖状态混乱

## 自检清单

- [ ] 变更集写盘（persisted=true）
- [ ] 新进程按 setId 能找回
- [ ] 回滚逐字节恢复
- [ ] 重复回滚报 WARN

## 参考实现指路

本仓库 `tools/agent/verify-changeset-persist.mjs`（7 项：进程 A 写盘 → 进程 B 全新仍能找回并回滚 → 逐字节恢复 → 反例「重复回滚报 WARN」）；实现在 `tools/agent/changeset.mjs`。

## 实测数据（本仓库，可复算）

```
node tools/agent/verify-changeset-persist.mjs
```

实测 **7 通过 / 0 失败**，关键三步：

1. 进程 A 跑通并返回 `setId`，变更集写盘（`persisted=true`），文件确实被改
2. **进程 B（全新，内存为空）** 仍能按 `setId` 找到变更集
3. 进程 B 回滚后，文件**逐字节**恢复成原始内容
4. 反例：再开一个进程重复回滚 → `WARN`（已回滚状态也被持久化）

**为什么「逐字节」而不是「看起来对」**：只比文本可能漏掉行尾/编码差异；
逐字节比对才证明真的还原。

**教训**：**持久化要验证的是"另一个进程也能读到并正确使用"，不是"文件写出来了"**。
