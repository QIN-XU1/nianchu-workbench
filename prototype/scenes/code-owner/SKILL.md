# 代码所有权 技能

> 代码所有权的问题是：**要么没有 owner（代码烂了没人管），要么 owner 成瓶颈（所有改动都等他）**。
> 判据：**一个改动，能不能找到「懂这块且该审」的人，且不需要无限等？**

## 什么时候用

- 多人/多团队维护代码库
- 评审总卡住
- 模块无人负责
- 要划清边界

## 什么时候**不**用

- 单人项目
- 完全一次性的脚本

## 第 1 步：划所有权（按目录/模块）

| 粒度 | 说明 |
|---|---|
| 按目录 | `src/payments/**` 归支付组（最常见） |
| 按模块 | 逻辑模块归某组 |
| 按文件 | 细但维护烦 |

工具常见用 `CODEOWNERS` 文件，匹配路径→负责人。

⛔ 不划边界的后果：改一处牵涉三个组，谁都不敢动。

## 第 2 步：owner 的职责（不只是「有权审」）

| 职责 | 说明 |
|---|---|
| **评审** | 对改动把关 |
| **维护** | 保持可维护、还债 |
| **咨询** | 别人改这块时被咨询 |
| **不阻塞** | 不能成为唯一单点 |

## 第 3 步：评审分配（避免瓶颈）

| 方式 | 说明 |
|---|---|
| 必审（审批） | 关键路径必须 owner 批 |
| 建议审（reviewer） | 一般改动建议看 |
| **多 owner** | 避免单点，任一可批 |
| 团队而非个人 | 一个人休假别人能顶 |

⛔ 只指定一个个人 owner = 他休假全卡住。

## 第 4 步：缺席兜底

| 场景 | 处理 |
|---|---|
| owner 休假 | 有 backup owner |
| owner 离职 | 所有权转移要显式 |
| 无人认领 | 明确「谁 default 接」 |

## 第 5 步：反模式

| 反模式 | 问题 |
|---|---|
| owner 是唯一瓶颈 | 所有 PR 等他 |
| 所有权模糊 | 出事互相推 |
| owner 只挂名维护 | 代码烂了没人管 |
| 所有权过细 | 一个改动要三个 owner 批 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 边界清晰 + 多 owner/团队 + 缺席有 backup
- WARN = 有 owner 但单点
- FAIL = 无所有权 / 单个人瓶颈 / 无缺席兜底
- UNKNOWN = 拿不到团队结构

**1. 所有权边界**
| 路径/模块 | owner | backup |
|---|---|---|

**2. 评审规则**
| 类型 | 必审/建议 |
|---|---|

**3. 兜底**
| 场景 | 处理 |
|---|---|

**4. 判不了的部分**
- <拿不到的团队信息>

## 假阳性清单（这些不算「有所有权」）

- 有 CODEOWNERS 但都是一个人
- 挂了名不维护

## 假阴性清单（最常漏的 8 类）

1. **owner 是单点**（休假全卡）
2. **无 backup**
3. **所有权模糊**
4. **owner 只挂名**
5. **无 default 接盘**
6. **离职未转移**
7. **过细导致多方批**
8. **关键路径无强制审**

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁
```

## 与其他技能的关系

- `code-review`：评审本身的方法
- `handoff`：owner 变更的交接
- `on-call`：谁值班和谁 owner
- `decision-log`：所有权决策记录

## 边界（如实说清）

- 所有权是人的问题，工具只是辅助
- 跨团队边界需要协商，不是单方定
- 本技能不配工具，只设计制度
