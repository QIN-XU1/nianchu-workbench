# 回滚预案 技能

> 回滚预案的价值不在「写了一份文档」，而在**出事的那一刻，你不需要思考**。
> 所以判据很硬：**预案必须是「照着做」的，不是「参考一下」的。**
> 另一条同样重要：**先判断「能不能回滚」**。有些变更根本不可逆（数据被覆盖、外部已消费），
> 对它们写「回滚步骤」是自欺 —— 该写的是「不可逆，所以上线前必须做什么」。

## 什么时候用

- 准备上线一个有风险的变更
- 要改数据结构 / 迁移数据
- 要换依赖 / 换服务
- 要做不可逆操作（删数据、改协议、发外部通知）

## 什么时候**不**用

- 变更完全可逆且无风险（改个文案）→ 不需要
- 已经出事了正在救 → 直接执行预案，不要现写
- 要复盘已发生的事故 → `postmortem`

## 第 0 步：先判断「可逆性」（这一步决定预案的形态）

### 0.1 三类变更

| 类型 | 特征 | 预案形态 |
|---|---|---|
| **完全可逆** | 代码回滚即恢复，数据不变 | 写回滚步骤即可 |
| **部分可逆** | 代码可回滚，但数据已变 | 必须写「数据怎么回」 |
| **不可逆** | 数据被覆盖 / 外部已消费 / 已通知用户 | **写止损而非回滚** |

### 0.2 可逆性的判定问题

对每个变更问：

| 问题 | 若答案是「是」 |
|---|---|
| 有没有数据被**覆盖**（旧值丢失）？ | 部分可逆或不可逆 |
| 有没有数据被**删除**且无备份？ | 不可逆 |
| 有没有**外部系统**已消费了这次变更？ | 不可逆（对方不会退） |
| 有没有**用户**已看到/已收到通知？ | 不可逆（信任不可回滚） |
| 代码回滚后，旧代码能读**新格式**的数据吗？ | 不能 → 部分可逆，需要数据回滚 |

⛔ 最常见的自欺：**「代码能回滚」就以为「变更能回滚」**。
代码回去了，但数据库里已经是新格式 —— 旧代码读不了，等于回滚失败。

## 第 1 步：写触发条件（什么时候该回滚）

### 1.1 触发条件必须可观测

| 差 | 好 |
|---|---|
| 「如果出问题就回滚」 | 「错误率 > 5% 持续 3 分钟」 |
| 「看情况」 | 「P95 延迟 > 2s，或任一用户报告数据错误」 |
| 「严重的话」 | 「核心功能不可用（登录/下单/保存）」 |

### 1.2 三档触发

| 档位 | 条件 | 动作 |
|---|---|---|
| **立即回滚** | 数据错误 / 核心功能挂 / 安全事件 | 不等确认，直接回 |
| **准备回滚** | 指标异常但功能可用 | 5 分钟内决定 |
| **观察** | 指标轻微波动 | 继续观察，记录 |

⛔ 没有「立即回滚」这一档，出事时所有人都会等别人拍板 —— 那几分钟就是损失。

### 1.3 谁来按下按钮

必须写**具体角色**（不是「团队」）：

- 谁有权决定回滚（一个人，不是委员会）
- 谁执行（可能是同一个人）
- 谁负责通知（用户/上下游）

## 第 2 步：写回滚步骤（必须能照着做）

### 2.1 步骤的写法

每条必须是**一条命令或一次点击**，不是「恢复之前的版本」。

```
1. 执行 node tools/workbench/serve.mjs --rollback 或 git revert <commit>
2. 确认进程重启：curl http://127.0.0.1:47124/health 返回 200
3. 若第 2 步失败：手动 kill 进程后重跑 start-product.cmd
4. 数据回滚：从备份目录手工复制回 tools/memory/store.mjs 使用的数据文件（先 node tools/memory/verify-bulk-corrupt.mjs 确认备份可读）
5. 验证：见第 4 步
```

### 2.2 必须包含「如果这步失败」

每步都要有 fallback：

| 步骤 | 失败时 |
|---|---|
| 回滚命令 | 手动 checkout 到上一个 tag |
| 进程重启 | kill + 冷启动 |
| 数据恢复 | 从备份目录手工复制 |

⛔ 只写「成功路径」的预案，在真出事时会卡在第 1 步。

### 2.3 顺序很重要

**先止血还是先查因？** 一般是：

1. 先回滚代码（止血）
2. 再确认指标恢复
3. 最后查原因（不在回滚时查）

⛔ 在回滚过程中顺手查原因，会让回滚变慢 —— 而回滚速度就是损失大小。

## 第 3 步：数据可逆性（最容易翻车的地方）

### 3.1 三种数据变更

| 变更 | 回滚方式 | 前提 |
|---|---|---|
| **新增字段**（可空） | 代码回滚即可 | 旧代码忽略新字段 |
| **改字段含义** | 需要数据回滚 | 必须备份了旧值 |
| **删字段/删表** | 需要数据回滚 | 必须有备份 |

### 3.2 数据回滚的三问

| 问题 | 若答不上来 |
|---|---|
| 备份在哪？ | 没有数据回滚能力 |
| 备份是什么时候的？ | 回滚会丢那之后的数据 |
| 备份验证过能恢复吗？ | 回滚可能失败（备份是坏的） |

⛔ 「有备份」不等于「能恢复」。必须**验证过**（见 `data-migration` 技能）。

### 3.3 回滚窗口

**备份时刻 → 回滚时刻之间产生的数据会丢。**

必须写清：

- 备份时间点
- 预计回滚时间点
- 这段窗口内预计有多少写入（会丢多少）

## 第 4 步：验证回滚成功（不能凭感觉）

### 4.1 四项验证

| 项 | 怎么验 |
|---|---|
| **进程起来了** | 健康检查返回 200 |
| **版本对了** | 版本接口返回旧版本号 |
| **功能恢复** | 跑核心路径（登录/主流程） |
| **数据对了** | 抽样比对回滚前后的关键数据 |

### 4.2 反例：什么不算「回滚成功」

- 进程起来了但版本还是新的（回滚没生效）
- 版本对了但数据还是新格式（部分回滚）
- 核心功能能用但边缘功能挂了（没验全）
- 指标恢复了但错误日志还在刷（可能只是流量走了）

## 第 5 步：不可逆变更的「止损」写法

如果变更不可逆，预案应该写：

### 5.1 上线前的强制条件

| 条件 | 为什么 |
|---|---|
| 备份已验证可恢复 | 这是唯一的后悔药 |
| 灰度/小批量先行 | 把不可逆的范围缩小 |
| 有回滚窗口的明确截止时间 | 过了就真的不能退了 |
| 用户已被告知 | 信任层面不能事后补 |

### 5.2 出问题后的止损

不可逆变更出问题，不能「回滚」，只能：

1. **停止扩大**（关掉入口/停掉批次）
2. **补偿**（给受影响用户补数据/退款/道歉）
3. **修复**（在新状态上修，不是退回去）

⛔ 对不可逆变更写「回滚步骤」，等于在事故现场发现预案是假的。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 可逆性判定 + 触发条件 + 可照做的步骤 + 数据方案 + 验证方法
- WARN = 有步骤缺 fallback
- FAIL = 不可逆却写「回滚」/ 触发条件不可观测 / 无验证方法
- UNKNOWN = 可逆性无法判定（不知道有哪些外部消费方）

**1. 可逆性判定**
| 问题 | 答案 |
|---|---|
| 有数据被覆盖？ | |
| 有数据被删除？ | |
| 外部已消费？ | |
| 用户已知晓？ | |
| 旧代码能读新数据？ | |

→ 结论：完全可逆 / 部分可逆 / 不可逆

**2. 触发条件**
| 档位 | 条件（可观测） | 谁决定 |
|---|---|---|

**3. 回滚步骤**
| # | 命令/操作 | 失败时怎么办 |
|---|---|---|

**4. 数据方案**
- 备份位置：<> 备份时间：<> 验证过可恢复：<>
- 回滚窗口：<> 预计丢失：<>

**5. 验证**
| 项 | 方法 | 期望 |
|---|---|---|

**6. 不可逆时的止损**（如适用）
- 上线前强制条件：<>
- 出事后的止损动作：<>

**7. 判不了的部分**
- <哪些外部消费方无法确认>

## 假阳性清单（这些不构成「预案完整」）

- 写了「回滚到上一版本」但没说怎么回
- 触发条件写「看情况」
- 只有成功路径没有 fallback
- 有备份但没验证过
- 不可逆变更写了「回滚步骤」

## 假阴性清单（最常漏的 8 类）

1. **以为「代码能回滚」= 「变更能回滚」**（数据已是新格式）
2. **没有「立即回滚」档**（出事时都在等拍板）
3. **触发条件不可观测**（「看情况」）
4. **步骤缺 fallback**（第 1 步失败就卡住）
5. **回滚时顺手查原因**（拖慢止血）
6. **有备份但没验证可恢复**
7. **没算回滚窗口内会丢多少数据**
8. **不可逆变更写「回滚」而非「止损」**

## 本仓库可用的命令

```bash
node tools/skills/verify-release-rollback.mjs   # 回滚必须真的把内容恢复回来（10/10，含 3 反例）
node tools/memory/verify-bulk-corrupt.mjs       # 损坏库必须拒绝而非静默覆盖
node tools/quality/commit-gate.mjs              # 回滚后跑门禁
```

## 与其他技能的关系

- `release-pipeline`：发布流水线里必须有回滚预案
- `data-migration`：数据迁移的回滚方案（本技能是变更级）
- `postmortem`：回滚后复盘为什么需要回滚
- `release-gate`：发布前检查预案是否齐备
- `ci-pipeline`：回滚脚本应在 CI 里被测试过

## 边界（如实说清）

- 预案**不能覆盖未预见的失败模式**（没想到的事故按预案处理不了）
- 回滚速度受限于部署方式；手工部署的回滚必然慢
- 外部消费方不可枚举时，可逆性判定只能是 UNKNOWN
- 数据回滚的完整性取决于备份；备份之后的写入必丢
- 本技能不判断「该不该上线」——那是 `release-gate`
