# 数据迁移 技能

> 数据迁移是**唯一不可撤销的操作类型**（除非你有可用的备份）。
> 代码写错了可以重写，数据覆盖错了就没了。
> 所以本技能的核心不是「怎么迁移」，而是**「怎么保证迁移错了还能退回来」**。

## 什么时候用

- 改表结构、加字段、拆表
- 搬数据（换存储位置/换格式）
- 批量订正字段值（修脏数据）
- 重建派生数据

## 什么时候**不**用

- 还没定新结构 → 先 `schema-design`
- 只是改代码不改存量数据 → 普通改动
- 要核对两份数据是否一致 → `data-reconcile`

## 第 0 步：先确认「这真的是迁移吗」

在动手前回答三个问题：

| 问题 | 答不上来意味着 |
|---|---|
| 迁移的**范围**是什么？（哪些数据、多少条） | 你可能不知道自己在改什么 |
| 迁移后**旧代码还能跑吗**？ | 不能 → 需要双写期或同步改代码 |
| 最坏情况**丢什么**？ | 说不出 → 你没评估风险 |

⛔ 最常见的灾难：把「文件存在但解析失败（损坏）」当成「新库」，
然后用空库覆盖 —— **静默丢数据**。本仓库踩过（`tools/memory/bulk.mjs`）。

## 第 1 步：备份（且必须验证备份真的可用）

### 1.1 备份三要素

| 要素 | 要求 |
|---|---|
| **完整性** | 备份必须包含全部相关数据（不能只备一部分） |
| **可读性** | 备份必须能被解析回来（不是损坏的副本） |
| **可定位** | 备份路径/时间要记录，回滚时能找到 |

### 1.2 验证备份可用（这一步最常被跳过）

备份完必须做三件事：

1. **能读**：把备份文件解析一遍（`JSON.parse` / 打开 / 校验和）
2. **条数对**：备份里的记录数 == 原数据的记录数
3. **抽样对**：随机抽 3~5 条，逐字段与原数据比对

⛔ 「我复制了文件」不等于「我有可用备份」。复制过程可能截断、编码可能变、权限可能丢。

本仓库实例：`verify-bulk-corrupt.mjs` 5/5 验证了
「损坏库 → exit 2 且不覆盖」、「BOM 输入可读」、「正常路径可用」、「恢复原大小 642905B」。

### 1.3 备份放哪里

- **不要**放在会被迁移脚本扫到的目录里（否则会被当成待迁移数据）
- **不要**只放在同一块磁盘（磁盘故障时一起丢）
- 文件名带时间戳（多次迁移不互相覆盖）

## 第 2 步：dry-run（必须与真实执行走同一段代码）

### 2.1 为什么必须同一段代码

如果 dry-run 是「另写一段逻辑来估算」，那它证明的是「估算逻辑对不对」，
不是「迁移逻辑对不对」。两者不一致时，dry-run 全绿而真实执行出错 —— 这是**假安全**。

正确做法：迁移函数接受一个 `dryRun` 标志，除了「最后写盘」那一步，其余全部照跑。

### 2.2 dry-run 必须输出什么

| 输出 | 用途 |
|---|---|
| 会改多少条 | 与预期对比 |
| 每条改什么（前 N 条样本） | 人工核对是否符合预期 |
| 哪些条会被跳过、为什么 | 发现意外的跳过 |
| 哪些条会失败、为什么 | 提前发现脏数据 |

⛔ 只输出「共 X 条」不够 —— 必须能看**具体改了什么**，否则无法核对。

### 2.3 dry-run 的核对清单

- [ ] 变更条数 == 预期条数？
- [ ] 样本的「改前 → 改后」符合业务预期？
- [ ] 跳过的条目原因合理？（不该有大量「解析失败」）
- [ ] 失败的条目是什么？（脏数据要提前处理）
- [ ] 有没有意外的连带修改？（不该动的字段被动了）

## 第 3 步：小批试跑（先 10 条，验证真实效果）

### 3.1 为什么还要小批

dry-run 不写盘，所以它验证不了：

- 写盘是否真的成功（权限、磁盘满、编码）
- 写入后的数据能否被读回（序列化往返是否丢字段）
- 下游是否真的能消费新格式

小批试跑能验证这三件事。

### 3.2 小批之后必须「读回来验」

写完不是结束，要重新读一遍：

1. 读回条数 == 写入条数？
2. 读回的字段值 == 期望值？
3. 用**下游真实的读取代码**读一次（不是自己写的校验脚本）

⛔ 只用自己写的校验脚本读，可能掩盖「下游读不了」的问题。

### 3.3 小批出问题怎么办

立刻回滚，**不要「修一下再试」**：

- 回滚到备份
- 分析原因（是脚本错还是数据脏）
- 修脚本 → 重新 dry-run → 重新小批

⛔ 在小批失败后继续全量，是最危险的操作。

## 第 4 步：全量执行（带计数校验）

### 4.1 执行前最后确认

- [ ] 备份已验证可用
- [ ] dry-run 已核对
- [ ] 小批已通过且读回验证过
- [ ] 回滚脚本已就绪（且**测试过**）
- [ ] 执行期间没有其他写入（或已处理并发）

### 4.2 执行中记录

边跑边记录：已处理条数、成功数、失败数、失败原因分布。

失败要**分类**，不能只报「失败 3 条」：

- 数据本身脏（缺字段/类型错）→ 可跳过并记录
- 脚本逻辑错 → 必须停
- 环境问题（磁盘满/权限）→ 必须停

### 4.3 执行后计数校验（核心判据）

| 检查 | 期望 |
|---|---|
| 处理总数 | == 备份中的总条数 |
| 成功数 + 跳过数 + 失败数 | == 处理总数（不能丢） |
| 实际变更数 | == dry-run 预告的变更数 |
| 抽样比对 | 随机抽 5 条，逐字段与预期一致 |

⛔ **「实际变更数」与「dry-run 预告数」不一致 = 迁移有问题**，必须查明再继续。

### 4.4 幂等性（重跑不重复改）

迁移脚本必须能安全重跑：

- 用「目标状态判断」而不是「操作计数」（已迁移的跳过）
- 或用版本标记（`schemaVersion`）判断
- 重跑后结果必须与首次一致

为什么重要：全量执行中途失败，必须能重跑；不幂等的脚本重跑会产生重复数据或二次变换。

## 第 5 步：回滚脚本（必须写，且必须测过）

### 5.1 回滚脚本要做什么

| 场景 | 回滚方式 |
|---|---|
| 全量覆盖 | 从备份恢复 |
| 增量修改 | 反向操作（把改后的值改回去）—— 但要求记录了「改前值」 |
| 结构变更 | 反向 DDL + 数据回填 |

### 5.2 回滚必须测试过

⛔ 没测过的回滚脚本等于没有回滚。测试方式：

1. 在**备份副本**上跑一遍迁移
2. 跑回滚脚本
3. 验证结果与迁移前**逐字节/逐字段一致**

本仓库实例：`verify-release-rollback.mjs` 10/10 —— 临时 git 仓库 v1→v2→回滚，
验证「v1 内容真的回来了」再恢复 v2；含 3 条反例。

### 5.3 回滚的边界

回滚**不能**恢复：

- 迁移期间新产生的数据（除非备份后停止写入）
- 已被外部系统消费的数据
- 人工在迁移后做的修改

所以回滚窗口要明确：**备份时刻 → 回滚时刻之间产生的数据会丢**。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 备份已验证 + dry-run 核对 + 小批通过 + 计数吻合 + 回滚已测
- WARN = 迁移成功但有不一致项（列出）
- FAIL = 计数不符 / 有静默丢数据 / 回滚不可用
- UNKNOWN = 无法验证备份或无法计数

**1. 范围与风险**
- 迁移什么：<>
- 多少条：<>
- 最坏情况丢什么：<>
- 旧代码是否兼容：<>

**2. 备份**
- 位置：<路径 + 时间戳>
- 验证：能读 <是/否> · 条数 <N vs M> · 抽样 <3~5 条结果>

**3. dry-run**
- 是否同一段代码：<是/否>
- 预告变更数：<>
- 样本（改前→改后）：<>
- 跳过/失败：<分类与原因>

**4. 小批**
- 试跑条数：<>
- 读回验证：<条数 + 字段比对结果>

**5. 全量**
- 处理总数 / 成功 / 跳过 / 失败：<数字>
- 实际变更数 vs dry-run 预告：<是否一致>
- 抽样比对：<结果>
- 幂等性：<重跑验证结果>

**6. 回滚**
- 脚本位置：<>
- 是否测试过：<是/否，测试方式>
- 回滚窗口与数据损失：<>

**7. 判不了的部分**
- <缺什么>

## 假阳性清单（这些不是迁移问题）

- 跳过了「本来就不需要迁移」的记录（如已经是新格式的）
- 变更条数少于总数（只迁移需要改的）
- 执行耗时较长（数据量大，正常）
- 日志里出现「跳过」但原因是合理过滤

## 假阴性清单（最常漏的 8 类）

1. **没备份就迁移**
2. **备份了但没验证可用**（复制截断/编码变/权限丢）
3. **dry-run 与真实执行不是同一段代码**（假安全）
4. **dry-run 只输出总数，看不出改了什么**
5. **小批之后没读回来验证**（写盘成功但读不回来）
6. **全量后没做计数校验**（丢了几条不知道）
7. **回滚脚本没测试过**
8. **脚本不幂等**（重跑产生重复或二次变换）

## 本仓库可用的命令

```bash
node tools/memory/verify-bulk-corrupt.mjs      # 损坏库必须拒绝而非静默覆盖（数据安全底线，5/5）
node tools/skills/verify-release-rollback.mjs  # 回滚必须真的把内容恢复回来（10/10，含 3 反例）
node tools/quality/audit-doc-numbers.mjs       # 迁移后文档里的数字要同步
```

## 与其他技能的关系

- `schema-design`：先定结构再迁移
- `data-reconcile`：迁移后核对两份数据是否一致
- `test-writing`：迁移逻辑要补测试（尤其幂等性与边界）
- `release-gate`：迁移属于发布动作，走发布门禁
- `code-review`：迁移脚本要按五层审（重点「删除与副作用」层）

## 边界（如实说清）

- 备份只能恢复到**备份时刻**；备份后的写入会丢
- 回滚不能恢复外部系统已消费的数据
- 无法验证备份可用时（如备份在异地拿不到），结论只能是 UNKNOWN
- 迁移的正确性依赖对现有数据质量的了解；脏数据会让 dry-run 的预告数不准
- 大规模迁移（亿级）需要分批与限流，本技能只给原则不给具体参数
- 本技能不覆盖跨数据库引擎的迁移（那涉及类型映射等额外问题）
