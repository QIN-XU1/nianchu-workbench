# 幂等设计 技能

> 幂等不是「加个 unique 约束」就完事。
> 真正难的是：**请求超时了（不知道成没成）、消息重复投递（至少一次语义）、
> 用户连点两下、并发同键同时到**——这四种都要不出错。
> 判据：**同一个请求发 N 次，效果等于发 1 次吗？** 不等于就有重复风险。

## 什么时候用

- 涉及钱/库存/下单/发送等有副作用的写操作
- 有重试机制
- 有消息队列（至少一次投递）
- 用户可能连点

## 什么时候**不**用

- 纯读操作（天然幂等）
- 纯覆盖写（`SET x = 5` 天然幂等，但 `SET x = x+1` 不是）

## 第 1 步：先判断「这个操作需要幂等吗」

| 操作 | 天然幂等？ | 需要额外设计？ |
|---|---|---|
| `SET balance = 100` | 是 | 否 |
| `balance = balance + 100` | 否 | **是** |
| `INSERT`（无唯一键） | 否 | **是** |
| `INSERT`（有唯一键） | 靠唯一键 | 是（要处理冲突） |
| `DELETE by id` | 是（第二次删空） | 否 |

## 第 2 步：幂等键（最重要的一步）

### 2.1 幂等键从哪来

| 来源 | 说明 | 好坏 |
|---|---|---|
| **客户端生成** | 客户端在发起前生成 UUID | ✅ 最好（能覆盖重试） |
| **业务唯一键** | 订单号、请求 ID | ✅ 好 |
| **请求内容哈希** | 对 body 做 hash | ⚠ 内容变了就不同 |
| **时间戳** | | ❌ 重试时变了，失效 |

⛔ 用时间戳当幂等键 = 重试就变新键 = 幂等失效。

### 2.2 幂等键的作用域

同一幂等键在**多长窗口内**有效？

| 窗口 | 问题 |
|---|---|
| 太短 | 用户 5 分钟后重试就重复了 |
| 太长 | 存储爆、真实的新请求被误判重复 |
| 常见 | 24 小时 / 7 天（按业务） |

## 第 3 步：去重存储（四种实现）

| 方式 | 优点 | 缺点 |
|---|---|---|
| **唯一索引** | 简单可靠 | 冲突时要处理 |
| **Redis SETNX** | 快 | 要设过期、宕机丢 |
| **状态机** | 能表达「处理中/完成」 | 复杂 |
| **事务表** | 强一致 | 稍慢 |

### 3.1 三态记录（推荐）

幂等键要记录**三种状态**，不能只记「处理过」：

| 状态 | 含义 | 重复请求时 |
|---|---|---|
| **处理中** | 已收到，未完成 | 返回「处理中」或等待 |
| **成功** | 已完成 | 返回缓存的成功结果 |
| **失败** | 已失败 | 可重试 或 返回失败 |

⛔ 只记「处理过」不区分成功失败 → 失败后重试被判重复，永远好不了。

## 第 4 步：并发与部分成功

### 4.1 同键并发

两个同幂等键的请求**同时**到：

| 处理 | 结果 |
|---|---|
| 先查后写（有竞态） | 两个都通过，重复 |
| 唯一约束兜底 | 一个成功一个冲突 → 正确 |

判据：**必须有数据库层的唯一约束兜底**，不能只靠应用层「先查」。

### 4.2 部分成功

一个跨多步的操作（扣款→扣库存→发通知）中途失败：

| 策略 | 适用 |
|---|---|
| **本地事务** | 单库 |
| **Saga/补偿** | 跨服务 |
| **状态机 + 重试** | 异步 |

⛔ 「扣了款没扣库存」是幂等要一起解决的问题——不然重试会重复扣款。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 有幂等键 + 三态记录 + 唯一约束兜底 + 部分成功有补偿
- WARN = 有幂等键但无唯一约束兜底
- FAIL = 用时间戳当键 / 只记「处理过」/ 无并发兜底
- UNKNOWN = 拿不到写操作的实现

## 假阳性清单（这些不算「幂等」）

- 有 unique 约束但冲突时直接报错（没返回成功结果）
- 只记「处理过」不分状态
- 用时间戳当键
- 只靠应用层先查（无并发兜底）

## 假阴性清单（最常漏的 8 类）

1. **时间戳当幂等键**
2. **只记「处理过」**（失败后重试被判重复）
3. **无数据库唯一约束兜底**（并发重复）
4. **跨服务部分成功无补偿**（重复扣款）
5. **幂等窗口太短**（用户稍后重试重复）
6. **消息队列重复投递未去重**
7. **缓存去重宕机丢**（无持久化）
8. **重试时改了请求内容**（键该基于客户端生成）

- `data-migration`：迁移中的重复执行
- `ci-pipeline`：测试要覆盖重复请求

## 边界（如实说清）

- 分布式强一致幂等有成本；最终一致需业务接受短暂重复
- 幂等键的生成方必须是「发起方」，服务端无法凭空造
- 本技能不实现，只设计「键/存储/兜底/补偿」
