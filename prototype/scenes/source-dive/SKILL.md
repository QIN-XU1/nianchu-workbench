# 源码拆解 技能

> 拆解的目的不是「读一遍代码」，而是**回答一个具体问题，并留下可复算的证据**。
> 判断标准：**结论能不能被别人按你给的路径打开文件、看到同一件事。**
> 做不到这一点的「拆解」，只是读后感。

## 什么时候用

- 要搞清楚某个项目「某个能力怎么实现的」
- 要判断「它有没有 X」（对标/竞品分析）
- 接手一个陌生仓库
- 要借鉴别人的做法

## 什么时候**不**用

- 只要跑起来用它 → 读 README 即可
- 要审自己写的代码 → `code-review`
- 要对比多个项目 → `capability-benchmark`（或本技能逐家做，再汇总）

## 第 0 步：先定问题（没有问题的拆解会漫无目的）

### 0.1 问题要具体到「可判定」

| 差 | 好 |
|---|---|
| 「看看它的架构」 | 「它的工具调用是怎么注册和调度的？」 |
| 「它有什么功能」 | 「它支持技能热加载吗？如果支持，在哪一行？」 |
| 「它做得好不好」 | 「它的路径校验做了几层？能挡住 `..` 吗？」 |

判据：**这个问题的答案，能不能用「有/没有 + 路径:行号」回答？** 不能 → 问题太宽。

### 0.2 一次只回答一个问题

拆解时容易发散（看到什么都想记）。**每轮只回答一个问题**，其余记到「待查」。

⛔ 想一次搞清整个项目，结果往往是什么都只懂个大概。

## 第 1 步：定位（先找入口，别从头读）

### 1.1 三种入口

| 入口 | 怎么找 | 适合 |
|---|---|---|
| **名字** | 按关键词 grep 文件名/目录名 | 知道能力叫什么 |
| **调用链** | 从入口（main/路由/命令）往下追 | 知道从哪触发 |
| **数据结构** | 找核心类型/表定义 | 想知道「它怎么表示」 |

### 1.2 搜索的策略

- **先宽后窄**：先 `grep -l`（只列文件），再进具体文件
- **多个关键词**：同一能力常有多种叫法（`skill` / `capability` / `plugin`）
- **注意排除**：`node_modules`、测试、示例、文档

### 1.3 命名陷阱（本技能最重要的一节）

**「名字像」不等于「真的实现了」**。必须验证。

| 陷阱 | 例子 | 怎么验 |
|---|---|---|
| **同名不同义** | `compression` 指 zlib 压缩，不是上下文压缩 | 看它压缩的是什么数据 |
| **测试/示例冒充实现** | 17 个 `SKILL.md` 有 16 个在 `test/example` 里 | 看路径是否在 test/example 下 |
| **只声明未使用** | 定义了接口但没有任何调用点 | grep 调用点 |
| **空实现** | 函数体是 `return []` / `throw not implemented` | 读函数体 |
| **配置项存在但被忽略** | 配置里能写，但代码从不读它 | grep 配置键名 |

本仓库踩过的实例：`pi` 项目里 `zlib` 被误判为「无压缩能力」——
因为只查了单文件，而那是多 package 仓库。**多包仓库不能凭单文件否证一个能力。**

## 第 2 步：验证（三层证据，缺一层就不能下结论）

### 2.1 三层证据

| 层 | 证据 | 强度 |
|---|---|---|
| **声明** | 类型定义/接口/文档写了 | 最弱（可能没实现） |
| **实现** | 函数体真的做了这件事 | 中（可能没被调用） |
| **调用** | 有人真的调它（且在生产路径上） | 强 |

**判据：「有」需要三层齐全；只有声明 = 「无」或「部分」。**

### 2.2 验证「真的实现了」

1. 找到实现文件（`路径:行号`）
2. 读函数体，确认不是空实现/桩
3. 找调用点（`grep 函数名`），确认有人用
4. 确认调用点在**生产路径**上（不是只在测试里）

### 2.3 验证「真的没有」

⛔ 「我没找到」≠「没有」。必须：

1. 列出**查过哪些关键词/路径**（可复算）
2. 说明**为什么这些关键词足够覆盖**（同义词考虑了吗）
3. 检查**是否是多包仓库**（单包结论不能推广）
4. 明确标注「在 X 范围内未找到」（限定范围，不宣称全局无）

本仓库的纪律：**拿不到证据标 UNKNOWN，不因为「我没看到」就说「没有」。**

## 第 3 步：理解实现（读懂设计意图，不只是读代码）

### 3.1 四个要问的问题

| 问题 | 为什么问 |
|---|---|
| **它解决什么问题？** | 不理解问题，就无法判断实现是否合理 |
| **它的约束是什么？** | 约束决定了实现方式（为什么不用更简单的做法） |
| **它的失败模式是什么？** | 出错时怎样？这最能反映设计成熟度 |
| **它放弃了什么？** | 任何设计都有取舍，看不到取舍说明没读懂 |

### 3.2 找「反直觉的地方」

最值得记的是「看起来该这样、其实是那样」：

- 为什么用轮询而不是事件？
- 为什么这里要加一层间接？
- 为什么这个函数要重复校验两次？

⛔ 看到反直觉的地方就跳过，等于放弃了拆解最大的收获。

### 3.3 找「它踩过的坑」

代码里的注释、特殊处理、防御性检查，往往记录了作者踩过的坑：

- `// 注意：这里不能直接 XXX，否则 YYY`
- 特殊 case 的 if 分支
- 看似多余的校验

这些是**别人用代价换来的知识**，最值得抄。

## 第 4 步：写结论（每条都要能复算）

### 4.1 结论的格式

　　`【判定】有 / 部分 / 无 / 判不了`
　　`【证据】路径:行号（可复算）`
　　`【说明】它怎么做的 / 为什么没做`
　　`【反例】什么情况下这个判定会翻`

### 4.2 「部分」怎么写

「部分」是最常见的判定，必须写清**哪部分有、哪部分没有**：

　　`【判定】部分`
　　`【有】发现 + 校验 + 懒加载（loader.mjs:57-112）`
　　`【无】安装、卸载、市场检索（grep install/uninstall 无实现）`
　　`【说明】机制齐但生态未闭环`

### 4.3 反例（必须有）

每条结论都要写「什么情况下会翻」：

- 「有」→ 如果它只在测试里被调用，就降级为「部分」
- 「无」→ 如果在多包仓库的其他包里存在，就改为「有」

## 第 5 步：留下「待查」（不要假装查完了）

拆解时总会遇到「暂时不清楚」的地方。**记下来，不要猜**。

| 待查项 | 为什么重要 |
|---|---|
| 某个函数没看懂 | 可能是关键设计 |
| 某个路径没追完 | 可能有隐藏实现 |
| 某个依赖没查 | 能力可能在依赖里 |

⛔ 把「没看懂」写成「它没有」，是最严重的拆解错误。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 问题明确 + 三层证据齐 + 有反例
- WARN = 有「待查」未清（列出）
- FAIL = 只有声明就判「有」 / 「我没找到」就判「无」
- UNKNOWN = 关键代码不可得

```markdown
# 拆解：<项目> 的 <能力>

## 1. 问题
<可判定的一句话>

## 2. 结论
【判定】有 / 部分 / 无 / 判不了
【证据】<路径:行号>
【说明】<>
【反例】<什么情况下会翻>

## 3. 证据链
| 层 | 证据 | 路径:行号 |
|---|---|---|
| 声明 | | |
| 实现 | | |
| 调用 | | |

## 4. 设计意图
- 解决什么问题：
- 约束：
- 失败模式：
- 放弃了什么：
- 反直觉的地方：
- 它踩过的坑（代码里的注释/特殊处理）：

## 5. 查过的范围（「无」判定必须写）
- 关键词：<>
- 路径：<>
- 是否多包仓库：<>
- 未覆盖的范围：<>

## 6. 待查
- <没搞清的地方>
```

## 假阳性清单（这些不构成「有」）

- 只有类型定义/接口声明
- 只有测试用例
- 只有示例/文档
- 函数体是空实现或 `throw not implemented`
- 配置项能写但代码从不读
- 名字像但做的是别的事

## 假阴性清单（最常漏的 8 类）

1. **名字像就判「有」**（没验证实现）
2. **「我没找到」就判「无」**（没写查过什么）
3. **单包结论推广到多包仓库**
4. **把测试/示例当成实现**
5. **只读声明层就下结论**
6. **没检查调用点是否在生产路径**
7. **遇到看不懂的就说「它没有」**（应该记待查）
8. **没有反例**（结论不可反驳）

## 本仓库可用的命令

```bash
node tools/evolve/audit-evidence-provenance.mjs   # 检查证据能否复算到对方源码
node tools/benchmark/absence-check.mjs            # 「缺席核验」（证明真的没有）
node tools/evolve/verify-evidence-completeness.mjs # 证据完整性
```

## 与其他技能的关系

- `capability-benchmark`：拆解多家后做汇总对比
- `evidence-audit`：检查自己的证据是否可复算
- `tech-selection`：拆解结论用于选型
- `code-review`：拆自己代码时的五层审
- `reverse-eng`：拆二进制/打包产物（本技能拆源码）

## 边界（如实说清）

- 无法判断「实现质量」——只判断「有没有、怎么做的」
- 无法知道「作者为什么这样设计」——只能从约束推断
- 闭源/混淆代码无法拆解，结论只能是 UNKNOWN
- 「没找到」永远不等于「没有」；只能限定范围地说
- 大规模仓库（万级文件）无法穷尽，必须接受抽样误差
