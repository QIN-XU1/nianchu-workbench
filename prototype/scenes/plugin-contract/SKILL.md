# 插件契约 技能

> 插件化的诱惑是「什么都能插」。但内核若认识具体插件、或接受任意贡献点，插件就成了特权后门。
> 判据：**内核认识任何具体插件吗？未知贡献点会被拒绝吗？**

## 什么时候用

- 要给系统做插件化扩展
- 要评审「插件内核/无特权核心」这类声明
- 插件越加越多，开始互相干扰

## 什么时候**不**用

- 单体、无扩展需求的系统

## 第 1 步：内核只做三件事，不认识具体插件

内核的职责严格限定：

1. **发现**清单
2. **校验**契约
3. **派发**贡献点

内核代码里**不出现任何具体插件的名字**。加了新插件，内核一行不改。

## 第 2 步：声明式清单 + 纯函数贡献点

插件用 `plugin.json` 声明（id / version / contributes），贡献点是纯函数。插件不直接操作内核状态。

## 第 3 步：贡献点白名单，未知的拒绝装载（不静默忽略）

贡献点只允许白名单内的（如 commands / panels / verifiers）。**出现未知贡献点 → 拒绝装载并报错**，不要静默跳过——静默忽略会让插件「以为注册了其实没生效」。

## 反例（写下来防复发）

- ✗ 内核里有 `if (pluginId === 'xxx')` → 内核有特权，不是无特权
- ✗ 未知贡献点静默忽略 → 插件以为生效了
- ✗ 插件能直接改内核状态 → 隔离失效
- ✗ 清单缺失也能加载 → 契约形同虚设

## 自检清单

- [ ] 内核代码不含任何具体插件名
- [ ] 插件用声明式清单接入
- [ ] 贡献点在白名单内才装载
- [ ] 未知贡献点 → 拒绝并报错

## 参考实现指路

本仓库 `tools/plugin/kernel.mjs`：内核只做发现/校验/派发、不认识任何具体插件；插件以 plugin.json（id/version/contributes）+ 纯函数贡献点接入；贡献点白名单 commands/panels/verifiers，未知贡献点拒绝装载。`POST /api/plugin-run` 可实跑（probe-reader/probe-audit 两个内置插件）。

## 实测数据（本仓库，可复算）

```
# 经宿主接口实跑两个内置插件
POST /api/plugin-run  {pluginId: "probe-reader"}   # 读取类贡献点
POST /api/plugin-run  {pluginId: "probe-audit"}    # 审计类贡献点
```

实测两个插件都能被内核发现、校验、派发并返回结果。

- 内核只做三件事：发现清单 / 校验契约 / 派发贡献点
- 插件以 `plugin.json`（id / version / contributes）+ **纯函数**贡献点接入
- 贡献点白名单：commands / panels / verifiers；**未知贡献点拒绝装载**
- 内核代码里**不出现任何具体插件的名字**（加了插件内核一行不改）

**教训**：**「无特权内核」的判据是「内核里没有 if (pluginId === 'xxx')」**。
只要你还在内核里点名某个插件，它就有特权，插件化就是假的。
