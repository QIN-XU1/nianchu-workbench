# 数据分片 技能

> 分片的成败 90% 取决于**分片键选得对不对**。
> 选错分片键，后面所有问题（热点、跨片查询、再平衡）都无解。
> 判据：**用这个分片键，是否既有均匀分布，又让常见查询落在单片？**

## 什么时候用

- 单表/单库数据量或写入超限
- 要做水平扩展
- 有热点（某一行/某用户被打爆）

## 什么时候**不**用

- 数据量还能靠索引/归档解决
- 能垂直拆分（按业务分库）先做

## 第 1 步：选分片键（最关键的决策）

| 分片键 | 均匀性 | 常用查询落单片 | 陷阱 |
|---|---|---|---|
| **用户 ID** | 好 | 用户维度查询好 | 全局查询要扫全片 |
| **时间** | 差（新数据集中） | 时间范围查询好 | **热点全在最新片** |
| **哈希（任意 ID）** | 最好 | 随机查好，范围查差 | 范围查询要扫全片 |
| **业务实体（订单号）** | 中 | 该实体查询好 | 跨实体关联难 |

⛔ 用时间当分片键 = 所有写入都压最新片 = 热点。要用时间的话得「时间 + 哈希」组合。

## 第 2 步：热点问题（分片后仍可能有）

| 热点类型 | 例子 | 解法 |
|---|---|---|
| **分片级热点** | 大客户独占一片 | 大客户单独拆 |
| **行级热点** | 秒杀同一商品 | 拆库存为多行/计数分桶 |
| **时间热点** | 最新数据 | 组合键 |

⛔ 均匀的分片键不等于没热点：某个 key 本身访问极高（如爆款商品）就是热点。

## 第 3 步：跨分片查询（分片的代价）

| 查询类型 | 分片后 |
|---|---|
| 按分片键查 | ✅ 落单片 |
| 非分片键查 | ❌ 扫全片（广播） |
| 跨片 JOIN | ❌ 要应用层拼 |
| 全局聚合 | ❌ 各片算再合并 |
| 全局唯一 ID | 需雪花/号段 |

解决：
- **二级索引表**（把非分片键映射到分片）
- **宽表/冗余**（常用查询字段冗余）
- **搜索索引**（复杂查询走 ES）
- **异步聚合**

## 第 4 步：再平衡（加机器怎么迁）

| 方式 | 说明 |
|---|---|
| **固定分片 + 映射** | 先分 N 片（如 1024），机器是分片的宿主，扩容搬分片（推荐） |
| 一致性哈希 | 节点增减影响小但要虚拟节点 |
| 取模 | ❌ 加机器几乎全量重分布 |

⛔ 用 `hash(key) % 机器数` = 加一台机器所有数据都要迁。**要用「固定片数 + 映射」**。

## 第 5 步：迁移与双写

| 阶段 | 做法 |
|---|---|
| 1 影子写 | 新老双写，读还在老 |
| 2 校验 | 比对两边数据 |
| 3 切读 | 灰度切读新 |
| 4 停老写 | 稳定后停 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 分片键均匀且贴合查询 + 无热点 + 有再平衡方案 + 跨片查询有解
- WARN = 分片键可但跨片查询未解
- FAIL = 时间/取模当分片键 / 无热点方案 / 无迁移方案
- UNKNOWN = 拿不到数据模型与查询模式

## 假阳性清单（这些不算「分好片」）

- 按时间分片（热点）
- 取模扩容（全量迁）
- 没考虑跨片查询

## 假阴性清单（最常漏的 8 类）

1. **时间当分片键**（写入热点）
2. **取模扩容**（全量重分布）
3. **忽略行级热点**（爆款）
4. **跨片 JOIN 无解**
5. **全局唯一 ID 没方案**
6. **无迁移双写阶段**
7. **分片键与主查询不符**（全扫）
8. **聚合查询变慢没预案**

## 与其他技能的关系

- `schema-design`：分片前的表设计
- `data-migration`：分片迁移
- `load-balancing`：一致性哈希
- `sql-review`：分片后查询
- `caching-strategy`：热点缓解

## 边界（如实说清）

- 分片大幅增加复杂度，能不拆先不拆
- 跨片事务/查询几乎无法优雅解决
- 本技能不实现中间件，只设计分片策略
