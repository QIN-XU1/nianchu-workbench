# 代码审查 技能

审查的目标不是「找出所有问题」，而是**给出可被反驳的结论**：
每条结论都必须能指向 `路径:行号`，并附一个「这段代码在什么输入下会错」的具体反例。
做不到这两点的，就不是审查结论，是印象。

## 什么时候用

- 有 diff（`git diff`、PR、补丁）要审
- 提交前自查
- 合并前最后一道关

## 什么时候**不**用

- 只有需求没有代码 → 用 `refactor-plan` 或 `adr`
- 关心的是安全攻击面 → 用 `security-review` / `threat-model`（本技能只做通用正确性）
- 关心的是「能不能复现这个 bug」 → 用 `debug-repro`
- 关心的是「改动有没有被测试覆盖」为主 → 用 `test-writing`

## 第一步：先把「审什么」定下来（不许跳过）

```bash
git diff --stat                    # 改了哪些文件、各多少行
git diff                           # 未暂存的改动
git diff --cached                  # 已暂存的改动
git diff main...HEAD               # 整个分支相对主干的改动
```

定范围时立刻判一次四态：

| 情况 | 四态 | 动作 |
|---|---|---|
| 拿不到 diff（没仓库/没改动/读不到） | **UNKNOWN** | 停下来问清楚审哪个范围，**不要**凭印象审 |
| diff 超过 800 行或跨 10+ 文件 | **WARN** | 先要求拆成可独立审的几块；一次审太大的改动必然漏 |
| 改动里含生成产物（dist/、lock 文件、构建产物） | 说明 | 生成物单独跳过，只看源 |

⛔ 不许在没有 diff 的情况下说「我看了一下，没问题」——那是编造。

## 五层审查（按顺序，不要跳层）

### 第 1 层：范围与意图

- 这段改动**声称**做什么？（从 commit message / PR 描述 / 用户话里取）
- 实际改了哪些文件？**有没有改到声称范围之外的文件？**
- 有没有「顺手重构」夹在里面？（夹带重构会让审查看不出真正的行为变化）

反例尝试：`git diff --stat` 里出现了一个与声称功能无关的文件 → 要求拆出去或说明原因。

### 第 2 层：正确性（边界 / 错误分支 / 并发）

逐个问，每个都要落到具体行：

1. **空与缺失**：`null` / `undefined` / 空数组 / 空字符串 / 缺字段，分别会怎样？
2. **边界值**：0、1、-1、最大值、超长字符串、超大文件
3. **错误分支**：`catch` 里到底做了什么？是**处理**了，还是**吞掉**了？
   本仓库可用 `node tools/quality/scan-silent-catch.mjs` 扫空 catch（命令集中列在下方第 5 层）。
4. **并发/重入**：同一函数被并发调用会怎样？有没有「读-改-写」之间被别人插进来？
5. **资源**：文件句柄、定时器、监听器有没有在失败路径上也释放？

反例尝试的写法（必须具体）：
> 若 `items` 为空数组，`items[0].id` 在第 42 行抛 TypeError，调用方未捕获 → 接口 500。

⛔ 只写「注意空值」不算反例——要说清**哪一行、什么输入、什么后果**。

### 第 3 层：删除与副作用（最容易被跳过的一层）

- **看删除的行**：删掉的判断/校验/日志，是不是别人依赖的？
- **看改动的默认值**：把 `true` 改成 `false`、把阈值调大，会静默改变行为
- **看全局状态**：模块级变量、缓存、单例、环境变量是否被改写
- **看写盘/网络**：失败时会不会留下半成品文件？会不会重复发送？

反例尝试：
> 第 88 行删掉了 `if (!exists) return`，现在文件不存在时会继续走到第 95 行 `readFileSync` → ENOENT 冒到顶层。

⛔ 只看新增不看删除，是审查最常见的漏。

### 第 4 层：契约（对外行为有没有变）

- 返回结构：字段有没有被删/改名/改类型？（调用方会静默拿到 undefined）
- 错误表达：原来是 200 + 内层 `ok:false`，现在改成 4xx？调用方要同步改
- 日志级别：把 error 降成 warn，会让问题在监控里消失
- 命令行：退出码有没有变？（0/1/2/3 的语义变了就是破坏性改动）

反例尝试：
> `list()` 原来只返回 `{name, description}`，这次加了 `category` —— 若下游有 `Object.keys(x).length === 2` 之类的断言就会红。

### 第 5 层：可测性

- 新增逻辑有没有对应的断言？断言是不是**真的会红**（不是只数标签）？
- 有没有反例用例（故意喂错，确认它会报错）？
- 断言有没有写死数字/路径（下次改动就过期）？

本仓库可直接用的检查（一次跑完）：

```bash
node tools/quality/scan-silent-catch.mjs       # 空 catch 是否都有解释
node tools/quality/scan-mutation-residue.mjs   # 源码里有没有变异残留
node tools/agent/verify-a1-patch.mjs           # 补丁应用/回滚类验收（示例）
```

反例尝试：
> 新增了 `parsePort()` 但没有一条「非法端口」的用例 → 无法证明它会拒绝。

## 输出格式（必须长这样）

按这个顺序写，每段都必须有：

**第 1 行**：`四态: PASS | WARN | FAIL | UNKNOWN`

**阻断问题（FAIL 级，必须改）**
　　`路径/文件.mjs:42`　<问题>　反例：<输入> → <后果>

**小问题（WARN 级，建议改）**
　　`路径/文件.mjs:88`　<问题>

**无法判断（UNKNOWN 级，需要信息）**
　　<缺什么信息才能判>

**已尝试但未发现问题的反例**
　　<我试过哪些输入/场景，结果正常>

最后一行很重要：**写清你试过什么**。没有「已尝试反例」清单的审查，无法区分「查过没问题」和「没查」。

## 假阳性清单（不要把下面这些当缺陷）

- 风格差异（引号、缩进、命名习惯）——除非项目有强制规范
- 「我觉得可以用更优雅的写法」——除非能指出具体风险
- 测试文件里的魔法数字——测试里写死数字常常是对的（要的就是精确）
- 缺注释——注释缺失不是缺陷；**注释与代码矛盾**才是
- 依赖版本不是最新——除非有已知漏洞或明确要求

## 假阴性清单（最常漏的 8 类，逐条自查）

1. **删除的行**没看
2. **错误分支**没看（catch 里到底做了什么）
3. **默认值/阈值**被改动没发现
4. **并发**没考虑（尤其读-改-写）
5. **失败路径的资源释放**没看
6. **对外契约**（字段/退出码/状态码）变了没同步调用方
7. **断言写死数字**，下次改动必然过期
8. **「改对了但没测」**——行为正确但没有任何断言守着

## 与其他技能的关系

- `debug-repro`：审查中发现「说不清会不会出错」时，转去写复现
- `test-writing`：第 5 层发现问题时，转去补断言
- `security-review` / `threat-model`：涉及输入信任边界、权限、注入面时转过去
- `refactor-plan`：改动大到需要先拆时，转去做拆分计划
- `release-gate`：审查通过后，发布前还要跑发布门禁
- `evidence-audit`：审查结论里引用的证据（路径/行号/命令输出）需要复核时用它

## 边界（如实说清）

- 本技能**不执行**代码，只做静态阅读 + 少量命令；运行期行为要靠 `debug-repro` 或验收脚本
- 不覆盖性能与安全（各有专门技能）
- 「审完了」不等于「没问题」——只能说「在我尝试的这些反例下没发现问题」
- 审查者与被审代码作者是同一个模型时，**存在共同盲区**：同一种误解会同时出现在代码和审查里
- 拿不到 diff、拿不到运行环境时，结论只能是 **UNKNOWN**，不许降级成 PASS
