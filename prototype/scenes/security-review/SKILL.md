# 安全审查 技能

> 安全审查的价值不在「列出一堆理论风险」，而在**给出一个具体的攻击输入，并说明它会造成什么后果**。
> 说不出输入的攻击，等于没发现。
> 另一条同样重要：**本产品不做越界拦截闸**（用户明令）。审查输出的是「风险提示与修复建议」，
> 不是「加一道硬拦截」。混淆这两件事会让产品形态跑偏。

## 什么时候用

- 新增了处理**外部输入**的代码（HTTP/WS/CLI 参数/文件内容）
- 拼接了 **shell 命令 / SQL / 模板**
- 使用了**凭证**（token / 密钥 / 密码）
- 处理**用户提供的路径**
- 新增了**权限判断**或改了权限模型

## 什么时候**不**用

- 纯内部计算、无外部输入 → 风险极低
- 要看代码质量问题 → `code-review`
- 要做威胁建模（还没写代码）→ `threat-model`
- 要加运行时拦截 → **本产品不做**（见下方边界）

## 第 0 步：先划清「输入来源」

安全问题的根因几乎都是「**不可信输入被当成了可信**」。
所以第一步是列出所有输入来源，并标记可信度：

| 来源 | 可信度 | 说明 |
|---|---|---|
| 用户直接输入（表单/命令行） | **不可信** | 必须校验 |
| 网络请求（HTTP 头/体/查询串） | **不可信** | 可被伪造 |
| 文件内容 | **不可信** | 可能来自任何地方 |
| 第三方 API 响应 | **不可信** | 对方可能被攻破 |
| 环境变量 | **半可信** | 部署者可控 |
| 配置文件 | **半可信** | 需确认谁能改 |
| 代码内常量 | 可信 | — |

⛔ 最常见的漏洞：把「半可信」当「可信」用（比如把环境变量直接拼进 shell）。

## 第 1 步：查注入面（最高频）

### 1.1 命令注入

**危险模式**：把不可信输入拼进 shell 字符串。

| 危险写法 | 风险 | 安全写法 |
|---|---|---|
| `exec(\`git ${userInput}\`)` | 用户传 `; rm -rf /` 即执行 | 用 `execFile`/`spawn` 传数组参数 |
| `sh -c "cmd " + input` | 同上 | 避免 `sh -c`，直接调程序 |
| `execSync(\`ls ${dir}\`)` | 目录名含空格/分号即出问题 | `execFileSync('ls', [dir])` |

判据：**有没有把变量拼进命令字符串？** 有 → 找替代方式。

本仓库实例（正面）：`tools/hostapi/git-methods.mjs` 调外部命令用 `execFile('git', [...])` 传数组，
不经过 shell —— 即使参数含 `;`/`$()` 也不会被解释。

### 1.2 SQL 注入

| 危险写法 | 安全写法 |
|---|---|
| `db.query("SELECT * FROM t WHERE id=" + id)` | 参数化：`db.query("... WHERE id=?", [id])` |
| 拼接表名/列名 | 白名单校验（表名列名不能用参数占位） |

⛔ 「用了 ORM 就安全」是错觉 —— ORM 也有 `raw()` / `whereRaw()` 这类字符串接口。
**要看到实际是否参数化**，不能只看用了什么库。

### 1.3 模板注入

- 服务端模板把用户输入当模板代码执行（如 `eval` / `new Function` / 模板引擎的 `raw`）
- 判据：用户输入是否进入了「会被求值」的位置？

### 1.4 路径穿越（单独算一类，见第 3 步）

## 第 2 步：查凭证（最容易泄露且最难发现）

### 2.1 三个泄露点

| 泄露点 | 为什么会泄露 | 检查方式 |
|---|---|---|
| **日志** | 打印了整个请求体/配置对象 | 搜索日志里是否含 token/password/key |
| **argv** | 命令行参数会出现在进程列表里 | 凭证不许走命令行参数 |
| **异常信息** | 错误堆栈带出内部路径/配置 | 检查 `catch` 里是否把 err 整个返回给前端 |

本仓库实例（真实踩过）：`gateway_models` 用只读配置视图投影（`readOnly: true`）而非直接给 key —
**不是靠「记得别打印」，是靠结构上拿不到明文**。

### 2.2 凭证的四个「不许」

1. 不许**硬编码**在源码里（哪怕注释里）
2. 不许走**命令行参数**（`ps` 能看到）
3. 不许**进日志**（尤其是 debug 级别）
4. 不许**进错误响应**（给前端的错误信息要脱敏）

### 2.3 检查方法

　　`grep -rnE "(api[_-]?key|token|password|secret)\s*[:=]\s*['\"][^'\"]{16,}" --include=*.mjs .`（搜硬编码密钥）
　　`grep -rn "console\.log(.*config" --include=*.mjs .`（搜日志打印整个配置对象）

⛔ 这两条只覆盖「写死的」，覆盖不了「运行时的」—— 后者要读代码看数据流。

## 第 3 步：查路径穿越

### 3.1 危险模式

用户提供路径 → 直接 `fs.readFile(userPath)`。

攻击输入：`../../../../etc/passwd`

### 3.2 正确做法

1. **规范化**：`path.resolve(base, userPath)`
2. **前缀校验**：`resolved.startsWith(base + path.sep)`
3. **拒绝**：不满足就报错（不是静默回退）

⛔ 只用 `path.normalize` 不够 —— `..` 会被规范化但可能仍在 base 外。
必须做**解析后的前缀比较**。

本仓库实例（正面）：`tools/workbench/serve.mjs:321-337` 的 `/ui-plugins/` 路由做了三步校验 ——
`normalize(rel)` 归一化 → 去掉开头斜杠 → `if (safeRel.includes('..'))` 直接 400，
再用 `join(ROOT, 'ui-plugins', safeRel)` 拼出真实路径。`normalize` 之后再查 `..` 是关键：
只查原始字符串会被 `..%2F` 这类编码绕过。

### 3.3 检查清单

- [ ] 每个接收路径的入口都做了 resolve + 前缀校验？
- [ ] 校验的是「解析后的绝对路径」还是「原始字符串」？
- [ ] 符号链接是否被跟随？（`fs.realpath` 后再校验）
- [ ] Windows 下盘符/UNC/短文件名（`PROGRA~1`）是否覆盖？

## 第 4 步：查越权

### 4.1 三类越权

| 类型 | 含义 | 例子 |
|---|---|---|
| **水平越权** | 同角色访问别人的数据 | 改 URL 里的 `userId` 看别人订单 |
| **垂直越权** | 低权限执行高权限操作 | 普通用户调管理接口 |
| **上下文越权** | 跨工作区/跨会话访问 | 用 A 工作区的 token 读 B 工作区文件 |

### 4.2 检查方法

对每个「按 ID 取资源」的接口问：**这个 ID 是不是从会话/令牌里来的，而不是从请求参数里来的？**

- 安全：`const ws = session.workspaceId`（服务端绑定）
- 危险：`const ws = req.query.workspaceId`（客户端可控）

本仓库实例（正面）：`workspaces` 存根**没有切换方法**（17/17 验证）——
不能通过接口切工作区，只能通过环境变量在启动时指定。这是**结构性防越权**：
不是「检查了权限」，而是「根本没有这个入口」。

## 第 5 步：给出可复现的风险（不是泛泛而谈）

### 5.1 每条风险必须三段式

```
【触发输入】<具体输入，可直接复制>
【执行路径】<经过哪些代码，路径:行号>
【后果】<会发生什么，可观测>
```

举例（好）：
> **触发输入**：`GET /preview?path=../../../../etc/passwd`
> **执行路径**：`http-routes.mjs:120` → `resolveWorkspacePath`（未做前缀校验的旧版本）
> **后果**：返回 `/etc/passwd` 内容（系统用户列表泄露）

举例（差）：「可能存在路径穿越风险」← 没有输入、没有路径、没有后果。

### 5.2 无风险时也要交代

如果查完没发现风险，必须写：

> 已查：命令注入（无字符串拼接，全用 execFile 数组）、SQL（无 SQL 拼接）、
> 凭证（无硬编码，日志已脱敏）、路径（统一走 resolveWorkspacePath，已对抗测试）、
> 越权（无切换入口）。**未查**：依赖库自身的漏洞（需单独跑审计工具）。

⛔ 「没问题」不是结论；「查了哪几类、为什么安全、哪类没查」才是。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 五类都查过且无风险（附「已查/未查」清单）
- WARN = 有低危项或需确认项
- FAIL = 有可复现的高危风险（附三段式）
- UNKNOWN = 输入来源不明 / 拿不到关键代码 / 无法确认可信边界

## 假阳性清单（这些不是漏洞）

- 内部常量拼进命令（非用户输入）
- 测试代码里的假密钥（如 `sk-test-xxx`，但要确认不在生产配置里）
- 日志里打印了**脱敏后**的 token（前 4 位 + 后 4 位）
- 路径校验用了白名单（不是前缀比较但同样安全）
- 依赖有 CVE 但该代码路径未被调用
- `eval` 用在构建脚本里且输入可信

## 假阴性清单（最常漏的 8 类）

1. **只查了字符串拼接，漏了 `sh -c` / `execSync` 的字符串形式**
2. **以为用了 ORM 就安全**（`raw()` 仍是拼接）
3. **凭证进了 debug 日志**（生产不开 debug 就以为没事）
4. **路径只做了 normalize 没做前缀校验**
5. **符号链接跟随**（校验了路径字符串，但链接指向外面）
6. **越权：ID 从请求参数来**（而不是从会话来）
7. **错误响应泄露内部路径/配置**
8. **只看代码没看依赖**（第三方库的已知漏洞）

## 本仓库可用的命令

　　`node tools/quality/scan-silent-catch.mjs`（空 catch 会吞掉安全异常）
　　`node tools/agent/verify-a15-approval.mjs`（确认「不做越界拦截」这条边界仍成立）
　　`node tools/quality/audit-doc-numbers.mjs`（文档里的安全声明要与实测一致）

## 与其他技能的关系

- `threat-model`：还没写代码时先做威胁建模（本技能是事后审查）
- `code-review`：安全审查是代码审查的一个专项
- `api-contract`：权限模型变化属于契约变更
- `release-gate`：发布前必须过安全审查
- `evidence-audit`：怀疑「已修复」不实时复核

## 边界（如实说清）—— 本产品的重要约定

**⛔ 本产品不做越界拦截闸（用户明令）。**

这句话的含义：

- 本技能输出的是**风险提示与修复建议**，不是「加一道运行时拦截」
- 不做「审批闸」式的强制中断（那是 A15，被明确排除在目标外）
- 审查结果用于**改进代码**，不是用于**阻断用户操作**

为什么要写这么清楚：如果把「安全审查」理解成「加拦截」，产品会变成
「什么都要审批」的形态，与「用户自主」的产品定位冲突。

其他边界：

- 本技能**不能证明系统安全**，只能发现已知模式的问题；未知漏洞（0day/逻辑缺陷）发现不了
- 依赖库自身的漏洞需要独立工具（`npm audit` 等），本技能只做提示
- 「可信度」判断依赖对部署环境的了解；拿不到部署信息时结论只能是 UNKNOWN
- 逻辑越权（业务规则层面的）本技能覆盖有限，需要结合业务理解
- 审计日志/合规要求不在本技能范围
