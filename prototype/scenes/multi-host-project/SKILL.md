# 多宿主投影 技能

> 多宿主投影的本质不是「生成 5 个文件」，而是**「证明 5 个文件的内容来自同一个源」**。
> 如果每个宿主各自维护一份，那就不是投影，是**分叉** —— 分叉必然漂移，漂移必然不一致。
> 所以本技能的核心纪律：**canonical 是唯一权威源，宿主产物只许派生、不许手改。**

## 什么时候用

- 要让 Claude Code / Codex / Cursor / Gemini / OpenCode 等工具读到我们的技能
- 要验证「同一套内容投影多宿主」是否真的成立（B3 维度）
- 新增一个宿主格式
- 怀疑某个宿主的技能与 canonical 漂移了

## 什么时候**不**用

- 只维护 canonical（单个宿主）→ 不需要
- 宿主的**配置**（不是技能内容）→ 那是宿主自己的事，本技能只生成文本
- 要审技能内容本身 → `code-review` / `doctor`

## 第 0 步：先搞清「投影」与「导出」的区别

| | 投影（projection） | 导出（export） |
|---|---|---|
| **方向** | 单向：canonical → 宿主 | 单向：canonical → 文件 |
| **可重复** | ✅ 同样输入必得同样输出 | ✅ |
| **可手改** | ❌ 改了会被下次覆盖 | ✅ 导出物是一次性的 |
| **权威源** | canonical | canonical |

本技能做的是**投影**：宿主产物是「视图」，不是「副本」。
判据：**删掉所有宿主产物，重跑一次，能完全恢复吗？** 能 → 是投影。

## 第 1 步：canonical 就是唯一权威源

### 1.1 canonical 在哪

　　`prototype/scenes/changelog/SKILL.md`（每个技能一个目录，一个 `SKILL.md`）

每个技能一个目录，一个 `SKILL.md`。frontmatter（`name` / `category` / `description` / `depth`）是元数据。

### 1.2 canonical 的三条纪律

| 纪律 | 说明 |
|---|---|
| **只在这里改** | 宿主产物里改的内容会被覆盖 |
| **frontmatter 必须完整** | `name` 与目录名一致、`description` 非空 |
| **不引用宿主私有特性** | 否则投影不到别的宿主 |

⛔ 第三条最容易违反：如果 canonical 里写了「在 Claude 里用 `@file` 语法」，
投影到 Codex 就是错的。**canonical 必须与宿主无关。**

### 1.3 canonical 的体检

　　`node tools/skills/doctor.mjs`（30/30 通过）
　　`node tools/skills/verify-index.mjs`（索引完整）

## 第 2 步：跑投影（一次生成全部）

### 2.1 生成

　　`node tools/portable/project.mjs`

产物在 `.nianchu-hosts/`：

| 宿主 | 产物 | 格式 |
|---|---|---|
| Claude Code | `claude/CLAUDE.md` | Markdown |
| Codex | `codex/AGENTS.md` | Markdown |
| Cursor | `cursor/.cursorrules` | 纯文本规则 |
| Gemini | `gemini/GEMINI.md` | Markdown |
| OpenCode | `opencode/AGENTS.md` | Markdown |
| 通用清单 | `agents.json` | JSON（机器可读） |

### 2.2 为什么是这 6 个

前 5 个是主流宿主的**原生格式**（各家的约定文件名/路径不同）；
第 6 个 `agents.json` 是**机器可读的兜底**（给没有约定的宿主用）。

⛔ 不要为了「支持更多」而加宿主 —— 每个宿主都是一份需要维护的投影。
**加宿主的成本是长期的。**

## 第 3 步：5 条验收（含 2 条反例）

### 3.1 跑验收

　　`node tools/portable/verify-project.mjs`

### 3.2 五条验收逐条说明

| # | 验收项 | 为什么重要 | 失败含义 |
|---|---|---|---|
| 1 | **覆盖 6 个输出** | 少一个宿主就是没投影 | 某宿主生成器坏了 |
| 2 | **每个宿主技能 id 集合 == canonical** | 不能多也不能少 | 投影逻辑有过滤 bug |
| 3 | **二次生成字节一致** | 可重复性 | 生成器有随机/时间戳 |
| 4 | **canonical 空时报错**（反例 1） | 防空真通过 | 拿空集合同源当成功 |
| 5 | **篡改宿主产物后能检出**（反例 2） | 防手改漂移 | 校验没比对内容 |

### 3.3 反例为什么必须有

**反例 1（canonical 为空）**：
如果 canonical 是空的，那么「所有宿主 id 集合 == 空集合」是**真**的 ——
校验会通过，但什么都没投影。这是**空真通过（vacuous truth）**。

**反例 2（篡改宿主产物）**：
如果只校验「文件存在」，那手改了内容也会通过。必须校验**内容哈希**。

⛔ 本工具曾因反例 1 漏掉而假通过 —— 现已修复并加了反例。
**加了反例的校验才是真校验。**

### 3.4 验收不过怎么办

| 失败项 | 排查方向 |
|---|---|
| 覆盖不全 | 看 `project.mjs` 的宿主列表 |
| id 集合不等 | 看 canonical 里有没有 frontmatter 缺失的技能 |
| 二次生成不一致 | 看生成器有没有用 `Date.now()` / 随机数 |
| 反例 1 不过 | 空检查逻辑 |
| 反例 2 不过 | 内容哈希比对 |

## 第 4 步：B3 维度（这是本技能存在的理由）

### 4.1 B3 是什么

31 维对比里的 **B3 = 多宿主投影能力**。
参照项目大多只支持单一宿主（自己的格式），我们能做到「一套内容投影 5 个宿主」= 这一维领先。

### 4.2 B3 怎么证明领先

| 证据 | 怎么看 |
|---|---|
| 6 个产物文件存在 | `verify-project.mjs` 覆盖检查 |
| 每个宿主 id 集合 == canonical | 同上 |
| 二次生成字节一致 | 同上 |
| 反例能检出 | 同上 |

⛔ **「生成了文件」不等于「投影正确」** —— 必须 id 集合与字节一致都对上。

### 4.3 B3 的边界（不要夸大）

- 我们生成的是**技能内容**，不是宿主的全部能力
- 宿主可能需要额外配置才能真正加载（本技能不配置宿主）
- 「投影」不保证宿主**理解**内容（那是宿主模型的能力）

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 6 输出覆盖 + id 集合一致 + 二次一致 + 2 反例通过
- WARN = 有宿主产物存在但未验证理解
- FAIL = 覆盖不全 / id 不一致 / 二次不一致 / 反例不过
- UNKNOWN = 无法生成（canonical 缺失）

## 假阳性清单（这些不是「投影成功」）

- 文件存在但内容为空（空真通过）
- 只校验文件名没校验内容
- 二次生成「看起来一样」（要字节比对，不是肉眼）
- 宿主产物手改后没重新生成（漂移未被发现）
- 「支持 5 个宿主」但只测了 1 个

## 假阴性清单（最常漏的 8 类）

1. **canonical 为空时假通过**（空真）
2. **只校验文件存在不校验内容**
3. **二次生成不一致**（用了时间戳/随机）
4. **宿主产物手改后未检出**
5. **canonical 里写了宿主私有语法**（投影到别的宿主是错的）
6. **加了新宿主但没加验收**
7. **frontmatter 缺失导致 id 集合不等**
8. **「生成了」当成「投影正确」**

## 本仓库可用的命令

```bash
node tools/portable/project.mjs          # 生成 .nianchu-hosts/ 全部产物
node tools/portable/verify-project.mjs   # 5 条验收（含 2 条反例）
node tools/skills/doctor.mjs             # canonical 体检（30/30）
node tools/skills/verify-index.mjs       # 索引完整
```

## 与其他技能的关系

- `code-review`：canonical 内容本身要审
- `doctor`：canonical 的体量/结构检查
- `project-verdict`：B3 是 31 维之一，结果进对比矩阵
- `docs-index`：canonical 索引一致性
- `release-gate`：投影产物要进发布包

## 边界（如实说清）

- 本技能**只生成文本**，不改宿主配置、不执行任何东西
- 不保证宿主真的能加载（取决于宿主的加载约定，需要人工验证）
- 不保证宿主模型**理解**内容
- canonical 与宿主格式的语义差异无法完全消除（如 Cursor 的 `.cursorrules` 是纯文本，无 frontmatter）
- 宿主版本更新可能导致约定变化；本技能不跟踪宿主版本
- B3 的「领先」是相对参照项目的能力，不代表产品整体领先
