# 发版说明 技能

> 发版说明的读者**不关心你改了什么代码**，只关心一件事：
> **「我要不要升？升了会不会坏？坏了好不好退？」**
> 所以它的单位不是「改动」，是「用户能感知的变化」。
> 一条用户感知不到的内容，不管技术上多重要，都不该出现在这里。

## 什么时候用

- 要发布新版本，需要告诉用户更新了什么
- 需要向非技术读者解释一个技术变更
- 用户问「这次更新有什么」

## 什么时候**不**用

- 面向维护者/集成方的分类清单 → `changelog`
- 记录「为什么这么改」→ `adr`
- 写「怎么用新功能」→ `doc-write`
- 内部重构、无用户可见变化 → 不发说明（或只写一句「内部改进」）

## 第 0 步：先确定「读者是谁」

读者不同，同一件事的写法完全不同：

| 读者 | 关心 | 写法 |
|---|---|---|
| **终端用户** | 我的使用会不会受影响 | 「现在支持 X 了」「有个按钮位置变了」 |
| **集成方/开发者** | 我的代码会不会坏 | 「`parse()` 现在拒绝空串，需传 `{}`」 |
| **运维** | 部署会不会出问题 | 「需要新增一个环境变量」 |
| **内部团队** | 有哪些已知坑 | 「Y 场景下仍可能卡住，见 #123」 |

⛔ 一份说明混用四种语言，等于谁都没说清。**先选一个主读者**，其他读者关心的内容放「附注」。

## 第 1 步：把改动翻译成「用户影响」

### 1.1 翻译对照表

| 技术描述（错） | 用户影响（对） |
|---|---|
| 重构了 `ConfigLoader` | （不写，用户无感） |
| 把 `for` 改成 `map` | （不写） |
| 升级 `zod` 到 v4 | 配置写错时，报错会指出**具体哪个字段**，不再只说「配置无效」 |
| 修复 `pickPath` 的 bug | 修复：工作区路径为空时，文件可能被写到错误位置（**升级前请检查最近的提交**） |
| 拆了单文件 | 启动更快（冷启动从 1.2s 降到 0.4s） |
| 加了权限校验 | 现在只有工作区成员能看到文件列表 |

### 1.2 三条翻译原则

1. **说现象不说机制**：「报错会指出具体字段」而非「用了 zod 的 issues 数组」
2. **说收益不说工作量**：「启动快 3 倍」而非「重构了 5 个模块」
3. **可验证**：用户能自己确认「确实变了」吗？不能 → 重写

### 1.3 什么该省略

- 纯内部重构（用户无感）
- 测试/CI 调整
- 依赖小版本（无 API 变化）
- 代码风格

判据：**用户升级后，能感知到这个变化吗？** 不能 → 不写。

## 第 2 步：亮点区（只放 1~3 件）

### 2.1 为什么限 3 件

人的注意力有限。列 10 个「亮点」等于没有亮点。
选**最能让人决定「值得升」**的 1~3 件。

### 2.2 亮点怎么写

结构：**问题 → 变化 → 收益**

　　**标题**：上传不再卡住
　　**问题**：之前上传大文件时界面会假死
　　**变化**：现在有进度条，可以边传边做别的事

- 问题：用户遇到过的痛点
- 变化：现在怎么不一样
- 收益：对他有什么好处

⛔ 亮点里不要出现实现术语（「异步流式」「背压」）—— 那是给开发看的。

### 2.3 如果这次没有亮点

有时一个版本就是「修了一堆小问题」。此时：

- 不要硬凑亮点
- 写「本次为维护版本，主要修复了 N 个问题」，然后列出来
- 诚实比包装重要

## 第 3 步：不兼容变更（必须给动作）

### 3.1 三项缺一不可

| 项 | 内容 |
|---|---|
| **影响谁** | 哪类用户/哪种用法会受影响 |
| **会怎样** | 升级后具体会发生什么（报错？行为变了？） |
| **怎么办** | **可执行的迁移步骤** |

### 3.2 写法示例

　　**如果你在配置里用过 `null`**
　　· 影响：调用 `parseConfig(null)` 的代码
　　· 会怎样：升级后直接抛 `TypeError`（此前静默用默认值）
　　· 怎么办：把 `parseConfig(null)` 改成 `parseConfig({})`，或直接不传

　　**如果你解析过错误信息**
　　· 影响：读 `err.errors[]` 的代码
　　· 会怎样：字段改名为 `err.issues[]`
　　· 怎么办：全局搜索 `.errors[` 改成 `.issues[`，或锁版本

⛔ 「可能有影响」不是说明，是推卸责任。必须说清**谁、会怎样、怎么办**。

### 3.3 给「不升级」这个选项

如果不升级也能用（只是没有新功能），要明确说：
「本版本无不兼容变更，可放心升级」或「如果你不需要 X，可以留在旧版本」。

## 第 4 步：已知问题（诚实，但不吓人）

### 4.1 该写什么

- 已知但未修复的 bug（含影响范围）
- 已知的性能瓶颈（含触发条件）
- 已知的兼容性限制

### 4.2 写法

　　· 超大文件（>500MB）上传时进度条会停在 99%（实际已完成，刷新即可）— #123
　　· Windows 下路径含中文时预览可能失败 — #124

要点：**说清影响 + 有无 workaround + 追踪链接**。

⛔ 藏已知问题是最伤的：用户遇到了会认为你不可信。
但也不要把它写成「这个版本很烂」—— 说清范围与 workaround。

## 第 5 步：版本号与升级指引

### 5.1 版本号语义

| 版本位 | 含义 | 用户该做什么 |
|---|---|---|
| major | 有 breaking | 读「升级前请注意」 |
| minor | 有新功能，兼容 | 可直接升 |
| patch | 只修 bug | 建议升 |

### 5.2 升级指引要具体

- 差：「请升级到最新版」
- 好：「`pnpm add foo@2.1.0`，然后重跑 `pnpm build`」

### 5.3 回退指引

如果升级后出问题，怎么退？

- 退到哪个版本
- 有没有数据格式变化（退回去会不会读不了新数据）

⛔ 「数据格式升级后不可回退」是最重要的一条 —— 必须显著提示。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 亮点 ≤3 + 不兼容给动作 + 已知问题诚实 + 升级/回退指引
- WARN = 有未覆盖项（如某些改动无法判断影响）
- FAIL = 用实现术语 / 不兼容只说「可能有影响」 / 藏已知问题
- UNKNOWN = 无法判断用户影响（缺使用者信息）

```markdown
# v<版本>

<一句话：这次最值得说的一件事>

## 亮点
### <标题>
<问题 → 变化 → 收益>

## ⚠ 升级前请注意
### <不兼容项>
- 影响谁：
- 会怎样：
- 怎么办：

## 本次还修复了
- <用户可感知的修复>

## 已知问题
- <影响 + workaround + 链接>

## 升级方式
<具体命令>

## 想回退？
<退到哪个版本 + 数据是否兼容>
```

**读者**：<终端用户 / 集成方 / 运维>

**判不了的部分**
- <哪些改动无法判断用户影响>

## 假阳性清单（这些不必写进发版说明）

- 内部重构（用户无感）
- 测试/CI 改动
- 依赖小版本升级（无 API 变化）
- 代码风格调整
- 文档内部链接修正
- 性能微优化（用户感知不到，如 5ms → 4ms）

## 假阴性清单（最常漏的 8 类）

1. **默认值变化**没写（用户不报错但行为变了）
2. **错误信息/格式变化**（解析错误的代码会坏）
3. **需要手动操作的步骤**（如「要重跑迁移」）没写
4. **数据格式变化不可回退**没显著提示
5. **已知问题藏着**（用户遇到会觉得被骗）
6. **用实现术语解释用户可见变化**
7. **亮点列太多**（10 个等于没有）
8. **没有回退指引**

## 本仓库可用的命令

```bash
node tools/quality/verify-docs.mjs        # 说明里的版本号/数字与仓库一致
node tools/evolve/evolve.mjs verify        # 台账条目可追溯
```

## 与其他技能的关系

- `changelog`：面向维护者的分类清单，发版说明从它派生（但**重写语言**）
- `doc-write`：新功能的详细用法写在这里，发版说明只给一句 + 链接
- `release-gate`：发版前的完整门禁
- `release-pipeline`：发布流程本身
- `adr`：记录「为什么改」，发版说明只讲「改了对用户意味着什么」

## 边界（如实说清）

- 发版说明只能写**已知的**影响；未预见的副作用不会出现
- 「用户能感知」的判断依赖对用户的了解；内部工具与面向公众的产品写法不同
- 无法确认影响范围时（如不确定谁在用某 API），只能提示「若你使用 X 请检查」
- 面向多类读者时，一份说明无法同时满足；应拆成多份或明确主读者
- 本技能不判断「该不该发版」；那是 `release-gate` 的事
