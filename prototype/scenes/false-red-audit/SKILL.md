# 假失败审计 技能

> 假绿（该红不红）常见，**假红**（该绿却红）同样致命：真实存在的实现被判「没有」，团队就去补一份假的。
> 判据：**验收器判「没证据」时，是真没有，还是正则/解析写错了？**

## 什么时候用

- 验收器报「无证据/无法核验」但实现明明在
- 要评审「验收器可信」这类声明
- 出现「补了证据还是判没有」

## 什么时候**不**用

- 纯人工审查（无自动验收器）

## 第 1 步：先建最小反例

拿一个**真实存在**的实现（路径 + 行号），喂给验收器，看它为什么判「没有」。**不要先改验收器，先复现。**

## 第 2 步：三类常见解析 bug（真实案例）

| 类 | 症状 | 根因 |
|---|---|---|
| 正则状态残留 | 第二次调用起失配 | 带 `/g` 的 `exec` 的 `lastIndex` 跨调用残留 |
| 交替量词错误 | `.tsx` 被截成 `.ts` | 扩展名交替 `ts\|tsx` 未加锚定/分组 |
| 字符类不全 | 中文目录匹配不上 | 字符类不含 CJK |

## 第 3 步：修完要证明「真实现现在能过」

修完后，用第 1 步的真实实现复跑——**必须从 FAIL 变 PASS**。同时确认「真没有的」仍判 FAIL（不能为了过而放宽）。

## 第 4 步：把 bug 固化成测试

每个假红根因，都要留一条回归用例。

## 反例（写下来防复发）

- ✗ 不改验收器，去补一份假证据 → 掩盖 bug 且污染数据
- ✗ 为让实现过而放宽判据 → 真的没证据也过了
- ✗ 修完不回归 → 下次又错
- ✗ 只在单次调用验证 → 漏掉 `/g` lastIndex 残留

## 自检清单

- [ ] 先建最小反例复现
- [ ] 定位解析 bug 类别
- [ ] 修后真实现从 FAIL 变 PASS
- [ ] 真没有的仍 FAIL（判据未放宽）
- [ ] 留回归用例
