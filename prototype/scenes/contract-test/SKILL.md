# 契约测试 技能

> 微服务集成测试贵且慢；契约测试用「消费者和提供者的约定」在**各自 CI 里**验证兼容，不必起全套环境。
> 判据：**提供者改了接口，消费者会不会在合并前就发现？**

## 什么时候用

- 多服务/多团队接口协作
- 接口改动常互相破坏
- 集成测试太慢

## 什么时候**不**用

- 单体/单一团队

## 第 1 步：消费者驱动契约（CDC）

| 步骤 | 说明 |
|---|---|
| 1 消费者定义期望 | 我调用 X 接口，期望返回什么样 |
| 2 生成契约 | 存契约文件（Pact） |
| 3 提供者验证 | 提供者 CI 跑契约验证 |
| 4 双向验证 | 提供者真实实现满足契约 |

★ 由**消费者**定义期望（不是提供者自说自话）。

## 第 2 步：契约测什么

| 项 | 内容 |
|---|---|
| 请求格式 | 路径/方法/参数 |
| 响应结构 | 字段/类型 |
| 状态码 | 成功/错误 |
| 边界 | 空/错误响应 |

不测：业务逻辑正确性（那是别的测试）。

## 第 3 步：CI 集成

| 项 | 要求 |
|---|---|
| 契约版本化 | 契约本身有版本 |
| 提供者 CI 验证 | 合并前跑 |
| 破坏门禁 | 契约不满足则阻止合并 |

## 第 4 步：与 API 版本关系

契约测试是「兼容性护栏」，配合 `api-versioning`：破坏性改动要么升版本，要么被契约测试拦下。

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 契约与真实脱节 | 假通过 |
| 只测 happy | 边界漏 |
| 不阻塞合并 | 没护栏 |
| 契约过期 | 误导 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = CDC + 提供者 CI 验证 + 阻塞合并 + 边界
- WARN = 有契约但未阻塞合并
- FAIL = 无契约测试 / 契约脱节 / 只 happy
- UNKNOWN = 拿不到接口协作

**1. 契约**
| 项 | 有吗 |
|---|---|

**2. CI**
| 项 | 有吗 |
|---|---|

**3. 判不了的部分**
- <拿不到的消费者清单>

## 假阳性清单（这些不算「契约测试」）

- 契约与真实脱节
- 不阻塞合并
- 只测 happy

## 假阴性清单（最常漏的 8 类）

1. **契约脱节**
2. **不阻塞合并**
3. **只 happy path**
4. **提供者自定契约**（非消费者驱动）
5. **契约无版本**
6. **边界未测**
7. **无提供者验证**
8. **契约过期不维护**

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁
```

## 与其他技能的关系

- `api-contract`：契约核对
- `api-versioning`：兼容
- `test-strategy`：测试策略
- `ci-pipeline`：CI 集成

## 边界（如实说清）

- 契约测试不替代 E2E（业务流仍要测）
- 契约维护是持续成本
- 本技能不实现，只设计
