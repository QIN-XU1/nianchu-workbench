# 发布后验证 技能

> 「部署成功了」不等于「新版生效了」。装了新版却还是旧行为，是最坑的发布事故。
> 判据：**核心路径通吗？服务报的数字和代码实测一致吗？进程没崩吗？真实用户流程走通吗？**

## 什么时候用

- 每次发布/部署后
- 要评审「发布验证」这类声明
- 出现「明明发了新版但行为没变」

## 什么时候**不**用

- 纯本地开发迭代（无发布环节）

## 第 1 步：冒烟核心路径，不是首页

打 `/api/host-status` 这类核心接口，**不是「首页能打开」**。首页 200 只说明静态资源在，不说明服务正常。

## 第 2 步：数字核对（防「装了新版还是旧行为」）

服务自报的能力数/技能数，必须与**代码实测**一致。不一致 = 跑的还是旧代码。

## 第 3 步：进程未崩

验证期间服务仍在、后续请求仍通。不能「第一个请求过了，后面全 500」。

## 第 4 步：真实用户流程走一遍

建会话 → 写记忆 → 回读。**不只看健康检查**——健康检查过了但用户流程断的发布事故很常见。

## 反例（写下来防复发）

- ✗ 只测首页 200 → 不知道核心接口通不通
- ✗ 不核对数字 → 新版没生效也发现不了
- ✗ 只看健康检查 → 用户流程断了不知道
- ✗ 打不存在的路由返回 200 → 错误被掩盖

## 自检清单

- [ ] 核心路径冒烟（非首页）
- [ ] 数字与代码实测一致
- [ ] 验证期间进程未崩
- [ ] 真实用户流程走通
- [ ] 反例：不存在路由必须 4xx

## 实测数据（本仓库，可复算）

```
node tools/skills/verify-release-postdeploy.mjs
```

实测 **6 通过 / 0 失败**（脚本自起服务）：

- ① 冒烟：`/api/host-status` 200（**不是「首页能打开」**）
- ② 数字核对：服务报告的技能数/能力数与**代码实测**一致
- ③ 未崩：验证期间服务仍活，后续请求仍通
- ④ 用户流程：建会话 → 写记忆 → 回读
- 反例 A：打不存在的路由 → 必须 4xx（不能 200）
- 反例 B：故意用错误期望值 → 必须报「数字不一致」

**一句如实声明写在输出里**：「未覆盖（UNKNOWN）：真实线上流量/错误率基线对比——本机无线上环境」。
即：**这条验证只覆盖本机能覆盖的部分，不冒充线上观测**。

**教训**：**发布后验证要能证明「新版真的生效」**。只测「服务活着」证明不了这一点——数字核对才是关键那一刀。
