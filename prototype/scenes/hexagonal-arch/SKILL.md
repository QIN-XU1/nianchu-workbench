# 六边形架构（端口-适配器）技能

> 六边形的核心：**业务核心不依赖技术细节**（DB/HTTP/框架）。依赖指向内（业务），不指向外。
> 判据：**换个数据库/换套 API，业务核心代码要不要改？** 要改 = 耦合。

## 什么时候用

- 业务逻辑被框架/ORM 污染
- 要能替换技术实现
- 核心业务要可测试

## 什么时候**不**用

- 简单 CRUD（过度设计）

## 结构

| 层 | 职责 | 依赖 |
|---|---|---|
| **领域核心** | 业务规则 | 不依赖任何技术 |
| **端口** | 核心需要的接口（仓储/网关） | 核心定义 |
| **适配器** | 端口的技术实现（DB/HTTP） | 依赖核心 |

依赖方向：适配器 → 端口 → 核心（核心不 import 适配器）。

## 常见违反

| 违反 | 后果 |
|---|---|
| 领域核心 import ORM/框架 | 换技术要改核心 |
| 业务逻辑在 controller | 难测 |
| 端口是技术接口 | 依赖泄漏 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 核心无技术依赖 + 端口抽象 + 适配器隔离
- WARN = 大致分层但核心有泄漏
- FAIL = 业务在 controller / 核心直接依赖 ORM
- UNKNOWN = 拿不到代码结构

**1. 分层**
| 层 | 依赖方向 |
|---|---|

**2. 泄漏**
| 位置 | 泄漏 |
|---|---|

**3. 判不了的部分**
- <拿不到的代码>

## 假阳性清单（这些不算「六边形」）

- 分了目录但核心还是 import 框架
- 端口是技术接口

## 假阴性清单（最常漏的 8 类）

1. **核心 import ORM/框架**
2. **业务在 controller**
3. **端口泄漏技术**
4. **依赖方向反了**
5. **过度抽象**（简单也分七层）
6. **适配器含业务**
7. **核心不可独立测**
8. **换实现要改核心**

## 与其他技能的关系

- `domain-model`：领域建模
- `refactor-plan`：重构到六边形
- `dependency-injection`：依赖注入
- `test-strategy`：核心可测

## 边界（如实说清）

- 六边形有抽象成本，简单系统不必
- 本技能不实现，只检查
