# 多 Agent 编排 技能

> 多 agent 最常见的错误：**为了用多 agent 而用**。大多数任务一个 agent 更快更省。
> 多 agent 引入通信开销、状态不一致、死循环、成本翻倍。
> 判据：**这个任务真的需要并行/隔离，还是拆了反而更慢更贵？**

## 什么时候用

- 任务可并行（多文件/多角度独立）
- 需要上下文隔离（子任务互不污染）
- 需要不同角色（生成 vs 审查）

## 什么时候**不**用

- 单 agent 能做的（优先单 agent）
- 高度串行依赖
- 通信成本 > 并行收益

## 第 1 步：先问「该不该拆」

| 情况 | 结论 |
|---|---|
| 子任务独立且并行 | 适合 |
| 子任务强依赖（B 要 A 的结果） | 慎拆（串行即可） |
| 一人能做 | 不拆 |
| 需要对抗性验证 | 适合（生成+审查） |

⛔ 拆多 agent 的隐性成本：上下文传递、结果合并、重复劳动、协调复杂度。

## 第 2 步：编排模式

| 模式 | 说明 | 适用 |
|---|---|---|
| **扇出-汇总**（fan-out/fan-in） | 并行后合并 | 多文件审计 |
| **流水线**（pipeline） | 逐阶段传递 | 多阶段处理 |
| **主管-工人**（orchestrator-worker） | 主分配任务给子 | 动态分工 |
| **生成-审查**（adversarial） | 一个做一审查 | 质量把关 |

## 第 3 步：通信与状态

| 问题 | 处理 |
|---|---|
| 子 agent 之间怎么传 | 通过编排者中转（共享黑板/消息） |
| 上下文隔离 | 每个子 agent 只给它需要的 |
| 结果合并 | 定义清晰的合并规则 |
| 失败处理 | 某子失败不影响其他（独立） |

⛔ 所有子 agent 共享全部上下文 = 等于没隔离（还更贵）。

## 第 4 步：防死循环与失控

| 风险 | 防法 |
|---|---|
| 互相触发无限循环 | 最大轮次/深度限制 |
| 循环委派 | 检测重复任务 |
| 成本爆炸 | token/调用预算上限 |
| 无法收敛 | 明确终止条件 |

★ 必须有**全局预算与终止条件**，否则多 agent 会失控烧钱。

## 第 5 步：验证（多 agent 的产出可信吗）

| 检查 | 说明 |
|---|---|
| 子结果可复算 | 不是「agent 说对就对」 |
| 交叉验证 | 对抗性审查 |
| 去重 | 多 agent 可能重复产出 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 拆得合理 + 上下文隔离 + 有预算终止 + 结果可验证
- WARN = 拆了但无预算限制
- FAIL = 该单 agent 却拆 / 共享全部上下文 / 无终止条件
- UNKNOWN = 拿不到编排设计

## 假阳性清单（这些不算「多 agent 有优势」）

- 拆了但串行跑
- 子 agent 共享全上下文
- 无预算（烧钱）

## 假阴性清单（最常漏的 8 类）

1. **该单 agent 却拆**（更慢更贵）
2. **共享全部上下文**（没隔离）
3. **无终止条件**（死循环）
4. **无预算上限**（成本爆炸）
5. **结果不可复算**（agent 说啥信啥）
6. **重复劳动**（无去重）
7. **失败不隔离**（一个挂全挂）
8. **强依赖却硬并行**

## 与其他技能的关系

- `context-management`：子 agent 上下文隔离
- `agent-tool-design`：agent 的工具
- `capability-benchmark`：多 agent 效果评估
- `cost-optimization`：成本控制

## 边界（如实说清）

- 多 agent 不是越多越好，协调成本真实
- 子 agent 质量取决于模型
- 本技能不实现框架，只设计编排
