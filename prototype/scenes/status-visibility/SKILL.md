# 状态可见性 技能

> agent 跑起来，用户只看到一个转圈。它在做什么？花了多少？为什么停了？
> 判据：**界面上能读到「状态 + 为什么停 + 用量 + 耗时 + trace」吗？**

## 什么时候用

- 做 agent/长任务的界面
- 要评审「状态可见」这类声明
- 用户抱怨「不知道它在干嘛」

## 什么时候**不**用

- 瞬时操作（<1 秒）

## 第 1 步：状态条要有 5 个字段

| 字段 | 回答什么 |
|---|---|
| 状态 | 在做什么（运行/空闲/失败） |
| 停止原因 | **为什么停**（完成/撞预算/取消/出错） |
| 用量 | 花了多少（tokens/调用数） |
| 耗时 | 花了多久 |
| trace | 复盘入口（traceId） |

## 第 2 步：前端停止原因表必须与后端枚举一致

前端硬编码一份「原因 → 中文标签」的表，**键集合必须与后端 `STOP_META` 完全一致**。前端多一个/少一个都会显示英文 reason 或错标签。

## 第 3 步：空闲时也显示占位，不藏起来

空闲时显示「—」或「空闲」，而不是把整个状态条隐藏。**藏起来 = 用户不知道有没有这个能力。**

## 反例（写下来防复发）

- ✗ 只显示 state 和 tokens，没有「为什么停」 → 用户不知道是完成还是撞墙
- ✗ 前端标签表与后端枚举不一致 → 显示英文 reason
- ✗ 空闲时隐藏状态条 → 用户不知道有这功能
- ✗ 只有 traceId 没有「为什么停」 → 能复盘但不能一眼看懂

## 自检清单

- [ ] 5 字段齐全（状态/停止原因/用量/耗时/trace）
- [ ] 前端标签表 == 后端枚举
- [ ] 空闲显示占位
- [ ] 真渲染验证（不是只查源码）

## 参考实现指路

本仓库 `tools/agent/verify-d3-status.mjs`（16 项：前端 STOP_LABEL 与后端 STOP_META 一致 + 真 Chromium dump DOM 验状态条 5 字段 + 空闲占位）；后端枚举见 `tools/agent/stop.mjs`。

## 实测数据（本仓库，可复算）

```
node tools/agent/verify-d3-status.mjs
```

实测 **16 通过 / 0 失败**，两条主线：

1. **防漂移**（纯逻辑）：前端 `STOP_LABEL` 的键集合必须与后端 `stop.mjs` 的 `STOP_META` **完全一致**
   —— 多一个少一个都算错（否则界面会显示英文 reason 或错标签）。
2. **真渲染**：用 headless Edge（`--headless --virtual-time-budget`）dump DOM，
   断言状态条 5 个字段真的在页面上：`dp__statusbar` 容器 + 状态 / 停止原因 / 用量 / 耗时 / trace。
3. **空闲占位**：空闲时显示「—」而不是把整条隐藏。

**一个真实边界**：后端 `stopReason` 那 6 条断言依赖「真跑一次模型」。
本环境网关 401，所以脚本会打印「模型不可用 → 三段 UNKNOWN，跳过 6 条」，而**不判 FAIL**。

**教训**：**「界面有状态条」要分两半验**：标签表一致性（静态）+ 真渲染（动态）。只验一半会漏掉「DIV 在但内容没渲染」。
