# 威胁建模 技能

> 威胁建模不是列一张「可能的攻击」清单 —— 那是安全通告。
> 它的产出应该是：**这张图里，哪个边界最容易被跨过，跨过之后最坏能怎样。**
> 所以本技能的判据是：**每个入口都必须有「信任判断 + 校验方式」，说不出校验的就是漏洞。**

## 什么时候用

- 新增涉及**外部输入**或**敏感数据**的入口
- 上线前的安全自查
- 架构变更（新增服务/新增信任关系）
- 出了安全事件后的复盘

## 什么时候**不**用

- 已有代码要查具体漏洞 → `security-review`（本技能在**设计阶段**做）
- 要加运行时拦截 → **本产品不做**（见边界）
- 纯内部工具（无外部输入、无敏感数据）→ 风险极低

## 第 0 步：本技能的定位（与 `security-review` 的分工）

| 技能 | 时机 | 输入 | 产出 |
|---|---|---|---|
| **threat-model**（本技能） | **设计阶段**（代码还没写） | 架构/数据流 | 信任边界图 + 滥用路径 |
| `security-review` | **审查阶段**（代码已写） | 代码 | 具体漏洞 + 修复建议 |

⛔ 在代码写完后做威胁建模，多半会变成「给已有实现找理由」。
**威胁建模的价值在设计阶段**：它能让某些漏洞根本不出现。

## 第 1 步：列资产（保护什么）

### 1.1 四类资产

| 类型 | 例子 | 泄露/破坏的后果 |
|---|---|---|
| **数据** | 用户内容、配置、日志、数据库 | 隐私泄露、业务损失 |
| **凭证** | API key、token、密码、证书 | 被冒充、被滥用 |
| **算力** | CPU/内存/带宽/存储 | 被白嫖、服务不可用 |
| **信誉** | 域名、签名、包名 | 被钓鱼利用、供应链攻击 |

### 1.2 资产分级

| 级别 | 定义 | 例子 |
|---|---|---|
| **机密** | 泄露即造成实质损害 | 用户凭证、私钥 |
| **敏感** | 泄露造成困扰 | 用户内容、日志 |
| **公开** | 泄露无影响 | 开源代码、公开文档 |

⛔ 分级不是形式：**机密资产必须加密/隔离，敏感资产必须访问控制，公开资产可以不设防。**
没分级就一律「都重要」，等于都不重要。

### 1.3 资产清单的检验

对每个资产问：**如果它明天被公开，最坏会怎样？**

- 答不出后果 → 可能不是资产
- 后果严重 → 必须有机密级保护

## 第 2 步：枚举入口（外部能从哪里进来）

### 2.1 入口清单（六类）

| 入口 | 例子 | 常见遗漏 |
|---|---|---|
| **网络** | HTTP/WS/gRPC 端点 | 健康检查、指标端点 |
| **文件** | 上传、配置、日志读取 | 临时文件、缓存 |
| **命令行** | argv、环境变量 | CI 变量、`NODE_OPTIONS` |
| **进程间** | 管道、socket、共享内存 | 子进程继承的 fd |
| **依赖** | 第三方库、插件 | 传递依赖 |
| **人** | 运维操作、手动改配置 | 应急脚本 |

### 2.2 每个入口必须写清

| 字段 | 说明 |
|---|---|
| **谁可以访问** | 匿名/认证用户/管理员/本机 |
| **输入格式** | JSON/表单/文件/命令行 |
| **输入可信度** | 完全不可信 / 半可信 / 可信 |
| **校验位置** | 在哪一层校验（入口/业务/存储） |

⛔ 「校验位置」是威胁建模的核心：**如果校验只在前端，等于没校验。**

### 2.3 容易漏的入口

- **健康检查/指标端点**（常无认证）
- **错误页面**（可能回显输入）
- **日志**（可能记录敏感数据）
- **重定向**（开放重定向）
- **文件上传的元数据**（文件名、MIME、EXIF）
- **CI/CD 的环境变量**（可能被 PR 修改）

## 第 3 步：画信任边界（本技能最重要的产出）

### 3.1 什么是信任边界

**信任边界 = 数据从「不可信」进入「可信」区域的那条线。**

跨这条线的地方，**必须**有校验。没有校验的跨界点就是漏洞。

### 3.2 怎么画

1. 把所有组件画成框（浏览器 / 网关 / 服务 / 数据库 / 文件系统）
2. 标出**谁信任谁**（→ 表示「信任」）
3. 箭头穿过的地方就是边界

```
[浏览器] --不可信--> [HTTP 入口] --校验后--> [业务逻辑] --参数化--> [数据库]
                          ↑
                    信任边界在这里
```

### 3.3 边界清单（必须逐条确认）

| 边界 | 校验什么 | 在哪里校验 |
|---|---|---|
| 浏览器 → 服务 | 认证、输入格式、权限 | 中间件（**不是前端**） |
| 服务 → 数据库 | 参数化（防注入） | 数据访问层 |
| 服务 → 文件系统 | 路径前缀（防穿越） | 统一路径函数 |
| 服务 → 外部 API | 响应内容（对方可能被攻破） | 反序列化前 |
| CI → 部署 | 制品签名/来源 | 部署前 |

⛔ 最常见的错误：**信任边界画在「内网」**。
「内网就安全」是错觉 —— 内网也有被攻破的主机、也有恶意的内部人员、也有配置错误。

## 第 4 步：逐个入口推演滥用路径

### 4.1 推演方法（对每个入口问 5 个问题）

1. **能不能传超长/超大？**（DoS）
2. **能不能传特殊字符？**（注入/路径穿越）
3. **能不能传别人 ID？**（越权）
4. **能不能重复提交？**（重放/竞态）
5. **能不能让它报错？**（错误信息泄露）

### 4.2 每条滥用路径必须三段式

| 段 | 内容 |
|---|---|
| **触发方式** | 具体的输入（可复制） |
| **经过路径** | 经过哪些组件 |
| **后果** | 会发生什么（可观测） |

举例：

> **入口**：`POST /api/workspace/switch`
> **触发**：body 传 `{"workspaceId": "../../etc"}`
> **路径**：入口 → 未做前缀校验的路径解析
> **后果**：读到工作区外的文件

### 4.3 本仓库的正面实例

`workspaces` 存根**没有切换方法**（`tools/agent/verify-a15-approval.mjs` 的边界声明里写明）——
不是「校验了 workspaceId」，而是**结构上不存在这个入口**。

这是威胁建模里最有效的一类缓解：**消除入口，而不是校验入口。**
校验会漏（新代码忘了调），入口不存在就不会漏。

## 第 5 步：给缓解措施（分级，不是一律加拦截）

### 5.1 四类缓解（按效果排序）

| 类型 | 例子 | 效果 |
|---|---|---|
| **消除** | 不提供该入口 | 最好（不会漏） |
| **隔离** | 沙箱、独立进程、权限分离 | 好（影响受限） |
| **校验** | 输入验证、权限检查、参数化 | 中（会漏） |
| **监控** | 日志、告警 | 差（事后） |

⛔ 优先「消除」和「隔离」，不要一上来就「加校验」——
校验代码会随业务增长而遗漏，结构性的缓解不会。

### 5.2 本产品的特殊约定

**⛔ 本产品不做越界拦截闸（用户明令）。**

这意味着：

- 建模产出的是**风险提示与设计建议**，不是「加一道强制审批」
- 不做「什么都要审批」的形态（与「用户自主」的产品定位冲突）
- 建议的缓解措施应优先选「消除入口」而不是「运行时拦截」

为什么要写清楚：如果把威胁建模理解成「加拦截」，产品会变成
「每一步都要授权」的形态，那不是用户要的。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 每个入口都有信任判断 + 校验方式 + 滥用路径推演
- WARN = 有入口未推演 / 有缓解措施未落地
- FAIL = 有入口无校验 / 信任边界画错 / 只列入口没说怎么防
- UNKNOWN = 架构不清 / 拿不到数据流

| 资产 | 级别 | 泄露后果 |
|---|---|---|

**2. 入口清单**
| 入口 | 谁可访问 | 输入格式 | 可信度 | 校验位置 |
|---|---|---|---|---|

**3. 信任边界**

|---|---|---|---|

**4. 滥用路径（逐条三段式）**

## 假阳性清单（这些不是风险）

- 内部常量作为输入（无外部可控）
- 本机 CLI（已假设操作者有本机权限）
- 公开文档/开源代码（本就公开）
- 需要已有管理员权限才能触发的路径（除非能提权）
- 测试环境的假凭证

## 假阴性清单（最常漏的 8 类）

1. **健康检查/指标端点无认证**
2. **信任边界画在「内网」**（内网不等于安全）
3. **只在前端校验**（绕过前端直接调 API）
4. **错误页面回显输入**（XSS/信息泄露）
5. **日志记录敏感数据**
6. **重定向/文件上传元数据未校验**
7. **CI 环境变量可被 PR 修改**
8. **只列入口不说怎么防**（那只是清单，不是建模）

## 与其他技能的关系

- `security-review`：本技能在**设计阶段**，它**审代码**
- `api-contract`：权限模型变化属于契约变更
- `design-review`：威胁建模是设计评审的一个输入
- `adr`：重大的安全取舍应留 ADR
- `release-gate`：发布前必须有威胁建模结论

## 边界（如实说清）—— 本产品的重要约定

**⛔ 本产品不做越界拦截闸（用户明令）。**

其他边界：

- 威胁建模**不能证明系统安全**，只能穷举想得到的滥用路径
- 未知攻击（0day/逻辑组合）发现不了
- 无法评估「可能性」，只能列「可行性」；风险排序依赖业务判断
- 内部人员威胁覆盖有限（需要组织层面的控制）
- 拿不到完整架构/数据流时，结论只能是 UNKNOWN
