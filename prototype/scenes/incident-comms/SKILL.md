# 事故沟通 技能

> 事故沟通的目标不是「让用户不生气」，而是**让用户能自己判断要不要采取行动**。
> 所以它必须包含：**现在坏了什么、影响谁、我能做什么、下次什么时候有消息**。
> 另一条同样重要：**不知道就说不知道**。一次猜测被证伪，后面所有沟通都不被信。

## 什么时候用

- 线上事故正在处理，需要对外/对内通报
- 要写故障公告、状态页更新
- 要给管理层同步进展
- 恢复后要发收尾通知

## 什么时候**不**用

- 事故已结束要做深度复盘 → `postmortem`
- 要写给用户的功能更新 → `release-notes`
- 只是内部技术排查 → 直接说，不必套格式

## 第 0 步：先分清「对内」与「对外」

| 维度 | 对内（团队/管理层） | 对外（用户/客户） |
|---|---|---|
| **关心** | 谁在处理、根因、什么时候好 | 我受不受影响、我要做什么 |
| **能给** | 技术细节、影响范围、决策 | 影响、绕行方案、时间预期 |
| **不能给** | 未确认的猜测、甩锅 | 内部系统名、未确认根因、精确到分的承诺 |

⛔ 最常见错误：把对内的技术细节直接发给用户（「我们的 Redis 连接池耗尽」）——
用户不关心也不该知道，他要知道的是「你的数据还在不在」。

## 第 1 步：四段结构（每段都不能省）

### 1.1 已知（确认的事实）

只写**已验证**的：

　　已确认：从 10:02 起，约 12% 的请求返回 500 错误。
　　已确认：影响范围是「保存草稿」功能，读取不受影响。
　　已确认：10:35 已回滚到上一版本。

⛔ 每条「已确认」都要能指向一个观测（监控/日志/复现）。

### 1.2 未知（诚实说明边界）

这一段最常被省略，但它决定了可信度：

　　尚不清楚：为什么回滚后仍有 0.3% 的请求失败（正在排查）。
　　尚不清楚：是否有用户数据受影响（正在核对）。

⛔ 不写「未知」段，用户会假设「你什么都知道了」—— 一旦后面出现新问题，
就会变成「你之前骗我」。

### 1.3 正在做什么

　　正在做：
　　· 核对是否有数据受影响（预计 15 分钟内出结论）
　　· 排查回滚后残留的 0.3% 失败

要点：**动作 + 预期产出时间**，不是「我们正在全力处理」。

### 1.4 下次更新时间

**这是最重要的一段**，也是最常被省略的：

　　下次更新：11:00（无论有没有进展都会更新）

⛔ 不承诺更新时间，用户会每隔几分钟来问一次 —— 那是二次消耗。
承诺了但没更新，比不承诺更伤信任。

## 第 2 步：影响描述（用户能据此行动）

### 2.1 影响要写成「用户视角」

| 差（系统视角） | 好（用户视角） |
|---|---|
| 「数据库连接池耗尽」 | 「保存草稿会失败，已保存的内容不受影响」 |
| 「12% 请求 500」 | 「大约每 8 次保存有 1 次会失败，重试通常能成功」 |
| 「服务降级中」 | 「暂时不能上传图片，其他功能正常」 |

判据：**用户读完能不能判断「我要不要换个做法」？**

### 2.2 必须给绕行方案（如果有）

　　现在可以这样：先复制内容到本地，等恢复后再粘贴保存。

⛔ 没有绕行方案时，明确说「暂时没有替代方案」—— 别让用户自己找。

### 2.3 数据安全要单独说

用户最怕的是丢数据：

　　你的数据：已保存的内容没有丢失；故障期间未保存的编辑会丢失。

⛔ 这一条必须**明确**，不能靠「应该没事」带过。

## 第 3 步：不许做的事（信任的底线）

### 3.1 四不许

| 不许 | 为什么 |
|---|---|
| **不许猜根因** | 猜错了后面所有沟通都不被信 |
| **不许承诺精确时间**（「10 分钟内恢复」） | 做不到就是二次伤害；给区间或「下次更新时间」 |
| **不许甩锅**（「第三方服务的问题」） | 用户不关心是谁的问题，只关心你解不解决 |
| **不许说「已修复」而没验证** | 那是假成功，回退后信任归零 |

### 3.2 关于「已修复」的纪律

只有满足三条才能说「已修复」：

1. 故障现象消失（有观测）
2. 核心功能验证通过（跑过）
3. 观察了一个稳定窗口（如 10 分钟无复发）

⛔ 「看起来好了」不是修复。本仓库的纪律：**没有证据就说 UNKNOWN，不说 PASS。**

## 第 4 步：收尾通知（恢复后必须发）

### 4.1 收尾四要素

　　1. 已恢复：从 11:20 起，功能正常。
　　2. 影响回顾：10:02-11:20（78 分钟），影响「保存草稿」约 3400 次请求。
　　3. 数据结论：无数据丢失；故障期间未保存的编辑已丢失。
　　4. 后续：明天会发一份复盘，说明原因与改进。

### 4.2 收尾必须包含「数据结论」

不管有没有丢，都要说。**没说 = 用户会假设丢了。**

### 4.3 承诺后续要兑现

如果说了「明天发复盘」，就必须发。**不兑现的承诺比不承诺更伤信任。**

## 第 5 步：不同渠道的差异

| 渠道 | 特点 | 调整 |
|---|---|---|
| **状态页** | 公开、可订阅 | 极简，只写影响与时间 |
| **邮件/公告** | 一次性、正式 | 完整四段 + 绕行方案 |
| **群聊/IM** | 实时、简短 | 每次只写变化，不重复全文 |
| **对管理层** | 关心决策 | 加「需要什么支持」 |

⛔ 同一份文案发所有渠道，会在某个渠道显得太啰嗦或太简略。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 四段齐 + 影响用户视角 + 有绕行/数据结论 + 有下次更新时间
- WARN = 缺「未知」段或数据结论
- FAIL = 猜根因 / 承诺精确时间 / 说「已修复」未验证
- UNKNOWN = 影响范围还没查清（此时应只发「正在排查」）

　　## 状态更新 · <时间>

　　**影响**：<用户视角：什么功能坏了，谁受影响>
　　**数据**：<已保存的有没有丢 / 未保存的会丢>
　　**现在可以**：<绕行方案，或「暂无替代方案」>

　　**已确认**：
　　· <事实 1>
　　· <事实 2>

　　**尚不清楚**：
　　· <未知 1>

　　**正在做**：
　　· <动作 + 预期产出时间>

　　**下次更新**：<时间，无论有无进展>

**收尾通知**
```markdown
## 已恢复 · <时间>

**恢复时间**：<>
**影响回顾**：<时段 + 次数/人数>
**数据结论**：<有/无丢失>
**后续**：<复盘时间 / 改进项>
```

**判不了的部分**
- <哪些影响范围还没确认>

## 假阳性清单（这些不算「沟通到位」）

- 只写「正在处理」没有下次更新时间
- 只写系统指标没有用户视角影响
- 没有绕行方案也没说「暂无」
- 恢复通知没提数据结论

## 假阴性清单（最常漏的 8 类）

1. **猜根因**（「是 Redis 的问题」）
2. **承诺精确时间**（「10 分钟内」）
3. **没有「未知」段**（假装全知道）
4. **没有下次更新时间**（用户反复来问）
5. **影响用系统语言**（用户看不懂）
6. **不提数据是否丢失**
7. **说「已修复」但没验证**
8. **收尾不兑现后续承诺**

## 本仓库可用的命令

```bash
node tools/workbench/verify-http-e2e.mjs   # 确认功能真的恢复
node tools/quality/commit-gate.mjs          # 修复提交前跑门禁
```

## 与其他技能的关系

- `postmortem`：事故结束后的深度复盘
- `debug-repro`：定位根因（沟通时不要说未确认的根因）
- `rollback-plan`：回滚是止血手段，沟通要同步进展
- `release-notes`：面向用户的功能更新（非事故）
- `handoff`：事故交接班时的信息传递

## 边界（如实说清）

- 沟通**不能减少事故损失**，只能减少「因信息不明造成的二次损失」
- 影响范围在排查完成前无法准确给出，此时只能报「正在确认」
- 无法预测恢复时间时，**不该给数字** —— 只给「下次更新时间」
- 对已流失的用户，事后沟通效果有限
- 本技能不判断「该不该公开」——那是公司决策
