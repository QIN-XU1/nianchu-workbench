# 依赖升级 技能

> 升级依赖的风险不在「装不上」，而在**装上了但行为变了**。
> 编译通过、测试全绿、然后线上出错 —— 这是依赖升级最典型的失败形态。
> 所以本技能的核心动作是：**在升级之前，先把「哪些地方会受影响」列出来**。

## 什么时候用

- 依赖有安全漏洞需要修
- 依赖太旧，想跟进新版本
- 某个库停止维护，要换掉
- 间接依赖冲突，必须升直接依赖来解

## 什么时候**不**用

- 只是新增一个依赖（不是升级）→ 走 `design-review` 评估是否必要
- 要换掉整个技术栈 → `design-review` + `adr` + `refactor-plan`
- 是应用代码升级（不是依赖）→ `refactor-plan`

## 第 0 步：先判断「该不该升」

不是所有「有新版本」都值得升。三个判断：

| 情况 | 该升吗 |
|---|---|
| 有安全漏洞（CVE）且影响你的用法 | **必须升** |
| 有安全漏洞但不影响你的用法 | 可以等（记录原因） |
| 无漏洞，只是版本旧 | 看收益：新功能/性能/维护性 |
| 大版本 breaking 很多，收益很小 | **不升**（记录为「评估后不升」） |

⛔ 「最新版总是更好」是错的。升级本身有成本（时间、风险、回归测试）。
**评估后决定不升，也是一个正当结论** —— 但要写清理由（见 `adr`）。

## 第 1 步：读 changelog，找出 breaking change

### 1.1 三种信息源，优先级从高到低

1. **CHANGELOG.md / releases 页面**（最权威）
2. **迁移指南**（major 版本通常有 MIGRATION.md）
3. **git diff**（前两者都没有时，直接比 tag）

⛔ 只升不读 changelog = 隐形 breaking。这是最常见的翻车原因。

### 1.2 从 changelog 里提炼「受影响调用点」

不要只列「breaking 1/2/3」，要**映射到自己的代码**：

| changelog 里的变化 | 我们哪里受影响 | 怎么改 |
|---|---|---|
| 删除了 `foo()` | `src/a.mjs:42` 调用了它 | 改用 `bar()` |
| `opts.timeout` 单位从秒改成毫秒 | `src/b.mjs:88` 传了 `30` | 改成 `30000` |
| 默认值从 `true` 改成 `false` | `src/c.mjs:15` 依赖默认值 | 显式传 `true` |

判据：**每条 breaking 都能指到我们代码的具体行号**，否则就是没读完。

### 1.3 检查「没有写进 changelog 的变化」

有些变化 changelog 不会写，但会影响你：

- **传递依赖**（我们的依赖的依赖）变了
- **Node/运行时最低版本**要求变了
- **打包体积**显著变化
- **行为细节**（错误信息、排序稳定性、浮点精度）

手段：升级后看 `lock` 文件的 diff，以及跑对比测试。

## 第 2 步：分阶段升级（patch → minor → major）

### 2.1 为什么必须分阶段

一次从 1.2 跳到 3.0，出问题时无法定位是哪一步引入的。
分阶段升，每阶段都能独立验证与回滚。

| 阶段 | 语义版本 | 风险 | 预期 |
|---|---|---|---|
| patch | 1.2.3 → 1.2.9 | 低 | 只有 bug 修复，应无行为变化 |
| minor | 1.2 → 1.9 | 中 | 有新功能，通常向后兼容 |
| major | 1.x → 2.x | 高 | 有 breaking，需逐条处理 |

### 2.2 每阶段的三步

1. **升版本**（只改 package.json / lock）
2. **跑验证**（测试 + 构建 + 关键路径手工验证）
3. **单独提交**（便于 `git revert`）

⛔ **锁文件变更必须与 package.json 一起单独提交**，不要混在功能改动里。
混在一起的后果：出问题时无法只回滚依赖升级。

### 2.3 每阶段后必须验证的四件事

| 检查 | 怎么验 |
|---|---|
| 测试全绿 | 跑全量测试，记录通过数 |
| 构建通过 | 类型检查 / 打包 |
| 无新告警 | 编译告警、运行时警告、废弃提示 |
| 关键路径可用 | 手工跑一遍核心功能（不只是测试） |

⛔ 「测试全绿」不等于「行为没变」—— 测试只覆盖你想到的路径。

## 第 3 步：处理 breaking change（逐条，不许批量糊过）

### 3.1 逐条处理的纪律

对每条 breaking：

1. 找到受影响的调用点（第 1.2 步列的清单）
2. 改代码
3. **改完单独验证那一条**（不要攒到最后一起跑）

### 3.2 三类常见 breaking 的处理

| 类型 | 处理方式 |
|---|---|
| **API 改名/移动** | 全局搜索旧名，逐个改；注意动态调用（`obj[name]()`） |
| **参数语义变化** | 找出所有传该参数的地方，逐个核对单位/含义 |
| **默认值变化** | 所有依赖默认值的地方都要显式传值 |

⛔ 第三类最隐蔽：代码没报错，但行为变了。

### 3.3 无法立即处理时的过渡

如果某些 breaking 暂时处理不了：

- 先锁定在旧版本（不升那个包）
- 或用兼容层（同时支持新旧），但**必须写退出条件**

## 第 4 步：验证「没有隐形行为变化」

### 4.1 三类隐形变化

| 类型 | 怎么发现 |
|---|---|
| **输出格式变了** | 对比升级前后的输出（同输入） |
| **性能变了** | 跑基线对比（见 `perf-profile`） |
| **错误表达变了** | 触发错误路径，对比错误类型/码 |

### 4.2 对比测试的做法

1. 升级**前**用固定输入跑一遍，存下输出
2. 升级**后**用同样输入跑，逐字段对比
3. 差异逐条判断：是预期的（breaking 处理过）还是意外的

本仓库实例：`verify-git-status.mjs` 的做法就是「与权威源对拍」——
不关心内部实现，只要求输出与 `git status --porcelain=v1` 一致。升级 git 相关依赖时可直接复用。

### 4.3 检查 lock 文件的 diff

```bash
git diff <升级前提交> -- package-lock.json pnpm-lock.yaml | head -100
```

要看：

- 只升了目标包，还是**连带升了一堆传递依赖**？
- 有没有**新增依赖**（可能是某个包引入了新东西）？
- 有没有**删掉依赖**（可能影响别的包）

⛔ 连带升级大量传递依赖是常见风险源 —— 出问题时不知道是哪个导致的。

## 第 5 步：安全漏洞类升级的特殊要求

如果升级原因是 CVE：

1. **确认漏洞真的影响我们**（很多 CVE 只在特定用法下触发）
2. **确认升级真的修了它**（不是升到另一个仍有漏洞的版本）
3. **记录漏洞编号与修复版本**（便于审计）

⛔ 「升到最新版就安全了」不一定对 —— 有些漏洞在新版本仍存在，或有新的漏洞。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 升级完成、验证全绿、无隐形变化
- WARN = 升级完成但有已知遗留（列出）
- FAIL = 有 breaking 未处理 / 验证失败 / 行为意外变化
- UNKNOWN = 无法验证（缺测试/缺基线/无法对比）

## 假阳性清单（这些不是升级问题）

- 传递依赖小版本变化但没有行为影响
- 编译告警增加但都是废弃提示（且已记录）
- 打包体积略增（新功能带来的）
- 测试耗时变化（不是性能问题）
- 新版本 API 更严格导致原代码要加类型断言（那是 breaking，但要处理）

## 假阴性清单（最常漏的 8 类）

1. **不读 changelog 直接升**
2. **一次跨多个 major**
3. **锁文件变更与功能改动混在一个提交**
4. **默认值变化没检查**（代码不报错但行为变了）
5. **只跑测试没手工验证关键路径**
6. **没看 lock diff 里的连带升级**
7. **CVE 升级没确认真的修了**
8. **没有回滚预案**

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs        # 每阶段提交前跑门禁
node tools/agent/verify-models.mjs        # 模型相关依赖升级后的验证（18 项）
node tools/workbench/verify-http-e2e.mjs  # 端到端验证（17 项）
```

## 与其他技能的关系

- `design-review`：升级涉及架构变化时先评审
- `adr`：决定「升/不升」这类不可逆选择应留 ADR
- `refactor-plan`：大版本迁移需要分期时用它
- `perf-profile`：升级后怀疑变慢时用它测量
- `code-review`：升级带来的代码改动要审
- `release-gate`：升级属于发布动作，走发布门禁

## 边界（如实说清）

- 无法发现「changelog 没写」的行为变化；只能靠对比测试，而对比测试只覆盖已测路径
- 传递依赖的行为无法完全掌控（它们没有 changelog 给我们读）
- 大版本升级可能需要重写调用方代码，那已超出「升级」范围，应转 `refactor-plan`
- 没有基线（升级前没跑过对比）时，无法判断「行为是否变化」，结论只能是 UNKNOWN
- 本技能不评估「新版本是否更安全」——那需要独立的漏洞评估
