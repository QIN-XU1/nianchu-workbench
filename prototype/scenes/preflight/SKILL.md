# 前置探活 技能

> 在后台重启服务的**同时**跑验证，界面层正好落在服务不可用窗口——于是报「假失败」，浪费一轮排查。
> 判据：**跑验证前，先确认被测环境真的在吗？探活失败会不会被误报成产品故障？**

## 什么时候用

- 验证依赖外部服务/环境
- 出现「偶发失败、重跑就好」
- 要评审「失败归因」这类声明

## 什么时候**不**用

- 纯单元测试（无外部依赖）

## 第 1 步：显式探活三件事

| 检查 | 断言 |
|---|---|
| HTTP | `/api/host-status` 返回 200 且 `ok:true` |
| 方法表 | `implemented` 是数组且长度 > 0 |
| WebSocket | 同端口 `/ws` 握手能收到响应 |

## 第 2 步：探活失败就停，不往下跑

探活失败 → 报 UNKNOWN 并退出（exit 2），**不要把后续失败归因给产品**。

## 第 3 步：把「环境窗口」与「产品故障」分开

这是核心：偶发失败要先怀疑「环境在窗口期」，而不是「产品坏了」。探活把这件事显式化。

## 反例（写下来防复发）

- ✗ 不探活直接跑 → 服务没起也报「界面层 7/8 失败」
- ✗ 探活失败还继续 → 一堆假失败
- ✗ 习惯性「重跑一次就算了」 → 掩盖真实问题
- ✗ 把环境失败写进产品缺陷台账 → 污染数据

## 自检清单

- [ ] HTTP + 方法表 + WS 三项探活
- [ ] 探活失败 → UNKNOWN 退出，不归因产品
- [ ] 区分环境窗口与产品故障
- [ ] 有反例（服务不在时必须判 UNKNOWN 而非 FAIL）

## 参考实现指路

本仓库 `tools/quality/preflight.mjs`（85 行：HTTP 200 + implemented 非空 + WS 握手；失败即停，不归因产品）；`tools/workbench/_serve.mjs` 的自起逻辑与它配套（先探活，不可达才自起）。

## 实战记录（本仓库真实事件）

**事件（第 104 轮）**：`verify-goal` 报 R8 FAIL（界面层 7/8）。追查发现——是我在后台
**重启 47124 服务的同一时刻**跑了 verify-goal，界面层断言正好落在「服务不可用窗口」。
产品其实没问题，是**探活缺失**导致的假失败。

**代价**：浪费一轮排查；更糟的是它可能让人「习惯性重跑一次就算了」，从而忽略真实回归。

**现在的做法**：`tools/quality/preflight.mjs` 先做三项探活，失败即停（exit 2 / UNKNOWN），
**不把后续失败归因给产品**。

**复算**：
```
node tools/quality/preflight.mjs
```
三项：① `/api/host-status` 200 且 ok:true；② `implemented` 是数组且长度 > 0；③ 同端口 `/ws` 握手收到响应。

**配套**：`tools/workbench/_serve.mjs` 的 `ensureServer(base)` 先探活，不可达才自起；
起不来如实返回 `ok:false`（调用方标 UNKNOWN，不伪 FAIL）。

**教训**：**偶发失败先怀疑环境窗口，再怀疑产品**。但"怀疑"要变成可执行的探活，不能只是心里想想。
