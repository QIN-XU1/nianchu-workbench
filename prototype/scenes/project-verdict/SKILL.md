# 逐项目结项判定 技能

> 这个技能只回答一个问题：**「这个参照项目，我们真的超过了吗？」**
> 它的难点不在计算，而在**拒绝自我抬高的诱惑**：
> 把「部分」算成「有」、把 OWN 证据当 REAL、把「净胜为正」当「零落后」——
> 每一种偷换都能让结论好看一点，也都让结论失去意义。

## 什么时候用

- 要回答「对比做到哪一步了、能不能结项」
- 要找出「我们现在还不如谁、差在哪一维」
- 每轮对比收尾时的固定动作
- 有人质疑「凭什么说超过了」

## 什么时候**不**用

- 要审证据本身可不可复算 → `evidence-audit`（本技能的输入）
- 要重跑对比 → `fair-compare`
- 要补某一维的短板 → 具体维度的技能（如 `test-writing`）

## 第 0 步：输入从哪来（先确认数据可信）

### 0.1 两种入口

```bash
node tools/evolve/project-verdict.mjs          # 文本输出（人看）
node tools/evolve/project-verdict.mjs --json   # 写入 evidence/evolve/project-verdict.json（机读）
```

### 0.2 输入依赖

判定基于**对比矩阵**（31 维 × 22 家）。矩阵本身可信吗？先看：

| 检查 | 命令 | 不过会怎样 |
|---|---|---|
| 证据可复算比例 | `audit-evidence-provenance.mjs` | REAL 低 ⇒ 判定不可靠 |
| 矩阵完整性 | `check-matrix-integrity.mjs` | 有空格 ⇒ 统计偏差 |
| 维度清单 | `verify-dim-manifest.mjs` | 维度定义漂移 ⇒ 前后不可比 |

⛔ **先跑 `evidence-audit` 再看判定。** 证据是 OWN 的维度，判定再好看也不成立。

## 第 1 步：四档判定（写死在代码里，不许手调）

### 1.1 四档定义

| 档位 | 条件 | 含义 |
|---|---|---|
| **实质超越** | 可比维 ≥ 10 且 落后维 = 0 且 净胜 ≥ 2 且 覆盖 ≥ 60% | 可以结项 |
| **基本超越** | 可比维 ≥ 10 且 落后维 = 0 且 净胜 ≥ 0 | 打平偏上，可结项 |
| **不及** | 存在**任何**一个落后维 | 不能结项（哪怕净胜很大） |
| **可比不足** | 可比维 < 10 | 样本太小，无法判定 |

### 1.2 为什么「落后维 = 0」是硬条件

净胜 10 但落后 1，**不能**叫超越 —— 那个落后的维度就是对方能说你「不如我」的地方。

判据：**「落后维 = 0」是必要条件，不是加权项。**
加权会让「用 10 个优势抵消 1 个劣势」变得合理，但对比的语义不是这样。

### 1.3 「可比不足」不是「超越」

可比维 < 10 时，无论净胜多少都只能判「可比不足」。
这是防止「只挑我们强的维度比」——**样本太小，结论没有统计意义。**

### 1.4 覆盖率的含义

覆盖 ≥ 60% 指「31 维里有 ≥ 19 维拿到了可对比数据」。
覆盖不足说明对比不完整，此时「实质超越」要降级。

## 第 2 步：读结论（三个数字一起看）

### 2.1 每个对手输出什么

| 字段 | 含义 | 怎么看 |
|---|---|---|
| `verdict` | 四档之一 | 结论 |
| `netWin` | 净胜维数（有 - 无） | 正数才好 |
| `lag` | 落后的维度列表 | **必须为空** |
| `comparable` | 可比维数 | ≥ 10 |
| `coverage` | 覆盖率 | ≥ 60% |
| `realRatio` | 证据可复算比例 | 越低越不可信 |

### 2.2 三个数字的口径不能混

本仓库有两套说法，**必须同时报**：

| 口径 | 含义 | 用途 |
|---|---|---|
| **「有 + 部分」家数** | 把「部分」也算作不落后 | 宽松：说明不是完全空白 |
| **「REAL 家数」** | 只算证据可复算的 | 严格：说明领先是真的 |

⛔ 混用会说错话。正确写法：

> 净胜 14 家（「有+部分」口径）；其中 REAL（证据可复算）11 家，
> 另 3 家（ecc/openclaw/hermes）的领先依赖 OWN 证据，**未核实**。

### 2.3 「不及」的对手怎么处理

对每个「不及」的对手：

1. 看 `lag` 列出落后维
2. 逐维判断：是**真落后**（对方确实更强）还是**证据缺失**（没查到）
3. 真落后 → 补短板；证据缺失 → 补证据（可能判定会变）

⛔ 不要因为「补证据后可能还是落后」就不补 —— 那是回避，不是判定。

## 第 3 步：结项条件（全部满足才能进下一个项目）

### 3.1 结项检查清单

- [ ] 该对手判定为「实质超越」或「基本超越」
- [ ] `lag` 为空（零落后维）
- [ ] `comparable` ≥ 10（样本够）
- [ ] `coverage` ≥ 60%（对比完整）
- [ ] `realRatio` 达到阈值（证据可复算）
- [ ] 31 维 × 22 家的矩阵已提交（可复算）
- [ ] 台账已记录本轮判定（含口径声明）

⛔ **任一不过，就不能结项。** 尤其是 `lag` 不为空时，无论净胜多少都不行。

### 3.2 本仓库当前状态（示例，会过期）

> 判定：**部分**。已接线 20/20 能力，但规模仍落后（186 个技能 vs 对方唯一技能 186~314；全仓 SKILL.md 141~1068）。
> 落后点已从「能力」改为「规模」—— 这是本轮最重要的判定变化。

⛔ 上面这段会过期。**用之前必须重跑 `project-verdict.mjs` 拿最新值**，不要抄。

## 第 4 步：写回台账（可追溯）

### 4.1 每轮必须记录

| 字段 | 内容 |
|---|---|
| 判定 | 四档之一 |
| 关键数字 | netWin / lag / comparable / coverage / realRatio |
| 口径 | 本轮用哪种（或两种都报） |
| 变化 | 相比上轮变了什么（哪个对手升/降档） |
| 依据 | 矩阵提交 / 审计输出路径 |

### 4.2 记录样例

> 第 119 轮判定：**部分**。
> 净胜 14 家（有+部分口径）/ REAL 11 家。
> 本轮变化：adr、dep-upgrade 从「无深度」补到 8~9KB，deep 技能 3→11。
> 落后点：规模（30 vs 141~1068），非能力。
> 依据：`evidence/evolve/project-verdict.json`。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 所有对手可结项（实质/基本超越）+ 零落后 + 证据达标
- WARN = 部分对手「可比不足」（样本不够）
- FAIL = 有对手「不及」/ 有落后维 / 证据不可复算
- UNKNOWN = 矩阵不完整 / 无法判定

**1. 逐对手判定**
| 对手 | 判定 | netWin | lag | comparable | coverage | realRatio |
|---|---|---|---|---|---|---|

**2. 口径声明**
- 宽松（有+部分）：<> 家
- 严格（REAL）：<> 家
- 差异：<>

**3. 本轮变化**
- 升档：<>
- 降档：<>
- 新落后维：<>

**4. 结项检查**
- [ ] 零落后
- [ ] 样本 ≥ 10
- [ ] 覆盖 ≥ 60%
- [ ] 证据可复算
- [ ] 矩阵已提交
- [ ] 台账已记录

**5. 判不了的部分**
- <哪些对手/维度无法判定>

## 假阳性清单（这些不是「超越」）

- 净胜为正但有一个落后维（**不是超越**）
- 可比维 < 10 但净胜很大（**可比不足**）
- 对手证据是 OWN（未核实）
- 只比了我们强的维度（样本偏差）
- 「部分」被当成「有」（口径偷换）
- 矩阵有空格但统计时当 0 处理（偏差）

## 假阴性清单（最常漏的 8 类）

1. **不先跑 evidence-audit 就看判定**
2. **把「净胜为正」当「零落后」**
3. **可比不足判成超越**
4. **口径混用**（有+部分 vs REAL）
5. **矩阵有空格**（统计偏差）
6. **抄上一轮的结论**（已经过期）
7. **「不及」的对手不追 lag**
8. **判定没写回台账**（下轮又从头）

## 本仓库可用的命令

```bash
node tools/evolve/project-verdict.mjs            # 逐项目判定
node tools/evolve/project-verdict.mjs --json     # 写入 JSON
node tools/evolve/audit-evidence-provenance.mjs  # 先确认证据可复算
node tools/benchmark/check-matrix-integrity.mjs  # 矩阵完整性
node tools/evolve/verify-dim-manifest.mjs        # 维度清单未漂移
```

## 与其他技能的关系

- `evidence-audit`：本技能的输入必须先过它
- `fair-compare`：重跑对比（判定变了要重跑）
- `self-review`：我方「有」的断言也要审
- `release-gate`：结项判定是发布门禁的一项
- 各维度技能：补 `lag` 里列出的落后维

## 边界（如实说清）

- 判定只反映**矩阵里记录的**维度；矩阵没覆盖的能力不会被计入
- 「超越」是相对参照项目的，不代表产品好（对手可能本身不好）
- 证据不可复算时，结论只能是 UNKNOWN（不是「不及」也不是「超越」）
- 维度权重相同；不区分重要性（这是有意的简化，但要知道）
- 对手仓库不可得时无法判定
- 本技能不做对比，只做收敛
