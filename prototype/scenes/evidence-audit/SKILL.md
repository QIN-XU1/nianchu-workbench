# 证据溯源审计 技能

> 这一整套工作的地基是「证据」。
> 如果证据只是**我们自己写的分析文档**，那「领先」就是自说自话 —— 逻辑上循环。
> 所以本技能只问一个问题：
> **这条「对手有 X」的判定，能不能在对方的仓库里点开一个具体文件看到 X？**
> 看不到，就是 OWN，不是 REAL。

## 什么时候用

- 要确认某条「对手有/部分/无」的判定真的指向对方仓库里的文件
- 怀疑「领先」结论是靠自我评分堆出来的
- **每轮对比收尾前的固定动作**（不是可选项）
- 有人质疑「你怎么证明对方没有」

## 什么时候**不**用

- 要审我们自己的代码质量 → `code-review`
- 要审我们的文档一致性 → `verify-docs`
- 要重跑对比 → `fair-compare`

## 第 0 步：三种证据等级（先搞清定义）

| 等级 | 定义 | 可复算吗 |
|---|---|---|
| **REAL** | 证据路径能 join 到**对方仓库**里的真实文件 | ✅ 能（点开就看到） |
| **OWN** | 证据只指向**我方**的分析文档/矩阵条目 | ❌ 不能（循环论证） |
| **NONE** | 没有证据路径 | ❌ 不能（纯断言） |

判据：**REAL 才能支撑对比结论；OWN 和 NONE 都只能说「未核实」。**

⛔ 本仓库最初的问题就是：矩阵里的证据大量是 OWN（「见 hermes 的 memory 模块」），
但那条路径 join 不到对方仓库 —— 于是「领先」不可复算。

## 第 1 步：跑溯源审计，看 REAL/OWN/NONE 比例

### 1.1 三条命令

```bash
node tools/evolve/audit-evidence-provenance.mjs            # 看 REAL/OWN/NONE 比例
node tools/evolve/audit-evidence-provenance.mjs --strict   # 列出「判有/部分但抽不出路径」的格（exit 4）
node tools/evolve/audit-self-claims.mjs                    # 用同一把尺子量我方「有」
```

### 1.2 三条命令各自回答什么

| 命令 | 回答的问题 |
|---|---|
| `audit-evidence-provenance` | 对手的证据里，多少能复算？ |
| `--strict` | 哪些**声称有/部分**的格，证据其实是空的？ |
| `audit-self-claims` | **我方**声称「有」的，指向本仓库真实文件吗？ |

⛔ 第三条最容易被忽略，也最重要：**只量对手不量自己，就是双标。**
如果我方「有」也是 OWN，那领先同样不成立。

### 1.3 三段自检（工具本身是否可信）

审计工具会先自检：

| 自检 | 检查什么 | 失败含义 |
|---|---|---|
| **抽取** | 能不能从条目里抽出路径 | 抽不出 ⇒ 全部判 OWN（假阴性） |
| **根目录** | 路径能不能 join 到仓库根 | join 不到 ⇒ 配置错 |
| **键名** | 矩阵键名是否匹配 | 不匹配 ⇒ 统计错位 |

⛔ **自检 exit 2 表示工具本身坏了，此时所有结论作废。**
不能因为「跑完了没报错」就相信结果 —— 工具坏了会伪装成「全部通过」。

## 第 2 步：对 OWN 的格，二选一（补路径 或 降级）

### 2.1 只有两个合法动作

| 动作 | 什么时候用 | 怎么做 |
|---|---|---|
| **补真实路径** | 对方仓库里确实有这个能力 | 找到具体文件，写成可 join 的完整相对路径 |
| **如实降级** | 找不到（对方可能没有，或我们没查清） | 把「有」改成「部分」或「无」，并记录为什么 |

⛔ **没有第三个选项**。「先留着，以后再补」= 保留了一个不可复算的断言。

### 2.2 补路径的写法（最容易错的地方）

| 写法 | 能 join 吗 | 判定 |
|---|---|---|
| `foo.ts` | ❌ 裸文件名 | OWN |
| `src/foo.ts` | ✅ | REAL |
| `packages/core/src/foo.ts` | ✅ | REAL |
| `见 hermes 的 memory 模块` | ❌ 自然语言 | OWN |
| `hermes/memory/index.ts`（若仓库根是 hermes） | ✅ | REAL |

判据：**把这段路径贴到仓库根后面，能不能用 `Test-Path` 打开？**

本仓库实测：`pi` 的 `zlib` 曾被误判为「无」——
因为只查了单文件，而那是多 package 仓库。**多 package 仓库不能凭单文件否证一个能力。**

### 2.3 降级时的纪律

降级不是「认输」，是**让结论可信**：

- 改「有」→「部分」：说明哪部分有、哪部分没有
- 改「有」→「无」：说明查了哪些路径都没有
- 改「有」→「UNKNOWN」：说明无法确认（对方代码不可得）

⛔ 降级后必须重跑 `fair-compare`，因为判定变了，净胜数会变。

## 第 3 步：核对口径（同一句话不能用两种统计）

### 3.1 两种口径

| 口径 | 含义 | 用途 |
|---|---|---|
| **「有 + 部分」家数** | 把「部分」也算作不落后 | 宽松：说明我们不是完全空白 |
| **「REAL 家数」** | 只算证据可复算的 | 严格：说明领先是真的 |

### 3.2 混用的后果

- 用「有+部分」说「14 家净胜」→ 听起来很好
- 用「REAL」说「只有 3 家真正领先」→ 才是事实

⛔ **混用会说错话**：把宽松口径的结论当成严格口径的结论，
就等于把「部分」偷换成「有」。

### 3.3 正确做法

**同时报两个数**，并说明差异来源：

> 净胜 14 家（按「有+部分」口径）；其中 REAL（证据可复算）的 11 家，
> 另 3 家（ecc/openclaw/hermes）的「领先」依赖 OWN 证据，**未核实**。

## 第 4 步：把审计结论写回台账（可追溯）

### 4.1 每轮必须记录

| 字段 | 内容 |
|---|---|
| **REAL/OWN/NONE 比例** | 本轮实测 |
| **降级的格** | 哪些从「有」改成「部分/无」 |
| **补充的路径** | 哪些格补了真实路径 |
| **口径** | 本轮用的是哪种 |
| **自检结果** | 三段自检是否全过 |

### 4.2 写进台账的样例

> 证据溯源：REAL 62 / OWN 31 / NONE 7（REAL 比例 62%）。
> 本轮降级 3 格（ecc 的 A12 从「有」改「部分」——证据是 OWN）。
> 口径：同时报「有+部分 14 家」与「REAL 11 家」。
> 三段自检：抽取 ✅ / 根目录 ✅ / 键名 ✅。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = REAL 比例上升 + 三段自检全过 + 口径明确
- WARN = 有 OWN 未处理（列出）
- FAIL = 自检 exit 2（工具坏了）/ 有断言无证据 / 口径混用
- UNKNOWN = 对方仓库不可得 / 无法 join

## 假阳性清单（这些不算证据问题）

- 对方仓库是私有/不可得，只能标 UNKNOWN（不是 OWN）
- 证据路径指向对方的文档（文档也是对方仓库的文件，算 REAL）
- 对方能力在多个文件里，指向其中一个就够（只要那个文件确实描述了该能力）
- 证据是截图（若截图来自对方仓库，算 REAL，但要标注来源）

## 假阴性清单（最常漏的 8 类）

1. **只量对手不量自己**（双标）
2. **裸文件名**（`foo.ts` 抽不出路径 ⇒ OWN）
3. **多 package 仓库凭单文件否证**（pi 的 zlib 教训）
4. **口径混用**（「有+部分」当成「REAL」）
5. **自检 exit 2 视而不见**（工具坏了但结论照用）
6. **降级后没重跑 fair-compare**（净胜数不对）
7. **「以后补」的 OWN 格越积越多**（不可复算的断言）
8. **审计结论没写回台账**（下一轮又从头）

## 本仓库可用的命令

```bash
node tools/evolve/audit-evidence-provenance.mjs            # REAL/OWN/NONE 比例
node tools/evolve/audit-evidence-provenance.mjs --strict   # 抽不出路径的格（exit 4）
node tools/evolve/audit-self-claims.mjs                    # 量我方「有」
node tools/evolve/fair-compare.mjs                         # 判定变了要重跑
node tools/evolve/evolve.mjs verify                        # 台账完整性
```

## 与其他技能的关系

- `fair-compare`：审计后判定变了，必须重跑对比
- `code-review`：审我方代码质量（本技能审证据）
- `project-verdict`：项目整体结论依赖证据可信度
- `self-review`：自我复盘的证据同样要能复算
- `doc-write`：审计报告本身也要经 verify-docs

## 边界（如实说清）

- 本技能**不能证明结论正确**，只能证明「证据可复算」；可复算的证据也可能被误读
- 对方仓库不可得时，结论只能是 UNKNOWN（不是 OWN，也不是「无」）
- 「证据路径存在」≠「该能力真的实现」；还需要读代码确认
- 无法审计「我们没写下来的判断」（只审已记录的）
- 本技能不做对比本身（那是 `fair-compare`）
