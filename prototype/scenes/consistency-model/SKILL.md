# 一致性模型 技能

> 「要强一致」这句话在分布式里几乎等于「我要牺牲可用性」。
> 真正要问的是：**这个场景能容忍读到多久以前的数据？**
> 判据：**用户会不会因为读到旧数据而做错决定或受伤害？** 不会的，通常最终一致就够。

## 什么时候用

- 设计读写分离/多副本
- 用户反馈「刚改的数据看不到」
- 要在一致性与性能间取舍

## 什么时候**不**用

- 单机单副本（天然一致）
- 纯分析离线（不需要实时一致）

## 第 1 步：四种一致性模型

| 模型 | 含义 | 代价 | 适用 |
|---|---|---|---|
| **线性一致（强）** | 所有读看到最新已提交写，如同单机 | 最高（要协调/共识） | 余额、库存扣减、分布式锁 |
| **顺序一致** | 所有节点看到相同顺序 | 高 | 有序日志 |
| **因果一致** | 有因果关系的操作保序 | 中 | 评论回复、聊天 |
| **最终一致** | 最终收敛，中间可旧 | 低 | 点赞数、Feed、搜索索引 |

## 第 2 步：会话保证（比全局强一致便宜得多）

很多时候不需要全局强一致，只要**「用户看到自己的操作」**：

| 保证 | 含义 | 代价 |
|---|---|---|
| **读己之写** | 用户读到自己刚写的 | 低（写后读主库/粘会话） |
| **单调读** | 不会读到比之前更旧的数据 | 低（固定副本/版本号） |
| **单调写** | 自己的写按顺序生效 | 低 |
| **读己之写 + 单调读** | 组合，体验最好 | 低 |

⛔ 大多数「读到旧数据」的用户投诉，用「读己之写」就能解决，不必上全局强一致。

## 第 3 步：主从延迟（最常见的坑）

| 场景 | 问题 | 解法 |
|---|---|---|
| 写主库读从库 | 刚写就读从库读不到 | 写后短时读主库 |
| 分片迁移中 | 读旧分片 | 迁移期双写/路由切换 |
| 跨地域复制 | 异地读旧 | 按地域就近读 + 接受延迟 |

## 第 4 步：如何检查（反例驱动）

| 检查 | 反例 |
|---|---|
| 关键写是否走主库 | 扣款后读从库显示旧余额 |
| 幂等与版本 | 重复写导致版本乱 |
| 冲突解决 | 最终一致的并发写谁赢（LWW/向量时钟） |
| 因果 | 回复出现在原帖之前 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 每类数据有明确一致性级别 + 会话保证 + 冲突策略
- WARN = 全用最终一致但没会话保证
- FAIL = 钱/库存用最终一致且无补偿 / 读己之写都没保证
- UNKNOWN = 拿不到副本/读写路径

## 假阳性清单（这些不算「解决了一致性」）

- 全用最终一致
- 有主从但写后读从库
- 没有冲突解决策略

## 假阴性清单（最常漏的 8 类）

1. **钱/库存用最终一致无补偿**
2. **写后读从库**（读不到自己写的）
3. **无单调读**（一会新一会旧）
4. **最终一致无冲突解决**
5. **因果乱序**（回复在原帖前）
6. **跨地域不就近读**
7. **迁移期无路由切换**
8. **把会话保证当全局强一致卖**

## 与其他技能的关系

## 边界（如实说清）

- 强一致有性能和可用性代价，不是默认选项
- 一致性级别是业务决策，需产品参与
- 本技能不实现共识算法，只帮选级别
