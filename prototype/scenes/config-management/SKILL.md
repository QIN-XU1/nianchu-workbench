# 配置管理 技能

> 配置事故的共同点：**改了一个值，不知道影响了哪里，也不知道什么时候生效**。
> 判据：**一个配置项，能不能回答「谁改的、改前是什么、影响哪些服务、怎么回滚」？**

## 什么时候用

- 多环境配置
- 配置散落各处
- 配置改错的故障
- 要灰度改配置

## 什么时候**不**用

- 单一固定常量（直接写死）
- 密钥 → `secrets-management`

## 第 1 步：配置分级（放对地方）

| 类型 | 放哪 | 例子 |
|---|---|---|
| **代码常量** | 代码里 | 不会变的值 |
| **环境配置** | 配置文件/环境变量 | 端口、DB 地址 |
| **动态配置** | 配置中心 | 开关、阈值、限流 |
| **密钥** | 密钥服务 | 密码、token（≠配置） |

⛔ 密钥当普通配置放在配置文件里 = 泄露风险。

## 第 2 步：分层覆盖（环境差异）

```
默认值 → 环境级 → 服务级 → 实例级（后者覆盖前者）
```

| 要求 | 说明 |
|---|---|
| 有默认值 | 缺配置能跑（不是崩） |
| 覆盖可追溯 | 知道最终值来自哪层 |
| 环境隔离 | dev 的配置不能进 prod |

## 第 3 步：验证（配置错了要早发现）

| 检查 | 时机 |
|---|---|
| 类型/范围 | 启动时 |
| 必填项 | 启动时（缺失即 fail fast） |
| 跨字段一致性 | 启动时（如 min<max） |
| 值是否合理 | 启动时（如端口 0-65535） |

⛔ 配置错了但启动成功、运行时才炸 = 最难查。**启动时就校验。**

## 第 4 步：变更安全

| 项 | 要求 |
|---|---|
| 审计 | 谁改的、改前改后、何时 |
| 灰度 | 先小范围生效 |
| 回滚 | 一键回退到上一版 |
| 热更新 | 生效延迟要明确（秒级还是重启） |
| 影响面 | 改这个影响哪些服务 |

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 配置改了要重启才生效但没人知道 | 以为生效了其实没有 |
| 环境变量拼写错 | 静默用默认值 |
| 明文密钥进配置文件 | 泄露 |
| 无默认值 | 缺了直接崩 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 分级合理 + 启动校验 + 变更审计灰度回滚
- WARN = 有配置但无启动校验
- FAIL = 密钥当配置 / 改了不知何时生效 / 无回滚
- UNKNOWN = 拿不到配置文件

## 假阳性清单（这些不算「配置管理好」）

- 配置集中了但改了要重启没人知道
- 有配置但无校验
- 密钥混在配置里

## 假阴性清单（最常漏的 8 类）

1. **密钥当普通配置**
2. **无启动校验**
3. **改配置不知何时生效**
4. **无审计**（不知谁改的）
5. **环境变量拼写错用默认**
6. **无默认值**（缺了崩）
7. **无回滚**
8. **dev 配置进 prod**

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁
```

## 与其他技能的关系

- `secrets-management`：密钥单独管
- `feature-flag`：动态开关
- `ci-pipeline`：配置注入
- `graceful-degradation`：降级配置

## 边界（如实说清）

- 配置中心本身的高可用要保证
- 热更新的语义（何时生效）常被低估
- 本技能不实现配置中心，只设计规则
