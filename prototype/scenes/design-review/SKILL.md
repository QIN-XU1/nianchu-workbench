# 设计评审 技能

> 设计评审不是「这个方案好不好」，而是**「这个方案在什么条件下会不成立」**。
> 说得出「什么条件下它会崩」，才算真的审过；说「我觉得挺好的」等于没审。
> 评审的第一职责不是批准，而是**在动手之前把代价摆到桌面上**。

## 什么时候用

- 有人提了方案要评审（文档、口头、代码骨架都算）
- 自己设计完要自查（自查必须更狠，因为没人反驳你）
- 要在两个方案之间做选择
- 方案已经开始写了，想确认「还要不要继续」

## 什么时候**不**用

- 代码已经写完要审质量 → `code-review`
- 要核对接口兼容性 → `api-contract`
- 要定数据结构细节 → `schema-design`
- 要把决策记录下来 → `adr`（评审通过后写）

## 第 1 步：核对目标（最常见的失败点）

### 1.1 方案解决的是不是「真问题」

问三个问题，答不上来就打回：

| 问题 | 危险信号 |
|---|---|
| 不解决会怎样？ | 「不解决也没啥」→ 可能不是真问题 |
| 现在怎么凑合的？ | 「现在没法做」→ 先确认真的没法做 |
| 谁会因此受益、受益多少？ | 「用户会更爽」→ 太模糊，不可衡量 |

⛔ 最常见的失败：**被「技术先进」吸引**。用 Rust 重写、引入消息队列、上微服务 ——
先问「当前规模需要吗」，而不是「这是不是更先进」。

### 1.2 目标是否可衡量

把目标改写成可验证的形式：

- 差：「提升性能」
- 好：「P95 延迟从 800ms 降到 300ms 以下，在 100 并发下测得」

- 差：「让代码更清晰」
- 好：「新增一个数据源不需要改 3 个文件，只需改 1 个」

判据：**评审结束时，能不能用这个目标判断「做完了没有」？** 不能 → 目标未定义。

### 1.3 检查「方案与目标的匹配度」

| 现象 | 问题 |
|---|---|
| 方案很大，目标很小 | 过度设计（成本远超收益） |
| 方案很小，目标很大 | 可能做不到（低估复杂度） |
| 方案与目标无关 | 答非所问（很常见，且不易发现） |

## 第 2 步：要求列出取舍（没有代价的方案一定有问题）

### 2.1 必须有的三栏

任何方案都要能填出这张表：

| 得到什么 | 付出什么 | 放弃什么 |
|---|---|---|
| 好处 1 | 成本 1（工时/复杂度/依赖） | 原本可以做的事 A |
| 好处 2 | 成本 2（运维/学习曲线） | 原本可以做的事 B |

⛔ **只说好处不提代价 = 可疑**。如果提方案的人说不出代价，通常是他还没想清楚，
而不是「这个方案真的没有代价」。

### 2.2 检查「放弃什么」是否被隐藏

最容易隐藏的是**机会成本**与**锁定成本**：

- 引入新依赖 → 以后升级/替换的锁定
- 新抽象层 → 以后所有人要学的概念
- 新数据格式 → 迁移成本与双写期
- 新服务 → 部署、监控、故障排查的额外面

### 2.3 与「不做」对比

必须回答：**如果什么都不做，会怎样？**

很多时候「不做」是合理选项，而方案文档里从不提它。不提「不做」的方案，
等于假设「必须做」——那个假设本身要接受审查。

## 第 3 步：压测失败模式（这一层最容易被跳过）

### 3.1 五类失败，逐类问

| 类别 | 要问的问题 |
|---|---|
| **输入异常** | 空/超大/超长/非法/类型错时怎样？ |
| **依赖失败** | 网络断、第三方挂了、数据库满了怎么办？ |
| **并发与时序** | 两个请求同时来？重试导致重复执行？ |
| **部分失败** | 批量操作中一半成功，状态一致吗？ |
| **人为误用** | 参数传反、忘记调用、调了两次会怎样？ |

### 3.2 每个失败模式要给出三件事

1. **检测**：怎么知道它发生了？（日志/指标/告警）
2. **降级**：发生时系统退到什么状态？（拒绝服务 / 只读 / 用缓存）
3. **恢复**：怎么回到正常？（重试 / 回滚 / 人工介入）

⛔ 只说「会处理好」不算 —— 要具体到「谁检测、退到什么状态、怎么恢复」。

### 3.3 找「不可恢复」的点

最危险的不是会失败，而是**失败了没法恢复**：

- 数据被覆盖且没有备份
- 迁移做到一半，前后都不一致
- 状态机卡在中间态，既不能前进也不能后退

判据：**能说出「最坏情况是什么，能不能退回来」才算审过失败模式**。

## 第 4 步：找更简单的解法（评审的核心价值）

### 4.1 四个降级方向

按成本从低到高，逐个问「能不能用更低的方案达到同样目标」：

1. **能不能不做**（目标本身可以放弃吗）
2. **能不能手工做**（一次性的事不需要自动化）
3. **能不能用现成的**（已有工具/库/服务）
4. **能不能做小一点**（先做 20% 覆盖 80% 场景）

### 4.2 检查「方案是否可拆」

大方案应该能拆成「先做哪一步就有价值」：

- 不能拆 → 风险集中，一旦中途停就没有产出
- 能拆 → 每步可独立验证、可独立回滚

判据：**能不能在 1/3 的成本处停下来，仍然有可用产出？**

## 第 5 步：给结论（必须可被反驳）

### 5.1 四态判定

| 四态 | 含义 |
|---|---|
| **PASS** | 目标清晰 + 取舍透明 + 失败模式有交代 + 没有更简单解法 |
| **WARN** | 可以继续，但有需补的项（列出具体补什么） |
| **FAIL** | 解决的不是真问题 / 隐藏了代价 / 有致命失败模式无应对 |
| **UNKNOWN** | 信息不足（缺目标、缺约束、缺数据），无法判断 |

⛔ 不许用「我觉得还行」代替四态；也不许因为「方案很大很完整」就给 PASS。

### 5.2 结论必须附「什么条件下会翻」

这是本技能最重要的一条：

> 在 <某个条件> 下，这个结论会翻转。

举例：
> 当前判 PASS，因为目标明确且失败模式有应对。
> **但如果**并发量预期从 100 涨到 10000，现有的单机队列会成为瓶颈，届时需重新评审。

没有这句话的评审，等于宣称「永远成立」——那是不可反驳的，也就没有信息量。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`

**1. 目标核对**
- 真问题？<是/否，依据>
- 可衡量？<改写后的可验证目标>
- 方案与目标匹配？<匹配/过度/不足/无关>

**2. 取舍**
| 得到什么 | 付出什么 | 放弃什么 |
|---|---|---|

- 与「不做」对比：<不做会怎样>
- 隐藏的锁定成本：<依赖/抽象/格式/服务>

**3. 失败模式**
| 类别 | 失败情形 | 检测 | 降级 | 恢复 |
|---|---|---|---|---|

- 不可恢复的点：<有/无，是什么>

**4. 更简单的解法**
- 能不能不做：<>
- 能不能手工：<>
- 能不能用现成：<>
- 能不能做小：<>
- 可拆性：<能否在 1/3 成本处停下仍有产出>

**5. 结论与翻盘条件**
- 判定：<四态>
- 需补的项（WARN 时）：<逐条>
- **什么条件下这个结论会翻**：<必须写>

**6. 判不了的部分**
- <缺什么信息>

## 假阳性清单（这些不是设计缺陷）

- 方案比「理论上最优」差一点，但符合当前团队能力与时间约束
- 用了「不够先进」的技术，但解决了真问题
- 没有做抽象（三次重复才抽象是合理策略）
- 没有写单元测试（方案阶段还没有代码）
- 性能不是最优但满足当前目标

## 假阴性清单（最常漏的 8 类）

1. **目标不可衡量**，评审完也不知道做没做完
2. **只列好处不列代价**，或代价一笔带过
3. **没提「不做」这个选项**
4. **失败模式只说「会处理」，没说到检测/降级/恢复**
5. **没找「不可恢复」的点**（最危险）
6. **没问「能不能更简单」**，直接接受方案规模
7. **没检查可拆性**，导致中途停就没有产出
8. **结论不可反驳**（没有「什么条件下会翻」）

## 本仓库可用的命令

```bash
node tools/quality/size-guard.mjs        # 方案若涉及新增文件，先看体量红线
node tools/evolve/fair-compare.mjs       # 方案涉及「对标领先」时，先看可复算的差距
```

## 与其他技能的关系

- `adr`：评审通过后把决策与理由记录下来
- `refactor-plan`：方案是重构时，转去做分期计划
- `schema-design`：方案涉及数据结构时，转去定字段与约束
- `api-contract`：方案涉及对外接口时，转去核对兼容性
- `code-review`：方案落地成代码后，按五层审
- `evidence-audit`：方案里引用的数据/结论需要复核时用它

## 边界（如实说清）

- 评审质量取决于评审者的经验与领域知识；**同一批人审自己的方案存在共同盲区**
- 无法判断「方案是否真的能实现」——那要靠原型验证
- 组织的政治/时间压力会影响判断，本技能无法消除这一点
- 信息不足时结论只能是 UNKNOWN，**不许用「看起来合理」补上缺失信息**
- 本技能不产出实现方案，只评判已有方案
