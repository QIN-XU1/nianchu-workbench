# 数据保留与删除 技能

> 数据保留的核心矛盾：**「留着可能有用」vs「留着是负债」**。
> 每多留一天数据，就多一天泄露风险、存储成本、合规责任。
> 判据：**每条数据都必须能回答「为什么留、留到什么时候、到期怎么删干净」**，
> 答不出来的就不该留。

## 什么时候用

- 新系统设计存储
- 合规审计前（GDPR/个保法要求「最小必要」「限期存储」）
- 用户要求删除自己的数据
- 存储成本失控

## 什么时候**不**用

- 只是清理一次磁盘 → 直接清
- 要迁移数据 → `data-migration`
- 要设计表结构 → `schema-design`

## 第 1 步：给每条数据定「保留理由」

### 1.1 四类理由

| 理由 | 例子 | 保留期依据 |
|---|---|---|
| **业务必需** | 订单记录 | 业务/税务规定（如税务 7 年） |
| **法律要求** | 审计日志、合同 | 法定期限 |
| **用户同意** | 用户上传的内容 | 「直到用户撤回同意」 |
| **无理由** | 「以后可能有用」 | **← 这条不能留** |

⛔ 「以后可能有用」不是保留理由。它是数据负债的开始。

### 1.2 数据分级

| 级别 | 特征 | 保留策略 |
|---|---|---|
| **敏感** | 身份证/银行卡/密码/生物特征 | 最短必要 + 加密 + 严格审计 |
| **个人** | 手机/邮箱/地址 | 限期 + 脱敏 |
| **业务** | 订单/交易 | 按法定/业务期限 |
| **公开** | 产品目录 | 按需 |

## 第 2 步：定保留期（三类依据）

| 依据 | 怎么定 |
|---|---|
| **法定** | 查法规（税务/金融/医疗各有年限） |
| **业务** | 「多久后客户还会来查」 |
| **技术** | 备份/日志的滚动窗口 |

### 2.1 常见数据的参考保留期

| 数据 | 典型保留 |
|---|---|
| 访问日志 | 30-90 天（安全调查窗口） |
| 应用错误日志 | 30-180 天 |
| 用户行为埋点 | 13 个月（很多分析工具的默认上限） |
| 交易记录 | 按税法（常见 5-10 年） |
| 会话/临时数据 | 几小时到 30 天 |
| 备份 | 按 RPO，滚动删除旧备份 |

⛔ 保留期必须**写到配置里可执行**，不能只是「原则上 90 天」然后没人删。

## 第 3 步：可删性设计（能不能真的删掉）

### 3.1 删除的三个层次

| 层次 | 做法 | 够不够 |
|---|---|---|
| **软删除** | 标记 deleted_at | ❌ 数据还在 |
| **硬删除** | 真删行 | ⚠ 备份和副本里还有 |
| **彻底删除** | 主库+备份+副本+缓存+日志全覆盖 | ✅ |

### 3.2 删除的五个藏身处（最常漏）

| 藏身处 | 是否常被漏 |
|---|---|
| 主数据库 | 会删 |
| **备份** | ⚠ 常漏（备份里还有） |
| **只读副本/从库** | ⚠ 常漏 |
| **缓存（Redis 等）** | ⚠ 常漏 |
| **日志/分析系统** | ⚠ 常漏（埋点里还有） |
| **搜索索引（ES 等）** | ⚠ 常漏 |

⛔ 「我删了数据库」不等于「数据没了」。用户要的是「彻底删除」，而你只删了一个地方。

### 3.3 「被遗忘权」的可执行检查

| 检查 | 判据 |
|---|---|
| 能定位到这个人的所有数据吗？ | 有用户 ID 到各系统的映射 |
| 能在 N 天内完成删除吗？ | 有删除任务与 SLA |
| 能证明删除了吗？ | 有删除审计记录（删了谁、何时、哪些系统） |

## 第 4 步：归档而非删除（当必须留时）

有些数据必须留但不必在线。做法：

| 方式 | 适用 |
|---|---|
| **冷存储** | 很少访问但要留（如历史订单） |
| **脱敏后保留** | 分析用，但去掉个人标识 |
| **聚合后保留** | 只留统计，不留个体 |

⛔ 归档也要有到期时间——归档不是「永久保存」的借口。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 每条数据有保留理由+期限+可执行删除+覆盖藏身处
- WARN = 有数据无明确期限
- FAIL = 敏感数据无限期保留 / 删除漏掉备份副本
- UNKNOWN = 不知道数据分布在哪

## 假阳性清单（这些不算「会删数据」）

- 只有软删除（标记）
- 只删主库不删备份
- 保留期写在文档里但无自动任务
- 归档当永久保存

## 假阴性清单（最常漏的 8 类）

1. **删除漏掉备份**
2. **删除漏掉只读副本**
3. **删除漏掉缓存**
4. **删除漏掉日志/埋点**
5. **软删除当硬删除**
6. **保留期不落到配置/任务**
7. **「以后可能有用」当成保留理由**
8. **归档无到期时间**

## 与其他技能的关系

- `data-migration`：迁移时的数据一致性
- `schema-design`：表结构（本技能管生命周期）
- `inventory-ledger`：数据资产清单（本技能的数据来源）
- `security-review`：敏感数据保护
- `support-assign`：处理用户删除请求的分派

## 边界（如实说清）

- 法定保留期因国家/行业而异，必须查具体法规
- 「彻底删除」在分布式系统里很难证明，只能尽力+审计
- 备份的删除受备份策略制约，可能需要「过期即不留」
- 本技能不实现删除，只设计策略与验证方式
