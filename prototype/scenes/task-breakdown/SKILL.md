# 任务拆解 技能

> 拆解的目的不是「把任务写成一堆小条目」，而是**让每一步都能独立判断「做完了没有」**。
> 判断标准很硬：**拆完之后，任何一个人拿到任一单元，不需要再问「这算完成吗」就能动手。**
> 做不到这一点的拆解，只是把焦虑换了个排版。

## 什么时候用

- 目标太大，不知道从哪开始
- 多人协作，需要分工
- 一个任务做了很久还没结束（说明没拆开）
- 要估算工期（不拆解就无法估算）

## 什么时候**不**用

- 任务本身很小（一两小时能完）
- 目标还不清楚 → 先用 `design-review` 把目标定清
- 是「要不要做」的问题 → 那是决策，不是拆解（用 `adr`）

## 第 0 步：先确认目标可判定

拆解之前必须能回答：**做完之后，怎么知道做完了？**

| 情况 | 处理 |
|---|---|
| 能写出可验证的完成判据 | 可以拆 |
| 只能写出模糊目标（「更好用」） | 先回到 `design-review` |
| 目标本身可能在变 | 先拆到「能验证的那一层」，别往下拆 |

⛔ 目标不清楚时拆解，会把「不清楚」复制到每个单元里。

## 第 1 步：按「可独立验证」切，不按「工作量」切

### 1.1 错误切法 vs 正确切法

| 错误切法 | 为什么错 |
|---|---|
| 「第一步做 30%，第二步做 30%」 | 30% 的工作量无法验证「做完了」 |
| 「先写后端，再写前端」 | 后端写完时无法验证端到端是否通 |
| 「按文件切」（改 A 文件、改 B 文件） | 文件是手段，不是交付物 |

| 正确切法 | 为什么对 |
|---|---|
| 「能让 `GET /status` 返回真实数据」 | 可验证（curl 一下就知道） |
| 「能让界面显示这份数据」 | 可验证（看一眼就知道） |
| 「能在数据缺失时给出明确错误」 | 可验证（构造缺失场景） |

**判据：每个单元的完成状态，能不能用一条命令/一次操作判定？**

### 1.2 切分粒度

| 粒度 | 适用 |
|---|---|
| 半天到两天 | 最佳（可估算、可验证、不易中途放弃） |
| 超过三天 | 太大，继续拆 |
| 小于两小时 | 太小，合并（管理成本超过收益） |

⛔ 粒度不是越细越好：**每个单元都有「描述成本 + 验证成本 + 交接成本」**。

## 第 2 步：每个单元写四件事（缺一不可）

### 2.1 完成判据

必须可观测。写法：

- 差：「实现登录功能」
- 好：「用测试账号能登录，登录后 `/me` 返回该账号信息，密码错误时返回 401 且不建会话」

⛔ 判据里出现「正常」「合理」「完善」这类词，说明还没写清。

### 2.2 依赖

| 依赖类型 | 要写什么 |
|---|---|
| **前置任务** | 必须先完成哪个单元（为什么） |
| **外部条件** | 需要谁提供什么（数据/接口/权限/环境） |
| **假设** | 假设什么成立（若假设不成立会怎样） |

⛔ 依赖不写清，会在执行到一半时才发现被卡住 —— 那时已经浪费了时间。

### 2.3 验证方式

必须写具体命令或操作步骤：

- 差：「跑测试」
- 好：「`node tools/quality/verify-docs.mjs` 返回 exit 0」

### 2.4 失败怎么办

| 情况 | 预案 |
|---|---|
| 验证不通过 | 回滚到哪个状态 |
| 外部依赖没到位 | 降级方案 / 阻塞并上报 |
| 做到一半发现方向错 | 止损点在哪（做到什么程度就该停） |

⛔ 「失败再说」不是预案。

## 第 3 步：标出并行与串行

### 3.1 画依赖关系

用最简形式表达：

　　`A ──→ B ──→ D` ／ `A ──→ C ──→ D`（A 完成后 B、C 可并行；B、C 都完成才能做 D）

含义：A 完成后 B、C 可并行；B、C 都完成后才能做 D。

### 3.2 找「关键路径」

关键路径 = 最长的那条链。它决定总工期。

优化顺序：
1. 缩短关键路径上的单元（拆分/并行化）
2. 关键路径外的单元可以慢一点（有缓冲）

⛔ 在非关键路径上优化，不会缩短总工期。

### 3.3 找「可并行的假串行」

很多「必须先 A 再 B」其实不成立：

| 看起来串行 | 其实可以并行 |
|---|---|
| 先定接口再写实现 | 先定**接口签名**（半小时），然后实现和调用方可并行 |
| 先做后端再做前端 | 后端出 mock 后，前端可先行 |
| 先写文档再写代码 | 先写「怎么用」（接口草案），代码与文档同步演进 |

判据：**问一句「如果反过来做，会怎样？」** 很多顺序假设经不起这一问。

## 第 4 步：排出优先级（不是按顺序，是按价值/风险）

### 4.1 两个维度

| 维度 | 问题 |
|---|---|
| **价值** | 做完这个，用户能用上什么？ |
| **风险** | 这个单元最可能出问题吗？ |

### 4.2 优先做「高风险 + 阻塞别人」的

理由：风险早暴露，代价最小；阻塞别人的先做，避免全员等待。

⛔ 最常见的错误：先做「容易的」建立信心 —— 结果难的留到最后，时间不够。

### 4.3 找「可以先砍掉的」

拆解时就要标：**哪些单元如果不做，目标仍然达成？**

这让你在时间不够时有明确的减法选项，而不是全部做一半。

## 第 5 步：拆完自检

- [ ] 每个单元都有可观测的完成判据
- [ ] 每个单元都有验证方式（命令或步骤）
- [ ] 依赖关系画出来了，没有循环依赖
- [ ] 关键路径识别出来了
- [ ] 找到了至少一个「可并行的假串行」
- [ ] 每个单元都写了失败预案
- [ ] 标出了「可以先砍掉的」
- [ ] 粒度在半天~两天之间（过大拆、过小并）

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 八项自检全过
- WARN = 有单元判据不够可观测（列出）
- FAIL = 有循环依赖 / 无完成判据 / 粒度失控
- UNKNOWN = 目标不可判定，无法拆解

**1. 目标**
- 一句话：<>
- 完成判据：<可观测>

**2. 任务单元**
| # | 单元 | 完成判据 | 依赖 | 验证方式 | 失败预案 | 预估 |
|---|---|---|---|---|---|---|

**3. 依赖图**
　　`A → B → D`（用箭头写清，别画复杂图）

**4. 关键路径**：<A → B → D>（总工期 <>）

**5. 可并行**：<哪些看起来串行其实可并行，理由>

**6. 可砍掉的**：<哪些不做目标仍达成>

**7. 判不了的部分**
- <哪些单元无法估算/无法验证>

## 假阳性清单（这些不是「拆得不好」）

- 单元数少于 5 个（任务本身不大）
- 有些单元预估不准（正常，拆解不保证估算精度）
- 有单元依赖外部团队（不可控，但已标注）
- 关键路径上只有一个单元（串行任务，正常）

## 假阴性清单（最常漏的 8 类）

1. **按工作量切而不是按可验证性切**
2. **完成判据含「正常/合理/完善」**（不可判定）
3. **依赖没写**（执行到一半才发现被卡）
4. **没画依赖图**（看不出并行机会）
5. **没识别关键路径**（优化错地方）
6. **没写失败预案**
7. **没标「可砍掉的」**（时间不够时只能全做一半）
8. **粒度失控**（单元太大做不完 / 太小管不过来）

## 本仓库可用的命令

```bash
node tools/quality/verify-docs.mjs     # 单元涉及文档时的验证
node tools/quality/commit-gate.mjs     # 每个单元完成后跑门禁
```

## 与其他技能的关系

- `design-review`：目标不清楚时先评审
- `refactor-plan`：代码重构的拆解用它（本技能是通用拆解）
- `handoff`：拆完要交给别人时用它
- `release-pipeline`：交付类任务的拆解
- `evidence-audit`：拆解里的「预估」需要复核时用它

## 边界（如实说清）

- 拆解**不能提高**对未知领域的估算精度；新领域仍会估错
- 无法判断「这个单元是否值得做」（那是价值判断，需要业务输入）
- 依赖外部团队的单元无法保证时间
- 目标本身在变时，任何拆解都会很快过期
- 本技能不产出代码，只产出「怎么分工」的判断
