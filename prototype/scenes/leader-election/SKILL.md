# 选主（Leader Election）技能

> 选主的核心难题：**网络分区时，每边都以为自己选出了主 → 双主（split-brain）→ 数据冲突**。
> 判据：**网络分区后，会不会有两个节点同时认为自己是主？**

## 什么时候用

- 定时任务/后台任务只选一个实例执行
- 有主从架构（主写入）
- 需要一个协调者

## 什么时候**不**用

- 无状态服务（不需要主）
- 能用分布式锁解决单个任务（可用锁）

## 第 1 步：选主机制

| 机制 | 说明 |
|---|---|
| **基于分布式锁** | 抢到锁的是主（配合 `distributed-lock`） |
| **基于租约（lease）** | 主需定期续约，不续则失效 |
| **Raft/Paxos** | 共识算法选主（etcd/ZK 内置） |
| **数据库** | 抢一行做「主」标记 |

## 第 2 步：租约与续期（关键）

| 要点 | 说明 |
|---|---|
| 主必须**定期续约** | 证明自己还活着 |
| 续不上 → 主失效 | 别人可竞选 |
| **租约有效期** | 比续约间隔长（容忍抖动） |

⛔ 租约太长：主真挂了要等很久才切换。租约太短：网络抖动就频繁换主。

## 第 3 步：防脑裂（最重要）

| 手段 | 说明 |
|---|---|
| **过半（quorum）** | 只有拿到多数票才能当主（ZK/etcd） |
| **fencing token** | 每次选主递增 token，下游校验（见 `distributed-lock`） |
| **网络分区检测** | 少数派主动让位 |

★ 没有 quorum 或 fencing 的选主，网络分区时**必然可能出现双主**。

## 第 4 步：主的工作与让位

| 要点 | 说明 |
|---|---|
| 主检测自己失去租约 | **主动停止**（别继续写） |
| 主动让位 | 维护时优雅交接 |
| 新人接管 | 从检查点/最新状态继续 |

⛔ 主失去租约但还继续工作 = 双主写冲突。

## 第 5 步：定时任务的特殊处理

| 问题 | 解决 |
|---|---|
| 每个实例都跑定时任务 | 选主后只有主跑 |
| 主切换时重复跑 | 幂等 + 检查点 |
| 错过的任务 | 补偿机制 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 租约续期 + quorum/fencing + 失租即停
- WARN = 有选主但无 fencing
- FAIL = 无 quorum（可能双主）/ 失租还继续 / 无续约

## 假阳性清单（这些不算「选主安全」）

- 抢到锁就当主但无续约
- 无 quorum（分区双主）
- 失租还继续

## 假阴性清单（最常漏的 8 类）

1. **无 quorum**（分区双主）
2. **无 fencing**
3. **无续约**（死主不失效）
4. **失租还继续写**
5. **租约太短**（频繁换主）
6. **租约太长**（切换慢）
7. **定时任务不幂等**（切换重复）
8. **无让位**（维护难）

## 与其他技能的关系

- `distributed-lock`：选主的实现基础
- `consistency-model`：双主的数据冲突
- `distributed-transaction`：主从写
- `idempotency-design`：切换重试

## 边界（如实说清）

- 强一致的选主需要共识算法（ZK/etcd）
- 单机无法提供真正的选主
- 本技能不实现，只设计
