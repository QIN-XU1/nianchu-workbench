# 数据结构设计 技能

> 结构设计的错误代价最高：代码可以重构，**数据一旦写进去就很难改**。
> 所以本技能的顺序是固定的：**先想清楚事实是什么（实体/关系）→ 再想约束 → 再想查询 → 最后才想迁移**。
> 反过来（先定字段再想关系）几乎必然导致冗余与不一致。

## 什么时候用

- 新增需要持久化的数据
- 改现有结构（加字段、拆表、改约束）
- 两份数据对不上，怀疑结构设计有问题
- 要判断「同一事实是不是存了两份」

## 什么时候**不**用

- 只是内存里的临时对象 → 不需要本技能
- 已定结构，要核对调用方是否兼容 → `api-contract`
- 要迁移已有数据（结构已定）→ `data-migration`

## 第 1 步：实体与关系（先想事实，不想字段）

### 1.1 列出「名词」= 候选实体

从需求里把名词挑出来，问三个问题：

| 问题 | 意义 |
|---|---|
| 它有独立的生命周期吗？（能单独创建/删除） | 有 → 是实体 |
| 它需要被单独查询吗？ | 需要 → 是实体 |
| 它只在某个父对象里存在吗？ | 是 → 可能是字段或子表 |

⛔ 不要因为「看起来像一张表」就建表 —— 实体必须有独立身份。

### 1.2 定关系与基数

| 关系 | 怎么存 | 常见错误 |
|---|---|---|
| 一对一 | 同一行，或两张表共享主键 | 拆成两张表但没约束，导致有 A 没 B |
| 一对多 | 多的一方存外键 | 一方存数组（更新时整数组重写，并发丢数据） |
| 多对多 | 中间表（含两侧外键 + 关系自身的字段） | 中间表漏了关系属性（如「加入时间」「角色」） |

⛔ 一对多里「一方存数组」是最常见的坑：它把关系塞进一个字段，导致
「查某子项属于谁」需要全表扫描，且并发更新会互相覆盖。

### 1.3 找「同一事实」（单一权威源判定）

对每个事实问：**这个值能不能从别处算出来？**

- 能算出来 → **派生**，不存（或存成缓存并标明可重建）
- 不能算出来 → **权威源**，只存一份

本仓库实例：记忆条目的「有效状态」（fresh/superseded/expired）不单独存，
而是由 `expiresAt` 与 `supersededBy` **算出来**（`effectiveState`）。
存两份必然不一致 —— 一旦算法改了，旧数据的存储值就成了谎言。

⛔ 冗余存两份同一事实 = 迟早不一致。若必须冗余（性能），要写明「谁是权威、怎么重建、多久校验一次」。

## 第 2 步：字段与约束（这一步决定数据质量）

每个字段必须写全五项，缺一项就是设计未完成：

| 项 | 要写清 | 反例 |
|---|---|---|
| 类型 | 具体类型与精度（整数/小数/字符串长度/时间格式） | 「数字」→ 是整数还是浮点？金额用浮点会丢精度 |
| 必填性 | 缺了会怎样（拒绝写入 / 默认值 / 允许为空） | 没写 = 迟早有人写空 |
| 空值语义 | `null` / `空串` / `0` / `[]` 分别代表什么 | 混用导致「查不到」与「值为空」无法区分 |
| 唯一性 | 哪些字段组合必须唯一 | 没唯一约束 = 重复数据 |
| 取值范围 | 枚举值、上下界、格式 | 枚举没约束 = 出现拼错的状态值 |

### 2.1 空值语义（最容易被忽略，代价最高）

必须能区分这四种情况，不许混用：

1. **未知**：还没采集到（如 `lastSeen: null`）
2. **为空**：采集到了，值是空的（如 `items: []`）
3. **零值**：数值上的 0（如 `count: 0`）
4. **不适用**：这个实体没有这个概念（如纯本地仓库的 `remoteUrl: null`）

本仓库实例：`repositoryStatus` 对「非仓库」返回 `clean: null`（不适用），
对「干净仓库」返回 `clean: true`。如果两者都用 `false`，调用方无法区分
「这不是 git 仓库」和「这是仓库但有改动」—— 后续逻辑会走错分支。

### 2.2 时间与金额（两个特殊类型）

- **时间**：统一用 UTC ISO8601 字符串或 epoch 毫秒，**不要混用**；要写清「这是事件时间还是记录时间」
- **金额**：用整数最小单位（分）或定点小数，**不要用浮点**；要写清币种

### 2.3 状态机字段

有状态的实体，必须写出：

- 合法状态集合（枚举）
- 合法转移（哪些状态能到哪些状态）
- 非法转移怎么办（拒绝 / 报错 / 记录并继续）

本仓库实例：`handoff` 的五态不可跳级（verify-handoff 25/25 验证）；
`memory` 的 `effectiveState` 由时间与推翻关系算出，不是手工改。

## 第 3 步：查询反推索引（先想怎么查，再定索引）

### 3.1 列出主要查询（按频率排序）

写成具体形态：

```
Q1（高频）：按 workspaceId 列出最近 50 条会话，按 updatedAt 倒序
Q2（中频）：按 status 统计数量
Q3（低频）：按关键词搜标题
```

### 3.2 每个查询配索引

| 查询形态 | 索引 |
|---|---|
| 等值 + 排序 | 复合索引（等值字段在前，排序字段在后） |
| 范围查询 | 范围字段索引 |
| 多字段 OR | 可能需要多个单列索引 |
| 全文搜索 | 倒排索引 / 外部搜索 |

⛔ 索引不是越多越好：每个索引都会拖慢写入并占空间。**只为真实存在的查询建索引**。

### 3.3 检查「查询能不能被索引覆盖」

写出执行计划（或在小数据上实测）。如果查询需要全表扫描，要么改查询，要么改索引。

## 第 4 步：迁移方案（老数据怎么办）

结构设计必须**同时给出迁移路径**，否则只是纸面设计。

### 4.1 三种迁移策略

| 策略 | 适用 | 风险 |
|---|---|---|
| **原地加字段**（可空 + 默认值） | 新增可选信息 | 低；但旧代码不认新字段 |
| **双写 + 回填 + 切换** | 改字段含义/拆表 | 中；需要回填脚本与校验 |
| **建新表 + 迁移 + 切流量** | 大改结构 | 高；需要回滚预案 |

### 4.2 迁移必须回答的四个问题

1. **老数据怎么处理？**（补默认值 / 保持为空 / 丢弃）
2. **迁移中途能不能读？**（不能读 = 必须停机，要说明窗口）
3. **怎么回滚？**（迁移脚本的反向操作是什么）
4. **怎么验证迁移成功？**（条数一致？抽样比对？校验和？）

### 4.3 破坏性变更的前置条件

删字段/改类型/加唯一约束属于破坏性变更，必须先：

1. 确认没有代码在读旧字段（grep 调用点）
2. 确认新约束在老数据上成立（先跑校验查询）
3. 准备好回滚

## 第 5 步：自检清单（设计完逐条过）

- [ ] 每个实体有独立身份（主键）
- [ ] 每个关系有明确基数，且没有「数组存一对多」
- [ ] 每个事实只有一个权威源；冗余处写明重建方式
- [ ] 每个字段类型/必填/空值语义/唯一性/范围都写清
- [ ] 四种空值语义（未知/为空/零值/不适用）没有混用
- [ ] 时间格式统一，金额不用浮点
- [ ] 状态字段有枚举与合法转移
- [ ] 主要查询都有索引，且不是全表扫描
- [ ] 迁移方案含：老数据处理 / 可读性 / 回滚 / 验证
- [ ] 破坏性变更已确认无旧代码依赖

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 五项自检全过
- WARN = 有未定项（如迁移方案待定）
- FAIL = 存在已知缺陷（冗余无权威源 / 无唯一约束 / 查询无索引）
- UNKNOWN = 主要查询形态不清楚，无法定索引

**1. 实体与关系**
| 实体 | 身份（主键） | 关系 | 基数 |
|---|---|---|---|

**2. 字段定义**
| 字段 | 类型 | 必填 | 空值语义 | 唯一 | 范围/枚举 |
|---|---|---|---|---|---|

**3. 单一权威源判定**
| 事实 | 权威源 | 派生值（如有） | 重建方式 |
|---|---|---|---|

**4. 查询与索引**
| 查询 | 频率 | 形态 | 索引 |
|---|---|---|---|

**5. 迁移方案**
- 策略：<三种之一>
- 老数据：<怎么处理>
- 可读性：<迁移中能否读>
- 回滚：<怎么做>
- 验证：<怎么证明成功>

**6. 判不了的部分**
- <缺什么>

## 假阳性清单（这些不算设计缺陷）

- 单表少量数据没有索引（数据量小，全扫可接受）
- 加了冗余字段但写明了重建方式与校验频率
- 字段用 string 存枚举但加了取值校验
- 没有分表（数据量远未到需要分表）

## 假阴性清单（最常漏的 8 类）

1. **一对多用数组存**（并发丢数据、查询要全扫）
2. **同一事实存两份且没写权威源**
3. **空值语义混用**（`null` 当「为空」用）
4. **金额用浮点**
5. **时间格式混用**（有的 UTC 有的本地时间）
6. **状态字段无枚举约束**（出现拼错的状态值）
7. **索引缺失或建了没用的索引**
8. **没有迁移方案**（结构改了，老数据没管）

## 本仓库可用的命令

```bash
node tools/memory/verify-bulk-corrupt.mjs        # 损坏库必须拒绝而非静默覆盖（数据安全底线）
node tools/quality/audit-doc-numbers.mjs         # 文档里的数字与实测是否一致（结构变了文档要跟上）
```

## 与其他技能的关系

- `data-migration`：结构定完后执行迁移
- `api-contract`：结构变成对外接口后核对兼容性
- `data-reconcile`：两份数据对不上时先查是不是结构冗余导致的
- `code-review`：新结构的读写代码要审
- `adr`：重大结构决策应留决策记录

## 边界（如实说清）

- 本技能给的是**设计判断**，不是性能实测；索引效果要在大数据量上验证
- 数据量很小时「最优结构」与「够用结构」差别不大，不必过度设计
- 迁移方案的正确性依赖对现有数据质量的了解；脏数据会让回填失败
- 拿不到真实查询形态时（不知道该查什么），索引设计只能是猜测，应标 UNKNOWN
- 不覆盖分布式一致性、分库分表等大规模场景
