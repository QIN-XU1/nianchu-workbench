# 缓存策略 技能

> 缓存最容易出的不是「没用缓存」，而是**加了缓存引入三类新故障**：
> 穿透（查不存在的）、击穿（热点过期瞬间）、雪崩（大批同时过期）。
> 判据：**缓存失效的那一刻，数据库会不会被打垮？** 会的，就是没设计好。

## 什么时候用

- 要决定某数据该不该缓存
- 缓存与数据库数据不一致
- 缓存失效引发数据库压力
- 高频读、低频写

## 什么时候**不**用

- 强一致要求（如余额，缓存会害事）
- 数据变化频繁且要实时
- 读本身就不慢

## 第 1 步：先判断「该不该缓存」

| 问题 | 该缓存的信号 |
|---|---|
| 读远多于写？ | 是 |
| 能容忍短暂不一致？ | 是 |
| 计算/查库成本高？ | 是 |
| 数据量可控（放得下）？ | 是 |

⛔ 强一致数据（钱、库存扣减）**不要用缓存做权威源**——缓存只能加速读，不能当账本。

## 第 2 步：三类故障（必防）

### 2.1 穿透（查不存在的数据）

| 问题 | 大量请求查一个不存在的 key → 全打到 DB |
|---|---|
| 防法 | ① 缓存空值（短 TTL）② 布隆过滤器 ③ 参数校验前置 |

### 2.2 击穿（热点 key 过期瞬间）

| 问题 | 一个超热 key 过期 → 瞬间大量请求同时回源 |
|---|---|
| 防法 | ① 互斥锁（只让一个回源，其他等）② 逻辑过期（不设 TTL，后台异步续） |

### 2.3 雪崩（大批 key 同时过期）

| 问题 | 同一时间批量写入的 key 同时到期 → DB 峰值 |
|---|---|
| 防法 | ① TTL 加随机抖动 ② 多级缓存 ③ 熔断降级 |

⛔ TTL 全用同一个值 = 定时炸弹。

## 第 3 步：失效策略（四种）

| 策略 | 一致性 | 复杂度 | 适用 |
|---|---|---|---|
| **Cache-Aside**（旁路） | 最终 | 低 | 最常用：读时回填，写时删缓存 |
| **Write-Through**（写穿透） | 较强 | 中 | 写多读少、要求一致 |
| **Write-Behind**（写回） | 弱（有丢失风险） | 高 | 极高写入 |
| **Read-Through** | 最终 | 中 | 读为主 |

### 3.1 Cache-Aside 的正确顺序

```
写：先更新 DB → 再删缓存（不是更新缓存）
读：读缓存 → 未命中 → 读 DB → 回填缓存
```

⛔ 「先删缓存再更新 DB」有并发窗口（删了缓存但 DB 还没更新，别的请求读到旧值回填）。

## 第 4 步：一致性收敛

| 方案 | 说明 |
|---|---|
| **延迟双删** | 更新 DB 后删缓存，延迟再删一次（覆盖并发窗口） |
| **订阅 binlog** | 从 DB 变更日志驱动失效（最可靠） |
| **版本号** | 缓存带版本，写入时递增 |

⛔ 缓存与 DB 的强一致几乎不可能；要问的是「能容忍多久不一致」，而不是「怎么做到强一致」。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 该缓存的判断合理 + 三类故障都防 + 失效顺序正确
- WARN = 缺击穿/雪崩防护
- FAIL = 缓存当权威源 / TTL 无抖动 / 先删缓存再写 DB
- UNKNOWN = 拿不到读写比例

## 假阳性清单（这些不算「缓存设计好」）

- 只加了 Redis 没想失效
- TTL 全同一个值
- 缓存当账本

## 假阴性清单（最常漏的 8 类）

1. **缓存当权威源**（钱/库存）
2. **TTL 无抖动**（雪崩）
3. **热点无互斥**（击穿）
4. **空值不缓存**（穿透）
5. **先删缓存再写 DB**（并发脏读）
6. **缓存与 DB 无收敛机制**
7. **缓存 key 设计无命名空间**（冲突）
8. **无缓存监控**（命中率/内存）

## 边界（如实说清）

- 缓存不能解决写瓶颈，只优化读
- 分布式缓存有一致性问题，单机缓存有容量问题
- 本技能不实现缓存，只设计「要不要/怎么失效/怎么防」
