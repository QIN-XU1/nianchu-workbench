# 健康检查 技能

> 健康检查配错最典型的灾难：**liveness 检查里查了数据库**，数据库抖一下 → 所有实例被判死 → 全部重启 → 雪崩。
> 判据：**依赖挂了的时候，健康检查会不会把你的实例也拖死？**

## 什么时候用

- K8s 探针配置
- 负载均衡健康检查
- 服务自愈

## 什么时候**不**用

- 无编排/无 LB 的单体

## 第 1 步：三种探针各管什么

| 探针 | 回答 | 失败后果 |
|---|---|---|
| **liveness** | 进程还活着吗（要不要重启） | 重启容器 |
| **readiness** | 能接流量吗（要不要摘除） | 从 LB 摘除（不重启） |
| **startup** | 启动完成了吗 | 启动期不执行其他探针 |

⛔ 三者混用 = 该摘除的却重启、该重启的却不重启。

## 第 2 步：各查什么（关键区分）

| 探针 | 该查 | 不该查 |
|---|---|---|
| **liveness** | 进程是否死锁/卡死（只查自己） | **外部依赖**（DB/下游） |
| **readiness** | 能否处理请求（可含关键依赖） | 非关键依赖 |
| **startup** | 初始化完成（加载配置/预热） | 持续依赖 |

★ **liveness 绝不查外部依赖**：DB 挂了是 DB 的事，重启你的进程解决不了，只会让所有实例一起重启。

## 第 3 步：依赖怎么处理

| 依赖 | liveness | readiness |
|---|---|---|
| 数据库 | ❌ 不查 | ⚠ 可查（但要防级联） |
| 缓存 | ❌ | 一般不查（能降级） |
| 下游服务 | ❌ | 谨慎（可能一起雪崩） |

⛔ readiness 查下游也要小心：下游全挂 → 所有实例都 not ready → 整个服务下线。**要区分「我依赖它」和「我离了它不能活」**。

## 第 4 步：探针参数

| 参数 | 考虑 |
|---|---|
| initialDelay / startup | 启动慢的要给足（否则启动期就被杀） |
| periodSeconds | 太频繁增加负担 |
| timeoutSeconds | 别太长 |
| failureThreshold | 连续几次才算失败（防抖动） |

## 第 5 步：端点设计

| 端点 | 用途 |
|---|---|
| /livez | liveness（只查自身） |
| /readyz | readiness（能否接流量） |
| /healthz | 综合（给 LB/人工） |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 三探针分清 + liveness 不查依赖 + 防级联
- WARN = readiness 查了下游但无防级联
- FAIL = liveness 查数据库 / 探针混用 / 无 startup
- UNKNOWN = 拿不到部署配置

## 假阳性清单（这些不算「健康检查对」）

- 有 /health 但什么都查
- liveness 查了数据库

## 假阴性清单（最常漏的 8 类）

1. **liveness 查外部依赖**（级联重启）
2. **readiness 查下游致全下线**
3. **探针混用**
4. **无 startup（慢启动被杀）**
5. **failureThreshold 太低**（抖动重启）
6. **健康检查太重**（拖累自身）
7. **摘除无传播延迟**（配合 graceful-shutdown）
8. **健康端点暴露敏感信息**

## 边界（如实说清）

- 健康检查不能替代监控（它只回答「能不能接流量」）
- 不同编排语义不同（K8s vs 传统 LB）
- 本技能不实现，只设计
