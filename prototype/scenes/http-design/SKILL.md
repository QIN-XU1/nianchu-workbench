# HTTP 接口设计 技能

> 好的 HTTP 接口让「资源、方法、状态码、幂等」各司其职；坏的接口把动作塞进 URL、滥用状态码、搞不清幂等。
> 判据：**一个常见操作，能不能用规范的 HTTP 语义表达清楚，而不是「什么都能 POST」？**

## 什么时候用

- 设计新的 HTTP API
- 接口语义不清/状态码乱用
- 要规范化现有接口

## 什么时候**不**用

- 内部进程调用（非 HTTP）
- 纯 RPC（gRPC/GraphQL 有自己的语义）

## 第 1 步：资源建模

| 原则 | 说明 |
|---|---|
| **用资源而非动作** | `/orders/123` 而非 `/order/123` 或 `/createOrder` |
| 名词复数 | `/orders` 而非 `/order` |
| 嵌套 | `/orders/123/items` 表达从属 |
| 动作类用子资源或 RPC 端点 | `/orders/123/cancel`（动词端点要克制） |

⛔ 全是 `/doXxx` 的 URL = 没按资源建模，等于 RPC 套 HTTP 皮。

## 第 2 步：方法语义（别都用 POST）

| 方法 | 语义 | 幂等 |
|---|---|---|
| GET | 读，不改 | ✅ |
| POST | 创建/操作 | ❌（一般） |
| PUT | 替换（全量） | ✅ |
| PATCH | 部分更新 | ⚠ |
| DELETE | 删除 | ✅ |

★ **读用 GET、写用 PUT/PATCH/POST 按语义**，不是所有操作都 POST。

## 第 3 步：状态码用对

| 场景 | 状态码 |
|---|---|
| 成功读 | 200 |
| 创建成功 | 201（带 Location） |
| 无内容（删除） | 204 |
| 资源不存在 | 404 |
| 未认证 | 401 |
| 无权限 | 403 |
| 参数/请求体错 | 400 / 422 |
| 冲突（已存在/版本） | 409 |
| 限流 | 429 |
| 服务错 | 500 |
| 下游不可用 | 503 |

⛔ 全部返回 200 + `{code: "xxx", msg:"error"}` = 状态码形同虚设（客户端、代理、缓存都识别不了）。

## 第 4 步：幂等

| 操作 | 幂等性 |
|---|---|
| GET/DELETE/PUT | 天然幂等 |
| POST | **需幂等键**（见 `idempotency-design`） |

⛔ 用户重复提交 POST 导致重复下单 = 接口没做幂等。

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 状态码全 200 | 缓存/客户端识别不了 |
| 读走 POST | 不能缓存、不幂等 |
| 动作塞进 URL | 语义乱 |
| 响应体过宽 | 泄露/浪费 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 资源建模 + 方法语义 + 状态码正确 + 幂等
- WARN = 有资源建模但状态码乱用
- FAIL = 全 POST 全 200 / 无幂等 / 动作塞 URL
- UNKNOWN = 拿不到接口定义

**1. 资源**
| 接口 | 资源 | 合理 |
|---|---|---|

**2. 方法**
| 操作 | 方法 | 幂等 |
|---|---|---|

**3. 状态码**
| 场景 | 状态码 |
|---|---|

**4. 判不了的部分**
- <拿不到的接口清单>

## 假阳性清单（这些不算「接口设计好」）

- 全 POST + 全 200
- 读走 POST
- 动作塞进 URL

## 假阴性清单（最常漏的 8 类）

1. **全 200 吞错误**
2. **读用 POST**
3. **动作塞 URL**
4. **POST 不幂等**
5. **状态码与语义不符**（如创建返回 200 而非 201）
6. **命名不一致**（单复数/大小写混用）
7. **响应体过宽**
8. **无统一错误格式**
