# 事后复盘 技能

> 复盘的产物不是「一份检讨」，而是**一组可验证的改进项**。
> 判断标准：**复盘结束后，如果什么都不改，这次复盘就等于没做。**
> 另一条同样重要：**无责** —— 追责会让下一次没人愿意说真话，而真相是复盘唯一的原料。

## 什么时候用

- 出了线上事故（服务挂了/数据错了/发布了坏版本）
- 一个任务严重超期或失败
- 同一个问题反复出现
- 想搞清楚「为什么没早发现」

## 什么时候**不**用

- 事故还在进行中 → 先止损（`debug-repro` / `rollback-plan`）
- 只是单个 bug 定位 → `debug-repro`
- 是「要不要做某决定」→ `adr`

## 第 0 步：先确认「这是不是复盘」

| 特征 | 是复盘 | 不是复盘 |
|---|---|---|
| 目的 | 改进系统 | 找人负责 |
| 语言 | 「什么条件下会发生」 | 「谁干的」 |
| 产出 | 可验证的改进项 | 一份说明 |
| 态度 | 假设人是善意的 | 假设有人失职 |

⛔ 如果开头就问「这是谁的责任」，那就不是复盘，是审判 —— 后面拿不到真信息。

## 第 1 步：时间线（只写事实，不写判断）

### 1.1 时间线的写法

每条只写：**时间 + 观察到什么 + 做了什么**。不写「因为疏忽」「本来应该」。

| 时间 | 事实 | 依据 |
|---|---|---|
| 10:02 | 部署 v2.3 | CI 日志 |
| 10:05 | 错误率从 0.1% 升到 12% | 监控面板 |
| 10:08 | 收到第一条用户反馈 | 工单 #1234 |
| 10:20 | 定位到新版本 | 排查记录 |
| 10:35 | 回滚完成 | 部署日志 |

### 1.2 三个必须标出的时刻

| 时刻 | 为什么要标 |
|---|---|
| **故障开始** | 计算影响时长的起点 |
| **首次发现** | 检测能力的关键指标 |
| **恢复完成** | 影响时长的终点 |

**检测延迟 = 首次发现 − 故障开始**
**恢复延迟 = 恢复完成 − 首次发现**

⛔ 这两个数字比「总时长」更有用：它们分别指向「监控」和「应急」两个不同的问题。

### 1.3 时间线常见缺口

- 只写了「系统侧」时间，没写「人什么时候知道」
- 只写成功路径，没写「试了但没用的方案」
- 时间点靠回忆（应标注「约」或「据 X 记录」）

## 第 2 步：分清「直接原因」与「根因」

### 2.1 三层结构

| 层 | 定义 | 例子 |
|---|---|---|
| **触发** | 直接引发的那一下 | 一次配置改动 |
| **直接原因** | 为什么这一下会造成故障 | 配置没校验，空值被当成 0 |
| **根因** | 为什么这个缺陷能存在并被发布 | 配置改动没有 review，也没有测试覆盖 |

⛔ **只写「触发」是假复盘**（「因为改了配置」）—— 改配置是正常操作，问题在于为什么改配置会出事。

### 2.2 根因的判定方法：连问「为什么」

对直接原因连续问「为什么」，直到遇到**系统性的、可改进的**答案：

　　`配置空值导致崩溃`
　　`→ 为什么空值没被拦住？因为解析函数没校验`
　　`→ 为什么没校验？因为写的时候没想到空值（且没有测试）`
　　`→ 为什么没想到？因为这类配置项没有统一的校验入口`
　　`→ 为什么没有统一入口？因为配置读取散落在各处`
　　`← 这是根因（可改进：统一配置入口）`

⛔ 停在「某人没想到」不是根因 —— 那是人的状态，不是系统的性质。

### 2.3 根因的三条判据

| 判据 | 说明 |
|---|---|
| **可改进** | 能对应到具体改动（加校验/加测试/改结构） |
| **不指向个人** | 「某人疏忽」不是根因 |
| **能解释「为什么没早发现」** | 根因通常同时解释了「缺陷存在」和「没被发现」 |

## 第 3 步：为什么没早发现（这一步最有价值）

### 3.1 检测能力的四个层次

| 层次 | 手段 | 若缺失则 |
|---|---|---|
| 1 | **编译/类型检查** | 明显错误进入运行 |
| 2 | **自动化测试** | 行为错误进入发布 |
| 3 | **监控/告警** | 故障由用户发现 |
| 4 | **人工巡检/反馈** | 故障持续很久才发现 |

对这次事故问：**哪一层本该拦住它，为什么没拦住？**

| 问题 | 指向的改进 |
|---|---|
| 测试没覆盖这个场景 | 补测试（要能「改坏会红」） |
| 有测试但没测到这种输入 | 补边界/反例 |
| 监控没覆盖这个指标 | 加指标 |
| 有告警但没人看到 | 改告警渠道/阈值 |
| 有人看到了但没当回事 | 改流程/权限 |

⛔ 「没早发现」往往比「为什么会坏」更值得改 —— 因为不知道会坏的事永远会有，但**发现能力是通用的**。

## 第 4 步：影响评估（要具体）

### 4.1 四个维度

| 维度 | 要写清 |
|---|---|
| **范围** | 影响了多少用户/多少数据/哪些功能 |
| **时长** | 从故障开始到恢复 |
| **严重度** | 数据丢了？只是慢了？完全不可用？ |
| **可恢复性** | 数据能补回来吗？用户信任能恢复吗？ |

### 4.2 不许模糊

- 差：「影响了部分用户」
- 好：「约 12% 的请求失败（约 3400 次），持续 33 分钟，无数据丢失」

⛔ 「部分」「一些」「若干」在复盘里等于没写。

## 第 5 步：改进项（必须可验证）

### 5.1 每条改进项四个字段

| 字段 | 说明 |
|---|---|
| **改什么** | 具体动作（不是「加强管理」） |
| **怎么验证** | 可执行的检查（命令/指标/演练） |
| **谁负责** | 一个具体的人（不是「团队」） |
| **何时完成** | 日期 |

### 5.2 改进项的三种类型

| 类型 | 例子 | 强度 |
|---|---|---|
| **消除** | 让这类故障不可能发生（去掉该配置项） | 最强 |
| **拦截** | 加校验/加测试，让它到不了生产 | 强 |
| **发现** | 加监控/告警，让它早被发现 | 中 |
| **应急** | 加预案，让它恢复更快 | 弱（但有用） |

⛔ 全部改进项都是「加监控」= 没打算真正修。

### 5.3 改进项要能「被检查」

- 差：「加强配置校验」← 无法验证
- 好：「`parseConfig` 对空值抛错，`verify-config.mjs` 覆盖 5 种空值场景，全过」← 可验证

## 复盘自检

- [ ] 时间线只有事实，没有判断
- [ ] 标出了故障开始/首次发现/恢复完成
- [ ] 算了检测延迟与恢复延迟
- [ ] 区分了触发、直接原因、根因
- [ ] 根因可改进、不指向个人
- [ ] 回答了「为什么没早发现」
- [ ] 影响有具体数字
- [ ] 每条改进项有「怎么验证 + 谁 + 何时」
- [ ] 改进项不全是一类（有消除/拦截，不只是监控）

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 九项自检全过
- WARN = 有改进项无法验证
- FAIL = 时间线含判断 / 根因指向个人 / 没有改进项
- UNKNOWN = 关键事实无法还原

```markdown
# 复盘：<一句话事件名>

## 1. 时间线
| 时间 | 事实 | 依据 |
|---|---|---|

- 故障开始：
- 首次发现：
- 恢复完成：
- **检测延迟**：<> **恢复延迟**：<>

## 2. 原因
- 触发：
- 直接原因：
- 根因：<连问的结果>

## 3. 为什么没早发现
| 本该拦住它的层次 | 为什么没拦住 | 指向的改进 |
|---|---|---|

## 4. 影响
- 范围：<> 时长：<> 严重度：<> 可恢复性：<>

## 5. 改进项
| # | 改什么 | 类型 | 怎么验证 | 谁 | 何时 |
|---|---|---|---|---|---|

## 6. 判不了的部分
- <哪些事实无法还原>
```

## 假阳性清单（这些不算复盘缺陷）

- 根因只有一个（很多事故确实是单点）
- 改进项少于 3 个（如果确实只需要改一处）
- 时间线不精确到秒（如果只能确定到分钟）
- 有的事故没有「为什么没早发现」（如果监控确实报了但处理慢）

## 假阴性清单（最常漏的 8 类）

1. **时间线写判断**（「因为疏忽」）
2. **只写触发，不写根因**
3. **根因指向个人**（「某人没想到」）
4. **没算检测延迟**（错过最重要的改进点）
5. **没回答「为什么没早发现」**
6. **影响用「部分/一些」**
7. **改进项无法验证**（「加强管理」）
8. **改进项全是一类**（全是加监控）

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs        # 改进项落地后跑门禁
node tools/quality/verify-docs.mjs        # 复盘文档本身的一致性
node tools/evolve/evolve.mjs verify        # 改进项记进台账（可追溯）
```

## 与其他技能的关系

- `debug-repro`：单个 bug 的定位（本技能看系统性问题）
- `rollback-plan`：恢复阶段的做法
- `release-gate`：复盘出的门禁缺口补在这里
- `test-writing`：补「本该拦住它」的测试
- `adr`：复盘出的结构性决定留 ADR
- `handoff`：复盘结论要交接给接手的人

## 边界（如实说清）

- 复盘**不能保证同类问题不再发生**，只能降低概率
- 无法还原「当事人当时怎么想的」—— 记忆不可靠
- 无责复盘依赖组织文化；文化不支持时，拿到的信息会失真
- 无法评估「改进项是否会被执行」—— 那需要后续跟踪
- 有些事故的根因在组织/流程层面，超出技术范围
