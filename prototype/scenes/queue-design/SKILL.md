# 队列设计 技能

> 消息队列的可靠性不在「能不能发出去」，而在**三个必答题**：
> 至少一次投递必然重复，你怎么去重？处理失败怎么重试不雪崩？积压了怎么发现？
> 判据：**同一条消息被消费 N 次，结果对不对？** 不对就缺幂等。

## 什么时候用

- 引入消息队列做异步/解耦
- 消息丢失/重复
- 处理失败重试
- 队列积压

## 什么时候**不**用

- 同步调用够用的简单场景（别为了解耦而解耦）
- 强一致要求（队列是最终一致）

## 第 1 步：选投递语义

| 语义 | 会不会丢 | 会不会重复 | 说明 |
|---|---|---|---|
| **至多一次** | 可能丢 | 不重复 | 不重试，最快最不安全 |
| **至少一次** | 不丢 | **一定重复** | 最常用，必须幂等 |
| **恰好一次** | 不丢 | 不重复 | 代价高（事务/两阶段） |

⛔ 「恰好一次」在分布式里很难真做到；多数「exactly-once」是「至少一次 + 消费端去重」。

## 第 2 步：重复处理（至少一次必须面对）

| 手段 | 说明 |
|---|---|
| **幂等消费** | 用消息 ID 去重（配合 `idempotency-design`） |
| **去重表** | 已处理的 message_id 记录 |
| **天然幂等** | 覆盖写而非累加 |

⛔ 消费端不去重 = 至少一次一定会出错。

## 第 3 步：顺序（很多人以为不需要）

| 场景 | 要不要顺序 |
|---|---|
| 同一订单的状态变更 | **要**（先创建后支付） |
| 不同用户的消息 | 通常不要 |

保序的手段：
- 相同 key（如 order_id）路由到同一分区
- 单消费者顺序处理该分区
- 乱序场景用版本号/状态机兜底

⛔ 多分区并行处理同一实体的消息 = 乱序。

## 第 4 步：重试与死信

| 要点 | 做法 |
|---|---|
| **重试次数** | 有限次（如 3-5 次） |
| **退避** | 指数退避 + 抖动（别同时重试） |
| **死信队列** | 超过次数转 DLQ，人工/异步处理 |
| **毒消息** | 一条坏消息不能堵住整个队列 |

⛔ 无限重试 = 一条毒消息堵死队列 + 打爆下游。

## 第 5 步：积压监控（最常漏）

| 指标 | 告警 |
|---|---|
| **积压条数** | 持续增长 |
| **消费延迟** | 最老未消费消息的年龄 |
| **消费速率** | 低于生产速率 |
| **DLQ 数量** | 有任何增长 |

⛔ 只看「生产成功」不看「消费掉没」= 积压到爆才发现。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 语义明确 + 消费幂等 + 顺序保证 + 重试/死信 + 积压监控
- WARN = 缺顺序或积压监控
- FAIL = 至少一次但消费不幂等 / 无限重试 / 无毒消息处理
- UNKNOWN = 拿不到消息模型

## 假阳性清单（这些不算「队列可靠」）

- 生产成功就当消费成功
- 有重试但无限次
- 有毒消息没隔离
- 没看积压

## 假阴性清单（最常漏的 8 类）

1. **至少一次但消费不幂等**
2. **无限重试**（毒消息堵队列）
3. **同实体多分区**（乱序）
4. **无死信队列**
5. **退避无抖动**（重试风暴）
6. **只看生产不看消费**
7. **无积压/延迟监控**
8. **恰好一次当真的**（其实是至少一次）

## 与其他技能的关系

- `idempotency-design`：消费端去重（本技能的搭档）
- `caching-strategy`：异步链路的缓存
- `observability-design`：积压监控
- `rate-limit-design`：削峰与限流

## 边界（如实说清）

- 队列是最终一致，不保证实时
- 恰好一次有性能代价，多数场景用至少一次+去重
- 本技能不实现，只设计可靠性
