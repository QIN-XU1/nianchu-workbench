# 技术债管理 技能

> 「技术债」被滥用的方式：把一切不喜欢的东西都叫技术债，然后要么全还（拖垮交付）、要么全不还（最终重构不动）。
> 判据：**这笔债的「利息」是多少？**（每改这块要多花多少时间/多少 bug）。利息高才值得还。

## 什么时候用

- 要排「先重构哪块」
- 交付压力 vs 质量的权衡
- 新人抱怨代码难改
- 事故后要还债

## 什么时候**不**用

- 具体怎么重构 → `refactor-plan`
- 单次改动 → 直接做

## 第 1 步：识别（什么算技术债）

| 类型 | 例子 |
|---|---|
| **设计债** | 早期设计不支持现在的需求，只能打补丁 |
| **代码债** | 重复代码、超长函数、隐式依赖 |
| **测试债** | 关键路径无测试 |
| **文档债** | 没有文档/文档过期 |
| **依赖债** | 过时依赖、锁死版本 |
| **基础设施债** | 手工部署、无监控 |

⛔ 「代码写得不好看」不一定是债——如果它稳定、好改、无 bug，就不还。

## 第 2 步：量化利息（最关键）

技术债的「利息」= 它给未来带来的持续成本：

| 利息维度 | 怎么估 |
|---|---|
| **改动成本** | 每改这块多花几天 |
| **bug 率** | 这块 bug 占比 |
| **新人上手** | 多久能改这块 |
| **阻碍新功能** | 有多少需求因它做不了 |

★ 没有量化利息的技术债清单 = 一堆「感觉该还」的东西，排不出优先级。

## 第 3 步：分级（四象限）

| | 利息高 | 利息低 |
|---|---|---|
| **改动频繁** | 🔴 立即还 | 🟡 计划还 |
| **改动少** | 🟠 顺手还 | ⚪ 不还（留着） |

⛔ 「改动少 + 利息低」的债不该还——还它没有回报。

## 第 4 步：偿还策略

| 策略 | 适用 |
|---|---|
| **Boy Scout**（顺手改） | 小债，改到时顺手清理 |
| **专项重构** | 大债，单独立项 |
| **绞杀者**（strangler） | 旧系统逐步替换 |
| **冻结** | 不还，但禁止继续恶化（加围栏/告警） |

## 第 5 步：防新债

| 手段 | 说明 |
|---|---|
| 评审拦 | code review 拦住新增重复/隐式依赖 |
| 债务登记 | 明知欠债要记录（不是偷偷欠） |
| 预算 | 每 sprint 留固定比例还债 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 债有利息量化 + 四象限分级 + 有偿还计划
- WARN = 有清单无利息量化
- FAIL = 无优先级 / 把稳定代码当债硬还 / 禁止新债无机制
- UNKNOWN = 拿不到改动频率与 bug 数据

**1. 债务清单**
| 债 | 类型 | 利息（改动成本/bug率） | 改动频率 |
|---|---|---|---|

**2. 四象限**
| 债 | 象限 | 处置 |
|---|---|---|

**3. 偿还计划**
| 债 | 策略 | 何时 |
|---|---|---|

**4. 判不了的部分**
- <拿不到的利息数据>

## 假阳性清单（这些不算「该还的债」）

- 稳定好改无 bug 的「丑代码」
- 没人改的旧模块
- 只是个人偏好

## 假阴性清单（最常漏的 8 类）

1. **不量化利息**
2. **改动少的债也硬还**（无回报）
3. **把稳定代码当债**
4. **无优先级**
5. **偷偷欠债**（不登记）
6. **只还不防**（边还边欠）
7. **大重构不立不变量**
8. **债影响新功能却没算**

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁
```

## 与其他技能的关系

- `refactor-plan`：还债的具体重构计划
- `code-review`：防新债
- `perf-profile`：性能债
- `dependency-audit`：依赖债

## 边界（如实说清）

- 利息是估计值，有主观性
- 有些债永远不该还（可接受的取舍）
- 本技能不重构，只帮排优先级
