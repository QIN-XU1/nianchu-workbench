# 重构计划 技能

> 重构的定义只有一条：**外部行为不变，内部结构改善**。
> 一旦行为变了，那就不是重构，是「改功能 + 改结构」混在一起 —— 出错时无法定位是哪个导致的。
> 所以本技能的每一步都在回答同一个问题：**这一步做完，怎么证明行为没变？**

## 什么时候用

- 代码要动结构，但对外行为必须保持
- 一次性大改风险高，需要分期
- 换实现（换库、换算法、换存储）但调用方不该感知
- 拆文件（单文件太大，撞体量红线）

## 什么时候**不**用

- 行为本来就要改 → 那是功能开发，不是重构
- 只是加注释/改格式 → 直接做
- 要审已完成的改动 → `code-review`
- 要设计新结构 → `schema-design` 或 `design-review`

## 第 1 步：立不变量（没有这一步，重构就是赌博）

### 1.1 什么是不变量

不变量 = **重构前后必须完全一致的可观测行为**。它必须是可测的，不能是「感觉上一样」。

按这五类逐条列出：

| 类别 | 不变量举例 |
|---|---|
| **返回值** | 同样的输入 → 同样的输出（含空值、错误形态） |
| **副作用** | 写哪些文件、写什么内容、顺序是否有关 |
| **错误** | 错误码/错误类型/退出码不变（文案可变） |
| **性能量级** | 不显著变慢（给出可接受阈值，如 <1.2 倍） |
| **对外契约** | 函数签名、API 路径、字段名不变 |

### 1.2 每条不变量必须有「兜住它的东西」

| 兜底手段 | 强度 | 适用 |
|---|---|---|
| 已有测试 | 强 | 首选 |
| 新建表征测试（characterization test） | 强 | 老代码没测试时**必须先建** |
| 手工跑对比脚本 | 中 | 一次性验证 |
| 只靠读代码 | 弱 | **不算兜底** |

⛔ **没有测试兜底就大改 = 赌命**。如果老代码一条测试都没有，第一步不是重构，是补表征测试。

### 1.3 表征测试怎么建（老代码没测试时）

1. 用**当前实现**跑一批真实输入，把输出**存下来**当基线
2. 写测试断言「当前实现 == 基线」
3. 重构后再跑，必须仍然相等
4. 基线要覆盖：正常值、边界值、错误输入

本仓库实例：`verify-git-status.mjs` 用临时 git 仓库造 4 种状态
（干净/未跟踪/已修改/重命名），把「我们的解析结果」与「`git status --porcelain=v1` 原始输出」对拍 ——
这就是表征测试：不关心内部怎么实现，只要求与权威源一致。

## 第 2 步：分期（每步只做一类改动）

### 2.1 六类改动，一次只做一类

| 类型 | 例子 | 为什么不混做 |
|---|---|---|
| **改名** | 变量/函数/文件重命名 | 纯机械，出错一眼可见 |
| **搬移** | 把函数从 A 文件挪到 B 文件 | 不动逻辑，diff 应只有移动 |
| **抽函数** | 从长函数里切出一段 | 不改行为，只改组织 |
| **换实现** | 换算法/换库 | 行为应等价，需强验证 |
| **改接口** | 改参数形状 | 影响调用方，要单独一步 |
| **删旧路径** | 移除兼容层/旧代码 | 必须最后做 |

⛔ 混做（如「一边改名一边换算法」）会导致 diff 巨大且无法判断哪处引入问题。

### 2.2 排序原则

1. **先立不变量与测试**（第 1 步）
2. **先做纯机械的**（改名、搬移）—— 风险最低
3. **再做结构性的**（抽函数）
4. **然后做换实现** —— 风险最高，放中间（前后都有测试保护）
5. **最后删旧路径** —— 确认无人使用后再删

### 2.3 每步的规模上限

| 指标 | 建议上限 | 理由 |
|---|---|---|
| 单步改动行数 | ≤ 300 行 | 超过难以一次审清 |
| 单步涉及文件 | ≤ 10 个 | 超过难以一次验证 |
| 单步耗时 | ≤ 半天 | 超过容易中途放弃留下半成品 |

超过上限就再拆。**宁可 10 个小步，不要 1 个大步。**

## 第 3 步：每步的验证（这一步不能省）

每一步完成后，必须跑并记录：

| 检查 | 怎么验 |
|---|---|
| 不变量保持 | 跑第 1 步列的测试，全绿 |
| 没有新增问题 | 跑相关验证脚本，记录通过数 |
| 构建/编译通过 | 语法检查、类型检查 |
| 体量没有失控 | 单文件体量红线（本仓库 32KB） |

⛔ 「跑了一下没问题」不算 —— 要贴出**通过数**与**退出码**。

### 3.1 每步一个提交

要求：

- 一个提交 = 一个步骤 = 一类改动
- 提交信息写清「这一步做了什么、为什么、验证结果」
- 出问题能单独 `git revert` 这一步而不影响其他步

⛔ 多步混在一个提交里，等于放弃了回滚能力。

## 第 4 步：清理旧路径（最后一步，且必须确认无人使用）

### 4.1 删除前必须证明「没人用」

```bash
grep -rn "旧函数名\|旧文件路径" --include=*.mjs --include=*.js --include=*.ts .
```

三个容易漏的地方：

1. **前端编译产物**里的调用（源码已删但 bundle 还在用）
2. **测试文件**里的调用（删了源码测试会红）
3. **文档/脚本/CI** 里的调用（README 示例、部署脚本）

判据：**能列出「0 处引用」的证据**（grep 输出为空）才允许删。

### 4.2 保留兼容层时必须有退出条件

如果暂时不能删（外部调用方还没迁），要写明：

- 兼容层何时删（日期或条件）
- 谁负责删
- 怎么确认可以删

⛔ 没有退出条件的兼容层会永久存在，最终两套逻辑都腐化。

## 第 5 步：收尾验证（整体，不是单步）

全部步骤做完后，还要做一次整体检查：

1. **全量测试**：不只跑改动相关的，跑全部
2. **端到端**：真实调用链路跑一遍（单测过 ≠ 端到端过）
3. **体量与结构**：目标结构是否达成（比如「单文件 < 10KB」）
4. **文档同步**：架构图/文档里的路径是否要更新

本仓库踩过：`git_get_file_content` 单测全过，但通过 WS 传参时失败 ——
因为 `pickPath` 把 `path` 当仓库路径。**单测和端到端各有一半盲区。**

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 计划完整（不变量可测 + 每步可独立验证回滚）
- WARN = 有不变量无法兜住（列出哪些）
- FAIL = 没有测试兜底 / 行为与结构混做
- UNKNOWN = 拿不到调用点或行为基线

**1. 不变量清单**
| 类别 | 不变量 | 兜底手段 | 强度 |
|---|---|---|---|

**2. 分期计划**
| 步 | 类型（改名/搬移/抽函数/换实现/改接口/删旧） | 改什么 | 规模 | 验证方式 |
|---|---|---|---|---|

**3. 每步的验证与回滚**
- 验证命令：<具体命令>
- 回滚方式：<git revert 哪一步>

**4. 旧路径清理**
- 引用检查结果：<grep 输出>
- 兼容层退出条件：<有/无，是什么>

**5. 整体收尾**
- 全量测试：<通过数>
- 端到端：<结果>
- 文档同步：<需要改什么>

**6. 判不了的部分**
- <缺什么>

## 假阳性清单（这些不算重构失败）

- 文件名变了但所有引用已同步更新
- 函数内部实现完全重写但测试全绿
- 代码行数增加（抽函数会增加行数，但结构更清晰）
- 性能略有变化但在阈值内

## 假阴性清单（最常漏的 8 类）

1. **没有不变量清单就直接改**（改完无法证明行为没变）
2. **老代码没测试就开始大改**（赌命）
3. **重构与改行为混在一个提交里**
4. **一步改太多文件**（无法定位问题）
5. **每步没验证，攒到最后一起跑**（问题归因困难）
6. **删旧路径前没 grep 全仓**（漏掉 bundle/测试/文档）
7. **兼容层没有退出条件**（永久双套逻辑）
8. **只跑单测没跑端到端**（层间契约不一致查不出）

## 本仓库可用的命令

```bash
node tools/quality/size-guard.mjs          # 单文件体量红线（拆文件时看这个）
node tools/quality/commit-gate.mjs         # 每步提交前跑门禁
node tools/quality/scan-silent-catch.mjs   # 搬移代码时别把空 catch 一起搬
```

## 与其他技能的关系

- `test-writing`：第 1 步补表征测试时用它（重点是「改坏必须红」）
- `code-review`：每步提交前按五层审
- `api-contract`：改动涉及对外接口时，先核对兼容性
- `schema-design`：涉及数据结构变化时先定结构
- `data-migration`：涉及存量数据时先出迁移方案
- `release-gate`：整体完成后跑发布门禁

## 边界（如实说清）

- 重构**不能提升**未被测试覆盖的行为质量 —— 没测到的部分改坏了也发现不了
- 表征测试只能守住「当前行为」，如果当前行为本身是错的，重构会把它固化下来
- 分期计划的步数受时间压力影响；被压缩时风险会集中到少数大步骤
- 换实现的「性能等价」很难严格证明，通常只能给量级阈值
- 拿不到调用点清单（动态调用、闭源调用方）时，删旧路径的结论只能是 UNKNOWN
