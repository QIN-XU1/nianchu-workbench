# WebSocket 设计 技能

> WebSocket 的坑都在「长连接」上：**连接会断（网络/重启/空闲超时）、多实例难广播、消息可能丢**。
> 判据：**断线重连后，用户会不会丢消息？多实例时消息能送达每个连接吗？**

## 什么时候用

- 实时推送/聊天/协作
- 需要服务端主动推
- 低延迟双向

## 什么时候**不**用

- 一次性请求（用 HTTP）
- 只需服务端→客户端（SSE 更简单）

## 第 1 步：先问会不会用 SSE

| 需求 | 选择 |
|---|---|
| 只要服务端→客户端 | **SSE**（更简单，走 HTTP） |
| 要双向 | WebSocket |
| 高频双向 | WebSocket |

⛔ 只需单向推送却用 WebSocket = 过度（SSE 更简单可靠）。

## 第 2 步：心跳保活（防中间层超时断）

| 项 | 说明 |
|---|---|
| 心跳 ping/pong | 定期，防空闲超时 |
| 间隔 | 小于中间层超时 |
| 检测死连接 | 超时未 pong 则关 |

⛔ 无心跳 = 中间层（LB/代理）认为空闲超时断开 = 连接老断。

## 第 3 步：断线重连（客户端）

| 项 | 要求 |
|---|---|
| 自动重连 | 指数退避（防风暴） |
| 重连后状态 | 补拉断线期间的消息 |
| 消息去重 | 重连可能重复 |

★ 重连后要**补消息**（用 last message id 拉断线期间的），否则丢消息。

## 第 4 步：水平扩展（最难）

| 问题 | 解决 |
|---|---|
| 用户在实例 A，消息从 B 发 | 需要**跨实例广播**（Redis pub/sub/消息队列） |
| 连接粘性 | 或按用户路由到固定实例 |
| 广播风暴 | 发布订阅而非全连 |

⛔ 单实例存活连接有上限，多实例时「消息从别的实例推给用户」必须跨实例转发。

## 第 5 步：消息可靠性

| 项 | 处理 |
|---|---|
| 消息顺序 | 同一连接保序 |
| 消息不丢 | ack + 重发（如需要） |
| 消息不重 | 幂等/去重 |
| 背压 | 发送队列有上限（见 `backpressure`） |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 心跳 + 重连补消息 + 跨实例广播 + 背压
- WARN = 有连接但无心跳/重连补消息
- FAIL = 无心跳（老断）/ 多实例无广播 / 无背压
- UNKNOWN = 拿不到实时需求

## 假阳性清单（这些不算「WebSocket 好」）

- 有连接无心跳
- 多实例无广播
- 重连不补消息

## 假阴性清单（最常漏的 8 类）

1. **无心跳**（中间层超时断）
2. **重连不补消息**（丢）
3. **多实例无跨实例广播**
4. **无背压**（发送队列爆）
5. **单向用 WebSocket**（该用 SSE）
6. **无去重**（重连重复）
7. **连接数无上限**
8. **无死连接检测**
