# 熔断器 技能

> 熔断的价值：下游已经挂了，你还在拼命调它 = 把资源耗在必然失败上 + 拖垮自己。
> 但阈值配错会「误熔断」（下游好好的却被熔断）。
> 判据：**下游挂了的时候，你的系统是快速失败还是被拖死？**

## 什么时候用

- 调用下游/第三方
- 防雪崩
- 下游不稳定

## 什么时候**不**用

- 无下游的纯计算服务
- 只做重试 → `retry-strategy`

## 第 1 步：三态状态机

| 状态 | 行为 |
|---|---|
| **Closed（闭合）** | 正常放行，统计失败率 |
| **Open（断开）** | 直接失败（不调用下游） |
| **Half-Open（半开）** | 放少量试探请求 |

```
Closed --失败率达阈值--> Open
Open --等待窗口到--> Half-Open
Half-Open --试探成功--> Closed
Half-Open --试探失败--> Open
```

## 第 2 步：阈值（配错就误熔断）

| 参数 | 考虑 |
|---|---|
| **统计窗口** | 滚动窗口（如 10s） |
| **最小请求数** | 太少样本不熔断（如 <10 个不判） |
| **失败率阈值** | 如 50% |
| **熔断时长** | 断开后多久进半开（如 30s） |
| **半开试探数** | 放几个（如 3 个） |

⛔ 没有「最小请求数」= 深夜 1 个失败就熔断。

## 第 3 步：什么算「失败」

| 算失败 | 不算失败 |
|---|---|
| 超时 | 4xx（业务错误，下游是好的） |
| 5xx（下游错） | 明确的业务拒绝 |
| 连接失败 | |

⛔ 把 4xx 算失败 = 用户输错密码就把熔断器打开。

## 第 4 步：与重试/降级的配合（顺序很重要）

| 组合 | 正确顺序 |
|---|---|
| 熔断 + 重试 | 重试在熔断内侧（熔断开着就不重试） |
| 熔断 + 降级 | 熔断开 → 走降级（返回缓存/默认） |
| 熔断 + 限流 | 都防过载，但对象不同（限流防自己被打，熔断防下游被打） |

⛔ 熔断开了还重试 = 白重试。

## 第 5 步：按实例还是按接口熔断

| 粒度 | 适用 |
|---|---|
| 按接口 | 某接口坏了不影响其他 |
| 按下游 | 整个下游挂了统一熔断 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 三态 + 合理阈值（含最小请求数）+ 失败定义正确 + 与重试降级配合
- WARN = 有熔断但无最小请求数
- FAIL = 4xx 算失败 / 熔断开着还重试 / 无半开
- UNKNOWN = 拿不到下游调用

## 假阳性清单（这些不算「有熔断」）

- 只判失败次数不判率
- 无最小请求数（深夜误熔断）
- 4xx 算失败

## 假阴性清单（最常漏的 8 类）

1. **无最小请求数**（少样本误熔断）
2. **4xx 算失败**
3. **无半开**（断了不起来）
4. **熔断开着还重试**
5. **熔断无降级**（只是变报错）
6. **阈值拍脑袋**（不压测）
7. **粒度太粗**（一个接口坏全熔断）
8. **熔断状态无监控**

## 与其他技能的关系

- `retry-strategy`：重试在熔断内侧
- `graceful-degradation`：熔断后降级
- `rate-limit-design`：限流防自己被打
- `observability-design`：熔断状态监控

## 边界（如实说清）

- 熔断会牺牲功能（快速失败），是取舍
- 阈值需要真实流量校准
- 本技能不实现，只设计
