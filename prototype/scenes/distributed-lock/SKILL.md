# 分布式锁 技能

> 分布式锁最大的坑：**锁超时了但业务没做完** → 第二个进程进来 → 两个同时跑。
> 更隐蔽的：**GC 停顿让持锁进程「假死」**，锁过期，别人拿到，老进程恢复后也以为自己持锁。
> 判据：**持锁进程暂停了（GC/网络/卡顿）之后，锁还能保证互斥吗？**

## 什么时候用

- 防并发重复执行（定时任务、秒杀扣减）
- 临界区只能一个进程进
- 分布式环境下的互斥

## 什么时候**不**用

- 能用唯一约束/乐观锁解决（优先，更简单）
- 单进程（用本地锁）

## 第 1 步：先问「能不能不用分布式锁」

| 场景 | 更简单的方案 |
|---|---|
| 防重复插入 | 唯一索引 |
| 防重复执行 | 幂等键 + 状态机（见 `idempotency-design`） |
| 库存扣减 | 数据库行锁/乐观锁 |

⛔ 分布式锁是重武器，能用数据库约束解决就别上。

## 第 2 步：选实现

| 实现 | 优点 | 缺点 |
|---|---|---|
| **Redis SETNX + 过期** | 快 | 过期即失效（GC 停顿会丢锁） |
| **Redis Redlock** | 多节点 | 有争议（依赖时钟） |
| **ZooKeeper/etcd** | 会话机制、可靠 | 重、依赖 ZK |
| **数据库行锁/唯一** | 简单、强 | 性能、锁范围 |

## 第 3 步：三个必解问题

### 3.1 锁超时 vs 业务耗时

| 问题 | 解法 |
|---|---|
| 业务比锁 TTL 久 | **看门狗续期**（后台定期延长 TTL） |
| 续期进程挂了 | TTL 到期释放（最终一致） |

### 3.2 释放别人的锁

| 问题 | 解法 |
|---|---|
| A 的锁过期，B 拿到，A 恢复后删锁删了 B 的 | **锁带唯一标识**（value=owner id），删除时校验是不是自己的 |

⛔ `DEL lockkey` 无条件删 = A 可能删掉 B 的锁。必须 `if value==mine then del`（Lua 原子）。

### 3.3 脑裂 / 假死（最致命）

持锁进程「假死」（GC/网络分区），锁过期，别人拿到，老进程恢复后**不知道锁已丢**，继续操作共享资源。

**唯一可靠解：fencing token**。

| 机制 | 说明 |
|---|---|
| 每次加锁返回**递增 token** | 如 ZK 的 zxid / Redis INCR |
| 下游存储校验 token | 只接受「比上次见过更大的 token」的写 |

```
锁1 → token=33 写存储（存记录 last=33）
锁过期，锁2 → token=34 写存储（34>33，接受，last=34）
锁1 恢复，想写 token=33（33<34，拒绝！）
```

⛔ 没有 fencing token 的分布式锁，在假死场景下**无法真正互斥**。这是很多人不知道的。

## 第 4 步：Redlock 的争议（要知道）

Redlock 依赖「各节点时钟大致同步 + 网络延迟远小于 TTL」。在时钟漂移或长 GC 时不可靠。Martin Kleppmann 与 antirez 的著名争论核心：**Redlock 解决不了 fencing 问题**。需要强一致就用 etcd/ZK。

## 假阳性清单（这些不算「安全锁」）

- 有 SETNX 但无条件 DEL
- 有 TTL 无续期（长业务会丢锁）
- 无 fencing（假死不安全）

## 假阴性清单（最常漏的 8 类）

1. **无条件 DEL**（删别人的锁）
2. **业务超 TTL 无续期**
3. **无 fencing token**（假死不互斥）
4. **无 owner 校验**
5. **Redlock 当绝对可靠**
6. **锁范围过大**（性能）
7. **续期进程与主进程共命运**
8. **能用唯一约束却上分布式锁**
