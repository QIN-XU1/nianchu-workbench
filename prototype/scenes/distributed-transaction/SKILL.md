# 分布式事务 技能

> 分布式事务的核心矛盾：**CAP 决定了强一致和可用性不可兼得**。
> 所以真正要回答的不是「怎么做到 ACID」，而是**「能容忍什么样的中间态，以及中间态怎么收拾」**。
> 判据：**在任意一步崩溃后，数据最终能收敛到正确状态吗？**

## 什么时候用

- 一个业务跨多个服务/库写
- 扣款成功但扣库存失败
- 要保证「要么都成要么都不成」

## 什么时候**不**用

- 单库单表（用本地事务）
- 可以重构成单库（优先重构，而不是上分布式事务）
- 只读

## 第 1 步：先判断「是不是真需要分布式事务」

| 情况 | 处理 |
|---|---|
| 能放一个库 | **用本地事务**（最简单） |
| 能改成异步最终一致 | 优先（大多数业务可接受） |
| 必须强一致 | 才考虑 2PC/TCC |

⛔ 大量「分布式事务」需求其实是「表设计/服务划分」没做好。先问「能不能不跨服务」。

## 第 2 步：五种方案对比

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|---|---|---|---|---|
| **2PC**（两阶段提交） | 强 | 差（锁到提交） | 中（需协调者） | 跨库强一致、短事务 |
| **TCC**（Try-Confirm-Cancel） | 较强 | 中 | 高（每服务写三个接口） | 金融、资源预留 |
| **Saga**（长事务补偿） | 最终 | 好 | 中（每步有补偿） | 长流程、微服务 |
| **本地消息表** | 最终 | 好 | 低 | 本服务写 + 发消息 |
| **对账补偿** | 最终 | 好 | 低（但要兜底） | 数量型、可事后修 |

## 第 3 步：各方案的关键陷阱

### 3.1 2PC

| 陷阱 | 后果 |
|---|---|
| 协调者挂了 | 参与者锁住资源等它恢复（阻塞） |
| 第二阶段部分失败 | 已提交的无法回滚（数据不一致） |
| 长事务 | 锁持有久，吞吐低 |

⛔ 2PC 的「阻塞」是致命的：协调者宕机能让整个系统卡住。

### 3.2 TCC

| 阶段 | 要做 | 陷阱 |
|---|---|---|
| **Try** | 预留资源（冻结） | 要幂等；预留要能超时释放 |
| **Confirm** | 确认使用预留 | 必须幂等（可能重复调用） |
| **Cancel** | 释放预留 | 必须幂等；空回滚（Try 没执行就 Cancel）要处理 |

⛔ TCC 三接口都要幂等，且要处理「空回滚」「悬挂」（Cancel 先于 Try 到）。

### 3.3 Saga

| 要点 | 说明 |
|---|---|
| 正向步骤 | 每步一个操作 |
| **补偿步骤** | 每步一个反向操作（不是回滚，是业务补偿） |
| 失败 | 逆序执行补偿 |

⛔ 补偿不等于「撤销」：发了的短信补偿不了，只能发「更正」。**补偿必须是业务上可接受的**。

### 3.4 本地消息表

| 步骤 | 说明 |
|---|---|
| 1 | 本地事务里：业务写 + 消息写（同一库，原子） |
| 2 | 独立进程扫消息表，投递到 MQ |
| 3 | 消费方幂等消费 |

⛔ 关键是「业务与消息在同一本地事务」，否则消息会丢或重复。

### 3.5 对账补偿

| 要点 | 说明 |
|---|---|
| 定时对账 | 定期比对两边状态 |
| 发现差异 | 修或告警 |
| 兜底 | 对不清的手工处理 |

⛔ 对账是最后一道防线，不是主方案——它假定已经有差异了。

## 第 4 步：中间态设计（最容易被忽略）

每个方案都会经历「中间态」。必须定义：

| 问题 | 例子 |
|---|---|
| 中间态对其他读可见吗？ | 冻结中的余额算不算可用 |
| 中间态能停留多久？ | 预留超时多久释放 |
| 中间态崩溃怎么恢复？ | 定时任务扫描悬挂事务 |
| 中间态怎么让用户理解？ | 「处理中」状态 |

⛔ 不设计中间态 = 系统一卡，用户看到「钱扣了但没到账」，客服被打爆。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 方案合理 + 每步幂等/补偿 + 中间态定义 + 兜底对账
- WARN = 有方案但中间态未定义
- FAIL = 该用本地事务却上分布式 / 补偿不可行 / 无对账兜底
- UNKNOWN = 拿不到服务边界

## 假阳性清单（这些不算「解决了分布式事务」）

- 用了 TCC 但接口不幂等
- Saga 补偿是「删掉」但已发外部通知
- 有 2PC 但协调者单点
- 只靠对账（那是事后修）

## 假阴性清单（最常漏的 8 类）

1. **能用本地事务却上分布式**
2. **TCC 接口不幂等**
3. **未处理空回滚/悬挂**
4. **Saga 补偿不可行业务**（发了的通知撤不回）
5. **本地消息不由同事务写入**（消息丢）
6. **中间态未定义**（用户看到一半）
7. **无兜底对账**
8. **2PC 协调者单点阻塞**

## 边界（如实说清）

- 真正的强一致跨服务几乎必然牺牲可用性
- TCC/Saga 的复杂度高，团队要能维护
- 本技能不实现框架，只设计一致性方案
