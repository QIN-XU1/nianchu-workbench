# SLO 设计 技能

> SLO 最常见的错：**定一个 99.99% 但没有对应的成本与流程**。
> 99.99% 意味着一年只能挂 52 分钟，需要多活+冗余+演练，成本是 99.9% 的几十倍。
> 判据：**这个 SLO 数字，你愿意为它付出的成本和流程跟得上吗？** 跟不上就是自欺。

## 什么时候用

- 定义服务的可靠性目标
- 要在稳定性与发布速度间权衡
- 多团队要对齐「多可靠才算够」

## 什么时候**不**用

- 内部玩具服务（不需要正式 SLO）
- 只查一次故障 → `postmortem`

## 第 1 步：SLI（先选对指标）

SLI = 实际测量值。要好测量、贴近用户感受。

| 服务类型 | 好的 SLI | 差的 SLI |
|---|---|---|
| 请求型 | 成功请求比例 / 延迟分位 | CPU 使用率 |
| 数据处理 | 处理时延 / 新鲜度 | 队列长度 |
| 存储 | 读写可用性 / 持久性 | 磁盘 IOPS |

⛔ 用「资源指标」（CPU/内存）当 SLI = 测的是机器不是用户体验。

## 第 2 步：SLO（定目标）

| 可用性 | 年停机 | 月停机 | 成本量级 |
|---|---|---|---|
| 99% | 3.65 天 | 7.2 小时 | 低 |
| 99.9% | 8.76 小时 | 43 分钟 | 中 |
| 99.99% | 52.6 分钟 | 4.3 分钟 | 高 |
| 99.999% | 5.26 分钟 | 26 秒 | 极高 |

⛔ 每加一个 9，成本指数上升。**没有业务理由的 99.99% 是浪费**。

## 第 3 步：错误预算（SLO 的真正价值）

错误预算 = 100% − SLO。

| SLO | 错误预算（月） |
|---|---|
| 99.9% | 43 分钟不可用 |

**用途**：
- 预算没用完 → 可以激进发布
- 预算耗尽 → **冻结发布，优先稳定性**

⛔ SLO 不用错误预算驱动流程 = 只是一个好看的仪表盘，没有约束力。

## 第 4 步：测量口径（最容易含糊）

| 项 | 要说清 |
|---|---|
| 分母 | 哪些请求算（内部/健康检查排不排） |
| 分子 | 什么算「好」（多快算快） |
| 时间窗 | 滚动 28 天 vs 自然月 |
| 聚合 | 按服务/接口/地域 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = SLI 贴近用户 + SLO 有成本理由 + 错误预算驱动发布 + 口径清楚
- WARN = 有 SLO 但没接错误预算流程
- FAIL = 用资源指标当 SLI / SLO 无成本依据 / 口径含糊
- UNKNOWN = 拿不到流量与错误数据

|---|---|---|

## 假阳性清单（这些不算「有 SLO」）

- 用 CPU 当 SLI
- 有 SLO 数字但没错误预算流程
- 定 99.99% 但没有对应架构

## 假阴性清单（最常漏的 8 类）

1. **资源指标当 SLI**
2. **SLO 无成本依据**
3. **不接错误预算流程**
4. **分母含健康检查**（虚高可用性）
5. **时间窗含糊**
6. **只定总 SLO 不分接口**
7. **SLO 从不复盘调整**
8. **多团队 SLO 冲突**

## 与其他技能的关系

- `observability-design`：SLI 的数据来源
- `incident-comms`：预算耗尽时的事故沟通
- `postmortem`：超预算后的复盘
- `graceful-degradation`：保 SLO 的降级手段

## 边界（如实说清）

- SLO 是内部目标，SLA 是对外承诺（SLO 应严于 SLA）
- 用户感知的可靠性取决于最弱一环（依赖也要算）
- 本技能不采集数据，只定指标与流程
