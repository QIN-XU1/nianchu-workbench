# 事件驱动架构 技能

> 事件驱动最容易被滥用：把「调用」包装成「事件」但其实还是要同步结果，反而更复杂。
> 判据：**发布者真的不关心谁消费、也不等结果吗？** 关心或要等，就不是事件驱动。

## 什么时候用

- 多消费者关心同一件事
- 要解耦发布/订阅
- 审计/回放需求（事件溯源）

## 什么时候**不**用

- 需要同步结果（用调用）
- 单一消费者且要即时结果

## 第 1 步：先分清「事件」vs「命令」

| 类型 | 语义 | 例子 |
|---|---|---|
| **事件**（Event） | 已发生的事实（过去式） | OrderPlaced（订单已下单） |
| **命令**（Command） | 请求做某事（祈使） | PlaceOrder（请下单） |

⛔ 把命令叫成事件（`PlaceOrderEvent`）= 混淆。事件是「已发生」，命令是「请去做」。

## 第 2 步：事件契约（最易漏）

| 项 | 要求 |
|---|---|
| **不可变** | 事件是事实，不能改 |
| **版本** | 事件 schema 演进要兼容 |
| **自包含** | 带足够信息，消费者不用回调 |
| **唯一 ID** | 去重 |
| **时间戳** | 排序/审计 |

⛔ 事件里只放一个 ID，消费者还得回调查详情 = 没解耦。

## 第 3 步：事件溯源（Event Sourcing，慎用）

| 概念 | 说明 |
|---|---|
| 存事件而非状态 | 状态 = 重放所有事件 |
| 优点 | 完整历史、可回放、可审计 |
| 代价 | 复杂、查询难、快照 |

⛔ 事件溯源不是银弹。大多数系统「存状态 + 发事件通知」就够，不必溯源。

## 第 4 步：最终一致

| 问题 | 处理 |
|---|---|
| 事件延迟 | 接受最终一致 |
| 重复消费 | 幂等（见 `idempotency-design`） |
| 顺序 | 按 key 分区保序（见 `queue-design`） |
| 失败 | 重试+死信 |

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 事件当同步 RPC 用 | 复杂且慢 |
| 事件不含足够信息 | 消费者反复回查 |
| 事件契约无版本 | 消费者崩 |
| 无消费幂等 | 重复副作用 |
| 事件风暴 | 循环事件 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 事件/命令分清 + 契约自包含 + 最终一致处理 + 幂等
- WARN = 有事件但契约不自包含
- FAIL = 命令当事件 / 事件当同步 RPC / 无幂等

## 假阳性清单（这些不算「事件驱动」）

- 命令叫成事件
- 事件当同步调用
- 事件只放 ID 要回调

## 假阴性清单（最常漏的 8 类）

1. **命令当事件**
2. **事件当同步 RPC**
3. **事件不自包含**（要回调）
4. **契约无版本**
5. **无幂等**（重复）
6. **无序**（同实体乱序）
7. **循环事件**（A→B→A）
8. **盲目上事件溯源**

## 与其他技能的关系

- `queue-design`：事件的传输
- `idempotency-design`：消费幂等
- `distributed-transaction`：Saga 用事件
- `consistency-model`：最终一致

## 边界（如实说清）

- 事件驱动增加调试难度（链路长）
- 事件溯源维护成本高
- 本技能不实现，只设计
