# 测试替身（Mock）技能

> 替身用错的两个极端：**过度 mock**（测了个寂寞，真实 bug 没测到）和 **不 mock**（依赖外部，慢且脆）。
> 判据：**这个 mock 是为了隔离外部，还是为了绕开难测的真实逻辑？** 后者危险。

## 什么时候用

- 测试依赖外部服务/DB/时间
- 要隔离慢/不稳定的依赖
- 构造边界（错误/超时）

## 什么时候**不**用

- 被测逻辑本身简单（直接用真的）

## 第 1 步：分清替身类型

| 类型 | 说明 |
|---|---|
| **Stub** | 返回固定值 |
| **Mock** | 断言「被调用过」 |
| **Fake** | 轻量真实实现（如内存 DB） |
| **Spy** | 记录调用 |

## 第 2 步：mock 的边界（只 mock 外部，不 mock 被测逻辑）

| 该 mock | 不该 mock |
|---|---|
| 外部 HTTP/第三方 | 被测的核心业务逻辑 |
| 数据库（用 fake 更好） | 同模块内的纯函数 |
| 时间/随机 | 被测对象本身 |

⛔ mock 掉被测逻辑 = 测试通过但什么都没测。

## 第 3 步：过度 mock 的危害

| 问题 | 后果 |
|---|---|
| mock 了太多 | 测试只验证「调用了 mock」 |
| mock 与真实行为不符 | 假绿（真实会崩） |
| 改真实实现 mock 不更新 | 测试失去意义 |

★ 优先 fake（内存实现）而非 mock 交互——fake 更接近真实。

## 第 4 步：契约对齐

mock 的返回要符合真实接口契约（见 `contract-test`），否则「mock 说成功、真实失败」。

## 第 5 步：何时必须用真依赖

集成测试/端到端要至少有一层用真依赖，否则永远测不出集成 bug。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 只 mock 外部 + fake 优先 + 契约对齐 + 有真集成层
- WARN = mock 较多但合理
- FAIL = mock 被测逻辑 / 与真实不符 / 全 mock 无集成
- UNKNOWN = 拿不到测试结构

## 假阳性清单（这些不算「测试有效」）

- mock 了被测逻辑
- mock 与真实不符
- 全 mock 无集成

## 假阴性清单（最常漏的 8 类）

1. **mock 被测逻辑**
2. **mock 与真实契约不符**
3. **全 mock 无集成层**
4. **过度断言 mock 调用**
5. **mock 时间不一致**
6. **fake 与真实行为偏差**
7. **改实现 mock 不更新**
8. **无错误/超时 mock**
