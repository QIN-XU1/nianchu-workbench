# 规则引擎 技能

> 规则引擎适合「规则多且频繁变」的场景；但硬套规则引擎会给简单逻辑增加复杂度。
> 判据：**规则改一次要发版吗？规则冲突时谁赢说得清吗？**

## 什么时候用

- 规则多、频繁变（风控/定价/审批）
- 业务人员要能改规则
- 规则要可审计

## 什么时候**不**用

- 规则少且稳定（用代码 if 更简单）

## 第 1 步：规则表达

| 方式 | 适用 |
|---|---|
| 决策表 | 多条件组合（可读） |
| DSL | 表达力强 |
| 表达式字符串 | 灵活但要防注入 |

⛔ 规则用字符串 eval = 注入风险 + 难测。用受控 DSL。

## 第 2 步：冲突与优先级

| 问题 | 处理 |
|---|---|
| 多规则同时命中 | **明确优先级** |
| 优先级相同 | 定义顺序（后覆盖/先赢） |
| 冲突检测 | 静态检查互斥规则 |

⛔ 不定义优先级 = 结果取决于执行顺序 = 不确定。

## 第 3 步：可测试

| 项 | 要求 |
|---|---|
| 规则单测 | 每条规则有正反例 |
| 决策表覆盖 | 每格可测 |
| 回归 | 改规则跑全量 |

## 第 4 步：可审计

| 项 | 要求 |
|---|---|
| 版本 | 规则有版本（见 `audit-log`） |
| 生效记录 | 谁改的、何时生效 |
| 决策追踪 | 这次为什么这样判（命中哪条） |

## 第 5 步：性能与安全

| 项 | 说明 |
|---|---|
| 规则数量 | 多时用索引/Rete 算法 |
| 表达式安全 | 禁任意代码执行 |
| 循环 | 规则互相触发要防 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 受控表达 + 优先级明确 + 可测 + 可审计
- WARN = 有规则但冲突未定义
- FAIL = 字符串 eval / 无优先级 / 无版本
- UNKNOWN = 拿不到规则集

**1. 表达**
| 项 | 方式 |
|---|---|

**2. 优先级**
| 情况 | 处理 |
|---|---|

**3. 审计**
| 项 | 有吗 |
|---|---|

**4. 判不了的部分**
- <拿不到的规则>

## 假阳性清单（这些不算「规则引擎」）

- 字符串 eval 当规则
- 无优先级
- 规则无版本

## 假阴性清单（最常漏的 8 类）

1. **字符串 eval**（注入/难测）
2. **无优先级**（结果不定）
3. **冲突未检测**
4. **无版本**（改了什么不知）
5. **无决策追踪**（不知命中哪条）
6. **规则无单测**
7. **规则互相触发循环**
8. **性能无优化**（规则多慢）

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁
```

## 与其他技能的关系

- `audit-log`：规则变更审计
- `config-management`：规则配置
- `test-strategy`：规则测试
- `workflow-engine`：规则驱动流程

## 边界（如实说清）

- 规则引擎有学习/维护成本
- 复杂逻辑仍需代码
- 本技能不实现，只设计
