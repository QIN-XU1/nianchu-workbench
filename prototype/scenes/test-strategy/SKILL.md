# 测试策略 技能

> 测试最常见的两个极端：**什么都测**（慢、脆、维护成本高）和**几乎不测**（一改就崩）。
> 判据不是「覆盖率多少」，而是：**改动时，你会不会因为怕改坏而不敢动？**
> 会，说明关键路径没测住。

## 什么时候用

- 新项目定测试方案
- 覆盖率上不去但不知测哪
- 测试太慢/太脆
- 要决定「这个功能测到什么程度」

## 什么时候**不**用

- 写具体某个测试 → `test-writing`
- 只查一次测试是否通过 → 直接跑

## 第 1 步：分层（金字塔，不是冰淇淋）

| 层 | 数量 | 速度 | 测什么 |
|---|---|---|---|
| **单元** | 多 | 快（毫秒） | 纯逻辑、边界、计算 |
| **集成** | 中 | 中（秒） | 组件间、DB、外部桩 |
| **端到端** | 少 | 慢（分钟） | 关键用户旅程 |

⛔ 「冰淇淋」反模式：大量 E2E（慢脆）+ 少量单元 → 反馈慢、维护贵。应是金字塔。

## 第 2 步：每层测什么（分工）

| 层 | 适合测 | 不适合测 |
|---|---|---|
| 单元 | 分支、边界、错误处理、纯函数 | 网络、DB（要用桩） |
| 集成 | 契约、序列化、SQL、事务 | 完整 UI 流程 |
| E2E | 登录→核心操作→结果 | 每个分支（太贵） |

## 第 3 步：哪些必须测（优先级）

**必须测**（不测就是风险）：
- 涉及钱/权限/数据安全的逻辑
- 复杂条件分支（边界、并发）
- 曾经出过 bug 的地方（回归）
- 核心用户旅程

**可以不测**：
- 纯 getter/setter
- 一次性脚本
- 框架已保证的部分（不必重测框架）

⛔ 追求「100% 覆盖率」= 大量低价值断言（测 getter、测框架）拉低性价比。

## 第 4 步：覆盖率怎么用（不要当目标）

| 用法 | 对/错 |
|---|---|
| 看「哪些关键路径没覆盖」 | ✅ 用作发现盲区 |
| 当 KPI 追求数字 | ❌ 会导致刷覆盖率 |
| 100% 才算合格 | ❌ 不现实且有害 |

★ 真正看的不是覆盖率，是**变异测试**（故意改坏代码，看测试能否抓住）。

## 第 5 步：测试质量（能抓住 bug 吗）

| 反模式 | 问题 |
|---|---|
| 只测 happy path | 抓不到错误处理 bug |
| 断言太弱（只测不抛异常） | 没验证结果对不对 |
| 测试互相依赖 | 单独跑就挂 |
| 测实现细节 | 重构就得改测试 |
| 脆弱（依赖时间/随机） | 抖动 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 金字塔分布 + 关键路径有测 + 断言有效
- WARN = 覆盖率有但关键路径无测
- FAIL = 冰淇淋反模式 / 只 happy path / 关键逻辑无测
- UNKNOWN = 拿不到代码与测试

## 假阳性清单（这些不算「测试好」）

- 覆盖率 100% 但测的是 getter
- 有大量 E2E 但慢且脆
- 只测 happy path

## 假阴性清单（最常漏的 8 类）

1. **冰淇淋反模式**（E2E 太多）
2. **只测 happy path**
3. **断言太弱**（不验证结果）
4. **关键路径无测**（钱/权限）
5. **把覆盖率当 KPI**
6. **测实现细节**（重构就挂）
7. **脆弱测试**（时间/随机）
8. **无回归测试**（同 bug 反复）

## 本仓库可用的命令

```bash
node tools/quality/commit-gate.mjs   # 提交前门禁（含变异残留检查）
```

## 与其他技能的关系

- `test-writing`：写具体测试（本技能定策略）
- `ci-pipeline`：测试在 CI 中跑
- `debug-repro`：bug 复现后补回归测试
- `refactor-plan`：重构前立不变量测试

## 边界（如实说清）

- 测试不能证明无 bug，只能证明测过的路径对
- 覆盖率是必要不充分
- 本技能不写测试，只定策略
