# 依赖注入（DI）技能

> DI 的本质是「依赖从外部传入，而非内部 new」，让代码可替换、可测试。
> 判据：**想测一个类，能不能不启动真实依赖就注入它的替身？**

## 什么时候用

- 代码耦合难测
- 依赖需要替换/管理生命周期
- 大型应用组件管理

## 什么时候**不**用

- 小脚本（手工 new 即可，DI 是过度设计）

## 第 1 步：三种注入方式

| 方式 | 说明 |
|---|---|
| **构造注入**（推荐） | 依赖通过构造函数传入 |
| 属性注入 | 设属性（可选依赖） |
| 方法注入 | 每次调用传入 |

⛔ 构造注入最清晰、最可测；避免服务定位器（隐藏依赖）。

## 第 2 步：作用域与生命周期

| 作用域 | 说明 |
|---|---|
| 单例 | 全局一个 |
| 请求 | 每请求一个 |
| 瞬态 | 每次 new |

紧耦合生命周期的坑：单例依赖请求作用域对象 = 生命周期错误。

## 第 3 步：服务定位器是反模式

| 反模式 | 问题 |
|---|---|
| `container.get('x')` 到处调 | 依赖隐藏、难测、难追踪 |

★ 显式构造注入 > 服务定位器。

## 第 4 步：避免把 DI 当目标

| 过度 DI | 问题 |
|---|---|
| 什么都注入 | 配置爆炸 |
| 接口套接口 | 难懂 |
| 简单值也注入 | 过度设计 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 构造注入 + 生命周期清晰 + 无服务定位器
- WARN = 有 DI 但生命周期混乱
- FAIL = 服务定位器 / 依赖隐藏 / 不可测
- UNKNOWN = 拿不到代码

## 假阳性清单（这些不算「好 DI」）

- 服务定位器当 DI
- 生命周期混乱
- 过度注入

## 假阴性清单（最常漏的 8 类）

1. **服务定位器**（隐藏依赖）
2. **生命周期错误**（单例依赖请求）
3. **依赖隐藏**（内部 new）
4. **接口套接口**（难懂）
5. **过度注入**（配置爆炸）
6. **循环依赖**
7. **全局状态**
8. **不可独立测**
