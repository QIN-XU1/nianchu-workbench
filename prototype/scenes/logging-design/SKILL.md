# 日志设计 技能

> 日志的两个失败：**记太多**（噪音+贵，真问题淹了）和**记太少**（出事了查不到）。
> 判据：**线上出问题时，靠日志能不能还原发生了什么？**

## 什么时候用

- 设计日志规范
- 日志太多/太乱
- 排障查不到信息

## 什么时候**不**用

- 纯本地脚本

## 第 1 步：结构化（最重要的基础）

| 项 | 要求 |
|---|---|
| 格式 | JSON（可查询聚合） |
| 时间戳 | 统一时区（UTC） |
| **trace id** | 串起一次请求（见 `observability-design`） |
| 关键字段 | 服务/级别/事件/耗时 |

⛔ 纯文本日志 `log("出错")` = 无法查询、无法聚合、无法关联。

## 第 2 步：级别用对

| 级别 | 记什么 | 生产默认 |
|---|---|---|
| ERROR | 需人介入 | 开 |
| WARN | 可自愈异常 | 开 |
| INFO | 关键状态变迁 | 开 |
| DEBUG | 详细过程 | 关（用时开） |
| TRACE | 极详细 | 关 |

⛔ 生产打 DEBUG = 日志爆 + 贵 + 慢。

## 第 3 步：采样与保留

| 项 | 策略 |
|---|---|
| 高频日志 | 采样（如 1%） |
| 慢请求 | 全记 |
| 保留期 | 按需（见 `data-retention`） |
| 分级存储 | 热查最近，冷归档 |

## 第 4 步：脱敏（合规红线）

| 不能进日志 | 处理 |
|---|---|
| 密码/密钥 | 不记或打码 |
| 身份证/手机号/银行卡 | 掩码 |
| 完整请求体 | 脱敏后记 |

⛔ 密钥进日志 = 泄露（见 `secrets-management`）。

## 第 5 步：「记了但查不到」的坑

| 坑 | 后果 |
|---|---|
| 无 trace id | 串不起来 |
| 时间戳不一致 | 对不齐 |
| 字段名不统一 | 查不全 |
| 日志分散多系统 | 拼不起来 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 结构化 + trace id + 级别对 + 脱敏 + 可查
- WARN = 有结构无 trace id
- FAIL = 纯文本 / 密钥进日志 / 生产 DEBUG / 无脱敏
- UNKNOWN = 拿不到日志配置

## 假阳性清单（这些不算「日志好」）

- 有日志但纯文本
- 无 trace id
- 全打 DEBUG

## 假阴性清单（最常漏的 8 类）

1. **纯文本日志**
2. **无 trace id**
3. **密钥/隐私进日志**
4. **生产 DEBUG**
5. **时间戳不一致**
6. **字段名不统一**
7. **无采样**（高频爆）
8. **无保留策略**

## 边界（如实说清）

- 日志成本随量线性涨
- 结构化有格式开销（但值得）
- 本技能不实现，只设计
