# 运维手册（Runbook）技能

> Runbook 的唯一验收标准：**凌晨 3 点、半睡半醒、不是原作者的人，能不能照着它把事办了？**
> 所以每条步骤必须是**一条可复制的命令**，不是「检查一下服务状态」。
> 另一条：**每条告警必须有一条 runbook**。没有 runbook 的告警等于「叫醒你却不说怎么办」。

## 什么时候用

- 新增一个告警（必配套 runbook）
- 一次故障复盘后（把当时怎么救的写下来）
- 交接班前
- 值班手册初始化

## 什么时候**不**用

- 要设计告警本身 → `observability-design`
- 事故进行中的沟通 → `incident-comms`
- 事故后的深度复盘 → `postmortem`

## 第 1 步：一条 runbook 对应一条告警

### 1.1 结构

　　告警名：<与告警系统里完全一致>
　　含义：<这个告警说明发生了什么>
　　影响：<用户可感知的影响>
　　紧急度：P0/P1/P2
　　第一步：<立即执行的一条命令>

⛔ 告警名必须**一字不差**匹配监控系统——否则出事时搜不到。

## 第 2 步：步骤必须「可复制执行」

### 2.1 每条步骤的三个要求

| 要求 | 反例 | 正例 |
|---|---|---|
| **一条命令** | 「看看服务是否正常」 | `curl -f http://127.0.0.1:8080/health` |
| **有预期输出** | 「确认返回值」 | 「返回 200 且 body 含 "ok"」 |
| **有失败分支** | （无） | 「若超时 → 跳到步骤 4」 |

### 2.2 分支结构（不能只有一条直线）

　　步骤 1：查进程在不在
　　  ├─ 在 → 步骤 2（查健康检查）
　　  └─ 不在 → 步骤 5（重启）
　　步骤 2：健康检查
　　  ├─ 200 → 步骤 3（抽查核心功能）
　　  └─ 非 200 → 步骤 4（看日志找原因）

⛔ 只写「成功路径」的 runbook，第一步分支就卡住。

## 第 3 步：必含「回滚 / 止血 / 升级」三条出口

| 出口 | 什么时候 |
|---|---|
| **止血** | 先让用户不受影响（切流量/降级/回滚） |
| **升级** | 15 分钟没解决 → 叫谁（写具体人/群） |
| **记录** | 边救边记时间线（给复盘用） |

⛔ 没有「15 分钟没搞定叫谁」，值班的人会一直硬扛到天亮。

## 第 4 步：判定 runbook 质量（五问）

| 问题 | 不合格的样子 |
|---|---|
| 命令能直接复制吗？ | 「检查磁盘」 |
| 有预期输出吗？ | 「确认成功」 |
| 有失败分支吗？ | 只有一条路径 |
| 有升级联系人吗？ | 「联系相关同事」 |
| 非原作者能执行吗？ | 用了只有作者懂的缩写 |

## 第 5 步：验证 runbook（不能只写不测）

### 5.1 三种验证

| 方法 | 做法 |
|---|---|
| **桌面推演** | 找没写它的人，按步骤做一遍（不实际操作） |
| **演练** | 在测试环境真的执行一遍 |
| **故障复盘校准** | 每次真实故障后，看 runbook 哪一步不准 |

⛔ 从不演练的 runbook = 假设，不是手册。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 每条告警有 runbook + 步骤可复制 + 有分支/升级 + 演练过
- WARN = 有 runbook 但未演练
- FAIL = 告警无 runbook / 步骤不可执行
- UNKNOWN = 拿不到告警清单

**告警 → runbook 映射**
| 告警名 | 有 runbook？ | 紧急度 |
|---|---|---|

**单条 runbook 模板**
　　## <告警名>
　　- 含义：
　　- 影响：
　　- 紧急度：

　　### 步骤
　　1. <命令>
　　   - 预期：<输出>
　　   - 失败 → <跳到哪>
　　2. ...

　　### 止血
　　<切换/回滚/降级的命令>

　　### 升级
　　- 15 分钟未解决 → <具体人/群>

　　### 记录
　　- 开一个时间线记录：<在哪记>

**判不了的部分**
- <哪些告警的处置方式不清楚>

## 假阳性清单（这些不算「有 runbook」）

- 只有一句「重启服务」
- 步骤不可复制（「检查一下」）
- 没有失败分支
- 没有升级路径
- 从没演练过

## 假阴性清单（最常漏的 8 类）

1. **步骤不可执行**（描述性而非命令）
2. **无预期输出**（不知做对了没）
3. **无失败分支**
4. **无升级联系人**
5. **无止血手段**（只会重启）
6. **无记录**（复盘时没有时间线）
7. **告警名与监控系统不一致**
8. **从不演练**

## 与其他技能的关系

- `observability-design`：告警从哪来
- `incident-comms`：出事后怎么对外说
- `postmortem`：事后复盘并更新 runbook
- `rollback-plan`：止血常是回滚
- `handoff`：交接班时把未结的 runbook 传下去

## 边界（如实说清）

- Runbook 覆盖不了未预见的故障
- 命令依赖环境；换环境要重新验
- 演练有成本，不可能每次都全量演练
- 本技能不设计告警，只写「告警后怎么做」
