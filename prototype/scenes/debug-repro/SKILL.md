# 复现与定位 技能

> 调试的目标不是「让它不报错」，而是**能说清它为什么错，并且能证明修好了**。
> 「改完看起来好了」是最危险的中间态：它既可能是真修好，也可能是把错误挪到了别处。

## 什么时候用

- 有 bug 要定位根因
- 报告说「偶发」「有时会」「重试就好了」
- 改完想确认「真的修好了」而不是「这次没触发」

## 什么时候**不**用

- 需求本身不清楚 → 先 `design-review` 或 `adr`
- 是审查别人的改动 → `code-review`
- 要补测试但根因已知 → `test-writing`

## 第 0 步：先判定「这是不是真 bug」

在动手之前，先回答三件事，答不上来就别急着改：

| 问题 | 答不上来意味着 |
|---|---|
| 期望行为是什么？（写下来，可验证） | 你可能在修「不符合个人偏好」，不是 bug |
| 实际行为是什么？（贴输出，不转述） | 你在凭印象调试 |
| 差异在哪个观察点被看到？（日志/退出码/返回值） | 你不知道该在哪里下断点 |

⛔ 不许把「我觉得应该这样」当期望行为 —— 期望必须能指到规格/文档/用户原话。

## 第 1 步：复现（这一步没做，后面全是猜）

### 1.1 写出可复算的复现步骤

必须是**别人照着做能复现**的，包含四要素：

```
1. 环境：操作系统 / 运行时版本 / 关键依赖版本
2. 前置状态：数据文件内容、目录结构、环境变量
3. 命令或操作序列：（逐条，可直接复制）
4. 观察到的输出：（完整贴出，含退出码）
```

自检：**换一个人（或换一台机器）照这个步骤做，会不会得到同样的输出？** 不会就还没写完。

### 1.2 判定稳定性：跑 3 次

　　`for i in 1 2 3; do <命令>; echo "exit=$?"; done`

| 结果 | 判定 | 下一步 |
|---|---|---|
| 3/3 都失败 | **稳定复现** | 直接进最小化 |
| 有失败有成功 | **偶发** | 走 1.3 |
| 0/3 失败 | **复现失败** | 走 1.4，不许开始改代码 |

### 1.3 偶发 bug：先找触发条件，别急着改

偶发几乎总是「某个状态/时序/顺序」在变。按这四类逐个排查：

1. **状态残留**：上一次运行的缓存/临时文件/数据库行是否影响本次？
   → 试着「干净状态下跑」vs「跑过一次后再跑」
2. **时序/并发**：是否两个操作同时发生？文件锁、连接池、定时器？
   → 人为加延迟/串行化，看是否消失
3. **顺序依赖**：测试单独跑通过、整批跑失败？
   → 只跑失败的那个用例 vs 跑全批
4. **外部不稳定**：网络、时钟、DNS、第三方服务、随机数
   → 固定随机种子、mock 外部依赖、换时间点重试

判据：**能说出「什么条件下必现」才算找到触发条件**。说不出就是还没找到。

### 1.4 复现不了怎么办（这本身就是结论）

不许假装复现了。按这个顺序降级：

1. **加观测**：在可疑路径加日志（不是改逻辑），等下次出现
2. **收窄窗口**：从「用户报告的时间段」缩到具体请求 ID / 会话 ID
3. **找同类**：仓库里有没有同结构的代码已经修过？（同一个坑常犯多次）
4. **如实标 UNKNOWN**：写下「在 X 条件下无法复现，需要 Y 信息才能继续」

⛔ 「复现不了但我猜是 Z 的问题」不是结论 —— 那是假设，必须标注为假设。

## 第 2 步：最小化（把无关变量删掉）

目标：**用最少的代码/数据/步骤仍能触发**。

做法：

1. 从复现步骤开始，**一次只删一样**（一个文件、一个参数、一行配置）
2. 每次删完重跑，仍失败 → 保留删除；不再失败 → 恢复
3. 直到删掉任何一样都不再触发

为什么必须做：最小复现能直接暴露「哪个输入/哪个分支」是关键，而且**修完之后它就是你回归测试的用例**。

## 第 3 步：二分定位（缩小到函数/行）

### 3.1 代码二分

　　`git bisect start` → `git bisect bad` → `git bisect good <已知好提交>` → 跑复现命令报 good/bad → `git bisect reset`

适用：知道「以前是好的」但不知道哪次改坏的。

⛔ 二分前必须确认复现命令**在两端都能给出确定结果**（好端必过、坏端必败），否则会二分到错误提交。

### 3.2 逻辑二分

没有 git 历史时，用「注释掉一半」：

1. 把可疑函数从中间切开，先让前半段返回固定值
2. 现象消失 → 问题在前半段；现象还在 → 在后半段
3. 重复直到只剩几行

### 3.3 定位到行之后，还要回答「为什么」

能指向 `文件:行号` 只是第一步。必须补一句因果：

> 第 42 行 `items[0].id` 在 `items` 为空数组时抛 TypeError；
> 上游第 30 行的过滤条件在 `status='archived'` 时会把所有项滤掉，所以这里拿到空数组。

⛔ 只说「这里空指针」不算根因 —— 要回答「为什么这里会是空」。

## 第 4 步：验证修复（不许跳过）

修完之后，**必须按原复现步骤再跑一次**，并记录：

| 检查 | 怎么验 |
|---|---|
| 原现象消失 | 跑第 1 步的复现命令，输出与期望一致 |
| 没有引入新问题 | 跑相关测试/验证脚本，记录通过数 |
| 最小复现变成回归用例 | 把第 2 步的最小复现固化成测试（见 `test-writing`） |
| 修的是根因而非症状 | 能说出「如果换个输入还会不会犯」 |

⛔ 最常见的假修复：在报错处加了 try/catch 或判空，现象消失但根因还在。

## 输出格式

按这个结构写，缺项要说明缺什么：

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`

**1. 现象与期望**
- 期望：<可指到规格/用户原话>
- 实际：<贴输出>
- 观察点：<日志/退出码/返回值>

**2. 复现**
- 稳定性：稳定 / 偶发（触发条件：…）/ 无法复现（已试：…）
- 最小复现：<步骤或最小代码>
- 命令与输出：<完整贴出>

**3. 根因**
- 位置：`文件:行号`
- 因果：<为什么会这样，不是「这里错了」>

**4. 修复与验证**
- 改了什么：`文件:行号`
- 原复现步骤现在的结果：<贴输出>
- 相关测试：<脚本 + 通过数>
- 回归用例：<是否已固化>

**5. 判不了的部分**
- <缺什么信息>

## 假阳性清单（这些不是 bug）

- 日志顺序不同但结果一致
- 时间戳/耗时数值不同
- 错误信息文案变化（只要错误码/类型没变）
- 测试并行执行导致的输出交错
- 依赖版本「不是最新」

## 假阴性清单（最常漏的 8 类）

1. **只跑了一次就宣布修好**（偶发 bug 必须多次）
2. **只测了修复路径，没测原失败路径**
3. **加了判空/try-catch 就收工**（症状压制）
4. **改了 A 处，问题挪到 B 处**（没有全局回归）
5. **在最小复现之外的环境验证**（环境不同结论无效）
6. **没有把最小复现固化成测试**（下次还会犯）
7. **把「复现不了」写成「已修复」**
8. **根因只写到行号，没写因果**

## 本仓库可用的命令

```bash
node tools/quality/scan-silent-catch.mjs        # 空 catch 扫描（错误被吞掉的地方）
node tools/quality/scan-mutation-residue.mjs    # 变异残留（调试代码没删干净）
node tools/quality/commit-gate.mjs              # 提交前门禁（修完确认没弄坏别的）
```

## 与其他技能的关系

- `code-review`：修完后请人按五层审一遍（尤其「删除与副作用」层）
- `test-writing`：把最小复现固化成回归用例
- `perf-profile`：如果「慢」是现象而非报错，转去测量而不是猜
- `release-gate`：修完准备提交前跑门禁
- `evidence-audit`：怀疑「已修复」的证据不实时用它复核

## 边界（如实说清）

- 本技能不保证能修好 —— 只能保证「要么说清根因，要么如实说复现不了」
- 偶发 bug 的触发条件常常需要长时间观察，**一次会话内可能拿不到**
- 二分定位要求「好端/坏端可判定」，不满足时只能退回逻辑二分
- 修完的验证受限于现有测试覆盖；**没覆盖到的路径仍可能坏**
- 如果 bug 只在生产环境出现，本地复现不了时结论只能是 UNKNOWN
