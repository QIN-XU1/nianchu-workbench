# 技术选型 技能

> 选型最常见的失败不是「选错」，而是**「没有先定约束就开始比」** ——
> 于是比的是「哪个更先进」，而不是「哪个适合我们」。
> 本技能的纪律：**先用硬约束淘汰，再在剩下的里面比。** 顺序反了，比较就是装饰。

## 什么时候用

- 在两个以上技术方案之间选（库/框架/协议/存储/架构）
- 要不要引入一个新依赖/新服务
- 现有方案要不要换掉
- 有人推荐「用 X 更好」

## 什么时候**不**用

- 只有一个方案，要评审它 → `design-review`
- 已经定了，要记录理由 → `adr`
- 要评估某个具体风险 → `threat-model`
- 要拆解落地步骤 → `task-breakdown`

## 第 0 步：先定硬约束（不满足直接出局）

### 0.1 什么是硬约束

**不满足就不能用**的条件，不是「差一点也行」。常见六类：

| 类型 | 例子 |
|---|---|
| **平台** | 必须跑在 Windows / 必须在浏览器里 |
| **规模** | 必须支撑 10 万条记录 |
| **许可** | 不能是 GPL（要商用） |
| **依赖** | 不能引入需要常驻服务的组件 |
| **能力** | 必须支持流式输出 |
| **团队** | 现有团队能维护（不能要求学新语言） |

### 0.2 硬约束的检验

对每条约束问：**不满足时，我们能接受吗？**

- 能接受 → 那不是硬约束，是加权维度
- 不能接受 → 硬约束，**先淘汰**

⛔ 硬约束最常见的错误：把「希望有」当成「必须有」。
后果是淘汰掉本来可用的方案，或者留下不满足的方案然后用加权掩盖。

### 0.3 本仓库的实例

选「技能市场要不要默认联网」时的硬约束：
- 平台：本地工作台（不能假设有网）
- 依赖：不能引入常驻服务
- 隐私：不能在未经同意时发出元数据

→ 结论：默认不联网（远程源必须显式指定）。这是约束推导出来的，不是偏好。

## 第 1 步：淘汰（把不满足硬约束的直接划掉）

### 1.1 淘汰表

| 方案 | 硬约束 1 | 硬约束 2 | 硬约束 3 | 结论 |
|---|---|---|---|---|
| A | ✅ | ❌ | — | **出局**（不满足约束 2） |
| B | ✅ | ✅ | ✅ | 进入比较 |
| C | ✅ | ✅ | ❌ | **出局** |

⛔ 淘汰必须写「不满足哪一条」。写「不合适」等于没淘汰。

### 1.2 只剩一个怎么办

如果淘汰后只剩一个：
- 它满足所有硬约束 → **直接选它**，不需要加权比较
- 一个都不剩 → **约束太严**，回去重新审视哪条其实不是硬的

⛔ 只剩一个还硬要比加权分，是在制造「深思熟虑」的假象。

## 第 2 步：加权比较（只在剩下的里面比）

### 2.1 先定维度与权重（在打分之前！）

| 维度 | 权重 | 为什么这个权重 |
|---|---|---|
| 维护成本 | 30% | 长期成本最高 |
| 学习曲线 | 20% | 影响上手速度 |
| 功能匹配 | 25% | 能满足多少需求 |
| 生态/文档 | 15% | 出问题时能否找到答案 |
| 性能 | 10% | 当前规模够用即可 |

⛔ **先定权重再打分**。反过来（先打分再凑权重）就是事后合理化。

### 2.2 打分要能指向证据

| 打分 | 要求 |
|---|---|
| 5 分 | 有实测/有文档明确支持 |
| 3 分 | 有间接证据 |
| 1 分 | 只是印象 |

⛔ 全部靠印象打分，等于用直觉伪装成分析。

### 2.3 加权分的陷阱

| 陷阱 | 后果 |
|---|---|
| 权重加起来不等于 100% | 分数不可比 |
| 用绝对分数而非相对 | 5 分制里的「5」是什么基准？ |
| 差异很小（如 3.8 vs 3.9） | 结论不稳健，别当真 |

**判据：如果两个方案加权分差 < 10%，视为「打平」**，此时应该用别的理由决断（团队熟悉度/迁移成本），而不是假装算出了胜负。

## 第 3 步：小规模验证（不要只靠文档）

### 3.1 为什么必须验证

文档说的和实际行为经常不一致。三类常见偏差：

| 偏差 | 例子 |
|---|---|
| 文档说支持，实际不支持 | 「支持 Windows」但有路径 bug |
| 文档没说但影响很大 | 首次加载要 8 秒 |
| 版本差异 | 文档是最新版，你装的是旧版 |

### 3.2 验证什么（最小集）

| 验证项 | 怎么验 |
|---|---|
| **核心能力** | 用它做一件真实的小事 |
| **约束满足** | 在目标平台上跑一次 |
| **集成成本** | 接入现有代码要改几处 |
| **失败表现** | 故意传错参数，看错误信息是否有用 |

⛔ 只跑「Hello World」不算验证 —— 那验证的是「能装上」。

### 3.3 验证的时间上限

**给验证设时间盒**（如半天）。超时就说明：
- 要么这个方案集成成本比预期高（这本身是重要发现）
- 要么验证方式不对

## 第 4 步：写下「什么条件下这个选择会翻」

### 4.1 为什么必须写

技术选型都有时效。不写翻转条件，选择会变成教条。

### 4.2 写法

```
选 A 而非 B。
如果出现以下任一情况，需要重新评估：
- 数据量超过 10 万条（A 的单机方案会到瓶颈）
- 需要多用户并发写（A 没有并发控制）
- B 的生态成熟到有官方 Windows 支持
```

判据：**这些条件能被观测到吗？** 不能就不是条件。

## 第 5 步：写清「放弃了什么」

| 放弃的 | 影响 |
|---|---|
| B 的生态更丰富 | 以后遇到问题时可能找不到现成答案 |
| B 的性能更好 | 数据量增长后可能要迁移 |

⛔ 只说「A 更好」不说「放弃了 B 的什么优点」，是事后合理化。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 硬约束淘汰 + 加权比较 + 小规模验证 + 翻转条件
- WARN = 验证不充分（列出未验项）
- FAIL = 没定硬约束就开始比 / 打分无证据 / 无翻转条件

## 假阳性清单（这些不算选型缺陷）

- 加权分接近但选了团队更熟悉的（合理，团队熟悉度难量化）
- 没做性能压测（当前规模不需要）
- 选了「不够先进」的方案（约束决定的）
- 淘汰后只剩一个（说明约束筛选有效）

## 假阴性清单（最常漏的 8 类）

1. **没定硬约束就开始加权比较**
2. **把「希望有」当「必须有」**（淘汰掉可用方案）
3. **先打分再凑权重**（事后合理化）
4. **打分没有证据**（全是印象）
5. **只跑 Hello World 就认为验证过**
6. **没有翻转条件**（选择变教条）
7. **没说放弃了什么**
8. **加权分差很小却宣布胜出**

## 与其他技能的关系

- `design-review`：单方案评审（本技能是多方案选择）
- `adr`：选型结论应留 ADR
- `threat-model`：选型涉及安全边界时
- `dep-upgrade`：选了新依赖后的升级管理
- `perf-profile`：需要实测性能时用它测量

## 边界（如实说清）

- 加权打分**不能消除主观性**，只是让主观判断显式化
- 无法预测「三年后这个方案是否还合适」
- 小规模验证无法暴露大规模问题
- 团队熟悉度、组织政治等软因素无法量化，但往往是决定性的
- 关键信息不可得时（如闭源产品的真实性能），结论只能是 UNKNOWN
