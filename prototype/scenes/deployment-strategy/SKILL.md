# 部署策略 技能

> 部署的核心矛盾：**要快发布，又不能一次炸全量**。
> 判据：**发布出问题时，影响多少用户？多久能回滚？**

## 什么时候用

- 设计发布流程
- 降低发布风险
- 要灰度

## 什么时候**不**用

- 无用户的内部工具

## 第 1 步：四种策略

| 策略 | 原理 | 回滚 | 资源 |
|---|---|---|---|
| **滚动**（rolling） | 逐批替换实例 | 再滚回 | 少 |
| **蓝绿**（blue-green） | 新旧两套，切换流量 | 切回 | 双倍 |
| **金丝雀**（canary） | 先给 1% 流量 | 停投放 | 少 |
| **特性开关** | 代码上线但功能关 | 关开关 | 少 |

## 第 2 步：按风险选

| 场景 | 推荐 |
|---|---|
| 常规小改 | 滚动 |
| 大版本/高风险 | 蓝绿或金丝雀 |
| 要即时关功能 | 特性开关 |
| 数据库不兼容改动 | 蓝绿（可切回旧版） |

⛔ 高风险改动用滚动 = 一半新一半旧，问题扩散。

## 第 3 步：金丝雀的关键

| 项 | 要求 |
|---|---|
| 分流 | 按用户/IP/百分比 |
| **观测** | 对比新旧指标（错误率/延迟） |
| 自动判断 | 指标差则自动回滚 |
| 渐进 | 1%→5%→25%→100% |

⛔ 金丝雀不看指标 = 只是慢一点的发布，没护栏。

## 第 4 步：回滚能力（最重要）

| 项 | 要求 |
|---|---|
| 一键回滚 | 秒级/分钟级 |
| 数据兼容 | 新版本写的旧版本能读（否则回滚炸） |
| 测试回滚 | 演练过 |

★ 部署策略的价值一半在**回滚**。回滚不了 = 出事只能修不能退。

## 第 5 步：数据库变更与部署解耦

- 数据库变更要**向后兼容**（旧代码也能跑），否则回滚炸
- 分两步：先加字段（兼容）→ 部署 → 后删旧（见 `schema-evolution`）

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 策略匹配风险 + 金丝雀有观测 + 可回滚 + 数据兼容
- WARN = 有策略但回滚未演练
- FAIL = 高风险用滚动 / 无法回滚 / 数据不兼容
- UNKNOWN = 拿不到发布流程

## 假阳性清单（这些不算「发布安全」）

- 有金丝雀但不看指标
- 回滚没演练
- 数据不兼容

## 假阴性清单（最常漏的 8 类）

1. **高风险用滚动**
2. **金丝雀无观测**
3. **回滚没演练**
4. **数据不兼容**（回滚炸）
5. **数据库变更与部署不分离**
6. **无自动回滚**
7. **回滚慢**
8. **无灰度**

## 与其他技能的关系

- `release-pipeline`：发布流水线
- `rollback-plan`：回滚方案
- `feature-flag`：特性开关
- `schema-evolution`：数据兼容

## 边界（如实说清）

- 蓝绿成本双倍
- 金丝雀需要可靠的分流与观测
- 本技能不实现，只设计
