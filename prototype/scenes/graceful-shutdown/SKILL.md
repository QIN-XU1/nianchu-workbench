# 优雅停机 技能

> 直接 kill 进程的后果：**正在处理的请求被截断、消息处理到一半丢失、连接突然断**。
> 判据：**发布重启的那几十秒，用户会不会遇到报错或丢数据？**

## 什么时候用

- 滚动发布/重启
- 处理长请求/后台任务
- 消息消费者
- 有状态连接

## 什么时候**不**用

- 一次性批处理（本来就跑完才退）
- 无状态且请求极短

## 第 1 步：正确顺序（最容易做反）

```
1. 收到 SIGTERM
2. 从负载均衡摘除（不再接新请求）★ 先做这个
3. 等待在途请求处理完（排空）
4. 关闭资源（DB 连接、队列）
5. 退出（或超时强制）
```

⛔ 顺序做反（先关连接再排空）= 在途请求全失败。

## 第 2 步：摘除与排空（关键）

| 步骤 | 要点 |
|---|---|
| **摘除** | 健康检查先返回不健康 → LB 停止发送 |
| **摘除传播延迟** | 等一个「LB 刷新周期」再排空（否则还有请求进来） |
| **排空** | 等在途请求完成（grace period） |
| **超时** | 排空超时则强制退出（防止卡死） |

★ 「摘除传播延迟」常被漏：健康检查标不健康了，但 LB 还有几秒才会停止发请求，这段还要接住。

## 第 3 步：不同负载的处理

| 负载 | 停机处理 |
|---|---|
| HTTP 请求 | 排空在途 |
| 长连接（WebSocket） | 通知客户端重连 |
| 消息消费者 | 停止拉新消息，处理完手上的，再提交 offset |
| 定时任务 | 等当前任务跑完或存检查点 |
| 后台线程 | 设停止标志，循环检查 |

## 第 4 步：超时与强制

| 项 | 要求 |
|---|---|
| grace period | 合理（如 30s，大于最长请求） |
| 强制退出 | 超时后 SIGKILL（不能永远等） |
| 幂等 | 半截任务要能重试不重复 |

## 第 5 步：信号

| 信号 | 含义 |
|---|---|
| SIGTERM | 请求优雅退出（要处理） |
| SIGKILL | 无法捕获，强杀（所以要在 SIGTERM 内做完） |
| SIGINT | Ctrl-C（开发时） |

⛔ 不处理 SIGTERM = 默认立即被杀 = 没有优雅停机。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 处理 SIGTERM + 先摘除再排空 + 超时强制 + 幂等
- WARN = 有排空但无摘除传播延迟
- FAIL = 不处理信号 / 先关资源再排空 / 无超时
- UNKNOWN = 拿不到部署方式

## 假阳性清单（这些不算「优雅停机」）

- 有 grace period 但不处理信号
- 先关连接再排空
- 无超时（可能永久卡）

## 假阴性清单（最常漏的 8 类）

1. **不处理 SIGTERM**
2. **先关资源再排空**
3. **漏摘除传播延迟**
4. **无强制超时**
5. **消息消费者不提交 offset**
6. **长连接不通知重连**
7. **半截任务不幂等**（重启重复）
8. **定时任务无检查点**

## 边界（如实说清）

- SIGKILL 无法优雅处理，只能靠幂等兜底
- 排空会延长发布总时长
- 本技能不实现，只设计流程
