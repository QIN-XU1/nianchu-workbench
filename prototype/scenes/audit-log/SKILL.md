# 审计日志 技能

> 审计日志和普通日志的区别：**它要能回答「谁在什么时候对什么做了什么」，且不可篡改、不可抵赖**。
> 判据：**出了内鬼/纠纷，这份日志能作为证据吗？** 能被改、缺关键字段 = 不是审计日志。

## 什么时候用

- 敏感操作（权限/资金/数据删除）
- 合规要求（SOX/等保/金融）
- 追责/纠纷

## 什么时候**不**用

- 纯调试日志（见 `logging-design`）

## 第 1 步：记什么（五要素）

| 要素 | 内容 |
|---|---|
| **谁**（Who） | 用户/服务/来源 IP |
| **何时**（When） | 时间戳（准确、UTC） |
| **做了什么**（What） | 操作类型 + 目标对象 |
| **结果**（Result） | 成功/失败 + 原因 |
| **上下文**（Context） | 请求 ID、改前/改后值 |

⛔ 只记「用户 A 登录了」不记「改了什么值」= 无法追责。

## 第 2 步：不可篡改（审计的灵魂）

| 手段 | 说明 |
|---|---|
| **只追加**（append-only） | 不提供修改/删除接口 |
| **WORM 存储** | 一次写多次读 |
| **哈希链** | 每条含上一条哈希（防篡改可检测） |
| **独立存储** | 与应用分离（应用被攻破不影响） |
| **权限分离** | 写日志的不能删日志 |

⛔ 审计日志和应用同库且可删 = 内鬼删库跑路，日志一起没了。

## 第 3 步：记在哪一层

| 层 | 记什么 |
|---|---|
| 应用 | 业务操作（改了什么） |
| 数据库 | 数据变更 |
| 网关 | 访问/认证 |

## 第 4 步：保留与查询

| 项 | 要求 |
|---|---|
| 保留期 | 按合规（金融/医疗常 5-10 年） |
| 可查询 | 按谁/时间/对象 |
| 脱敏 | 敏感字段打码但保留可审计 |
| 导出 | 供审计/司法 |

## 第 5 步：常见坑

| 坑 | 后果 |
|---|---|
| 记了但可改 | 不是证据 |
| 缺「改前/改后」 | 不知道改了什么 |
| 无用户身份 | 不知道谁 |
| 与应用同库 | 一起被删 |
| 记敏感明文 | 日志本身泄露 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 五要素 + 不可篡改 + 保留查询 + 脱敏
- WARN = 有审计但可篡改
- FAIL = 无审计 / 缺用户/改前改后 / 同库可删
- UNKNOWN = 拿不到审计需求

## 假阳性清单（这些不算「审计日志」）

- 有日志但可改
- 缺用户身份
- 无改前改后

## 假阴性清单（最常漏的 8 类）

1. **可篡改**（非 append-only）
2. **缺「改前改后」**
3. **无用户身份/来源**
4. **与应用同库**（一起没了）
5. **记敏感明文**
6. **无保留策略**
7. **无哈希链**（篡改不可检测）
8. **写日志的人能删日志**

## 边界（如实说清）

- WORM 存储成本高
- 审计日志量大要分区
- 本技能不实现，只设计
