# 多租户 技能

> 多租户最严重的事故：**A 客户看到了 B 客户的数据（串租户）**。
> 判据：**任何一个查询，如果漏了租户条件，会不会返回别的租户的数据？** 会 = 隔离不足。

## 什么时候用

- SaaS 多客户
- 一套系统服务多个组织
- 数据要按租户隔离

## 什么时候**不**用

- 单租户内部系统

## 第 1 步：隔离级别（三选一）

| 级别 | 隔离 | 成本 |
|---|---|---|
| **独立库**（每租户一库） | 最强 | 最高（运维多） |
| **共享库独立 schema** | 强 | 中 |
| **共享表 + tenant_id 列** | 弱（靠代码） | 最低（最常见） |

⛔ 共享表模式：**每个查询都必须带 tenant_id**，漏一个就串数据。

## 第 2 步：租户识别

| 来源 | 说明 |
|---|---|
| 登录 token 里的 tenant | 最可靠 |
| 子域名 | 常见 |
| 请求头 | 要防伪造 |

⛔ 从「请求参数」取 tenant_id = 用户能改成别人的 = 越权。

## 第 3 步：防串租户（共享表模式的重点）

| 手段 | 说明 |
|---|---|
| **强制加 tenant 条件** | ORM 全局钩子/中间件自动加 |
| **行级安全（RLS）** | 数据库层强制（最可靠） |
| **复合唯一键带 tenant** | `(tenant_id, email)` |
| **代码审查** | 检查每处查询 |

★ 最可靠的是**数据库 RLS**：即使代码忘了加条件，数据库也拦住。纯靠代码纪律迟早漏。

## 第 4 步：配额与隔离

| 资源 | 隔离 |
|---|---|
| 请求量 | 按租户限流（防一个租户拖垮全系统） |
| 存储 | 配额 |
| 缓存 | key 含 tenant（防串） |
| 后台任务 | 按租户隔离 |

⛔ 缓存 key 不含 tenant = 租户 A 命中租户 B 的缓存。

## 第 5 步：租户生命周期

| 操作 | 要点 |
|---|---|
| 创建 | 初始化数据/配置 |
| 删除 | 删干净（含缓存/搜索索引/备份） |
| 迁移 | 租户搬家 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 隔离级别合理 + 强制 tenant 条件（RLS）+ 配额 + 缓存隔离
- WARN = 共享表但靠代码纪律无 RLS
- FAIL = tenant 从请求参数取 / 漏 tenant 条件 / 缓存不隔离
- UNKNOWN = 拿不到数据模型

## 假阳性清单（这些不算「隔离好」）

- 有 tenant_id 但靠人记得加
- tenant 从参数取
- 缓存不含 tenant

## 假阴性清单（最常漏的 8 类）

1. **tenant 从请求参数取**（可改）
2. **漏 tenant 条件**（串数据）
3. **无 RLS**（纯靠纪律）
4. **缓存 key 不含 tenant**
5. **无按租户限流**（一个拖垮全）
6. **唯一键不含 tenant**（冲突）
7. **搜索索引不隔离**
8. **删租户不彻底**

## 边界（如实说清）

- 共享表模式性能好但隔离靠纪律/RLS
- 独立库隔离强但运维成本高
- 本技能不实现，只设计
