# 提示词工程 技能

> 提示词失效的三种典型：**要求模糊**（模型不知道做到什么程度）、**自相矛盾**（两条规则打架）、**过长被稀释**（关键约束埋在中间）。
> 判据：**一个新来的聪明人只看这份提示词，能不能做出你想要的？** 不能就是没写清。

## 什么时候用

- 写/改 system prompt、任务提示
- 模型输出不稳定
- 要控制格式/风格/边界

## 什么时候**不**用

- 简单事实问答（不需要复杂提示）
- 提示词问题其实是上下文问题 → `context-management`

## 第 1 步：结构（先说什么，后说什么）

| 顺序 | 内容 |
|---|---|
| 1 | 角色/目标（你要成为谁、达成什么） |
| 2 | 硬约束（必须/禁止） |
| 3 | 可用信息/工具 |
| 4 | 输出格式 |
| 5 | 样例（如需） |

⛔ 关键约束放最后或埋中间 = 被稀释。

## 第 2 步：约束要可判定

| 模糊 | 可判定 |
|---|---|
| 「简洁一点」 | 「不超过 3 句」 |
| 「专业」 | 「用术语，避免口语」 |
| 「准确」 | 「每个数字标注来源，拿不到标 UNKNOWN」 |

⛔ 不可量化的形容词 = 模型各理解各的。

## 第 3 步：样例（few-shot）用得对

| 要点 | 说明 |
|---|---|
| 样例要覆盖**边界** | 不只 happy path |
| 样例要**一致** | 互相矛盾会误导 |
| 数量 | 少而精，别堆 |
| 格式 | 与要求的输出格式一致 |

⛔ 堆一堆样例会「约束」模型创造力，也占上下文。

## 第 4 步：常见失效与修法

| 失效 | 原因 | 修法 |
|---|---|---|
| 不遵守格式 | 没说清/没样例 | 给格式+样例 |
| 编造 | 没让它承认不知道 | 加「拿不到就说 UNKNOWN」 |
| 越权 | 边界不清 | 明确「不要做 X」 |
| 前后矛盾 | 规则冲突 | 检查并消除冲突 |
| 长提示被忽略 | 太长 | 精简、关键重述 |

## 第 5 步：迭代（提示词是试出来的）

| 做法 | 说明 |
|---|---|
| 先写最小可用版 | 别一上来写巨型 |
| 用真实输入测 | 不是想象 |
| 看失败案例 | 针对性改 |
| 保留回归用例 | 改提示词不破坏旧的 |

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 结构清晰 + 约束可判定 + 有边界 + 无矛盾
- WARN = 有结构但约束模糊
- FAIL = 规则矛盾 / 无「不知道就说」/ 关键埋中间
- UNKNOWN = 拿不到提示词

**1. 结构**
| 段 | 有吗 |
|---|---|
| 目标 | |
| 硬约束 | |
| 输出格式 | |

**2. 约束可判定性**
| 约束 | 可量化 |
|---|---|

**3. 矛盾检查**
| 冲突 | 处理 |
|---|---|

**4. 判不了的部分**
- <拿不到的真实输入>

## 假阳性清单（这些不算「提示词好」）

- 很长很全但矛盾
- 有样例但只 happy path
- 形容词一堆不可量化

## 假阴性清单（最常漏的 8 类）

1. **形容词不可量化**
2. **规则自相矛盾**
3. **关键约束埋中间**
4. **不要求承认不知道**（编造）
5. **无边界（越权）**
6. **样例只 happy path**
7. **堆太多样例**（约束创造力）
8. **改了不回归**

## 与其他技能的关系

- `context-management`：上下文预算
- `agent-tool-design`：工具描述也是提示词
- `doc-write`：写文档
- `capability-benchmark`：提示词效果评估

## 边界（如实说清）

- 提示词能力受模型限制（弱模型再好的提示也有限）
- 提示词无法保证 100% 稳定
- 本技能不训练模型，只优化输入
