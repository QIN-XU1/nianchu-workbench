# 可观测性设计 技能

> 可观测性最容易沦为「上了一个监控大盘，然后没人看」。
> 判据只有一条：**出事的时候，它能不能让你在 5 分钟内定位到根因？**
> 不能的大盘、没被触发的告警、写进去没人查的日志，都是成本不是能力。

## 什么时候用

- 新服务上线前的可观测性设计
- 线上问题查不到根因
- 告警太多但都不准（告警疲劳）
- 要把「黑盒」变「白盒」

## 什么时候**不**用

- 只是配一个具体的告警规则 → 直接做
- 要查一次具体事故 → `debug-repro`
- 要设计事故沟通 → `incident-comms`

## 第 1 步：三支柱各管什么（先分清）

| 支柱 | 回答什么问题 | 成本 | 采样 |
|---|---|---|---|
| **指标 Metrics** | 整体健康吗？趋势如何？ | 低（聚合数） | 全量 |
| **日志 Logs** | 这一次发生了什么？ | 高（每事件） | 可采样 |
| **追踪 Traces** | 这一次慢在哪一跳？ | 中（每请求） | 可采样 |

⛔ 三者不是替代关系。只有指标 → 知道坏了但不知为什么；只有日志 → 能查单次但看不出趋势。

## 第 2 步：指标（先定「黄金信号」）

### 2.1 四个黄金信号

| 信号 | 定义 | 典型指标 |
|---|---|---|
| **延迟** | 请求多慢 | P50/P95/P99（不是平均值！） |
| **流量** | 多少请求 | QPS / 日活 |
| **错误** | 错多少 | 错误率 / 错误类型分布 |
| **饱和度** | 资源多满 | CPU/内存/连接池/队列深度 |

⛔ 用**平均值**看延迟是最常见的错误——平均值掩盖长尾，而用户感受的是 P99。

### 2.2 指标的三个要求

| 要求 | 反例 |
|---|---|
| **有维度**（可按服务/实例/接口下钻） | 只有全局 QPS，不知道哪个接口 |
| **有分布**（P50/P95/P99） | 只有 avg |
| **有基线**（正常是多少） | 只有绝对值，没有对照 |

## 第 3 步：日志（记「能定位」的，不记「全量」的）

### 3.1 结构化日志的三要素

| 要素 | 作用 |
|---|---|
| **时间戳** | 排序 |
| **追踪 ID** | 串起一次请求的所有日志 |
| **结构化字段**（JSON） | 可查询、可聚合 |

### 3.2 什么级别记什么

| 级别 | 记什么 | 什么时候看 |
|---|---|---|
| ERROR | 需要人介入的失败 | 告警时 |
| WARN | 可自愈但异常的 | 排查时 |
| INFO | 关键状态变迁（启动/迁移/配置变更） | 复盘时 |
| DEBUG | 详细过程 | 只在你真的会查时开 |

⛔ 最高频的错误：**日志里没有 trace ID**。于是「这次请求的所有日志」串不起来，等于没有。

### 3.3 不许写进日志的

- 密码、token、密钥（要脱敏）
- 完整身份证/手机号/银行卡（要掩码）
- 大对象全量 dump（会爆盘）

## 第 4 步：追踪（定位「慢在哪一跳」）

### 4.1 一个 trace 的构成

```
trace_id（整条链路）
  └─ span A（服务1，耗时 120ms）
       ├─ span B（DB 查询，80ms）   ← 慢在这里
       └─ span C（缓存，2ms）
```

### 4.2 判据：能不能回答「这 80ms 花在哪」

| 情况 | 追踪够不够 |
|---|---|
| 只有服务间调用，没有 DB/缓存/外部 API 的 span | 不够 |
| 有 span 但没打关键属性（SQL/URL/参数） | 半够 |
| 有 span + 关键属性 + 父子关系 | 够 |

## 第 5 步：告警（只对「需要人现在动手」的事告警）

### 5.1 告警的黄金判据

**每一条告警都必须能回答：「收到后我该做什么？」**
答不上来的告警，删掉。

### 5.2 三类告警的分级

| 级别 | 条件 | 响应 |
|---|---|---|
| **P0 叫醒** | 用户可感知的故障（错误率/延迟超标、核心功能挂） | 立即 |
| **P1 上班处理** | 趋势恶化但尚未影响用户（磁盘 80%） | 工作时间内 |
| **P2 记录** | 只是异常（某接口偶发慢） | 看板，不推人 |

⛔ 把 P2 当 P0 推送 = 告警疲劳 = 真 P0 来时被无视。

### 5.3 反例：什么告警是坏的

- 「CPU > 80%」但没说是哪台、为什么、该怎么办
- 每个错误都告警（噪音，应聚合成「错误率 > X%」）
- 告警只发到群里没有负责人（没人认领）
- 阈值恒定不随流量变化（大促必然误报）

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 三支柱齐 + 黄金信号有分布 + 日志有 trace ID + 告警可行动
- WARN = 缺一支柱或日志无 trace ID
- FAIL = 告警不可行动 / 敏感信息进日志
- UNKNOWN = 不知道系统有哪些组件

**1. 三支柱覆盖**
| 支柱 | 有吗 | 采什么 | 采样率 |
|---|---|---|---|

**2. 黄金信号**
| 信号 | 指标 | 有维度？ | 有分布？ |
|---|---|---|---|

**3. 日志**
| 项 | 现状 | 问题 |
|---|---|---|
| 有 trace ID？ | | |
| 有脱敏？ | | |

**4. 追踪**
| 关键一跳 | 有 span？ | 有属性？ |
|---|---|---|

**5. 告警**
| 告警 | 级别 | 收到后做什么 |
|---|---|---|

**6. 判不了的部分**
- <哪些组件没有观测>

## 假阳性清单（这些不算「有可观测性」）

- 有大盘但没人看
- 有告警但全是 P0（等于没分级）
- 有日志但无 trace ID（串不起来）
- 只有 avg 延迟

## 假阴性清单（最常漏的 8 类）

1. **延迟用平均值**不看 P99
2. **日志无 trace ID**
3. **告警不可行动**（不知该怎么办）
4. **P2 当 P0 推**（告警疲劳）
5. **敏感信息进日志**
6. **只有服务间 span** 没有 DB/外部 API 的
7. **饱和度过** 没监控（连接池/队列）
8. **没有基线**（不知正常值）

## 与其他技能的关系

- `debug-repro`：用可观测性数据定位问题
- `incident-comms`：告警触发后的对外沟通
- `perf-profile`：延迟的深挖
- `postmortem`：复盘可观测性哪里不够
- `runbook`：告警对应的处置手册

## 边界（如实说清）

- 可观测性不能替代测试；它是「出事后能不能查」而非「不出事」
- 采样会丢细节；高价值请求要能强制全采
- 追踪有性能开销，不是越多越好
- 本技能不实现采集，只设计「采什么、告什么」
