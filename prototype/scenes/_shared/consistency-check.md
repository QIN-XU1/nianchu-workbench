# 一致性检查 · 共享步骤（6 个场景 skill 共用）

> 这份文件是**可被多个场景 skill 引用的共享 reference**。
> 以前同样的「怎么做 2-4 / 判据 / 坑」被复制到 6 个 SKILL.md 里
> （data-reconcile / doc-consistency / docs-index / inventory-ledger / self-review / support-assign）。
> 按上下文工程原则「don't repeat yourself + progressive disclosure」抽到这里一份，
> 各技能只保留自己的第 1 步与一句指针。**改这里，6 个技能一起生效。**

## 适用边界（先确认你在做的是这一类事）

六个技能共享同一个骨架，但检查对象不同：

| 技能 | 检查什么 | 典型差异来源 |
|---|---|---|
| `data-reconcile` | 两份数据源的记录集合与金额 | 两个系统各自记账 |
| `doc-consistency` | 术语是否登记、有无未登记缩写 | 文档多人写、术语漂移 |
| `docs-index` | README 索引是否覆盖全部文档、是否重复 | 新增文档忘了登记 |
| `inventory-ledger` | 账面量与仓库记录、物料号在主数据里 | 出入库未同步 |
| `self-review` | 自己的档案有索引、索引不指向不存在的档案 | 档案增删未更新索引 |
| `support-assign` | 每单有 owner、owner 在值班表、无重复单 | 派单与值班表不同步 |

共同点：**都是「两份事实应当一致」**。所以下面这套流程对六个都成立。

## 第 1 步：跑检查（各技能自己的命令）

　　`node prototype/scenes/<技能名>/check.mjs`

　　输出形如 `PASS data-reconcile: 差异集合 = 0`（exit 0），
　　或 `FAIL docs-index: 差异集合 = 1 项` 并列出每一项的定位（exit 1）。

　　**注意**：每个技能目录下都有自己的 `check.mjs`（`scene.json` 的 `check` 字段指向它），
　　直接跑即可 —— 不需要任何外层调度器。

## 第 2 步：读懂差异集合（不要急着修）

差异分三类，**处理方式完全不同**：

| 类型 | 特征 | 该怎么办 |
|---|---|---|
| **真不一致** | 两份数据都合法，但值不同 | 查明哪份是对的，改错的那份 |
| **假阳性** | 检查规则太宽/太窄 | 改规则，**不要改数据** |
| **数据损坏** | 解析失败、字段缺失、编码错 | 先修数据，再重跑；不许静默跳过 |

⛔ 最常见的错误：把所有差异都当「真不一致」直接改数据 —— 那会把假阳性也「修」成错的。

判断顺序建议：

1. 先看差异项里有没有**解析失败/字段缺失**的（那是数据损坏，优先）
2. 再看有没有**明显是同一事物的两种写法**（如 `Node.js` vs `nodejs`，那是规则问题）
3. 剩下的才是真不一致

## 第 3 步：逐项定位到具体文件与字段

每一项差异必须能回答：

- **在哪份数据的哪个文件？**（路径）
- **哪个字段？**（字段名）
- **两边分别是什么值？**

做不到这三点就说明差异描述不够具体，检查工具需要改进（而不是靠人猜）。

## 第 4 步：修数据（⛔ 不修 baseline/）

修的时候守三条：

1. **只改错的那一份**，不动正确的（先确认哪份对）
2. **不修改基线/基准文件**（`baseline/`）—— 那是判定依据，改它等于改考卷
3. **不为了通过检查而改数据**（那是作弊，不是修复）

⛔ 「改 baseline 让它通过」是最常见的自欺。基线是事实的快照，不是可调参数。

## 第 5 步：重跑，确认差异归零

　　`node prototype/scenes/<技能名>/check.mjs`

　　必须看到 `PASS <技能名>: 差异集合 = 0` 且 exit 0。

⛔ 如果重跑后差异从 A 变成 B（数量变了但没归零），说明你的修改引入了新问题 —— 回滚重来。

## 判据（四态）

| 四态 | 条件 |
|---|---|
| **PASS** | exit 0 且输出「差异集合 = 0」 |
| **WARN** | 差异为 0，但检查本身有未覆盖项（如某些字段没检查） |
| **FAIL** | exit 非 0 且输出「差异集合 = N 项」，每项可定位 |
| **UNKNOWN** | 检查跑不起来（数据源缺失/权限/格式无法解析） |

⛔ 「差异集合 = 0」不等于「数据一定对」—— 它只说明**检查覆盖到的部分**一致。
没被检查的字段仍然可能错。

## 反例清单（这些不是真不一致）

1. **写法差异**：`Node.js` / `nodejs` / `NodeJS` 指同一事物
2. **时间格式**：`2026-11-20` 与 `2026-11-20T00:00:00Z` 是同一天
3. **数值精度**：`1.0` 与 `1` 相等；金额 `100` 分与 `1.00` 元相等
4. **顺序不同**：集合内容相同、顺序不同
5. **可选字段缺失**：一方没写该字段，另一方写了默认值
6. **已归档/已删除**：一方已标记删除，另一方还是旧状态（要确认删除是否已同步）

## 假阴性清单（最常漏的 8 类）

1. **检查规则太窄**：只比了 ID，没比值（差异被漏掉）
2. **只比数量不比内容**：「两边都是 100 条」但内容完全不同
3. **忽略可选字段**：一方缺失被当成「相等」
4. **时区/精度导致误判为相等**（或误判为不等）
5. **数据源本身是脏的**：解析失败被静默跳过，导致「看起来 0 差异」
6. **检查工具自己坏了**：脚本 bug 导致空跑（0 项差异但实际没检查）
7. **只跑一次没重跑**：修完没验证是否真归零
8. **改了 baseline** 让它通过

⛔ 第 6 类最隐蔽：**工具坏了会伪装成「数据一致」**。
本仓库踩过：展平目录只下钻两层，把目录当 0 字节文件，导致统计全是 0 —— 看起来「没有超限文件」。
防法：检查工具必须有**自检**（拿已知会不一致的样本跑一遍，必须报出差异）。

## 本仓库的坑（实测踩过）

- ⛔ **改 `check.mjs` 后必须重跑一次**，否则可能悄悄漏报（没有外层调度器会自动帮你验）
- ⛔ 场景记忆超 25KB 或 `§〇` 超 4KB 时先归档（`memory-guard.mjs archive`）
- ⛔ 展平目录时注意深度：只下钻两层会把深层目录当 0 字节文件（已踩）
- ⛔ 空 catch 会吞掉解析失败，让「数据损坏」变成「没有差异」（已踩）

## 什么时候该升级为「不是一致性问题」

如果差异的根因不在数据，而在**结构或流程**，那就不是这个技能能解决的：

| 现象 | 真正的问题 | 转去 |
|---|---|---|
| 两份数据总是不一致，每次都要手工对 | 缺少单一权威源 | `schema-design`（定权威源） |
| 差异来自字段含义变了 | 契约变更没同步 | `api-contract` |
| 差异来自老数据格式 | 需要迁移 | `data-migration` |
| 差异来自检查规则本身有争议 | 规则设计问题 | `design-review` |
| 差异来自有人手工改了 baseline | 流程失控 | 记录到台账并追溯 |

## 与其他技能的关系

- `data-migration`：迁移后用它核对两份数据是否一致
- `schema-design`：如果反复出现同类差异，说明结构缺少权威源
- `api-contract`：差异来自契约变更时，先核对兼容性
- `evidence-audit`：怀疑「差异 = 0」不可信时复核
- `code-review`：检查脚本本身的改动要审（重点看会不会漏报）

## 边界（如实说清）

- 一致性检查只能证明**被检查的字段**一致，不能证明数据整体正确
- 差异为 0 可能是「检查规则太窄」，也可能是「工具坏了」—— 两者都无法从结果本身区分
- 判定「哪份是对的」需要业务知识，工具给不出答案
- 数据源本身不可读时（权限/格式），结论只能是 UNKNOWN
- 本技能不做数据修复的自动化；修复永远要人确认（改错数据的代价高于漏改）
