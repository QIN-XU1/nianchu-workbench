# 跨仓库重构（深度技能）

> **深度技能**（`depth: deep`）：跨仓库重构的风险不在「改代码」，而在「改不彻底」和「改出隐形破坏」。
> 它需要一条有阶段、有验证、有回滚的流程，而不是一次大规模 sed。

## 什么时候用

- 一个能力要从仓库 A 搬到仓库 B
- 两个模块长期并存同一职责，要统一接口
- 大范围改名 / 改签名（影响几十个调用点）
- 拆包、拆模块、改目录结构

## 0. 先写「不变量」——这是整个重构的验收标准

在动任何代码之前，写下 3~7 条**重构前后必须成立**的事实。例：

- 「对外导出的函数签名与行为不变」
- 「旧调用点全部走新实现，旧实现不再被任何文件 import」
- 「关键流程的输出字节一致（同输入同输出）」
- 「构建产物大小变化 < 5%」

**没有不变量的重构 = 无法判断是否改坏。** 每条不变量都要能用一个命令或一段断言验证。

## 1. 摸底：先把影响面数清楚

1. 全仓搜调用点（用 `grep` 工具，不要凭记忆）：
   - 函数/类名、接口路径、配置键、事件名
   - **别名与再导出**（`export * from`、`__init__.py` 的 re-export）最容易漏
2. 统计：**N 个文件 / M 处调用**。写下这个数字——它后面要用来核对「是否改全」。
3. 找出**跨语言边界**：如果 A 是 TS、B 是 Rust，接口要靠 JSON/协议，那里是高风险区。

**判据**：能报出准确的影响面数字，且列出了别名/再导出的处理方式。

## 2. 建「双跑」验证（能对比新旧输出的黄金手段）

在迁移前，让**新旧两条路径同时可运行**，并对同一批输入比较输出：

1. 准备一批**真实输入样本**（不是手搓的玩具数据）
2. 写一个对比脚本：跑旧实现 → 跑新实现 → 逐字段 diff
3. 先跑一遍**迁移前**的基线（此时新旧应完全一致，用来验证对比脚本本身没错）

**反例（必须做一次）**：故意改动新实现的一个字段，确认对比脚本**会报差异**。
若它不报，说明这个对比是假的，后面所有「一致」都不可信。

## 3. 分批迁移（每批都能独立回滚）

按**调用点聚类**分批，不要一次全改：

| 批次 | 内容 | 回滚方式 |
|---|---|---|
| B1 | 新实现 + 双跑脚本（不改调用点） | 删新文件 |
| B2 | 低风险调用点（内部工具/测试） | revert 该提交 |
| B3 | 中风险（有测试覆盖的业务路径） | revert 该提交 |
| B4 | 高风险（对外接口/数据格式） | revert + 数据兼容层 |

**每批之后**：跑全量验证 + 双跑对比 + 检查影响面数字是否在减少。

**判据**：每批是一个独立提交，能单独 revert，且 revert 后系统仍可用。

## 4. 清理旧路径（最容易被跳过、也最容易留坑的一步）

迁移完成后：

1. **删掉旧实现**——不是注释掉，是删除。注释掉的旧代码会被人当成「还在用」。
2. 再全仓搜一次旧名字，确认 **0 命中**（包括注释、文档、测试夹具）。
3. 检查**构建产物**里旧代码是否真的没了（有时打包配置会把它带上）。
4. 更新文档与示例——文档里还写着旧用法等于教人犯错。

**判据**：旧名字全仓 0 命中，且构建产物里也不含旧实现。

## 5. 收尾：把不变量逐条复核

回到第 0 步写的不变量，**逐条**给出验证结果：

- 每条要有「怎么验的 + 结果」
- 任何一条不成立 → 这次重构**没有完成**，不许「大体上没问题」

## 常见坑（跨仓库重构特有）

- ⛔ **只搜函数名，漏了别名/再导出**：改完编译过，运行时才发现某条路径还是旧实现。
- ⛔ **新旧并存期太长**：两套实现并行，行为逐渐漂移，最后没人知道哪套是对的。
- ⛔ **注释掉旧代码而不是删除**：半年后有人「恢复」它，造成回退事故。
- ⛔ **没有双跑基线**：无法区分「重构引入的差异」和「本来就存在的差异」。
- ⛔ **一次性全改**：出错时无法定位是哪一处改动引起的，只能整体回滚。
- ⛔ **只跑单测不看产物**：单测全绿但打包漏了文件，线上才炸。

## 与其他技能的关系

- 前置：`refactor-plan`（单仓库重构的分期方法，本技能是它的跨仓库扩展）
- 并行：`api-contract`（接口契约核对）、`test-writing`（补不变量测试）
- 收尾：`doc-write`（更新文档）、`release-pipeline`（发布这次重构）
