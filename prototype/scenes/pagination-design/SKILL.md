# 分页设计 技能

> 分页最容易被忽略的 bug：**数据在翻页过程中变动 → 重复或漏掉**。
> offset 分页在「翻到第 3 页时前面删了一条」后，第 3 页会漏一条。
> 判据：**边翻页边增删，用户会不会看到重复或漏掉？**

## 什么时候用

- 列表/搜索/Feed 分页
- 数据量大要用游标
- 翻页数据异常

## 什么时候**不**用

- 数据量极小（一页装下）
- 导出全量（不是分页问题）

## 第 1 步：选类型（关键决策）

| 类型 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **offset/limit** | 简单、可跳页 | 深翻慢、数据变动重复/漏 | 后台管理、数据稳定 |
| **游标（cursor）** | 稳定、深翻快 | 不能跳页 | Feed、大数据量 |
| **keyset** | 高效 | 排序键要唯一 | 有序大数据 |

⛔ offset 深翻页（OFFSET 100000）会扫掉前 10 万行，越来越慢。

## 第 2 步：数据变动问题

| 场景 | offset 的后果 |
|---|---|
| 翻页时前面新增 | 第 2 页重复出现第 1 页末尾 |
| 翻页时前面删除 | 第 2 页漏掉一条 |

游标方案天然避免：游标锚定「最后一条的位置」，不按序号。

## 第 3 步：游标设计

| 要素 | 要求 |
|---|---|
| 游标内容 | 排序键值 + 唯一键（防并列歧义） |
| 是否可猜测 | 建议 base64/签名，防篡改 |
| 排序键 | 必须有序且稳定（如 `(created_at, id)`） |

## 第 4 步：page size 与总数

| 项 | 建议 |
|---|---|
| **上限** | 必须限制（如 max 100），防拉全表 |
| 默认值 | 合理（20/50） |
| **总数 count** | 大数据量 count(*) 很慢 → 可不给精确总数，用「还有更多」 |

⛔ 不限 page size = 有人传 `size=999999` 拉爆数据库。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 类型合理 + 变动安全 + size 上限 + 游标可验证
- WARN = offset 但数据会变动
- FAIL = 无 size 上限 / offset 深翻 / 游标可篡改且影响权限

## 假阳性清单（这些不算「分页正确」）

- 有 offset 但没限 size
- 游标用可猜的自增 id
- 数据稳定时测试通过

## 假阴性清单（最常漏的 8 类）

1. **offset 深翻变慢**
2. **翻页时变动 → 重复/漏**
3. **无 size 上限**
4. **游标可篡改**（越权看别人数据）
5. **排序键不唯一**（并列歧义）
6. **大数据 count(*)** 慢
7. **游标不含唯一键**
8. **最后一页判断错**（多一次空请求）
