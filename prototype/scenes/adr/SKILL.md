# 架构决策记录（ADR） 技能

> ADR 的唯一用途：**让未来的人（包括三个月后的你）不必重新推导一遍当时的取舍。**
> 它不是教程，不是设计文档，不是会议纪要 —— 它只回答一个问题：
> **「当时明明还有别的选择，为什么走了这条？」**
> 判据很硬：**如果一份 ADR 里没有被否掉的选项，它就等于没写。**

## 什么时候用

- 做了一个**难回退**的技术决定（换存储、换框架、定协议、定数据格式）
- 决定「**不做**某件看起来该做的事」（非目标也需要 ADR）
- 后人会反复问「为什么这么设计」
- 某个决定已经在被挑战，需要把当时的理由固化下来

## 什么时候**不**用

- 日常实现细节（命名、目录结构）→ 不需要，代码本身就是记录
- 决定还没做，正在评审 → 先 `design-review`，通过后再写 ADR
- 是可逆的小决定（改回来只要几分钟）→ 不必写
- 要写「怎么用」→ 那是 `doc-write`；要写「改了什么」→ `changelog`

## ADR 与相邻文档的分工

| 文档 | 回答的问题 | 时态 |
|---|---|---|
| `design-review` | 这个方案行不行？ | 决定**之前** |
| **ADR** | **为什么选了它、放弃了什么** | 决定**当时** |
| `doc-write` | 它怎么用？ | 决定之后 |
| `changelog` | 什么时候改了什么？ | 每次变更 |

⛔ 把 ADR 写成教程（大段「如何使用 X」）是最常见的跑偏 —— 那部分内容属于 `doc-write`。

## 第 1 步：写背景（必须包含「约束」，不只是「问题」）

### 1.1 三要素

| 要素 | 要写什么 | 反例 |
|---|---|---|
| **问题** | 当时遇到了什么具体问题（可观测的现象） | 「系统不够好」 |
| **约束** | 时间/人力/已有技术栈/兼容要求/合规/预算 | 只写问题不写约束，后人会问「那为什么不选更好的方案」 |
| **不做的代价** | 如果一直不解决会怎样 | 缺这项，后人无法判断「是否还值得坚持这个决定」 |

⛔ **约束是 ADR 里最有价值的部分**。很多决定在当时是合理的，只因为约束变了才显得过时 ——
如果不写约束，后人会误以为「当时的决策者水平不行」。

### 1.2 背景要写成「可验证的事实」

- 差：「性能有问题」
- 好：「`/api/host-status` 在本机实测 P95 800ms，超过 200ms 的目标」

- 差：「团队人手不足」
- 好：「当时只有 1 人维护，无法承担引入新服务后的运维成本」

判据：**背景里的每个论断，能不能指向一个数字/文档/工单？**

## 第 2 步：列选项（至少 2 个，含「不做」）

### 2.1 必须包含「不做」这个选项

很多决定默认「必须做」，于是从不比较「不做」的代价。
把「不做」写成一个正式选项，会强迫你回答：**现在这个问题真的必须现在解决吗？**

### 2.2 每个选项写四栏

| 选项 | 得到什么 | 付出什么 | 放弃什么 |
|---|---|---|---|
| A（选中的） | 好处 | 成本（工时/复杂度/依赖/运维） | 机会成本 |
| B | | | |
| C：不做 | 省下成本 | 问题继续存在 | 未来可能更贵 |

⛔ 只写选中选项的好处、其他选项的坏处，是**事后合理化**，不是决策记录。
好的 ADR 里，**被否掉的选项也有一两条真实优点**。

### 2.3 选项数量：2~4 个

- 只有 1 个 → 不是决策，是通知
- 超过 4 个 → 说明还没想清楚，先收敛

## 第 3 步：写决定与理由（理由必须能对上背景里的约束）

### 3.1 决定的表述要具体

- 差：「采用模块化架构」
- 好：「把单文件 `toolkit.mjs`（35.6KB）拆为 `toolkit.mjs` + `toolkit-net.mjs`，
  因为单文件红线是 32KB，且网络工具与文件工具没有共享状态」

判据：**决定能不能被验证「做到了没有」？**

### 3.2 理由必须对应约束

结构建议：

> 在**约束 X**（来自背景）下，选项 A 的**代价 Y** 是可以接受的，
> 而选项 B 会违反约束 Z，选项 C（不做）会导致 **W**。

⛔ 如果理由里出现了背景里没有的约束，说明背景写漏了 —— 回去补背景，不要在后面偷偷引入。

## 第 4 步：写后果（这是 ADR 区别于「决定通知」的关键）

### 4.1 三类后果都要写

| 类型 | 要写什么 |
|---|---|
| **接受的代价** | 明知有但接受了的缺点（如「牺牲了 X 性能换可读性」） |
| **新的约束** | 这个决定给未来加了什么限制（如「此后所有工具必须注册到同一张表」） |
| **触发重新考虑的条件** | **什么情况下该推翻这个决定** |

⛔ 第三项最常被漏，但它是最有用的：没有它，决定会变成永久教条。

### 4.2 「重新考虑的条件」要写成可观测的

- 差：「如果情况变化再评估」
- 好：「若并发从 100 涨到 1000，或单次请求 P95 超过 2s，需重新评估当前单机队列方案」

判据：**这个条件能被监控/测量到吗？** 不能就不是条件，是安慰。

## 第 5 步：写清「非目标」（决定不做什么）

ADR 里应有一节明确说：**这个决定不解决什么。**

本仓库实例：A10（IM 多通道）与 A15（审批闸/越界拦截）是**明确的目标外选择**，
每次对比矩阵输出都会打印出来 —— 不藏、不含糊，也不因为「别人有」就偷偷加进来。

为什么重要：非目标不写清，后人会不断问「为什么不做 X」，而每次回答都会走样。

## ADR 的格式与存放

### 建议结构（按此顺序，缺项要说明缺什么）

1. **标题**：`ADR-<编号>: <决定的一句话>`
2. **状态**：提议 / 已接受 / 已废弃 / 被 ADR-XXX 取代
3. **日期**
4. **背景**（问题 + 约束 + 不做的代价）
5. **选项**（2~4 个，含「不做」，各写四栏）
6. **决定**
7. **理由**（对应约束）
8. **后果**（接受的代价 + 新约束 + 重新考虑的条件）
9. **非目标**

### 关于「被取代」

ADR 是**追加式**的：旧 ADR 不改内容，只改状态为「被 ADR-XXX 取代」。
这样历史可追溯 —— 能看到「当时为什么那样想」和「后来为什么改了」。

⛔ 直接改写旧 ADR = 抹掉历史，等于假装当初就想对了。

## 输出格式

**结论**：`四态: PASS | WARN | FAIL | UNKNOWN`
- PASS = 背景有约束、选项含「不做」、后果含重考条件、非目标明确
- WARN = 有缺项（列出缺什么）
- FAIL = 只有结论没有选项 / 没有理由 / 把 ADR 写成教程
- UNKNOWN = 背景事实无法核实（缺数据/缺记录）

正文按上面九节结构写。每节至少一句话，不允许空着。

## 假阳性清单（这些不算 ADR 缺陷）

- 选项只有 2 个（2 个足够时不必凑 3 个）
- 决定与直觉相反但理由充分（那是好 ADR）
- 没有量化数据（当时确实没有测量条件，但要写明这一点）
- 篇幅很短（决定本身简单时，短 ADR 优于注水长文）

## 假阴性清单（最常漏的 8 类）

1. **没有约束**（只写问题），后人无法理解为何不选更好的方案
2. **没有「不做」选项**，等于假设「必须做」
3. **被否选项只写坏处**（事后合理化）
4. **理由与背景脱节**（理由里出现背景没提的约束）
5. **没有「重新考虑的条件」**，决定变成永久教条
6. **没有非目标**，后人反复问「为什么不做 X」
7. **改写了旧 ADR**（抹掉历史）
8. **写成教程**（大段 how-to，占了 ADR 的位置）

## 本仓库可用的命令

　　`node tools/quality/verify-docs.mjs`（ADR 若被 README 索引，检查索引是否覆盖）
　　`node tools/quality/audit-doc-numbers.mjs`（ADR 里引用的数字要与实测一致）

## 与其他技能的关系

- `design-review`：决定**之前**评审方案；通过后写 ADR
- `doc-write`：ADR 里「怎么用」的部分转给它
- `changelog`：ADR 记「为什么」，changelog 记「什么时候改了什么」
- `refactor-plan`：ADR 决定的结构变更，用分期计划落地
- `dep-upgrade`：升级依赖若涉及不可逆选择，也应有 ADR

## 边界（如实说清）

- ADR 只能记录**当时已知的**信息；当时不知道的因素无法补进去（可以追加「事后补充」但不要改原文）
- 无法验证「理由是否真实」—— 决策者可以事后合理化，ADR 只能约束形式不能约束诚实
- 有些决定是政治/人事原因，不适合写进 ADR；此时至少写明「非技术原因」，不要编造技术理由
- 大量微小决定不值得写 ADR；写太多会让重要 ADR 被淹没
- 本技能不判断决定对不对，只保证决定被完整记录
