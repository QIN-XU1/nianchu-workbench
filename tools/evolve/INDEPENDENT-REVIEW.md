# 独立验证协议

> **这份文档定义「独立验证方」到底要做什么。**
>
> 起因：本体论的 C5 要求「改进会被独立验证 —— 验收方与实现方不是同一个」。
> 台账 H-0001 因此被判 `partial` 而不是 `closed`。
>
> **但如果只是换个人说「我看了，挺好的」，那不是独立验证，是换个签名。**
> 所以这份协议把独立验证定义成一件**对抗性**的工作。

---

## 一、独立验证方的工作是「证伪」，不是「确认」

| | 不独立（我自评） | 独立（本协议） |
|---|---|---|
| 任务 | 证明我对了 | **找出我哪里错了** |
| 成功判据 | 结论与我的主张一致 | **要么找到一个可复现的反驳，要么证明「我尽力了但找不到」** |
| 产出 | 「通过」 | 「反驳清单」或「穷尽过的攻击面清单」 |
| 失败的样子 | — | 说「看起来没问题」（那是没干活） |

**独立验证方的产出里如果没有任何攻击记录，这次验证无效。**

---

## 二、必须回答的四个问题

对每一个待验证的主张，独立验证方要给出**带证据的**回答：

### Q1 证据是否真实存在？
不许看结论文字，**必须自己打开文件核对**：
- 声称的 `路径:行号` 真的存在吗？那一行真的是那个意思吗？
- 声称的数字真的能在文件里找到吗？
- 有没有「证据指向的文件被改过，但证据没更新」？

### Q2 度量本身可信吗？
- 指标的定义是否可能被「优化」而不是被「改进」？（Goodhart）
- 基线值是怎么得到的？能否复现？
- 样本量够吗？两次结果真的一致吗？
- **度量工具自己会不会出错？**（本轮实测：度量工具确实出错过 —— 残留探针污染基线、树脏时假通过）

### Q3 反例是否真的会失败？
- 声称「有反例」的检查，**故意注入违规，它真的会红吗？**
- 反例覆盖的边界够吗？（只测「显然该拒」的不算 —— 要测**模糊边界**）
- 有没有「这个检查永远通过」的情况？

### Q4 结论有没有超出证据？
- 结论的措辞比证据强吗？（「证明了」vs「支持」「一致」）
- 有没有把「没找到反例」说成「证明了」？
- 有没有把「环境不在」说成「产品缺陷」，或反过来？

---

## 三、可以打的分（三档，不许给第四档）

| 档 | 含义 | 判据 |
|---|---|---|
| `refuted` | **找到可复现的反驳** | 能给出复现步骤 + 实际结果 ≠ 声称结果 |
| `not-refuted` | 尽力攻击但没推翻 | **必须附攻击面清单**（试过什么、结果如何） |
| `unverifiable` | 证据不足，判不了 | 说明缺什么才能判 |

⛔ **不许给「基本通过」「大致正确」这类档** —— 那是模糊，不是判定。

---

## 四、独立验证方的资格

算「独立」需要满足**全部三条**：

1. **不是实现方**（不同的人或不同的 agent 实例）
2. **没有参与该主张的形成过程**（不共享「我为什么这么写」的上下文）
3. **有动机找错**（任务就是证伪，不是为了确认）

**光换个人签名不算独立。**

---

## 五、记录格式（写进台账的 verifier 字段与 notes）

```json
{
  "verifier": "<谁>",
  "independenceBasis": "<为什么算独立：1/2/3 三条怎么满足>",
  "verdict": "refuted | not-refuted | unverifiable",
  "attacks": [
    { "surface": "<攻击了什么>", "method": "<怎么攻的>", "result": "<结果>" }
  ],
  "evidenceChecked": ["<核对了哪些 路径:行号>"],
  "limits": "<这次没能攻到的地方>"
}
```

**`attacks` 为空 ⇒ 验证无效**（见第一节）。

## 六、对本次待验证对象的说明（H-0001）

待验证的主张：

> 修掉 1 个真 bug（`audit-coverage.mjs` 无退出码）+ 4 个故障定义错 + 2 个度量器健壮性问题后，
> `recall` 从 0.750 升到 1.000，`fpr` 从 0.375 降到 0.000，且两轮结果完全一致。

**实现方**：lead（本会话）

**独立验证方应该重点攻击的地方**（提示，不是答案）：
- `recall` 是不是被「改成更容易通过」而不是「真的更能发现问题」？
  具体：故障目录是**我写的** —— 如果我写的 8 条故障恰好都是这些验收器容易抓的，
  那 recall=1.000 只证明「我挑了好抓的题」
- `fpr=0.000` 是不是因为基线判据被我放松了？
  具体：`expectOutput` 是我加的 —— 它会不会让某些真误报被算成通过？
- 「两次一致」是不是因为两次都跑在同样的错误前提上？
- `audit-coverage.mjs` 的修复：**它现在真的会在该红的时候红吗？**
  还是只是「加了 process.exit 但判的是错的对象」？
