# 界面编排设计（v3）

> 本文回答一个具体问题：**技能 / MCP / 工具 / 模型 / 智能体这些「能力」，在界面上到底放在哪。**
> 这是 v1 / v2 没回答的问题，也是它们被判「设计逻辑有问题」的原因。

---

## 一、v1 / v2 错在哪（结构性，不是排版）

| 版本 | 布局单位 | 结果 |
|---|---|---|
| v1 | 6 个停靠面板塞进三栏 | 三栏等权重、4 个面板标题、没有主角 |
| v2 | 3 个停靠面板（每栏一个） | 主角确立了，但**仍然只有面板** |

**根本错误：只有「面板」，没有「页面」。**

面板适合承载「正在进行的活」——对话、文件、验证结果。
但技能、MCP、工具权限、模型供应商、智能体组合，这些东西需要的是**整页、可列表、可增删改**的界面。
把它们塞进一个小面板，必然塞不下；不给它们位置，用户就会问「这些该放哪」。

系统里没有页面这个概念，就没有地方安放它们 —— 这是信息架构缺口，不是视觉问题。

---

## 二、三个参照系统的做法（源码级证据）

### 2.1 AionUi（`D:\refs\aionui\AionUi-main`，1521 文件 / 69.1MB 全量）

设置用 **模态 + 标签页**，内置标签页枚举是硬编码的：

```
packages/desktop/src/renderer/components/settings/SettingsModal/index.tsx:58
  export type BuiltinSettingTab = 'model' | 'agent' | 'tools' | 'webui' | 'system' | 'about';
```

同文件 `:190-230` 的 `menuItems` 构建了左侧菜单：`model`（模型/供应商）、`tools`（工具）、
`webui`、`system`、`about`。**MCP 归在 `tools` 里**（`renderer/hooks/mcp/`）。

设置里还有独立的整页（不是模态标签页）：

```
packages/desktop/src/renderer/pages/settings/
  AgentSettings/  AppearanceSettings/  ArchivedSettings/
  AssistantSettings/  SkillsSettings/  ToolsSettings/
  ExtensionSettingsPage.tsx  ModeSettings.tsx  PetSettings.tsx
  SystemSettings.tsx  WebuiSettings.tsx
```

**关键设计：扩展标签页带锚点，可以插到内置标签页前后。**

```
SettingsModal/index.tsx —— extension tab 的 position 声明：
  position: { relativeTo: <内置 tab 的 key>, placement: 'before' | 'after' }
```

内置 tab 不在列表里时，扩展落到「未锚定」组。这是**第三方扩展往设置里加页**的正式通道，
不需要改内置代码。对我们是直接可借的：技能 / MCP 的连接器就是扩展，它们应该能自己插设置页。

主窗口布局数学也很具体（`pages/conversation/utils/layoutCalc.ts`）：

```
MIN_CHAT_PANEL_PX = 360        MIN_PREVIEW_PANEL_PX = 340
MIN_WORKSPACE_PANEL_PX = 220   MAX_WORKSPACE_PANEL_PX = 500
DEFAULT_WORKSPACE_PANEL_PX = 260
PREVIEW_REGION_CHROME_PX = 24   // ml-8 + mr-12 + 两侧 1px 边框 + 余量
titleAreaMaxWidth = clamp(320, containerWidth - 520, 820)
```

结构是 **[左：会话栏] [中：聊天 | 预览] [右：工作区（固定 px，可折叠）]**，
并且**聊天区吸收视口变化**，工作区固定像素。左栏拖到 <200px 吸附收起。

侧栏条目可排序且顺序持久化，`components/layout/Sider/siderOrder.ts` 里
`reconcileStoredSiderOrder()` 的做法是：**丢掉已不存在的 id，把新出现的 id 追加到末尾**。

### 2.2 omp-studio

十个真实页面：`HomePage / History / Statistics / Evaluation / Media / AgentHub /
CapabilitiesPage / ModelConfig / Settings / Diagnostics`。

**技能与 MCP 收在 `CapabilitiesPage`；智能体独立成 `AgentHub`；模型独立成 `ModelConfig`。**
与 AionUi 的结论一致：能力是**页面**，不是工作区里的面板。

### 2.3 Orca

IDE 形态：编辑区 + 智能体侧栏 + 设置。能力同样在设置里，不在主工作区。

### 2.4 三者一致的结论

> **主工作区只放「正在干的活」；能力是另一个区域，用页面承载。**
> 而且能力必须能**被配置**（增删改、开关、连接状态），不能只是展示。

## 三、我们的编排方案

### 3.1 两级导航：一级分区 + 二级列表

```
┌──────────── 侧栏 268px ────────────┬──────────── 主区（路由）────────────┐
│ 工作区切换  架构梳理               │ 标题栏（当前对象 + 主操作）          │
│ 搜索（会话 / 能力 / 工具）          ├──────────────────────────────────────┤
│ ── 一级导航 ──                     │                                      │
│  会话      5                       │  会话视图   对话 + 右工作区           │
│  智能体    5                       │  能力视图   技能/MCP/工具/模型/智能体  │
│  能力      5   ← 技能/MCP 在这     │  自动化视图 定时任务                   │
│  自动化    3                       │  设置视图                             │
│ ── 二级列表（随一级切换）──         │                                      │
│  最近会话 …                        │                                      │
│ 底部：布局 / 暗 / 标准              │                                      │
└────────────────────────────────────┴──────────────────────────────────────┘
```

**一级导航四项，直接对应四类工作**，不做第五项「设置」（设置留在底部，低频）。
不用图标导轨：v1 的「台/图/务/忆/布/设」单字导轨被判为最业余的一处，已彻底删除。

### 3.2 能力的五个分类 —— 「技能 / MCP 放哪」的答案

| 分类 | 回答什么 | 每条有哪些列 |
|---|---|---|
| **技能** | 有哪些可被调用的流程知识 | 名称+说明 / 来源 / 使用范围 / 状态 / 开关 |
| **MCP** | 连了哪些外部工具服务器 | 名称+说明 / 传输(stdio·SSE) / 工具数 / 状态 / 开关 |
| **工具** | 内置工具有哪些、权限如何 | 名称+说明 / 权限(自动·需确认·禁止) / 范围 / 状态 / 开关 |
| **模型** | 有哪些供应商与模型 | 名称+说明 / 供应商 / 上下文 / 状态 |
| **智能体** | 智能体 = 模型 + 技能 + MCP 的组合 | 名称+说明 / 模型 / 组合(技能·MCP) / 状态 |

**归属三条通道，缺一不可：**

1. **能力页**（全局）—— 增删改、开关、看状态。这是它们的主场。
2. **智能体详情**（组合）—— 每个智能体勾选哪些技能 / 连哪些 MCP / 工具权限如何。组合逻辑在这里，不在能力页。
3. **会话内**（上下文）—— 输入框下方的 `6 技能 · 2 MCP` 胶囊，点开跳能力页。会话里只**看得到**当前生效的能力，不在这里配置。

这三条对应三个不同的问题：有哪些 → 给谁用 → 这次用了什么。混淆它们就是 v2 的病。

### 3.3 会话视图的编排

```
┌──────────────────── 主区 ────────────────────┐
│ 标题栏  接口审批链路加固  架构梳理 · 42 条   [工作区] │
├──────────────────────────┬───────────────────┤
│ 对话（正文 760 居中）      │ 右工作区 320px     │
│                          │ 文件/上下文/验证/变更│
│                          │                   │
├──────────────────────────┤                   │
│ 验证带 106 通过 6 待补 …   │                   │
├──────────────────────────┤                   │
│ 输入框 + 能力胶囊          │                   │
└──────────────────────────┴───────────────────┘
```

- **右工作区 320px**（借 AionUi 的 `DEFAULT_WORKSPACE_PANEL_PX = 260`，我们内容更宽取 320）
- **验证带常驻在输入框上方**：验证是我们的差异点，必须在你动手的地方，不是藏在右栏第二个面板
- **左对齐 760 与居中对齐的取舍**：v2 里「标题左对齐、正文居中」是两条打架的线；
  v3 统一为正文 760 居中、验证带用同一个 760 内容盒居中，标题栏左对齐但内容盒一致

### 3.4 配色：从「暖褐灰」换成中性灰阶

v2 用的是暖褐灰（`#16120f / #0a0908`），实测观感偏脏。AionUi 的实测数值是**纯中性灰**：

```
styles/themes/default-color-scheme.css（暗色）
  --bg-base: #0e0e0e   --bg-1: #1a1a1a   --bg-2: #262626   --bg-3: #333333
  --bg-4: #404040      --bg-hover: #1f1f1f   --bg-active: #2d2d2d
  --text-primary: #ffffff   --text-secondary: #ced3da（注释写着"提亮至 ~11:1 对比度"）
```

它的关键不是具体色值，而是**一条灰阶同时充当背景 / 边框 / 文字**（`--bg-3` 的用途注释就是「边框/分隔」），
所以整屏的灰是同源的，不会脏。我们照此结构：

```
暗色  --bg-base #0e0e10  --bg-1 #17171a  --bg-2 #202024  --bg-3 #2b2b30  --bg-4 #383840
亮色  --bg-base #ffffff  --bg-1 #f7f8fa  --bg-2 #f2f3f5  --bg-3 #e5e6eb  --bg-4 #d0d3da
```

保留我们自己的设计原则：**颜色只表示状态，不表示装饰**。
所以主色只有一个（`--primary` 蓝，用于可交互），其余颜色只用于验证四态（通过 / 待补 / 失败 / 判不了）。

## 四、这一版还没做的（诚实清单）

| 项 | 状态 |
|---|---|
| 技能 / MCP 编辑表单 | 只有列表与开关，没有编辑页 |
| 智能体的技能 / MCP 勾选 | 只读展示，不能改 |
| 工具权限的实际生效链路 | 界面只是展示，没接到真正的拦截器 |
| 面板可拖拽停靠 | v3 放弃了 v2 的停靠模型，改为固定布局 + 路由；停靠要不要回来待定 |
| 扩展往设置里插页 | 参照 AionUi 的锚点机制，未实现 |
| 数据 | 全部是示例值（8 条技能 / 4 个 MCP / 5 个智能体），没有接真数据 |

**示例数据里被抓到的一处编造**：智能体写「6 技能 / 7 技能」，但技能库当时只有 5 条。
自检断言「智能体的技能数不超过技能总数」红了，已把技能库补到 8 条。
这条断言留在验收里，防止再编。
