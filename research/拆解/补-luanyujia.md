## 二、六个值得学的治理机制

### 2.1 文档生命周期：四词状态 + 四种处置动作

**这是最有价值的一个机制。**

> 用户原话：「及时清理历史文档、更新需要的文档、合并杂乱的文档、归档有历史价值的文档。」

**① 状态只有四个词**

| 状态 | 含义 | 复核期 |
|---|---|---|
| `活` | 每次干活都读写的 | 每次动就刷日期 |
| `常备` | 半年内还会用 | **180 天** |
| `留档` | 只作证据，不再更新 | 不催 |
| `待清` | 已经没用了 | **7 天** |

**② 到期必须四选一（不许只是「留着」）**
`更新` / `合并`（**优先**）/ `归档` / `清`

**③ 归档落点固定，不许另创目录名**
场景记忆 → `<场景记忆目录>\归档\§<节>-<名字>-<YYYYMMDD>.md`
跨场景 → `<工作区>\_归档\<主题>-<YYYYMMDD>\`

**④ 合并/改名/删除 ⇒ 同一步改索引那一行**，并写进「处置记录」（只追加：日期 + 动作 + 为什么）

**⑤ 命名**：用途 + 时间。⛔ 禁 `最终版` / `v2` / `副本` / `新建文档`；同一主题**只留一份**

**⑥ 体量红线**：场景记忆主文件 ≤25KB、`§〇` ≤4KB、`SKILL.md` ≤12KB、定位卡 ≤25KB
拆法：按节搬 `归档\` + 原位留一行指针（**只搬不丢**），搬完跑 `核对拆分.mjs` 验**「丢失 0 行」**

**⑦ 节奏**：每周日 12:30 跑体检；每月 1 日 05:00 生成整理清单

**⑧ 反馈回路**：每次处置落「处置记录 + 复核日期」，**下次体检按新日期算** —— 文档池只会越用越干净

**与我们 A7 记忆治理的对比：**

| 维度 | 我们 A7 | luanyujia 2.10 |
|---|---|---|
| 过期判定 | `expiresAt` TTL | 四词状态 + 复核期（活/常备180天/留档/待清7天） |
| 过期后动作 | 标 `expired`，默认不进结果 | **四选一：更新/合并/归档/清** |
| 索引层 | 无 | **有**（索引与文件同生共死） |
| 体量红线 | 有（B4 代码 32KB） | 有（**文档** 25KB/12KB/4KB 分级） |
| 拆分正确性 | 无 | **验「丢失 0 行」** |
| 处置留痕 | 有（runs 记录） | 有（处置记录，只追加） |
| 自动化节奏 | 有（调度器种子 job） | 有（每周日/每月1日） |

**判断**：我们的 A7 在「冲突检测 + supersede 链」上更强（它没有 supersede 语义），
但它在**「处置动作」与「索引同步」**上更完整 —— 我们的 TTL 过期只是标记，它要求必须做一件事。

### 2.2 索引机制：四列 + 三硬规矩 + 三禁

**索引表就四列**：`| 文件 | 是什么 | 状态 | 复核日期 |`
**状态只有四个词**（同 2.1）

**三条硬规矩**：
1. 新建文本/文档 ⇒ **同时**登记一行
2. 删/改名/移动 ⇒ **同时**改那一行（**索引与文件同生共死**）
3. 到期自己处置 —— 更新 / 合并 / 归档 / 清

**三禁**：同一主题多份并存 · 已完成的一次性产物留在活目录 · **只删文件不删索引行**

**体检**：`索引体检.mjs`（未登记 / 死条目 / 过期 / **身份索引漂移**）
判据分级：**未登记 = ⚠，死条目/过期/漂移 = ⛔**

**判断**：「只删文件不删索引行」这条很关键 —— 索引一旦漂移就失去可信度，
和我们的「假绿」是同一类问题。

### 2.3 整树部署铁律：把「我记得」换成「机械比对」

> 来源：`oa-ai` 实测。`deploy_backend.py` 传的是**整棵本地后端工作树** ——
> 一个代理在改 `assess.js`、另一个正在改 `quiz.js`，**谁单独跑部署，就会把对方没验完的半成品传上线**。

**① 适用范围（通用）**：任何「把一整棵树推上去/盖过去」的动作 ——
部署、发布、同步、批量覆盖、`robocopy /MIR` 之类，动手前**必须先做一次只读预检**

**② 预检看什么**：打出「本地与目标之间的差异集合」，再对照「这次我自己改了哪些文件」

**③ 判据（机械的）**：
```
差异集合 == 自己的改动集合  ⇒ 才可以真做
差异里出现不是自己改的文件 ⇒ ⛔ 停手，先通知那个文件的主人
```

**④ 做不到预检就先补预检**：没有只读开关的部署脚本 ⇒ **先补一个开关，再部署**

**⑤ 部署后再打一次差异**：若又冒出别人的文件，说明**有并发者在飞**，立刻互相通知

**⑥ 帮手并行干活时尤其容易踩**

**判断**：**这条与我们 R8 判据同源。**
它的「差异集合 == 自己的改动集合」就是我们的「git 干净 + 验收器全绿」。
区别是：它明确要求**部署前后各打一次差异**（照出并发者）—— 我们只打了前一次。

### 2.4 记忆分两级：场景私有 + 全局共享，不许混

> 宿主原话：「场景有自己独立的记忆，然后总的有大家的记忆」

⛔ **这两级不许混**：写错层级 = 有的看不到（写进私有）或污染别人（写进共享）

**场景私有记忆**：一场景一份，别的场景不读、也不该读
**结构固定**：`§〇 当前交接`（**≤4KB，每次覆盖写**）+ `§一`~`§五`（**只追加**）
超 25KB 就搬 `归档\`
**谁能写**：只有该场景自己的会话（及其帮手）

**判断**：`§〇 覆盖写` + `§一~§五 只追加` 是个精巧设计 ——
把「每次都要看的最新状态」与「历史证据」在结构上分开，既保证前缀稳定（只追加部分不变），
又保证交接信息总是最新。

**对比我们的 A7**：我们没有「层级」概念，所有记忆一个池子。
在单 agent 场景下没问题，但**Agent Teams 多 agent 并行时会撞车**（谁写谁的？）。

### 2.5 共享件 / 专属件修改权：五档

> 反面教材：2026-10-17「客户助手1 与自己助手」互相往对方地盘写，内容互相覆盖污染 ——
> **专区只让一个人进门**。

| 档 | 范围 | 谁能改 | 流程 |
|---|---|---|---|
| **A 共享·宪法** | 全局铁律 / 标准化规范 / 跨场景协作 / 默认工作区 | **只有 `dg-dsh`，且必须在宿主指令下** | 改前说明理由 → 改后公告受影响方 + 记台账；⛔ 别的场景不许直接改（哪怕只改一个数字） |
| **B 共享·板与台账** | 待办板（加行）/ 通知看板 / 总索引 / 文档台账 / 体检结果 | **任何场景按规矩写** | ⛔ **不许删改别人的行**；要改结构 ⇒ 按 A 档申请；**写前必须重读** |
| **C 共享·工具与运行时** | 工具 `*.mjs` / profiles / 插件 / MCP / skills 目录结构 / 计划任务 / 环境变量 | **只有 `dg-dsh`** | 场景只能报需求/报 bug ⇒ 我改 ⇒ 公告 |
| **D 专属** | 自己的场景记忆 / 定位卡 / 自己名下的技能 / 自己的脚本产物 | **该场景自己** | ⚠ 但改「自己的规矩」必须告知 `dg-dsh` |
| **E 别人的专属** | D 档里属于别的场景的 | ⛔ **一律不许写** | 只能写请求：往对方 `§〇` 写一行，或待办板加一行 |

**判据（动手前一句话自问）**：**「这份文件属于哪一档？」**
A/C ⇒ 停手报 `dg-dsh`；B ⇒ 只写自己的、不许动别人行；D ⇒ 自由但「改自己规矩」要通知；E ⇒ 一个字都不许写

**判断**：**这套机制直接对应 Agent Teams 的写冲突问题。**
我这次拆解派了 6 个 subagent 并行，它们的写作用域是我口头分的（「你写补-exec-1.md」），
**没有任何机制强制**。如果两个 agent 同时写同一个文件，会静默覆盖。

**这是我认为 luanyujia 最值得照搬的一条。**

### 2.6 源码直跑，永不打包

> 用户 2026-10-15 明确要求

**判断**：这条与我们的处境相反 —— 我们 fork 了 OpenBitFun，必须构建。
但它的**动机**值得借鉴：不打包意味着改完立即生效、不会有「源码与产物不一致」的问题。
我们的应对是**构建产物可复现 + 验收器断言产物内容**（已做，verify-ui-layer 检查构建产物）。

## 三、优势（可验证，≥3）

1. **文档治理有完整的闭环**
   - 证据：`二-标准化规范.md` §2.10（四词状态 + 四选一处置 + 归档落点 + 体量红线 + 节奏 + 反馈回路）
   - 为什么对：**多数项目只有「写文档」，没有「文档会烂」的对策**。
     它把文档当成有生命周期的资产，且**处置动作是强制的**（不许只是「留着」）。

2. **索引与文件同生共死**
   - 证据：§2.7 三条硬规矩
   - 为什么对：索引一旦漂移就失去可信度。**「只删文件不删索引行」被列为禁止项** ——
     这与我抓的「假绿」是同一类问题的两种表现。

3. **部署铁律把「我记得」换成「机械比对」**
   - 证据：§2.14 判据「差异集合 == 自己的改动集合 ⇒ 才可以真做」
   - 为什么对：人对自己改了什么记不准，对别人改了什么更不知道。**只有比对是可验证的。**

4. **修改权五档直接解决多 agent 写冲突**
   - 证据：§6.8 表格 + 反面教材（两个助手互相覆盖）
   - 为什么对：**这是从真实事故里长出来的机制**，不是设计出来的。
     「专区只让一个人进门」是朴素但正确的原则。

5. **记忆的两级结构 + 覆盖/追加分离**
   - 证据：§6.7.1（`§〇` 覆盖写 ≤4KB + `§一~§五` 只追加）
   - 为什么对：交接信息要最新（覆盖），历史证据不能变（追加）；
     两者混在一起会导致要么丢历史、要么交接信息过期。

6. **体量红线分文档类型**
   - 证据：§2.10 ④：场景记忆 ≤25KB、`§〇` ≤4KB、`SKILL.md` ≤12KB、定位卡 ≤25KB
   - 为什么对：不同用途的文档有不同的合理体量，一刀切不对。

7. **拆分要验「丢失 0 行」**
   - 证据：§2.10 ④「搬完跑 `核对拆分.mjs` 验『丢失 0 行』」
   - 为什么对：搬运文档最容易丢内容且没人发现。**有断言才能证明没丢。**

## 四、缺点（可验证，≥3）

1. **22MB 里 72% 是启动动画**
   - 证据：`196 文件 / 21.9MB`，其中动画资源占绝大多数
   - 什么场景出问题：仓库克隆慢；且**视觉资产与机制文档混在同一树里**，
     看仓库大小无法判断它有多少实质内容。

2. **全部机制靠「自觉」执行，没有强制**
   - 证据：三份规范共 184.6KB（102.8 + 59.2 + 22.6）全是 Markdown，**0 行代码**
   - 什么场景出问题：
     - 规范说「新建文档 ⇒ 同时登记一行」，但**没有任何东西会阻止你忘记登记**
     - `索引体检.mjs` 能查出未登记，但它**依赖人主动跑**
     - 对比 ECC 的 CI 硬门（`validate-skill-host-compat.js` fail-closed），
       这套规范的强制力弱得多

3. **自己承认「无对照实验、无前后发生率」**
   - 证据：`solo-to-team-skills` 的 SKILL.md 明写（同一体系的项目）
   - 什么场景出问题：机制是否真的减少了事故，**没有数据**。
     规范里全是「实测」轶事（某次 OA 部署踩坑），但没有「执行这套规矩前后，事故率变化」。

4. **寄生式 DOM 劫持，脆弱性来自结构**
   - 证据：`面板-harness-AI会话.js` 3164 行里只有 7-813 是 AI 面板，其余 11 个渲染器是拼进去的；
     注入走 `executeJavaScript` + `MutationObserver`（`main.js:996-1175`）
   - 什么场景出问题：宿主页面一改结构就崩；且 `executeJavaScript` 的注入时机有竞态。

5. **规范文档本身违反了自己的体量红线**
   - 证据：`二-标准化规范.md` **102.8KB**，而它自己的 §2.10 ④ 规定「定位卡 ≤25KB」
   - 什么场景出问题：**规范要求别人拆文档，自己却是最大的单文件**。
     这正是「只删文件不删索引行」想防的那类不一致。

6. **README 声称的行数与实测不符，且无可信解释**
   - 证据：README 声称 `面板-harness-AI会话.js` 2717 行，实测 **3164 行**
   - 什么场景出问题：元数据不可信会让「核对」失去意义 —— 与索引漂移同一个问题。

7. **修改权五档的 A 档是单点**
   - 证据：§6.8「A 共享·宪法：只有 `dg-dsh`」
   - 什么场景出问题：`dg-dsh` 不在时，共享规矩无法修改；且**没有备选审批人**。

## 六、要超过（≥1）

| 能力 | luanyujia 现状 | 我们怎么做 | 怎么验证 |
|---|---|---|---|
| **规范要可强制** ★核心 | 184.6KB 规范全靠自觉，0 行代码 | 每条规矩配一个**可运行断言**，违规就红 | 故意违反一条规矩，验收器必须失败。**这是它最大的弱点** |
| **机制有效性要有数据** | 自认「无对照实验、无前后发生率」 | 记录机制启用前后的指标（事故数/返工数） | 有前后对比数字，且样本量写明 |
| **文档体量红线要包括自己** | 自己的规范 102.8KB，超自定红线 | 红线对**所有**文档生效，包括规范本身 | 扫描所有 md，超红线的必须拆或豁免（写理由） |
| **索引不可漂移要机械化** | 靠 `索引体检.mjs` 但需人主动跑 | 接进验收器，每次跑都查 | 索引与文件不一致时验收器红 |
| **多 agent 写作用域要机制化** | 五档规范 + 靠自觉 | 在 Agent Teams 的任务上声明 write scope，冲突即报 | 两个 agent 同时声明同一文件时必须报错，不能静默覆盖 |
| **元数据要与事实一致** | README 行数 2717 vs 实测 3164 | 行数/文件数类元数据由脚本生成，不手写 | 元数据可复算，与实测一致 |

## 七、给我们的三条直接结论

1. **修改权五档是最该抄的一条** —— 我这次派 6 个 subagent 并行拆解，
   写作用域是我口头分的，**没有任何机制强制**。两个 agent 同时写一个文件会静默覆盖。
   这正好是 Agent Teams 的 `write_scopes` 该解决的问题。

2. **「规范要可强制」是它的最大弱点，也是我们的机会** ——
   它写了 184.6KB 规范，但 0 行代码保证执行。我们已有 `verify-goal`（18 条硬要求）这种做法，
   应该把「规矩」都落到断言上。

3. **「部署前后各打一次差异」值得加到 R8** ——
   我们现在只在提交前查 `git status`。按它的做法，构建/部署**之后**要再查一次，
   以照出并发者（这在我派多 agent 时特别重要）。

## 八、诚实边界
