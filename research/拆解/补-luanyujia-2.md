## 零、先说结论：这份文档解释了我 A15 为什么该删

`把规矩变成机制.md` 开头写了一句判据：

> **没有「会失败的检查」的规矩 = 一句口号。**
> 如果一个检查**永远通过**，它就不是检查，是装饰。

以及一张**「什么不该变成机制」**的表，其中第一条是：

| 情况 | 为什么 |
|---|---|
| **判断类**（好不好、该不该做） | **没有客观判据，硬写成检查会误杀** |
| 一次性 | 写机制的成本高于收益 |
| **靠人拍板**（要不要花钱、要不要对外） | 这类必须留给人 —— **机制负责「提醒」，不负责「决定」** |

判据：**「这条规矩能不能写成『条件 + 差异集合』？能 ⇒ 机械化；不能 ⇒ 留在规矩层，但要写清『谁来判』。」**

**对照我做的 A15**：
- 「这个操作该不该放行」= **判断类**，不是「条件 + 差异集合」
- 我把它写成了 `tools/guard/gate.mjs`（应用层判断 + 自检 27 项 + 对抗日志 6/6 拦住）
- 看起来「会失败」（有 19 个反例），**但失败方向不可接受** —— 判错一次就是把危险操作放行

**用户说「越界行为这类机制暂不做，因为一旦做错就是很大的漏洞」—— 用这份文档的语言就是：
它属于「判断类」，硬写成检查会误杀（或漏杀，两者都是漏洞）。**

正确的做法不是「做得更小心」，而是**把它留在规矩层，并写清「谁来判」**——
由 OS 沙箱判（Trae 用 bwrap）、由用户在审批时判，而不是由我的正则判。

**这条我要写进我们自己的规范。**

## 一、把规矩变成机制：五步法

```
第 1 步  写清「违规长什么样」
         ── 必须是可判定的（能写成条件），不能是形容词
         ❌「索引要完整」     ✅「文件存在但索引里没这一行」
         ❌「记忆不要太长」   ✅「§〇 超过 4096 字节」

第 2 步  找到唯一的判据出处
         ── 同一个判断只写在一个地方（一个工具/一节规范），别两处各判一次
         ⛔ 两处判据 = 两份结论 = 早晚打架

第 3 步  写一个能 exit 非 0 的检查
         ── 输出必须能说出「差异集合」，不是只给一个 0/1
         ❌「体检通过」
         ✅「⛔ 3 项：未登记 2（a.md / b.md）· 死条目 1（c.md）」

第 4 步  给它一个「应当失败的反例」
         ── ⛔ 这一步 90% 的人会漏，也是最容易自欺的地方
         做法：故意造一个违规样本，确认它会报；再把样本恢复
         判据：**反例不报 = 这个检查是假的**

第 5 步  挂到节奏上
         ── 手动跑的检查等于没跑
         落地：计划任务（每周/每天）· 或「每次改完必须跑」的硬性流程
         再加一条：⛔ 检查失败的输出要进「待办」，不能只躺在日志里
```

### 1.1 与我们现有做法的对照

| 步骤 | 我们做到了吗 | 证据 |
|---|---|---|
| 1 违规可判定 | ✅ 大部分 | `audit-coverage.mjs`（八维度阈值）、`size-guard.mjs`（32KB 红线） |
| 2 判据唯一出处 | ⚠ **部分违反** | `audit-matrix-honesty.mjs` 与 `render-matrix.mjs --check` 都在判「证据是否合格」——**两处判据** |
| 3 输出差异集合 | ✅ 做到了 | 矩阵审计输出「疑似假绿: 10」+ 逐条列表；不是 0/1 |
| 4 **应当失败的反例** | ⚠ **部分** | `gate`/`injection-scan` 有 19 反例；但 `audit-coverage` **没有反例** |
| 5 挂到节奏上 | ✅ 做到了 | `tools/schedule/seed.mjs` 三条 job（每小时 verify-goal / 每6小时采状态 / 每天质量） |

**第 2 步我确实违反了** —— 「证据是否合格」这个判断在 `render-matrix.mjs`（模糊词表）和
`audit-matrix-honesty.mjs`（假绿检测）里各判一次。**两份结论早晚会打架。**

### 1.2 这条对 A15 的直接教训

**「反例不报 = 这个检查是假的」** —— 我的 `gate.mjs` 有 19 反例，看起来达标。
但**反例是我自己造的**（`C:/Windows/evil.dll` 这类显然该拒的）。
**我没有造「边界模糊」的反例** —— 比如：
- 符号链接指向围栏内但实际在围栏外
- 大小写在不同文件系统上的差异（NTFS 大小写不敏感，但挂载的 ext4 敏感）
- UNC 路径 `\\?\C:\...`
- 短文件名（8.3 格式）

这些才是真正会漏的地方。**我没有测它们，就等于不知道它会不会漏。**

## 二、多 agent 协作的五条硬约束（从真实事故长出来的）

### 2.1 规矩 10｜禁止无限对话 —— 最有价值的一条

**来源是用户 2026-10-17 14:15 的实测投诉**：

> 「他们之间处理回执都很慢一直无限对话」

**现象（实测数字）**：5 条帮手与 `oa-ai` 互发**技术长文**，助手2 **262 轮** · 助手4 **224 轮** · 助手5 **101 轮**
（前一晚分别只有 2/3/1 轮），把余额烧到
`Insufficient Balance (ACCOUNT_QUOTA, 402)`（04:19 停摆）⇒ 用户 12:15 归档助手 2/3/4/5。

**抓手**：`读会话尾巴.mjs --to <会话> --tail 6 --snip 160` 零打扰看「它在跟谁聊」；
**同一会话一小时内轮数增长 > 30 ⇒ 怀疑循环对话**。

**判据（一条）**：**一次派单 = 一条回执 = 结束**

| 约束 | 内容 |
|---|---|
| 回执长度 | **≤200 字 / ≤10 行**，只写「结论 + 证据（跑了什么、几条通过）+ 落盘路径」 |
| ⛔ 禁止 | 不许在回执里提新问题；不许把技术讨论塞进消息（**要讲细节就写文件，回执只给路径**） |
| 提问时机 | 要问就**开工前一次问清**；⛔ 不许连环问 |
| **调度方不回「收到」** | 回执是**单向**的，收到即结案（要记账就改台账 `ack`，别回消息） |
| 来回上限 | **同一任务最多 2 个来回**（派单→回执；仅当缺关键信息才允许一次澄清），超了 ⇒ 停手、写成文件、报用户 |
| **帮手之间禁止互发消息** | 只能 → 调度方或用户；两个帮手要协作 ⇒ **调度方拆成两份单**分别派 |
| **成本闸** | 见到 `Insufficient Balance` / `ACCOUNT_QUOTA` / `402` ⇒ 立即停所有派单并报用户 |

### 2.2 规矩 7｜没人认领的任务不许烂在那儿

- 「没人认领」的四种定义：① 台账挂着但没写归谁 ② 写了归谁但对口场景明确不管
  ③ 跨场景扯皮两边都说「不该我」 ④ 自己发现的问题不属于任何场景
- **派单必须 `--wake`（真发进会话），只落盘等于没通知**
- **依据是真实投诉**：2026-10-16 用户说「你这边派单他们没反应啊」——
  当天 **36 条通知里只有 8 条真发进会话**，其余全躺在对方记忆里、要等用户点开那个面板才看得见
- 抓手：`通知场景.mjs` 自己会判 —— 没加 `--wake` 又像派单 ⇒ 打醒目 ⚠ + 小结带 `未唤醒（疑似派单）N`
  （**只警告、绝不自动加 `--wake`**）
- ⛔ 禁止：看到无主任务**当作没看见**；把无主任务**堆在看板里反复刷**（那只是通知不是认领）

### 2.3 规矩 8｜有对话在等回信必须告知

**触发它的真实事故**：`dg-gui` 修好了一个 P0（`sessions.mjs` 的 `KEEP_CWD` 未定义）**却没告诉任何人** ——
用户以为没修、还专门来问，**白等一场**。

- 什么算「等回信」：**只认真发进会话**的那些通知；**只落盘的公告不算**（对方压根没被打扰，别拿它去催）
- 派单方：交活时必须 `--wake` + 写明「**我在等你的回执**」+ 隔一阵跑 `待回执.mjs`
- 被派单方：**干完 / 卡住 / 干不了，都要回一句**；⛔ **不许默默修好不说**

### 2.4 回执闭环协议

> 宿主原话：「改规矩让场景之间可以互相回执聊天，这样才能协作，然后任务做完要通知闭环防止无限聊天」

三条铁律：
1. **回执必须投递才算闭环** —— ⛔ **只在自己窗口里回答 = 没闭环**，发起方收不到（它会以为你还没干完）
2. **完成即闭环（链路在第 2 条终止）** —— 回执用 `【不需要回执·知悉】` 发出 ⇒ 发起方不再回复
   （「收到知悉一个字都不许回」）；只有确实需要追问才发第 3 条 ⇒ **全链路封顶 3 条**
3. ⛔ 不要为了「表示收到」再回一条 —— **那正是无限对话的开端**

### 2.5 发完就结束，不要在 turn 里等

> 原话：「你测试的时候应该发完消息结束，它发过来的自然就到了对话框」

- ✅ 正确：发完 `--wake` ⇒ **本 turn 直接结束**；对方回执作为一条消息进入本会话 inbox，**下一轮自然看到**
- ⛔ 错误：在 turn 里 `sleep` 几十秒再 `读会话尾巴` 找回执 ——
  既浪费一轮时间，还会**误判**（对方的回执发进我的 inbox，**不写在它自己的日志里**，翻日志看不到）

**这条与我自己的系统纪律一致**（「end your turn instead of sleeping or polling」），
但它给了**为什么**：对方的回执进的是我的 inbox，不在对方的日志里，**所以翻日志一定看不到**。

### 2.6 重叠时听谁的（判据表）

按**目录归属**决定听谁的，而不是按「谁先动手」或「谁更懂」：

| 撞车的地方 | 听谁的 |
|---|---|
| `外壳\**`（界面/场景/渲染器/IPC/样式） | `dg-gui` |
| `外壳\**` 里「盘容量/清理」相关 | `pc-cleanup`（它自己的资产；界面改动仍由 `dg-gui` 落地） |
| `外壳\renderer\` 里行情渲染器 | `stock-analysis` |
| `引擎\`（源码/构建/技能与插件机制） | `dg-dsh` |
| `引擎\.dsh\skills\<技能>\` | **谁的场景谁维护**；通用技能归 `dg-dsh` |
| **清理相关（任何目录）** | `pc-cleanup`；**别人只提请求不动手** |
| OA 的任何东西 | `oa-ops` |

**判断**：这张表把「写冲突」变成了「按路径查表」—— **不需要协商，查表即可**。
与修改权五档（A~E）配合，形成完整的写作用域机制。

1. **合并「证据合格性」的两处判据** —— 现在 `render-matrix.mjs --check`（模糊词表）与

2. **给 `audit-coverage.mjs` 补「应当失败的反例」** —— 它现在没有反例。

3. **补模糊边界的反例** —— 虽然 A15 的机制已删，但这条方法论要用到现有检查上：

   `verify-ui-layer` 的模糊边界是什么？（DOM 里恰好含关键字但界面没渲染出来）

## 四、优势（可验证，≥3）

1. **有「什么不该机械化」的判据，且明确写了「机制负责提醒，不负责决定」**
   - 证据：`把规矩变成机制.md` §4 三种情况表
   - 为什么对：**不是所有规矩都该写成代码**。判断类（好不好、该不该做）硬机械化会误杀；
     「要不要花钱/要不要对外」必须留给人。**这条判据比五步法本身更重要。**

2. **五步法的第 4 步（反例）被单独强调「90% 的人会漏，也是最容易自欺的地方」**
   - 证据：§2 第 4 步原文 + 判据「反例不报 = 这个检查是假的」
   - 为什么对：**它把「自欺」变成了可判定的**。一个永远通过的检查是装饰 —— 这句判据我该抄。

3. **多 agent 协作的五条约束全部来自真实事故，每条带实测数字**
   - 证据：262 轮 / 224 轮 / 101 轮 + 402 停摆 + 36 条通知只有 8 条真发出
   - 为什么对：不是设计出来的，是**被烧钱烧出来的**。这类机制的可信度远高于拍脑袋的规范。

4. **「只落盘等于没通知」有工具级判据（不是靠自觉）**
   - 证据：`通知场景.mjs` 自己会判「没加 `--wake` 又像派单」⇒ 打 ⚠ + 小结带 `未唤醒（疑似派单）N`
   - 为什么对：**工具知道什么算「像派单」**（句子里有「请你改 / 派单 / 做完回一句 / 改完跑 xxx 复验」），
     这比人去记规矩可靠。而且**只警告、绝不自动加 `--wake`** —— 没有替用户做决定。

5. **回执闭环封顶 3 条，且在协议里就终止**
   - 证据：§补充「完成即闭环（链路在第 2 条终止）」
   - 为什么对：它把「终止」写进了协议本身（回执用 `【不需要回执·知悉】` 发出 ⇒ 对方不再回），
     而不是靠人「记得别回了」。

6. **「发完就结束」给了机制性原因**
   - 证据：「对方的回执发进我的 inbox，不写在它自己的日志里，翻日志看不到」
   - 为什么对：这解释了**为什么**不能在 turn 里等 —— 不是「浪费时间」这种软理由，
     而是**翻日志一定看不到**（信息不在那里）。软理由可以说服自己忽略，硬理由不能。

## 五、缺点（可验证，≥3）

1. **规范数量庞大但强制力弱**
   - 证据：三份规范 184.6KB + `08` 清单两份 + `13` 情报七份，**全部是 Markdown，0 行代码**
   - 什么场景出问题：
     - 规矩写在文档里靠自觉；文档越长越没人读完（`二-标准化规范.md` 单文件 102.8KB）
     - 它自己也承认这点（`把规矩变成机制.md` 标题就是「能不能活过三个月的分水岭」）
     - **但它的解法只是「把 6 条做成机制」**，还有大量条目留在自觉层

2. **它的工具都不在仓库里，无法验证**
   - 证据：`索引体检.mjs` / `文档体检.mjs` / `核对拆分.mjs` / `稳定体检.mjs` /
     `任务分诊.mjs` / `待回执.mjs` / `通知场景.mjs` / `临时哨兵.mjs` / `清理巡检.mjs` / `插件体检.mjs` —— **一个都不在包里**
   - 什么场景出问题：所有「自测 PASS 5/5」的说法**无法复核**；
     照抄文档不会通（文档自己也警告「照抄不会通」）

3. **规范文档自己违反自己的体量红线**
   - 证据：`二-标准化规范.md` **102.8KB**，而它自己规定「定位卡 ≤25KB」「SKILL.md ≤12KB」
   - 什么场景出问题：**规则制定者不守规则**，规范的权威性受损

4. **多 agent 约束是「事后补救」而非「事前设计」**
   - 证据：规矩 10 来自 2026-10-17 的实测投诉（已经烧到 402 停摆）；
     规矩 8 来自 `dg-gui` 默默修好不说的事故；规矩 7 来自「派单没反应」的投诉
   - 什么场景出问题：**每一条都是先吃亏再立规矩**。这是真实系统的常态，
     但如果一开始就有这套约束，262 轮的浪费可以避免

5. **「不要为了表示收到再回一条」与人类礼貌直觉冲突**
   - 证据：§补充「⛔ 不要为了『表示收到』再回一条 —— 那正是无限对话的开端」
   - 什么场景出问题：新加入的 agent/人容易违反（本能会回「收到」）；
     需要工具强制或协议显著化，否则依赖记忆

6. **判据表按目录归属，但目录会变**
   - 证据：§三 判据表按 `外壳\**` / `引擎\**` / `<工作区>\**` 分
   - 什么场景出问题：新增目录或目录重构时，判据表要同步更新；
     **没有任何机制检测「有目录不在表里」**
