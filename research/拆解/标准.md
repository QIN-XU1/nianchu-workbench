# 拆解标准：16 个参照项目

> 这份文件定义「拆解」到底要拆到什么程度。所有拆解报告按此执行，不达标不算完成。

## 为什么要有标准

项目里已有 9 份 `vs-*.md`（约 300KB）。盘点后发现三个问题：

1. **缺「缺点」** —— 9 份里只有 3 份写了缺点。只列优点会变成抄作业。
2. **标准不一** —— 有的按功能列，有的按代码结构列，没法横向比。
3. **证据强度不齐** —— 有的写「文件路径:行号」，有的只有描述。

所以重拆一遍，统一到同一把尺子上。

## 六个必答维度

### 1. 底层架构（Architecture）

必须回答，每项附 `路径:行号`：

| 问题 | 为什么问 |
|---|---|
| 进程模型是什么 | 决定它能做什么、不能做什么 |
| 包的划分逻辑 | 按功能？按层？按协议？决定扩展成本 |
| 通信方式 | IPC / HTTP / stdio / 事件总线 —— 决定延迟与可靠性 |
| 状态真相在哪 | 谁持有权威状态，决定一致性难度 |
| 依赖方向 | 是否严格单向，决定能不能单独替换一层 |
| 扩展点在哪 | 插件、贡献点、hook —— 决定生态能不能长出来 |

### 2. 执行逻辑（Execution）

| 问题 | 为什么问 |
|---|---|
| 一次任务的完整链路 | 从输入到回写，每一步在哪 |
| 工具注册与调用 | 工具怎么被发现、被授权、被调用 |
| 并发与取消 | 怎么同时跑多件事，怎么中断 |
| 错误处理与重试 | 失败了怎么办，会不会无限重试 |
| 上下文管理 | 怎么裁剪/压缩，丢了什么 |
| 持久化 | 什么落盘，什么只在内存 |

### 3. 功能选取（Features）

| 问题 | 为什么问 |
|---|---|
| 它有而我们没有的 | 附具体路径 |
| 它刻意没做的 | 看 docs / 注释里的取舍说明 —— 这比「有的」更有信息量 |
| 它的功能边界在哪 | 什么它明确不管 |

### 4. 界面设计（UI）

有前端才答，否则写「无独立前端」。

| 问题 | 怎么量 |
|---|---|
| 信息架构 | 画出布局骨架的层级 |
| 导航层级 | 侧栏/顶栏/标签各承载什么 |
| 信息密度 | 一屏多少可操作元素（可数） |
| 状态呈现 | loading / error / progress / cost 怎么显示 |
| 颜色体系 | 是 token 还是散落色值？**数一下颜色字面量出现次数** |
| 字号阶梯 | 有几档，跨度多大 |
| 间距体系 | 基数是多少，有没有节奏 |
| 圆角与阴影 | 几档，用在哪 |
| 动画 | 时长与缓动，用在哪 |
| 主题 | 深色/浅色怎么实现 |

### 5. 优势（Strengths）

每条必须说清 **「为什么这样设计是对的」**。

不合格：「架构清晰」「性能好」「设计精美」
合格：「工具按能力边界授权而不是按命令文本黑名单 —— 因为黑名单可被等价分解绕过，而能力边界不行（实测 6 类分解全部拦住）」

### 6. 缺点（Weaknesses）

每条必须说清 **「在什么场景下会出问题」**。

不合格：「文档不全」「有点慢」
合格：「一切皆插件导致启动要扫 338 个包 —— 冷启动在低配机器上会明显卡（实测 7953 文件 / 63MB 包体）」

## 证据规则

1. **本地源码 > 联网文档 > 二手描述**（严格按此优先级）
2. 每条结论必须附证据：`文件路径:行号` 或 `目录路径` 或 `URL`
3. 闭源产品只能引用官方文档 + 产品行为，**不许声称读过源码**
4. 读不到就写「推测」并说明依据
5. 数字必须自己数（rg / 文件统计），不许从 README 抄

## 输出要求

每条结论三段式：

```
- 结论
  - 证据：路径:行号
  - 判断：为什么对 / 什么场景出问题
```

## 拆解完成判据

一个项目算「拆完」需满足：

- [ ] 六个维度都有内容（界面维度可写「无」但要有理由）
- [ ] 优势 ≥ 3 条，每条带「为什么对」
- [ ] 缺点 ≥ 3 条，每条带「什么场景出问题」
- [ ] 至少 5 处 `路径:行号` 级证据
- [ ] 实测数字 ≥ 3 个（文件数/组件数/颜色字面量数/工具数…）
- [ ] 有「可照搬」清单（具体到模块）
- [ ] 有「要超过」清单（具体到能力 + 怎么验证超过）
