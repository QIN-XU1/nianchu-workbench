# 拆解模板 v2（2026-11-17 用户要求重做）

> 用户的批评：「你的项目拆解其实都不是很全面…… 一直埋头苦做、一直出错，
> 这些优秀的项目都有了成熟的开发为何不去直接看呢」
>
> 所以 v2 的重点从「调研」改成 **「找可抄的实现」**。
> 每份报告必须回答：**我们要抄哪个文件、抄哪几行、抄来解决我们的哪个问题。**

---

## 每个仓库必须产出的 10 段

### 1. 定位与规模（1 段）
- 一句话它是什么
- 文件数 / 主语言 / 最近 push 日期 / star
- **证据**：`<repo>/package.json` 或 `Cargo.toml` / `go.mod` 的路径

### 2. 架构骨架
- 顶层目录 → 各自职责（附路径）
- **依赖方向**：谁 import 谁，有没有单向约束（附 `文件:行号`）
- 有没有「核心 / 插件」边界？边界靠什么强制（类型？CI 脚本？目录约定？）

### 3. 【A12】插件 / 扩展机制 —— 这是重中之重
必须回答：
- 插件清单长什么样（文件名 + 字段）→ 贴真实片段
- **怎么被发现**：扫描逻辑在哪个文件哪几行
- **怎么校验**：schema？手写校验？失败怎么报
- **怎么装载**：动态 import？子进程？沙箱？
- **贡献点**：插件能往宿主里加什么（命令/面板/工具/路由/中间件）
- **隔离**：插件拿得到宿主内部对象吗？能力怎么限
- **热插拔**：能装/卸/启用/禁用吗？状态存哪

### 4. 【A13】MCP / 工具接入
- MCP client 在哪、多长、怎么起 server
- 工具列表怎么暴露给模型
- 有没有 UI 让用户管理 MCP server（增删改/启用禁用）
- 工具调用结果怎么回填

### 5. 【A11】调度 / 后台任务
- 定时任务怎么定义、怎么存、谁来 tick
- 常驻进程怎么起（systemd？内置 loop？）
- 失败重试 / 超时 / 四态

### 6. 【C1/C2】agent 循环与停止条件
- 主循环在哪个文件（贴行号范围）
- 一轮的定义（模型→工具→再模型）
- **停止条件有哪些**：max turns？预算？无工具调用？显式 done？
- 循环状态怎么持久化（断了能续吗）

### 7. 【A6/A7】记忆
- 存储形态（文件 / DB / 向量）
- 有没有溯源、冲突消解、TTL/老化
- 跨会话召回怎么做

### 8. 【D1–D5】界面
- 技术栈（React/Vue/Svelte？）
- 布局范式（分栏？画布？时间线？）
- 状态可见性：用户能看到「在做什么/花了多少/还差什么」吗
- 主题/密度/多工作区

### 9. ⭐ 最值得抄的 3 条机制（最重要的一段）
每条必须写成：
```
机制：<一句话>
位置：<文件:行号>（可多个）
为什么好：<它解决了什么我们解决不了/做错的问题>
我们抄到哪：<我们仓库的哪个文件>
```

### 10. 我们不该抄的
- 哪些是它的历史包袱 / 过度设计 / 与我们的形态不匹配
- 避免「看到就抄」导致新的复杂度

---

## 纪律

- **每个结论必须带 `文件:行号`**。没有行号的结论一律视为猜测。
- 没找到就说「未找到」，**不要凭产品名推断**。
- 不要复述 README —— README 是宣传，代码才是事实。
- 重点放在 **第 3、9 段**：我们最缺的就是插件生态，最需要的是「可抄的具体位置」。
