1. **你的记忆总量（25.6 KB）根本没到需要"检索"的规模。** 25.6 KB ≈ 8–10k token，全量注入是对的。现在上向量库是过早优化。

## 1. 顶尖团队会主动做、但你没要求的事

以下 12 条，每条都是"不做会怎样"有论文数据支撑的硬要求。

### 1.1 失效（invalidation），而不是删除，也不是只追加

- **做什么**：每条事实带两个时间轴——「何时为真」（valid time）和「系统何时知道」（transaction time）；事实被推翻时**不删**，把旧的标 `t_invalid = 现在`，新事实保留 `t_valid`。查询默认只取 `t_invalid IS NULL` 的边。
- **为什么必须**：你的 `§五 坑与决策` 只追加，第 3 条决策和第 11 条决策如果冲突，文件里两条都在，AI 读到哪条看运气。bi-temporal 让"当时是对的、现在过时了"这件事变成**可查询的状态**，而不是靠人记。
- **不做会怎样**：arXiv **2610.36308**《When Retrieval Is Not Enough: Obsolete Facts in Agent Memory》实测——Qwen2.5-7B 在 6K 历史上，检索预算从 64 token 增到 512 token，准确率**从 45% 掉到 32%**；把一条无关证据换成一条过期竞争事实，准确率**从 100% 掉到 44.6%**。也就是说：**检索得越多、过期事实带进来越多、越差**。你不做失效，增加检索就是负收益。
- **出处**：Graphiti 时间知识图谱（arXiv **2501.13956**，Zep）；GitHub `getzep/graphiti`（32.7k stars，2026-11-09 仍在推送）。Graphiti 官方文档明确：episode 是节点，实体通过 `MENTIONS` 边连到 episode，`reference_time` 记录时间戳——"Episodes enable querying for information at a point in time and understanding the provenance of nodes and their edge relationships"（`help.getzep.com/graphiti/core-concepts/adding-episodes`）。

### 1.2 写入是"决策"，不是"追加"

- **做什么**：新信息进库前，先检索语义相近的旧记忆，然后让 LLM 在四个操作里选一个：**ADD / UPDATE / DELETE / NOOP**。NOOP 是"这条已知，不写"。
- **为什么必须**：这是去重和冲突消解**同一个机制**。没有 NOOP，重复写入会把同一事实堆成 N 份；没有 UPDATE，矛盾事实共存；没有 DELETE，过期事实永生。
- **不做会怎样**：`记忆约定.md` 写"只记结论，不记过程（≤10 行/次）"，但没有任何机制阻止同一结论被交接 5 次写 5 遍。文件涨到 25 KB 上限后，唯一的出路是人工归档——而归档不是失效，是把过期事实搬到旁边，AI 依然可能读到。
- **出处**：arXiv **2504.19413**《Mem0》§2.1 原文：*"The LLM itself determines which of four distinct operations to execute: ADD for creation of new memories when no semantically equivalent memory exists; UPDATE for augmentation...; DELETE for removal of memories contradicted by new information; and NOOP when the candidate fact requires no modification."* 完整流水线是 extraction + update 两阶段。

### 1.3 时间衰减 + 重要度 + 相关度 三因子排序

- **做什么**：检索打分不是单一相似度，而是 `score = α·recency + β·importance + γ·relevance`，其中 recency 是指数衰减。
- **为什么必须**：纯相似度检索会让"三个月前讨论过、已经废弃的方案"和"昨天刚定的方案"同分。衰减让新结论天然占优。
- **数据**：Generative Agents 的衰减因子是 **0.995**（按"自上次被检索以来经过的小时数"衰减）；importance 直接让 LLM 打整数分。
- **出处**：arXiv **2304.03442**《Generative Agents》§4.1 原文：*"we treat recency as an exponential decay function over the number of sandbox game hours since the memory was last retrieved. Our decay factor is 0.995."* 另见 arXiv **2305.10250**《MemoryBank》，显式采用艾宾浩斯遗忘曲线，按"时间 + 相对重要度"决定遗忘与强化。

### 1.4 来源追溯（provenance）——每条记忆必须能指回它的出处

- **做什么**：每条记忆不是一个字符串，而是一个带指针的对象：`{内容, 来源文件/URL, 来源会话 id, 产生时间, 由谁写入, 置信度}`。
- **为什么必须**：没有 provenance，(a) 无法判断该不该信；(b) 无法在源头变更时级联失效；(c) 无法审计"这条结论是谁说的"。你的场景记忆里 `§五` 有一堆决策，但没有一条注明"基于哪次会话、哪个文件"。
- **标准**：**W3C PROV-O**（`https://www.w3.org/TR/prov-o/`，HTTP 200 已验证）。这是来源追溯的**正式 W3C 推荐标准**，提供 `Entity / Activity / Agent` 三元 + `wasGeneratedBy / wasDerivedFrom / wasAttributedTo` 关系。你不需要全盘实现，但字段命名应与之对齐。
- **工程参照**：Graphiti 的 episode-`MENTIONS`-实体结构（同上）；MCP 官方知识图谱记忆服务器把记忆拆成 `Entity{name, entityType, observations[]}` + `Relation{from, to, relationType}`，并明确要求 observation **"Should be atomic (one fact per observation)"**（GitHub `modelcontextprotocol/servers`，`src/memory/README.md`）。

### 1.5 反思 / 巩固（consolidation）——后台把碎片合成高层结论

- **做什么**：不只在会话中写记忆，还要有**离线进程**定期回看近期记忆，把 N 条碎片合成 1 条更高层的结论，并更新/废弃底层碎片。
- **为什么必须**：会话中写的永远是"过程碎片"。不巩固，记忆库只增不减、只碎不合，最终全是没法直接用的碎片。
- **业界做法**：
  - Generative Agents 的 **reflection**：把记忆流合成为更高层推断（arXiv 2304.03442）。
  - **Letta 的 "dreaming"**：后台子代理 review 近期对话、consolidate lessons、更新记忆。触发条件是 `"step-count" | "compaction-event" | "off"`——即**每 N 步**或**上下文压缩时**自动跑，`behavior: "auto-launch"` 直接起后台子代理（`docs.letta.com/agent-sdk/memory/index.md`，已抓 `.md` 源文件核验）。
  - **A-MEM** 的 "memory evolution"：新记忆进来时，**反向更新已有记忆的上下文描述与属性**，让记忆网络自我精炼（arXiv **2502.12110**）。
- **成本证据**：arXiv **2504.13171**《Sleep-time Compute》——把"离线预想用户会问什么并预计算"做进去，达到同等准确率所需的 test-time compute **降低约 5 倍**，准确率还能再涨 13%（GSM-Symbolic）/ 18%（AIME）。

### 1.6 分层抽象，而不是平铺文件

- **做什么**：同一批内容存多个粒度——原始片段 / 会话级摘要 / 主题级摘要 / 全局摘要。
- **为什么必须**："这个项目整体在干什么"这类问题，平铺文件永远答不了，因为答案不在任何单个文件里，而在文件之上。
- **出处**：
  - **RAPTOR**（arXiv **2401.18059**）：递归地 embed → cluster → summarize，自底向上建摘要树，检索时跨抽象层取。QuALITY 基准上配 GPT-4 **绝对提升 20%**。
  - **GraphRAG**（arXiv **2404.16130**）：LLM 先抽实体知识图谱，再为紧密关联的实体群**预生成 community summary**；回答全局问题时逐 community 生成部分回答再汇总。这正是"全局问题 RAG 答不了"的解法。
  - **MemGPT**（arXiv **2310.08560**）：主上下文 / recall / archival 三级 + 中断控制流，类比操作系统在快慢存储间搬数据。

### 1.7 上下文预算必须是硬不变量

- **做什么**：每层记忆有字节/token 上限，超了就是构建失败。
- **业界做法**：Claude Code 的 auto memory **"Loaded into every session (first 200 lines or 25KB)"**（`docs.anthropic.com/en/docs/claude-code/memory`，已核验原文）。Anthropic 明确区分两种记忆：CLAUDE.md 是"你写的指令"，auto memory 是"AI 自己写的学习"，**两者都在每个会话开头加载**。
- **你已有的优势**：`记忆哨兵` 的 INV-1/2/3（注入层 ≤2048B、§〇 ≤4096B、主文件 ≤25600B）与这条业界实践**同构**，且你比 Claude Code 多了"每场景分片"。这条要保留，别推翻。

### 1.8 "即时检索"优先于"预先注入"（progressive disclosure）

- **做什么**：不在开头把所有东西塞进上下文，而是**保留轻量标识符**（文件路径、查询语句、URL），让 agent 在运行时按需加载。
- **原文**：Anthropic《Effective context engineering for AI agents》(2025-09-29)：*"agents built with the 'just in time' approach maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools... This approach mirrors human cognition... The metadata of these references provides a mechanism to efficiently refine behavior... file sizes suggest complexity; naming conventions hint at purpose; timestamps can be a proxy for relevance."*
- **对你的意义**：你的 `_文件索引.md` + `记忆地图` 其实就是这套。**方向是对的**，缺的是"索引里没有可用于判断的信号"——没有大小、没有时间、没有一句话摘要，AI 无法据此决定该读哪个。

### 1.9 记忆安全：跨会话提示注入是独立攻击面

- **做什么**：把记忆当成**不可信输入**处理。写入前做来源分级（用户原话 / 工具输出 / 网页抓取 / 其他 agent 的消息），读取时按来源打标，来自低信任源的指令**不得升级为规则**。
- **为什么必须**：你的 `发消息.mjs` 是跨场景写文件通道，`_跨场景通知.md` 会被对方场景当上下文读。这就是一条**没有校验的记忆写入 API**。
- **证据**：arXiv **2611.01700**《MemHarmBench》——恶意指令被存进记忆后，**即使原始攻击内容已被删除**，在新会话里依然生效；而且"cross-session attacks can remain behaviorally stealthy: agents often complete tasks..."（表面上任务正常完成）。另见 arXiv **2611.09721**《MemoryDojo: Benchmarking Poisoning Through LLM Agent Memory》。
- **不做会怎样**：你会有一个"能正常干活、但持续执行某人植入的规则"的工作台，且没有任何哨兵能发现——因为你的 9 个哨兵全在验结构，没有一个在验内容来源。

### 1.10 净价值核算：记忆经常是负收益

- **做什么**：任何记忆机制上线前，必须与 **Raw-RAG 基线**（对原始历史做 dense retrieval + rerank）对比；报告"收益 - 成本"，成本包括构建、存储、暴露的 token 与延迟。
- **证据**：
  - arXiv **2610.30755**《Is Complex Agentic Memory Always Needed?》——Raw-RAG 在 LoCoMo / LongMemEval / MEME / MemoryAgentBench 四个基准、七个"基准×模型"设置里**六次排第一**，比最强 agentic memory 高 0.13–5.53 分。原因是"higher coverage of necessary evidence can offset lower utilization"。
  - arXiv **2610.34073**《Memory Tax》——把净价值拆成 **memory benefit** 与 **memory tax**："many dedicated memory systems underperform naive RAG in many cases, indicating a negative net value"。
- **对你的意义**：这条是你最该先读的。你现在的对比对象不是 Mem0/Letta，是"直接把 117 份方案文档 + 会话历史丢给模型"。

### 1.11 四个能力的评估口径（不是只看答对率）

- **做什么**：记忆能力拆成四个正交能力分别测，而不是一个总分。
- **出处**：arXiv **2507.05257**《MemoryAgentBench》（ICLR 2026，GitHub `HUST-AI-HYZ/MemoryAgentBench`，486 stars）——四能力为 **accurate retrieval / test-time learning / long-range understanding / selective forgetting**。"selective forgetting" 被单列为一项能力，说明**会忘**和**会记**同等重要。

### 1.12 诊断可归因：错误要能定位到"哪一步错了"

- **做什么**：检索失败和生成失败要**分开记分**。
- **证据**：arXiv **2610.36308** 开头即指出 —— *"Memory-agent benchmarks often collapse retrieval and answer generation into one score, making it hard to tell whether a failure comes from missing an update or from not using an update that was already retrieved."* 另见 arXiv **2610.25373**《MemDerive》，用 Datalog 推导 gold derivation DAG，然后**逐节点探测**来定位失败，能测出"最终答案型基准藏起来的失败"。
- **对你的意义**：你 `机制体检` 输出的 `diffs` 已经是"差异集合"思路（AGENTS.md §4 要求"跑完要能说出差异集合，不是只给一个 0"）——**这个设计是对的**，但差异集合里全是结构项，没有一项是"召回错了"。

| **OpenTelemetry GenAI semconv** | `opentelemetry.io/docs/specs/semconv/gen-ai/` | 已核验，**v1.45.0**，含 MCP 段 | 记忆读写的**遥测约定**：把 recall/retrieve 当 span 打点，才能算延迟与命中 |

**明确"未找到"**：目前**没有**针对"agent 记忆系统"的 ISO / IEEE / W3C 正式标准。PROV-O 是通用溯源标准，MCP 是接口协议，OTel 是遥测约定——三者都不是记忆语义标准。任何声称"记忆系统有 ISO 标准"的说法，在本次核验范围内**未找到依据**。

### 2.3 数据结构：四种，不是一种

| 结构 | 长什么样 | 适合什么 | 出处 |
|---|---|---|---|
| **实体-关系-观察三元组**（最小可用） | `Entity{name, entityType, observations[]}`；`Relation{from, to, relationType}`；observation **原子化，一事实一条** | 人物/项目/文件这类有名字的东西之间的关系 | MCP `server-memory`，npm `@modelcontextprotocol/server-memory` |
| **双时态知识图谱** | 边带 `t_valid` / `t_invalid`，episode 节点 + `MENTIONS` 边，`reference_time` | 会变的事实（版本、决策、负责人） | Graphiti（arXiv 2501.13956） |
| **分层摘要树** | 叶子=原始片段，内节点=聚类摘要，逐层向上 | 长文档、"整体讲了什么" | RAPTOR（2401.18059）、GraphRAG community summary（2404.16130） |
| **记忆块 + Git 版本化文件树** | `system/` 下的文件每轮进系统提示；其余文件只暴露**文件树**，按需读 | 身份/人设这类必须常驻的少量内容 | Letta MemFS（`docs.letta.com`，已核验："Files under `system/` are in the system prompt every turn. Everything else stays out of context — the agent sees the file tree and reads what it needs."） |

**关键洞察**：Letta 的 MemFS 证明了一件事——**用文件做记忆不是落后方案，Letta 就是文件 + Git + 树形可见性**。你的问题不在"用 md"，在于 md 里的内容**没有时态、没有指针、没有触发写入的事件**。

## 3. 具体方法与工具

### 3.1 检索：混合 + RRF + 重排，不是单选

- **业界标准组合**：语义向量 + BM25 关键词，用 **RRF（Reciprocal Rank Fusion）** 融合，再做重排。
- **原文核验**：Graphiti 官方文档 `help.getzep.com/graphiti/working-with-data/searching`：*"**Hybrid Search** ... Combines semantic similarity and BM25 retrieval, reranked using **Reciprocal Rank Fusion**."* 另有 **Node Distance Reranking**：`graphiti.search(query, focal_node_uuid)`，按到焦点节点的图距离加权——实体特定问题时明显更准。
- **RRF 本身**：Cormack, Clarke, Buettcher, *Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods*, SIGIR 2009（PDF 已核验可达：`plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf`）。核心就是 `score(d) = Σ 1/(k + rank_i(d))`，`k=60` 是常用默认值。**RRF 不需要分数归一化**，这是它比加权求和好用的原因。
- **图检索**：HippoRAG 用 **Personalized PageRank** 在实体图上做单步多跳（2405.14831）——比迭代检索便宜 10–30 倍。
- **选 embedding**：必须用 **MTEB**（arXiv **2210.07316**，8 类任务 / 58 数据集 / 112 语言）挑，别凭感觉选模型。

### 3.2 写入：什么触发、怎么去重、怎么处理冲突

**触发（三种，业界都在用）：**

| 触发方式 | 谁在用 | 特点 |
|---|---|---|
| 每条消息对进来就抽 | Mem0（2504.19413） | 粒度细、成本高 |
| 每 N 步 / 上下文压缩时 | Letta dreaming：`trigger: "step-count" \| "compaction-event"` | **成本可控，且压缩点天然是"该整理"的信号** |
| 阶段结束/交接时 | 你的现状（手动 `交接`） | 最省，但**最容易忘**——零会话就是这么来的 |

**去重 + 冲突：一个机制解决**

`候选事实 → 检索 top-s 相似记忆 → LLM 判 ADD/UPDATE/DELETE/NOOP → 执行`。注意 Mem0 论文强调：*"Rather than using a separate classifier, we leverage the LLM's reasoning capabilities to directly select the appropriate operation"*——不要写一个独立的相似度阈值分类器，让模型判。

**索引侧的三个免费增益（LongMemEval 论文直接给的）：**
- **session decomposition**（按会话切，保证 value 粒度）
- **fact-augmented key expansion**（索引用事实增强的 key，不是原句）
- **time-aware query expansion**（查询时扩时间范围）

出处：arXiv **2410.10813** 摘要原文。

### 3.3 评估：这是最重要的一节

#### 三个必用基准

| 基准 | 规模/构成 | 指标 | 出处 |
|---|---|---|---|
| **LoCoMo** | 超长期对话，平均 300 轮 / 9K token / 最多 35 个会话；含 QA、事件摘要、多模态对话生成 | QA 准确率（LLM-judge）、事件摘要、多模态生成 | arXiv **2402.17753**；GitHub `snap-research/locomo`（1.27k stars） |
| **LongMemEval** | **500 题**，5 项核心能力：信息抽取 / 多会话推理 / **知识更新** / 时间推理 / **拒答** | **检索层：`recall_all@5`、`ndcg_any@5`、`recall_all@10`、`ndcg_any@10`（turn 级还有 @50）；读取层：LLM-judge 准确率 + 拒答题单列** | arXiv **2410.10813**（ICLR 2025）；数据 `huggingface.co/datasets/xiaowu0162/longmemeval-cleaned`；代码 `github.com/xiaowu0162/LongMemEval` |

#### 具体指标口径（从源码核出来的，不是猜的）

`LongMemEval/src/evaluation/print_retrieval_metrics.py` 实际输出：

```
Session-level metrics:
  recall_all@5, ndcg_any@5, recall_all@10, ndcg_any@10
Turn-level metrics:
  recall_all@5, ndcg_any@5, recall_all@10, ndcg_any@10, recall_all@50, ndcg_any@50
```

并且**评估检索时恒定跳过 30 个 abstention 实例**（"these instances generally refer to non-existing events and do not have a ground truth answer location"）。

`LongMemEval/src/evaluation/evaluate_qa.py` 的判分是 **LLM-as-judge、yes/no**，prompt 原文：
> *"Please answer yes if the response contains the correct answer. Otherwise, answer no. If the response is equivalent to the correct answer or contains all the intermediate steps to get the correct answer, you should also answer yes. If the response only contains a subset of the information required by the answer, answer no."*

**这给了你一个可直接抄的最小评估装置**：
1. 你的每道题有 `answer`（参考答案）；
2. 用固定 judge prompt 判 yes/no；
3. 检索层单独算 `recall@5`（答案所在文件/段落有没有进 top-5）。

#### 两个诊断型基准（比总分更有用）

- **MemDerive**（arXiv **2610.25373**）：用 Datalog 从事件符号化推导出 gold answer 和 **gold derivation DAG**，然后逐节点探测，定位"你漏了哪一步推导"。10 场景 / 4,692 事件 / 1,503 查询。
- **MemHarmBench**（arXiv **2611.01700**）：三视角受害者（用户 / 工作区所有者 / 外部相关方），测"移除攻击内容后攻击是否仍生效"。

## 4. 除了人和 AI，什么能证明结果是对的

### 4.1 客观数据集：有，且可下载

- **LongMemEval**：`huggingface.co/datasets/xiaowu0162/longmemeval-cleaned`，三个档位 `longmemeval_oracle.json`（只给证据会话）/ `_s_cleaned.json` / `_m_cleaned.json`。**500 题，每题带 `answer`、`answer_session_ids`（证据会话 id）、turn 级 `has_answer: true` 标注**。这是"金标准证据位置"，可以算检索指标。
- **LoCoMo**：GitHub `snap-research/locomo`。
- **MemoryAgentBench**：GitHub `HUST-AI-HYZ/MemoryAgentBench`。
- **MTEB**：挑 embedding 用（arXiv 2210.07316）。

### 4.2 可复现：基准自带跑法

LongMemEval README 给的是完整命令链（已核验原文）：

```bash
# 只算指标
python3 print_qa_metrics.py gpt-4o your_hypothesis_file.log ../../data/longmemeval_oracle.json
# 跑检索基线
cd src/retrieval && bash run_retrieval.sh IN_FILE RETRIEVER GRANULARITY
python3 src/evaluation/print_retrieval_metrics.py log_file
# 跑检索增强生成
bash run_generation.sh RETRIEVAL_LOG_FILE MODEL EXP TOPK
```

**可复现的三要素**（这套结构你可以直接搬）：
1. 固定的 gold 文件（`longmemeval_oracle.json`）——**证据位置是金标准**；
2. 检索和生成**两段分开跑、分开出分**；
3. 拒答题单列，且有明确规则"评检索时跳过 abstention"。

### 4.3 业界怎么证明"A 比 B 好"

不是靠演示，是靠**四件事同时成立**：

1. **同一基准、同一读取模型、同等 token 预算**。
2. **报两个数，不只报一个**：检索召回（`recall_all@k` / `ndcg_any@k`）+ 下游准确率（LLM-judge）。260.36308 就是在证明"只报最终准确率会掩盖失败"。
3. **报成本**：Mem0 论文的结论句式是 *"26% relative improvements in the LLM-as-a-Judge metric over OpenAI ... 91% lower p95 latency and saves more than 90% token cost"*——**收益和成本必须同时出现**，否则无法判断净价值。Zep 的句式是 *"superior performance (94.8% vs 93.4%)"* 加 LongMemEval 交叉验证。
4. **必须有 naive 基线**：Raw-RAG（2610.30755）。没有这条基线的"提升"不算数。

### 4.4 对你的直接含义

你现在**没有任何一项满足上面四条**。9 个哨兵验的是"文件结构对不对"，等价于"编译通过"，不等于"程序正确"。你需要的最小装置是：

> 20 条真实会话 → 50 道题（每题带 gold 答案 + gold 证据位置）→ 分成"检索分"和"答对分"两个数 → 与 Raw-RAG（把原始会话全塞进上下文）对比。

这个装置 1 天能搭完，比再写第 118 份方案文档有用得多。

## 5. 优先级：只做 3 件事

### 第 1 件：造出 20 条真实会话 + 一个 50 题的私有 mini-benchmark

**做什么**
- 用现有 9 个场景各跑 2–3 个真实任务，会话记录落盘。
- 每个任务出题：`{question, gold_answer, gold_evidence_path, ability_tag}`，ability_tag 用 LongMemEval 五分类（信息抽取 / 多会话推理 / **知识更新** / 时间推理 / 拒答）。
- 先跑 **Raw-RAG 基线**（把会话原文全塞进上下文 + dense 检索），拿到 baseline 分。

**为什么这是第 1 件**
- 你的 `记忆哨兵` 全部不变量都是字节数——**结构正确但效果为零**，这是当前最危险的状态（"机制做完了但没用起来"就是这个症状）。
- arXiv **2610.30755** 已经证明：naive RAG 在四个基准七个设置里赢六次。**你不做这个基线，任何"记忆系统升级"都可能是负收益。**
- 没有 gold evidence，你连 `recall@5` 都算不出来，后面两件事全都无法验收。

**验收**：50 题 × 2 个数（检索 `recall_all@5` / `ndcg_any@5`；回答 LLM-judge 准确率），有 Raw-RAG 对照行。

### 第 2 件：把"只追加"改成"带失效的写入协议 + provenance"

**做什么**（改数据结构，不换存储）
- 每场景私有记忆从纯 markdown 改成 **markdown + 伴生 JSON**：每条记忆 = `{id, text, t_valid, t_invalid|null, source_episode_id, source_path, created_at, confidence, trust_level}`。
- 写入时走 **ADD / UPDATE / DELETE / NOOP** 四选一（可先用规则 + LLM 判定）。
- `§五 只追加` 改为 **`§五 只追加 + 失效标记`**：推翻旧结论时，旧条目加 `~~删除线~~ + [失效 2026-11-10 ← 见 xxx]`，新条目另起。
- `冲突.md` 从"空着"改成**写入时自动登记**：NOOP 判定不了的情况一律进冲突表，不静默丢弃。

**为什么这是第 2 件**
- arXiv **2610.36308** 的实测：过期事实把准确率从 **100% 打到 44.6%**，且"retrieving the correct fact is not enough. An obsolete competing statement can be more harmful than an unrelated piece of evidence of the same size."
- 你的 `§五` 只追加规则**结构性地大量制造过期事实**。这是当前唯一的"架构级错误"，其余都是"缺功能"。
- provenance 是失效级联的前提：源文件变了要能顺着 `source_path` 反向失效。W3C PROV-O 给字段命名，Graphiti 给时态字段。

**验收**：`记忆哨兵` 新增 2 条不变量 —— (INV-6) 每条记忆必须有 `source_path` 且路径 `Test-Path` 为真；(INV-7) `t_invalid` 非空的条目不得出现在默认注入内容里。给两条各配一个**应当失败的反例**（符合 AGENTS.md §4"自证必须是真证"）。

### 第 3 件：把评估从"结构不变量"扩到"检索不变量"，做成第 10 个哨兵

**做什么**
- 新增 `工具\记忆召回哨兵.mjs`，跑第 1 件里的 50 题，输出 `recall_all@5`、`ndcg_any@5`、`recall_all@10`。
- 阈值写死（例如 `recall_all@5 ≥ 0.8`），进 `机制体检.mjs` 的 `GUARDS` 数组（现在 9 个 → 10 个）。
- 同时报 **cost**：本轮注入实际字节数 / token 数。因为 Mem0 和 Memory Tax 的结论都是"收益必须配成本"。
- 检索层和回答层**分开输出**，不合并成总分。

**为什么这是第 3 件**
- 没有它，前两件的改造无法验收，`机制体检` 依然只能告诉你"文件大小没超标"。
- 这是唯一能回答"这个记忆系统比那个好"的装置。指标口径直接抄 LongMemEval 源码（`recall_all@k` / `ndcg_any@k`），不用自己发明。
- 顺带把现在 7/9 的两个失败项（7 个假 `sessionId`、AGENTS.md 被改）修掉——它们会污染任何效果测量的起点。

## 7. 一句话总结

> 你缺的不是更先进的记忆架构，是**一个能证伪的记忆系统该有的三样东西**：可归因的样本、带时态的写入、分离口径的度量。
> 25.6 KB 的记忆不需要检索；零会话的记忆不需要重构；只追加的记忆需要失效。
