## 1. 结论先行

**做法：我们自己建前端工程（Vite + React + TS），把它的 `design-system` 三个包原样 vendor 进来
当基础组件与令牌（MIT 许可，可自由复制修改），外壳、场景、功能、后端全部由我们自己写。**

一句话分工：

```
它给：设计令牌 + 48 个受控组件 + 外壳的几何参数（别人调好的数值）
我们写：应用外壳、场景体系、每一个功能界面、全部后端与业务逻辑
```

许可依据：仓库 `LICENSE` = **MIT License, Copyright (c) 2026 CWing**，
允许 use / copy / modify / merge / publish / sublicense / sell，只需保留版权声明。
`design-system/LICENSE` 同为 MIT。

## 2. 「参考」与「自研」的明确分界

这张表是本文的核心 —— 它决定后面会不会返工。

| 资产 | 归属 | 怎么用 | 依据 |
|---|---|---|---|
| `design-tokens`（令牌 JSON） | **复用** | vendor 进仓，生成我们的 `tokens.css` | 零依赖；纯数据 |
| `theme-openbitfun`（明/暗/高对比主题值） | **复用** | 同上 | 1 个依赖 |
| `ui`（48 个组件 · 372 ts/tsx） | **复用** | 作为本地 workspace 包依赖 | 只 peer 依赖 react/react-dom + lucide-react |
| `ui/flow-chat`（工具卡 / composer / 会话块） | **复用为组件基线** | 用作消息渲染的零件库 | 同上，`./flow-chat` 是公开导出 |
| 外壳几何（216px 导航、45px 工具条、30px 行高、12px 窗口圆角） | **参考数值** | 抄数值，不抄代码 | 从真实编译产物与 SCSS 实测 |
| 分层架构（tokens → reset → base → components → overrides） | **参考模式** | 我们按同一分层组织 | 它自己的 CSS 分层 |
| 场景注册表模式（`registry.ts`：id/label/icon/pinned/closable/singleton） | **参考模式** | 我们写自己的注册表 | 这个模式本身值得借鉴 |
| `app/` 外壳（NavPanel / SceneBar / AppLayout） | **自研** | 我们按参考重写 | 要能长期演进 |
| 每个场景的业务界面与交互 | **自研** | 全部自己写 | 我们的产品不是它的产品 |
| 文案 / i18n / 业务状态 | **自研** | 用我们自己的文案 | 不复制它的产品表述 |
| 全部后端与业务逻辑 | **自研** | 我们已有的 runtime | 与它无关 |

> 判断标准：**「组件/令牌」复用，「页面/流程/业务」自研。**

## 3. 技术栈与工程结构

### 3.1 技术栈（就这几样，不再摇摆）

| 层 | 选型 | 理由 |
|---|---|---|
| 构建 | **Vite 6** | 它自己用的就是 Vite；生态一致、快 |
| 框架 | **React 18 + TypeScript** | `@openbitfun/ui` 的 peer 就是 react>=18.3；用 Vue 会拿不到那 48 个组件 |
| 样式 | **原生 CSS + CSS 变量（分层）** | 它的设计系统就是令牌 + CSS Modules；用 Tailwind 会与它打架 |
| 图标 | **lucide-react** | `@openbitfun/ui` 已依赖，命中同一套图标 |
| 路由 | hash 路由 + 场景注册表 | 桌面壳不需要 URL 服务端路由 |

不引入：Tailwind、UI 框架第二套（antd/arco 之类）、状态库（先用 React 内置 + 少量 store）、
不引入它的 `app/` 业务代码。

## 4. 我们自己的场景与功能（由我们的产品决定，不照抄它的）

它的场景是它的产品（首页/任务看板/会话/Agent/Skills/Insights/Pages/Browser/Mini App…）。
我们的产品核心是 **agent 工作台 + 四态验证**，所以我们的场景清单是：

| # | 场景 | 为什么有它 | 数据来源 |
|---|---|---|---|
| 1 | **会话**（session） | 主线：和 agent 干活 | 我们后端 |
| 2 | **验证中心**（verify） | **我们的差异化**：PASS/WARN/FAIL/UNKNOWN 四态 | 我们已有 `four-state.mjs` / `verify-*.mjs` |
| 3 | **能力**（capabilities） | 技能 / MCP / 工具 / 模型 / 智能体 | 我们后端 + 配置文件 |
| 4 | **场景**（scenes） | 我们自己的概念：一套配置好的工作环境 | 我们后端 |
| 5 | **任务**（tasks） | 派单与定时 | 我们已有调度 |
| 6 | **记忆**（memory） | 跨会话记忆与 TTL | 我们已有 |
| 7 | **设置**（settings） | 模型网关、外观、快捷键 | 本地 |
| 8 | **关于/诊断**（about） | 版本、断线、自检结果 | 本地 |

**排序原则**：先把 1 + 2 做到能用（会话与验证是产品立身之本），其余按需。
不追求一次做满 8 个场景。

## 5. 分阶段计划（每阶段都有可运行验收门，不通过不进下一阶段）

### S0 · 工程骨架跑起来（**先做这个**）

- `apps/agent-ui` 用 Vite + React + TS 起项目
- vendor 三个包进 `design-system/`，配置为本地 workspace 依赖
- 页面里能 `import { Button } from '@openbitfun/ui'` 并渲染出来
- 我们的 `NavPanel` 空壳 + 一行标题

**验收门**
- [ ] `pnpm --dir apps/agent-ui build` 成功
- [ ] 打开页面能看到 `@openbitfun/ui` 的按钮（证明 vendor 成功）
- [ ] `design-system/VENDOR.md` 记录了基线 commit 与许可
- [ ] 装依赖过程写进 `research/依赖与镜像说明.md`（网络间歇性，必须可复现）

> 网络风险最高的一步。npmmirror 时通时不通（实测：unpkg 200 / npmmirror tarball 200 /
> jsdelivr 000），本机有 6.4 万文件 npm 缓存 + pnpm store。S0 必须先把「怎么装得上」固化。

### S1 · 令牌层

- 从 `design-tokens` 生成我们的 `tokens.css`：明 / 暗两套 + compact/cozy 两档密度
- 落地分层：`tokens → reset → base → components → overrides`
- 沿用我们已有的**对比度实测**断言（不是声称）

**验收门**
- [ ] 明暗两套正文/次要/弱化文字对比度实测 ≥ 门槛（沿用 `verify-agent-ui` 的方法）
- [ ] 密度只缩放间距、不改字号（可断言）
- [ ] 无悬空 `var(--x)`

### S2 · 外壳与场景体系

- 外壳三件：`NavPanel`（216px）、`SceneBar`（场景标签）、`Content`
- 场景注册表：`{ id, label, icon, pinned, closable, singleton }`
- hash 路由 + 刷新保持

**验收门**
- [ ] 场景注册表驱动的导航可切换、可关闭、pinned 不乱序
- [ ] 刷新后停留在同一场景
- [ ] 注册表里加一个场景只需改一处（可断言：注册项数 = 渲染项数）

### S3 · 会话场景（主线）

- 消息流：用户 / 助手 / 工具调用 / 工具输出 / 思考 / 用量
- 输入区：多行、快捷键、附件、停止
- 用 `ui/flow-chat` 的组件当零件，但**消息语义与状态机由我们定义**

**验收门**
- [ ] 真发一条消息 → 渲染出一次工具调用与输出
- [ ] 流式/中断/错误三态都有明确视觉（不是只有正常态）
- [ ] 断后端时显示可恢复错误，不是白屏

### S4 · 验证中心（差异化，必须真跑）

- 四态视图：PASS / WARN / FAIL / UNKNOWN，UNKNOWN 必须和 FAIL 分开
- 接我们已有的 `four-state.mjs` 与 `verify-*.mjs` 真实数据
- 「accepted ≠ success」写进界面语义

**验收门**
- [ ] 跑一次真实验收，界面显示的计数与脚本输出一致（可 diff）
- [ ] 判不了的项目显示为 UNKNOWN，不得计入通过
- [ ] 点一条能下钻到证据（文件:行）

### S5 · 能力场景

- 技能 / MCP / 工具 / 模型 / 智能体 五类，接后端
- 开关生效（改完能被后端读到）

**验收门**
- [ ] 五类都有真实条目（不是示例数据）
- [ ] 开关落盘后重启仍在
- [ ] 智能体的技能/MCP 组合可编辑

### S6 · 后端桥与打包

- 前端 ↔ 本地后端：HTTP + 一次性 token，超时与降级明确
- 打包成可运行的桌面壳（先 Windows）

**验收门**
- [ ] token 鉴权生效（无 token 拒绝）
- [ ] 后端不可用时界面可用（只读降级）
- [ ] 打包产物在干净目录能启动

## 7. 风险与前置动作

| 风险 | 影响 | 前置动作 |
|---|---|---|
| **npm 依赖装不上**（间歇性 000） | 真工程起不来，退回单文件 = 重蹈覆辙 | S0 先固化安装方案：镜像列表 + 重试脚本 + 离线缓存；把能装成功的最小命令集写进文档 |
| `@openbitfun/ui` 需要构建（tsdown） | vendor 后 import 不到 | S0 直接验证 import；失败则退化为 vendored 静态 CSS + 按需移植单个组件 |
| 上游版本漂移 | 与我们的代码脱节 | `VENDOR.md` 固定 commit；升级走独立 PR + 全量验收 |
| 只复用组件会「像它」 | 产品辨识度低 | 外壳、场景、会话语义、配色分支由我们定；令牌可覆盖 |
| 我们后端接口未定 | S3/S4 接不上 | S3 之前先定 3 个最小接口：会话流、验证数据、能力列表 |
