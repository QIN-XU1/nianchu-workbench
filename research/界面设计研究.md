# 主流 Agent 界面设计研究

> 用户要求：「整体的界面设计还是需要全方面借鉴当下主流的这些 agent，看看他们是怎么设计的」。
>
> 取证方式三种，全部可复算：
> 1. **本地源码**（hermes 全套、Pi 全套、openclaw、ECC）
> 2. **活体解剖**（我正跑在 DSH 的 Web GUI 里，用 `cordis_inspect_query` 直接读它的实时 Slot 树和主题 token）
> 3. **像素测量**（`prototype/hermes-agents/measure-ui.mjs`，同一算法跑所有截图）

---

## 一、先给结论

主流 agent 的界面设计，本质在回答**同一个问题**：

> **「内核不动，界面怎么长出来？」**

七个系统给出了四种答案：

| 路线 | 代表 | 做法 | 代价 |
|---|---|---|---|
| **A. 语义 token + 类型化 Slot 树** | DSH | 界面整棵树都是具名扩展点，每点标风险等级 | 前期设计重 |
| **B. 组件库 + 环境自适应** | Pi | 自研 TUI 组件库，颜色从终端算，WCAG 硬保证 | 只适合终端 |
| **C. 贡献点注册表** | hermes | contrib 注册 + React 组件 | 变量失控（344 个） |
| **D. 单体页面** | luanyujia / ECC | 直接写页面 | 漂移（24 面板 vs 36） |

**我们的界面 = C（hermes 的路子）。** 所以差距不在"好不好看"，在**语义纪律**：
hermes 有 344 个 CSS 变量，DSH 只有 14 个语义 token。**这是可数的差距。**

## 二、DSH：活体解剖（这是最强的一份证据）

我在 DSH 的 Web GUI 里用 `cordis_inspect_query(platform=client, provider=Slots)` 直接读了它的实时 UI 树。这是别人拿不到的证据 —— 不是看图猜，是读运行时的类型化结构。

### 2.1 整棵树都是具名 Slot

```
root                                    ← 唯一的渲染根
├── main (keyed by 侧栏入口 id)         ← "Central panel selected by sidebar entry id"
│   ├── main.conversation
│   │   ├── conversation.header
│   │   │   └── conversation.session.header
│   │   │       ├── .utilities (list)   ← 右对齐工具
│   │   │       ├── .actions (list)     ← 标题旁动作，溢出裁剪+淡出
│   │   │       ├── .corner (single)
│   │   │       └── .lineage (single)
│   │   ├── conversation.chat.flow
│   │   │   └── conversation.chat.node (keyed by ChatNodeKind)
│   │   │       └── tool.call.toolview (keyed by 工具 wire name)
│   │   └── conversation.composer.bar
│   │       ├── conversation.input.overlay / .attachments / .permission
│   │       ├── conversation.input.left / .plan / .right / .model / .activity
│   │       └── conversation.composer.dock
│   ├── conversation.hero.brand.mark     ← 空态！有专门的扩展点
│   ├── conversation.hero.agentPreset
│   └── conversation.hero.options
├── shell.overlay                        ← 全框浮层
│   ├── contextMenu.content / .icon
│   ├── shell.quota-notice (chain)
│   └── workspace.toast (keyed)
└── sidebar
    ├── sidebar.brand.mark
    ├── sidebar.footer.action (list)
    └── sidebar.panellist.actions
```

### 2.2 五种 Slot 类型，语义各不相同

| 类型 | 语义 | 例子 |
|---|---|---|
| `single` | 只能有一个占用者 | `conversation.header` |
| `list` | 有序多个，靠 `order` 排序 | `conversation.input.left` |
| `keyed` | 按 key 分派 | `conversation.chat.node`（18 种节点） |
| `chain` | 由 `select` 决定的覆盖链 | `shell.quota-notice` |
| `hoc` | 包裹宿主内容 | `conversation.chat.markdown.fence`（diff/math/patch） |

**这五种类型覆盖了 UI 扩展的全部形态。** 我们只有一种（contrib 注册），所以只能"加东西"，不能"换/包/接管"。

### 2.3 每个 Slot 自带 `replaceRisk`

这是我最想抄的一个设计 —— **每个扩展点自己声明替换风险**：

- `none` —— 纯追加，安全
- `shadows-shipped-ui` —— 会**盖住**官方 UI（危险，需自知）
- `wraps-owner-content` —— **包裹**宿主内容（可能破坏布局）

配合 `purpose` 字段写清楚"这个点在版面哪里、溢出怎么处理"。例如：

> `conversation.session.header.actions`：**"overflow is clipped and faded before the utilities, so overlays must portal."**

—— 连"你得 portal 出去不然会被裁掉"这种坑都写进了类型描述里。

**这是把「界面契约」写成了机器可读的文档。** 我们没有任何等价物。

### 2.4 聊天节点是 18 种类型的联合

`conversation.chat.node` 的 keyDomain 明确列出：

```
assistant-step, command, command-input, compaction, context,
manual-compaction, model-retry, question-reply, steering,
system-prompt, tool-call, turn-error, turn-max-tokens,
turn-process, turn-tail, turn-trigger, unknown, user, workflow-run
```

**一个 agent 的对话流里到底有几种"东西"，这里给了完整答案。** 不是"消息"一种，
而是 18 种 —— 压缩、重试、转向、超 token、触发……每种都有自己的渲染器。

我们（hermes）的 transcript 也有类型，但没有这种**显式枚举的可扩展性**。

### 2.5 主题：只有 14 个语义 token，且强制明暗成对

```
--dsw-alias-bg-base / bg-layer-1 / bg-layer-2 / bg-overlay
--dsw-alias-border-l1 / border-l2
--dsw-alias-brand-primary
--dsw-alias-label-primary / label-secondary
--dsw-alias-state-error-primary / idle / success / warn
--dsw-specific-sidebar-fill
```

全部 `requiresLightAndDark: true`。**没有暴露任何一个原始色值。**

对比 **hermes：17 个 CSS 文件里有 344 个唯一变量**，包括：

```
--arc-angle, --arc-c0, --arc-c1, --arc-radius, --arc-standoff, --arc-width
--bb-bg, --bb-dot, --bb-dot-active, --bb-edge, --bb-fg, --bb-hover, --bb-link, --bb-mix
--capabilities-gap-controls, --capabilities-gap-heading
--backdrop-invert-mul
```

`--arc-c0/1/2`、`--bb-*` 这类是**某个组件的一次性变量**，直接写进全局命名空间。
**这就是"设计欠缺"的量化证据：不是审美问题，是层缺失 —— 没有语义层，组件各自造词。**

## 三、Pi：把设计约束变成代码

Pi 的 UI 全在 TUI（`packages/tui`，46 文件 / 20,061 行）。三个可直接抄的硬规则：

### 3.1 宽度按可见列算，不按字符串长度

> Measure **visible terminal columns** rather than string length because ANSI escapes,
> **wide characters, emoji, and combining characters** change display width.

对中文界面是致命的：一个汉字 2 列，按 `str.length` 排版必然错位。

### 3.2 焦点不传播，中文输入法候选框会跑到错的位置

> Containers that wrap an `Input` or `Editor` must **propagate their `focused` state** to that child.
> Without propagation, **Chinese, Japanese, Korean, and other IME candidate windows
> can appear at the wrong screen position.**

### 3.3 对比度是算出来的保证

`system` 主题（默认）：查终端前景/背景 + 16 ANSI 色 → **每个颜色取色相，亮度按最小对比度反算**：

> Body text keeps at least a **4.5:1 WCAG** contrast ratio on the background and **every panel**.

并且有三级降级表（背景+ANSI / 只有背景 / 什么都没有），启动最多等 100ms，超时回退。

### 3.4 组件库的布局原语和 Web 同构

`Container / VStack / HStack / Box / Spacer` + `Text / Markdown / Image / TruncatedText` +
`Input / Editor` + `SelectList / SettingsList` + `ScrollView` + `Loader` + `MouseRegion`。

`editor.ts` **82.7KB**、`markdown.ts` **39.7KB** —— 单文件体量不小，但那是**一个通用编辑器**，
不是"一个页面"。这是合理的集中。

## 四、像素测量：主流 agent 的实际密度

同一套算法（`measure-ui.mjs`）跑所有截图，归一化到 1400px 宽：

| 界面 | 面板 | 文字块 | 密度% | 留白% | 分区 |
|---|---|---|---|---|---|
| Claude 首页 | 12 | 225 | 13.88 | 86.12 | 10 |
| Claude 对话 | 11 | 290 | 7.70 | 92.30 | 22 |
| DeepSeek 对话 | 9 | 310 | 7.89 | 92.11 | 21 |
| **hermes 聊天页（我们）** | 4 | **124** | **2.66** | **97.34** | 10 |
| **hermes 命令中心（我们）** | — | 42 | — | — | — |
| **hermes 设置页（我们）** | — | 90 块 / 154 按钮 | — | — | — |
| **hermes 星图（我们）** | 4 | **451** | **17.34** | 82.66 | 1 |

### 读法（不美化）

**赢的**：星图 451 文字块 / 17.34% 密度，是所有图里最高的。

**输的**：**聊天页 124 文字块 / 2.66% 密度**，不到 Claude 首页（225/13.88%）的一半，是 DeepSeek 对话页（310/7.89%）的 40%。

原因很具体 —— 看截图：聊天空态只有一个**超大 serif 字标 "HERMES AGENT" + 一行副标题**，
中间全是空白。而 Claude/ChatGPT 的空态有：问候语 + 建议卡片 + 能力提示 + 最近项。

**命令中心更空**：左导航 + 面包屑 + 搜索框，主区只有一行 "Getting started"。

## 五、七个可判定的设计决定（横向对比）

| # | 设计决定 | DSH | Pi | hermes（我们） | ChatGPT/Claude |
|---|---|---|---|---|---|
| 1 | **主题层数** | 14 语义 token | 计算生成 | **344 个混合变量** | 语义 token |
| 2 | **扩展点类型** | 5 种（single/list/keyed/chain/hoc） | 组件组合 | 1 种（contrib） | 无（闭源） |
| 3 | **扩展点风险标注** | ✅ 每点 `replaceRisk` | — | ❌ | — |
| 4 | **对话节点类型化** | ✅ 18 种 keyed | 事件流 | 部分 | 部分 |
| 5 | **空态设计** | ✅ 专门 `conversation.hero.*` slot | loader/widget | ❌ **只有字标** | ✅ 建议卡 |
| 6 | **中文宽度/IME** | — | ✅ 明确处理 | ❓ 未验证 | — |
| 7 | **对比度保证** | ✅ 强制明暗成对 | ✅ WCAG 4.5:1 反算 | ❌ | ✅ |

**七项里我们明确输 4 项（1/3/5/7），部分输 2 项（2/4）。**

## 六、落地：按性价比排序的改法

### P0：空态加可点入口（投入最小，收益最大）

**问题**：聊天页 2.66% 密度，主区一大片空白，`intro.tsx` 整个是 `pointer-events-none` 的死文本。

**主流怎么做**：ChatGPT 的建议卡片、Claude 的能力提示、DSH 的 `conversation.hero.*` slot。

**我们的优势**：我们有 **12 个场景**（名字 + 领域 + 简介），这是别人没有的内容资产。
直接把场景变成空态的可点入口 —— 点一下就填入对应任务。

**这是"借鉴主流形态 + 用我们自己的内容"**，不是照搬。

### P1：给主题补语义层

**问题**：344 个变量，组件各自造词（`--arc-c0`、`--bb-dot-active`）。

**改法**：DSH 的做法 —— 定义 14~20 个语义 token，组件只能用语义 token；
现有 344 个变量逐步收敛为「语义 token 的组合」。
一次性成本高，但这是**唯一能止住漂移的办法**（我们批评 ECC 漂移，自己界面也在漂）。

### P2：扩展点加风险标注

**问题**：contrib 只能"加"，不能声明"我盖住了什么"。

**改法**：抄 DSH 的 `replaceRisk`（none / shadows-shipped-ui / wraps-owner-content）+
`purpose` 写清楚版面位置和溢出行为。

### P3：中文宽度与 IME

**改法**：`Intl.Segmenter` 或 canvas `measureText` 算显示宽度；容器必须把 `focused` 往下传。

### P4：对比度工具

**改法**：写 `ensureContrast(fg, bg, 4.5)`，主题色一律过它。参考 Pi 的「取色相 + 反算亮度」。

## 七、诚实的局限

1. **只量了 3 个外部产品的截图**（Claude 首页/对话、DeepSeek 对话）。ChatGPT、Cursor、openclaw 的实际界面没有抓到本地截图。
2. **DSH 的证据是活体结构，不是视觉**。我知道它的 Slot 树和 token 名，但没量它的像素密度。
3. **像素指标是代理量**，高密度不等于好用。只用它做横向可比，不当"更好"的证据。
4. **hermes 的 344 个变量不全是坏的** —— 有些是动画参数（`--arc-duration`），那本该是变量。
   但 `--arc-c0/1/2` 这种"第几个颜色"确实是缺语义层。
