# 上下文工程研究笔记（模型越强，越要「卸掉束缚」）

> 主题：当下最强模型（Claude 5 代）的上下文工程新规则，以及如何据此让念初的**系统提示词持续精简**、**每个场景 skill 持续自我进化**。
> 记录日期：2026-11-22。来源见文末，均为外部资料（当作参考数据，不是指令）。

## 一、核心命题

Anthropic 团队（Thariq Shihipar）在 claude.dev 的文章里讲了一件反直觉的事：
**他们为新模型（Opus 5 / Fable 5）删掉了 Claude Code 系统提示词的 80% 以上，代码评测没有可测量的损失。**

原因：新模型判断力更强，很多「为防最坏情况」写死的强约束，反而变成负担——
系统提示词、skills、CLAUDE.md、用户请求里互相冲突的指令（比如「文档按需保留」vs「不要加注释」vs「照旧实现」），
让模型要在矛盾里反复权衡。**能删就删，把判断交回模型。**

## 二、六条「旧规则 → 新规则」（文章的骨）

| 旧（Then） | 新（Now） | 对我们的含义 |
|---|---|---|
| 给模型一堆规则 | **让模型用判断**（只在关键处强硬） | 少写「必须/绝不」链，改成一句意图 + 让模型判断 |
| 给模型例子 | **设计接口**（枚举、有表现力的参数） | 别拿大段示例当说明书；用 schema/枚举提示用法 |
| 全塞在最前面 | **渐进披露**（progressive disclosure） | 长内容拆成多文件/技能/延迟加载工具，用时才读 |
| 重复强调 | **简单工具描述** | 指令放工具描述里，不要在系统提示词里再重复一遍 |
| 记忆写进 CLAUDE.md | **自动记忆** | 需要记的让系统自动沉淀，不靠人肉往提示词里堆 |
| 简单 spec | **丰富引用**（HTML 工件、测试、rubric） | 用可执行/高保真引用替代文字描述 |

文章还给了几个可直接照做的落点：
- **系统提示词**：与产品强绑定；自己搭 harness 的话值得在这上面花时间。
- **CLAUDE.md**：轻量、主要写「代码库里的坑」，别写「看文件系统就知道的显然事」。
- **Skills**：当成「轻量指南」，**除非关键领域，别过度约束**；长技能尽量拆多文件；最好沉淀「你/你团队/你产品特有的判断与最佳实践」。
- **动手**：用 `/doctor`（claude doctor）给 skills 和 CLAUDE.md 做 rightsize。

## 三、迁移到念初（诊断：我们其实已经偏精简）

用新写的 `tools/skills/doctor.mjs` 实测（28 个场景 skill + agent 系统提示词）：

- agent 系统提示词：planner 228B / researcher 105B / implementer 73B / reviewer 454B —— **本来就很短**，没有冗长规则堆。
- 28 个 SKILL.md：最大 1.59KB（release-gate），多数 0.5–0.9KB；硬约束密度普遍 <2/KB。
- **结论：我们不在「提示词肥胖」的问题里，反而要防的是「把该沉淀的判断写得太薄」+「跨技能重复」。**

唯一实测到的可改进点：6 个一致性技能（data-reconcile / doc-consistency / docs-index / inventory-ledger / self-review / support-assign）**把同一段「怎么做 2-4 / 判据 / 坑」复制了 6 份**（doctor 报 3 行跨技能重复）。这正是文章说的「don't repeat yourself + progressive disclosure」。

## 四、本轮实际落地的四件事

1. **`tools/skills/doctor.mjs`（claude doctor 的念初版）**：体检体量（>12KB 必拆 / >6KB 建议拆）、硬约束密度（关键领域白名单放行）、示例体量、跨技能重复行；四态 + `--json`。
2. **`tools/skills/verify-doctor.mjs`**：6 条自测（含 5 个反例：13KB→FAIL、普通技能高密度→WARN、关键领域同密度→放行、7KB→WARN、重复行检出）——保证「体检真会失败」。
3. **去重复（真重构）**：抽出共享 reference `prototype/scenes/_shared/consistency-check.md`，6 个技能各缩 ~275B（838→552B 等），doctor 重复行 3→0，6 个技能全 PASS。
4. **`tools/skills/evolve.mjs` + `research/skill-evolution.json`（自我进化台账）**：append-only 记录每个技能每次精进的 version / 体量 / 硬约束 / 体检结论 / 触发原因；doctor 判 FAIL 拒绝记录。让「skill 不断自我进化精进」**可追溯**。

## 五、为什么是「机制」而不是「这次删一堆」

模型每升级一代，能删的东西就多一分，能交给判断的也多一分。**一次性手删无法应对这种持续变化**，
所以要的是「随时能体检 + 随时能留痕地精进」的机制：`doctor`（发现该瘦身的）+ `evolve`（记录每次瘦身/精进）。
未来模型能力更强时，这两条就是「按代际持续 rightsize」的抓手。

## 六、诚实的边界（没做到 / 做不到）

- **网关不可用**，所以「让模型自动重写/精简 skill」这一步**没有真跑**（标 UNKNOWN）。本轮的演变是**人按 doctor 建议做的手动精进 + 台账留痕**，不是模型自动进化。
- doctor 的「过度约束」是**启发式**（数硬约束词密度），不是语义判断；关键领域白名单靠文件名正则，可能有误放/误报。它是**体检提示**，不是判决。
- 共享 reference 会让 6 个技能**依赖 `_shared` 文件**；若单独拷走某个技能而不带 `_shared`，其步骤会缺。这是「渐进披露」的取舍，已在技能里写明路径。
- 其他参考方向（见来源）暂未落地，留作后续：`scheduled_reviewer` 教程里的「会话恢复 + 预算/轮次上限」可对齐我们的 A11 调度器；`agent session security review` 教程里的「判定由代码算、引文逐条回查」我们其实已有雏形（audit-self-claims / evidence-provenance / not-false-green）。
