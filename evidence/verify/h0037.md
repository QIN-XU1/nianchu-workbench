## 硬伤

### 硬伤 1（致命）：`ABSENT 单文件体量红线` 是假阴性 —— 对方确实有

工具输出（`node tools/benchmark/absence-check.mjs`，实测）：

```
  ABSENT  单文件体量红线（超阈值即失败）
           范围：src + scripts + packages · 33280 个源文件
           依据：（若零命中才用）排除产物类后，未见源码单文件体量阈值
```

**openclaw 有这条红线，而且是 error 级、会挂 lint：**

`D:/refs/openclaw/openclaw-main/.oxlintrc.json:414`
```json
"max-lines": ["error", { "max": 700, "skipBlankLines": true, "skipComments": true }]
```
同类规则另有 6 处：`:436`(700) `:458`(800) `:479`(1000) `:486`(3736) `:492`(950) `:498`(1200)。

**而且它真的在生效**（不是写了不用）—— 源码里成片出现豁免注释：

```
src/agents/auth-profiles/store.ts:771            /* oxlint-disable max-lines -- TODO: split this grandfathered oversized file. */
src/agents/agent-hooks/compaction-safeguard.ts:3 /* oxlint-disable max-lines -- ... */
src/agents/auth-profiles/oauth-manager.ts:988    /* oxlint-disable max-lines -- ... */
src/agents/cli-runner/prepare.ts:1709            /* oxlint-disable max-lines -- ... */
```
`store.ts` 实测 **1724 行**，远超 700 —— 必须写豁免才过。豁免注释的存在本身证明规则在跑。

**为什么漏了（两处盲区叠加，都在代码里）：**

1. `absence-check.mjs:96` —— 文件白名单只有 `/\.(ts|tsx|js|mjs|cjs)$/`，**`.json` 根本不收集**
2. `absence-check.mjs:69` —— `dirs: ['src','scripts','packages']`，而 `.oxlintrc.json` 在**仓库根目录**，不在范围内

于是「扫了 33280 个文件」这个看起来很硬的数字，恰好绕过了唯一写规则的地方。**这正是文件头 `:17-23` 自己警告的失败模式，只不过这次栽在文件类型和根目录上，不是关键词上。**

### 硬伤 2：`ABSENT 记忆冲突状态` 是范围产物 —— 换个目录就 PRESENT

工具 `why` 写：「openclaw 的 knowledge-correct 用 SKILL.md 提示词描述纠正流程，**代码层无冲突状态机**」。

这是对**整个系统**的断言，但只搜了 `extensions/memory-core`。用工具**自己的 hit 正则**（`/\b(conflictGroup|supersededBy|CONFLICTED|contradict(?:ion|ory)?)\b/i`），只把 `dirs` 换成 `extensions/knowledge/src`：

```
  extensions/knowledge/src/chronicle.ts:61            ...(replacement && visible.has(replacement) ? { supersededBy: replacement } : {}),
  extensions/knowledge/src/contract.ts:375            "Agent-only explicit correction of an exact claim or typed relationship..."
  extensions/knowledge/src/record-view.ts:212         const supersededBy = meta?.superseded_by;
```

再核代码层状态机（直接读文件）：

```

extensions/knowledge/src/claim-view.ts:165 record.metadata.continuity.some((link) => link.relation === "contradicts") ? "Conflicting account"
```

`correct` / `supersede` 是**代码层动作**（contract.ts:372/388），`contradicts` 是**关系类型**，`supersededBy` 是**持久化字段**。这不是「SKILL.md 提示词」，是代码层状态机。**`why` 那句话是错的。**

讽刺的是，文件头 `:20` 原话就是：「加上 knowledge/src 范围后 → 命中 expires_at + valid_until ⇒ 它其实有」—— 同一条记忆，同一个 `knowledge/src`，**mem-ttl 改了范围，mem-conflict 没改**。4 次误判的教训只被吸收了一半。

### 硬伤 3：工具无法区分「真缺位」和「关键词写错」，而自检没钉住

构造反例（实测，只 import 不写盘）：


T2 就是「关键词写错」的最小复现：目录对、文件扫了 19 个、能力真实存在、**输出 ABSENT**。工具输出里没有任何字段能让人区分 T2 和真缺位 —— `why` 都写「指定范围内零命中」。

## 一句话结论

工具本身是能跑的、可复跑的、带行号的 —— 这部分是真的。但它**报的 2 项 ABSENT 没有一项站得住**：一项（体量红线）因文件类型白名单和根目录盲区漏掉了真实存在的 CI 红线，另一项（记忆冲突）纯因范围选错，同一条正则换到 `knowledge/src` 就是 17 命中 PRESENT。再叠上 `after=2` 与实际 3 项不符、`samples=8` 无口径且恰为门槛值、reopen 理由的核心事实（「5 条扩到 5 条」）经 git 历史证伪 —— **H-0037 作为「能力缺位检查可复跑且可信」的主张，refuted**。

真正的问题不是这个工具写得差，而是它**输出的权威感远超它的判据强度**：`ABSENT` 一个词，读起来是「查过了，没有」，实际是「我在我自己选的范围里、用我自己选的关键词、没找到」。这两者之间的差距，正是它文件头警告过 4 次的那个坑 —— 只是这次，坑在工具自己的输出里。
