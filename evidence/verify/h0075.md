## 硬伤

**H-0075-A｜归因错位：把 `git checkout` 的功劳记在守卫头上（最严重）**

- commit `2735a182` 的 stat 只有 `tools/benchmark/check-matrix-integrity.mjs | 149 ++++`，**1 file changed**。
- 同一 commit 正文：> 「**`git checkout` 恢复后：4 组 31 维**，可核验 22 / 借力 8 / 都没有 0 / 声明无 1」
- `verify-goal.mjs:227-237`：R2 跑 `render-matrix.mjs --check`，维度数从它的 stdout 正则取（`:229`），**与守卫无调用关系**。
- 全仓库 grep 守卫名 → **0 引用**。
⇒ 「基线 16 → 改后 18」的真实原因是**数据文件被恢复**；守卫是事故后加的**并行产物**，对度量贡献为 0。台账 `delta: 2 / moved: true / verdict: keep` 把二者混成一条因果。

**H-0075-B｜核心主张「能区分开」不成立**

守卫的判据只有四条形状：组数、维度数、id 唯一、us 二元组（`:53-65`）。「文件被写坏」与「矩阵真没做完」在这四条上**给出逐字相同的 FAIL 输出**。守卫**不读 git、不比对基线、不比对历史版本**，因此没有任何可用于区分的信息源。它做的是「形状告警」，不是「原因判定」。台账 hypo 里「可与『矩阵真没做完』区分开」这句**被证伪**。
顺带：`us` 二元组检查在**真实使用过的突变形态**上失效（E1：`['有','']` → PASS），所以连「守卫覆盖了 us」这个说法在语义层面也只是长度检查。

**H-0075-C｜根因叙述与代码不符，且未被要求给证据**

- 「10 个工具」→ 实测 **4 个写该文件的代码路径**（A/D1）。
- 「measure-real-recall 临时改写再恢复」→ 恢复逻辑真实存在（`finally` `:363-365`），但它的矩阵突变是 `dim.us=['有']`（`:187-190`），**不可能**产出「1 组 16 维、id/name 全没」。
- 台账走的是 `record()`（`evolve.mjs:107`），**不要求 evidence**（`attest` 才要求，`:206,:259`），所以「根因已查明」这句话**从未被任何机制强制举证**。
⇒ 根因是**推测**，台账**未标注为推测**（只标注了 C5 自验自）。

**H-0075-D｜覆盖面被夸大（E 组的结论）**

守卫拦得住「塌陷」，拦不住「污染」。漏报实测：证据清空、状态静默降级 `有→无`、假证据、改 name、组内乱序 —— **6/6 全 PASS**。而仓库里**真实用过**的突变形态（`tools/_attest1.py:11` 的 `us=['有','']`）正是漏报之一。若台账要表述为「防止文件被写坏」，覆盖面应缩为「**防止结构塌陷**」；「污染」这一大类它一格都没覆盖。
